# Bezel: Design Rationale

**Companion to the Bezel Language Specification, v0.217 — July 2026**

The spec describes the language. This document explains the choices that aren't obvious from reading the spec — places where Bezel diverges from its inheritance, places where two reasonable designs were possible and we picked one, and places where the spec's stated rule has a less-stated rule behind it.

This document is not exhaustive. Decisions that follow Pascal/C#/Rust convention without modification (`:=` for assignment, word keywords for boolean operators, non-virtual by default, `case` for pattern matching) are not discussed; the precedent is the rationale.

<a id="sec-the-big-picture"></a>
## 1. The big picture

Bezel is a compiled language for services and tools, with ownership-based memory management and no GC. It tries to feel high-level while delivering three things at once: performance you can predict (no garbage collector, no surprise allocations), modern concurrency (async/await with structured cancellation), and a type system that catches mistakes before the program runs (non-nullable types, exhaustive `case`, generics with variance).

Stated as goals, those three are not rare — most modern languages promise some version of each, and Rust genuinely delivers all three. What defines Bezel is the constraint it adds on how they are achieved: the memory rules must stay few enough to learn in full and cheap enough to apply everywhere. Rust pays for its guarantees with a compile-time discipline famous for its learning curve; garbage-collected languages pay by giving up predictable performance. Bezel bets that between those two prices there is a third worth paying — a deliberately small ownership discipline that catches most memory mistakes at compile time and the remainder at run time.

The weight of that bet lands in one place: the memory model. This is where Bezel's most interesting decision lives, and the clearest way to see it is next to Rust, the language Bezel is closest to here.

Rust keeps memory safe with its borrow checker — at compile time it allows either many readers of a value or a single writer, but never both at once, and that single rule eliminates entire families of bugs. It is a genuine guarantee, and it asks a genuine price: the rule takes real effort to learn, and it turns away many programs that would have been perfectly correct. Bezel takes a gentler path to the same destination. It keeps what matters most for a systems language — no garbage collector, with ownership written down plainly through `owned` references and `using var` — but it asks less of its compile-time checker than Rust does. The checker still follows who owns what and where borrowed references are allowed to travel ([§28.3](Bezel_Language_Spec.md#sec-local-variables-ownership-and-borrows) of the spec), so most lifetime and leak mistakes are still caught before the program runs; it simply doesn't enforce the reader-or-writer rule. The exchange is deliberate and modest: a small number of errors Rust would have caught at compile time instead show up at run time, and in return the ownership model stays simple enough to keep entirely in your head. Most of this document is that same kind of exchange, considered carefully and made again at smaller scale.

Where Bezel looks familiar, it usually is. A great deal of the syntax and many of the type-system ideas come straight from C#, which is the closest relative for nearly everything *except* the memory model. The chapters that follow are mostly about the places where Bezel leaves that inheritance behind, and the reasons each departure seemed worth making.

<a id="sec-modules-and-files"></a>
## 2. Modules and files

<a id="sec-dotted-module-names-are-one-name"></a>
### 2.1 Dotted module names are one name

`module Foo.Bar.Baz;` declares one module. The dots are punctuation in the name. `Foo.Bar` and `Foo.Bar.Baz` are unrelated modules, with no implicit visibility between them.

The alternative — nested names that relate to each other, as C# namespaces do — is a reliable source of confusion, because the relationship is weaker than the syntax suggests. In C#, code inside `Foo.Bar.Baz` can name types from `Foo.Bar` without qualification, and that lexical convenience trains programmers to read the dots as a containment hierarchy — so they assume `internal` scopes to the namespace (it scopes to the whole assembly, ignoring namespaces entirely) and that `using Foo` imports `Foo.Bar`'s types (it does not). The hierarchy the dots suggest is not one any visibility or import rule actually follows. Bezel removes the suggestion: the dots are spelling, and the obvious reading — no relationship — is the correct one.

The cost: no sub-package privacy. Use `internal` and put related code in the same module.

<a id="sec-no-top-level-functions-or-fields"></a>
### 2.2 No top-level functions or fields

Every method, field, and constant lives inside a class, record, or enum. Classes already group code and own static state; a parallel module-level grouping mechanism doubles the surface area without solving anything. A `public static class` of static methods is the entry point for what other languages call free functions.

Extension blocks are the one exception. They live at module level because their identity is the type they extend, not a surrounding class.

<a id="sec-syntax"></a>
## 3. Syntax

Most syntax follows Pascal/Modula-2 conventions; the precedent is the rationale. The choices that needed more than precedent are recorded below.

<a id="sec-always-semicolons"></a>
### 3.1 Always semicolons

Pascal famously had places where a semicolon was wrong — typically before `else` — and places where it was required, with the rule depending on what came next. The Ada designers fixed this by making semicolons unconditional: every statement ends with `;`, every block ends with `end;`, no exceptions.

Bezel follows the Ada rule. The rule is "always put a semicolon," which is impossible to get wrong by accident. The cost is occasional visual noise; the benefit is one fewer thing to remember.

<a id="sec-the-discard-_"></a>
### 3.2 The discard `_`

`_` works as in C# in all three of its positions: wildcard in patterns, discard for `out` arguments, and the expression-statement form `_ := expression;` (C# spells it `_ = expression;`), which evaluates `expression` and throws the result away. What Bezel changes is not the form but the weight it carries.

In C#, discarding a result is the default — an expression statement drops its value silently, so `_ = ...` is optional documentation of intent (most visibly for a deliberately-unawaited task). Bezel warns on every expression statement that discards a non-`()` result (spec §21.9), so the discard is the sanctioned opt-out: without it, a programmer who means to drop a value must either declare a throwaway local (which trips the unused-variable warning) or live with the discarded-result warning (which trains them to ignore warnings). The discard keeps the deliberate case syntactically distinct from the accidental one.

Ownership gives the same form a second job: applied to a named owned binding, `_ := x;` is an announced consume — the explicit "dispose this now" spelling, standing beside `throw x` and `owned` returns in the announced-kill family ([§5.23](#sec-the-affine-model); spec §28.3). And one result type stays out of the discard's reach entirely: dropping a `Task` is a hard error, not a warning, because abandoning a running operation is a semantic decision — that case is routed to `Task.FireAndForget`.

`_` is a sink, not a binding. It cannot be read.

<a id="sec-the-value-position-conditional"></a>
### 3.3 The value-position conditional is condition-first and paren-delimited (`(if c then a else b)`)

The expression form of selection is the parenthesized, condition-first atom — `(if c then a elif c2 then b else fallback)` — the same word order as the statement form, with the atom's parentheses as its delimiters and no `end` (spec §20, v0.208; proposal 0057). The form's history is a genuine reversal, recorded as one: through v0.207 the expression form was Python's postfix conditional (`value if condition else fallback`), a deliberate word-order split re-examined and confirmed in 2026-07 (issue #1373) on the strength of the value-first reading for the default-with-override idiom. The v0.208 re-weighing — by the same decider — overturned that preference: one selection word order across the language retires the asymmetry's erratum class (#748); first-class `elif` replaces the postfix form's right-nested chaining; the branches of a delimited atom derive full expressions, dissolving the v0.182 true-branch `throw` parse trap and the conditional's precedence entry outright; and the value-first idiom's strongest case keeps `??` for the nullable default, with the boolean-conditioned default now reading condition-first — a real, accepted residual cost. What made the reversal available rather than a re-ask was the delimiter design: the #1373-era condition-first candidate was `if c then a else b end`, declined for `end`-noise inside nested expressions; the paren-delimited atom adopts the statement's word order while deleting exactly that cost.

The atom's parentheses earn their keep three ways: `(` + `if` commits the parse at the second token; the delimiters make dangling-`else` and extent-by-precedence questions unaskable; and the form composes in any operand position like the `(case …)`/`(when …)` atoms. The recorded ergonomic cost: in call- and index-argument position the atom supplies its own pair inside the argument list's (`f((if c then a else b))`).

Alternatives declined: the postfix form (retired v0.208, above — reopening it requires new evidence against this section's reasons, per the standing discipline); `if c then a else b end` (the end-noise objection stands; the adopted form is its repair); C's `c ? a : b` (two more sigils in a language that spells `and`/`or`/`not` as words); the bare unparenthesized `if c then a else b` (statement-position prefix collision with the statement form, dangling-`else` under nesting).

<a id="sec-compound-assignment-spelling"></a>
### 3.4 Compound assignment keeps the C spellings

Assignment is `:=` and equality is `=` (the Pascal family), yet compound assignment uses the C-family spellings `+=`, `-=`, `*=`, `/=`, `&=`, `|=`, `^=`, `<<=`, `>>=`, `??=`. The Pascal-pure alternative (`+:=` and friends) has no precedent in any language programmers arrive from; omitting compound assignment entirely (the Ada position) buys no safety and gives up the evaluate-the-target-once guarantee the compound forms carry (spec §6.6) — the expanded `x := x + 1` spelling evaluates its target expression twice. Familiarity won over purity; the cost is aesthetic only. Nor is there ambiguity to pay: the compound forms exist only in statement position, where an equality expression cannot begin.

<a id="sec-arrow-body-family"></a>
### 3.5 The `=>` body family: one addition, three recorded divergences

v0.160 gives unit-returning methods the assignment arrow (`method SetX(v: int) => _x := v;`) that accessors always had — the two contexts are the same declaration shape, and the asymmetry had no recorded reason (review finding #1345). The **remaining** divergences are deliberate, with reasons:

- **Lambdas** do not take a bare-statement body: a statement's mandatory `;` collides with expression position (`Apply(lambda(x) => _total := x;, 5)` puts the arm form's `;,` seam inside an argument list; `var f := lambda(x) => _total := x;;` doubles the terminator). Multi-statement lambdas use `=> do … end`.
- **Operators** are expression-only: an operator must produce a value; a statement form could never typecheck.
- **Methods and constructors** have no `=> do … end` form: both already have the lighter bare-block body (`… end Name;`), so the arrow-block would be a second spelling of the same thing (declined for methods as far back as v0.84).

<a id="sec-destructor-takes-no-parens"></a>
### 3.6 `destructor` takes no parameter list

`constructor()` carries parens because parameters may follow — the parens are the parameter list, present even when empty for uniformity across constructors. A destructor can never take parameters (it is invoked by the compiler-generated `Dispose()`, §28.4), so a mandatory empty `()` would be pure ceremony attached to nothing. The asymmetry is intentional (confirmed 2026-07, review finding #1343): `destructor` is a keyword-introduced block like `try` or `extension`, not a callable signature. (The §1.6 closer taxonomy already treats `constructor`/`destructor`/`operator` as one keyword-labeled family.)

<a id="sec-case-scrutinee-of-delimiter"></a>
### 3.7 The `case` scrutinee is delimited by `of`

Adopted v0.166 (#1370). Through v0.165 nothing separated the scrutinee from the first arm's pattern, and since patterns may begin with `-` (a negative range bound), `..`, `..<`, or a relational token, the scrutinee had to parse at a restricted precedence level — multiplicative and postfix only, with a mandatory-parenthesization rule for anything lower (`case (x - 1)`). The restriction served no semantic purpose; it existed to substitute for the missing boundary, surprised users whose scrutinee was a perfectly ordinary arithmetic expression, and required a normative paragraph (and issues #1320 and #1233) to keep the rule honest.

`of` supplies the boundary explicitly: `case score of 90..100 => …`. The scrutinee becomes a full `Expression` with no restriction; the leading-pattern-token ambiguity vanishes by construction rather than by precedence surgery; and the spelling is the language's declared §3 Pascal heritage verbatim (`case x of` is Pascal's form). One extra keyword-token per case was weighed against the removed restriction, the removed parens rule, and the removed parser delicacy, and judged the better trade at every scale of program. `when` (the scrutinee-less sibling) takes no delimiter — there is nothing to delimit. Alternatives declined: a colon (`case x:`) reads as a type annotation; a mandatory newline resurrects layout-sensitivity, which #744 deliberately removed from this construct family.

<a id="sec-pattern-alternatives-pipe"></a>
### 3.8 Pattern alternatives are spelled `|`

Adopted v0.167 (#1371). Through v0.166 the comma did triple duty in pattern context — arm separator, alternative separator (`1, 2 => "low"`), and positional-slot separator — disambiguated only by scanning ahead for `=>`. Three consequences followed: alternatives had to be banned inside positional destructure slots (the #1300 fix), `catch` grew its own comma-based multi-type list that read differently from case alternatives (#1341), and every tool that parses patterns needed the lookahead.

`|` gives alternatives their own spelling: `1 | 2 => "low"`, `FormatException | OverflowException => …`, and — newly expressible — the per-slot form `TwoColor(Color.Red | Color.Blue, var x)`. The comma now means exactly one thing in pattern context; the `=>` lookahead is gone; case and catch share one alternatives syntax; and the spelling matches the Rust/Scala/Python-`match` precedent readers already know. The bitwise-or collision is dissolved structurally rather than by rule: the only expression positions inside patterns (relational operands, range bounds) parse below `|`'s precedence level, and the scrutinee is `of`-delimited (§3.7), so a pattern-level `|` is always the separator. Alternative members exclude types and bindings in case patterns (a type member stays a compile error; grouped type tests are separate arms) — the v0.144-era reasoning that constant-vs-type alternatives have different exhaustiveness and binding semantics is unchanged by the respelling. *(v0.183 widened the admitted members from constants-only to constants, ranges, and relationals: those are binding-free pure membership tests, which the recorded reasoning never targeted; the exclusion of types and bindings is the decision, and it stands.)*

<a id="sec-owning-prefix"></a>
### 3.9 The owning family is prefixed `Owning`, not `Owned`

Adopted v0.168 (#1372; the stronger remedy #1334 hedged toward). `OwnedArray<T>` grammatically read as the wrong axis: "an array that *is owned*" (the container axis), when the family actually denotes "an array that *owns its elements*" (the element axis). The misreading was not hypothetical — §28.3 and Appendix C.3 both carried defensive parentheticals explaining that a bare `OwnedArray<T>` return is a borrow, and `owned OwnedArray<T>` stacked one word across two meanings. The rename gives each axis its own word: **`owned` is the container qualifier; `Owning` is the element prefix.** `owned OwningArray<Dog>` reads correctly; a bare `OwningArray<Dog>` no longer *sounds* owned.

Folded in (per the v0.165 #1359 deferral): the owning **interfaces** gain the standard `I` prefix — `IOwningEnumerable`/`IOwningEnumerator` (and the async pair), `IOwningList`/`IOwningCollection` — since they were the stdlib's only unprefixed interfaces; `GetOwnedEnumerator()` follows as `GetOwningEnumerator()`. Method names that describe an owned **argument** — `AppendOwned`, `FromOwnedResult` — keep `Owned`: there the word correctly names the qualifier axis (the value being passed is owned), not the element axis. The inline-array slot marker is deliberately **not** touched (a separate decision, recorded here as deferred, not declined). Historical changelog entries ([`Bezel_Changelog.md`](Bezel_Changelog.md)) retain the names as they were at each revision.

<a id="sec-call-site-transfer-marker"></a>
### 3.10 Ownership transfer is marked at ordinary call sites

Adopted v0.169 (#1348 — an adversarially-verified review finding, not a rejected-then-revived design; no prior recorded decision had weighed a call-site marker). The gap: `ref` and `out` require call-site keywords, `move` announces a field take-out at the read site (§5.10), yet passing a named owned binding to an `owned` parameter — the mode that leaves the argument *moved-from* — was invisible: `M(value)`. The spec paid for the invisibility twice: §22.6's owned-overload ban and the stdlib's dual naming (`Append`/`AppendOwned`) both exist because the call site couldn't distinguish the forms.

The marker reuses grammar the language already reserved: Appendix A.7's `ArgModifiers` carried an orphaned bare-`owned` alternative with no prose semantics — v0.169 defines it rather than inventing syntax. `M(owned x)` is required exactly when a **named owned binding** is consumed (an owned local or `owned` parameter); **fresh producers** (`new`, owned-returning calls, `move obj._f`) stay unmarked because no live binding is invalidated — the marker announces invalidation, not the parameter's mode. `owned` was preferred over a `move` spelling: it fills the reserved slot, mirrors `out owned var x`, and avoids relaxing MoveExpr's deliberate field-only operand restriction (§5.10). The §22.6 overload ban deliberately stands — its own carve-out criterion is now satisfiable, but lifting it drags stdlib renames and resolution rules along; that is a recorded follow-on, adopted separately or not at all.

<a id="sec-uniform-end-closer"></a>
### 3.11 One uniform end-closer rule

Adopted v0.170 (#1374; one of #1343's recorded seams). The closer discipline was three rules: named declarations took an optional *name* label (`end Main;`), constructor/destructor/operator bodies an optional *keyword* label (`end constructor;`), and every statement-level block — plus extension and extern, the longest un-labelable bodies in the language — **forbade** any label, so the Ada-style keyword-labeled closers (`end if;`, `end for;` — the closer scheme of the very heritage §3 cites, though Ada itself spells every loop's closer `end loop;`) were an error. v0.170 collapses the three rules into one: `end` may repeat the construct's name (if it has one) or its introducing keyword (otherwise), checked when present. Bare `end;` stays legal everywhere, so the change is fully additive — zero migration — and long blocks gain the compiler-checked readability the declaration closers always had. The alternative of *requiring* labels on long blocks was declined: label ergonomics are a style choice, and the compiler-checked optional form gives tooling and reviewers the same benefit without ceremony.

<a id="sec-the-binding-atom-names-a-subexpression"></a>
### 3.12 The binding atom names a subexpression (`(var x := E; body)`)

Adopted v0.216 (proposal 0061 §1; owner-deferred 2026-07-21, activated on the owner's direction 2026-07-22). The atom exists for one job: naming a subresult where only an expression is admitted, so it need not be recomputed. The motivating position is the contract clause (spec §22.16) — clauses are expression-only and pure, so a clause using a subresult twice previously had to evaluate it twice: `ensures(var n := result.Count; n >= 0 and n <= _capacity)` names it once, harmlessly. Expression-position `case`/`when` arm bodies are the second beneficiary; helper extraction remains the doctrine for multi-*statement* logic.

The form passed the atom admission test proposal 0061 records — the test future paren-atom candidates must also meet: (1) it produces a value whose computation is ceremony-heavy in expression position today; (2) it rides existing kernel machinery — clause typing is spec §21.1's, ownership is K2/K3.4 verbatim plus one boundary clause (K8.5: an owned initializer is a *named unbound temporary* bounded by the atom — tighter than the enclosing full expression, escape rejected-never-extended per K8.4); (3) it makes no doctrine-declined path more ergonomic. The same review declined the try-expression and comprehensions under tests (3) and (1) — `DECLINED.md`, 2026-07-21.

Design choices worth recording: the spelling reuses `(` + `var` (a unique two-token commit, like `(if`/`(case`/`(when`) and the statement declaration's own clause syntax — no new keyword, no new token; `;` separates because no expression contains a top-level `;`, where `in` collides with membership and `=>` with lambdas. The binding is **single-assignment by construction** — assignment is a statement and the atom admits none — and is additionally not an assignable location (the runtime-`const` rule, spec §21.1), which closes the `do`-bodied-lambda capture hole. The body is deliberately *not* a K3.4 marked-transfer position (an atom cannot launder its own binding into an owned result); lifting that, and admitting all-constant atoms into §17.14 constancy, are recorded liftable bounds. **It does not reopen §5.13's block-expression decline**: that decline is about statement *sequencing* in value position — effects, `do … end`'s single meaning, the trailing-expression/`yield`/`give` designs — while this atom admits no statements at all; a clause is a pure-shape binding, the body one expression. The distinction the two rules jointly draw: naming intermediate *values* in an expression is cheap and now admitted; interleaving *effects* into an expression remains declined.

<a id="sec-lambdas-are-keyword-led"></a>
### 3.13 Lambdas are keyword-led (`lambda(params): T => body`)

Adopted v0.217 (proposal 0064; owner-directed 2026-07-22). Through v0.216 a lambda was spelled `(params) => body` — the last major expression form with no committing first token: the reading was decided only at the `=>` after the matching `)`, which cost the parser its one unbounded lookahead, required a dedicated carve so a `when`-guard `(t > 0) => …` was not mis-scanned as a lambda (#1256), and gave the reader the same late signal in argument-position paren soup. The keyword fixes all three at once — `lambda` begins no other expression or statement, so the form commits at its first token, stronger than even the v0.208 paren atoms' second-token commits — and it opens the one slot the old spelling structurally could not host: a **return-type ascription** (`): T =>` after a bare parenthesized form collides with dictionary-literal key position), which resolves §27.3's divergent-return case at the site instead of at the enclosing variable. That capability is what distinguishes this landing from the spelling-only churn `DECLINED.md` D-0003 warns against: the revision retires the lookahead machinery *and* closes a recorded expressiveness gap, rather than re-spelling for taste.

The keyword is `lambda` because it is already the language's name for the construct — §27's title, the grammar's `LambdaExpr`, the diagnostics — and the term-of-art objection is answered by `async`/`await`/`yield`, which are equally terms of art and equally reserved. `function` was the runner-up (matches "function types" but is heaviest at the hottest sites and implies a free-function category the language lacks); `func`/`fn` would be the keyword set's first abbreviations; `method` is free but answers "method of what?" with "nothing". The word is unconditionally reserved, not contextual — reservation was free (the identifier appears nowhere in the corpus), and contextual status would reopen the `Identifier`-lookalike seams the keyword exists to close. The cutover is **hard** — the old spelling left the grammar in the same revision, the 0057-reversal precedent — because with no external users a deprecation window serves nobody and defers the entire parser payoff. The broader survey (eight syntax families, the verified colon-fatality of the literal Python form, the declined placeholder/brace/`end`-delimited shapes) is recorded in proposal 0064, whose §9 verification record backs every grammar claim here.

<a id="sec-memory-management"></a>
## 4. Memory management

Bezel's ownership model is the part most likely to surprise readers. The high-level shape:

- Class instances are heap-allocated and must be disposed exactly once.
- Records, enums, and primitives need no disposal.
- A small set of types — `string`, boxed value types, function values — are **runtime-managed** and exempt from manual disposal.

The runtime is not specified. Reference counting works. Region allocators work. A small generational collector for the runtime-managed subset works. Implementations choose.

<a id="sec-why-strings-are-runtime-managed"></a>
### 4.1 Why strings are runtime-managed

Marking `string` as owned would mean `using var` on the result of `int.ToString()`, every interpolation, every concatenation. The result would be unreadable.

The alternative — value-type strings with copy-on-write — silently allocates on every concatenation and complicates interop with languages where `string` is a reference type.

The chosen path is to put `string` (and a small set of other deeply-pervasive types: boxed values, function values) in a runtime-managed region and leave manual ownership clean for the 95% of types where it actually matters. Manual ownership would be unworkable for strings; runtime management is unworkable for resources. Each gets the right tool.

<a id="sec-why-function-typed-values-are-runtime-managed"></a>
### 4.2 Why function-typed values are runtime-managed

A non-capturing lambda is just a function pointer; a capturing lambda owns its captured environment; a method reference (`obj.Method`) carries the receiver. These are heterogeneous enough that requiring callers to track ownership of every function-typed value would force `using var` on every callback.

The simple rule — function-typed values are runtime-managed — makes them as easy to use as any other value while keeping the ownership story for resource-bearing types intact.

<a id="sec-why-classes-are-non-nullable-by-default"></a>
### 4.3 Why classes are non-nullable by default

C#'s opt-in nullable reference types proved that most reference fields are non-null in practice. Bezel goes one step further: non-nullability is the default, nullable types are opt-in via `?`. The cost is `?` on a small minority of types; the benefit is that `null` is noteworthy, not the default value of every reference.

<a id="sec-allocation-failure-fatal"></a>
### 4.4 Allocation failure is fatal

When the runtime cannot obtain memory — for a `new`, a growing collection, a string, a boxed value, or a closure/iterator/async frame — the program terminates: the runtime reports the failure and aborts the process (spec §31.4). Nothing is catchable, no unwinding runs, and the disposal-at-exit pass is skipped — allocation failure joins the abnormal terminations of spec §22.13, where disposal at exit is already excused. The report's form is implementation-defined; the termination is not.

C trained generations of programmers to treat an unchecked `malloc` as a bug, so refusing to surface the failure at all deserves a defense. Making allocation failure catchable — an `OutOfMemoryException` — would turn every `new`, every collection growth, and every closure, iterator, and async frame into a potential throw site: a permanent tax on the exception control-flow graph and on the ownership checker's discharge analysis, paid by every program on every path. What the tax would buy is a handler invoked at the precise moment allocation has stopped working — and OOM handlers almost universally allocate on their way to failing. Programs that genuinely must survive memory pressure do it before the fact — bounding inputs, pooling buffers — not by catching the failure after it happens. `StackOverflowException` had already established that resource exhaustion is uncatchable and fatal; allocation failure follows the precedent.

Declined: a named uncatchable `OutOfMemoryException`, purely for report symmetry with `StackOverflowException`. The report's wording is implementation territory, so the name is cosmetic — and revisitable without breaking anything.

<a id="sec-ownership"></a>
## 5. Ownership

<a id="sec-owned-not-borrows"></a>
### 5.1 `owned`, not borrows

Rust's borrow checker enforces single-writer-or-many-readers at compile time. Most working programmers don't need that guarantee; they need "free this once and don't use it after." Bezel targets the second and skips the first.

`owned` marks a field, parameter, or return as on the disposal hook for its containing object. The compiler enforces that owned values reach an owned location and don't escape to non-owned references. Use-after-dispose is not statically prevented; it's caught at runtime via the idempotent `Dispose()` rule.

Trade-off: programmers can write aliasing bugs that Rust would reject. They can also write a working web server in 200 lines without `Arc<Mutex<T>>`.

*(v0.180 narrowing — the consume-site freeze, recorded.)* Spec §28.3 (v0.180) makes it a compile error to **consume** an owned binding — move it into an `owned` argument (including a domain spawn or channel send), transfer it with the binding/assignment marker, store it into an owned slot, return it owned, or reassign it — while a live local borrow of that binding exists. This is a deliberate, scoped narrowing of this section's decline of compile-time borrow-liveness checking, **not** a borrow checker, and the recorded boundary is load-bearing: **explicit `Dispose()` while borrowed remains runtime-checked**, exactly as this section decided — disposal sets the per-instance flag, so checked mode deterministically catches every later aliased use, and the `Dispose()` call is itself the source-visible announcement. What forced the static rule for the *silent* kills is the case with **no runtime backstop of any kind**: an object moved to another domain stays alive, no flag is ever set, and a surviving pre-transfer borrow is a live data race (probe-confirmed, 2026-07 review) — §30.14's isolation claim was false without the freeze. The freeze was applied uniformly at every consume site rather than at a compiler-known-transfer subset because transfer positions are not closed under composition (any `owned` argument may be forwarded to a spawn), and because the rule composes with §28.7's drop-on-overwrite — unborrowed reassignment stays legal (the reference compiler's former blanket rejection of owned-local reassignment, #1465, was narrowed to exactly the borrowed case). Cost accepted: the borrow-then-transfer-then-keep-using-the-borrow idiom is rejected (mechanical rewrite: re-borrow from the new owner). Alternatives declined: (a) freezing explicit `Dispose()` too — converts this section's recorded trade-off into a de-facto borrow checker for no soundness gain (the backstop is real); one deliberate exception is recorded: sources captured under §28.14's storage-bounded admission *are* frozen against disposal as well, because a stored callback's later invocation is invisible at the dispose site and the admission promises a fully static bound; (b) scoping the freeze to domain-crossing sites only — leaky (not compositionally closed), unpredictable at call sites, and it would leave the borrowed-reassignment silent kill entirely outside the rule.*

*(Supersession notes, v0.157.* Two of this section's original claims have been overtaken by later decisions and are preserved above only where still true. **Data races:** as first written, this section accepted that programmers could write data races; since v0.131–v0.133 the domain model closed that hole — continuations are serial per domain and no mutable state is reachable from two domains ([§12.5](#sec-execution-domains), [§12.6](#sec-sendability-spawning-channels)), so data races are no longer expressible in safe code and the remaining trade-off is aliasing/use-after-dispose, caught at runtime. **Discharge errors:** the original hard "must discharge every owned value" compile error became the affine auto-drop-with-warning model in v0.150–v0.152 — see [§5.23](#sec-the-affine-model).)*

*(v0.184 refinements, recorded.)* Three further boundary placements compose with the v0.180 narrowing. (1) **The join rule**: a read of an owned local after a *conditional* explicit `Dispose()` (or discard) is a compile error — owned ⊓ explicitly-disposed = maybe-consumed (spec §28.3). This is a deliberate step past this section's runtime-checked posture for announced kills: the per-path consumption tracking exists regardless (per-path scope-end disposal requires it), so the rejection is free precision, not a borrow checker; the posture continues to govern straight-line use after an announced kill, which stays a (now mandatory) warning plus the checked-mode backstop. (2) **The dispose-capability rule** (spec §28.6): `Dispose()` requires an owned receiver; disposing through a tracked borrow is a compile error — this is not borrow-liveness checking (it reads only the receiver's own ownership classification, already computed at every site) and it leaves this section's recorded trade-off intact: disposing an *owned* binding while borrows of it live remains legal and runtime-checked. The rule is exception-free since v0.213: the borrowing-collection transit regime (per-element disposal through element borrows, the manual form of the retired `DisposeElements()` escape hatch) was retired with axiom A8 when the 2026-07 corpus sweep found no load-bearing client — the owning family expresses the vouch structurally. (3) **Captured owned bindings** are borrow-state inside closures (no consume, no reassign, no dispose through the capture): the alternative admitted a silent drop-on-overwrite kill that the consume-site freeze — decidable precisely because it is local to one body — could never see.

*(v0.198: the model this section motivates is stated normatively as the ownership kernel — spec §28.3, K1–K9 — with this section's recorded decisions appearing in its axiom register; see [§5.26](#sec-the-ownership-kernel).)*

<a id="sec-dispose-is-not-on-object"></a>
### 5.2 `Dispose` is not on `Object`

Records, enums, and primitives don't need disposal. Putting `Dispose()` on `Object` would mean asking the user "should I dispose this `int`?" — a meaningless question. Disposal lives on classes, where the need actually exists.

Code that takes "any disposable thing" accepts `IDisposable`, not `Object`. This documents intent.

<a id="sec-collections-do-not-own-their-elements"></a>
### 5.3 Collections do not own their elements

The most-debated decision in this area. Three options were considered:

1. Collections always own their elements (Add takes ownership; Dispose disposes everything).
2. Borrowing collections (the original v0.52–v0.87 choice; remains the *default* in v0.97 alongside the explicit owning forms).
3. Collections optionally own via a generic flag.

Option 1 fails for collections of borrowed references, common when a class has a back-reference list. Option 3 doubles the API surface and forces the choice at type-construction time, which is the moment when the programmer least wants to think about it. Option 2 keeps collections universal; at the time it carried an explicit `DisposeElements()` escape hatch for holders that owned their elements — retired v0.213 with axiom A8, the owning family having taken that role structurally.

Asymmetric ownership in the values-owned direction is `OwningDictionary<K, V>`'s shape by construction; the own-keys direction has no recorded client.

v0.97's resolution: option 2 remains for the borrowing types (`Array<T>`, `Dictionary<K, V>`, etc.), and option 1 is provided as separately-named owning types (`OwningArray<T>`, `OwningDictionary<K, V>`, etc.). Users pick the form that matches their ownership intent at the declaration site. The earlier v0.88-v0.96 attempt at option 3 (an `<owned T>` generic-argument modifier with merged class declarations) was abandoned in v0.97 because the substitution machinery accumulated more complexity each revision; separate named types capture the semantic distinction directly without the substitution rules. The non-owning baseline retains its original justification — it is the right default for collections of borrows; a holding class that owns its elements commits the collection's type to ownership (the owning family), which is the honest spelling of what the retired escape hatch used to vouch.

*(The v0.184 per-element manual form and its `DisposeElements()` bulk sibling — the one exception spec §28.6 carried to dispose-requires-an-owned-receiver — were retired together at v0.213 (axiom A8's tombstone): the 2026-07 corpus sweep, #2075, found every use whole-collection-owned and migratable to the owning family; tracked borrows may not be disposed anywhere, with no residual carve.)*

<a id="sec-no-shared-ownership"></a>
### 5.4 No shared ownership

There is no `Rc<T>` or `Arc<T>`. Single ownership only.

The cases where shared ownership is genuinely needed are rare in Bezel's target use cases and are served by other patterns: handle-and-table indirection, channels, or the runtime-managed region for shared immutable data.

If shared ownership turns out to be needed, it can be added as a library type without language changes. *(v0.134: it was — `Shared<T>`/`Weak<T>`, scoped, explicit, and domain-local; see [§5.21](#sec-shared-t) and language spec [§28.13](Bezel_Language_Spec.md#sec-shared-ownership). The position of this section otherwise stands: single ownership remains the default and the only implicit regime.)*

<a id="sec-local-variable-ownership-is-inferred-not-annotated"></a>
### 5.5 Local-variable ownership is inferred, not annotated

Fields, parameters, and returns carry an explicit `owned`. Locals do not. The compiler infers each local's ownership state from how it was introduced — from the right-hand side's classification, for `using var` and plain `var` alike: `var x := new T()` is owned, `var x := someField` is borrowed, and a `using var` is owned over an owned producer but a scope-pinned borrow with no disposal obligation over a borrow ([§28.10](Bezel_Language_Spec.md#sec-using-var-initialized-from-a-borrow)). The full rules are in [§28.3](Bezel_Language_Spec.md#sec-local-variables-ownership-and-borrows) of the spec.

The asymmetry is signal-to-noise. Annotations on field, parameter, and return positions communicate API intent across module boundaries — they need to be explicit. Annotations on every local would be redundant noise: the compiler can already see what the local was initialized from.

<a id="sec-the-lattice-direction-at-control-flow-joins"></a>
### 5.6 The lattice direction at control-flow joins

The [§28.3](Bezel_Language_Spec.md#sec-local-variables-ownership-and-borrows) lattice puts owned ⊑ borrowed: owned is the *stronger* state, borrowed the *weaker*. At a control-flow merge where two branches produced different states for the same variable, the meet would have to be the weaker state — but a meet between owned and borrowed at the same merge is rejected outright, because demoting owned to borrowed silently drops a disposal obligation.

The earlier reading (borrowed ⊑ owned, with the owned branch winning at the join) is wrong: there is no value to dispose on the borrowed branch, so the merged owned slot would carry an obligation it cannot discharge. The compiler instead requires programs to equalize the branches before the merge — either produce an owned value on both branches by allocation or `Clone`-style copy, or arrange for both branches to bind the variable to a borrow whose source outlives the merge. The latter does not mean "borrow the `using var`": an owned value discharged with `using var` in a branch must do its work and be released *within* that branch; the post-merge variable takes its value from a longer-lived source, because a borrow may never outlive the source it points into (the merge inherits, rather than escapes, that rule).

This is the standard lattice-meet rule in linear/affine type systems applied to Bezel's specific kinds. It is more restrictive than what some informal readings of v0.55 suggested, but the prior reading was unsound.

*(v0.198: this rule is kernel principle K7 — spec §28.3; see [§5.26](#sec-the-ownership-kernel).)*

<a id="sec-factory-method-ownership"></a>
### 5.7 Factory method ownership

v0.59 left a gap in the producers table for static factory methods. A method like `File.ReadAllLines(path)` returns a freshly-allocated `Array<string>` — semantically identical to a `new` expression — but the return type carried no `owned` annotation. Under the strict reading of [§28.3](Bezel_Language_Spec.md#sec-local-variables-ownership-and-borrows), the return was a "borrow," but from what source? A static method has no receiver.

The v0.60 rule was: when a method returns a class type without `owned` and the compiler cannot identify a borrow source, the return is treated as owned, with a warning recommending the explicit `owned` return type.

*(v0.201 — the heuristic is retired; proposal 0048.)* The warning was designed as a bridge, and both of its recorded motives discharged: the stdlib annotation pass completed (a 2026-07 sweep found **zero** static signatures relying on the treated-owned classification), and the module/artifact model (spec §2.8) delivers an unannotated third-party factory's diagnostic at the third party's own build rather than silently rewriting consumers' obligations. What remained was cost: a core ownership rule memorized rather than read, and the instance↔static refactor hazard — moving a method between kinds silently flipped every call site between borrow and owned. Spec §28.3 now **rejects at the declaration** a static method or operator whose class- or interface-typed return does not announce its classification (`owned`, a `Task`-family type, an iterable/enumerator interface, or a sourced bare type parameter); the v0.196 per-instantiation erasure was the last enabler, making `owned T` spellable over mixed constraint domains. The kernel's axiom A1 is tombstoned (the register's first planned decrease; budget → thirteen). Body-inference and call-site-error alternatives were declined with reasons in proposal 0048 §8; §5.5's boundary-explicitness doctrine is what the retirement completes.

The `owned` annotation remains the preferred mechanism. The compiler-inferred rule exists as a safety net for two reasons: (1) third-party libraries may not annotate their returns, and (2) adding `owned` to every factory method across the standard library in one step would be a large surface-area change. The v0.60 standard library adds `owned` to the most common factory methods; future revisions will complete the pass.

(v0.194) The premise — *cannot identify a borrow source* — was completed for generic signatures. A static method whose declared return type is a bare type parameter *does* have identifiable sources: its T-reaching plain arguments. Treating `Math.Max<T>(a, b)` as a fresh-owned factory at a class substitution had made the caller a second owner of one of its own still-owned arguments (two owners, one obligation — the exactly-once invariant broken through the argument binding), while the callee-side borrow-return prohibition made the selector body unwritable in-language. The bare-type-parameter rule (spec [§28.3](Bezel_Language_Spec.md#sec-bare-type-parameter-returns)) classifies such calls as borrows carrying the union of the receiver's and the T-reaching arguments' source-liveness constraints, and reserves this section's owned-with-warning fallback for the genuinely sourceless shapes (`Create<T>(): T where T: new()`) — where fresh production is the only writable body and owned is the right answer (with one v0.194 tightening: a static-storage-sourced borrow return is rejected under such an empty-set signature — the caller side mints ownership there, so the borrow would acquire a second owner; a static property is the sound spelling). Callee-side, the bare-type-parameter return admits parameter- and receiver-sourced borrows, enforced per instantiation category (§3.6 rule 2's pattern): the announcement-by-declared-type doctrine of the iterator and `Task`-family conventions, and what makes the standard library's own `Min`/`Max`/`Clamp` writable at class substitutions. Fresh-producing generic signatures spell `owned T`, as `OwningSet<T>.Take(query: T): owned T` does under `where T: class`.

The v0.194 declines are recorded with the rule. *Post-substitution keying* — classifying each call by its substituted return type — reads plausibly at `Math.Max<Connection>` and is refuted one shelf over: `First<T>(): T` at `T = Task<int>` would substitute into the `Task`-family rule and mint a disposal obligation over a collection-owned element. The sound geometry, shared with the v0.190 ruling, is pre-substitution *keying* with per-instantiation *enforcement*: what rule governs a call is fixed by the declaration, while the checks fire only where a substitution gives them content. *Marking selector returns `owned`* fails twice over — as engineering it is marker spam across every generic selector in every library, and as semantics it is a false statement: a selector transfers nothing, and `owned` would mint exactly the second obligation the ruling exists to remove. What makes the borrow classification look inevitable in hindsight is the signature grammar it completes, one the standard library had been writing by instinct all along: bare `T` with T-reaching inputs is a **selector** and borrows (`Min`/`Max`/`Clamp`); `owned T` is a **producer** and transfers (`Take`, `Deserialize`); bare `T` with no T-reaching inputs is a **factory** and is owned, the warning nudging toward the explicit spelling. A generic signature's ownership behavior is readable off its shape — the rule did not add a distinction, it recognized one the signatures already drew.

(v0.196) The spelling was then completed for *mixed* domains: `owned` on a bare-type-parameter slot became per-instantiation — the ordinary transfer at class and interface substitutions, **erased by the substitution** at value and runtime-managed ones — replacing v0.193's instantiation-site rejection, which had left fresh-producing generics over domains admitting value substitutions (the stdlib §2.19 numeric abstractions; `Create<T>(): T where T: new()`) with no spelling at all: the factory warning was pointing authors at a qualifier the checker then rejected at exactly the substitutions such domains exist for. Stdlib §2.19's producer members and spec §11.8's `Sum<T>` now carry the marker, which is what opens the class-conformer arithmetic surface (a heap-backed BigInteger is the recorded prospective occupant). A second, fresh-vs-selector marker was declined — it would duplicate `owned`'s class-substitution semantics keyword for keyword, differing only in value-substitution admissibility; restricting the numeric interfaces to value conformers was declined — spec §11.8's own canonical conformer is a class, and the restriction would only defer this exact design plus a compatibility event. The generic `owned` **field** rejection (spec [§28.5](Bezel_Language_Spec.md#sec-owned-fields)) deliberately stands: a field marker commits the containing type's shape — destructor synthesis, derived properties — in a way a call-boundary marker does not.

<a id="sec-collection-literal-ownership"></a>
### 5.8 Collection literal ownership

A collection literal `[1, 2, 3]` targeting `Array<T>` (or another collection class) allocates a heap object. It is semantically a `new` expression with initialization — the fact that the syntax is a literal does not change the allocation behavior. v0.59 did not list collection literals in the producers table, leaving the ownership of `var xs := [1, 2, 3];` unspecified.

v0.60 adds collection literals to the producers table as owned values when targeting a heap collection class. The rationale is straightforward: the literal creates a fresh object, so the binding must own it. The same discharge rules as `new` apply. (Collection literals targeting inline arrays `[N]T` (v0.98+) produce value-typed inline arrays, with no heap ownership; they participate in the move-only category only when the inline-array slots are themselves `owned`.)

<a id="sec-trivial-dispose-classes"></a>
### 5.9 Trivial-dispose classes

Not every class holds resources. `Random` holds only an internal seed. `StringBuilder` holds a buffer that is plain memory. The `Encoding` singletons hold nothing at all. Under v0.60's strict rules, `new Random()` required `using var` or triggered a warning — adding ceremony for a no-op dispose.

The runtime-managed exemption ([§28.9](Bezel_Language_Spec.md#sec-runtime-managed-types) of the spec) covers `string`, boxed values, and function types — types the language itself creates implicitly and pervasively — but it is a fixed list, and joining it permanently is the wrong model for user classes: what a resource-free class needs is an exemption that is *computed from its declaration* and tracks the class as it changes.

That is the resolution: **trivial-dispose** is a derived type property (spec [§3.6](Bezel_Language_Spec.md#sec-derived-type-properties), [§28.9](Bezel_Language_Spec.md#sec-trivial-dispose-classes)). A class with no destructor, no `owned` fields, no owning-inline-array fields, and a trivial-dispose base has a provably no-op `Dispose()`, and the compiler drops the discharge obligation entirely: a bare `var r := new Random()` compiles clean, the discard `_ := new StringBuilder();` is legal and purely cosmetic, and memory is reclaimed by an implementation-defined mechanism that runs no user code. (The endpoint was reached in two recorded steps: v0.61 first softened the discharge diagnostic to a reduced-severity informational warning; v0.66 dropped even that — there is nothing to discharge, so there is nothing to warn about.)

The class-gains-a-destructor hazard is answered by recomputation, not by ceremony at every use site. Adding a destructor, an `owned` field, or an owning-inline-array field ([§15.1.1](Bezel_Language_Spec.md#sec-owning-inline-arrays) of the spec) flips the classification, and formerly-silent sites immediately draw the standard obligations — the must-use auto-drop warning, a discard that now actually disposes. The flip is source-affecting by design, which is why spec [§28.9](Bezel_Language_Spec.md#sec-trivial-dispose-classes) directs API authors to treat a public class's trivial-dispose status as part of its published contract. `using var` remains accepted (a no-op) for code that wants to be robust against the flip in advance.

<a id="sec-the-move-expression-on-owned-fields"></a>
### 5.10 The `move` expression on owned fields

Through v0.86, ownership transfer in Bezel was *single-shot*: a value moved from a `using var` local to an `owned` parameter, from an `owned` parameter to an `owned` field, from an `owned` field to memory at destructor time. Each transition was implicit, named by the syntactic position. There was no transition for "take this owned field's value out and return it to a caller."

The reason was a deliberate conservatism. Field reads always produced borrows ([§28.3](Bezel_Language_Spec.md#sec-local-variables-ownership-and-borrows) of the spec), because fields are *retained*: a class instance exists to be acted upon multiple times, and the natural operation on a field is "read while leaving the value in place." Owning vs. borrowing was a property of the read site's intent, but every field read promised the same thing — the field's value is still there afterward. A take-out operation on a field would have to invalidate the field's contents, and the spec had no machinery for tracking "this field is currently empty."

The cost of this conservatism was visible. The standard pattern "replace a resource and return the old one" (a transactional update on an owned field) had no clean form. The v0.85 spec showed a `Utils.Swap`-via-`ref` workaround that exchanged the field with a freshly-built local; v0.86 documented the gap explicitly when a related case (batch-aggregating `Task<owned T>` results) had no workaround at all. Each acknowledgement made the gap more visible.

v0.87 closes the field-take case with `move x.f`. The expression reads the field as an owned value and leaves the field in *moved-from* state. The compiler tracks the moved-from state across the rest of the method body and rejects any path that exits the method without first reassigning the field. The rule is the same definite-assignment analysis Bezel already performs for non-nullable locals, lifted to the field level.

The design choice is to make the move *explicit*. A bare `var x := _resource;` continues to produce a borrow as it always did; only the explicit `move _resource` form transfers ownership out. Three reasons for the explicitness:

1. **Visibility in code review.** A reader scanning a method body learns the local effect of each line. With explicit `move`, the take-out is announced at the read site; the reader does not have to reason about subsequent lines to discover that the read was actually a take. This matches Bezel's existing preference for syntactic visibility — `using var` declares scope-bound disposal at the binding site, `owned` declares ownership transfer at the type position, `out` declares output at the call site. `move` is the analogous keyword for the take-from-field operation.

2. **Refactoring stability.** A version of the rule that *inferred* take-out from the pattern "read followed by reassignment" would be sensitive to insertions between the two lines. Adding a `Log(...)` call between read and reassignment, or extracting the reassignment into a helper method, would silently change whether the read was a borrow or a take. Programs that compiled would compile differently after small edits. Explicit `move` makes the take-out a user decision; inserting a log call between the move and the reassignment does not change the move's semantics.

3. **The exception-path obligation.** The field-restoration rule has to handle exception edges as well as normal control flow: if a throwable expression appears between the move and the reassignment, the throwing edge is an exit path on which the field has not been restored. The fix is the *build-before-take* discipline — construct the replacement value first, then take, then assign — which is the same discipline RAII code in C++ and transactional code in functional languages already commits to. Making the move explicit lets the spec write down this rule without forcing the user to discover it through experiment.

The `move` form is permitted only on owned instance fields, not on locals (which already have the implicit move-on-read semantics), not on static fields (whose lifetime crosses methods, breaking the field-restoration rule's scoping), and not on collection elements (which are not owned slots in this version). The first two restrictions are by design; the third is open — a future revision that admits `Array<owned T>` ([§14.4](Bezel_Language_Spec.md#sec-owned-as-a-generic-argument)) would naturally extend `move` to collection-indexed slots.

The field-restoration rule's analysis reuses the existing definite-assignment machinery. The compiler's flow analysis already tracks "is this non-nullable local definitely assigned on every path that reads it." The same machinery applied to the inverse question — "is this owned field definitely reassigned on every path that exits after a move" — needs no new graph algorithms, only a new state on field nodes. This is why `move` was a feasible v0.87 addition: the cost on the implementation side is small and localized.

v0.87 originally shipped without addressing the collection-of-owned case — `Array<T>` did not own its elements, so `move arr[i]` had no slot to move from. v0.88 closes that gap by extending language spec [§14.4](Bezel_Language_Spec.md#sec-owned-as-a-generic-argument)'s opt-in list to admit `Array<owned T>` and the other standard collection types; the next subsection covers the rationale.

<a id="sec-owning-collections"></a>
<a id="sec-owned-element-collections"></a>
### 5.11 Owning collections

For nine revisions (v0.78 through v0.96), Bezel's collection types were uniformly non-owning (`Array<T>`, `Dictionary<K, V>`, etc., storing borrows), with a separate **`<owned T>` instantiation** form admitted for the standard collection types. `Array<owned Connection>` was a distinct type from `Array<Connection>` and owned its elements; the language spec [§14.4](Bezel_Language_Spec.md#sec-owned-as-a-generic-argument) of those revisions defined an opt-in list of generic types that could accept the `owned T` argument.

v0.97 replaces the `<owned T>` mechanism with **separate named classes**. `OwningArray<T>`, `OwningLinkedList<T>`, `OwningSet<T>`, `OwningStack<T>`, `OwningQueue<T>`, `OwningDictionary<K, V>`, plus the owning task type `OwningTask<T>` and the owning iteration interfaces `IOwningEnumerable<T>` / `IOwningEnumerator<T>` (and async variants), are first-class types in the standard library. The borrowing collection types retain their existing names. The `owned` modifier no longer propagates through generic type arguments.

**Why the change.** The `<owned T>` mechanism accumulated language machinery across revisions: an opt-in list (v0.78), conditional inheritance semantics (v0.95), substitution rules and form-conditioning constraints (v0.96), an inheritance-projection rule (also v0.96). Each addition fixed a specific issue and introduced a corner case for the next revision to address. By v0.96 the spec had three substitution rules, two new constraint forms, a special inheritance-projection rule, and ongoing concerns about how future features (LINQ over owning collections, user-defined owning containers) would interact with the mechanism.

The underlying observation: an owning collection's `Add` takes ownership of its argument; a borrowing collection's `Add` takes a borrow. These are *genuinely different operations*, not two specializations of one operation. Trying to express the difference as a parameter modifier substituted through a single generic forced two unrelated semantics through one syntactic vehicle. Separate types capture the semantic distinction directly.

**What was lost.** The `<owned T>` mechanism let one generic algorithm work over both ownership forms. A `Where<T>(items: IReadOnlyList<T>)` would accept both `Array<MyClass>` and `Array<owned MyClass>` via type inference (T inferred as `MyClass` and `owned MyClass` respectively, with the v0.96 inheritance projection stripping owned at iteration points). In v0.97, the generic still accepts both — `Array<T>` and `OwningArray<T>` both implement `IReadOnlyList<T>` — but T is now always `MyClass`, not parameterized over the ownership form.

For read-only access (the common case), this is no loss: the generic works identically. For *mutating* algorithms over either kind, the user picks one mutating interface (`IList<T>` for borrowing; `IOwningList<T>` for owning) and parameterizes over that. Code that wants to abstract over both mutating forms isn't expressible in v0.97 — but on reflection, such code is rare and would face the same semantic dilemma the language faced ("does `Add` take ownership?") just at the user's call site rather than at the language layer.

**What was gained.** Substantial simplification:
- The language spec [§14.4](Bezel_Language_Spec.md#sec-owned-as-a-generic-argument) opt-in mechanism, substitution rules, and constraint forms are gone.
- The `IEnumerator<owned T>` destructive-Current rule becomes a normal interface declaration (`IOwningEnumerator<T>` has destructive Current by its own definition; `IEnumerator<T>` doesn't).
- User-defined owning containers are now expressible via composition over `OwningArray<T>` (or another owning primitive), without any opt-in mechanism.
- The Dictionary "four combinations" complication (v0.96 admitted `Dictionary<owned K, V>`, `<K, owned V>`, `<owned K, owned V>`) collapses: `OwningDictionary<K, V>` covers the one realistic case (V is owned; K is value-like).
- The `Stack.Pop` and `Queue.Dequeue` "return-type form-conditioning" mechanism in v0.96 becomes a simple separate declaration on the owning class.

**User-defined owning containers.** A user who wants their own owning container builds it by composition over an `OwningArray<T>` (or another owning primitive) — the same composition that language spec [§14.4](Bezel_Language_Spec.md#sec-owned-as-a-generic-argument) now carries as its worked example:

```bezel
public class OwningCache<T> where T: class
  private owned _items: OwningArray<T>;

  public constructor() _items := new(); end;

  public method Add(owned item: T) => _items.Add(owned item);   // transfer marker per spec §22.3 (v0.169)
  public method Drain(): IOwningEnumerable<T> => _items.Drain();
end OwningCache;
```

Every line is ordinary current-spec code, and each carries the semantics it names. The `owned` field puts the cache's destructor cascade onto the array — and, through it, onto the elements. `Add`'s parameter is a named owned binding, so forwarding it into the stdlib's `Add(owned item: T)` writes the v0.169 call-site transfer marker, `_items.Add(owned item)`, announcing that the call consumes `item` (§3.10; spec §22.3). The `Drain()` wrapper follows the same convention the stdlib's own `Drain()` uses: the `IOwningEnumerable<T>` return type is itself the transfer announcement (spec §28.3's iterator-factory convention — callers discharge the enumerable, typically through the `for` loop's implicit `using var` source binding, and each yielded element arrives owned in the loop variable). The user's class needs no special opt-in or compiler magic — `OwningArray<T>` is a primitive whose semantics are spec-defined, and the user inherits those semantics by storing one. The "deferred problem" of v0.78-v0.96 (how can user-defined types opt in to owning generics?) is solved by simplification rather than by adding more language.

**LINQ over owning collections.** Still deferred, but on different grounds. v0.96 deferred it because the design questions (does `Where`'s predicate take a borrow or owned? what does `Select`'s output look like for owning sources?) interacted with the substitution rules in complicated ways. v0.97 simplifies the question: LINQ extension methods can be declared in two families — one over `IEnumerable<T>` (borrowing), one over `IOwningEnumerable<T>` (owning) — with appropriate signatures for each. The work is mechanical: each LINQ method gets two declarations. A future revision will add the owning family when there is a sufficiently complete design.

**Migration.** Code written for v0.78-v0.96 that uses `<owned T>` instantiations needs to be rewritten with the new type names. Every `Array<owned T>` becomes `OwningArray<T>`. Every `Task<owned T>` becomes `OwningTask<T>`. Every `IEnumerable<owned T>` becomes `IOwningEnumerable<T>`. The change is mechanical and pervasive but each replacement is local — there are no semantic shifts that require rethinking algorithm design.

<a id="sec-pattern-b-loosening-and-iterator-yield-refinement"></a>
### 5.12 Pattern B loosening and iterator-yield refinement

Two of v0.89's changes refine ownership rules that v0.88 had introduced: the Pattern B consumer rule for `Task<owned T>` (language spec [§30.5](Bezel_Language_Spec.md#sec-result-lifetime-and-task-disposal)), and the iterator-yield-ownership rule for owned-class-typed values (language spec [§29.2](Bezel_Language_Spec.md#sec-desugaring-of-for)'s "Iterator yield ownership" subsection). Both are reactions to inconsistencies that surfaced once v0.88's `WhenAllOwned` example had to be written end-to-end.

**Pattern B's "immediate operand of `using var`" rule was over-restrictive.** From v0.74 through v0.88, the rule for awaiting a `Task<owned T>` for class T said the await must be the immediate operand of `using var` or `await using var`. The rule's intent was clear: ensure that the owned result reached an owned location with a definite discharge path. The `using var` form was the canonical such location, so naming it directly was the simplest expression of the rule.

But the `using var` form is one of several owned-consuming contexts the type system already recognizes. An owned-consuming context is any position in the AST where the surrounding expression's type system requires an owned value to be discharged: `using var` is one; an `owned` parameter of a method call is another; an `owned` return expression is a third. In each of these contexts, the type system already enforces that ownership is discharged after the value reaches that position — the same property `using var` provides. The Pattern B rule was distinguishing a single owned-consuming context (`using var`) from the others without a principled reason.

The cost of the over-restrictive rule became visible when v0.88's `WhenAllOwned` example tried to write `results.Add(await task)` — a natural shape, type-correct under the broader rule, rejected under the original rule. The workaround required an intermediate `using var t := await task; results.Add(t);` — three statements where one would do, with the intermediate variable serving no purpose other than satisfying the rule.

v0.89 loosens the rule to admit any owned-consuming context. The safety property is unchanged: every owned-consuming context is one whose type system already requires the value to be discharged, so the rule continues to prevent owned values from being silently dropped. The change is purely about admitting more syntactic positions where the await can appear.

**The iterator-yield-ownership rule needed a split case for `IEnumerable<owned T>`.** v0.78's `IEnumerable<T>` iterator-yield rule said that an iterator yielding owned class-typed values has the enumerator own each yielded value, with the consumer's iteration variable being a borrow valid only for the iteration body. This was the right rule when iterators returning `IEnumerable<owned T>` did not exist — the rule applied uniformly to any iterator that *yielded* owned values, regardless of the iterator's return type.

v0.88 admitted `IEnumerable<owned T>` to language spec [§14.4](Bezel_Language_Spec.md#sec-owned-as-a-generic-argument)'s opt-in list. Iterators returning `IEnumerable<owned T>` are now possible and useful — `Drain()` on every owned-element collection is implemented as such. But the v0.78 rule applied to them too, which produced a contradiction: language spec [§28.11](Bezel_Language_Spec.md#sec-collection-element-ownership) said the consumer's iteration variable from `coll.Drain()` is owned, but language spec [§29.2](Bezel_Language_Spec.md#sec-desugaring-of-for)'s "Iterator yield ownership" said it is a borrow. Both rules cannot be right.

v0.89 splits the owned-class-typed-yield rule into two cases, distinguished by the iterator's declared return type:

1. **Iterator returns `IEnumerable<T>` (no `owned` modifier on T).** The original v0.78 rule applies: enumerator owns each yielded value, consumer borrows. This is appropriate when the iterator's contract is "let the consumer look at each value briefly" — filtering, formatting, dispatch.

2. **Iterator returns `IEnumerable<owned T>`.** Ownership transfers from enumerator to consumer at each `MoveNext`. The consumer's iteration variable is owned and must be discharged in the loop body. This is the rule that makes `Drain()` work.

The split is determined at compile time by the iterator method's return type. The same physical implementation (a state machine that pops elements from the source one at a time) compiles to different consumer-side semantics depending on which signature it presents.

The split rule's complexity is justified because the two cases address distinct use patterns. A filter iterator that yields owned values (perhaps because it constructs them on the fly) and wants the consumer to borrow each one briefly is one valid pattern; a drain iterator that yields owned values and wants the consumer to take responsibility is another. Forcing both into one rule would require either making every consumer-borrow scenario also accept the discharge obligation (adding ceremony to filtering use cases) or making every consumer-owned scenario accept the borrow restriction (preventing drain use cases entirely). The split lets each pattern be expressed naturally.

*(v0.184.)* The v0.180 marker discipline reached yield position: an owning iterator's yield of a named owned binding is an announced consume (the declared return type is the announcement, the owned-return parallel) that joins the consume-site freeze — a yield transfer hands the value alive, so it has no disposed-flag backstop and cannot ride the throw/dispose/discard exemption — while a borrowing iterator's unmarked named-binding yield is a borrow (nothing announces a kill; the enumerator-owns model is scoped to fresh producers and `move` results, and the adopt-then-yield spelling is the warning-free named form). A yield-position transfer marker was declined as grammar without need and stays on the recorded liftable-marker list with the arm positions. The same pass recorded Pattern B await as the announced-kill family's fourth member (keyword + single-consumer type + disposal-sets-flag) and Pattern A's chained `return await` as unfrozen for the structural reason that the outer task cannot dispose the chained source before the body completes.

The error-message-side complexity is small: an iterator's static signature is known at the call site, and the compiler can produce a clear "this is `IEnumerable<owned T>` — the iteration variable is owned" message when the consumer fails to discharge.

<a id="sec-no-block-expressions"></a>
### 5.13 No block expressions

Bezel does not provide a value-returning `do ... end` form. `do ... end` is a statement-sequencing block with type `()` everywhere it appears — in method bodies, in `case` arms at statement position, in `for` and `while` bodies, and as the body of a multi-statement lambda. Multi-statement logic in expression-position contexts (most visibly, `case` arms inside `var x := (case ...)`) is written as an extracted helper method or a local lambda, both of which produce values.

Earlier revisions of this spec flagged the absence of block expressions as an "ergonomic gap" and anticipated a future revision adding a value-returning form. v0.93 closes the question: the gap is real but the answer is to leave it. The reasoning, briefly:

**The alternatives all carry real costs.** We considered four shapes for a value-returning block expression:

1. *Rust-style trailing-expression-without-semicolon* (`do { stmts; final-expr } end`). This fights Bezel's mandatory-semicolon rule ([§1.6](Bezel_Language_Spec.md#sec-statements-and-termination)). A trailing expression without a semicolon, in a language otherwise strict about semicolons, would be a foreign element learners would trip over.

2. *Explicit `yield expr;` to produce the block's value.* This reuses `yield`, which is already a keyword for iterator methods (`yield return`, `yield break`). Code inside an iterator method that also contained a block expression would have two scopes the `yield` could target, creating a resolution rule learners would need to track.

3. *A new keyword introducing the block* (`expr ... end`, `compute ... end`, or similar) with `return` exiting the block. This requires `return` to have scope-local semantics — exits the innermost enclosing return-bearing scope — which is one more rule on top of method/lambda return scoping. It also expands the language's keyword surface for a use case the helper-method extraction already covers.

4. *A new keyword for the value-producer statement* (`give expr;` or similar) inside `do ... end`, with the block becoming value-returning iff a `give` appears. This introduces a new keyword and creates a third interpretation of `do ... end` (the value-bearing one), partially undoing the consistency the current design has.

Each option has at least one cost we judge larger than the cost of the helper-method extraction it would replace.

**The helper-method extraction is good design independently.** Pulling a multi-statement arm body into a named method gives the per-arm logic a name. Names are valuable: a reader can scan the `case` and see what each arm does without descending into the body. The extracted helper also localizes any side effects the arm performs, which is the harder thing to track — far harder than the syntactic awkwardness of writing the helper. A spec that requires extraction is steering toward better-structured code.

**The use case is uncommon.** In practice, `case` arms are short — a literal, a method call, an arithmetic expression. Arms with substantial logic are rare; when they occur, they usually benefit from a name. Adding language machinery for a rare case is poor leverage.

**The single-meaning `do ... end` is itself a feature.** Across the language, `do ... end` does one thing: sequence statements. It introduces a fresh scope and has type `()`. This consistency makes the construct easy to learn and easy to reason about — wherever you see `do ... end`, you know what it does. Admitting a value-returning variant, regardless of which option above, would make the construct's meaning context-dependent: sometimes value-less, sometimes value-bearing, with the distinction visible only by reading the body or surrounding context. Single meaning beats two meanings here.

The [§19.2](Bezel_Language_Spec.md#sec-arms) documentation reflects this decision: `do ... end` is described as statement-sequencing, the helper-method extraction is the recommended pattern for multi-statement arm bodies, and no "future revision" promise is carried.

**v0.126 addendum: the bare-statement arm form is not a block expression.** v0.126 added a third arm-body alternative — `=> Statement` — alongside the existing `=> Expression` and `=> do … end` forms, for arms in statement-position `case` and in `catch` arms. This removes the ergonomic friction of writing `=> do _x := y; end` for a one-line assignment-shaped arm body; the new spelling is `=> _x := y;`. The change does *not* relax §5.13. The four declined designs above were all ways of producing a value from a multi-statement block; the v0.126 addition is a syntactic convenience for the single-statement case in arm bodies that already accept `do … end` (which has type `()` and produces no value). No new value-producing construct exists; `do … end` retains its single meaning; the helper-method extraction is still the idiom for multi-statement arms in expression-position `case`. The question §5.13 settled — whether to add value-returning blocks — was re-examined during the v0.126 cycle and the same conclusion was reached: the four candidate designs still carry the same costs, the helper-method extraction still has independent merits, and `do … end`'s single meaning is still worth preserving. The v0.126 change addresses a different question (single-statement ergonomics in arm bodies) which §5.13 did not consider.

**v0.216 addendum: the binding atom is not a block expression.** The `(var x := E; body)` atom (spec §17.15; rationale [§3.12](#sec-the-binding-atom-names-a-subexpression)) names subresults inside one expression; it admits no statements — a clause is a binding, the body is one expression, and no effectful statement form can be spelled inside it. The four declined designs above were all ways of producing a value from a *statement sequence*; §5.13's conclusion — `do … end` has one meaning, multi-statement logic in value position is extracted into a named helper — stands unchanged.

<a id="sec-inline-arrays-and-array-kind-split"></a>
<a id="sec-inline-arrays-and-the-array-kind-split"></a>
### 5.14 Inline arrays and the array-kind split

v0.98 introduces inline arrays `[N]T` and retires the previous `T[]` (fixed-size, runtime-managed) form. The change has three motivations and four supporting design decisions.

**Foundational implementability.** Up through v0.97, the standard library's owning collections (`OwningArray<T>`, `OwningDictionary<K, V>`, etc.) were compiler intrinsics — their slot-take operations on the backing storage could not be expressed in pure Bezel because `T[]` did not admit per-element ownership tracking. This left the language's most safety-critical primitives in a "trust the compiler" position with no path for users to verify or extend. With v0.98's `[N owned]T?` form, the *per-slot ownership-transfer operations* — `move arr[i]` and the field-restoration discipline that goes with it — became expressible at the user level. For fixed-capacity owning containers, this was sufficient. The remaining intrinsic surface was the *runtime-sized backing storage* used by resizable owning collections like `OwningArray<T>` and `OwningDictionary<K, V>`; `[N owned]T?` requires a compile-time N. v0.99 closes that gap by introducing `OwningBuffer<T>`, a class wrapping runtime-sized owning storage with the same per-slot semantics extended to runtime-determined length; see [§5.15](#sec-owned-buffers-and-spans) for the full story. After v0.99, the intrinsic surface of the entire owning-collection family reduces to one well-scoped primitive (`OwningBuffer<T>`) plus the inline-array form (`[N owned]T?`); every resizable owning collection composes over these in pure Bezel.

**Disposal-discipline clarity.** `T[]` straddled two categories: it was a reference type (allocated with `new`) but was runtime-managed (no `Dispose`). This was an inconsistency users had to learn — every other heap-allocated reference type in Bezel has a real `Dispose` contract. v0.98 cleans this up: heap arrays (`Array<T>`, `OwningArray<T>`) are classes with real disposal; inline arrays are value types stored inline. The "runtime-managed" exception for arrays goes away. The remaining runtime-managed types are `string`, function values, and boxed values, which are genuinely interned/runtime-tied at the implementation level in ways `T[]` was not.

**FFI ergonomics.** Inline arrays have C-equivalent layout (packed elements, no header). The previous `T[]` had a Bezel-level header, requiring marshalling cost to convert to C arrays at FFI boundaries. Inline arrays `[N]byte` and similar mean a Bezel `extern method foo(buf: [16]byte)` declaration matches `void foo(char buf[16])` in C with no marshalling. This is a real performance and clarity win for FFI-heavy code, and was repeatedly cited as a gap during v0.97 verification.

The supporting design decisions:

**The array-kind split.** v0.98 commits to two array kinds: inline `[N]T` (value-typed, fixed size at compile time, no allocation) and heap (`Array<T>`, `OwningArray<T>`, class types, real `Dispose`). Users pick by use case: "I want a value-typed buffer" picks inline; "I want a resizable container that can grow" picks heap. A separate "heap fixed-size" type (à la `FixedArray<T>`) is deliberately not provided — heap arrays support fixed-size discipline by not calling resize methods. The taxonomic simplification keeps two array kinds (one syntactic form per kind) rather than four.

**Move-only value types.** Inline arrays with `[N owned]T?` or `[N owned]T` slots own their slot contents (the per-slot reference is non-null on `[N owned]T`, and may be null or non-null on `[N owned]T?`). Copying such an array would duplicate ownership of those contents, so copying is forbidden — the array is move-only. v0.98 introduces "move-only value types" as a small new type-system category, scoped tightly: only owning inline arrays exhibit it. This is a real new concept but it's foundational (move semantics for owning slots are unavoidable) and the rules are localized to one form. A future revision may extend the move-only category if user-defined move-only types prove necessary; this version does not anticipate that need. *(v0.200: the anticipated extension arrived — owning-classified choices joined the category; see [§9.6](#sec-choices-why-a-new-kind) and spec §35.4.)*

**Collection literals.** The literal `[1, 2, 3]` is now contextually typed: it produces whatever target type the context names (`[3]int`, `Array<int>`, etc.). A literal in a position with no target type is a compile error, which makes the construction site explicit about what's being built. The contextual typing reuses the same machinery as `null` (untyped null) and is the right cost-benefit tradeoff for keeping the literal syntax both flexible and unambiguous.

**Migration.** The change requires every `T[]` reference in user code to be rewritten as either `Array<T>` (the common case — most fixed-size T[] uses were just "I want a sequence of T"), `OwningArray<T>` (when the element type was owned), or `[N]T` (when truly fixed-size and inline storage is wanted). The standard library was swept once for v0.98; user code makes the corresponding edits on its own schedule. The mechanical conversion is supported by the compiler's diagnostics, which flag `T[]` references with explicit guidance on the replacement form.

<a id="sec-owned-buffers-and-spans"></a>
### 5.15 Owned buffers and spans

**The current shape (as of v0.188).** Three families of types provide runtime-sized buffer storage and views over it:

| Type | Role |
|---|---|
| `OwningBuffer<T>` ([§4.14](Bezel_Standard_Library.md#sec-owned-buffers-and-spans)) | Owning fixed-at-construction storage. Class T: slots are owned `T?`. Value T: slots are `T` directly. |
| `Span<T>`, `ReadOnlySpan<T>` ([§4.14](Bezel_Standard_Library.md#sec-owned-buffers-and-spans)) | Views over `OwningBuffer<T>`. Read-write and read-only respectively. |
| `ArraySpan<T>`, `ReadOnlyArraySpan<T>` ([§4.15](Bezel_Standard_Library.md#sec-arrayspant-readonlyarrayspant)) | Views over heap `Array<T>` (borrowing collection). Uniform mutation API across class/value T because slots are borrows. |
| `ReadOnlyStringSpan` ([§3.3](Bezel_Standard_Library.md#sec-readonlystringspan)) | Read-only view over a contiguous range of code points in a `string`. |
| `IReadOnlySpan<TElement>` ([§4.16](Bezel_Standard_Library.md#sec-ireadonlyspan)) | Interface unifying the read-only surface across all five concrete span types. Implemented by all of them. |

All spans are records carrying a borrow of their source (`OwningBuffer<T>`, `Array<T>`, or `string`). The buffer- and array-backed spans are **borrow-bearing** records — the rule of language spec [§9.7](Bezel_Language_Spec.md#sec-records-and-disposal) gives them lifetime tracking through existing machinery — while the string-backed span's source is runtime-managed, so §9.7 classifies it as *not* borrow-bearing: it carries no tracked lifetime constraint, which is exactly why spec §30.1 exempts it from the async parameter/result restrictions. Indexer access is bounds-checked against the span's `Length` (as of v0.105). Span construction is non-allocating record construction; the standard entry points are `AsSpan` / `AsReadOnlySpan` methods on the source (`string.AsSpan()`, `Array<T>.AsSpan()`, `OwningBuffer<T>.AsSpan()`, etc.) and the explicit constructors.

The remainder of this section explains how each piece was added and the trade-offs that produced the current shape. Readers wanting the operational details should follow the §-references into the standard library document.

---

v0.99 introduces two stdlib types: `OwningBuffer<T>` (a class wrapping runtime-sized owning storage) and `Span<T>` / `ReadOnlySpan<T>` (records carrying views into a buffer; `Span<T>` is read-write as of v0.100, `ReadOnlySpan<T>` is read-only). v0.102 generalizes all three to admit value-typed T in addition to class-typed T. Together they complete what v0.98 started — making the owning-collection family expressible in pure Bezel — and add a safe, no-`unsafe`-keyword escape hatch for working with raw storage of either category.

**The gap v0.98 left.** v0.98's `[N owned]T?` admitted per-slot ownership semantics at the user level for fixed compile-time N. Resizable owning collections — `OwningArray<T>`, `OwningDictionary<K, V>`, `OwningSet<T>`, etc. — need runtime-sized owning storage. Until v0.99, the standard library's resizable owning collections remained compiler intrinsics: the per-slot operations *could* be expressed in user Bezel (via the [§28.8.1](Bezel_Language_Spec.md#sec-the-move-expression) move-and-null pattern), but the *underlying runtime-sized buffer* could not — no language syntax expressed "a class field of N owning slots where N is a constructor parameter."

**Why a class, not new language syntax.** A natural alternative would have been to extend inline arrays to admit a runtime-sized form, perhaps `[?owned]T?` with `?` denoting "runtime-determined." That would have been one additional language construct. Adding a stdlib class is the smaller intervention: the class is one new type, its surface is the standard indexer-and-move pattern that already applies to owning collections, and the language adds nothing new. The intrinsic boundary stays inside the standard library rather than expanding into the type-system primitives.

**The class/value category split (v0.102).** v0.99 restricted `OwningBuffer<T>`, `Span<T>`, and `ReadOnlySpan<T>` to class-typed T. The restriction kept the v0.99 design tight: slots are `T?` (nullable references), the buffer owns each non-null slot's referent, `move buf[i]` is admitted with field-restoration, the destructor cascades. v0.102 extends to value-typed T (primitives, records, enums, non-move-only inline arrays). For value T the semantics simplify substantially: slots are `T` directly (no nullability wrapper); the setter just overwrites; `move buf[i]` is not admitted (values have no ownership to transfer); the destructor performs no per-slot work, only releasing the buffer's allocation. The two presentations are different specializations of the same generic class — the compiler resolves T's category at instantiation and emits the appropriate semantics.

The motivating use case was binary buffers: `OwningBuffer<byte>` for file-format parsing, network protocols, image headers. Under the v0.99–v0.101 design these did not exist — `byte` is value-typed and the class constraint excluded it. Workarounds (use `Array<byte>`, copy data, etc.) all imposed costs the design should not have required. The honest fix is to admit value-typed T at the language-design level rather than continuing to ship a class-only buffer family.

The cost of the generalization is a small amount of additional design machinery: the slot type and several method signatures dispatch on T's category. The compiler must distinguish at instantiation time between "T is a class type" (existing semantics) and "T is a value type" (new semantics). This is *type-parameter-category-dependent specialization* — a new kind of generic specialization that previously did not exist in Bezel. v0.102 admits it as a compiler-known behavior specific to these three types (`OwningBuffer<T>`, `Span<T>`, `ReadOnlySpan<T>`); it is not a general user-available mechanism. Future revisions may generalize the mechanism if other types benefit, but that is not committed work. *(v0.200: the choice classification took the recorded generalization path — spec §3.6's second scoped exception; see [§9.6](#sec-choices-why-a-new-kind).)*

**Why move-only value types are not yet admitted.** The owning inline arrays `[N owned]T` and `[N owned]T?` are value-typed but move-only (rationale [§5.14](#sec-inline-arrays-and-array-kind-split) and language spec [§15.3](Bezel_Language_Spec.md#sec-move-only-value-types)). A buffer slot containing a move-only value type would itself be move-only — the slot setter would need to be `set(owned)`-equivalent for the inline-array contents, with the previous slot's owned slots being disposed before the new is set. This is implementable but adds a third category to the slot-semantics dispatch (class T, non-move-only value T, move-only value T) without unlocking a clearly-motivated use case. Deferred. Users who need a runtime-sized array of fixed-size owning arrays today can express it manually with `OwningArray<MyOwningBoxClass>` or similar wrappers.

**Why `OwningBuffer<T>`'s slots are nullable for class T.** The class-T buffer's slot type is `T?` rather than `T`. The slot-take pattern `move buf[i]` produces an owned `T?` and leaves the slot moved-from; the standard restoration is `buf[i] := null`. Non-nullable slots would require restoration via "assign a fresh owned T," which is inconvenient when the slot's intended state is "empty after take." Resizable owning collections need precisely the "empty after take" semantic — `OwningArray<T>` shrinks its used range without disposing the underlying buffer, `OwningDictionary<K, V>`'s buckets routinely hold null between rehashings. The nullable form serves these naturally. For value T the question doesn't arise — `move` isn't admitted, so there's no "empty after take" state to express, and slots are `T` directly.

**Why `Span<T>` and `ReadOnlySpan<T>` are records, not a `ref struct`.** C#'s `Span<T>` is a `ref struct` — stack-only, cannot escape to the heap. This gives it the strongest possible lifetime guarantees but introduces a new type kind that pervades the language (rules for where ref structs can appear, how they interact with generics, etc.). Bezel's spans are records carrying a borrow of an `OwningBuffer<T>`; the existing borrow-bearing-record rule ([§9.7](Bezel_Language_Spec.md#sec-records-and-disposal) of the spec) gives them lifetime tracking through machinery the language already has. The trade-off: Bezel spans participate in the standard borrow-lifetime tracking — they can be locals, parameters, and return values; a span may **not** be stored in a class field (v0.180 — a record-carried borrow can be consumed through access paths with no per-access disposed-flag check, so §28.3's field-store trust regime is unavailable to it; the earlier "where the lifetime tracker can statically prove the constraint holds" gloss had no provable case and is withdrawn, consistent with the #1438/#1448 no-backstop reasoning); a span *local* can also cross `await` points when its source is co-resident in the same async frame — an owned local, `using var`, or `owned` parameter of that method (spec §30.1, v0.179); a span may **not** be an `async` method's parameter or result, since a caller-side source cannot be shown to outlive the state-machine frame (#1438). Programs whose buffer lifetimes cannot be proven sufficient are rejected by the borrow tracker. The C# comparison has narrowed on both sides: neither language admits a span-typed class field, and C# 13 now admits span locals inside async methods though never across an `await`; what the record-plus-borrow-tracking form still buys is the frame-resident case — a Bezel span local may cross an `await` when its source lives in the same async frame — with the lifetime tracker, not a type kind, enforcing the constraint. This trade follows the same logic v0.98 applied to inline arrays — prefer existing mechanisms (borrow-bearing records, lifetime tracking) over new type-system primitives.

**Why no `unsafe` keyword.** C# pairs `Span<T>` with `unsafe` blocks for the cases where the developer needs raw-pointer access. Bezel's path is different: the user-facing surface never exposes raw pointers, pointer arithmetic, or untyped memory access. `OwningBuffer<T>` allocates through `new` (a normal class constructor), indexes through a bounds-checked indexer, and disposes through the standard destructor cascade. `Span<T>` indexes through the buffer's indexer. Operations that would need `unsafe` in C# — direct memory writes, byte-swapping, type punning — go through FFI: declare a C function that does the work and call it. The FFI surface ([§32](Bezel_Language_Spec.md#sec-foreign-function-interface) of the spec) already accepts inline arrays as FFI-boundary types, so the C interop is direct. The cost is one extra named function per low-level operation, versus a free-for-all `unsafe` block; the benefit is that Bezel's user-facing language remains fully checked.

**What this does not solve.** Two deliberate gaps remain in the current span family:

1. *Stack-allocated runtime-sized buffers* (C# `stackalloc`). Bezel's inline arrays handle fixed-size cases; runtime-sized stack allocation would require new language machinery and a story for how the stack-bound lifetime interacts with closures. Deferred — currently low priority.
2. *`Span<T>` over inline arrays `[N]T`*. Would need a new borrow-source kind tying the span's lifetime to a stack frame, with rules for closure capture, exception unwinding, and recursive calls. Substantial design work for a narrow performance gain. Deferred indefinitely; revisit if a specific need arises.

Earlier gaps that have since been closed: value-typed T (v0.102), byte-buffer accessors (v0.103), string-source spans (v0.104, v0.106), heap `Array<T>`-source spans (v0.107). See the chronological narrative below.

**The read/write split.** `Span<T>` is the read-write view; `ReadOnlySpan<T>` is the read-only view. The split was deferred briefly in v0.99 (which shipped both types as read-only) and resolved in v0.100 by giving `Span<T>` an indexer setter that delegates to the underlying buffer's owned-setter. The mechanism is the standard one: the span carries a borrow of the buffer, and calling a setter through a borrowed reference is the same operation as calling any instance method on a borrowed reference. No new lifetime rules are needed. `ReadOnlySpan<T>` remains the read-only variant; its absence of a setter is what makes it usable as an API-boundary contract for "this code will not mutate the underlying buffer through the span."

**API surface expansion.** v0.101 thickens the span surface to support common use cases without going through the underlying buffer: `IsEmpty`, `IndexOf`, `Contains`, `SequenceEqual` (search and equality on both span types); for-loop integration (a direct-indexed-loop desugaring rule in language spec [§29.2](Bezel_Language_Spec.md#sec-desugaring-of-for), parallel to the inline-array rule). For class-typed `Span<T>`: `Clear`, `MoveFrom`, `Reverse` (bulk mutation by ownership transfer; no `Fill`/`CopyFrom` because class references cannot be implicitly cloned). For value-typed `Span<T>` (added in v0.102): `Fill`, `CopyFrom`, `Reverse` (bulk mutation by value copy; no `Clear`/`MoveFrom` because values have no "empty" state and no ownership transfer). The category-dependent mutation API is a direct consequence of the ownership-vs-value-semantics distinction.

**Byte-buffer accessors (v0.103).** When T is `byte`, the spans are commonly used for binary I/O — file formats, network protocols, image headers, serialization. v0.103 adds endianness-aware reads and writes for the 16/32/64-bit integer types (signed and unsigned) and IEEE 754 floats on `Span<byte>` and `ReadOnlySpan<byte>`, via extension methods (stdlib [§4.14](Bezel_Standard_Library.md#sec-byte-buffer-accessors)). The methods name the endianness — `ReadInt32LittleEndian`, `WriteUInt64BigEndian`, etc. — rather than taking an endianness parameter or relying on a platform default; both alternatives invite the class of bugs where someone forgets that a particular format uses a specific byte order. Each method has a `Try*` variant that returns `false` instead of throwing on insufficient input, for incremental parsers that treat short input as end-of-stream rather than as an error. No offset parameter is provided; callers slice first (`header.Slice(8).ReadInt32LittleEndian()`), keeping the access model uniform with the rest of the span API. The implementation is pure byte-shuffling for integer types and routes through `BitConverter` ([§2.12](Bezel_Standard_Library.md#sec-bitconverter)) for floats. The choice to put `BitConverter` in `System` rather than gating it behind FFI keeps the user-facing language free of bit-level intrinsics while still admitting the operations that serialization, hashing, and exact float comparison need.

**String spans (v0.104).** The `ReadOnlyStringSpan` type (stdlib [§3.3](Bezel_Standard_Library.md#sec-readonlystringspan)) is a read-only view over a contiguous range of code points in a `string`, parallel to `ReadOnlySpan<char>` but with a string source instead of an `OwningBuffer<char>` source. The natural companion to `string.AsSpan()` for zero-allocation substring operations — tokenization, parsing, prefix/suffix checks — without materializing intermediate strings. The use case is the same one that motivates C#'s `ReadOnlySpan<char>` over `string`.

The design choice that took time was whether to extend `ReadOnlySpan<char>` to admit a second source type (alongside `OwningBuffer<char>`) or introduce a separate type. Extending the existing type would either change its record shape (breaking v0.99-v0.103 callers) or require a general source-polymorphism mechanism (an `IBufferSource<T>` interface or similar) that v0.104 should not be introducing on its own. The separate type — `ReadOnlyStringSpan` — leaves `ReadOnlySpan<char>` unchanged, makes the source visible at API boundaries, and uses the existing borrow-bearing-record machinery for lifetime tracking (the span's `Source` field carries a borrow of the string).

The cost is that two type names cover the "read-only view of char sequence" space — `ReadOnlySpan<char>` for buffer-backed views, `ReadOnlyStringSpan` for string-backed views. Methods that want either need overloads or to be written against the more common type (typically `ReadOnlyStringSpan`, since most char views in practice come from strings). C# avoids this through implicit conversion from `string` to `ReadOnlySpan<char>`; Bezel's nominal record typing makes the conversion explicit. The friction is real but bounded — most parsing code is written against one type or the other, not both.

The asymmetric ASCII-byte view (a read-only byte view over an ASCII string) was not addressed in v0.104. It would require a similar borrow-of-string mechanism as `ReadOnlyStringSpan` but applies only to ASCII strings and needs a runtime check at construction. The deferred work was delivered in v0.106 as `ReadOnlyAsciiByteSpan` — see the v0.106 paragraph below.

**Span-level bounds checking (v0.105).** v0.99-v0.104 declared the `Span<T>` and `ReadOnlySpan<T>` indexers with a delegating expression body — `public property [i: int]: T? => Buffer[Start + i]` — which checked the index only against the underlying buffer's length, not against the span's `Length`. If a `Span<int>` with `Length = 5` was constructed over a 100-element buffer, `span[10]` would silently succeed: `Buffer[Start + 10]` was within the buffer's bounds, so no exception fired. This was a latent correctness bug — the whole point of having a separate `Span<T>` type is to enforce the range restriction the span advertises. v0.105 fixes it by giving each indexer an explicit block-form body with a span-level bounds check:

```bezel
public property [i: int]: T?
  get => do
    if i < 0 or i >= Length then
      throw new IndexOutOfRangeException();
    end;
    return Buffer[Start + i];
  end;
  set(owned) => do
    if i < 0 or i >= Length then
      throw new IndexOutOfRangeException();
    end;
    Buffer[Start + i] := value;
  end;
end;
```

The same fix applies to `Span<T>`'s setter (class T and value T), `ReadOnlySpan<T>`'s getter (class T and value T), and the `move span[i]` form (which now bounds-checks against `span.Length` before delegating to the underlying buffer). The bounds-check semantics align with C#'s `Span<T>`/`ReadOnlySpan<T>` and with v0.104's `ReadOnlyStringSpan` (which used the explicit form from the start).

This is technically a behavior change for code that compiled against v0.99-v0.104. Programs that depended on the bug — reading or writing outside the span's declared range while the underlying buffer still admitted the access — will now throw `IndexOutOfRangeException` instead of silently succeeding. Such programs were almost certainly already buggy; the fix converts a silent failure into a clear error. No source-syntax change is required; correct programs continue to work without modification.

**ASCII byte spans (v0.106; retired v0.188).** v0.106 added `ReadOnlyAsciiByteSpan` — a read-only byte view over an ASCII string, parallel to `ReadOnlyStringSpan` (v0.104) but with `byte` elements, constructed via the validated `string.AsAsciiByteSpan()` / `TryAsAsciiByteSpan(out)` — and v0.188 retired it as a changed-circumstances removal: the FFI half of its motivation never materialized (a borrow-carrying record has no C-compatible form — language spec [§32.5](Bezel_Language_Spec.md#sec-ffi-compatible-types) admits only the §32.13 C-compatible records, which spans are not), the I/O half was overtaken by v0.165's span-destination encoding (`Encoding.GetBytes(s, destination: Span<byte>)` into a caller-reused buffer — every string, unconditional, zero per-call allocation), nothing consumed or implemented the type, and its admitted-but-unchecked positional constructor was the standard library's only construction surface documented as silently lossy on misuse; the full record is the v0.188 changelog entry ([`Bezel_Changelog.md`](Bezel_Changelog.md)). Should profiling evidence ever demand a zero-copy ASCII byte view again, the sanctioned re-addition shape is a *validated-only* view — construction APIs only, no public unchecked constructor — a purely additive stdlib change.

**Array spans (v0.107).** The `ArraySpan<T>` and `ReadOnlyArraySpan<T>` types (stdlib [§4.15](Bezel_Standard_Library.md#sec-arrayspant-readonlyarrayspant)) are span views over an `Array<T>` source, parallel to `Span<T>` and `ReadOnlySpan<T>` (over `OwningBuffer<T>`) but with a borrowing-collection source instead of an owning one. The natural companion to `Array<T>.AsSpan()` for passing a sub-range of an array to a method without copying.

The mechanics diverge from `Span<T>`/`ReadOnlySpan<T>` in one substantive way: `Array<T>` slots store borrows, not owned values. This changes the slot semantics in three places: (a) the indexer return type is `T` directly (the array's element type), not `T?` (no nullability wrapping — the array stores what it was instantiated with); (b) the setter takes the value with the default parameter convention rather than `set(owned)` (no ownership transfer; no dispose-previous); (c) `move arrSpan[i]` is *not* admitted for any T (borrowed slots have no ownership to transfer).

The mutation API simplifies as a consequence. `Span<T>` splits its bulk-mutation surface by T's category — `Clear`/`MoveFrom` for class T (which has owned slots), `Fill`/`CopyFrom` for value T (where copying is well-defined). `ArraySpan<T>` provides a single uniform surface — `Fill`/`CopyFrom`/`Reverse` — for both categories, because borrowed slots have no ownership constraints regardless of T. The category-dependent split was a consequence of ownership semantics that `Array<T>` doesn't have.

The choice of a separate type (vs extending `Span<T>`/`ReadOnlySpan<T>` to accept an `Array<T>` source) is the same one made in v0.104 and v0.106: extending the existing types would require source polymorphism, which would either break their record shape or require a general source-polymorphism mechanism this revision should not introduce on its own. The separate-type pattern is now the established Bezel approach for span family expansion. With v0.107, the span family contains six types: `Span<T>` and `ReadOnlySpan<T>` (`OwningBuffer<T>`-backed, v0.99-v0.102), `ReadOnlyStringSpan` (`string`-backed, v0.104), `ReadOnlyAsciiByteSpan` (ASCII-`string`-backed, v0.106), and `ArraySpan<T>` and `ReadOnlyArraySpan<T>` (`Array<T>`-backed, v0.107). Methods that want to operate on "any span" need overloads — Bezel's nominal record typing doesn't admit implicit conversions between them. The friction is real but bounded; most code is written against a specific source type.

The `Array<T>` class itself ([§4.4](Bezel_Standard_Library.md#sec-arrayt)) gets eight new methods in v0.107: four `AsSpan` overloads (no-arg, `(start)`, `(start, length)`, `(r: Range<int>)`) returning `ArraySpan<T>`, and four matching `AsReadOnlySpan` overloads returning `ReadOnlyArraySpan<T>`. `AsSpan` returns the writable form by default (matching `Array<T>`'s mutable nature); callers wanting read-only either call `AsReadOnlySpan` directly or call `.AsReadOnly()` on the writable form.

A structural difference from the `OwningBuffer<T>`-backed spans is worth noting: `Array<T>`'s `Count` can change during the array's lifetime, while `OwningBuffer<T>`'s `Length` is fixed. A span's range is set at construction and does not auto-update if the underlying array resizes. The intended usage pattern is short-lived spans — pass the span to a method that reads or writes through it without resizing the source. Programs that need a stable view across mutations should copy the relevant range into a fresh container. The stdlib [§4.15](Bezel_Standard_Library.md#sec-arrayspant-readonlyarrayspant) prose flags this with a "Caveat" paragraph; the v0.107 design accepts this footgun rather than designing around it (the alternative — making spans observe array resizes, or rejecting span construction over resizable sources — would either require new language machinery or eliminate the use case entirely).

**Unifying read-only spans through an interface (v0.108).** With v0.107, the span family contained six concrete types. Methods that wanted to accept "any read-only span" had no way to express that — they had to declare per-source overloads, accept one form and require callers to convert, or duplicate their implementation. v0.108 introduces `IReadOnlySpan<TElement>` (stdlib [§4.16](Bezel_Standard_Library.md#sec-ireadonlyspan)), an interface implemented by all six concrete span types, that unifies the read-only access surface.

The mechanism is straightforward and uses existing language machinery. Spans are records, records may implement interfaces (language spec [§9.7](Bezel_Language_Spec.md#sec-records-and-disposal)), and the borrow-bearing-record boxing rule (language spec [§8.6](Bezel_Language_Spec.md#sec-boxing-of-borrow-bearing-records)) tracks the borrow's lifetime through the boxed value. A span passed as an `IReadOnlySpan<TElement>` parameter boxes; the boxed value's lifetime is bounded by the source of the underlying borrow; the parameter cannot be stored in a long-lived location, returned from a method without lifetime evidence, or captured by an escaping closure. These are the standard borrow-bearing-record constraints, not new rules.

The element-type parameterization is exact and explicit. Each concrete span implements `IReadOnlySpan<TElement>` with `TElement` set to whatever the concrete indexer actually returns: `Span<MyClass>` (which has `[i: int]: MyClass?`) implements `IReadOnlySpan<MyClass?>`; `ArraySpan<MyClass>` (which has `[i: int]: MyClass`) implements `IReadOnlySpan<MyClass>`; `ReadOnlyStringSpan` implements `IReadOnlySpan<char>`; and so on. There is no implicit conversion across nullability or element types — the interface parameter must match exactly. Authors who want full breadth provide two overloads (one for `IReadOnlySpan<T>`, one for `IReadOnlySpan<T?>`); the friction is real but localized at API boundaries.

The interface's surface is deliberately minimal: indexer-get, `Length`, `IsEmpty`, `IndexOf`, `Contains`, and `SequenceEqual`. `Slice` is intentionally omitted — putting it on the interface would force the return type to be `IReadOnlySpan<TElement>`, propagating the interface-typed handle (and its virtual-dispatch cost) through the slicing chain. Callers who need to slice through the interface can recover the concrete type via a runtime check (`if s is ReadOnlySpan<T> then ...`) or read the relevant elements into a fresh container. `SequenceEqual` *is* on the interface; the convenience of cross-source equality through the interface outweighs the cost of dispatching two indexer reads per element.

The performance cost is opt-in and per-call. Code that takes a concrete span type continues to compile to direct-dispatch machine code identical to v0.107. Code that takes `IReadOnlySpan<TElement>` accepts virtual dispatch at the indexer and at every other interface-routed call — vtable lookup, indirect call, no inlining. For tight inner loops over many elements, the cost is significant (typically 5-10x slowdown depending on what the loop body does). For utility code that doesn't iterate hot, the cost is negligible. The recommended pattern is: in performance-sensitive APIs, take concrete span types (possibly via overloads); in utility or convenience APIs, take the interface. The choice is the method author's, made by signature.

No writable interface (`IMutableSpan` or similar) is introduced in v0.108. The writable side has substantive semantic differences across span families — `Span<T>` for class T has a disposing `set(owned)` setter; `ArraySpan<T>` has a non-disposing `set` setter taking a borrow; value-T setters are plain copies. Unifying these under a single writable interface would either pick one model and exclude the others, or fork the contract by source kind, defeating the unification. The read-only side is genuinely uniform: every span supports indexer-get returning the slot's element. That's enough for one interface, and one interface is what v0.108 adds. A partial writable interface (covering only the non-owned-slot writable spans) may be added in a later revision if a real use case emerges.

**Ergonomics pass (v0.109).** v0.109 is a pure-ergonomics release that fills two gaps in the span family surface: symmetric CopyTo/MoveTo methods, and `AsSpan` / `AsReadOnlySpan` factories on `OwningBuffer<T>`.

The CopyTo/MoveTo additions parallel the existing CopyFrom/MoveFrom methods. Each concrete span type's mutable form gets a symmetric method:

| Source | New method |
|---|---|
| `Span<T>` (value T) | `CopyTo(destination: Span<T>)` |
| `Span<T>` (class T) | `MoveTo(destination: Span<T>)` |
| `ReadOnlySpan<T>` (value T) | `CopyTo(destination: Span<T>)` |
| `ArraySpan<T>` | `CopyTo(destination: ArraySpan<T>)` |
| `ReadOnlyArraySpan<T>` | `CopyTo(destination: ArraySpan<T>)` |
| `ReadOnlyStringSpan` | `CopyTo(destination: Span<char>)` |

Each is equivalent to the corresponding CopyFrom/MoveFrom on the receiving side — `source.CopyTo(dest)` is `dest.CopyFrom(source)`. Both directions are provided because the natural call form depends on which side the caller holds. Tight processing loops typically write `dest.CopyFrom(source)` when the destination is the new local being filled; pipeline-style code typically writes `source.CopyTo(dest)` when chaining transformations left-to-right. Neither form is strictly necessary; both reduce friction.

The `ReadOnlyStringSpan` CopyTo destination is `Span<char>` — the OwningBuffer-backed writable form, since there is no writable string-backed span (strings are immutable).

`ReadOnlySpan<T>` for class T does not get CopyTo. Reading from a read-only class-T span produces a borrow; writing into a Span<T> for class T requires ownership transfer (the `set(owned)` setter); the two are incompatible. Code that needs this pattern moves through the underlying buffer or uses a different ownership model entirely.

CopyTo is deliberately *not* added to the `IReadOnlySpan<TElement>` interface (v0.108). Two reasons. First, the destination type varies by source family — `ReadOnlyArraySpan<T>.CopyTo` takes `ArraySpan<T>`; `ReadOnlySpan<T>.CopyTo` takes `Span<T>`; the string-family forms take `Span<char>` and `Span<byte>` respectively. A single interface method would have to pick one destination shape, fragmenting the implementations. Second, the class-T-borrow vs class-T-owned incompatibility (above) means CopyTo cannot be uniformly defined across all TElement instantiations of `IReadOnlySpan<TElement>` — there is no class-T destination Span that accepts borrowed-source content via copy. Code that wants "copy from any read-only span" writes an extension method against the concrete span types, accepting one destination shape per source family.

The `OwningBuffer<T>.AsSpan()` / `AsReadOnlySpan()` family adds eight methods (four overloads each, parallel to v0.107's `Array<T>.AsSpan()` and v0.104's `string.AsSpan()`). The methods replace `new Span<T>(buf, 0, buf.Length)` boilerplate at every span call site, completing the three-way symmetry across the standard collection sources (string for `ReadOnlyStringSpan`; Array for `ArraySpan<T>`/`ReadOnlyArraySpan<T>`; OwningBuffer for `Span<T>`/`ReadOnlySpan<T>`).

`OwningArray<T>.AsSpan()` was deliberately omitted. The class would need either a new span type with owned-slot semantics matching its element-ownership model, or exposure of its internal buffer through a public method. Neither is justified by current demand. Users with an `OwningArray<T>` who want span access can copy the relevant range into a fresh `OwningBuffer<T>` and call `AsSpan` on that — at the cost of one allocation. If real demand for a direct OwningArray span emerges in user code, a future revision can add the missing type.

**Migration.** No user code needs to change for v0.102 through v0.109. v0.101's spans (class-T-only) are a strict subset of v0.102's. v0.103, v0.104, v0.106, v0.107, v0.108, and v0.109 are pure stdlib additions (byte-buffer accessors and `BitConverter` in v0.103; `ReadOnlyStringSpan` and `string.AsSpan()` overloads in v0.104; `ReadOnlyAsciiByteSpan` and `string.AsAsciiByteSpan` / `TryAsAsciiByteSpan` in v0.106; `ArraySpan<T>`, `ReadOnlyArraySpan<T>`, and `Array<T>.AsSpan` / `AsReadOnlySpan` overloads in v0.107; `IReadOnlySpan<TElement>` interface and six `SequenceEqual(other: IReadOnlySpan<TElement>): bool` overloads on the concrete span types in v0.108; symmetric CopyTo/MoveTo methods on the span family and `OwningBuffer<T>.AsSpan` / `AsReadOnlySpan` overloads in v0.109). v0.105 is the bounds-check fix described above — only programs that read or wrote outside their declared span range will see a change (those will now throw). Programs that compiled against v0.101 compile against v0.109 without source modification.

### 5.16 Collection literals for complex collections

Bezel's collection-literal form `[e1, e2, ...]` is contextually typed: the literal has no standalone type and is well-typed only where a target type is determinable (language spec [§15.4](Bezel_Language_Spec.md#sec-collection-literals)). v0.110 broadens the set of target types and pins down the previously-underspecified dictionary case.

**Why the existing colon-pair dictionary syntax.** The dictionary form `[k: v, ...]` was present in the spec before v0.110 but documented in a single sentence with no examples, no ordering semantics, and no statement of edge-case behavior. v0.110 keeps the syntax — it was the right choice — and fills in the specification. The syntax was weighed against three alternatives. The arrow form `[k => v]` would overload `=>`, which Bezel uses for case arms and expression-bodied accessors; reusing it for data would make `[x => y]` ambiguous to a reader scanning for control flow. The brace form `{k: v}` would introduce a fourth bracket kind (`()`, `[]`, `<>`, `{}`) competing for visual distinctness, where `[]` already carries collection-literal meaning and `{}` appears only inside string interpolation; the cost is a permanent extra syntactic category for a single use. The tuple-list form `[(k, v), ...]` would require tuple types, which Bezel does not provide (deferred per [§18](#sec-things-deferred)); the named-record workaround `[new Pair(k, v), ...]` is verbose and reads as a list of pairs, not a mapping. The colon-pair form is compact, distinct from the bare sequence literal, familiar from JSON/Python/Swift/Ruby, and overloads no token in a conflicting role. The one parsing subtlety — distinguishing `[a: b]` (dictionary) from a hypothetical type-annotated expression — does not arise because Bezel has no inline expression type-annotation syntax; the grammar disambiguates purely on the presence of a top-level colon in a literal element.

**Why broaden to LinkedList / Stack / Queue.** Before v0.110 the supported target list named only inline arrays, `Array`/`OwningArray`, `Set`/`OwningSet`, and `Dictionary`/`OwningDictionary`. `LinkedList<T>`, `Stack<T>`, `Queue<T>` and their owning variants are sequence-shaped — a literal `[1, 2, 3]` has an obvious meaning for each — and excluding them was an omission, not a deliberate restriction. The only design question was element-order convention. For lists and queues the convention is unsurprising (textual order is head-to-tail / front-to-back). For stacks there were two defensible readings: left-to-right as push order (first element ends at the bottom) or left-to-right as pop order (first element on top). v0.110 picks push order — `[1, 2, 3]` means "push 1, push 2, push 3," so 3 is on top — because it lets a reader trace the literal as a sequence of construction operations, consistent with how the list and queue literals read. The pop-order alternative would have made the literal read "as the stack looks from the top," which is convenient for some mental models but breaks the uniform "textual order = construction order" rule the other sequence types follow.

**The user-defined sequence-literal protocol (v0.111).** v0.110 hard-coded the supported target types; v0.111 opens sequence-literal construction to user-defined types via a named static factory, `FromCollectionLiteral` (language spec [§15.4.1](Bezel_Language_Spec.md#sec-the-user-defined-sequence-literal-protocol)). The design was guided by a comparison with C#'s `[CollectionBuilder]` mechanism, which solves the same problem and surfaced three lessons.

*Mechanism: named static factory, not an attribute.* C# opts a type in via `[CollectionBuilder(typeof(BuilderType), "Create")]` — an attribute naming a separate non-generic builder class that holds the static generic `Create<T>(ReadOnlySpan<T>)`. The indirection through a separate builder type exists because C#'s attribute argument needs a `typeof` that cannot cleanly name a generic instantiation, and because static methods interact awkwardly with the generic type itself in their model. Bezel has no general attribute system, so the natural "explicit opt-in" equivalent is *declaring a specifically-named static method*. And a Bezel static method on a generic type may freely reference the type's own parameters — the recognized factory signature does exactly that (`public static method FromCollectionLiteral(elements: ReadOnlySpan<T>): owned C<T>`, spec §15.4.1) — so the factory goes *directly on the collection type* with no builder-type indirection. The result is simpler than C#'s: one method on the type, no attribute, no separate builder class.

*Element type: read from the factory signature, not inferred.* C#'s own design documents flag an unresolved wart: with `[CollectionBuilder]` alone the compiler cannot reliably determine the collection's element type, so C# additionally requires the type to define its iteration type (implement `IEnumerable<T>` or expose a `GetEnumerator`). Bezel's named-factory approach has no such problem — the element type *is* the `ReadOnlySpan<T>` (or `OwningArray<T>`) parameter's element type, declared right there in the signature the compiler is already looking up. There is no secondary requirement and no inference. This is a case where examining C#'s difficulty produced a cleaner Bezel design rather than a copy.

*Ownership: two factory shapes, a Bezel-specific concern.* C# has no ownership system, so its single `ReadOnlySpan<T>` factory shape suffices. Bezel's borrowing/owning collection duality requires two shapes: the borrowing form takes `ReadOnlySpan<T>` (the compiler synthesizes a temporary span over the borrowed element values); the owning form takes `owned OwningArray<T>` (the compiler builds a temporary owned array, transferring each owned element expression into it, and hands ownership to the factory, which drains it). Exactly one shape per type; declaring both is rejected because the literal's element-expression ownership would not unambiguously pick a target. The owning form's partial-failure behavior (an element expression throwing mid-construction) folds into the existing `OwningArray<T>`-literal exception-path discharge — no new rule.

*One opt-in path, not two.* C# also supports a duck-typed fallback (implement `IEnumerable<T>` + an `Add` method + a parameterless constructor, no attribute). Bezel deliberately does not replicate this. The specification is careful to keep exactly one structural-dispatch rule (`Contains` for `in`); a second "your type became literal-constructible because it happens to have an `Add` method" path would be exactly the kind of accidental enrollment that rule's deliberate scarcity guards against. C# carries the dual path largely for backward compatibility with pre-existing collection-initializer types; Bezel has no such legacy and chooses the single explicit path.

*A new recognition category, named honestly.* Bezel now has three ways the compiler recognizes a type's participation in a language construct: interface-based (the iteration protocol, [§29.1](Bezel_Language_Spec.md#sec-the-protocol)); the single structural-by-shape rule (`Contains`/`in`); and now name-based (`FromCollectionLiteral`). Name-based recognition — "declare this exact `public static` method with a recognized signature" — is the closest available analogue to C#'s explicit attribute opt-in given that Bezel has neither attributes nor (yet) static interface members. Static interface members have since shipped (v0.176, spec §11.8, with `ISteppable<T>` now real — stdlib §2.19), and promoting `FromCollectionLiteral` to an `ICollectionLiteralTarget<T>` interface method with the same name and signature is the recorded follow-up (spec §11.8) — recognition shifts from name-based to interface-based without breaking any user code. The name and signature were chosen to be interface-promotable, and that is now an open path rather than a bet on a future feature.

*Dictionaries stay out, matching C#'s staged path.* C# deliberately excluded dictionaries from collection expressions and is still, two years on, designing dictionary expressions as a separate feature. The pair-shaped literal needs its own factory design (a paired-span or key/value-span shape) and the design space is unsettled even in a mature language. v0.111 covers user-defined *sequence* collections only; user-extensible dictionary literals remain deferred, for the same reason C# deferred them.

**What is still deferred.** User-extensible *dictionary*-literal construction (the `[k: v, ...]` form for user-defined map-like types) remains deferred — see [§18](#sec-things-deferred). The built-in `Dictionary`/`OwningDictionary` keep the dictionary-literal form; user map-like types must use ordinary constructors until a future pass designs the paired-factory protocol.

<a id="sec-why-no-class-deconstruction"></a>
### 5.17 Why no class deconstruction

A recurring request is positional destructuring of class objects — `var (a, b) := someClass;` — paralleling the record-destructuring of [§19.3](Bezel_Language_Spec.md#sec-patterns). It was evaluated in full and declined. This section records the analysis so the decision is not silently re-litigated.

The motivating case is the multi-owned-value return: a method that produces several owned resources at once. This is already fully expressible. A class may own multiple fields ([§28.5](Bezel_Language_Spec.md#sec-owned-fields)); a method may return `owned C`; a single `using var` on the result discharges the whole aggregate, the destructor cascade disposing every owned field in reverse declaration order. The `OwningDictionary<K, V>.Drain()` case (stdlib [§4.9](Bezel_Standard_Library.md#sec-owneddictionaryk-v)) is exactly this pattern: `DrainedEntry<K, V>` is a class that owns its `Value`, iterated through `IOwningEnumerable<T>`. No language feature beyond what already exists is needed for the capability.

What class deconstruction would add is therefore *only* notation: referring to `conn` instead of `pair.Connection`. Three considerations made that notation not worth its cost.

First, the naive form — "destructuring disposes the class and yields its fields" — is unsound. A class destructor runs arbitrary user code and, per [§28.5](Bezel_Language_Spec.md#sec-owned-fields), runs *before* the owned-field auto-dispose cascade; destructor bodies routinely use the very fields a deconstruction would try to extract. "Dispose the container but keep its fields alive" inverts the dependency disposal embodies: disposal *is* the teardown of those fields. Extraction (move the fields out, transferring ownership) and disposal (the container tears the fields down) are opposite operations on the same slots; they cannot both happen.

Second, the sound form is a separate, opt-in `Deconstruct`-style method that *moves* each owned field out (transferring ownership) and consumes the receiver, leaving it moved-from and exempt from the field-restoration rule of [§28.8.1](Bezel_Language_Spec.md#sec-the-move-expression) — a new ownership-system rule ("a deconstruct method consumes its receiver, waiving restoration for fully-moved-out fields"). The language already waives restoration in one place — inside a destructor body ([§28.8.1](Bezel_Language_Spec.md#sec-the-move-expression), "the field-restoration rule does not require reassignment inside a destructor") — but that waiver rests on the destructor being *the* designated teardown site: the object's lifetime provably ends there and no later code can observe it. A `Deconstruct` method has neither property; it is an ordinary method, the husk survives the call, and other references to the object may still be live. The destructor carve-out therefore does not extend to it, which is exactly why a genuinely new rule (not a reuse of the existing one) would be required. To keep the borrow checker unchanged, the consumption would have to be syntactically visible at the use site (an explicit `move` at the destructuring position, so the existing move-invalidation machinery applies rather than a new borrow concept). This is implementable and coherent, but it adds a rule to the ownership system — Bezel's most cost-sensitive subsystem, where the whole value proposition is that the rules are few and composable. Every rule there raises the baseline cost of the feature that is supposed to be invisible when it works.

Third, the benefit is sugar on a solved problem at low frequency. Named owning classes and `out owned` parameters cover the capability; the recurring instance (`Drain()`) is closed by a pure standard-library addition. Weighing a new ownership rule against "saves writing `pair.` twice" does not clear the bar a change to the ownership system should meet. Bezel's design philosophy already argues, for records-versus-tuples, that a name and a documented shape is a feature rather than a limitation; `pair.Connection` tells a reader what they hold, where a positional `conn` tells them less. The same argument applies to owned aggregates.

The conservative resolution is taken: the capability stays (owning classes), the sugar is declined (no class deconstruction, no tuples as a prerequisite), and the one real friction point (`OwningDictionary` draining) is removed at the library level rather than the language level. If a future revision finds the notation genuinely necessary — driven by evidence from real code, not design aesthetics — the `Deconstruct`-with-explicit-`move` design recorded here is the starting point.

<a id="sec-type-identity-not-reflection"></a>
### 5.18 Type identity, not reflection

Bezel provides `typeof(T)`, `value.GetType()`, the `is`/`as` operators, and a `Type` token carrying name, kind predicates, and lattice queries (stdlib [§2.13](Bezel_Standard_Library.md#sec-the-type-class)). It deliberately does *not* provide member-access reflection: no enumeration of fields, properties, or methods; no by-name member access; no attribute reading; no dynamic instantiation. This section records why the boundary sits exactly there, so the question is settled rather than perennially reopened.

**The boundary is principled, not merely unimplemented.** Member-access reflection is in direct tension with the language's two load-bearing commitments.

*Ownership has no reflective site.* Every ownership contract in Bezel attaches to a static program point: a parameter declared `owned`, a field declared `owned`, a `move` expression, a `using var`. The borrow checker reasons about these points. A reflective field read — `someType.GetField("conn").GetValue(obj)` — has no such point. Is the returned `Connection` a borrow of the still-living object, or a transfer that leaves the field moved-from? The call site is `GetValue`, whose signature is identical regardless of the field's ownership; there is nowhere to write the contract and nowhere for the checker to enforce it. C#-style reflection works precisely because the GC makes the question moot — every reference is equivalent and lifetimes are not tracked. Bezel's whole value proposition is that they *are* tracked, at explicit sites. Reflective member access would be a hole in exactly the mechanism the language exists to provide. This is not a difficulty to be engineered around; it is a contradiction.

*It is the maximal "hidden magic."* The rationale invokes the no-hidden-magic principle repeatedly — every value has a static shape, every dispatch is either statically resolved or an explicit interface call, the one structural-dispatch rule (`Contains`/`in`) is singular and called out as exceptional. Member reflection is the largest conceivable violation: arbitrary code reaching arbitrary members of arbitrary types with no static trace. Admitting it would not bend the principle; it would delete it.

**The line is drawn at lattice metadata because that costs nothing.** Everything the `Type` token exposes — name, kind, base, interface conformance, enum members — is information the compiler already has and the runtime already carries so that `is`, `as`, and `GetType` can function at all. Surfacing it adds no new capability and no new tension; it only stops forcing users to thread `typeof(T)` through their own hand-built side tables. The genuine, ownership-neutral use cases are well served: type-keyed registries and caches, kind-based diagnostic formatting, interface-conformance checks on bare `Type` tokens, and enum reflection (closed, stateless, ownership-free — the safest introspection that exists, and the single most requested). None of these touch instance state, so none of them raises the ownership question.

**What was deliberately excluded from even the metadata surface.** Generic-instantiation decomposition — "is this some `Array<X>`, and what is `X`?" via a `GenericArguments` / `GenericDefinition` pair — is genuinely useful for mapping libraries, but it cannot be expressed without also adding an *unbound-generic* `typeof` (a way to write `typeof(Array<>)` to compare against a `GenericDefinition`), which the `typeof` grammar does not admit (language spec [§17.10](Bezel_Language_Spec.md#sec-the-typeof-operator) accepts only closed instantiations). That is a language change wearing a standard-library costume, and bundling it into a metadata revision would hide its true scope. It is therefore deferred as its own explicitly-scoped question ([§18](#sec-things-deferred)), to be decided together with the unbound-`typeof` syntax, not smuggled in.

**Attributes are the realistic future pressure valve, separately.** Several use cases that look like "reflection" (serialization hints, dependency-injection registration) are really *attribute* use cases. Bezel has no attribute system today. If reflection pressure ever genuinely materializes from real programs, the principled response is a minimal attribute system plus attribute-only `Type` queries — never member-access reflection. That, too, is its own scoped question ([§18](#sec-things-deferred)); it is named here so the eventual direction is on record and is not mistaken for a step toward member reflection.

The disposition mirrors [§5.17](#sec-why-no-class-deconstruction): deliver the part that fits the language cleanly (lattice metadata), decline the part that fights its foundations (member-access reflection) *with the reasoning written down*, and keep the genuinely-open adjacent questions (generic decomposition, attributes) explicitly scoped rather than vaguely "deferred." An explicitly reasoned "no" is more useful to users than an open "later": it tells them to architect with compile-time generics and explicit registration now, rather than waiting for a reflective capability that is not coming.

<a id="sec-serialization-without-reflection"></a>
### 5.19 Serialization without reflection

[§5.18](#sec-type-identity-not-reflection) closes the door on reflective serialization. This section records the design that replaces it, the staged plan, and why the v0.114 vocabulary (stdlib [§2.14](Bezel_Standard_Library.md#sec-serialization-vocabulary)) is shaped the way it is.

**Every reflection-free language converged on the same architecture.** Rust's serde generates `Serialize`/`Deserialize` implementations at compile time via a derive macro and routes them through a format-agnostic `Serializer`/`Deserializer` pair, so a type knows nothing about JSON or any other format. Swift's `Codable` has the *compiler itself* synthesize conformance for types whose stored properties are all `Codable`, routed through a format-agnostic `Encoder`/`Decoder` pair. Even C#, which has runtime reflection, moved its modern JSON path to *build-time source generators* for performance and ahead-of-time-compilation reasons — evidence that compile-time codegen is not a Bezel compromise forced by the lack of reflection but the destination reflection-capable languages migrate *to*. The shared invariant across all three: separate *what a type's shape is* (static, the type's concern) from *how a format encodes it* (the format's concern). Reflection conflates them by discovering shape at runtime; the reflection-free approach keeps them separate and resolves shape at compile time.

**Bezel already does opt-in compile-time codegen — it is called auto-equality.** A body record with only auto-properties automatically receives a synthesized `=`, `GetHashCode`, and `ToString` ([§9.2](Bezel_Language_Spec.md#sec-body-records)); a record with a disqualifying member instead produces a compile error at the use site, naming the obstruction. This is precisely opt-in-by-structure compile-time generation with a recursive eligibility rule and a disciplined error story — and it needs no attribute system, no macro system, and no general source-generator plugin mechanism. Serialization synthesis is not a new *kind* of feature for Bezel; it is auto-equality generalized from "compare the fields" to "read and write the fields against a format." Choosing the Swift model (a dedicated compiler feature keyed off a declared conformance) over the C# model (an open-ended source-generator subsystem) is therefore the choice that fits machinery the language already has, rather than the choice that requires building the deferred macro system first.

**The naming follows the established interface convention.** Bezel's interface set splits cleanly into capability adjectives a type declares about itself (`IDisposable`, `IEquatable<T>`, `IComparable<T>` — the `-able` family) and agent nouns that act on other values (`IEnumerator<T>`, `IEqualityComparer<T>`). Serialization has one of each: a *type* declares it can serialize itself (`ISerializable`/`IDeserializable`, the `-able` family, by direct analogy with `IDisposable`); a *format* is an agent that serializes values (`ISerializer`/`IDeserializer`, the agent-noun family, by analogy with `IEqualityComparer<T>`). The type-side interfaces are deliberately *parameterless* (not `ISerializable<TFormat>`): a value's shape is intrinsic and format-independent, so format polymorphism lives in the `ISerializer` parameter to the method, never in the type-side interface — the same place serde and Codable put it, and the same shape as the parameterless `IDisposable`. Splitting serialize and deserialize into two interfaces rather than one combined interface follows the existing `IDisposable`/`IAsyncDisposable` and `IEnumerable`/`IAsyncEnumerable` precedent of separating paired concerns, and is additionally forced here by a structural asymmetry: serialization is an instance operation (an existing value writes itself), deserialization a static one (a reader produces a value where none exists yet).

**That asymmetry is why `IDeserializable` is, for now, a marker.** A static construction entry point could not be an interface *method* until static interface members existed (they have since shipped — v0.176, spec §11.8 — and the `Deserialize` promotion is a recorded follow-up; until it lands, `IDeserializable` stays a marker). Rather than block deserialization on that keystone, v0.114 recognizes the entry point *by name* — a static `Deserialize(d: IDeserializer): T` (plain by-value for the record/enum common case; `owned T` only when the declaring type is a class, since `owned` on a non-class return is semantically rejected) whose presence is opted into by declaring `: IDeserializable` — exactly the mechanism, and exactly the forward-compatibility discipline, established for `FromCollectionLiteral` in [§5.16](#sec-collection-literals-for-complex-collections) and language spec [§15.4.1](Bezel_Language_Spec.md#sec-the-user-defined-sequence-literal-protocol). The name and signature are chosen so that the promotion, when it lands, turns `Deserialize` into a real interface method with no source change. This reuse of an already-justified pattern is deliberate: it avoids inventing a second recognition mechanism for the same shape of problem, and it means deserialization is not gated on the static-interface-members keystone — a materially better staging than making serialization wait.

**The synthesis design (delivered in v0.116).** A record or enum that declares `: ISerializable` (and/or `: IDeserializable`) and satisfies the synthesis-eligibility rule has the bodies generated by the compiler (language spec [§9.8](Bezel_Language_Spec.md#sec-serialization-synthesis)), governed by a recursive structural-eligibility rule that mirrors auto-equality's: a type is synthesis-eligible when every serialized component is itself serializable; a non-serializable component is a compile error at the conformance declaration, naming the offending member, with the same error discipline auto-equality uses for disqualifying members (reported at the declaration rather than the use site, because the conformance declaration is the explicit opt-in). Records (shape known from [§9.1](Bezel_Language_Spec.md#sec-positional-records)/[§9.2](Bezel_Language_Spec.md#sec-body-records)) and enums (closed, members known) are the eligible set; classes are not (no inheritance/identity/owned-field complications, exactly the closed-shape property that makes auto-equality sound for the same set). The ownership concern that made *reflection* unsound does not arise: the synthesized `Deserialize` body is a static program point that calls the type's constructor with read values, so field types, nullability, and definite-assignment are checked normally — exactly where the language wants the contract, and exactly the site reflection lacked. Synthesis is therefore sound for the same structural reason auto-equality is. Hand-writing either direction suppresses synthesis of that direction (as a manual `Equals` suppresses auto-equality); the two directions are independent. The specific wire choices are normative (language spec [§9.8](Bezel_Language_Spec.md#sec-serialization-synthesis)) so independent implementations agree: enums serialize by member *name* not underlying integer (stable against renumbering, self-describing in text), components in declaration order (matching auto-`ToString`), dictionaries as key/value-pair arrays (admitting non-string keys uniformly rather than forcing string coercion as JSON-object-keyed encodings do).

**Field-name customization (delivered in v0.117): a compiler-recognized modifier, not attributes, improving on `CodingKeys`.** Renaming a serialized field, excluding one, or tolerating a missing one has no auto-equality analog (equality needs no external names), so it required a new mechanism. Two off-the-shelf models were rejected. *Attributes* (`[JsonPropertyName("…")]`) were rejected because field-name customization is precisely the canonical case that, in C#, metastasizes into a dozen stacked serialization attributes per member — exactly the proliferation, stringly-typed-magic, and semantics/metadata-blur the attribute-system deferral ([§18](#sec-things-deferred)) is on record against; solving this one narrow need by importing a general attribute system would pay that entire cost to buy one feature, and would prejudice the still-open general-attribute question. *Swift's `CodingKeys`* (a nested `enum: String, CodingKey` listing every coded property) was rejected because it is a footgun by construction: it conflates "which members are coded" with "what they are renamed to" into one exhaustive list, so adding a member and forgetting its case **silently drops it** from serialization, and a reader cannot distinguish intentional exclusion from an omission — the same "blur" indictment, relocated into an enum. The chosen design is the narrow-modifier escape hatch [§18](#sec-things-deferred) already sanctions for `[Obsolete]`/`[MethodImpl]`-style needs: a closed `serialized` clause expressing three effects — rename (`serialized "name"`), exclude (`serialized skip`), tolerate (`serialized optional`), where rename and tolerate combine (`serialized "name" optional`) and exclude is mutually exclusive with both — attached to the member it affects (language spec [§9.8](Bezel_Language_Spec.md#sec-serialization-synthesis)). It improves on `CodingKeys` in the specific way the design question demanded: it is *per-member and total* — a member with no clause is coded under its own name, always, so there is no separate list to desynchronize and the silent-drop failure is structurally impossible; the clause is *local* — its effect is visible at the member, with one defined meaning, no reflective indirection, answering [§18](#sec-things-deferred)'s "a reader cannot tell what an annotation does" objection directly; and it is *closed* — a fixed effect vocabulary, no parameters interpreted by external machinery, no user extensibility, so it cannot proliferate (a new effect would be a language change with its own rationale, exactly the friction that prevents the C# explosion). It is forward-compatible: if a general attribute system later arrives, `serialized "x"` re-expresses mechanically as `[Serialized("x")]` with identical semantics, the same promotion discipline used for `FromCollectionLiteral` and recognized-`Deserialize`. The honest cost: this is the first serialization stage that adds grammar — unavoidable, since customization inherently needs somewhere to write the custom name, and the modifier is the *smallest* such addition (two closed productions, no new top-level construct, no attribute-target or retention rules, no reflection dependency) where attributes would have been the largest.

**Unknown-field tolerance is an operation policy, not a type annotation (v0.118).** The strict default — an input field matching no declared component raises (established with synthesis, v0.116) — is correct because silently dropping unrecognized input masks producer/consumer schema drift and field-name typos. But making it *configurable* raised a placement question worth recording, because the answer generalizes to future serialization-policy questions. The natural-seeming move was a type-level `serialized tolerant` clause, parallel to v0.117's member-level `serialized` modifier. That was rejected on a category distinction: the v0.117 effects (rename, skip, optional) are *intrinsic to the type* — `FirstName` *is* `"first_name"` in this type's wire form for every caller, every format, every call site; that is part of the type's serialization contract and belongs on the type. Unknown-field tolerance is not a fact about the type at all: the same type is legitimately read strictly when consuming a trusted internal message (drift *should* error) and leniently when consuming a third-party producer that adds fields freely. That is a property of the *read* — the caller has it, with the input, in a context — not of the type. A type-level annotation would force one answer on every call site, would be strictly less expressive than a per-operation control, and would reintroduce exactly the "inert-looking but load-bearing, and you cannot tell from the call site what it does" objection [§18](#sec-things-deferred) levels at attributes — the same objection the v0.117 design was careful to answer. So the knob lives on the deserialization operation: `JsonOptions.IgnoreUnknownFields` and the binary deserializer's constructor parameter (stdlib [§2.15](Bezel_Standard_Library.md#sec-concrete-serialization-formats)), defaulting to strict. Mechanically, the synthesized `Deserialize` is identical regardless of policy — on an unrecognized field it calls `IDeserializer.SkipValue` and continues; whether *reaching* an unknown field is an error is the deserializer's configured behavior. This is the v0.114 shape/format split extended to shape/policy: the synthesized code expresses structure, the deserializer expresses policy, and they compose without either knowing the other's choices. The general principle, worth stating once for future policy questions: a serialization knob belongs on the type when it is part of the type's wire contract, and on the operation when it is a property of a particular read or write; "which spelling is most consistent with an existing mechanism" does not override "where does this policy actually live."

**Tree-shaped class synthesis (v0.119): the part of the class-graph tier that was never actually blocked.** The class-graph tier was deferred wholesale through v0.118, but it decomposes into sub-problems of very different difficulty, and the easiest is not hard at all. A class whose serialized object graph is a *tree* — no two serialized edges alias the same object, no cycles — is, for synthesis purposes, a record plus heap allocation and ownership transfer: the synthesized `Deserialize` constructs each owned child and transfers it into the parent's constructor, and the ownership contract lives at that constructor signature, a static program point, exactly as for records. This is the case [§9.8](Bezel_Language_Spec.md#sec-serialization-synthesis)'s original soundness argument already covered ("an `owned`-field class's ownership contract lives at its constructor signature — exactly where the language wants it"); it was bundled with the genuinely hard sub-problems and deferred with them, but it does not need the reference-graph machinery the hard sub-problems do. v0.119 unbundles it.

The one real design question was that *tree-shape is not statically verifiable* — whether two `owned` subtrees alias is not a static property of the type. Three responses were possible: infer-and-hope (serde's choice: silently duplicate, the documented footgun where deserializing shared reference-counted pointers yields distinct objects with no diagnostic); require a static proof (impossible without an aliasing analysis the language does not have and does not want); or **assert-and-enforce**. Bezel takes the third: the programmer asserts tree-shape with an explicit `serialized tree` class-header clause, and the synthesized deserializer *dynamically enforces* it — a repeated object identity in the input raises `SerializationException` rather than silently duplicating. This is the disposition the project takes everywhere: do not let a generic mechanism paper over a property it cannot guarantee; make the assumption explicit and make its violation a *detected error*, never a silent corruption. Silent duplication is precisely the behavior other ecosystems ship and warn about; refusing it is worth a runtime check.

`serialized tree` is *type-scoped* — placed on the class header, not on a deserialization call — and this is consistent with, not a contradiction of, the v0.118 placement principle. v0.118 established: a knob belongs on the type when it is part of the type's wire contract, and on the operation when it is a property of a particular read. Tree-shape is squarely the former — a class either serializes as a tree for every caller, every format, every call site, or it does not; it is an invariant of the type's serialized form, exactly like a field's renamed wire name and unlike unknown-field tolerance (which legitimately varies per read). The v0.118 principle is what *tells* us `serialized tree` is type-scoped while `IgnoreUnknownFields` is operation-scoped; the two placements are the same rule applied to two genuinely different kinds of property.

**The generalization ceiling, stated honestly.** With tree-shaped class synthesis delivered (v0.119), the class-graph tier is narrowed to its genuinely hard residue, deferred with its reason. Three sub-problems remain, and they are really one: *shared references* (a DAG where two serialized edges alias one object), *cycles* (which in an exclusive-ownership model are necessarily an owning spanning tree plus borrowing back-edges, i.e. the shared-reference problem wearing a scarier hat), and *polymorphic dispatch* (a base-typed field holding a derived instance, needing a wire type-discriminator and an explicit construction registry — orthogonal to identity, and consistent only as *explicit registration*, never reflective discovery, per [§5.18](#sec-type-identity-not-reflection)). The crux for the first two is specific and unresolved: Bezel's `owned`/borrow annotations *already encode* which edges are owning (the canonical-owner information that defeats serde and every garbage-collected language is, uniquely, statically present here) — but reconstructing a back-borrow requires binding a borrowing field *after* its owning target is constructed, which collides with definite-assignment, the guarantee that is itself load-bearing. That tension (deferred borrow binding vs definite-assignment) is the single question that gates everything past trees, and it deserves its own rationale working-out *before* any spec text, exactly as every hard question in this design has been resolved reasoning-first. *Concrete formats* are delivered (v0.115, `System.Serialization`, stdlib [§2.15](Bezel_Standard_Library.md#sec-concrete-serialization-formats)). The staging held and continues: vocabulary (v0.114) → formats (v0.115) → record/enum synthesis (v0.116) → field-name customization (v0.117) → operation-scoped unknown-field tolerance (v0.118) → tree-shaped class synthesis (v0.119), each an independent non-breaking addition; the remaining work is the shared/cyclic/polymorphic residue, gated on the deferred-binding question.

**Working out the deferred-borrow-binding vs definite-assignment tension (v0.120, rationale only).** This subsection is the promised reasoning-first working-out. It commits no spec text; its purpose is to determine whether identity-preserving class-graph deserialization is *coherent* in Bezel before any syntax or semantics is proposed, because if the central tension has no sound resolution the honest outcome is a reasoned decline, not an open "later."

*The tension, stated exactly.* A shared-reference graph, after the v0.119 observation, is an owning spanning tree (the `owned` edges) plus a set of non-owning back-edges (borrowing fields that point at objects owned elsewhere in the tree). Deserialization must reconstruct the owning tree — that part v0.119 already does soundly — and then bind each borrowing field to the already-constructed object it references. The collision is with [§7.9](Bezel_Language_Spec.md#sec-definite-assignment-for-non-nullable-fields): a non-nullable reference field must be assigned in every constructor before that constructor returns, with no default value in existence for it. A borrowing field whose target appears *later* in the construction order cannot be given its value in its owner's constructor — the target does not exist yet. So either the field is left unassigned at construction (violating [§7.9](Bezel_Language_Spec.md#sec-definite-assignment-for-non-nullable-fields)), or construction is reordered so every borrow target precedes every borrower (impossible in general — a cycle of borrows has no such order), or the field is made nullable (changing the *type* to serve the deserializer, which is unacceptable: the type's contract must not be deformed by how it is read, the principle [§5.19](#sec-serialization-without-reflection) established when rejecting type-level tolerance).

*Why the three obvious escapes each fail.* (1) *Relax [§7.9](Bezel_Language_Spec.md#sec-definite-assignment-for-non-nullable-fields) for synthesized deserialization.* Rejected: [§7.9](Bezel_Language_Spec.md#sec-definite-assignment-for-non-nullable-fields) is not a local convenience, it is the guarantee that a non-nullable reference is never observed unset; a synthesized path that can produce a half-constructed object with an unset non-nullable field reintroduces exactly the null-dereference class the language spent its nullability design eliminating, and it would do so invisibly inside generated code where no reader can audit it. A guarantee with a synthesized exception is not a guarantee. (2) *Topologically order construction so borrowers follow targets.* Rejected as a general solution: it handles a DAG but not a cycle (mutually borrowing objects have no valid order), and even for a DAG it forces construction order to be a function of the borrow graph rather than the ownership tree, which the ownership model — not the serializer — is entitled to define. (3) *Make borrowing fields nullable for deserialization.* Rejected on the [§5.19](#sec-serialization-without-reflection) principle above, and independently because it would make every *reader* of such a type handle a `null` that the type's own invariants forbid — pushing the deserializer's difficulty onto every downstream use site, the worst possible place for it.

*The candidate that survives scrutiny: a bounded two-phase construction window, expressed in the ownership model rather than bolted onto it.* The serde comparison is instructive precisely because Rust hit the same wall and its answer (`Rc::new_cyclic`, which hands the closure a `Weak` to the not-yet-initialized allocation) is a *controlled* deferral: a narrowly-scoped window in which a back-reference may be wired up after the target's storage exists but before the object is considered fully constructed. The principled Bezel analog is *not* `Weak` (Bezel has no reference counting and should not grow one for serialization), but the structural idea transfers: deserialization of a shared/cyclic component group is a single operation with two phases — *allocate-and-own* (construct every object in the group through its owning constructor, establishing the owning tree, with borrowing back-edge fields in a defined not-yet-bound state that **is not observable outside the deserialization operation**), then *bind-backs* (assign every borrowing field to its now-existent target, after which the group is fully constructed and released to the caller). The [§7.9](Bezel_Language_Spec.md#sec-definite-assignment-for-non-nullable-fields) guarantee is preserved *as a guarantee* if and only if the not-yet-bound state is provably unobservable: no user code, no constructor body, no method runs against an object in the group between phase one and phase two. That is the whole crux reduced to a single checkable property — **unobservability of the intermediate state** — rather than a vague "two-phase init."

*What that reduction buys, and what it still costs.* It converts an open-ended "how do we deserialize graphs" into one precise design obligation: define a construction-group operation whose intermediate state is statically guaranteed unobservable, and prove the guarantee. This is tractable-looking because Bezel already has the ingredients — `owned`/borrow annotations supply the tree/back-edge partition for free (the information serde must guess), and the synthesized `Deserialize` is already a closed compiler-generated region with no user code interleaved. The residual hard part is honest and nameable: the unobservability proof must survive *constructor side effects* (a constructor in the group that calls a method that could reach a not-yet-bound borrow), which means either the group's constructors must be restricted to a statically-checkable "no escape during construction" shape, or the back-edges must be bound before any constructor body runs (constructor-parameter injection of the borrow, only possible if the target precedes — back to ordering for the acyclic case, and genuinely open for the cyclic case). Polymorphism remains orthogonal and is *not* gated on this: it is the explicit-registry sub-problem ([§5.18](#sec-type-identity-not-reflection)'s explicit-registration-not-reflection stance applies unchanged) and can be designed independently whenever wanted.

*Conclusion of the working-out.* The tension is **not** a dead end: the shared-reference and acyclic-back-edge case has a credible resolution (bounded two-phase construction with a statically-enforced unobservable intermediate state, the back-edge partition taken from the ownership annotations the language already requires). The **truly cyclic** case — mutual borrows with no construction order and constructors with potentially-escaping bodies — remains genuinely open and is the single honest blocker; it is *not* refuted here, but it is not resolved here either, and it should not receive spec text until the unobservability proof obligation is discharged for it specifically. The disposition matches the rest of the design: the sub-problem that fits (DAG-shaped shared references) is now understood well enough to specify in a future revision; the sub-problem that fights the foundations (arbitrary cycles under effectful constructors) stays explicitly scoped with its exact obstruction named — the unobservability-under-constructor-side-effects proof — rather than vaguely deferred. This is the gate cleared for *shared-reference* spec work and held, with a precise reason, for *cyclic* spec work.

**Shared-reference DAG synthesis (delivered in v0.121): the discharged proof, made spec.** v0.121 specifies the case the working-out cleared, and it is worth recording exactly *which* of the working-out's two candidate discharges the spec took, because the choice matters. The working-out named two ways to make the intermediate state unobservable: a bounded two-phase window (allocate-and-own, then bind-backs, with a hard unobservability proof that must survive constructor side effects), or — for the acyclic case only — binding the back-edges *before any constructor body runs*, via constructor-parameter injection, "only possible if the target precedes." A directed acyclic graph is *exactly* the condition under which the target can always precede: a DAG admits a topological (owner-before-borrower) construction order, so every borrowing back-edge's target is already constructed when the borrower's constructor is called, and the borrow is passed *as a constructor argument*. This takes the **easier** of the two discharges — the one with no separate mutable phase and therefore no unobservability-under-side-effects proof obligation at all, because there is no intermediate state to be observed: each object is fully constructed, back-edges included, by its single constructor call. [§7.9](Bezel_Language_Spec.md#sec-definite-assignment-for-non-nullable-fields) is satisfied *unmodified* — not relaxed, not excepted for synthesized code, not worked around with nullability — which was the non-negotiable requirement the working-out set. The harder two-phase discharge is precisely what the *cyclic* case would need (a cycle has no owner-before-borrower order, so constructor-parameter injection is impossible and a mutable post-construction bind is unavoidable), and it remains deferred with its proof obligation intact: v0.121 deliberately ships only the sub-problem whose discharge needs no new proof, exactly the project's standing disposition. The `serialized graph` clause is type-scoped for the same reason `serialized tree` is — graph shape is an intrinsic property of the type's serialization contract, the [§5.19](#sec-serialization-without-reflection) placement criterion — and the deserializer's dynamic cycle-detection (a reference whose target is still under construction) is the same assert-and-enforce discipline as the tree case: the assertion the compiler cannot check is checked at read, and its violation is a *detected error*, never silent corruption.

**Polymorphic dispatch (delivered in v0.122): explicit registration, vindicated by the ecosystem's own trajectory.** The polymorphism design was never the hard part — it was deferred only because it was orthogonal and could wait, not because it was unresolved. v0.122 specifies it, and the specific shape is worth recording because the wider ecosystem independently converged on it after learning the alternative the hard way. The mechanism is a closed registry, written explicitly in the `polymorphic` clause, mapping a wire discriminator string to each permitted concrete derived type; the synthesized serializer writes the discriminator first, the synthesized deserializer reads it first and dispatches through the registry, and any discriminator or run-time type outside the registry is a `SerializationException`. There is no reflective subtype discovery. This is exactly the [§5.18](#sec-type-identity-not-reflection) explicit-registration-never-reflection principle, and it is not an arbitrary preference: reflective type-discriminator binders (the historical Newtonsoft `$type` model, which resolved an attacker-controlled string to *any* constructible type) became a notorious remote-code-execution vector, and the modern mainstream (System.Text.Json from .NET 7) deliberately moved to *explicitly opted-in, closed* derived-type registration with undeclared types raising at runtime. Bezel's design lands at the same place by principle that the ecosystem reached by incident — the registry is closed because an open one is a security defect, not merely because closed is tidier. Two further design points were settled by the same external evidence: the discriminator is consumed *before* component binding (a serializer that treats it as an ordinary field hits the documented problem that it cannot then be a required data property and cannot participate in normal field machinery — so Bezel makes it structural, never a data field, never subject to field-name customization or the unknown-field policy); and polymorphism is *type-scoped*, the permitted-subtype set being an intrinsic property of the base type's serialization contract exactly as graph shape is, by the v0.118 placement principle. Polymorphic dispatch composes with `serialized tree`/`serialized graph` — the registry selects *which* concrete type, the graph-shape clause governs *how that type's edges reconstruct* — and is wholly independent of the cyclic deferral: nothing about choosing a concrete type touches the unobservability-under-constructor-side-effects obligation, so v0.122 ships without disturbing the one genuinely open problem.

**The generalization ceiling, reached (v0.124).** Cyclic class synthesis is delivered (v0.124): the spec makes normative exactly what the v0.123 working-out discharged — the self-contained-constructor eligibility rule and the two-phase construction whose intermediate state is provably unobservable, with [§7.9](Bezel_Language_Spec.md#sec-definite-assignment-for-non-nullable-fields) preserved unmodified. **The serialization stack is complete.** Every class object graph — tree, directed acyclic, or cyclic — is synthesizable; polymorphic edges resolve through an explicit closed registry; field names, missing-field tolerance, and unknown-field policy are all covered. The single remaining reason to hand-write `Serialize`/`Deserialize` is a class whose constructor cannot be made self-contained (construction logic genuinely entangled with its references) — and that is a *recorded, statically-detected, principled exclusion*, the honest residue every prior stage's reasoning anticipated, not an open problem. There is no undischarged obligation and no deferred shape. Stated plainly: serialization began (v0.114) as a format-abstraction vocabulary with the object-graph tier flagged as the genuinely hard part, and ends (v0.124) with that tier fully delivered, each hard question resolved reasoning-first before its spec text, the one irreducible limit (reference-entangled constructors) named and checked rather than hit at runtime. The external corroboration stands as the closing note: Java, with full GC and unrestricted mutable identity, cannot preserve a cycle through an immutable record's constructor for precisely the reason Bezel's two-phase-plus-self-contained-constructor design is engineered around — and Bezel turns that limitation into a compile-time restriction with a stated remedy rather than a silent failure.

**Working out the cyclic case (v0.123, rationale only).** This subsection attempts the discharge the v0.120 working-out named as the single outstanding obligation. It commits no spec text; its purpose is to determine whether the unobservability-under-constructor-side-effects proof can be carried, and to be honest if it cannot be carried in full. The v0.120 analysis left exactly two ways to make the two-phase intermediate state unobservable: (a) restrict the cyclic group's constructors to a statically-checkable "no escape during construction" shape, or (b) bind back-edges before any constructor body runs — and (b) is impossible for a cycle (a cycle has no owner-before-borrower order, so some back-edge's target cannot precede its borrower). The cyclic case is therefore forced onto path (a), and the whole question reduces to: *can "no escape during construction" be defined precisely enough to be a sound static check, and is it sufficient?*

*What "escape during construction" must forbid.* The two-phase deserializer constructs every object in the cyclic group with its back-edge fields unbound, then binds them. The intermediate state is unobservable iff, between the first allocation and the last bind, no code can read a back-edge field of any group object. The only code that runs in that window is the group's own constructor bodies — the synthesized deserializer interleaves no user code (it is a closed compiler-generated region, the property the v0.120 working-out already established). So the proof obligation is exactly: *no constructor body in the group, transitively, observes a not-yet-bound back-edge.* A constructor observes a back-edge if it (i) reads the back-edge field directly, (ii) calls a method on `this` that does, (iii) passes `this` to any code that could, or (iv) calls a virtual method an eligible subtype could override to do so. (iii) and (iv) are the "escape": once `this` leaves the constructor, unobservability of this object's fields is no longer locally checkable.

*The candidate static rule.* A class is **cyclic-serialization-eligible** only if its *construction* is *self-contained* — where "construction" means all code that runs while an instance is built: the constructor body, every constructor reached transitively through `this(...)`/`base(...)` chaining, and every field and property initializer that runs during that construction. All of it, taken together, may assign the instance's own fields and read its own value/owned fields and constructor parameters, but it may not (i) read any field that is a back-edge in the serialized graph, (ii) call any instance method on `this`, (iii) let `this` escape — pass it as an argument, store it in any location, capture it in a closure, or return it, or (iv) call a virtual/abstract method. (The transitive scope is essential, not incidental — but it decomposes into two parts of unequal weight. The field/property-initializer part is *already discharged by the language*: language spec [§22.8](Bezel_Language_Spec.md#sec-field-initializers) universally forbids any class's field initializers from referencing `this`, instance members, `base`, virtual methods, or any `this`-observing expression, so an initializer structurally cannot read a back-edge or call a virtual/instance method in the first place — the proof can simply cite that invariant rather than re-derive it. The load-bearing part is the **constructor chain**: a chained or `base(...)` constructor's *body* is construction-time code that [§22.8](Bezel_Language_Spec.md#sec-field-initializers) does not restrict — it may freely read its own fields and call virtual methods — so restricting attention to the most-derived constructor body would leave a real hole through which a base constructor's virtual call or own-field read could observe the unbound state. The rule closes exactly that hole, and the proof quantifies over the transitive chain for that reason.) This is a strong restriction, but it is *exactly* the restriction the proof needs, and it is statically checkable by the same escape analysis the borrow checker already performs (it is a strict subset of the "does this reference escape this scope" question the language answers everywhere else), run over the transitive construction-time code rather than one body. Under this rule no construction-time code can observe any back-edge — its own or another group member's — because it touches no back-edge field, calls no method that could, and never lets `this` reach code that could. The intermediate state is then provably unobservable: the only code in the window is self-contained construction, none of which can read a back-edge.

*Is it sufficient — and what does it cost?* It is sufficient: the proof goes through. It is also honestly costly, and the cost must be stated, not hidden. A self-contained constructor cannot do initialization work that depends on its references (no "validate the referenced peer," no "cache a value computed from a referenced object"). For the *common* cyclic shapes — parent/child trees with up-pointers, doubly-linked structures, observer graphs — constructors are typically pure field assignment and the rule bites lightly. For classes whose construction logic is entangled with their references, it bites hard: such a class is not cyclic-serialization-eligible and must hand-write `Deserialize` (always available). This is the project's standing disposition — synthesis covers the shape that fits soundly; the shape that fights the foundation is explicitly excluded with the reason recorded — applied one level deeper. It is *not* a relaxation of [§7.9](Bezel_Language_Spec.md#sec-definite-assignment-for-non-nullable-fields): the two-phase window binds every back-edge before the object is released and before any observing code runs, so no non-nullable field is ever observed unset; definite assignment holds exactly as for the DAG case, by a different but equally airtight argument (DAG: bound through the constructor; cyclic: bound in a provably-unobservable window before any observer exists).

*The residual honest gap.* One sub-case resists even this: a class whose construction *genuinely requires* observing a mutually-referenced peer (an invariant establishable only once the peer exists) cannot be made self-contained, because the language's constructor-centred initialization model is precisely what makes such logic want to live in the constructor. For these classes the synthesized path is correctly refused; the rule does not solve them, it *excludes* them with a stated reason. So the discharge is real but bounded: cyclic graphs whose participating classes have self-contained constructors are provably synthesizable; cyclic graphs whose construction is reference-entangled remain hand-written, by a recorded principled exclusion rather than an open question. That is a genuine resolution of the obligation — the proof is carried for a precisely delimited, statically-checkable class of programs, and the remainder is a declared boundary, not an unresolved tension.

*Conclusion of the working-out.* The unobservability-under-constructor-side-effects proof **is dischargeable**, via a statically-checkable self-contained-constructor rule the existing escape analysis already has the machinery to enforce, and it discharges *without* weakening [§7.9](Bezel_Language_Spec.md#sec-definite-assignment-for-non-nullable-fields). The cyclic case is therefore no longer "the single open problem"; it is a *specifiable* feature with a known eligibility restriction, gated now only on ordinary spec-design work: the wire mechanism for cycle-closing references (the identity/`$ref` table the DAG case already established, extended so a reference may target an object still under construction) and the `serialized` clause spelling. This subsection is the gate-clearing the project's discipline requires before that spec work — the next revision may specify cyclic synthesis for self-contained-constructor classes, exactly as v0.121 specified the DAG case after v0.120 cleared its gate. What is *not* claimed: this does not make every cyclic graph synthesizable; it discharges the proof for the statically-delimited eligible class and converts the remainder from "unresolved" to "explicitly excluded with reason" — the honest and complete form of the answer. *(v0.124: this discharge was made normative — language spec [§9.8](Bezel_Language_Spec.md#sec-serialization-synthesis) specifies the `serialized cyclic` clause, the self-contained-constructor eligibility rule as a compile-time check, and the two-phase construction, exactly as worked out here and with [§7.9](Bezel_Language_Spec.md#sec-definite-assignment-for-non-nullable-fields) preserved unmodified. The serialization stack is complete.)*

**Why v0.114 ships only the vocabulary.** The format abstraction is the one piece that cannot be retrofitted: if the type-side interface ever names a format, or the format ever inspects type shape, the separation is lost and every later tier is built on sand. It also costs no language feature and the writing direction is usable by hand the day it ships. Shipping it now, alone, fixes the architectural keystone at zero language cost and lets the synthesis feature, the concrete formats, and the customization mechanism land later as independent, non-breaking additions — each forward-compatible because the vocabulary was designed, like `FromCollectionLiteral` before it, to be promotable rather than replaced. The disposition is the same one applied in [§5.17](#sec-why-no-class-deconstruction) and [§5.18](#sec-type-identity-not-reflection): ship what fits the language now, record the staged plan for what does not yet, keep every open question explicitly scoped.

**A premise revisited (v0.141).** The completeness recorded above ("no undischarged obligation and no deferred shape", v0.124) was true of the wire-and-synthesis layer and remains so, but it rested on one unstated premise: that the language had no shared-ownership primitive, so the cyclic tier had to be carried by a synthesized two-phase window over non-nullable borrowing back-edges — and that tier, it later emerged, had no ownership-valid *construction* at all (a cycle of plain borrows cannot be built; #703). v0.134's `Shared<T>`/`Weak<T>` ([§5.21](#sec-shared-t)) removed the premise: a cycle now closes through a nullable `Weak<T>` back-edge on a `Shared<T>` spine, ordinary ownership-valid code, and the field types encode the wire shape the keywords asserted. The graph-shape keywords are accordingly retired in favour of type-driven inference; the working-out is [§5.22](#sec-type-driven-serialization). This records the v0.124 completeness as premise-bound, not retracted: a later, independently-motivated capability superseded the machinery the earlier constraint required.

<a id="sec-one-element-policy"></a>
### 5.20 One element policy, not twelve

v0.132 adds the element slot policy (language spec [§28.11](Bezel_Language_Spec.md#sec-element-slot-policy)): a single table — collection family × element category → slot kind, slot kind → the semantics of every element operation — from which all twelve standard collections derive their element behavior. The change is declarative, not behavioral: each collection's documented operations are unchanged; what changes is their *status*, from twelve independently-stated rule sets to twelve presentations of one rule.

**Why.** The implementation experience made the cost of the per-collection statement concrete. The compiler hand-wired each collection's element handling separately, and the defect history clustered exactly there: a long series of bugs in which one collection's handling of one element category diverged from its siblings' — string elements compared by `memcmp` in one list operation but structurally in another, dictionary value decoding correct for one value category and garbage for the next, disposal order right in one container and wrong in its peer (#556, #558–#560, #562–#563, #565–#566, #570–#571, #598 among others). Every one of those bugs is, in the table's terms, a cell filled in inconsistently with its column. A normative table makes the column the authority: an implementation can implement the column once, and a divergence between a per-collection clause and the table is now *defined* to be a spec defect rather than a judgment call. This is the specification-side half of the direction recorded in #545 (implement the element policy once, type-keyed, instead of per collection); the spec now says the twelve behaviors *are* one behavior, so the implementation is licensed to build them that way.

**What was already in place.** The owning column's storage embodiment, `OwningBuffer<T>` (stdlib [§4.14](Bezel_Standard_Library.md#sec-owned-buffers-and-spans), [§5.15](#sec-owned-buffers-and-spans) above), existed since v0.99/v0.102, and its category-dispatched slot semantics were the prototype for the table; the owning family's rejection of runtime-managed element types was likewise already normative ([§14.4](Bezel_Language_Spec.md#sec-owned-as-a-generic-argument)). v0.132 did not have to invent the policy — it had to *name* it, state it once, and subordinate the per-collection prose to it.

**The deferred half: a borrow-storing primitive.** The table's borrowing column has no user-expressible storage embodiment, and v0.132 deliberately does not add one. The blocker is principled: outside the compiler-known borrowing collections, storing a borrow in a field is rejected ([§28.3](Bezel_Language_Spec.md#sec-local-variables-ownership-and-borrows)) — that rule is what makes borrow lifetimes statically trackable. A user-expressible `Buffer<T>`-of-borrows would need its own lifetime discipline (the collection-as-transit rules of [§28.11](Bezel_Language_Spec.md#sec-collection-element-ownership), generalized and made checkable for arbitrary user containers), which is real design work, not transcription. Until that work is done, borrowing collections remain compiler intrinsics specified by the table. **Declined** rather than attempted now: a quick dispensation ("classes marked somehow may store borrows") would re-open the soundness of the borrow tracker for a convenience the standard library does not itself need — the same shape of reasoning that declined `<owned T>` generic parameterization in v0.97 ([§5.11](#sec-owning-collections)).

<a id="sec-shared-t"></a>
### 5.21 `Shared<T>`: scoped shared ownership

v0.134 adds `Shared<T>`/`Weak<T>` (language spec [§28.13](Bezel_Language_Spec.md#sec-shared-ownership), stdlib [§2.16](Bezel_Standard_Library.md#sec-shared-and-weak)) — the library type [§5.4](#sec-no-shared-ownership) predicted. The addition keeps every commitment that section made: single ownership remains the default and the only *implicit* regime; sharing is opt-in, and its cost is visible at every site (`Clone()` is an explicit call — there is no implicit handle duplication, consistent with the no-implicit-conversions discipline of [§14](#sec-operators)). What changed since §5.4 was written is that the gap stopped being hypothetical: caches handing out entries, registries whose entries outlive any single owner, and the multi-consumer channel question (§12.6) all reduce to "N holders, last one cleans up," and the workarounds (handle tables) push the same reference counting into user code where the compiler cannot see it.

**Why compiler-known rather than pure library.** Faithful shared ownership cannot be built from unique ownership in user Bezel: N handles must keep one control block alive, and "kept alive by N owners" *is* the feature. The precedent is the collection library — compiler-known types with ownership semantics user code cannot express (§28.11) — and the runtime already manages string and closure lifetimes invisibly (§28.9 deliberately leaves the mechanism unspecified; reference counting is the natural implementation); `Shared<T>` asks for the same kind of bookkeeping, now with user-visible semantics.

**Why the handles are ordinary owned objects.** The design's entire surface area is the *inside* of the type: count, last-one-disposes, and `Get()`'s borrow-from-handle sourcing (the same dispensation owning-collection indexer reads already have). Everything else — `using var`, owned fields, `move`, branch joins, exception-path discharge, storage in owning collections — applies to handles by virtue of their being class instances, with zero new checker rules. A design where sharing was a new *reference kind* (a third state beside owned and borrowed) was **declined**: it would have touched every join rule, every producer table entry, and every feature that dispatches on ownership state, for no expressiveness the handle form lacks.

**Why domain-local.** The count is unsynchronized; making `Shared<T>` sendable would either race the count or impose atomic operations on every single-domain user. A synchronized `SharedAtomic<T>` (or sendable-`Shared` mode) is the known follow-on — it is also what multi-consumer channels need (§12.6) — and is deferred until a use case forces the cost question; adding it later is non-breaking. Also **declined**: refcounting arbitrary classes via an annotation (hides cost, breaks the structural-facts discipline of [§3.6](Bezel_Language_Spec.md#sec-derived-type-properties)-style reasoning), and compiler-inferred sharing via escape analysis (implicit magic; the language's position is that ownership transitions are visible in source).

**The accepted hazard.** Reference cycles through `Shared<T>` leak, and the compiler does not detect them. This is the standard refcount trade, accepted with the standard mitigation (`Weak<T>`, with `TryUpgrade` in the Try-pattern shape the language already has). Cycle *detection* would be a tracing collector by another name — exactly what the language promises not to have.

<a id="sec-type-driven-serialization"></a>
### 5.22 Type-driven serialization: `Shared<T>`/`Weak<T>` retire the graph-shape keywords

[§5.19](#sec-serialization-without-reflection) closed (v0.124) with the serialization stack "complete… no undischarged obligation." That was a true description of what the *keyword* model achieved at the wire-and-synthesis layer, and this section does not retract it. What it records is that one of that model's premises stopped holding — the language gained the shared-ownership primitive [§5.19](#sec-serialization-without-reflection) explicitly declined to assume — and that the consequence is to **retire the `serialized tree`/`serialized graph`/`serialized cyclic` graph-shape clauses** and read the wire shape from field types instead (`owned` → an inline owning edge; `Shared<T>` → an identity participant; `Weak<T>` and a plain borrowing field → a back-reference). The keyword machinery is not deleted as *wrong*; the wire layer it produced stays. It is the *gate* that becomes redundant, and the one tier it could not give an ownership-valid construction — cyclic — that gains one.

**The premise that changed.** The whole v0.119–v0.124 design was built under one constraint, stated outright in the v0.120 working-out: reaching for the obvious mechanism — Rust's `Rc::new_cyclic`, which hands a closure a `Weak` into the not-yet-initialized allocation — it wrote "the principled Bezel analog is *not* `Weak` (Bezel has no reference counting and should not grow one for serialization)," and imported the *structural* idea (a controlled window in which a back-reference is wired after its target's storage exists) **without** the `Weak`, paying for it with the two-phase construction window and the self-contained-constructor eligibility rule (v0.123/v0.124). That was correct at the time: the language had no shared-ownership primitive, [§5.4](#sec-no-shared-ownership) having deliberately left one out. v0.134 then grew exactly that primitive — `Shared<T>`/`Weak<T>` ([§5.21](#sec-shared-t)) — for entirely independent reasons (caches, registries, the multi-consumer-channel question), as the scoped, explicit, opt-in form [§5.4](#sec-no-shared-ownership) had always said it would accept. Once `Weak<T>` exists as an ordinary owned handle, the mechanism v0.120 declined to grow is simply there, and the idea it imported by hand is expressible directly.

**What the new premise exposes: the cyclic tier had no ownership-valid construction.** The honest part, and the reason this is a correction and not only a tidy-up, is recorded as #703. A serialized graph is an owning spanning tree plus back-edges, where a back-edge is a borrowing reference field ([§9.8](Bezel_Language_Spec.md#sec-serialization-synthesis)). Whether such a field can be *populated* by an ownership-valid Bezel program is governed by the borrow-lifetime rule ([§28.3](Bezel_Language_Spec.md#sec-local-variables-ownership-and-borrows)): a borrow may live in a field only when its source provably outlives the containing object. For a **directed acyclic** graph this is satisfiable — a topological (owner-before-borrower) construction order builds each back-edge's target first and passes the borrow in as a constructor argument, its source outliving the borrower — which is exactly what `serialized graph` round-trips and what the §28.5 `_owner` back-reference shape constructs in ordinary code. For a **cycle** there is no such order: a mutual back-edge would require each node's source to outlive the other, which no construction sequence delivers, so the cycle-closing borrow cannot be shown safe and is rejected (`a.Next := a` is a borrow-into-field whose source is a scope-bound local — refused). The operational symptom is a test-honesty gap: the `serialized cyclic` positive round-trip tests cannot be written in ownership-valid Bezel and so bypass the ownership checker (#703) — a feature whose serialize direction has no value the language can construct. (The DAG tier is *not* in this position; its back-edges are constructable, so `serialized graph` is exercisable end-to-end. A stale sentence in §28.3 that read as a blanket "borrowing fields are not expressible" overstated the rule and was corrected separately, #717; the operative rule is the lifetime one.) With `Shared<T>`/`Weak<T>` the cyclic back-edge becomes a `Weak<T>` minted from a `Shared<T>` spine, and the cycle *is* constructable in honest Bezel (below); its round trip becomes expressible and passes through the checker like any other program. The defect dissolves not by relaxing a check but because the data finally has an ownership-valid producer.

**The construction, shown.** The reason the two-phase window becomes unnecessary is concrete, so it is worth exhibiting rather than asserting. A mutual cycle is built as a `Shared<T>` spine with `Weak<T>` back-edges wired after both nodes exist:

```bezel
using var a := new Shared<Node>(new Node(1));   // strong spine
using var b := new Shared<Node>(new Node(2));
a.Get().back := b.Downgrade();                  // Weak<Node>? back-edge, wired post-construction
b.Get().back := a.Downgrade();
```

Every step is ordinary ownership-valid code: `Downgrade()` yields an `owned Weak<Node>` from a live handle, stored into an `owned back: Weak<Node>?` field through the `Get()` borrow; the borrow checker accepts it (verified). The cost is real and stated: the back-edge field is **nullable** (`Weak<T>?`), assigned after construction rather than in the constructor. That is precisely *why* no two-phase window is needed — definite assignment ([§7.9](Bezel_Language_Spec.md#sec-definite-assignment-for-non-nullable-fields)) is satisfied trivially by the null initializer, and the later wiring is ordinary mutation, not a synthesized binding of a non-nullable field in a provably-unobservable interval. The v0.123/v0.124 machinery existed to bind a *non-nullable* back-edge without an observable unset window; a nullable `Weak<T>?` removes the obligation at its root. This is a genuine semantic difference from the keyword model (whose back-edges were non-nullable) and the right trade: a cycle-closing reference that can dangle (its target released) is nullable in substance, and the type now says so.

**Why this rather than the alternatives.** #703 named three resolutions; recording why the others were declined is the project's discipline ([§5.21](#sec-shared-t)'s declined-alternatives register). *Relax the ownership checker* to track owned-subobject lifetimes (so a borrow to a transitive owner is accepted) was declined: it is an open-ended ownership-analysis enhancement of uncertain blast radius that special-cases serialization back-edges inside the checker, and — decisively — it does not actually reach the cyclic case, because even an accepting checker leaves a *mutual* cycle with no order in which a **non-nullable** back-edge can be initialized at construction; one would still need a nullable field or a post-construction window. `Weak<T>` already exists, is nullable (so the definite-assignment question simply does not arise), carries last-one-disposes semantics the serializer needs anyway, and expresses the cycle in a first-class type rather than a checker exception. *Document the limitation* (ship `serialized cyclic` as construct-from-external-bytes-only) was declined as strictly worse than giving the feature an ownership-valid form: a serialization feature whose serialize direction is unreachable is the test-honesty defect, not a resolution of it.

**The field types already carry the shape the keyword asserted.** Each field's serialized role is read from its type: an `owned` field is an owning edge written inline; a borrowing field — plain or `Weak<T>` — is a back-reference written as a `$ref`; a `Shared<T>` field is an identity participant, written once at its first occurrence and as a `$ref` at every alias. The shape the clause asserted follows from those types, and the safe claim — the only one the redundancy argument needs — is that **the types are at least as informative as the clause and never contradict the data**: a class with no back-references of any kind serializes as a tree; one with borrowing fields and/or `Shared<T>` may alias; one with `Weak<T>` (or `Shared<T>` reaching an ancestor, the documented Shared-cycle leak, [§28.13](Bezel_Language_Spec.md#sec-shared-ownership)) may cycle. The clause therefore restated, as a header assertion, information the field types already carry — and could *diverge* from it (`serialized tree` on a class holding a `Shared<T>` field is a contradiction the compiler would have to police for no gain). The disposition is the one [§5.19](#sec-serialization-without-reflection) already took for the owning/borrow split it read straight from the annotations: delete the restatement and read the shape from the types. The clause is removed outright, not demoted to an optional checked assertion, because a checked assertion is still a second statement of the same fact, with the divergence-policing cost and none of the expressiveness.

**Retiring assert-and-enforce — and why it is not the regression it looks like.** v0.119 made *assert-and-enforce* load-bearing: tree-shape is not statically verifiable, so the programmer *asserts* `serialized tree` and the deserializer *dynamically enforces* it, raising on a repeated identity rather than silently duplicating (serde's documented footgun). Removing the keyword removes that assertion, and it deserves a direct answer. The answer is that the type-driven model does not need it, and the bad state it guarded against becomes *unrepresentable* rather than merely *detected* — the project's preferred disposition wherever it is reachable. Assert-and-enforce caught a *declared* shape that the data violates (`serialized tree` over a graph that aliases). With no declared shape there is nothing to violate: a `Shared<T>` field *is* an aliasing participant by its type, not by an assertion that might be wrong, so "declared tree, actually a graph" is not detected but cannot be written. The other thing the deserializer did — *identity preservation*, binding a `$ref` to the already-built object instead of silently duplicating — is **kept**, though its mechanism gains a step on the read side: the identity table now holds the first-reconstructed *handle* and resolves an aliasing `$ref` by `Clone()`ing it (incrementing the shared count) and a `Weak` `$ref` by `Downgrade()`, where the keyword model re-pointed a plain borrow. The wire form is unchanged; the deserializer's handle-aware resolution is the addition.

**No new wire, and the one soundness obligation.** No wire vocabulary is introduced: the `$id`/`$ref` identity envelope (v0.121, JSON form v0.139, stdlib [§2.15](Bezel_Standard_Library.md#sec-concrete-serialization-formats)) carries everything, so an aliased/DAG payload round-trips identity-for-identity; there are no legacy *cyclic* payloads to preserve, because none had an ownership-valid producer. The must-not-miss point is the identity *key*. A `Shared<T>`'s identity is the **object-reference identity of the value `Get()` borrows** — the same object-identity basis the existing `$id` tag→object table already uses (`Object.ReferenceEquals`, language spec [§8](Bezel_Language_Spec.md#sec-the-object-class)) — taken for a non-null live handle; a null `Shared<T>?` takes the ordinary `T?` null path, not the identity table. Two independently `Clone()`d handles to one value are distinct owned objects but their `Get()` borrows resolve to the same underlying object, so they collapse to one `$id` and alias correctly; keying on the *handle* instead would serialize the body twice and destroy the aliasing with no error in an unchecked build. The key is sound because within a single serialize pass every keyed value is simultaneously live ([§5.21](#sec-shared-t)'s last-handle-disposes invariant, normatively [§28.13](Bezel_Language_Spec.md#sec-shared-ownership)/Appendix C), so no address freed by a disposed value can be reused by another live one mid-pass.

**Disposal on deserialize.** Reconstructing a shared node returns `owned Shared<T>` — the caller's single vote, the handle at count one — and every alias in the graph is reconstructed by `Clone()`ing off the identity table, so the last handle disposes the value exactly once (the exactly-once invariant of [§28.13](Bezel_Language_Spec.md#sec-shared-ownership)/Appendix C). A class that merely *holds* `Shared<T>`/`Weak<T>` fields, rather than *being* the shared node, returns `owned C`; the distinction is locally decidable from the entry type. Double-free is structurally impossible: the value is released only at the last handle, behind the disposed guard, and `Weak<T>` never owns.

**Weak-reachability is enforced where shape always was — at read.** A `Weak<T>` back-reference is meaningful only if its target is *strongly* reached elsewhere in the same serialized graph; a `Weak` whose owning `Shared` is not serialized would resolve to nothing. This is a per-*value* property the field types cannot decide — type identity is not value identity, and the strong owner typically lives in an enclosing object, not a preceding same-class field — so it is enforced the way `serialized tree`/`serialized graph` shape always was, **dynamically**: a `Weak` `$ref` to a target never strongly tagged raises `SerializationException` ([§9.8](Bezel_Language_Spec.md#sec-serialization-synthesis)'s established read-side assert-and-enforce). A cheap static pre-check — a `Weak<T>` field is suspect unless some `Shared<T>` of the same `T` is serialized in the same class — is a lint that catches the trivial intra-class mistake early; it is necessary-not-sufficient and does not stand in for the dynamic guarantee. This keeps assert-and-enforce exactly where the keyword model kept it (the property the compiler cannot check is checked at read), now for the one obligation the types alone cannot carry.

**Polymorphic dispatch survives, rehomed — with one coupling rule retired.** The explicit closed registry (v0.122) — discriminator written first, dispatched through a closed registry on read, anything outside it raising — is orthogonal to graph shape and is **retained in mechanism**, including the security property that makes it closed-or-raise (the reflective `$type` remote-code-execution vector recorded in §5.19's v0.122 paragraph). What changes is more than its syntactic home: today the registry "may appear only together with a graph-shape assertion" and each registered type is eligible by "carrying a graph-shape clause" ([§9.8](Bezel_Language_Spec.md#sec-serialization-synthesis)). With the clauses gone, that coupling is dissolved and the eligibility predicate is restated in type-driven terms (a registered type must be type-driven serialization-eligible — `ISerializable`/`IDeserializable` with serialization-eligible components); the registry itself moves to a class-body member declaration listing the discriminator-to-type map. The closed-registry security argument and the type-scoping are unchanged.

**The honest accounting of "complete."** v0.124's claim was true of the wire-and-synthesis layer and stays true of it: every documented graph shape encodes and decodes. What it could not deliver — and could not, lacking a shared-ownership primitive — was an ownership-valid *construction* of a cyclic input, so the cyclic feature was complete-but-unexercisable, which is the #703 gap rather than a wire defect. "Rendered unnecessary" therefore applies cleanly to the two-phase machinery: a cycle now closes through a `Weak<T>` → `$ref` on an already-tagged node, the ordinary DAG resolve path, with no forward reference and no mutable post-construction window to prove unobservable; the v0.120/v0.123 unobservability-under-constructor-side-effects obligation is not merely discharged but off the critical path. "Given an ownership-valid form" applies cleanly to construction. The completeness is not retracted; it is recorded as premise-bound, and a later, independently-motivated capability ([§5.21](#sec-shared-t)) superseded the machinery the earlier constraint forced.

**The staging.** The migration follows the same additive-then-resolving discipline as every prior serialization stage. `Shared<T>`/`Weak<T>` are first admitted to the recursive serialization-eligibility set (purely additive: a class with these fields enters the identity path; every existing `owned`+borrow class is unaffected). Then the graph-shape clauses are removed, the field types having superseded them, the test surface migrated to express shape through types, and the `serialized cyclic` positive tests — which never had an ownership-valid producer — retired rather than rewritten. The `$id`/`$ref` envelope is unchanged throughout, so the one behavioural difference a user can observe is the intended one: a `Shared<T>` value's disposal happens at the last handle's release, anywhere in the program, rather than at a single owner's destruction — a contract of the shared-ownership type ([§5.21](#sec-shared-t)) made visible through serialization, not a regression in it.

<a id="sec-the-affine-model"></a>
### 5.23 The affine model: auto-drop with a must-use warning

*(This section hoists the load-bearing reasoning of the v0.150–v0.152 revisions out of the changelog ([`Bezel_Changelog.md`](Bezel_Changelog.md)) — which is not part of the language definition — into the rationale body, per the 2026-07 documentation review. The changelog entries remain the detailed record.)*

Bezel's ownership model was originally strict-linear on the normal path: an owned local that reached scope end undischarged — neither moved, returned, stored, nor disposed — was a hard compile error. Three pressures broke that position:

1. **The language was already affine at the seams.** The exception path has always disposed live owned values during unwinding (nobody proposes a compile error for "an exception happened while you held a resource"), and v0.149 made *unbound owned temporaries* auto-dispose at end of statement. That left the absurdity that *naming* a value changed whether the program compiled: `new Foo().Use();` compiled while `var a := new Foo(); a.Use();` was an error — a refactoring hazard with no safety content.
2. **The error rejected sound programs.** Every program it rejected had a perfectly defined meaning (dispose at scope end) that the exception path already implemented.
3. **Precedent.** Rust — the reference point for compile-time ownership — is affine: values drop at scope end, and "you probably meant to use this" is a lint (`#[must_use]`), not a rejection. Strict linearity (Austral-style) buys explicitness at the price of ceremony on every early return and every conditionally-consumed value.

The resolution (v0.150 for locals, v0.152 for `owned` parameters) is uniform **affine auto-drop**: an owned value still held at a normal scope exit is disposed there, implicitly, by the same mechanism the exception edge already used — with a **must-use warning** on the implicit drop of a plain `var`. The two declaration forms keep distinct intent: `using var` means scope-pinned (never movable, no warning — you said what you meant); plain `var` means movable, warned if implicitly dropped. The discard `_ := expr;` ([§3.2](#sec-the-discard-_)) becomes the explicit "dispose this now" form. Exactly-once disposal on every path is preserved throughout — the move analysis marks transferred values moved-from, and scope-end disposal skips them.

What was deliberately *kept* strict: `Task`/`Task<T>` discard stays an error (abandoning a running operation is a semantic decision, routed to `Task.FireAndForget`); moving out of a `using var` stays an error (scope-pinning is the form's entire meaning — the register's one recorded timing carve against the pin is axiom A12, Pattern A chaining, [§5.26](#sec-the-ownership-kernel)); and the §28.8.1 field-restoration rule is untouched (fields are object state, not scope state — auto-drop of a *field* would be a use-after-free generator, not a convenience).

The trade recorded honestly: the compile-time "you forgot to discharge" error is gone, replaced by a warning. Programs that leak by *intent-mismatch* (the author believed something consumed the value) now compile with a diagnostic instead of failing. Implementation experience since v0.150 supports the choice — the warning has proven sufficient signal in practice, and an entire class of false-positive discharge errors (branch-dependent consumption) disappeared with it.

*(v0.184.)* The three-pattern doctrine this section grounds is now stated once, normatively, in spec §28.3 "Choosing a disposal form": `using var` = declared intent + scope pin; plain `var` = movable, warned on the implicit drop; explicit `Dispose()` = an early/conditional release point (exception-safe by this section's own mechanism — the C# dispose-at-end anti-pattern deliberately does not transfer). The announced-kill family gained its third member — the discard of a named owned binding, `_ := x;` — under the same no-marker logic as `throw x` and `owned` returns; and the must-use warning was confirmed uniform across body kinds (frame-disposed `owned` parameters of iterators and async methods warn at the declaration, the adoption idiom being the warning-free spelling).

<a id="sec-the-full-expression-boundary"></a>
### 5.24 The full-expression boundary and the `case`-scrutinee extension (v0.193)

Once [§5.23](#sec-the-affine-model)'s model let unbound owned temporaries dispose implicitly "at the end of the full expression," that phrase carried load in a dozen rules — temporary-confined awaits, deferred-activation frame bounds, span admissions — without the spec ever saying what a full expression *is*. The 2026-07 round-2 sweep surfaced programs whose disposal points genuinely turned on the unstated boundary, and v0.193 defines it once (spec [§28.3](Bezel_Language_Spec.md#sec-unbound-owned-temporaries), #1795): a full expression is a **maximal** expression — one that is not a subexpression of a larger expression — with the positions enumerated (initializers, assignment right-hand sides, expression statements, each evaluation of a condition or pattern guard, `for` sources, `return`/`throw`/`yield return` operands, and `case` scrutinees).

Maximality is the only defensible direction: any narrower boundary disposes a temporary while an enclosing expression may still hold a borrow into it, and every sub-maximal candidate we examined was either unsound or an arbitrary line no reader could predict. (It is also the boundary C++ draws for its temporaries — one of the few places that precedent is genuinely simple.) The refinement that earns its keep is **per-evaluation** boundaries for conditions and guards: a loop condition is a fresh full expression at each iteration, so a condition's temporaries die before the next test runs. Keyed on the lexical occurrence instead, a condition that constructs a probe object would accumulate one undisposed temporary per iteration — an unbounded implicit leak inside the very mechanism §5.23 adopted to make disposal automatic and predictable.

The one place the boundary is deliberately wider than the producing expression is the `case` scrutinee: a scrutinee temporary lives through the whole construct, in statement position exactly as in expression position. Pattern bindings are borrows whose source is the scrutinee, so disposing the temporary at arm *selection* would kill every binding under the selected arm's feet (`case pool.PopFirst() of var f: FastConnection => f.Warm(), … end;`). In expression position this already followed from maximality — the enclosing full expression contains the whole construct — so the ruling aligns statement position with what expression position already did, rather than inventing new machinery. The alternative was the [§9.7](Bezel_Language_Spec.md#sec-records-and-disposal)-style rejection: forbid binding patterns over temporary scrutinees, as spans forbid temporary sources, and extend nothing. Declined, because the rejection could not be contained — to stay coherent it would have had to outlaw the expression-position form too, and that form was long-admitted and idiomatic. The stretch is recorded as the bounded thing it is: the boundary ends with the construct that syntactically contains the scrutinee, everywhere else §9.7's reject-not-extend posture stands, and Bezel still has no general lifetime-extension mechanism.

<a id="sec-deferred-activation-capture"></a>
### 5.25 Callbacks that outlive the call: frame residence and capture-carried sources (v0.196)

The capture rules of spec [§28.14](Bezel_Language_Spec.md#sec-scoped-callback-parameters) classify a plain function-typed parameter as *call-bounded* — every captured source trivially outlives the call, because the callback is not retained past it. That premise is false for precisely the callees whose point is deferral: an iterator, async iterator, or lazy query operator captures its callback into a frame that runs after the call returns. v0.179 had noticed the async half and added the settlement obligation, but iterators had neither a callee-side rule nor a caller-side one — and on the caller side, the frame's carried-source enumeration (receiver plus plain reference-typed arguments) never included *capture sets*, so returning an iterator frame built over a capturing callback (`return Doubled(nums, lambda(x) => scale.Apply(x));` with `scale` a `using var`) passed the frame-return check by the letter, while the same frame with `scale` passed as a plain argument was rejected at the same return site: a statically certain dangle, guarded by nothing. The v0.196 ruling (#1790) closes both halves with the announcement-by-declared-type doctrine this chapter keeps returning to. Callee side, **frame residence is the admitted retention and the frame's life is the bound** — settlement for a task, completion-or-disposal for an iterator frame, the single consumption point for a lazy query — announced by the deferred-activation return type exactly as that type already announces the frame's carried object borrows (spec [§28.3](Bezel_Language_Spec.md#sec-returning-a-deferred-activation-frame)). Caller side, a callback argument contributes its captured borrows' **sources** to the frame's carried-source set, so the ordinary borrow machinery — not a new check — rejects the dangling composition at the return site.

The contribution is computed from statically known provenance, transitively (a captured closure contributes *its* sources in turn), and the provenance table's edge rows are where the design earns its keep. A function value fetched from a plain field or a collection contributes nothing — *soundly*, because the closure-escape rules never admitted a borrow-capturing closure into such storage in the first place: plainly-stored function values are borrow-free by construction, and no whole-program analysis is needed. (The one storing location that does hold capture-bearing callbacks — a `scoped` field — contributes nothing only because the read-out is itself barred: passing a `scoped` field's value into a deferred-activation plain position is rejected as an escaping read-out, spec [§28.14](Bezel_Language_Spec.md#sec-scoped-callback-parameters), v0.196 — the liftable widening, contributing the field's owner as the source, is recorded there.) And a plain function-typed *parameter* of the enclosing body contributes *itself*: the parameter becomes a carried source that every caller re-establishes against its own actual argument, which is what keeps the forwarding combinator — `Filtered(xs, f) => xs.Where(f)` — compositional. (Rejecting opaque parameter arguments instead was declined as outlawing half the motivation.) This is the same signature-level re-establishment as [§5.7](#sec-factory-method-ownership)'s source-set rule and §12.10's callee-side task rule; the three rulings share one skeleton.

Two postures were declined by name. Spelling the retention `scoped` is the wrong tool on four counts: `scoped` means storage-bounded-by-an-*object*, with an admission and freeze built for open-ended object lifetimes, while a frame is a flow-tracked value the borrow machinery already bounds; v0.180 bars `scoped` on static methods without `owned` returns — a compile error for the dominant iterator shape; its admission forms exclude plain-parameter forwarding, half the motivation again; and it would force a breaking migration of every lazy standard-library operator. And leaving the retention *documented but unverified* — the pre-v0.179 async posture — was declined more firmly than anywhere else it has come up: v0.179 already rejected that posture for async, and the iterator case is worse, because the frame is long-lived *by design* (lazy evaluation is the feature), so the documented gap would be load-bearing for a statically certain soundness break rather than a hedge over a lifetime the checker cannot compare. What the declines protect: no standard-library signature changes (the lazy operators' plain signatures become the normative instance of the general rule, not a certified exception), async upgrades from trust to rejection — statically-certain dangles at return sites, and categorically, paralleling object-borrow escapes, at store and scope sites, and user code can finally write callback-taking iterators at all.

<a id="sec-the-ownership-kernel"></a>
### 5.26 The ownership kernel: reasons and the axiom budget (v0.198)

Spec §28.3 opens with the ownership kernel — nine principles, K1–K9, from which the chapter's rules derive — and closes its kernel subsection with a register of twelve recorded axioms and two tombstones (A1–A14; A1 retired v0.201, A8 retired v0.213): the rules the kernel cannot derive, each a design decision with a recorded reason. This section carries the reasons, and the discipline the register installs.

**Why a kernel.** The ownership chapters grew by accretion of rulings — each individually reasoned, collectively unpredictable: a reader could not derive the rule they hadn't read. Consolidating the load-bearing principles into one normative statement buys three things at once. *Predictability*: the freeze's membership, the admitted await positions, and the equalization patterns all compute from stated principles instead of being memorized as lists. *Auditability*: the "memory rules few enough to learn in full" bet (§1) finally has a count — nine principles plus the axiom register's rows are what "in full" contains (the count is the register's to state at any revision; the learnability claim is the *discipline* — visible append, tombstoned delete — not any fixed number). *Mechanizability*: a finite kernel is a modelable one, and a derivation-tagged chapter is one whose diagnostics can explain rejections by derivation. The kernel is deliberately prose, not formal notation: the spec's register is precise prose for the guides' audience, and the formal artifact has a better home in a mechanized model of the kernel, which can be exact without being normative.

**The budget discipline.** The axiom count is published as the language's honest complexity budget. A future ruling that touches §28/§30.5 states its classification — a derivation (naming the K's), an axiom extension (naming the axiom), or a new axiom (adding a register row with its recorded reason). This is a changelog-entry obligation on the spec-change checklist. Axiom ids are frozen: new axioms append; deletions leave a tombstone row pointing at the deleting revision's changelog entry, so "which axiom did this ruling extend?" stays answerable historically. Two candidate axioms were examined during consolidation and classified derived instead — the v0.196 property-getter-only static-storage admission (derives from K2.4 + the declaration-site static-return rule, v0.201 — at consolidation time, K2.4 + then-axiom A1: a storage-returning static *method* is signature-indistinguishable from a factory; the property face's read is the sound dual) and the maybe-consumed join (derives from K7 with the v0.184 free-precision argument) — the worked precedent that the register resists both inflation and laundering.

**The axioms' reasons.** Where an axiom's full reasoning already lives in this document, the register row points here and this list cross-references it rather than duplicating:

- **A1 (tombstone, retired v0.201)** — [§5.7](#sec-factory-method-ownership): the v0.60 factory-default bridge, retired when its motives discharged; static class- or interface-typed returns now announce in the signature (spec §28.3). The register keeps the tombstone so the extension point stays answerable historically.
- **A2 (calls-mint keyed to the `Task` family)** — [§12.10](#sec-calls-mint-storage-lends): extending calls-mint to iterables would break the legitimate stored-collection-view *method* idiom (`Items(): IEnumerable<Item>` returning a field); the task stored-view is routed to the property face — a recorded cost of v0.190 — so the family boundary is exactly where minting is sound.
- **A3 (the two-container async design)** — [§12.1](#sec-pattern-a-vs-pattern-b-is-type-directed)–[§12.2](#sec-choosing-between-taskt-and-taskowned-t): fan-out versus acquisition is a surface design choice the producer makes in the signature; the kernel checks both flows, forces neither.
- **A4 (accessor faces are lend-only)** — signature predictability: an accessor read has no marker position, so admitting owned production through a getter would make ownership invisible at every property read; factories are methods, where the `owned` return announces. (Recorded here; spec §23/§28.6 state the rule.)
- **A5 (`using var` is a scope pin)** — [§5.23](#sec-the-affine-model): the form's entire meaning is declared intent plus scope-pinning; movability was deliberately kept out at the affine transition so that the two declaration forms keep distinct intents.
- **A6 (`Task` discard rejection)** — [§5.23](#sec-the-affine-model) and [§3.2](#sec-the-discard-_): abandoning a running operation is a semantic decision, not a disposal; the routed spelling (`Task.FireAndForget`) keeps the decision visible.
- **A7 (no `??`-operand/operator-operand transfer marker; narrowed v0.209)** — the register's liftable bound, half-lifted as designed: proposal 0056 supplied the arm spelling (`owned x` in if-expression branches and expression-`case`/`when` arm results — a K3.4 derivation riding K7.4's existing per-path machinery, no new axiom), and the row narrowed to the positions still unspelled. The `??`-operand lift is gated on a genuinely new ruling 0056 records (the post-state of a marked nullable binding evaluated while null); operator operands remain unmotivated. No-silent-consume stays uniform where no marker exists.
- **A8 (tombstone, retired v0.213)** — [§5.3](#sec-collections-do-not-own-their-elements)/[§5.1](#sec-owned-not-borrows): the caller-vouched transit disposal, retired when the 2026-07 corpus sweep (#2075) found zero load-bearing clients — the values-owned shape is `OwningDictionary`'s by construction and the own-keys direction has none; the register keeps the tombstone so the extension point stays answerable.
- **A9 (the two collection families)** — [§5.3](#sec-collections-do-not-own-their-elements)/[§5.11](#sec-owned-element-collections): the v0.97 resolution after the `<owned T>` merged form (v0.88–v0.96) collapsed under its substitution machinery.
- **A10 (stdlib certification grants)** — a named allowlist of trust granted to specific stdlib types (`CancellationToken`'s source-outlives-settlement certification; the legacy completion-source admission): by construction not derivable — the grant is the stdlib vouching for its own implementation — and acceptable only because the list is closed, named, and normatively stated at each type.
- **A11 (the §28.14 admission forms and bounds)** — decidability engineering (#1421): the chosen static story for "capture source outlives bounding object" among several sound alternatives; several bounds are recorded liftable, and lifting one swaps an axiom clause for a derivation without touching the principle (K2.3 + K5.7).
- **A12 (chaining's timing dispensation)** — a recorded timing carve against A5's pin for the one composition where the pinned slot already lives in the async frame: deferral to the outer task's teardown preserves exactly-once transitively and moves nothing.
- **A13 (the move-only reassignment carve)** — recorded debt, tracked (#1385) and interacting with the open #747 design: the one carve-out on the exactly-once claim, kept visible as an axiom precisely so it cannot be mistaken for intended design.
- **A14 (no `owned` generic arguments)** — [§5.3](#sec-collections-do-not-own-their-elements)/[§5.11](#sec-owned-element-collections): the substitution machinery was tried for nine revisions and abandoned; named types capture owning semantics without it.

**What the kernel deliberately excludes.** Sendability and the domain memory model (§12.5–§12.7), nullability, and definite assignment are adjacent systems with their own rules; the kernel touches them only at named interface points (spawn/send as consume positions; the domain clause as K4.3's recorded limit). A second kernel for the domain model, if ever warranted, is its own proposal.

<a id="sec-why-using-var-is-not-folded-into-var"></a>
### 5.27 Why `using var` is not folded into plain `var` — or into `const` (v0.205)

The proposal recurs naturally, and this section is its standing answer. Local ownership is inferred, not annotated ([§5.5](#sec-local-variable-ownership-is-inferred-not-annotated)); `const` covers non-owned single assignment (v0.201, [§17.8](#sec-readonly-local-bindings-let-val-readonly-var)); and the affine auto-drop disposes a plain-`var` owned local at the same scope-end point as a `using var` on every non-moved path — the spec's own recap says the forms "never add *safety*; they add **declared intent** and **timing**" (spec [§28.3](Bezel_Language_Spec.md#sec-local-variables-ownership-and-borrows), *Choosing a disposal form*). So the keyword can look like ceremony over inference: why not let `var` do everything? The question was examined against the full rule surface at v0.204 and declined, for four reasons that are one reason: **the keyword is not an inference annotation but a declared constraint on the binding's future, and a checker cannot infer the intent it exists to check.** Inference reads the initializer — the past. The keyword constrains what comes after — reassignment, movement, source liveness — which no use pattern present in the code can imply, because the constraint is deliberately stronger than any use.

*First, the pin has no substitute.* A5's guarantees — non-reassignable, never movable out — exist to make *maintenance drift* a compile error at the drift site: a lock guard threaded out of its critical section, a mid-scope re-acquisition, a borrow's source consumed under a view the author meant to hold whole-scope. The borrow-pin (spec [§28.10](Bezel_Language_Spec.md#sec-using-var-initialized-from-a-borrow)) is the only spelling of "keep this source live to the end of this scope"; its nearest encoding without the keyword is a dummy use on the block's last line — an invariant written as dead code. Movability was deliberately kept out at the affine transition so that the two declaration forms keep distinct, checkable intents ([§5.23](#sec-the-affine-model)); that decision is re-affirmed here, not merely inherited.

*Second, the lint and the keyword are one economy.* The must-use warning is the affine model's compensating diagnostic — the v0.150 trade replaced the hard discharge error with a warning precisely because a zero-ceremony declared-intent spelling exists to silence it ([§5.23](#sec-the-affine-model)). Without `using var`, the warning either fires on every idiomatic scope-held acquisition (`using var guard := mutex.Acquire();` is the standard library's own idiom, stdlib [§6.2](Bezel_Standard_Library.md#sec-mutex-and-lock)), or is silenced by a trailing explicit `Dispose()` — ceremony that corrupts the doctrine that an explicit dispose signals an *early or conditional* release — or is retired, reversing the recorded trade and letting the intent-mismatch leak class go dark. The warning is high-signal because the silencer is zero-cost; the silencer is meaningful because the warning exists. The pair stands or falls together.

*Third, the keyword is a loudness channel for API evolution.* When a callee's return type flips between borrowed and `owned`, today's binding forms grade the blast radius at every call site: `const` sites reject (an owned production is inadmissible there, spec [§21.1](Bezel_Language_Spec.md#sec-variable-declarations)), plain-`var` sites warn at the new implicit drop, and `using var` sites absorb the change correctly by uniform admissibility. Unification — with the lint necessarily detuned per the previous paragraph — reduces that matrix to silence: sound in every cell, affinity guarantees it, and invisible in exactly the dimension (who disposes, and when) this language undertakes to make visible.

*Fourth, "only `var`" is unreachable anyway.* Whether disposal *awaits* is deliberately not inferable: an implicit disposal point never awaits, so a class whose async cleanup must run needs an `await using var` binding (spec [§28.12](Bezel_Language_Spec.md#sec-asynchronous-disposal)) — and `TaskScope` is consumable by `await using` only (stdlib [§6.10](Bezel_Standard_Library.md#sec-taskscope)). The `out owned` recipient form `out using var` (spec [§22.4](Bezel_Language_Spec.md#sec-inline-out-declarations)) survives for the same reason. The end state of the proposal is therefore not one binding form; it is the same number of forms with the common one missing.

**Nor does `const` absorb it.** The v0.201 settlement drew this seam deliberately ([§17.8](#sec-readonly-local-bindings-let-val-readonly-var)): `using var` is the owned, scope-pinned binding with declared disposal; `const` is the non-owned one whose bindings never change state — not by assignment, not by consumption, not by disposal — and the permissive owned-`const` was declined then as an undeclared-disposal duplicate of `using var`. The reasons hold from both directions. A `const` that accepted owned producers would hide a real scope-end event behind the one keyword whose entire claim is that nothing ever happens — `const guard := mutex.Acquire()` would release a lock at `end` — and the async surface makes the hiding structural: `await using var` marks a suspension point at scope exit, and an "await const" is incoherent. A `using var` doing `const`'s job forces pin semantics onto every fixed borrow — a `const` borrow's constraint on its source deliberately ends at its last use (spec [§21.1](Bezel_Language_Spec.md#sec-variable-declarations)), so the source may legitimately be consumed or disposed afterward, a program the pin rejects — and reads absurdly over plain values, which is the pre-v0.201 state §17.8 records as tolerated-not-endorsed (#1360). A single merged fixed-binding form must choose always-pin (rejecting legal `const` programs) or never-pin (deleting the borrow-pin's only spelling, on which the [§29.2](Bezel_Language_Spec.md#sec-desugaring-of-for) `for`-desugaring and deliberate iterable pinning stand); no intermediate point exists — a pin either is a compiler-enforced guarantee or it is not.

What the examination *conceded* is recorded with equal weight. The keyword adds no safety and no disposal timing on non-moved paths — the spec says so in terms. It does not tell the reader whether the binding is owned: its own owned-versus-pin split is dispatched by the right-hand side (spec [§28.10](Bezel_Language_Spec.md#sec-using-var-initialized-from-a-borrow)), the one genuine reader ambiguity in this area. The residual overlap with `const` over inert right-hand sides is real, tolerated for generic and desugaring uniformity, and steered by diagnostics rather than semantics (the vacuous-pin lint, #2073). And the compiler's two-path local classifier is duplication the surface design does not require — the spec defines a `using var`'s state by the same right-hand-side algebra as `var`, so the implementation should compute it through one funnel with the pin and the lint boundary as layered flags (#2071, #2072). Formally, unification introduces no ownership ambiguity: inference is total either way, and always was. What it removes is the reader's instrument, not the checker's — the one binding form whose *scope-boundness* is declared at the declaration, locally visible, and compiler-enforced. The checker never needed `using var`. The reader is who it is for.

<a id="sec-nullability"></a>
## 6. Nullability

<a id="sec-field-narrowing-is-not-safe-across-threads"></a>
### 6.1 Field narrowing is not safe across statements

`if user <> null then user.Method() end;` works for locals because the compiler knows nothing else can reassign them. For fields, the same code is a compile error — not primarily because of threads (since v0.131 a domain's continuations are serial, [§12.5](#sec-execution-domains)), but because the field can be reassigned between the check and the use by paths the compiler cannot see: a method call whose body writes the field (directly or through an alias to the same object), a closure invoked in between, re-entrant code reached from the check's own expression, or — across an `await` — any other continuation of the same domain interleaving at the suspension point. Foreign threads introduced through the FFI remain a residual case ([§16](#sec-ffi), spec §30.12). An **uncaptured** local has none of these writers, so narrowing it is sound; a local mutably captured by a lambda has exactly one — the closure — which is why spec §7.4 (v0.182) invalidates a captured local's narrowing at any call, function-value invocation, or `await` inside the controlled block.

The compiler does not narrow mutable fields. Since v0.214 the one field kind with *no* writers outside construction — `readonly` (single-assignment, §22.8; no `ref`/`out` escape, §22.3) — narrows, with the single-segment path and construction-window rules spec §7.4 states; the copy-to-local pattern remains for everything mutable:

```bezel
var u := _user;
if u <> null then u.DoStuff(); end;
```

Some languages (TypeScript) narrow property accesses and pay for it with subtle time-of-check/time-of-use bugs; Kotlin refuses to smart-cast mutable properties for exactly this reason. Bezel declines to narrow fields entirely.

<a id="sec-is-postfix-only"></a>
### 6.2 `!` is postfix only

`name!.Length` reads left-to-right; prefix `!name.Length` would have to be parenthesized. There is also a semantic argument: `!` asserts something about the value to its left, and putting the assertion to the left of the asserted value reads backwards.

There is no prefix `!` for boolean negation either; `not` is the boolean operator.

<a id="sec-interpolating-a-nullable-renders-null"></a>
### 6.3 Interpolating a nullable renders `null` (v0.184)

`$"{x}"` over a `T?` is the most common diagnostic line in the language; requiring narrowing or `??` there (the §4.6 strict-ordering template) would tax every log statement for zero safety — rendering is total and loses nothing. Between C#'s empty string and a visible token, the visible token wins: an empty hole *hides* the null that a log line exists to reveal. The format spec is skipped on null rather than dispatched (there is no value to format) but stays compile-checked against `T`, so a bad specifier target is caught regardless of the value's presence.

<a id="sec-equality-and-hashing"></a>
## 7. Equality and hashing

<a id="sec-=-invokes-equals"></a>
### 7.1 `=` invokes `Equals`

A perennial C# bug is reference-equality on a class that should have had value equality. Bezel chooses the other way: `=` invokes `Equals`. For records, `Equals` is value equality by default. For classes, `Equals` is reference equality by default but overrideable.

The common case does the right thing. For genuine reference comparison, `Object.ReferenceEquals(a, b)` is available.

<a id="sec-=-cannot-be-overloaded-on-classes"></a>
### 7.2 `=` cannot be overloaded on classes

Operator overloading of `=` on classes invites bugs: the override defines value equality, but the rest of the language treats classes as reference types in many places (collections that hash on identity, `is` checks). Classes customize equality through `Equals`; records and enums may overload `=` and `<>` freely.

<a id="sec-overriding-equals-requires-overriding-gethashcode"></a>
### 7.3 Overriding `Equals` requires overriding `GetHashCode`

The "if you override one, override both" invariant is a source of bugs in other languages because it's a documentation rule, not a language rule. Bezel enforces it at compile time. The cost is a `GetHashCode` on types that may never be hashed; the benefit is that no Bezel type can produce silent dictionary-lookup bugs years later when someone refactors.

<a id="sec-float-equality-is-reflexive"></a>
### 7.4 Float equality is reflexive

`NaN.Equals(NaN)` is `true`. `(-0.0).Equals(0.0)` is `true`. The relational operators `<`, `<=`, `>`, `>=` keep IEEE semantics — any comparison involving `NaN` is false.

The asymmetry is intentional. Equality is what hash tables, sets, and `case` patterns use; an irreflexive `=` makes `Set<double>` misbehave when NaN is inserted. Relational operators retain IEEE semantics so numeric algorithms work as published. Strict IEEE equality is available as `Double.IeeeEquals`; bit-pattern equality is `Double.BitwiseEquals`.

<a id="sec-inheritance"></a>
## 8. Inheritance

<a id="sec-member-hiding-is-forbidden"></a>
### 8.1 Member hiding is forbidden

C# allows a derived member with the same name as a base member to *shadow* (not override) it, with dispatch depending on the static type of the receiver. Almost no one understands the semantics correctly, and the rare cases where it's the right tool are better solved by renaming.

Bezel rejects same-name members in derived classes outright. To override a virtual base member, write `override`. To add something new, choose a different name.

(v0.184) The blocked set is **visible** inherited members (§12.2): the recorded motivation above — shadowing and dispatch confusion — requires a member the derived author could see. A base class's `private` (and cross-module `internal`) names stay out of its compatibility surface; the residual cross-module collision creates two distinct members resolved by visibility and static type, recorded as the deliberate scope of the guarantee.

<a id="sec-class-hierarchy-exhaustiveness-in-case"></a>
### 8.2 Class-hierarchy exhaustiveness in `case`

A sealed hierarchy can be matched exhaustively without a `_` arm: if the base class is `sealed abstract` (or abstract with only `sealed` subclasses, recursively forming a closed set — spec §19.6) and every concrete leaf type appears as a pattern, the match is provably total.

This is the partial form of sum types — useful where it applies, no language additions required. Full sum types remain deferred ([§18](#sec-things-deferred)); the hierarchy form covers most of the use cases.

<a id="sec-records-and-classes"></a>
## 9. Records and classes

<a id="sec-why-records-cannot-have-destructors-or-owned-fields"></a>
### 9.1 Why records cannot have destructors or `owned` fields

A record is copied on assignment. If a record had a destructor, every copy would need to track whether it owned or borrowed the underlying resource — C++ value semantics, with their attendant complications.

The clean rule: records hold values and borrowed references. They never own resources. If you need ownership, use a class.

<a id="sec-why-records-are-sealed"></a>
### 9.2 Why records are sealed

Inheritance and value-equality conflict. The classic problem: does `Square(5, 5) = Rectangle(5, 5)`? Either answer is wrong in some context. Records side-step this by being sealed. They may implement interfaces, which gives polymorphism without the equality problem.

<a id="sec-auto-equality-on-body-only-records"></a>
### 9.3 Auto-equality on body-only records

A record whose body contains only auto-properties and methods (no explicit fields, no computed properties with side effects) gets auto-generated `=`, `<>`, and `GetHashCode` over those auto-properties. This is what makes `DateTime`, `TimeSpan`, `Guid`, and similar standard types work as equality-bearing without per-type overloads.

The previous rule ("body-only records get no auto-equality") was simpler but forced every standard library record to write `=`/`<>` overloads explicitly, with no benefit. The refined rule keeps the simple cases simple.

<a id="sec-enum-interface-implementation"></a>
### 9.4 Enum interface implementation

v0.60 prohibited enums from implementing interfaces, even though enums could already declare methods and properties with the same signatures. This meant a user enum with a `CompareTo` method could not declare `: IComparable<MyEnum>`, making it invisible to generic algorithms constrained on interfaces. The restriction was artificial — there is no semantic obstacle to an enum implementing an interface, since the interface methods are simply dispatched to the enum's declared methods.

v0.61 lifts the restriction. Enums may now declare interface conformance. The interfaces appear after the underlying type in the inheritance list: `enum Priority: int, IComparable<Priority>`. The enum must provide matching public members for every interface member, just as classes and records do.

<a id="sec-sealed-abstract-classes"></a>
### 9.5 `sealed abstract` classes

The sum-type pattern — a closed set of alternatives matched exhaustively — is common in language design and appears frequently in Bezel's own `case` matching. v0.60 supported this via `abstract` base classes whose subclasses are all `sealed`, but the base class itself could not be both `abstract` and `sealed`, so external code could always subclass it (breaking exhaustiveness guarantees across module boundaries).

v0.61 permits `sealed abstract` on a class declaration. The meaning is: the class cannot be instantiated (abstract) and cannot be subclassed outside its declaring module (sealed). Within the declaring module, subclassing is permitted. This gives the language a mechanism for closed hierarchies that is enforced by the compiler rather than by convention.

The `sealed abstract` combination was previously rejected because `sealed` and `abstract` seemed contradictory. The resolution reads the pair, not the words in isolation: in the `sealed abstract` combination the seal sits at the module boundary — no subclasses outside the declaring module (spec §11.7) — while plain `sealed` keeps its ordinary meaning of no subclasses at all (spec §12.4).

<a id="sec-choices-why-a-new-kind"></a>
### 9.6 Choices: why a new kind, and why not the alternatives (v0.200)

Spec §35 adds `choice` — closed nominal sums with payload-carrying cases — as its own type kind. The decision has two halves: why the kind earns its place, and why the three rival encodings were declined as the primary answer.

**Why a kind.** The language's stated domain (services, tools, parsers, protocol code) has "expected failure with information" as its bread-and-butter shape, and the guide's own advice ("return the outcome, don't throw") had no natural spelling: nullable returns cannot carry *why*; the Try pattern spends four interacting features (`out owned`, inline `out`, the `when true` postcondition, the stdlib shape conventions) to express "value or failure" and still carries the failure in out-parameters; `sealed abstract` hierarchies are the real sum workhorse but are heavyweight for a return type — heap allocation, reference semantics, type-test patterns instead of destructuring, and the v0.196 generic-leaves determination rule, a page of machinery that exists only because class sums encode the discriminant in the runtime *type*. A choice's discriminant is a case *name*, so exhaustiveness is counted per name and the determination problem dissolves. Every hard ingredient existed by v0.197 — closed-set exhaustiveness, positional destructuring, derived type properties, the move-only category (whose extension §5.14 explicitly anticipated), announced-consumption forms, the full-expression `case`-scrutinee boundary — making the kind composition, not new theory.

**Why the ownership story is a classification.** The three-way payload-derived classification (value-like / borrow-bearing / owning, spec §35.4) reuses §9.7's derivation pattern exactly: aggregates carrying borrows need no new lifetime kind, and aggregates carrying obligations join §15.3's move-only category. The owning match's two announced triggers — fresh temporaries, and the explicit `case owned x of` marker — follow the v0.180 marker principle rather than §30.5's marker-free await consume, because two of the three announced-kill ingredients are absent (a choice is legitimately multiply-inspected, and a moved value sets no disposed flag); the scrutinee marker is the one position where the otherwise-redundant move-only `owned` marker carries meaning, because scrutinee position has an unmarked *borrow* reading to disambiguate. Guards observe borrows with transfer at arm selection — the only sound reading that keeps guards available. Owning choices deliberately escape §15.3's reassignment carve-out (#1385): a choice has no partial states, so automatic drop-on-overwrite is sound and taken.

**Declined: widening `enum`.** The enum contract is integer-backed at every joint — explicit values, duplicate-constant aliasing, integer casts, name-string serialization — and each would need an "unless it has payloads" fork: a kind split hiding inside one keyword. Swift's merged spelling works because it was built that way from day one. Two keywords, two clean contracts.

**Declined: class-backed sums (or sugar over them) as the primary answer.** Wrong cost model for outcome returns (allocation, reference semantics), no destructuring for classes by recorded decision (§5.17), and the determination-rule tax on generic coverage. `sealed abstract` hierarchies remain the right tool for open-ish, behavior-carrying, identity-bearing sums; the line is drawn at value-shaped outcomes.

**Declined: structural unions (`A | B`).** Anti-nominal: no case names to hang exhaustiveness on, unclear identity, an inference surface that pervades the type system, and a direct collision with the recorded nominal-products posture (D-0002; the records-vs-tuples argument). A payload's *meaning* is exactly what nominal cases record and structural unions erase.

**Equality follows the record precedent, not the inline-array one.** §15.3 gives owning inline arrays borrowing equality (per-slot reference equality for class elements); choices instead take §9.2's use-site error for the non-value-like classifications — reference equality smuggled inside a value type's `=` is virtually never the intended semantics, and the two recorded precedents genuinely conflicted; the conflict was surfaced and ruled, not papered over.

**`default` is declined for every choice.** A sum has no principled zero, and electing a case would make meaning depend on declaration order; the enum precedent does not transfer because an enum value *is* its integer and zero exists regardless. Recorded liftable if evidence arrives.

<a id="sec-pure-declared-not-derived"></a>
### 9.7 `pure` is declared, not derived (v0.202)

Spec §22.15 adds the `pure` member modifier — effect-freedom as a declared, compiler-verified signature fact. The mechanism choice needed defending, because §3.6's closing paragraph pushes new classifications toward *derivation*. Three reasons it is declared:

- §3.6 governs structural classifications of *types*; purity is a behavioral contract of a *member* — the same grammatical species as `owned` on a return or `scoped` on a parameter, all declared, none derivable from structure.
- §12.6's principle (derived properties are observations, not obligations) inverts here: **inferred** purity would be an observation callers silently convert into an obligation — adding one log line to a leaf method would flip the inferred purity of every transitive caller, breaking every pure-context use with no declaration anywhere recording that a promise existed. Declared purity puts the promise, and the breakage, at an explicit keyword whose removal is a visible signature change.
- The artifact interface (§2.8.2) carries signatures, not bodies; an inferred fact would make module interfaces change when bodies change — the instability §2.8.2 exists to prevent.

The v1 boundary decisions, recorded: purity is **not determinism** (reads of mutable state are permitted; `det`/`total` are separate future promises — `pure` permanently means effect-free); class construction is excluded except the **throw carve-out** (a trivial-dispose class with a pure constructor as the immediate throw operand — without it, argument validation would be unwritable in the whole pure fragment and programmers would launder faults through provoked built-ins); function-typed values may be defined but not invoked (their types carry no effect information; the `(int) pure -> int` extension is the recorded v2, riding §27.1's modifier-identity precedent); override/implementation matching is strengthening-only (never-drop / may-strengthen / monotone — the exact-match alternative would sever every stdlib interface implementation from purity). The stdlib first wave annotates only non-virtual concrete members; annotating `IComparable<T>`/`IEquatable<T>`/`Object` roots is a recorded breaking-change event for a future major revision. The recorded widening (trivial-dispose construction admission, lifting `string.Split`-class exclusions) is proposal 0042 §8's variant B, staged behind one implementation cycle.

<a id="sec-contracts-grammar-and-tiers"></a>
### 9.8 Contracts are grammar, and the tier is the contract's honesty (v0.203)

Spec §22.16 adds `requires`/`ensures`/`invariant` — SPARK-lineage behavioral contracts, not Dafny-lineage proof obligations. The decisions with recorded reasons:

**Grammar, not attributes or library calls.** Bezel has no attribute system and the deferral is reasoned (§18); C# Code Contracts — conditions as method calls, a bolt-on rewriter, no compiler ownership — is the named cautionary lineage, and §22.4 already chose the compiler-recognized-clause route for exactly this kind of declaration. A body statement (`Verify.That`) cannot appear in the signature or artifact interface, cannot bind overrides, cannot be consumed by callers, and has no `result`/`old` or every-return-edge evaluation point; 0031's `Verify.That` stays as the body-internal complement with its distinct exception.

**Clauses are pure borrows** — the 0042 dependency: because a clause has no effects, evaluating, eliding, and proving it are indistinguishable to every non-violating program, which is what makes the tier system (proven / checked / assumed) coherent and the checked→proven ratchet meaning-preserving. Eiffel's side-effecting assertions and its global suppression flag are the counter-examples; both are declined.

**One violation exception, always-on `requires`.** `ContractViolationException` for all three kinds — the `ArgumentException`-compatible alternative was presented and declined (no honest `ParamName` mapping for multi-term conditions; two types for one mechanism; recovery arms written for input validation should not silently absorb bug reports; the per-member migration cost is recorded and borne deliberately, which is why the stdlib ships no clause conversions yet). `requires` is never elided (the 0031 posture — it replaces an always-on idiom); `ensures`/`invariant` run under checked-contracts mode, the §28.2 two-mode shape with a crucially different relaxation: non-evaluation (defined behavior, purity making it unobservable), not undefined behavior.

**Behavioral subtyping without weakening syntax.** Overrides inherit clauses verbatim, may add `ensures`, may not declare `requires`; multi-root preconditions combine by disjunction (the Eiffel inherited-precondition rule, arrived at for the same reason); `require else`/`ensure then` refinement syntax is declined until demand materializes.

**Invariants at the public boundary with the `this`-reentrancy exemption** — the Eiffel lessons adopted (interior algorithms legitimately traverse broken states; checked/unchecked faces make the exemption statically decidable), the Eiffel machinery (suppression flags, refinement keywords) not. Getters exempt, with the residual recorded; construction checks at most-derived exit only, composing with §22.7's observation gate by construction.

**The prover floor is honest.** Exactly two things are proven in this revision: constant folds and §22.4's `when` clauses (the shipped flow prover, now *named* as the prover it is — §22.4 is retro-unified as a `static ensures`, surface-preserved, zero migration). Essentially every authored clause is checked; the extended fragment (linear integer arithmetic, null-test flow, closed-set case analysis) is fixed now as an Appendix D feature so `static`'s meaning never drifts — a demanded proof never silently becomes a runtime check.

<a id="sec-interface-carries-contracts"></a>
### 9.9 The interface carries contracts, textually (v0.204)

Spec §2.8.2's contract records (v0.204) rest on three decisions worth recording.

**Clause identity is textual.** Semantic equivalence of clauses is undecidable (clauses are boolean expressions over arithmetic and calls; deciding `requires(a and b)` ≡ `requires(b and a)` in general is deciding formula equivalence), and any decidable approximation misclassifies in one direction or the other. Textual identity is the conservative choice with a stated bias: it never *under*-reports a contract change — soundness for any gate built on the classification — at the cost of over-reporting stylistic re-spellings (`1_000` → `1000`, added parentheses, re-qualified names) as clause replacements. The two admitted canonicalizations (comments and whitespace; parameter and type-parameter positions) are exactly the ones that keep the record stable under edits *invisible at every use site*: a `ref`/`out`/`owned` parameter rename is call-site-invisible (spec §22.5: those arguments are positional-only), a plain-parameter rename is already a *signature* event (named arguments) and should surface once, as one — not twice with a spurious clause delta beside it; type-parameter names are likewise not part of signature identity (arity is). Semantic normalization — commutativity, constant folding, SMT-checked implication — was declined for the verdict itself: it would make the classification depend on prover strength, so two conforming tools could classify one delta differently, which for a CI gate is the worst available property. (Implication checking has a natural home as a future *advisory* layer, never as the verdict.) Redacting non-public state from carried clause text was also declined: a redacted record cannot be agreement-checked or diffed, which forfeits the staleness backstop exactly where stale consumption is least visible; the disclosure has the definition-site precedent and the same recompile-the-world cost profile.

**The recorded tier is demand-derived.** Spec §22.16 lets an implementation opportunistically discharge unqualified clauses and elide their checks, as-if. If the interface recorded those discharges, the recorded tier would be a function of the member's **body** — a body edit could flip proven→checked with no declaration change, silently invalidating the interface bytes (defeating early-cutoff builds keyed on interface identity) and, worse, silently invalidating any downstream proof that consumed the tier, with nothing in any declaration to point at. Deriving the recorded tier from the declaration alone — the `static` qualifier, plus §22.16's constant-fold floor, whose fold reads only the clause text and the `const` values it names — makes the tier a declaration fact: stable under body edits, guaranteed by compilation (a demanded proof that fails is a compile error), and therefore safe for downstream consumption. The recorded tier is simply the clause's §22.16 tier — one term, one value; what is never recorded is the per-site as-if elision of a checked clause, the only discharge that is not a declaration fact. The matching consumption rule in §2.8.2 is the same decision seen from the consumer: a proof no interface promises is not consumable.

**Identity excludes contracts; the verdict is layered.** Folding contract records into §2.8.3's type-identity key would make a clause edit mint a "new" type — every `is` test, `catch` clause, and pattern over it would bifurcate for values sharing one runtime representation — and would replace the *useful* answer to a contract mismatch (the staleness error, naming the stale artifact and the fix) with an unrelated-types error naming nothing. Identity is runtime oneness; contracts are obligations revised across revisions of one module while the type stays the same type. And a tier demotion gets a per-level verdict (spec §2.8.6) because both flat answers are wrong: flat-breaking cries wolf at every Core-level consumer (nothing they can consume changed — a tool that over-alarms teaches itself to be ignored), while flat-preserving mislabels a real break at the proof level. "Breaking where callers consumed the proof" is undecidable for a tool that cannot see callers; *level-gating* is its decidable refinement, and it keeps the ratchet culture healthy — promotion is everywhere-preserving, demotion is an honest, level-scoped event.

<a id="sec-generics"></a>
## 10. Generics

Two extreme implementations exist. Erasure (Java) is fast to compile but produces poor codegen and disallows reflection on type parameters. Monomorphization (C++ templates, Rust) produces excellent codegen but slow compile times and binary bloat.

Bezel's intended implementation specializes for value-type substitutions (where boxing would hurt) and shares for reference-type substitutions (where uniform layout is achievable). This gives most of the codegen benefit of monomorphization where it matters, and most of the binary-size benefit of erasure where it doesn't.

`typeof(T)` and `value.GetType()` work because the runtime carries enough type information to resolve them, regardless of whether a particular generic was specialized or shared.

(v0.184) Type-argument inference (§14.5) follows the same temperament as the dispatch strategy above — the predictable subset, stated fully. Bindings must agree exactly: the compiler computes no common supertype (`Pick(1, 2L)` is an error, not `long`), the §27.3/§20 no-LUB posture applied to inference, so a call's meaning never shifts because a distant hierarchy edit changed a join. The call's target type participates only as a *completion* for parameters the arguments cannot see (`var a: Array<int> := Util.Empty();`) — unification against one declared type, no suprema, error when absent — a deliberate divergence from C# (which refuses return-target inference) in favor of the factory idiom the reference implementation has always supported. Explicit lists are all-or-nothing, constraints are checked after inference rather than feeding it (liftable), and an otherwise-tied non-generic overload beats a generic one — ranked *after* the defaulted-arity tie-break, so adding an optional-parameter overload still never re-routes an existing call (v0.181's guarantee, kept where C#'s internal order would break it). Each declined power — bound-set fixpoints, best-common-type, constraint-driven inference, partial lists — is liftable later without rejecting a program this rule set accepts.

(v0.196, #1803) The ownership marker meets this dispatch strategy at one seam: what does `owned` mean on a parameter or return slot whose declared type is a bare `T`, when one instantiation substitutes a class and the next substitutes `int`? Through v0.194 the revisions had backed into an impasse from both sides — the marker was checked per instantiation and rejected at plain value substitutions, while the factory warning of [§5.7](#sec-factory-method-ownership)'s v0.194 rule *recommended* the `owned T` spelling to every mixed-domain producer — so a generic that produces fresh values over a domain admitting both kinds (`Create<T>(): T where T: new()`; the arithmetic behind [§11.8](Bezel_Language_Spec.md#sec-static-interface-members)'s `Sum<T>`) had no legal spelling of production at all. The v0.196 resolution is per-instantiation **erasure**: at class and interface substitutions the marker means transfer, exactly as on a concrete type; at value and runtime-managed substitutions the substitution erases it — the substituted signature *is* the unmarked one, down to function-type identity (`(owned T) -> ()` at `T = int` is `(int) -> ()`); a move-only value substitution instead keeps the marker admitted-but-redundant, as on the concrete type (spec [§28.1](Bezel_Language_Spec.md#sec-where-the-owned-modifier-can-appear)). This is the same temperament as the specialize-or-share strategy above: the ownership layer is already vacuous at value substitutions everywhere else in the language, and erasure states that vacuity in the signature algebra rather than as a rejection — which is also why erasure beat an inert-but-present marker of identical semantics: erased signatures compose mechanically with everything keyed on substituted forms, so conformance matching needs no waiver clause and type identity cannot manufacture two `int`-function types differing by a meaningless marker.

Two alternatives were declined. *Restricting the domain* — confining the numeric static-interface surface to value and runtime-managed conformers — falsifies §11.8's own canonical example (`class Meters: INumber<Meters>`), guarantees an unwind the day the first genuinely heap-backed conformer arrives (`BigInteger` is the recorded future occupant), and repairs only the stdlib's seam while leaving every user mixed-domain generic holding the same unactionable warning. *A new keyword* — a fresh-production marker distinct from `owned` — would duplicate `owned`'s class-substitution semantics exactly, differ only in value-substitution admissibility, and fork every marker-keyed rule in the spec for the privilege; erasure extracts the same admissibility from the marker the language already has. (This is not a retreat from [§5.11](#sec-owning-collections)'s abandonment of `<owned T>`: that mechanism made ownership a property of *type arguments* and drowned in substitution rules; erasure touches only signature slots, where the marker already lived — and the one slot that commits a type's *shape*, the generic `owned` field, deliberately stays rejected.) The recorded cost is honest: class-substituted arithmetic mints a fresh value on every operation — in an accumulator loop, one mint and one disposal per iteration — inherent to value-semantics arithmetic without in-place operators, deterministic, and a performance note rather than a soundness one.

<a id="sec-pattern-matching"></a>
## 11. Pattern matching

`case` is the multi-way conditional. Most of its design follows ML/Scala/F# precedent. Two Bezel-specific points:

<a id="sec-the-scrutinee-less-form"></a>
### 11.1 The `when` form (scrutinee-less condition dispatch)

A common need is "test totally different conditions." Forcing those into a scrutinee-having `case` would require gymnastics. Bezel provides `when` — a scrutinee-less sibling of `case` whose every arm is a full boolean test:

```bezel
var grade := (when
  score >= 90 => "A",
  score >= 80 => "B",
  score >= 70 => "C",
  _ => "F");
```

This subsumes most `if-else-if` chains.

Through v0.143 this was spelled `case` with the scrutinee omitted — the same keyword carried two readings, and the parser told them apart by source layout (whether the first arm began on the line after `case`, or whether an `or`/`and`/`=` appeared before the first `=>`). That made a `case`'s meaning depend on where line breaks fell, and it left a real ambiguity unresolved: a leading-open range pattern (`case x ..<0 => …`, §19.3) could not be distinguished from a `scrutinee..hi` range, so the spec listed `..<0` as a legal pattern that the parser had to reject. v0.144 (#744) gives condition dispatch its own keyword. `case` now *always* carries a scrutinee and `when` *never* does, so neither relies on layout; and because `case` is unconditionally scrutinee-bearing, its scrutinee can be parsed above the range precedence level, which makes the leading-open range pattern unambiguous and finally legal. The keyword `when` was already reserved (it introduces a `case`/`catch` arm guard); the construct use and the guard use never collide, because the construct `when` stands at the head of an expression or statement while the guard `when` follows a pattern inside an arm.

<a id="sec-naked-binding-inside-positional-patterns"></a>
### 11.2 Naked binding inside positional patterns

Inside `Point(x, y)`, `x` and `y` are bindings, not type tests. The explicit `Point(var x, var y)` is also accepted. Outside positional destructuring (at the top level of a pattern), an identifier is a type test, so a binding requires the `var` form.

The naked-identifier shorthand is allowed only where positional bindings are unambiguous, which is the common case and the natural reading.

<a id="sec-catch-is-case-for-exceptions"></a>
### 11.3 `catch` is `case` for exceptions

Bezel's `catch` is a multi-way pattern dispatcher: it takes a thrown exception and selects a handler based on type, optionally with a guard, optionally binding the value to a name. That is exactly what `case` does for ordinary values. v0.63 makes the syntax reflect this — `catch` arms now mirror `case` arms in every detail that matters.

The shape:

```bezel
try
  DoWork();
catch
  var ex: TimeoutException => RetryWithBackoff(ex),
  var ex: IOException | NetworkException => Retry(ex),
  InvalidOperationException => RecordInvalidState(),
  var ex: Exception => throw                 // re-raise unrecognized
end;
```

Arms are comma-separated. Bindings use `var` exactly as in `case`. Guards use `when` exactly as in `case`. Multi-type alternatives use `|` exactly as in `case` alternatives (v0.167, §3.8). Arm bodies are expressions or `do ... end` blocks, exactly as in `case`.

The previous syntax — repeated `catch ... then ... end` clauses — was inherited from C# without examination. C# inherited it from Java, which inherited it from C++. Each step preserved the surrounding shape because changing it would have broken existing code; Bezel has no such constraint and can pick the form that fits the rest of its design.

The same logic applied to C#'s `switch` statement and Bezel's `case`: C# has the heavy `case Type: ... break;` shape from C, while Bezel's `case` is arm-shaped from the start. The argument was structural — pattern dispatch reads more clearly as arms than as a sequence of labeled clauses. The argument applies to exception handlers too; v0.63 finally acts on it.

<a id="sec-why-the-change-was-deferred"></a>
#### Why the change was deferred

v0.62 explicitly deferred this change to give it dedicated attention. Three concerns held it back, all of which had answers but each of which deserved being thought through.

The first was the `=>` token's reading. In `case` expressions, `=> body` reads as "produces this value." In `catch`, the body is statement-position; nothing is produced. Resolved by noting that statement-position `case` already establishes that `=>` means "body for this match" without producing a value — the `case` and `catch` arms are both statement-position constructs in this respect.

The second was exhaustiveness. `case` warns when it can't prove exhaustiveness. `catch` should not — a `try` block usually catches a few specific exceptions and lets others propagate. Resolved by noting that exhaustiveness is a `case`-specific behavior, not a property of arm-shaped syntax. `catch` borrows the syntax without inheriting the exhaustiveness rule, just as statement-position `case` borrows the syntax without inheriting the value-producing rule.

The third was the cost on the dominant case. Most `catch` clauses today catch a single exception type and run a few statements. The new shape requires `do ... end` around any multi-statement body, where the old syntax accepted a bare statement sequence. This is real overhead for the most common form. The tradeoff: three extra tokens (`do`, `end`, comma) on the common case, in exchange for structural consistency with `case` and visibly cleaner multi-handler code. The empirical analysis was a near-tie on density; the structural argument tipped the decision.

<a id="sec-why-bindings-use-var"></a>
#### Why bindings use `var`

`for var i in coll`, `case ... var n: int => ...`, `out var name`. Every site in Bezel where a name is being introduced as a fresh local binding uses `var`. Catch bindings are no different — they introduce a name for the caught exception. Marking them `var` is consistency with the rest of the language, not new ceremony.

The cost is three letters per binding-form arm. The benefit is that a reader scanning code sees `var` and knows "binding being introduced," with no exception case to remember.

<a id="sec-multi-type-alternatives"></a>
#### Multi-type alternatives

The old syntax forced each exception type into its own `catch` clause. To handle two exception types identically, programmers either duplicated the body or used the `when ex is A or ex is B` workaround (documented in v0.62 [§31.2.1](Bezel_Language_Spec.md#sec-arm-patterns)). The new syntax expresses multi-type catches directly:

```bezel
catch
  var ex: IOException | TimeoutException => Retry()
end;
```

This matches Java's `catch (A | B)` and Python's `except (A, B):` in expressive power; the `|` spelling matches both Java's `catch (A | B)` and Bezel's own `case` alternatives (v0.167, §3.8). Inside the arm body, `ex` has the static type of the nearest common base — usually `Exception`. For type-specific handling within a multi-type arm, use a nested `case ex` or `is` test, but the common case (treating multiple types uniformly) doesn't need that.

<a id="sec-bare-throw-as-an-expression"></a>
#### Bare `throw` as an expression

The transition to arm-form `catch` surfaced an asymmetry in v0.62: `throw expr` was an expression (with bottom type, valid in any expression position), but bare `throw;` was statement-only. In the old `catch ... then statements end` form, this didn't matter — both fit naturally in a statement sequence. In the new arm form, where bodies are `=> expression` or `=> do statements end`, the asymmetry would have forced bare re-raises into the heavier `do ... end` form even when the re-raise was the entire body:

```bezel
// Without the change:
catch
  var ex: TransientException => Retry(),
  var ex: Exception => do throw; end       // do/end just for one statement
end;
```

v0.63 resolves this by promoting bare `throw` to an expression form too. The operand becomes optional: `throw expr` raises the supplied exception, `throw` (no operand) re-raises the current exception. Both have bottom type. The bare form is restricted to catch arm bodies — the same restriction as the statement form `throw;`. The natural arm shape becomes:

```bezel
catch
  var ex: TransientException => Retry(),
  var ex: Exception => throw
end;
```

The statement form `throw;` continues to work and means the same thing as the expression form followed by `;`. Inside `do ... end` arm bodies that perform multiple steps before re-raising, the statement form is still natural:

```bezel
catch
  var ex: SqlException => do
    metric.RecordSqlError(ex);
    throw;                                  // statement form, in a sequence
  end
end;
```

Both forms coexist; the choice between them is whether the re-raise is the whole arm body (use the expression form) or one step of several (use the statement form). This is the same expression-vs-statement choice that programmers already make for method calls, `case` arms, and other expressions that can also stand alone as statements.

The change is purely additive — every program that compiled in v0.62 continues to compile in v0.63 — but it materially improves the arm-form's ergonomics. Without it, the most common idiom in catch arms that re-raise (handle some types specifically, re-raise everything else) would have been heavier than the form it replaced. With it, the idiom reads cleanly:

```bezel
catch
  var ex: TransientException => Retry(),
  Exception => throw
end;
```

<a id="sec-what-catch-and-case-still-dont-share"></a>
#### What `catch` and `case` still don't share

The unification is structural, not total. Exception dispatch and value dispatch differ in two ways the syntax doesn't try to hide.

The first is the source of the value being matched. `case` matches an explicit scrutinee (its sibling `when` evaluates boolean conditions with no scrutinee). `catch` matches the implicit "currently-thrown exception" — there is no scrutinee to name, and the arms can only test types. A non-type `catch` arm pattern (a literal, a range, a record-destructuring) makes no sense and is a syntax error.

The second is the behavior on no match. `case` in expression position raises `MatchFailureException` on no match; `case` in statement position falls through silently. `catch` does neither — unmatched exceptions propagate to the enclosing handler. This is the right behavior for exception dispatch, and it is documented as a third position in [§19.6](Bezel_Language_Spec.md#sec-exhaustiveness) (alongside expression-position and statement-position `case`).

These differences aren't gaps; they're the parts of exception handling that don't reduce to value pattern matching. The syntax unifies the parts that are the same and leaves the parts that differ to the semantics.

<a id="sec-async"></a>
## 12. Async

<a id="sec-pattern-a-vs-pattern-b-is-type-directed"></a>
### 12.1 Pattern A vs Pattern B is type-directed

The interaction between async and ownership is the hardest design problem in the language. A class-typed task result must end up somewhere with defined disposal — but that somewhere is sometimes "the task itself, with multiple readers borrowing through it" (a fan-out cache, a future shared between subscribers) and sometimes "a fresh single owner" (a connection from `ConnectAsync`, a token from `AcquireAsync`).

The producer's return type carries the choice:

- `Task<T>` for class T means fan-out. Every awaiter borrows; the task must occupy an owning location — `using var` is the canonical form; plain owned locals (v0.184), owned parameters, owned fields of `this`, owning-collection slots, admitted static task fields (v0.184), and (v0.182) an unbound temporary whose borrowed result stays within one full expression also qualify (spec [§30.5](Bezel_Language_Spec.md#sec-result-lifetime-and-task-disposal)).
- `OwningTask<T>` for class T means single-consumer. One awaiter takes ownership; the task is consumed by `using var x := await t;`. A second await raises `InvalidOperationException`.

The rule reduces to "whatever the type says." Producers commit in their signature; consumers' obligations follow from that signature. There is no syntactic peek at the await context.

The motivating case is `Semaphore.AcquireAsync(): OwningTask<SemaphoreToken>` — an operation whose entire purpose is to produce a fresh, single-consumer token. The consumer writes the canonical shape:

```bezel
using var token := await sem.AcquireAsync();
DoCriticalWork();
```

Producers who want both shapes declare two methods with distinct names — and the second is typically one line: a Pattern B await is an owned expression, so an async façade's `return await CoreOwnedAsync(…);` republishes the owned result through a Pattern A task's owned slot (the adapter shape worked in [§12.2](#sec-choosing-between-taskt-and-taskowned-t)).

<a id="sec-choosing-between-taskt-and-taskowned-t"></a>
### 12.2 Choosing between `Task<T>` and `OwningTask<T>`

*(Spelling note: revisions v0.78–v0.96 wrote Pattern B as `Task<owned T>`; v0.97 replaced the `<owned T>` generic-argument mechanism with the named `Owned*` types — see [§5.11](#sec-owning-collections) and spec §14.4. §12.1–§12.2 were originally written in the old spelling and are stated here in the current one; the semantics are unchanged.)*

The choice between Pattern A and Pattern B is the producer's — it goes in the method signature and determines what every caller must do. The decision tree below is from the producer's perspective.

**Step 1: Is the result type a value type, `string`, or runtime-managed type?**

If yes, neither pattern applies. Return `Task<T>` and stop here. Value types are copied out; `string` and function values are runtime-managed. No ownership crosses the await boundary.

```bezel
public async method CountAsync(): Task<int>          // value type — no pattern
public async method FetchNameAsync(): Task<string>   // string — no pattern
```

**Step 2: The result is a class type. Will more than one consumer legitimately read the *same result instance*?**

This is the fan-out question, and it is architectural, not incidental: a config cache shared by every caller (spec [§22.13](Bezel_Language_Spec.md#sec-static-initialization-order) pattern (b)'s static task caches), a lookup result several subscribers await, a task stored once and awaited from multiple places (spec §30.4). Fan-out is announced in a design — it is rarely discovered late.

If yes → **Pattern A: `Task<T>`** — and say why at the declaration:

```bezel
/// Pattern A (fan-out): one fetch, every caller borrows the same Config.
public async method FetchConfigAsync(): Task<Config>
```

The same answer covers **chained republication** — an async body that re-exposes a longer-lived owner's result by chaining (`return await repo.LoadAsync(id);` — the source task's ownership transfers into the outer task, spec [§30.5](Bezel_Language_Spec.md#sec-result-lifetime-and-task-disposal)'s chained slots) or that shares a fresh value through the task's owned slot. Not "the task borrowing from the repository": a task cannot hold a borrow it did not produce — §30.5/§28.3's return rules forbid returning a bare borrow through a task (the original wording here predated the v0.67 owns-result ruling and was corrected in the 2026-07 review, #1332). Callers borrow *through the task*, whose teardown is the defined owner at every link.

**Step 3: Otherwise — the result is a fresh, single-consumer class value → Pattern B: `OwningTask<T>`.**

This is the default, and it covers more than classic resource acquisition. Connections, lock tokens, and file handles qualify, but so does ordinary fresh *data* the caller will hold: a parsed document, a materialized array, a response object. The consumer writes the form every caller writes unprompted:

```bezel
using var conn := await ConnectAsync(url);    // owned; disposed at scope end
var doc := await ParseAsync(input);           // owned local; affine discharge rules apply
```

**Summary**

| Question | Answer | Pattern | Return type |
|---|---|---|---|
| Result is value type / string / runtime-managed? | Yes | Neither | `Task<T>` |
| Several consumers read the same result instance (fan-out), or the body republishes a longer-lived owner's result (chaining)? | Yes | A — say why at the declaration | `Task<T>` |
| Fresh, single-consumer class result — including plain data the caller will hold? | Yes | **B (the default)** | `OwningTask<T>` |
| Still in doubt? | — | **B** | `OwningTask<T>` |

**When in doubt, choose Pattern B.** *(v0.204 — this reverses the guidance recorded here through v0.203; the changelog v0.204 entry carries the evidence for the reversal.)* Four reasons, each a recorded fact of the current model:

1. *The failure mode is caught.* Under the affine model ([§5.23](#sec-the-affine-model), v0.150), an owned result the caller never discharges is auto-dropped at scope end with the must-use warning — forgetting to dispose is not a leak, it is a diagnostic. The old argument for A-as-conservative ("no one can accidentally leak") was grounded in the pre-affine model; it is now equally true of B.
2. *A does not reduce the caller's obligations.* Since v0.190 ([§12.10](#sec-calls-mint-storage-lends)) the caller owns the *task* in either pattern. A moves the discharge obligation from the value the caller wants onto the wrapper around it; B puts it on the value itself and lets the await discharge the wrapper.
3. *The consumer form is the natural one.* B's canonical call site is the one-line `using var x := await …;` A's is the two-line bound-task form, and the one-line `var` bind of a Pattern A await is a compile error (spec [§30.5](Bezel_Language_Spec.md#sec-result-lifetime-and-task-disposal)).
4. *B is recoverable; the recovery is one line.* A producer who chose B and later discovers a fan-out need does not narrow the existing signature (that would break owners); it publishes a sibling ([§12.1](#sec-pattern-a-vs-pattern-b-is-type-directed)'s "two methods with distinct names"), and the adapter is the shape §30.5 itself anticipates: a Pattern B await is an owned expression, and a Pattern A async body's `return` of an owned expression fills the task's owned slot.

```bezel
/// Pattern A façade over the Pattern B core, for subscribers.
public async method FetchSharedAsync(url: string): Task<Config>
  return await FetchOwnedAsync(url);   // B result (owned) fills the A task's owned slot
end FetchSharedAsync;
```

The reversibility asymmetry the old guidance rested on is real and stays recorded: **A→B remains the mechanical-migration direction** (widening `Task<T>` to `OwningTask<T>` breaks callers loudly and compilably — one-line binds keep compiling as owned binds; non-owned-consuming awaits and multi-await sites are rejected with the §30.5 diagnostics, and the fixes are local), and **B→A remains breaking** (callers wrote `using var x := await t;` and owned the result; under A that same line is rejected). What the flip re-weighs is which default you *start* from: the reversibility argument buys an option — start at A, widen to B once ownership need is proven — that the recorded surface has never needed (no stdlib API started at A and widened; every recorded doubt-case went straight to B), and it pays for that option with the two-line consumer tax on every call site in the meantime, while the reverse risk has the one-line sibling recovery above, which does not touch the existing signature at all. Optimizing the everyday path over an unexercised option is the trade; it is made with the evidence attached, so it can be revisited if the evidence ever inverts.

**The question that settles it** is no longer "would forgetting to dispose leak?" (the affine model answers that for both patterns) but: ***"can a second consumer legitimately need this same result instance?"*** If yes, Pattern A — the task is the shared owner. If no — or if you are unsure — Pattern B: hand the caller the value, and let the ownership machinery do what it exists to do.

<a id="sec-no-configureawait"></a>
### 12.3 No `ConfigureAwait`

C#'s `ConfigureAwait(false)` exists because the default is to capture the synchronization context, and library code needs to opt out. Bezel's runtime has no synchronization contexts in this version, so no opt-out is needed. If UI-thread affinity is added later, this will need revisiting.

<a id="sec-cooperative-cancellation"></a>
### 12.4 Cooperative cancellation

Forcible cancellation (Thread.Abort) is unsafe — it can interrupt code holding a lock, corrupt invariants, or skip cleanup. Bezel uses cooperative cancellation: a `CancellationToken` is passed in and the operation checks it at safe points. This is C#'s model (and Go's, via `context`); Rust async reaches the same cooperative end differently — a future is cancelled by dropping it, which takes effect at a suspension point.

<a id="sec-execution-domains"></a>
### 12.5 Execution domains: why the async model is serial per domain

Through v0.130 the spec said async continuations "may resume on any thread-pool thread" and that shared mutable state "requires explicit synchronization," while the rationale (§5.1) accepted that programmers can write data races. Stated together, those two positions made the ownership chapter unsound in any program that actually exercised the stated freedom: the borrow checker's lifetime reasoning assumes nothing else runs between two points of a continuation with no suspension between them, yet the runtime model permitted another continuation — on another thread — to dispose a borrow's source mid-use. The language was protecting against the *smaller* hazard while permitting the larger one: §6.1 refuses to narrow nullable fields because another thread could write null between check and use, but a concurrent thread was permitted to *dispose* the object a borrow points into. v0.131 resolves the contradiction in favor of the ownership model: a domain is a unit of serial, run-to-completion execution, and every program in this revision is a single-domain program. The wording change costs existing programs nothing — no construct could observe genuine continuation parallelism portably, since any program doing so had data races whose behavior was already undefined — and it converts the §28 soundness assumptions from accidents of the current implementation into normative guarantees.

Three alternatives were considered and **declined**. *Send/Sync-style thread-safety typing* (Rust's approach) statically tracks which types may cross threads; it is the right tool for a language committed to shared-memory parallelism, but it infects every generic signature, roughly doubles the constraint vocabulary, and buys safety for a parallelism model Bezel does not actually offer — the cost lands on every user, the benefit on few. *Documenting the status quo* (keep "any thread, synchronize it yourself") was declined because it leaves the flagship feature unsound and outsources the hardest correctness problem to convention — the precise failure C++ shows daily. *Locks as discipline* (rely on `Mutex` use) was declined because nothing checks it; a forgotten lock is exactly as silent as the race it permits. The serial-domain model, by contrast, requires no new constructs, no new annotations, and no migration.

The decided direction for *parallelism* — multiple domains communicating by ownership transfer over channels, with sendability derived from existing type properties (owned transfer for classes, the §9.7 borrow-bearing computation for value types) — is recorded in the project tracker (#600) and deferred to a later revision. The one capability genuinely given up in the interim is CPU-bound parallelism inside one process; I/O-bound concurrency, the dominant async workload, is interleaving at suspension points and is unaffected by serialization of continuations. `Mutex`, `Semaphore`, and `Atomic<T>` (§30.12) are retained: foreign threads can still enter through the FFI, and the types are forward-compatible with multi-domain programs. *(v0.133: the deferred direction was delivered — language spec [§30.14](Bezel_Language_Spec.md#sec-multiple-domains)–[§30.15](Bezel_Language_Spec.md#sec-channels); the reasoning is §12.6 below.)*

<a id="sec-sendability-spawning-channels"></a>
### 12.6 Sendability, spawning, and channels

v0.133 delivers the parallelism half of the domain model: `Domain.Spawn` creates domains, `Channel<T>` moves data between them, and the **sendable** derived type property ([§3.6](Bezel_Language_Spec.md#sec-derived-type-properties) instance, defined in [§30.14](Bezel_Language_Spec.md#sec-sendable-types)) is the entire safety story. The design's one invariant — *no mutable state is reachable from two domains* — is what makes the v0.131 single-domain guarantees survive parallelism unchanged: every crossing value is moved (the origin domain provably loses it, by the same machinery as `move` and owned parameters) or immutable (`string`, value copies), and the channel core is the single compiler-known synchronized exception. Data-race freedom is purchased with the ownership system the language already had, not with a new type system. The decisions, and what was declined:

**Sendable classes must be `sealed` (or `sealed abstract` over a fully-sendable closed hierarchy).** The subtyping hole forced this: sendability is checked on static types, but an owned field typed at a sendable open class could hold, at runtime, a subclass instance carrying a back-reference into the origin domain — a data race smuggled past the static check. Three closures of the hole were considered. *Sealing* (chosen): zero runtime cost, compile-time diagnosis, statically airtight — at the price of excluding open classes from crossing domains. *A runtime send-check* (walk the transferred ownership tree at the send site, verifying each concrete class is transfer-closed): sound and more permissive, **declined for now** because it hides a per-send cost proportional to the transferred graph and converts a compile-time error into a runtime one; it remains the natural widening if sealing proves too narrow, and admitting it later is non-breaking. *Subclass-must-be-sendable inheritance rules* (deriving from a sendable class may not break self-containment): declined because it inverts the dependency — a base author's coincidental sendability would constrain every subclass author, violating the principle that derived type properties are observations, not obligations.

**Spawn entries are capture-free; data enters through explicit arguments.** The alternative — *move-capturing lambdas* (a closure form that takes ownership of its captures) — was declined: §28.9's capture-is-borrow rule is a single uniform story for every closure in the language, and carving out a second capture mode for one call site would ripple into closure typing, disposal of captured-but-never-run closures, and the §28.3 escape analysis. An explicit `owned arg` parameter is semantically identical, visibly costed at the call site, and required no new machinery. Multiple values aggregate into a sendable class, an `OwningArray`, or flow through a channel.

**Faults cross as `DomainFaultedException`, not as the original exception object.** Exception classes are not in general sendable (they are open classes, often carrying arbitrary state), and special-casing "exception objects may cross anyway" would reopen the invariant exactly where programs are least disciplined. Copying the message and stack-trace text (strings — sendable) preserves the diagnostic value; programs needing structured fault data return it as a sendable result or send it over a channel. Declined: a sendability requirement on throwable types (intrusive, retroactive) and runtime graph-checking of exception objects (the runtime-check costs above, on the unhappy path).

**Channels are MPSC, with the `Channel<T>` object as the receiving end and `NewSender()` minting sender endpoints.** Declined alternatives: *a `Create` returning two endpoints via `out owned` parameters* — more ceremony at every creation site and a third type, for no expressiveness gain over minting senders on demand; *multi-consumer channels* (receiver cloning) — cloning a receiving end is shared ownership of the consume capability, #603's territory — deferred at v0.133 pending `Shared<T>` (since delivered, v0.134): the remaining blocker is §28.13's unresolved domain-locality for the synchronized set (see the §18 entry); *bounded channels* — back-pressure wants an asynchronous `Send` that awaits capacity, a useful but separable design, deferred. The unbounded MPSC form covers the dominant fan-in/pipeline shapes and every deferral is an additive extension.

**`CancellationToken` does not cross domains.** Not by a new rule — it falls out: the token is a borrow-bearing record, hence not sendable. The cross-domain cancellation pattern (a dedicated channel carrying a cancel message) is documented rather than mechanized; a sendable cancellation primitive can be added later without disturbing anything in this revision.

<a id="sec-memory-model-edges"></a>
### 12.7 The memory model is five edges plus atomics

v0.184 wrote down the happens-before edges the runtime was always going to
need: mutex/semaphore release→next-acquire, channel accept→deliver,
spawn→entry and settlement→join, task settlement→awaiter (or blocking wait
at the process edge), and static publication — the store into an admitted
mutable static, and static-init completion, publishing the referent's memory
to observing domains. That fifth edge is the one §22.12's untorn-pointer
wording silently presumed, and the one that makes §22.13's cross-domain task
cache — and §30.5's borrowed-source chain through it — sound on weakly
ordered hardware rather than by x86 accident. Two object-specific guarantees
were already stated in place and are cross-referenced rather than restated:
CancellationToken's cross-thread flag visibility (§30.8) and Shared<T>'s
drop→last-drop-destruction ordering (§28.13). The striking property is how
little there is to say, and that is by construction, not omission: the
sendable discipline means no mutable state is ever reachable from two
domains, so a Bezel program cannot *write* the racy access whose semantics
memory models spend most of their pages on. The only deliberate hole is
memory shared with foreign threads outside the §30.12 primitives, which
belongs to the platform. Sequential consistency for atomics (v0.140) was
reconfirmed — no acquire/release variants until profiles demand them.

The same revision fixed the fate of a faulted channel send (the item is
disposed; a channel never retains what it did not accept — the TrySend
give-back RFC remains the path to a lossless failure mode), made the
TCS/OwningTCS source the owner of its task (every §30.11 example already
assumed it; the v0.75 changelog entry ([`Bezel_Changelog.md`](Bezel_Changelog.md)) records the alternative's typecheck failure;
disposal accounting splits by source kind so plain-TCS multi-await fan-out
survives untouched), and closed the one silent hole in structured
concurrency's quiescence guarantee: a TaskScope live across a yield in an
abandonable async iterator would have been physically reclaimed with
children running — now a compile error keyed on the same class-level fact as
§28.12's no-destructor warning, with the degraded-destructor fallback
recorded but not taken.

<a id="sec-locked-rwlocked"></a>
### 12.8 `Locked<T>`/`RwLocked<T>`: the lock owns the data (v0.186)

Real services share **structured state** — a session map, a cache, a registry — and before v0.186 the options were the
actor idiom (principled, heavy for a cache) or a `static readonly` collection "guarded" by a *separate* static
`Mutex`, which §22.12 rule 4 rightly warns about: the mutex is not tied to the data, and convention is what §30.14
exists to replace with checking. The shape adopted (from Rust's `Mutex<T>`/`RwLock<T>`, not .NET/Java standalone
monitors): the lock **owns** its interior, access is only through a scoped guard, and the guard's `Value` is a borrow
whose source is the guard — so the borrow-escape rules the language already has enforce the critical section, with no
new lifetime machinery. One type lifts any wholly-owned interior; the alternative — enumerating `ConcurrentDictionary`,
`ConcurrentSet`, … — grows the stdlib N types for N shapes and still leaves user classes unshareable.

The interior admission **reuses the sendable derived property** (§30.14) rather than defining a near-twin: a
`Locked<T>` is by design reachable from every domain (statics; `Shared<Locked<T>>`), so a borrow inside `T` would let
a guard-holder chase a reference into another domain's heap outside any lock. "T is a sendable class type" is exactly
the wholly-owned-tree condition, already implemented, already diagnosed.

**The read-guard ruling (recorded at graduation).** `RwLocked<T>`'s concurrent read guards across domains are the
type's point — and Bezel has no read-only borrow, so a "reader" mutating through `Value` would be a silent
cross-domain race. The graduation ruling splits the hazard the way v0.184 split the static-event rule: **stores are
checked where provenance is visible** — through a `ReadGuard`-sourced borrow, every assignment, `move`, and
`ref`/`out` pass is a compile error (expression-site, borrow-provenance-keyed, decidable, and **body-local**, because
borrow provenance does not cross call boundaries) — and the rest is a **recorded programmer obligation**: mutating
method calls through the read borrow (no const-method vocabulary exists, and one was declined — it is §12.5's
pervasive-constraint road), and callees reached with the read borrow as a plain argument (borrowed-parameter stores
are a core idiom no caller-side rule can reject). Declined: deferring `RwLocked` (cuts accepted scope and the
read-parallel complement of §12.9); pure residual trust (the flagship path would rest wholly on convention);
per-interior read facades (N types for N shapes again). The lift path, if evidence forces it, is a read-only
view/borrow form designed once with the frozen-view family (§12.9).

**Guard-kill and lock-kill strengthening (recorded at graduation).** §28.3's announced-kill carve-out is justified by
the killed object's own disposed-flag backstop; killing a guard sets no flag on the *interior* its surviving borrows
reference — while releasing the lock out from under them — so the carve-out's justification fails and the graduation
strengthens the freeze over guards (the §28.14 admission-freeze precedent): guard kills under live interior borrows,
and body-local lock kills under live guards, are compile errors. Lock destruction that no body-local rule can see —
the cross-domain last-`Shared`-handle drop while another domain holds a guard — takes the §28.2 posture, stated
normatively (checked-mode deterministic fault, unchecked UB) because the casualty here is user data mid-critical-
section, not a runtime lock word.

**Static membership, recast on v0.184's ground (recorded deviation from 0003's letter).** 0003 was written before
v0.184's store semantics for admitted mutable statics; its "join the rule-2 set" spelling would have made a *mutable*
static lock sound but overwrite-leaking — a displaced lock leaks its whole interior until exit, a payload-scaled cost
§22.12's `Task?`-cache acceptance does not cover — and racing first-use stores could transiently fork a registry into
two lock instances (last store wins): memory-sound, silently wrong. No use case demands lock-slot reassignment (the
interior's mutability lives behind the guards), so the locks join rule 4's new v0.186 **suppression list** — making
the `static owned readonly` registry, 0003's actual deliverable, warning-free and exit-disposed — and stay out of
form-(i). The same recast as `FrozenArray<T>`'s; liftable by separate ruling if a real mutable-slot use case appears.

Also recorded: the DI answer. A container's singleton table is a process-global mutable map — the same state made
less visible, resolved at runtime, reflection-shaped (and Bezel has no member-access reflection, §18). Wiring is
constructor parameters from a composition root; when state must genuinely be ambient-and-mutable, a synchronized
static `Locked<T>` is the visible, compiler-checked spelling of what a DI singleton hides. Guard-across-`await` is a
lint, not a ban (a "no-suspend type" concept would be disproportionate); lock ordering stays out of scope (the actor
idiom is the recommendation when ordering gets complicated).

<a id="sec-data-parallelism"></a>
### 12.9 Data parallelism: MOVE, FREEZE, and the recorded fork-join design (v0.186)

Bezel had *parallelism* (domains, §12.5–§12.6) but no *data parallelism*: "run this function over this array on all
cores" measured ~60 lines of ceremony (worker channels, a context class per worker, `FireAndForget` supervision
loss). A user-side library cannot close the gap — function values are never sendable, and the capture-free call-site
check is compiler-known machinery — so the combinators are compiler-known, in the position `Domain.Spawn` already
occupies. The v0.186 surface engages §12.5's Send/Sync decline without reopening it: no constraint vocabulary, no
declared properties — only boundary checks at call sites, the accepted §12.6 pattern.

Two strategies shipped: **MOVE** (`Parallel.Map`/`Reduce`/`ForEach` — chunk copies or ownership partition; zero new
checking rules, one table extension of the spawn-position category) and **FREEZE** (`FrozenArray<T>` — the `string`
immutable-crossing precedent generalized to bulk data; `Shared<FrozenArray<T>>` sendable via a recorded §28.13
membership ruling, the set's first deep-immutability member). **Freeze-time aliasing is closed conditionally, not
absolutely** (recorded at graduation): the consume-site freeze — with the v0.186 statement that span locals count as
live borrows of their carried sources — and §9.7's span-escape bullets close every body-local route to a surviving
writer; borrows held in fields, collection slots, or pending async frames are invisible to any body-local rule, so
the v0.180 domain clause is **extended** to consumption into domain-reachable constructions (`FrozenArray.From`, the
`Shared`/`Locked`/`RwLocked` constructors, admitted static stores) — the same recorded-obligation architecture as
every §30.14 residual, and the deliberate alternative to inventing a whole-program alias analysis for one
constructor. Seed semantics for `Reduce` are per-worker and stated plainly (a non-identity seed is incorporated once
per worker) — the alternative, threading one seed through, serializes the reduction; hiding the semantics is how
PLINQ earned its documentation warts. Declined, with reasons that stay binding: a **`parallel for` statement** (its
safety needs per-index write-disjointness dependence analysis the spec could neither state simply nor check totally;
a runtime check hides per-iteration cost, UB is not in the vocabulary, and a "trust me" independence annotation is
exactly what §3.6 rule 1 forbids — and the library-first posture already governs synchronization, §30.12);
**move-capturing spawn bodies** (§12.6's one-capture-mode decline stands; explicit `owned` arguments are semantically
identical and visibly costed); **user-generic parallel libraries** (the first step onto §12.5's declined road; the
compiler-known table can widen later without breaking); **a runtime send-check** (declined in §12.6, undisturbed).

**The recorded fork-join extension (designed, not shipped).** In-place divide-and-conquer — quicksort over one
buffer, `Parallel.Join(lambda() => QSort(lo), lambda() => QSort(hi))` — needs the two banned capabilities at once: shared reads
of frame data without copies, and disjoint mutable writes into one allocation. The design is recorded here so its
review cycle starts from settled rulings; **none of it is normative in v0.186** (no grammar, no §3.6 row, no
invariant change):

1. **Blocked-primary `Join`** (ruled): the parent *blocks*, which is both the soundness mechanism (a blocked
   continuation stalls its whole domain — §30.13 run-to-completion — so nothing domain-reachable mutates during the
   extent) and the liveness mechanism (the blocked parent lends its thread to the team; rayon's recruitment). The
   awaiting variant is recorded as weaker *and more novel*: it forfeits work-stealing and needs a frame-wide
   reachability admission with no existing shape to reuse (the TaskScope-sibling attack refutes the §28.14-reuse
   claim). The §30.3 dispensation it needs rests on an *enforced* pure-compute property: task/channel waits already
   fault inside sync closures (v0.162), and a **fork-extent runtime guard** makes every §30.12 blocking acquisition
   raise `InvalidOperationException` inside a fork extent — the guard's enumeration must cover the whole blocking
   family as of the landing revision, **including `Locked<T>`/`RwLocked<T>`** (§12.8), reachable through statics by
   name where no capture check sees them.
2. **A `concurrently-readable` derived type property** (§3.6 form, checked only at fork positions): sendable value
   types and `string`; `FrozenArray<T>` and `Shared<FrozenArray<T>>`; admitted read-only views whose source is
   admitted. Locks, channels, and the task family are deliberately excluded — capturing a lock the blocked parent
   holds is a deadlock vector, not a sharing vector (Bezel's Sync-analog is narrower than Rust's, on purpose).
3. **Fork-position closure admission** (`par` marker — a §28.14-family contextual modifier, compiler-known
   declarations only): captures remain §28.9 borrows (no second capture mode — §12.6's decline holds); fork-closure
   bodies are **write-restricted** (stores through captured borrows rejected; only captured lend-span writes and
   closure-local state); captured sources are frozen for the extent (§28.14's freeze, trivially enforced by
   quiescence in the blocked form).
4. **Disjoint span lending**: `SplitAt` witnesses with **provenance-linear** admission (per-binding linearity is
   vacuous for copyable records — the admission traces captures back to a disjointness witness, each witness feeding
   at most one closure) and **opaque lending by type** (ruled): a distinct lend-span family with no `Buffer`
   projection and `Slice`-only narrowing, so buffer recovery is closed by ordinary name resolution — a helper over
   `Span<T>` cannot receive one. The interprocedural body-rule alternative was declined: it requires a
   fork-reachability classification of functions, a whole-program analysis class with no precedent here. One
   inherited residual is named, not absorbed: §22.12 rule-4 warned statics are reachable from fork closures exactly
   as from any two domains today — sharpened at graduation: fork closures are lexically the *confining* domain's
   code, so a program honoring rule 4's one-domain confinement obligation would **newly** race if its own fork
   closures touch the static from team domains; the future landing must extend the confinement obligation (or the
   fork admission) to fork extents explicitly.
5. **The invariant amendment, ratified in principle** and pinned for the landing revision: §30.14's flagship sentence
   becomes location-granular — *"no mutable memory location is ever accessible from two running domains, except that
   a `Join` extent may lend provably disjoint slot ranges of one allocation to distinct fork closures, under the
   fork-admission rules"* — because object-granular reachability is the wrong predicate for the construct
   (its flagship case lends one buffer's disjoint ranges to two running domains). It is deliberately **not** applied
   in v0.186: nothing normative in this revision violates the current sentence, and flagship prose should never be
   weaker than the shipped language requires. A **memory-model clause** (fork-extent fork/join happens-before edges)
   lands with it.

The `.AsParallel()` endnote stays recorded: the §29.11 affine-query ruling removes PLINQ's two classic hazards
structurally (re-enumeration is already an error; consumption transfers the whole plan), but operator callbacks are
storing signatures and chunking needs an indexable source — high-cost machinery for wins the explicit combinators
already deliver. Evidence first.

<a id="sec-calls-mint-storage-lends"></a>
### 12.10 Task ownership at the call site: calls mint, storage lends (v0.190)

[§12.1](#sec-pattern-a-vs-pattern-b-is-type-directed) and §12.2 presume something the ownership chapter did not actually say until v0.190: that the caller of `FetchConfigAsync()` **owns** the returned task. The producers table classified a non-`owned` return from an instance method as a borrow of the receiver, with no exception for the `Task` family — so by the letter, every unmarked instance, interface, or function-value task call minted a state-machine frame that nobody owned, while §30's entire disposal story (`using var task := client.GetAsync(url);`, both decision trees above) required the opposite. Nor could any rule patch this by keying on `async`: it is an implementation-side modifier that no signature or interface exposes (spec [§28.12](Bezel_Language_Spec.md#sec-asynchronous-disposal)). v0.190 resolves the contradiction with a classification keyed on the construct rather than on a marker (spec [§28.3](Bezel_Language_Spec.md#sec-producers), #1786): a **call** whose declared — pre-substitution — return type is a `Task`-family type produces an owned task, with no marker and no factory warning, whatever the callee kind; a read of **storage** — a property, field, indexer, or local — remains a borrow of that storage. Calls mint, storage lends: a call is the moment a frame comes into being (or is forwarded by someone who owned it), and storage is the place a task someone else already owns is shared from.

The declined alternative was the marker: require `owned` on every fresh-task-returning signature. The blast radius alone was disqualifying — every async signature in every program, every task-returning function type, both decision trees above — but the deeper defect is what the *unmarked* spelling would then mean, because a marker whose omission compiles must leave the unmarked form meaning something. As a borrow it is a standing leak-by-omission trap, worst through interfaces, where a caller cannot see whether the implementation behind a signature is async; as a hard error it forces the marker onto every task signature — [§5.5](#sec-local-variable-ownership-is-inferred-not-annotated)'s "redundant noise" verdict, transplanted to the language's most common async surface. The declared return type already carries exactly the bit the marker would add; this is the announcement-by-declared-type doctrine the iterator convention had established, applied to the type family whose calls produce frames by construction. Also declined: post-substitution keying (`First<T>()` at `T = Task<int>` would mint a disposal obligation over a collection-owned element — the decline v0.194's bare-type-parameter ruling later reaffirmed, [§5.7](#sec-factory-method-ownership)), and extending calls-mint uniformly to all deferred-activation kinds — unsound for iterables, where the stored-collection view idiom (`method Items(): IEnumerable<Item> => return _items;`) is legitimate and common. The task/iterable asymmetry is principled, and is recorded here so the iterable analogue is not later "fixed" by copying this ruling blindly.

The rule is the §30.11 precedent made general. v0.184 had already decided, for one type, that a `TaskCompletionSource` owns its task and consumers reach it through the `.Task` **property** ([§12.7](#sec-memory-model-edges) above; spec [§30.11](Bezel_Language_Spec.md#sec-taskcompletionsourcet-and-ownedtaskcompletionsourcet)) — the source owns, storage lends. v0.190 draws that line everywhere, callee side included: an unmarked `Task`-family return type is itself container-ownership-transferring, so a non-`async` body must supply an owned task on every return path, and a *stored* task is re-exposed through a property, field, or collection slot — never through a non-`owned` method return. Costs, recorded: the stored-task *method* accessor became inexpressible (the storage-accessor shape belongs to properties — the same property-face resolution as the static idioms of §13.6); and the pre-existing `owned Task` markers on `Domain.Spawn` and the `Parallel` combinators became emphasis rather than contrast — recorded deliberately against the v0.186 note that the two spellings were "deliberate, not to be silently harmonized": this is the non-silent harmonization that note demanded.

<a id="sec-determinism-stated-hashes-assigned"></a>
### 12.11 Determinism is stated, and identity hashes are assigned (v0.204)

Spec §30.13's *Determinism* subsection adds no rule — every clause of it was already a consequence of serial-per-domain execution, the five memory-model edges, sendability, and the no-object-address invariant. It is stated anyway, for two reasons. First, as an audit obligation on the implementation: once "a domain's execution is a deterministic function of what its edges deliver" is normative, any within-domain nondeterminism given fixed edges — an uninitialized read, an unpinned iteration order, an address leak into an observable value — is a runtime *bug by definition*, not implementation latitude; the paragraph converts a diffuse design intention into a checkable property. Second, as the foundation record/replay tooling needs: a recorded execution is replayable exactly because everything a domain observes arrives through an enumerable set of runtime-mediated edges (proposal 0045 is the tooling design; the spec paragraph is what makes it *possible* rather than heroic). The exclusions are exactly two — elapsed real time, and foreign memory beyond declared writebacks — because those are the two places the runtime genuinely does not mediate.

Two supporting rulings landed with it. **Identity hashes are assigned, not derived** (spec §8.3): the .NET lazy-syncblock design with the entropy source replaced by a per-domain deterministic sequence. Without it the determinism statement is false for any program that hashes a class by identity — an address-derived hash is a per-run accident — and the address itself would leak into observable values, which §32.12's no-object-address invariant exists to prevent. Objects never hashed pay nothing; the storage is the runtime's per-object metadata word or a side table (implementation detail); programs are promised only within-run stability and address-independence, so no existing program's meaning changes. **`OwningDictionary<K, V>` iteration is deterministic-given-history, not order-pinned** (stdlib §4.9): pinning insertion order outright would force order metadata into the drain-and-rebuild representation whose economics §4.9 already chose; determinism given the operation-and-hash history is everything replay needs and is what the reference implementation already does. The borrowing containers (`Dictionary`, `Set`) were already insertion-order-pinned, so no frame-by-frame journaling of container iteration is ever needed.


<a id="sec-choosing-the-concurrency-shape"></a>
### 12.12 Choosing the concurrency shape: structured by default (v0.211)

The mechanisms are settled individually — `TaskScope` (stdlib §6.10), `Task.WhenAll`/`WhenAllOwned` (§6.4), `WhenAny`, `Task.FireAndForget`, bare task binds, and `Domain.Spawn` (§30.14) — but the map between them was reconstructible only from scattered passages. The doctrine, in one place:

**Structured is the default.** Spec §30.10 states the posture: concurrent fan-out reaches for the nursery — `await using var scope := new TaskScope();` — and the two discard idioms are the named escape hatches, not peers. The nursery's guarantee is lifetime-shaped: children cannot outlive the scope, and the scope's disposal is the join.

**The fault fork is the real chooser.** `WhenAll` *collects*: it awaits every task and re-raises the first non-success — it never cancels or abandons the laggards (§30.10's aggregation contract). `TaskScope` *supervises*: a child's fault cancels the siblings through the scope token, and `Join` surfaces the failure after quiescence. So: results-of-independent-work → `WhenAll` (all work is wanted regardless of failures); a unit of work whose parts stand or fall together → `TaskScope`. `WhenAny` is a selector, not a supervisor — the losers keep running and remain the caller's to settle. `FireAndForget` is the recorded abandon-with-supervision spelling for work whose result nobody will read (§17.13 routes the `Task` discard here precisely so abandonment is always a visible decision). `Domain.Spawn` is not a concurrency combinator at all — it is an isolation boundary (§12.5), chosen for state separation, with sendability doing the checking.

Why this is a rationale entry rather than new normative text: every sentence above restates a rule the spec already carries; what was missing was the adjacency. (The streaming as-completed combinator is `Task.WhenEach` — stdlib §6.7, graduated from proposal 0023 at v0.212: it *reports* completions in order without supervising or settling anything, the observer complement to `TaskScope`.)

<a id="sec-events"></a>
## 13. Events

<a id="sec-raise-instead-of-invoke"></a>
### 13.1 `Raise` instead of `?.Invoke`

The C# idiom `event?.Invoke(this, args)` carries two operators of boilerplate. The `?.` exists because an empty event is a null delegate. The `Invoke` exists because delegates need explicit invocation. Forgetting the `?.` raises `NullReferenceException` for an empty event.

Bezel uses `event.Raise(payload)` (sync) and `await event.RaiseAsync(payload)` (async). Three properties:

- **No null check.** Zero subscribers is just zero subscribers; `Raise` is a no-op. Whether the implementation backs the event with a null sentinel is invisible at the call site.
- **No `Invoke` indirection.** The verb `Raise` means "call all subscribed handlers." That replaces both `?.` and `Invoke`.
- **Symmetric with `Subscribe`.** The public face — the pattern's property — has type `IEvent<T>` (only `Subscribe`); the producer face — the private field — is `EventSource<T>` (both `Subscribe` and `Raise`). The asymmetry — outside callers can't `Raise`, inside callers can — is enforced by the static types of two declarations, not by a special access rule.

Direct invocation `event(args)` was considered. It's cleaner at the call site but conflicts with the asymmetric inside/outside types — "why is `event(args)` legal here but not there?" is harder to explain than "the type changes."

<a id="sec-payload-types-not-handler-types"></a>
### 13.2 Payload types, not handler types

v0.53 declared events with a handler function type: `event Clicked: (Button, ClickEventArgs) -> ()`. The generic parameter `TArgs` in `EventSource<TArgs>` was defined as "the handler function type." This created a type-system incoherence: `Subscribe(handler: TArgs)` was correct (handler *is* a function), but `Raise(args: TArgs)` would mean `Raise` takes a function, not the event's data. The call site worked around this with pseudo-tuple syntax that had no foundation in the type system.

v0.54 fixes this by making events name a **payload type**: `event Clicked: ClickedEvent`. The generic parameter `T` in `EventSource<T>` is the payload, and `Raise(payload: T)` is a well-typed generic method that means exactly what it says. The handler type `(T) -> ()` is derived mechanically from the payload type and the sync/async modifier.

Three options were considered:

1. **Compiler-synthesized `Raise`.** Keep the function-type declaration; the compiler generates a per-event `Raise` whose parameters mirror the handler's. This would be the first compiler-generated method not expressible in the generic type — a crack in the "no hidden magic" principle.
2. **Payload types (chosen).** Events name a payload record. `Raise(payload: T)` is a normal generic method. The handler type is derived.
3. **Tuple types.** Add language-level tuples to make the handler's parameter list a first-class type. Tuples are a large feature commitment for a single use case.

Option 2 wins because it requires no new language concepts, keeps `EventSource<T>` fully expressible as a generic class, and aligns with the existing recommendation (stdlib [§6.5](Bezel_Standard_Library.md#sec-events-ievent-eventsource), "Payload records") that event arguments be records. The cost — one record declaration per event — is modest and produces better-documented APIs than multi-parameter handlers.

The subscribe-side trade-off is that handlers take a single payload parameter instead of multiple: `lambda(e) => e.X` instead of `lambda(btn, args) => args.X`. This could be partially recovered by lambda-parameter destructuring (`lambda(ClickedEvent(_, x, y, _)) => ...`) in a future revision, but the single-parameter form is clear enough on its own.

<a id="sec-method-reference-subscriptions"></a>
### 13.3 Method-reference subscriptions

Once payload records are the convention, method-reference subscription becomes the natural idiom for handlers that have a name worth keeping:

```bezel
public method UpdateStatus(e: ClickedEvent)
  // ...
end UpdateStatus;

_clicked += UpdateStatus;           // method reference at the pattern's source field; no lambda wrapping needed
```

The method's signature `(ClickedEvent) -> ()` matches the handler type derived from the event's payload. The compiler resolves the `+=` form to `_clicked.Add(UpdateStatus)` via the desugaring described in spec [§17.2](Bezel_Language_Spec.md#sec-notes-on-operators). Lambdas remain available for ad-hoc handlers; named methods are preferred when the handler has a stable identity that supports later `-=` removal.

<a id="sec-events-on-interfaces"></a>
### 13.4 Events on interfaces

v0.61 prohibited event declarations in interfaces, deferring the feature pending design work on the interaction between interface-level events and the `IEvent<T>`/`EventSource<T>` type split. v0.62 lifts the restriction.

The resolution is straightforward given the type split that already existed. From outside the declaring class, every event has type `IEvent<T>` (sync) or `IAsyncEvent<T>` (async). That's exactly what an interface event member should expose: the public, subscribe-only surface of an event. The implementing class declares the event normally; its compiler-generated `EventSource<T>` backing satisfies the interface contract because `EventSource<T>` implements `IEvent<T>`. No new mechanism is required — the existing types compose to give interface events for free.

The motivating use cases are conventional: `INotifyPropertyChanged` and analogous observable contracts, UI component abstractions where multiple concrete types share an event-bearing interface, and plugin extension points where the host subscribes to events declared by the plugin contract. Without interface events, each of these patterns required either an abstract base class (which consumes the single-inheritance slot) or an awkward `GetEventX(): IEvent<X>` method that worked around the missing language feature. The cost of supporting the feature is one new grammar production (`IfaceEvent` in Appendix A.4) and a paragraph of semantics; the benefit is that observable contracts become idiomatic.

C# has supported interface events since C# 1.0 (2002); the precedent is well-established. The deferral in v0.61 was conservative; v0.62's resolution does not require any changes to the existing event system.

*(v0.187: interface events retired with the member kind — proposal 0035, §13.6 below. The contract shape is now the get-only `IEvent<T>` property, which removes precisely the awkwardness this section recorded in the `GetEventX(): IEvent<X>` workaround: no parens, declaratively read-only, and satisfied by the very property the pattern already declares. The use cases recorded here are served unchanged.)*

<a id="sec-handler-exception-policy-first-error-wins-not-aggregate"></a>
### 13.5 Handler exception policy: first error wins, not aggregate

When a synchronous event handler throws, subsequent handlers in the subscription list are not invoked, and the exception propagates out of `Raise` to the raiser. The same rule applies to async event handlers: if one handler's task faults or is cancelled, subsequent handlers are not invoked and the exception propagates from the awaited `RaiseAsync`. This is "first error wins": the publisher sees one exception and that's the end of the dispatch.

The alternative — running every handler regardless of failures and aggregating the exceptions — was considered. C# went this route for `Task.WhenAll` (which produces an `AggregateException`) and some event-like patterns. Bezel chose first-wins for three reasons.

The first is that aggregation introduces a special exception type that callers must handle differently. `AggregateException` in C# has a complex API (`Flatten`, `InnerExceptions`, `Handle`) and exists primarily because async-with-many-tasks produces multi-failure shapes that ordinary stack-walking exceptions cannot represent. Events are a different shape: a publisher fires once, multiple handlers respond, and the publisher usually does not care about all of them — it cares that *something* failed. Promoting "something failed" into a multi-exception object asks every event consumer to know about an aggregation type.

The second is that handlers that need to run independently can opt in trivially:

```bezel
button.Clicked += async lambda(e) => do
  try
    await ProcessAsync(e);
  catch
    var ex: Exception => Log(ex)        // swallow per-handler failures
  end;
end;
```

The handler catches its own exceptions, returns a successful task, and `Raise`/`RaiseAsync` continues to the next subscriber. Each handler decides whether its failure should poison the rest of the dispatch. This puts the policy where the failure semantics are known — in the handler, which knows whether its work is best-effort or critical — rather than in the publisher, which usually doesn't.

The third is that aggregation across handler boundaries can mask bugs. If a handler throws because it has a real defect (a null-deref, a state-machine violation), the publisher silently aggregating and continuing means the bug surfaces later, in a different code path, with the original stack trace already obscured by the aggregation wrapper. First-wins keeps the original exception visible at the point it was thrown.

The cost is real: a publisher that wants every handler to run regardless of failures must implement that policy itself, typically by catching inside each handler at subscribe time. That's the trade we're making — a small amount of subscriber-side ceremony for a simpler default and clearer failure semantics.

The published policy is normative (stdlib [§6.5](Bezel_Standard_Library.md#sec-events-ievent-eventsource), "Handler exceptions" — the normative home since the member kind's retirement, v0.187). Future revisions could add an opt-in aggregating raise method (e.g. `RaiseAggregated(payload: T)`) without breaking existing code, but the default would not change.

<a id="sec-retiring-the-event-member-kind"></a>
### 13.6 Retiring the `event` member kind (v0.187, proposal 0035)

Through v0.185, `public event Clicked: ClickedEvent;` was a member kind: a one-line declaration that generated a hidden `private owned EventSource<ClickedEvent>` backing field, with the language's only access-site-dependent member-type rule (former spec §24.3 — `IEvent<T>` outside the declaring class, `EventSource<T>` inside). v0.187 removes the member kind (proposal 0035, accepted 2026-07-12; #1550). An event is now the two-declaration pattern of stdlib §6.5 — `private owned readonly _clicked: EventSource<ClickedEvent> := new();` plus `public property Clicked: IEvent<ClickedEvent> => _clicked;` — and stdlib §6.5 is the normative home of event semantics. Subscriber-side call sites are unchanged.

**Why.** Everything observable about events was already library semantics on the stdlib §6.5 types; the member kind bought one saved line and one saved name, and paid with a carve-out family: two grammar productions (`EventDecl`, `IfaceEvent`), a placement rule (classes/interfaces only), the two-faced typing rule, spec §28.14 form 4's honorary-field clause for the generated backing member, spec §22.12 rule 5's member-kind keying (whose guarantee was unenforceable through an `IEvent<T>` alias — #1647), and its own modifier table. The two-line pattern is the floor for a public event under Bezel's own commitments — declaration-fixed member types, the type fence, no runtime type tests on the producer path — so no in-language shorthand could beat it by more than the one line.

**Alternatives declined** (0035 §5.1.2/§6): expansion sugar (option (a) — retains the member kind and a minted visible name to close a one-line gap) and its bare-name variant (rejected in advance); C3 field-type inference (a new inference form); C4 fused field+property declaration (a new declaration form); C5 primary-constructor capture (wrong lifetime story); C6 public source field (loses the fence); C7 a raiser/source split for instance events (two names, no gain); C8 a `Publisher` base class (consumes the single-inheritance slot); C9 rename-only; C10 an interface-typed field with downcast raise (a runtime type test on the producer path). Deleting the `+=`/`-=` desugaring was separately declined: it would close #1618 by deletion (record-receiver method-reference equality) but churn every producer-side subscription site; the desugaring survives, re-homed to spec §17.2 and keyed on the three source types, with its `readonly` interaction stated for the first time (the desugaring is recognized before `readonly`-assignability checking — previously unstatable, since events rejected `readonly` and the generated field had no name). #1618 stays open as a real bug.

**Statics (S1).** `static event` is replaced by the sealed pair `ISharedEvent<out T>`/`SharedEventSource<T>` — internally synchronized, capture-free at every subscribe position. The capture-freedom is a stdlib-stated entry in spec §28.14's capture-free register, keyed on the resolved callee, made alias-proof by two companion rules: the pair implements neither `IEvent<T>` (an upcast would launder capture admission through `IEvent<T>.Subscribe`'s capture-admitting `scoped` signature — the severed composition is a recorded cost, bridged by a channel relay, stdlib §6.5), and method-reference formation over any capture-free-register position is rejected (the formed plain function type would erase the admission; the bar covers `Domain.Spawn` too, closing the same latent formation hole there). This is the first enforceable statement of the v0.163/v0.180 rule-5 guarantee; #1647 closes by construction. User classes cannot be cross-domain publication points in v1 (a user `Subscribe` is retention-incapable under the call-bounded regime; the lift path is §28.14's deferred unbounded tier, #1427). S2 (regressing the guarantee) and S3 (silently synchronizing instance events — reversing v0.163's recorded instance-events-unsynchronized choice) were declined. The shared async twin is deferred until demand appears; until it ships a cross-domain async publication point is not spellable (`static async event`, grammatical through v0.185 and unused in every document, has no direct replacement — the migration note says so honestly; the channel bridge is the alternative).

**Small rules that land with the retirement.** (1) A bare read of a `static` `owned` field returned through a non-`owned` return is a borrow of process-lived static storage (spec §28.3/§28.6, v0.187) — the callee-side rule the static idiom's public property needed; previously only the caller-side producers-table row existed. (v0.196 narrows the admission to exactly that property face — #1804: the static-*method* arm v0.187 admitted alongside it never had a caller-side row, so a concrete static method call returning storage was factory-classified at every call site, pairing two owners over one obligation; the arm is retired, the pattern's property face plus the caller-side `T.P` row being the complete sound surface.) (2) Spec §2.3's always-available list gains all six event types (Q7, spelling (i)) — a recorded reversal of the first draft's "declinable knob" posture: the keyword's import exemption died with the keyword, and requiring `import System.Threading` to declare any event would fight the declaration-cleanliness the retirement exists to serve; relocating the types to `System` (the `Subscription`/v0.76 precedent) stays recorded as the equally-principled alternative. (3) `EventSource<T>`/`AsyncEventSource<T>` gain public parameterless constructors (#1646 tracks the compiler; sequenced first in the implementation roadmap — the pattern is the graduation's front door). (4) `event` moves from Appendix B.1 to B.3 as the language's one reserved-for-future identifier: pre-retirement code fails with a reserved-word diagnostic rather than parsing `event` as an identifier, and a one-line declaration form stays re-introducible without a breaking change (un-reserving is a separately declinable follow-up).

**Recorded costs and drops.** One extra line and one extra name per public event; producer sites read `_clicked` rather than `Clicked`; interface auto-satisfaction is gone (the implementer writes the property — see the §13.4 postscript above); a §28.14 form-4 narrowing for off-idiom discharges (the pattern's property is a getter hop, so an external capture-bearing subscription discharged neither by `using var` nor into an `owned` field of `this` is now rejected — correct-by-default, never unsound; the *transparent-getter* lift restoring form-4 parity for the idiom's property shape is recorded as liftable). Dropped without relocation, each recorded: former §24.1's placement rule (now just §9.7's owned-field rejection in records/enums); §24.1's and §24.7's modifier prose (each declaration's own grammar governs); §24.7's static-events-on-interfaces exclusion (dissolves — a static interface property is unspellable under §11.8, and a static method returning `ISharedEvent<T>` is an ordinary contract); the four-field `ClickedEvent` variant of former §24.2 (a duplicate declaration once the pattern example declares the three-field form). One wording correction rode along, recorded: former §24.5 called snapshot-raise "the same posture as" §29.12's loud-mutation discipline; stdlib §6.5 now states the true relation — both make mutation-during-traversal defined and loud, but the responses differ (snapshot vs fault), because a self-unsubscribing one-shot listener is a legitimate idiom while mid-iteration collection mutation is a bug.

<a id="sec-operators"></a>
## 14. Operators

<a id="sec-++-and-are-statements"></a>
### 14.1 `++` and `--` are statements

Statement-only, no expression form. `i++` vs `++i`, `arr[i++]`, sequence-point confusion, undefined behavior — none of those exist in Bezel because `++` produces no value. The cases where the old or new value is genuinely needed are clearer when written explicitly.

<a id="sec-mandatory-parentheses-on-mixed-precedence"></a>
### 14.2 Mandatory parentheses on mixed precedence

Mixing bitwise (`&`, `|`, `^`) with equality, relational, or logical operators in the same expression is a syntax error. `a & 1 = 0` doesn't compile; write `(a & 1) = 0`.

The rule costs nothing on programs that mean what they say and catches the most common precedence pitfalls inherited from C. Shift mixed with arithmetic is the same: `a << 2 + 1` is rejected; parenthesize.

<a id="sec-comparison-operators-must-be-defined-together"></a>
### 14.3 Comparison operators must be defined together

`<`, `<=`, `>`, `>=` together. `=` and `<>` together. Languages that derive `>=` from `not (a < b)` get the NaN cases wrong. Forcing each to be defined explicitly keeps the semantics explicit.

<a id="sec-not-is-not-user-overloadable"></a>
### 14.4 `not` is not user-overloadable

`not` is the boolean negation operator. It is not user-overloadable. v0.61 listed `not` among the user-overloadable operators ([§25.1](Bezel_Language_Spec.md#sec-overloadable-operators)) and contradicted the [§6.5](Bezel_Language_Spec.md#sec-bitwise-operations) statement that `not` is "valid only on `bool`." v0.62 resolves this by prohibiting `not` overloading entirely.

The reasoning: `not` reads as a boolean operation. A reader seeing `not x` expects `x` to be (or to behave like) a `bool`. Overloading `not` on arbitrary types would invite confusion — three-valued logic, set-complement semantics, "negate" as in "produce additive inverse" all have superficial appeal, but each interpretation departs from the boolean reading in ways that are easy to misread. Domain-specific inversion is better expressed by a named method (e.g. `.Negate()`, `.Invert()`, `.Complement()`), which makes intent explicit at every call site.

The bitwise complement operator `~` remains user-overloadable. Types that have a meaningful bit-pattern inversion or set-complement operation can overload `~`; types with logical-style negation should provide a named method.

<a id="sec-no-implicit-conversion-operators"></a>
### 14.5 No implicit conversion operators

Implicit conversions make overload resolution unpredictable, hide allocation costs, and let inappropriate values silently flow into APIs. Bezel has no `implicit` keyword; explicit conversion is the only user-defined conversion mechanism.

**Overload resolution tie-breaking (v0.128).** v0.127's §22.6 said overloads are distinguishable by number, type, and `ref`/`out` modifiers, but was silent on how to choose when two applicable overloads are each reachable through a different built-in implicit conversion (§5.1). §5.1 catalogs the implicit conversions; it did not say how they rank during overload resolution. v0.128 closes the gap conservatively: an exact match is preferred over any implicit conversion, but built-in implicit conversions are not ranked against one another, so a call that reaches two overloads only through (equally-ranked) conversions is ambiguous and is a compile error citing the candidates. The programmer disambiguates with an explicit cast.

We considered importing C#'s finer "better conversion target" ordering (narrower target preferred, so `int→long` would beat `int→float`). We declined it: §5.1 deliberately admits an implicit conversion only when no programmer-visible information is lost (or, for wide-integer-to-float, when an explicit cast would be unjustified noise), and it places every numeric widening in one undifferentiated row — including the precision-losing `int→float`. Ranking those conversions would be net-new semantics layered on top of §5.1, not a clarification of it. The conservative rule keeps faith with Bezel's "explicit over implicit" stance (the same principle that omits user-defined conversion operators, §25.4) and with the existing treatment of overloaded method references (§27.6), which already makes the absence of a unique winner a compile error citing the candidates. The cost is that a few calls that a C#-style rule would silently resolve are instead flagged for an explicit cast; that is the intended trade.

<a id="sec-compound-assignment-narrows-back-checked"></a>
### 14.6 Compound assignment narrows back, checked (v0.184)

`b += 10` on a `byte` is the one place every C-family language needs an exception to its no-implicit-narrowing rule, because §6.2-style promotion makes the natural desugaring `b := b + 10` ill-typed. C#'s answer is a hidden cast that silently truncates in unchecked contexts, guarded by an RHS-convertibility test to bound the damage. Bezel's answer (§6.6) is the same hidden cast made *checked*: the write-back raises `OverflowException` out of range, so the only loss is range and range loss is loud — which is why Bezel does not need C#'s guard and admits a runtime `int` RHS (`acc += n`), the same posture as §6.1's checked `a + b`. The line is drawn at the integer family (plus `char`): a binary-float or `decimal` result against a narrower LHS is rejected outright, because §5.2's float narrowings round or truncate *silently* — `b += 1.5` adding-then-flooring is exactly the invisible loss §5.1 exists to exclude, and the explicit `b := byte(b + 1.5)` spelling is the visible version. The carve-out is scoped to the compound form; plain assignment keeps the strict rule everywhere.

<a id="sec-strings"></a>
## 15. Strings

Strings appear in nearly every program. The choice of representation affects memory footprint and indexing performance, and the obvious choices each have a real cost.

Three options were on the table:

- **UTF-32, fixed width.** Simplest implementation, O(1) indexing trivially, but pays 4× memory for ASCII text.
- **UTF-8 without O(1) code-point indexing.** What Rust, Go, and Swift do. Smallest memory, efficient sequential operations, but indexing the i-th code point becomes O(i), and the API needs cursor types and view-based abstractions to stay usable.
- **Adaptive width (PEP 393).** Per-string storage of 1, 2, or 4 bytes per code point, chosen at construction. O(1) indexing always; ASCII pays one byte; the representation is invisible to programmers.

Bezel picks PEP 393.

The Swift route was attractive on technical merit but requires a substantial design package — substring views, cursor types, multiple abstraction levels — that Bezel doesn't have time to do well in this revision. Without that package, plain UTF-8 with O(i) indexing puts too much friction on basic string code.

A two-types route ("normal `string` is UTF-32; `Utf8String` is the memory-efficient form") fragments the ecosystem. Every API author chooses a side and every consumer pays for conversions across the boundary.

PEP 393 hides the choice in the runtime. The user model is "string is a sequence of code points indexed in O(1)." The implementation picks 1, 2, or 4 bytes per string. ASCII text pays one byte; mixed-BMP text pays two; only strings with code points above the BMP pay four. Indexing is one branch on the kind, reliably predicted. CPython has thirteen years of experience showing this works.

`char` remains 32 bits — the right type for a code point. `s.IsAscii` gives FFI and IO a runtime predicate to skip encoding work for the dominant case. The char-level non-allocating substring view landed in v0.104 as `ReadOnlyStringSpan` (stdlib [§3.3](Bezel_Standard_Library.md#sec-readonlystringspan)) — a record carrying a borrow of the string. A byte-level view from ASCII strings (`ReadOnlyAsciiByteSpan`, v0.106) was retired in v0.188 — a borrow-carrying record cannot cross the FFI boundary (spec §32.5 admits only the §32.13 C-compatible records), and v0.165's span-destination encoding (`Encoding.GetBytes(s, destination: Span<byte>)`, stdlib [§3.2](Bezel_Standard_Library.md#sec-encoding)) serves the allocation-conscious byte path for every string, not only ASCII ones. Byte access from strings routes through `Encoding.UTF8.GetBytes` in either its allocating one-shot or its buffer-reusing span-destination form. See rationale [§5.15](#sec-owned-buffers-and-spans) for the full design story.

<a id="sec-convert-is-a-familiarity-alias"></a>
### 15.x `Convert` is a familiarity alias (ruled 2026-07, #1356)

`Convert`'s string↔primitive members exactly duplicate the §9 primitive `Parse`/`TryParse`/`ToString` members. Ruled: **kept, explicitly as a C#-familiarity alias** — the duplication is documented rather than deleted (deleting would break arriving muscle memory for zero space savings), and `Convert` gains no cross-primitive conversion role: value conversion is the §5.2 checked cast, bit reinterpretation is `BitConverter.Reinterpret` (the recorded split), and `Convert` stays a thin naming veneer over Parse/ToString.

<a id="sec-ffi"></a>
## 16. FFI

<a id="sec-hand-written-declarations-not-bindgen"></a>
### 16.1 Hand-written declarations, not bindgen

Auto-generated bindings (Rust's `bindgen`, Python's `ctypesgen`, SWIG) parse C headers and produce language-side declarations automatically. Bezel's FFI is manual: the programmer writes the Bezel-side signature, and the compiler trusts it — the same hand-declared model as Python's `ctypes`.

Auto-generated bindings tend to expose every quirk of the C API; hand-written declarations let the programmer expose only what's needed, with the names they want. The cost is some typing per imported function. A bindgen tool could generate `extern` block source code in the future; nothing precludes that.

<a id="sec-distinct-types-for-cstring-wstring-rawbytes"></a>
### 16.2 Distinct types for `CString`, `WString`, `RawBytes`

C strings, UTF-16 strings, and arbitrary byte buffers have different ownership stories, different encoding assumptions, and different valid operations. Conflating them — as `void*` does — pushes the burden of remembering which is which onto the programmer at every call site. Distinct types let the compiler refuse calls that mix them up.

<a id="sec-typed-pointers-not-marshal"></a>
### 16.3 Typed pointers, not an untyped `Marshal` surface

Foreign memory access (spec §32.12, v0.186) had two candidate shapes: a Marshal-style static class (`Marshal.ReadInt32(p)` / `WriteInt32(p, v)` over bare `IntPtr` and byte offsets) and typed pointer wrappers. `Ptr<T>` won on §16.2's own argument: an untyped read surface is `void*` with method-name suffixes — `Marshal.ReadDouble(p)` compiles whether `p` came from `sqlite3_column_blob` or `__errno_location`, while `Ptr<double>` vs `Ptr<int>` moves that mistake to compile time. Element-scaled `LoadAt`/`Add` also delete the classic FFI bug class of hand-computed `i * sizeof(T)` with a platform-dependent `sizeof` — the compiler that knows the target stride computes it. The cost was weighed honestly: a generic intrinsic record family with a per-instantiation gate is more machinery than fourteen static methods; §16.2's recorded value judgment outweighs the surface count.

Also declined, with reasons. **Operator pointer arithmetic** (`p + 1`, `-`, `<`): named methods keep the element-scaling in the method's one-line contract, and C itself makes ordering over unrelated allocations undefined; nothing in the binding corpus (sqlite3, curl, BLAS, POSIX) needs them. **`Ptr<Ptr<T>>`**: every `T**` shape in the corpus is expressible as `Ptr<IntPtr>` plus one visible `FromIntPtr` re-typing per indirection level; nested pointee gating buys generality nothing needs. (A record wrapping `Ptr<T>` is itself a valid pointee via the single-field rule — a sanctioned reconstruction of typed double indirection where a binding genuinely wants it, not a loophole: it carries a declared type at every level.) **Panama-style checked foreign memory** (bounds/lifetime-carrying handles): the checking would be exactly as good as the trusted declarations it derives from; `RawBytes.FromForeign(p, length)` *is* the length-carrying form, opt-in where a length exists, and a general checked tier would promise verification §32's trust posture cannot deliver.

<a id="sec-instance-state-and-foreign-callbacks"></a>
### 16.4 Instance state and foreign callbacks: three tiers

The v0.163 callback rule (static reference / non-capturing lambda only) answered "how does a bound method cross a C function-pointer boundary?" with "it cannot" — correct for a bare pointer, but it left C's ubiquitous user-data idiom without a typed home, and the owner's question ("marshal an object method that can update the class object it comes from, the way C# does") deserved a designed answer. v0.186's answer is three tiers keyed to **when native may invoke**:

- **Pull** (call-shaped APIs): an ordinary instance method makes the extern call and writes results into `this` from returns, boundary `out`/`ref` (spec §32.5), and `Ptr<T>` reads (spec §32.12). Most of the question dissolves here; nothing about §32 ever prevented it — what prevented it in practice was the missing expressiveness this revision lands.
- **Call-bounded push** (`qsort_r`, `sqlite3_exec`): every invocation is bracketed by one synchronous extern call, so the callback's environment is structurally alive — its captures live on the calling frame, and extern bodies cannot suspend. §28.14's call-bounded caller rule ("any closure … every captured source trivially outlives the call") transfers across the boundary with one substitution: the callee obligations, compiler-verified in-language, become §32.10 documented trust. The `env` clause (spec §32.8) declares the two ABI facts no analysis can infer — which parameter is the `void*`, and which callback position receives it — and the compiler synthesizes the trampoline.
- **Retained push** (curl's split registration, buses, signal handlers): native holds the pointer past the registering call; no frame bounds the environment, so no lifetime-checked admission can be sound. The registry idiom (spec §32.8: static callback + integer token + `Locked<OwningDictionary<…>>`) makes the safety structural — synchronized state, token indirection (a stale token is a graceful miss, not a use-after-free), wrapper-ordered teardown with the blocking-acquisition discipline stated.

**Why `env` and not `scoped`** — the natural-looking reuse, declined on three grounds: (i) it would give one keyword opposite meanings — in-language `scoped` marks the *storage-bounded* tier (the callee may retain, bounded by an object), while the extern clause marks the *call-bounded* tier (the callee must **not** retain); (ii) v0.175's "`scoped` is illegal on extern" reasoning — storage obligations and quiescence unverifiable across the boundary — remains true and is kept, not reversed; (iii) the marker's grammatical job is ABI slot designation, not a lifetime tier — the paired parameter's lifetime tier is the plain call-bounded default it already has. `ctx` (what C calls the slot) lost to `env` (what Bezel puts there — the closure environment). Slot *inference* (no marker at all) is impossible: `sqlite3_exec` has two pointer-shaped candidate slots, and the callback-side position genuinely varies (first for `sqlite3_exec`'s callback, last for `qsort_r`'s comparator) — both associations must be declared.

**Why the retained tier is a documented idiom, not machinery**: every candidate mechanization (a `registry`-typed extern clause, auto-minted tokens, a compiler-managed handle table) re-derives exactly `Locked<OwningDictionary<…>>` with less visibility, adds grammar for what ten lines of ordinary code state, and forecloses per-binding policy (token reuse, multi-registration, what a "miss" means). It lands as normative guidance text so it is teachable, citable, and testable — the same status as §32.6's ownership patterns.

**The C# `GetFunctionPointerForDelegate` shape** — minting a retained (thunk, environment) pair as an `IntPtr` — is declined: it is precisely a retained environment with no bounding frame, i.e. the storage-bounded tier the boundary cannot verify. C# affords it because the GC roots the delegate via `GCHandle` and the *programmer* remembers to free it — the remembered-convention shape §28 exists to replace. The address-minting surface (`Interop.CodeAddress`) stays static-only so no retained pair is mintable.

**The checked-mode thread guard** rides §28.2's deterministic-backstop posture: foreign-thread invocation of an `env`-paired callback is undefined behavior, and checked mode converts the thread-axis violation into a deterministic abort via a per-activation record in the environment block (correct across concurrent calls and reentrancy; alive exactly while sanctioned invocations are). The **temporal axis** — invocation after the call returned — deliberately gets no promised backstop: the record the guard would read is itself dead at that point; an implementation may poison the environment block at call exit as a quality-of-implementation strengthening. A recorded asymmetry, not a silent one.

<a id="sec-c-compatible-layout-promise"></a>
### 16.5 The C-compatible layout promise

Struct marshalling (spec §32.13, v0.186) enters through §3.6's derived-property mechanism because "passable to C" is exactly a structural predicate; §3.6 itself mandates that form. The layout promise is the language's **first** normative representation guarantee, so its scope is the design's load-bearing feature: classified records get the target C ABI's layout; every other record keeps unspecified layout, preserving future representation freedom.

§3.6's reservation clause ("dispatch of behavior on a derived type property is reserved to compiler-known standard-library types") was engaged head-on rather than lawyered around. A static representation guarantee attaching to *user* records purely by structure is more than admissibility, even though nothing executes differently by classification. Two readings existed: (a) representation is not "behavior", clause untouched — defensible on the letter but eroding the clause's evident purpose (keeping derived properties from silently acquiring semantic weight on user types); (b) the clause needs a scoped, visible exception. Reading (b) was taken and ratified together with the promise; neither stands without the other.

What the promise deliberately excludes: **platform-independence** (sizes and layouts vary as C's do; *which* C struct matches which platform is the programmer's trusted declaration — glibc vs macOS `struct addrinfo` is the canonical divergence, and each platform gets its own declaration); **unions and bitfields** (no structural spelling survives §3.6's computed-never-declared discipline, and bitfield layout is ABI-quirky; the workarounds are recorded in the spec text); **by-value passing** (Stage D: frontend ABI classification — eightbyte splitting, INTEGER/SSE classing, hidden `sret` — is genuinely large, per-target, miscompile-prone work, and the by-address subset unblocks the whole binding corpus except `div_t`-style small-struct returns).

Two recorded deviations-with-reasons ride this area. First, the **inline-array element set** was extended to the full FFI-pointee scalar set *uniformly* — direct extern parameters and record fields alike — one deliberate step past accepted proposal 0033 §4.1's letter, which committed only the field position: pointer-sized scalars pack exactly as primitives do, and the asymmetry ("`[16]ulong` legal as a `SigAction` field, `[2]IntPtr` illegal as a parameter") would have been a rule with no rationale. (`[N]R` arrays of C-compatible records stay excluded as a recorded liftable bound, spec §32.14.) Second, a plain inline-array extern argument passes **by address with no call-site marker**, deviating from the v0.169 marked-mutation doctrine (§22.3) — deliberately: by-address is the *only* passing mode an inline array has at the boundary (C's array-to-pointer convention), so there is no unmarked-by-value alternative for a marker to distinguish, and a mandatory marker would mark nothing.

<a id="sec-variadic-imports-per-arity-aliases"></a>
### 16.6 C-variadic imports as per-arity aliases

§17.9's `params` decline is engaged, not contradicted, by spec §32.11's `variadic(N)` clause: no Bezel-side method becomes variadic, no allocation is hidden, and every call site has fixed, declared arity — what changes is only the emitted *calling sequence* for a symbol that is variadic on the C side. The clause exists to close a real trap: binding a variadic C symbol with a plain fixed-arity extern is undefined behavior on ABIs whose variadic callees consult a caller-set register (SysV x86-64's `%al`), and it often works until it doesn't — the worst failure shape. The compiler cannot detect the mismatch (the symbol's C-side arity is invisible), so the spec documents the trap loudly and provides the sound spelling.

Promotions are a compile error, not an implicit conversion: C promotes `float`→`double` and small integers→`int` in variadic slots; Bezel requires the *declaration* to carry the promoted type, so the promotion is visible where the contract is written. One recorded extension past accepted 0033's promoted-type list: single-integer/pointer-field records (spec §32.13's typed handles) are admitted in variadic positions — such a record marshals as its promoted scalar field, so the slot accounting is unchanged, and a typed handle in a `curl_easy_setopt` slot is the natural exemplar. **True call-site varargs** are declined for v1: they need a new call-arity rule and per-call-site promotion checking, and the measured corpus (curl_easy_setopt, open, fcntl, ioctl — all fixed small arities behind one symbol) is fully served by per-arity aliases; recorded as the v2 candidate if real bindings show alias proliferation.

<a id="sec-deferred-ffi-surface-reasons"></a>
### 16.7 Deferred FFI surface, with reasons

Spec §32.14 lists what stays out of v0.186's FFI; this section records the reasoning that must survive the deferral.

**Export-to-native**: three blockers — symbol-export/C-ABI entry generation belongs to the module/build layer (#1365, proposal 0034); a foreign process entering a Bezel `.so` on an unregistered thread needs a runtime-initialization story §32.10's foreign-thread obligations presuppose rather than provide; and the binding corpus (0007/0011/0014 and the review exemplars) contains no consumer. **`FnPtr<F>`** (calling pointers received from native) is the single most dangerous primitive in this space — it executes, not merely corrupts — and `Interop.CodeAddress` is one-way precisely so this stays independently deferred behind its own evidence bar. **Stage D by-value structs** wait for a dedicated review cycle with per-target ABI-classification tests (§16.5).

**`ForeignHandle<T>`** (the `GCHandle` analog: object↔`IntPtr`) was evaluated and deferred on four grounds: (1) the pinning half of `GCHandle`'s job does not exist here — Bezel heap objects never relocate, so the handle would provide only address minting plus liveness discipline; (2) the liveness discipline it offers is *weaker* than the registry idiom's — a stale handle resolve is silent undefined behavior, a stale registry token is a graceful miss under a lock, so for retained callbacks (the only tier that wants it) the idiom strictly dominates on safety at the cost of one dictionary lookup; (3) it would break the **no-object-address invariant** v0.186 otherwise establishes (spec §32.12): after this revision the only addresses in the language are buffer interiors, foreign values, and code — object identity stays outside the address space, load-bearing for §30.14 and for the unforgeability of §28's dispose-through-borrow rules; (4) the reopening condition is recorded — a measured per-invocation registry cost that matters, or a native API that requires the user pointer to be the object itself — and reopening takes its own small proposal.

**Declaration-bound destructors** (`extern owned handle Sqlite3Db closes sqlite3_close;`-style) are declined with 0033 §7.2's three reasons: the pattern it automates already works today in ten lines (probe `p9_wrapper`, exit 0); real bindings grow a wrapper class anyway (the destructor is three of its lines); and foreign destructors have *policies* a bound function name cannot express (`sqlite3_close` returns `SQLITE_BUSY`; `fclose` can fail and lose data) — a destructor body expresses the chosen policy, a `closes fn` clause silently discards every return code.

**Startup symbol resolution** (spec §32.11) is pinned eager — every failure before `Main` — with the cost recorded: absent conditional compilation (0034) and runtime loading, a module declaring any platform-absent symbol makes every program linking it unrunnable on that platform even if the call is never reached. Fail-fast was chosen because extern declarations are per-platform artifacts already and a probe-for-availability binding wants conditional compilation, not late failure; the item reopens alongside 0034.

<a id="sec-things-explicitly-rejected"></a>
## 17. Things explicitly rejected

<a id="sec-truthiness-in-conditions"></a>
### 17.1 Truthiness in conditions

`if (user)` is forbidden. Conditions must be `bool`. Truthiness collapses zero, empty string, empty collection, and null.

<a id="sec-string-concatenation-with-non-strings"></a>
### 17.2 String concatenation with non-strings

`"x = " + 42` doesn't compile. Use interpolation: `$"x = {42}"`. Implicit `.ToString()` calls hide allocation behavior.

<a id="sec-goto"></a>
### 17.3 `goto` — declined; labeled `break`/`continue` adopted instead (v0.201)

`goto` remains declined. Multi-level loop exit is **labeled `break`/`continue`** (spec §21.5, v0.201; proposal 0050): a loop may carry a `name :` label, and `break name;`/`continue name;` target it. Labeled break keeps the structured subset of goto's power — forward-only, cannot enter a scope, cannot form a loop, target named on a construct the jump is inside — so every scope-exit obligation stays statically enumerable and the disposal story needed zero new rules (the jump reuses the multi-scope unwind edge `return`/`throw` already defined). The closers ride v0.170's named-construct rule (`end scan;`); a labeled loop's keyword closer (`end for;`) is rejected per that rule's own "otherwise". Declined alongside goto: numeric break levels (positional targets are fragile under edit) and labeling arbitrary statements (dead weight — only loops are targets). Extraction into a method remains good style where the inner logic deserves a name; it is no longer the only spelling.

<a id="sec-default-interface-methods"></a>
### 17.4 Default interface methods

Interfaces have only signatures. Default interface methods (C# 8+) blur the line between interfaces and abstract classes and create surprising behavior around explicit implementation. For shared logic, use an abstract class.

<a id="sec-member-hiding"></a>
### 17.5 Member hiding

See [§8.1](#sec-member-hiding-is-forbidden).

<a id="sec-inline-fixed-size-value-type-array-fields"></a>
### 17.6 Inline fixed-size value-type array fields

*Previously rejected; provided in v0.98.* Inline arrays `[N]T` are now a first-class type. They can appear as locals, as class fields (including with owned slots via `[N owned]T`), and as record fields when the slots are not `owned` (records hold only copyable value types, so move-only `[N owned]…` inline arrays are not admitted as record fields). A class can have an inline-array field whose storage is part of the class's layout, equivalent to C#'s `fixed` or Rust's `[T; N]`. See language spec [§15.1](Bezel_Language_Spec.md#sec-inline-arrays) for the type form and [§15.3](Bezel_Language_Spec.md#sec-move-only-value-types) for the move-only category that supports inline arrays with owned slots. The v0.40-v0.97 rejection rationale was that the use case is rare; experience and the v0.97 verification rounds suggested that inline arrays' value extends beyond fixed-size buffers into FFI marshalling, packed records, and as the foundational storage primitive over which owning collections compose.

<a id="sec-combined-visibility-modifiers-protected-internal"></a>
### 17.7 Combined visibility modifiers (`protected internal`)

C#'s `protected internal` (union: visible to derived classes *or* same-module code) and `private protected` (intersection: visible to derived classes *only within* the same module) are not provided. Most C# developers cannot state the semantics of either without looking it up. Bezel's four levels — `public`, `internal`, `protected`, `private` — are individually clear and cover the majority of needs. The intersection case (framework-internal override points) is a real gap, but the workaround is acceptable: use `internal` and rely on code review for the "only subclasses should call this" convention. If implementation experience shows the pain is worse than expected, `protected internal` meaning the intersection can be added as a purely additive change in a future revision.

<a id="sec-readonly-local-bindings-let-val-readonly-var"></a>
### 17.8 Readonly local bindings (`let`, `val`, `readonly var`)

Many languages provide a way to declare a local variable that cannot be reassigned after initialization: `let` (Swift, Rust, JavaScript), `val` (Kotlin, Scala), `final` (Java). Bezel deliberately does not provide this in the current version.

`var` is always reassignable. `const` requires a compile-time constant. `using var` is non-reassignable and carries disposal semantics — with the honest footnote (2026-07, review finding #1360) that per spec §28.10 a `using var` whose RHS is value-typed, runtime-managed, or a borrow has a no-op disposal, making it an *admitted* (if unidiomatic) readonly-local spelling. That admission is tolerated for generic and desugaring uniformity, not endorsed as the readonly-local idiom; a runtime-`const` (see the deferred list, §18) remains the candidate if demand materializes. There is no `let`, `val`, or `readonly var` for runtime-computed but non-reassignable locals.

The omission is a cost-benefit judgment. The bug class prevented by readonly locals — accidental reassignment of a local that should have been stable — is real but small relative to the complexity budget. Most locals in well-written code are single-assignment regardless of enforcement, and the ownership system ([§28.3](Bezel_Language_Spec.md#sec-local-variables-ownership-and-borrows)) already tracks local-variable state far more aggressively than mutability alone. Adding a fourth local-declaration form (`let`, `readonly var`, or similar) would increase the decision burden on every local declaration without a proportionate safety payoff.

C# has lived without readonly locals for 25 years. Java added `final` locals but few teams enforce their use. The practical evidence is that this is a nice-to-have, not a must-have.

*(v0.201 — delivered; proposal 0049 train A.)* The named candidate landed: local `const` accepts any initializer, classified by form (spec §21.1) — a §17.14 constant expression of primitive/`string` type keeps compile-time-constant semantics; everything else is a **runtime const**, a single-assignment binding excluded from compile-time positions. The central ruling is ownership: a runtime `const` **rejects** owned-producing initializers, keeping the clean division — `using var` is the owned, scope-pinned binding with declared disposal; `const` is the non-owned one whose bindings never change state (not by assignment, consumption, or disposal). The permissive owned-`const` alternative was declined as an undeclared-disposal duplicate of `using var`. The checkable payoff is §7.4's amendment: a `const` local's narrowing is never invalidated — the invalidation forms are all compile errors on a `const`, so the guarantee costs no new analysis. The no-op-disposal `using var` footnote above stops being needed: `const` is now the endorsed readonly-local idiom.

<a id="sec-variadic-parameters-params"></a>
### 17.9 Variadic parameters (`params`)

There is no `params` keyword. A method that accepts a variable number of arguments uses `Array<T>` and the caller writes a collection literal:

```bezel
public method Log(messages: Array<string>) ...
Log(["hello", "world"]);
```

The brackets at the call site are syntactic friction but they make the allocation visible. A `params` mechanism that silently constructs an array from bare arguments hides allocation behavior — exactly the kind of implicit cost that Bezel's design philosophy aims to surface. The brackets also make the call site unambiguous when reading: `Log(["a", "b"])` is clearly one argument of type `Array<string>`, while `Log("a", "b")` under a `params` rule could be a two-argument overload or a params call, depending on what's declared.

<a id="sec-auto-ranked-extension-specificity"></a>
### 17.10 Auto-ranked extension specificity (the deleted §26.5.1 rules 2 and 3)

Through v0.185, extension-member resolution ranked equally-applicable candidates by three specificity relations (spec §26.5.1): subtype ordering on receiver-substituted heads (rule 1), a recursive more-concrete ordering on declared generic heads (rule 2 — `extension IEnumerable<int>` auto-beating `extension IEnumerable<T>` for an `Array<int>` receiver), and constraint-implication ordering (rule 3 — a `where`-constrained block beating a less-constrained same-head block when every constraint of the loser is "implied by" the winner's). Rules 2 and 3 are deleted (proposal 0039, accepted 2026-07-12): rule 1 alone remains, evaluated on receiver-substituted heads over applicable candidates, and every collision the deleted rules would have ordered is the §26.5 rule-4 ambiguity error.

The case against them was cost without a user. Rule 3's "implied by" was an entailment judgment whose semantics the spec never defined (is `where T: Dog` implied by `where T: Animal`? does implication chain through `where T: U` parameter chains, or through interface inheritance?) — the only constraint-entailment reasoning anywhere in the language; constraint *satisfaction* (spec §14.2) checks concrete arguments at instantiation, a different and decidable question. Rule 2 required a second ordering relation besides subtyping — a recursive concreteness comparison — plus the v0.183 clarification that rule 1 compares receiver-substituted heads while rule 2 compares declared heads: a two-views subtlety that existed only to keep the two rules from contradicting each other. Neither rule was ever implemented — the reference compiler applied first-declared-wins (#1307), so the spec's own worked example silently returned a declaration-order-dependent answer — and neither was ever exercised: the complete stdlib inventory (proposal 0039 §5, independently re-derived by its critique pass) shows every same-name pair across overlapping stdlib extension blocks differs in arity, so applicability alone decides every stdlib call and zero call sites resolve through rules 2–3. Deleting them also shrank #1307 from "implement a recursive ordering plus an entailment judgment" to "implement subtype ranking plus the rule-4 diagnostic".

What is lost is auto-ranked specialization: a generic block plus a same-head specialized (rule 2) or extra-constrained (rule 3) block sharing one member name and signature, the special form selected automatically. The remedies are the ones the language already records: keep one block and dispatch internally; split the blocks across modules so clients import one; or export the specialization under a **distinct name** — spec §22.6's posture (v0.181) that when same-name declarations cannot be soundly auto-ranked, the answer is distinct names, the convention the standard library uses everywhere. The terminal state — a rare, loud, remediable ambiguity error — is the terminal state §18's extension-call-disambiguation entry already records as acceptable for extension collisions.

The deletion is the cheap-to-reverse direction, and the re-addition condition is recorded: if demonstrated demand for auto-ranked specialization ever materializes, **rule 2 alone** may return as a compatible widening — the rules applied in order, so a restored rule 2 would only convert former ambiguity errors into resolutions and could not re-route any program that resolves under rule 1 alone. No re-addition condition is offered for rule 3: it would return with its unspecified entailment judgment, the worst item on the ledger.

<a id="sec-things-deferred"></a>
## 18. Things deferred

Not in this version; the design is open to them in future revisions.

- **Sum types / discriminated unions.** *Shipped in v0.200 (proposal 0041, spec §35)* — closed nominal sums as the `choice` kind, with the three-way payload-derived ownership classification and static exhaustiveness by case name; the reasons and declined alternatives are [§9.6](#sec-choices-why-a-new-kind). What remains open is what the proposal deliberately excluded: structural/anonymous unions (declined — §9.6), GADTs, multi-level exhaustiveness counting, and `Result` combinators (each recorded liftable in proposal 0041).
- **Static interface members.** *Shipped in v0.176 (#807, spec §11.8)* — abstract-only, recurrence-constrained, with compiler-provided primitive conformances. The follow-ups it unblocks (FromCollectionLiteral/IDeserializable promotion, Range<T> de-intrinsicking) are tracked issues.
- **Trait/typeclass-style polymorphism.** Interfaces handle most of what traits do; the gap is associated types.
- **Const generics.** Generic parameters that are values, not types.
- **Reflection beyond `typeof`/`GetType`.** This splits into three pieces with different dispositions. (1) *Type-lattice metadata* — kind predicates, `BaseType`, `Implements`/`IsAssignableFrom`, enum introspection — **delivered in v0.113** on the `Type` token (stdlib [§2.13](Bezel_Standard_Library.md#sec-the-type-class)). (2) *Member-access reflection* — field/method enumeration, by-name member access, dynamic instantiation — is **declined, not deferred**: it contradicts the ownership model (a reflective `owned`-member access has no static site to carry its contract) and is the maximal violation of the no-hidden-magic principle; see rationale [§5.18](#sec-type-identity-not-reflection). It is recorded as declined so the question is settled rather than perennially reopened. (3) *Generic-instantiation decomposition* (`GenericArguments`/`GenericDefinition`) remains genuinely **deferred** — it is useful but cannot be expressed without also adding an unbound-generic `typeof` (`typeof(Array<>)`), which is a language change; it is to be decided together with that syntax, not bundled into a metadata revision. Attribute-only reflection, if reflection pressure ever materializes, is the realistic future direction and is itself a separately-scoped question (the attribute-system entry below).
- **Macros / metaprogramming.** Source generators, compile-time evaluation, syntax-tree macros.
- **Serialization: complete (object-graph tier fully delivered).** The serialization stack landed in nine planned non-breaking stages: the format-abstraction vocabulary (v0.114, stdlib [§2.14](Bezel_Standard_Library.md#sec-serialization-vocabulary) — `ISerializer`/`IDeserializer` agents, `ISerializable`/`IDeserializable` capabilities); the concrete `Json`/`Binary` format implementations (v0.115, `System.Serialization`, stdlib [§2.15](Bezel_Standard_Library.md#sec-concrete-serialization-formats)); compiler-synthesized conformance for records and enums (v0.116, language spec [§9.8](Bezel_Language_Spec.md#sec-serialization-synthesis) — modeled on the existing auto-equality synthesis, a contained dedicated compiler feature, deliberately not the open-ended C# source-generator model and not gated on the macro system above); field-name customization (v0.117, the `serialized` clause of language spec [§9.8](Bezel_Language_Spec.md#sec-serialization-synthesis) — a closed compiler-recognized modifier with three effects (rename, exclude, tolerate; rename and tolerate combinable), deliberately *not* an attribute system and improving on Swift's `CodingKeys` by being per-member and total); operation-scoped unknown-field tolerance (v0.118 — `IgnoreUnknownFields` on the deserializer, *not* a type annotation, because tolerance is a property of a particular read rather than of the type's wire contract); tree-shaped class synthesis (v0.119, the `serialized tree` class-header clause of language spec [§9.8](Bezel_Language_Spec.md#sec-serialization-synthesis) — synthesis for classes whose serialized graph is a tree, the assertion enforced dynamically so a non-tree graph is a *detected error*, never silent duplication); the deferred-borrow-binding vs definite-assignment working-out (v0.120, rationale only, no spec text — determining the tension had a sound resolution before any syntax); shared-reference DAG synthesis (v0.121, the `serialized graph` class-header clause of language spec [§9.8](Bezel_Language_Spec.md#sec-serialization-synthesis) — identity-preserving deserialization of aliasing acyclic graphs, the owning tree reconstructed owner-before-borrower and every back-edge bound *through the constructor* so [§7.9](Bezel_Language_Spec.md#sec-definite-assignment-for-non-nullable-fields) holds unmodified); and polymorphic dispatch (v0.122, the `polymorphic` registry of language spec [§9.8](Bezel_Language_Spec.md#sec-serialization-synthesis) — a closed, explicitly-registered discriminator→derived-type map, no reflective subtype discovery, the discriminator consumed before component binding; explicit-registration-never-reflection per [§5.18](#sec-type-identity-not-reflection), the model the mainstream reached only after reflective `$type` became a remote-code-execution vector; rationale [§5.19](#sec-serialization-without-reflection)). One piece remained through v0.123 — *cyclic* class synthesis — and it is **delivered in v0.124**: language spec [§9.8](Bezel_Language_Spec.md#sec-serialization-synthesis) specifies the `serialized cyclic` clause, the statically-checked self-contained-constructor eligibility rule, and the two-phase construction whose intermediate state is provably unobservable, with [§7.9](Bezel_Language_Spec.md#sec-definite-assignment-for-non-nullable-fields) preserved unmodified — the v0.123 working-out's discharge made normative. **The serialization stack is now complete**: every class object graph (tree, DAG, cyclic) is synthesizable, polymorphic edges resolve through an explicit closed registry, and the only remaining reason to hand-write `Serialize`/`Deserialize` is a class whose constructor cannot be made self-contained — a recorded, compile-time-detected, principled exclusion, not a deferred feature. *(v0.141: the keyword model described here was retired for **type-driven** `Shared<T>`/`Weak<T>` serialization — the serialized shape is now read from field types, and a cycle closes through a nullable `Weak<T>?` back-edge on a `Shared<T>` spine, with no two-phase construction and no self-contained-constructor rule; the working-out is [§5.22](#sec-type-driven-serialization).)* The staging was deliberate throughout: the vocabulary (v0.114) is the one piece that cannot be retrofitted, and each later stage was an independent non-breaking addition forward-compatible with the next, every hard question (the deferred-binding tension, v0.120; the cyclic unobservability proof, v0.123) resolved reasoning-first before its spec text.
- **Custom collection-literal protocols.** As of v0.111, user-defined types opt into *sequence*-literal construction by declaring the `FromCollectionLiteral` static factory (language spec [§15.4.1](Bezel_Language_Spec.md#sec-the-user-defined-sequence-literal-protocol)); both borrowing (`ReadOnlySpan<T>` parameter) and owning (`owned OwningArray<T>` parameter) shapes are supported. What remains deferred: a user-extensible *dictionary*-literal protocol — the `[k: v, ...]` paired form for user-defined map-like types. The built-in `Dictionary`/`OwningDictionary` keep the dictionary-literal form; user map-like types use ordinary constructors until the paired-factory protocol is designed. See rationale [§5.16](#sec-collection-literals-for-complex-collections).
- **Synchronization contexts for async.** Needed if Bezel targets desktop UI frameworks.
- **Module-private types.** A `module` modifier restricting visibility to a sub-module rather than the whole assembly.
- **Ref-returning indexers.** Would let `dict[key]++` be one operation instead of two. The language currently has no ref returns ([§22.14](Bezel_Language_Spec.md#sec-no-params-no-ref-returns) of the spec); adding them is deferred.
- **Asymmetric record auto-equality customization.** A way to exclude one field (cached hash, debug timestamp) from auto-equality. Currently it's all-or-nothing.
- **Stack-allocated runtime-sized buffers (`stackalloc` analog).** v0.99 introduced `Span<T>` and `ReadOnlySpan<T>` as records carrying borrows of an `OwningBuffer<T>`; v0.100 added the write capability to `Span<T>`; v0.101 thickened the API surface with iteration, search, equality, and bulk-mutation methods; v0.102 generalized to admit value-typed T; v0.103 added byte-buffer accessors on `Span<byte>` and `ReadOnlySpan<byte>`. What remains deferred: a stack-allocated runtime-sized buffer (C# `stackalloc` analog) that would let spans view into stack memory rather than only heap memory. The use case is performance — avoiding heap allocation in hot paths like parsers. Bezel's existing inline arrays (`[N]T`, language spec [§15.1](Bezel_Language_Spec.md#sec-inline-arrays)) cover the fixed-size case; a runtime-sized stack form would extend the same lifetime story to runtime-N. The design must address how stack-bound lifetimes interact with closures, exception unwinding, and recursive calls. Low priority — the heap-backed `OwningBuffer<T>` is sufficient for almost all use cases; the gap is real but narrow.
- **Spans over additional view sources.** v0.99-v0.103 spans (`Span<T>` and `ReadOnlySpan<T>`) view only into `OwningBuffer<T>`. v0.104 added `ReadOnlyStringSpan` (stdlib [§3.3](Bezel_Standard_Library.md#sec-readonlystringspan)) for the string-source case. v0.106 added `ReadOnlyAsciiByteSpan` for the byte view over ASCII strings (retired v0.188 — the allocation-conscious byte path is `Encoding.GetBytes` with a span destination, v0.165). v0.107 added `ArraySpan<T>` and `ReadOnlyArraySpan<T>` (stdlib [§4.15](Bezel_Standard_Library.md#sec-arrayspant-readonlyarrayspant)) for sub-range views over `Array<T>`. v0.108 added the `IReadOnlySpan<TElement>` interface (stdlib [§4.16](Bezel_Standard_Library.md#sec-ireadonlyspan)) unifying the read-only surface across all concrete span types. What remains deferred: `Span<T>` over an inline array `[N]T` — would need a new borrow-source kind that ties the span's lifetime to a stack frame, with rules for closure capture, exception unwinding, and recursive calls. Substantial design work for a narrow performance gain over the existing `OwningBuffer<T>`-backed form. Deferred — the five concrete span types (OwningBuffer-backed pair, ReadOnlyStringSpan, and ArraySpan-pair) plus the read-only interface cover the dominant use cases.
- **Move-only value types in `OwningBuffer<T>` / `Span<T>` / `ReadOnlySpan<T>`.** v0.102 admits value-typed T but excludes the move-only value types (owning inline arrays `[N owned]T` and `[N owned]T?`). A buffer of move-only values would itself have move-only slot semantics — admissible in principle but requires a third category in the slot-semantics dispatch (class T, non-move-only value T, move-only value T) without an obvious motivating use case. Users who need a runtime-sized container of fixed-size owning arrays today wrap them in a class. Deferred until a motivating use case emerges.
- **Lambda-parameter destructuring.** *Shipped in v0.183 (#1408, spec §27.4)* — irrefutable positional-record destructuring in lambda parameter position, `lambda(ClickedEvent(_, x, y, _)) => ...`; the head names the parameter's exact record type, bindings are ordinary positional-field reads (borrows for class-typed fields, §28.3), and refutable pattern elements remain excluded — a parameter list is not a `case`.
- **Tuples and tuple destructuring.** A built-in anonymous-product type — `(int, string)` as a type, `(42, "hi")` as a value — with positional access and `for var (k, v) in dict do ...` destructuring in patterns and loops. This is an **ergonomic convenience, not a capability gap**: every use case is already expressible. Bezel's model uses positional records (language spec [§9.1](Bezel_Language_Spec.md#sec-positional-records)) for value-only products, and *owning classes with multiple `owned` fields* for products that carry owned resources (a class may own its fields per [§28.5](Bezel_Language_Spec.md#sec-owned-fields); a method may return `owned C`; one `using var` discharges the whole aggregate, cascading to every owned field). The `OwningDictionary<K, V>.Drain()` case — once thought to need tuples — is handled by exactly this pattern via the `DrainedEntry<K, V>` owning class (stdlib [§4.9](Bezel_Standard_Library.md#sec-owneddictionaryk-v)), with no language change. What tuples would add is purely notational: positional `(a, b)` destructuring sugar and one-shot anonymity, versus the named, documented shape that records and classes provide. Bezel's design philosophy already argues (records-vs-tuples) that a name and a documented shape is a feature, not a limitation; the same argument applies to the owned case. Class deconstruction (a `Deconstruct`-style positional surface for classes) was evaluated and declined for the same reason — see [§5.17](#sec-why-no-class-deconstruction). Tuples remain available as a low-priority future convenience; the structural-vs-nominal identity question and the named-vs-positional-fields question would need resolving, but neither blocks any program from being written today.
- **Runtime-evaluated `const` for locals.** *Shipped in v0.201 (proposal 0049 train A, spec §21.1)* — the classification split (compile-time vs runtime const), the never-owned ownership rule, and the §7.4 never-invalidated narrowing guarantee; reasons and declined alternatives in [§17.8](#sec-readonly-local-bindings-let-val-readonly-var).
- **Post-condition loops (`do-while` / `repeat-until`).** A loop that executes the body at least once before checking its termination condition. The current workaround — `while true do ...; if not cond then break; end; end;` — is straightforward but heavier than the dedicated form would be. The open design questions are syntactic: a literal `do ... while (cond);` form clashes with [§21.6](Bezel_Language_Spec.md#sec-do-end-blocks)'s `do ... end` blocks, so the addition would either need to disambiguate by the presence of `while`/`until` (which parses but reads ambiguously) or introduce a new keyword (`repeat ... until cond;` is the Pascal/Modula-2 form and would fit Bezel's overall vocabulary). The construct stays deferred as a decision, not a promise (v0.183): the payoff is the removal of one `if not cond then break; end;` line from an uncommon loop shape, and every candidate spelling has a real cost — a literal `do … while` collides with the block form, and `repeat … until` spends a new reserved word on that payoff. With the #745 block-form unification RFC declined (DECLINED.md D-0003), no syntax window is open for the form to ride. If it is ever adopted, `repeat StatementList until Expr;` is the presumptive spelling; until a stronger need is demonstrated, the workaround is the decision.
- **Multi-consumer channels / MPMC work queues.** Deferred at v0.133 pending `Shared<T>` (since delivered) and re-affirmed at v0.174 "pending pipeline evidence." That evidence now exists (2026-07 review probe: a 3-worker pool needs one channel per worker, a hand-written sendable carrier class per argument tuple, and blind `i mod N` round-robin — a slow item pins its worker while the others idle; ~90 lines for a trivial pipeline), so the deferral now stands on its remaining reason alone: receiver cloning is shared ownership of the *consume* capability, and §28.13's domain-locality questions for the synchronized core set are unresolved. The honest design options are `Channel<T>` joining the §28.13 synchronized set with cloneable receivers, or a dedicated MPMC `WorkQueue<T>`. Until one is designed, the N-single-consumer-channels + round-robin pattern is the sanctioned pool idiom, its load imbalance acknowledged rather than hidden.
- **Channel iteration (`ReceiveAll`).** The consume-until-closed loop is currently exception-terminated: `Receive` raises `ChannelClosedException` on drained-and-closed, so normal termination flows through a `catch` (stdlib §6.9). The language already has the right consumption shape — `await for` over `IOwningAsyncEnumerable<T>` with owned iteration variables — and the recorded future direction is `Channel<T>.ReceiveAll(): IOwningAsyncEnumerable<T>`: single-consumption (affine, like a lazy query), yields each item owned, ends the enumeration normally at drained-and-closed, and propagates disposal to a pending receive — the `ChannelReader.ReadAllAsync` shape. *Shipped in v0.186 — spec §30.15, stdlib §6.9; landed as sketched here (affine per §29.11, normal completion at drained-and-closed, abandonment deregisters). The entry was annotated late (v0.201, proposal 0049 train C), which misled two planning documents in the interim — the same-revision annotation rule now on the spec-change checklist exists because of this entry.*
- **`sendable` as a `where` constraint.** *Shipped in v0.201 (proposal 0049 train B, spec §14.2 "Derived-property constraints")* — the general rule decided once (derived-property constraints admitted individually by recorded ruling; nothing propagates unless written; no negated form), `sendable` admitted first, and `Domain.Spawn`/`Channel<T>` now state the requirement in their signatures (stdlib §6.8/§6.9). §12.5's decline of inference-driven Send/Sync typing stands untouched: the constraint is opt-in per declaration and appears only where a signature already traffics in domain crossing.
- **Exportable type aliases.** A module-level `type` alias is always module-internal (spec §27.8, v0.183). Making aliases exportable (`public type`) is deferred to the module-identity work (proposal 0034's family): it touches artifact metadata, §2.7 resolution order, and the collision rules, while the workaround — the importing module declares its own alias — is one line.
- **Extension-call disambiguation syntax.** When two equally-specific extensions collide (spec §26.5 rule 4), the remedies are import surgery or a static-class helper method; there is no call-site form naming the providing module. A first-class spelling is deferred: extension blocks are nameless, so any design must qualify by *module*, dragging §2.7 chain-resolution changes with it — and the collision is rare, loud, and totally remediable today.
- **`owned` as a generic argument on user-defined types.** v0.75 through v0.96 admitted `owned T` as a generic-argument modifier (`Array<owned T>`, `Task<owned T>`, etc.) via a hard-coded opt-in list. v0.97 retired this mechanism in favor of separate named classes (`OwningArray<T>`, `OwningTask<T>`, `OwningDictionary<K, V>`, etc.). What remains deferred is whether and how user-defined generic types should be able to express owning-element semantics: a mechanism by which a user-written `Pool<T>` could declare an "owning T" variant and define the corresponding per-operation semantics (which methods accept owned arguments, which dispose on removal, which transfer ownership out on drain). v0.98's inline-array primitive (`[N owned]T?`) gives user-defined owning containers a foundation to compose over (see rationale [§5.14](#sec-inline-arrays-and-array-kind-split)), but expressing this with full generic-argument-level support is deferred.
- **LINQ over owned-element collections.** The standard library's LINQ extensions (`Where`, `Select`, `OrderBy`, `ToArray`, etc.) are declared on `IEnumerable<T>` with non-owning element semantics. Applying them to an `OwningArray<T>` and other `OwningX<T>` collections works today through the borrowing-iteration upcast — owning collections implement `IEnumerable<T>` and produce borrows on iteration — so `ownedArr.Where(predicate)` produces a borrowing pipeline. What is deferred is a parallel LINQ surface declared on `IOwningEnumerable<T>` that preserves ownership through the pipeline (e.g., `Where(predicate: (T) -> bool): IOwningEnumerable<T>`). The design question is whether to provide one method per operation that infers from receiver type, or to add a parallel set of named methods on `IOwningEnumerable<T>`. Code that needs to drain-and-transform today writes the drain loop explicitly.
- **Attribute / annotation system.** A C#-style `[Attribute]` declaration syntax, with attribute classes derived from a base type and reflective query at runtime. Useful for serialization metadata, framework integration, deprecation markers, validation rules, dependency-injection registrations, and other annotations whose effect is interpreted by tools rather than the language itself. Not in this version because most attribute *uses* depend on machinery that is itself deferred — reflection beyond `typeof`/`GetType`, serialization frameworks, dependency injection, test frameworks. Designing attributes before designing how they are consumed would lock in syntax for an unbuilt feature, and that syntax would likely need to change once the consuming machinery exists. The corollary: any future attribute design will be tightly coupled to the reflection and serialization designs, and developing them together is the better order than attempting to retrofit one to the other.

  Two narrowly-useful capabilities can be added before the full system, if user demand emerges:
  - **`[Obsolete]`-style compile-time deprecation.** Achievable as a compiler-recognized declaration modifier (an `obsolete` keyword preceding a declaration, or a similar narrow syntax) without needing runtime reflection. The compiler emits a warning at every use site of an obsolete declaration; no runtime machinery required.
  - **Method-implementation hints** (`[MethodImpl]`-style: aggressive inlining, no inlining). Achievable as a small fixed set of compiler-recognized declaration modifiers. No runtime introspection required.

  These two narrow additions don't depend on reflection at runtime and could land independently of the broader attribute design. They are not committed for any particular revision; the deferred-list entry exists to mark the open question rather than to schedule the work.

  C# attributes have known costs that influence the deferral: attributes proliferate in real-world C# codebases (validation rules, serialization hints, ORM mappings, DI registrations stacking on a single class), they invite stringly-typed magic (attribute parameters often interpreted by reflection-based machinery with shallow type checking), and they blur the boundary between language semantics, framework machinery, and inert metadata (a reader cannot tell from an attribute alone what affects compilation, what affects runtime, and what affects nothing). Bezel has time to design around these costs rather than inheriting them.

## 20. Closing

If the opening framed Bezel by what it borrows, the body has shown what it actually contributes: not the features — those have ancestors — but the discipline applied to combining them. The recurring move in this document is the same one every time a hard question arrived. Ship the part that fits the foundations cleanly. Decline the part that fights them, with the reason written down so the question stays settled rather than perennially reopened. Scope whatever genuinely remains open by naming its precise blocker, not by deferring it vaguely. Member-access reflection is declined, not pending. The cyclic-serialization soundness obligation was discharged in prose before any syntax was written. Tuples and post-condition loops are conveniences with recorded costs, not gaps. The deferred list is a list of decisions deliberately not yet made — each with its reasoning — never a list of unsolved problems.

That is the claim this document makes for the language: not that it is novel, but that every line in it was chosen rather than defaulted into, and that the choices cohere. The design is, by intent, complete — and it is no longer only on paper. A reference compiler now implements most of it, exercised by a test suite that takes its cases from the spec's own examples, and it has done exactly what a compiler was always going to do: surface concrete questions the spec did not anticipate. Those questions are answered the same way every question here was — the spec stays normative, every divergence is recorded and resolved as its own decision, and what the foundations already imply is determined before anything new is added.
