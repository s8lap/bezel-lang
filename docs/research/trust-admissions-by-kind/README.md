# Trust admissions by kind: can each stored borrow get a cheaper safe treatment than one annotation everywhere?

Research lane, 2026-10-28. Base: origin/main `6deabe73e` (spec **v0.350**). Compiler: the r35 release `bezelc 0.0.0-f6863e62`. Model: a copy of `docs/research/soundness/bzcore-l1/bzcore.py` extended in `model/`. Nothing under `docs/`, `tests/`, `src/` was edited; nothing was posted. **MEASURED** marks a number produced by a script in this directory; **QUOTED** a number or sentence taken from the tree; **PRIOR ART** a claim from general knowledge, unsourced here.

## 0. One page for the owner

**The question.** K4.3 (§28.3.1, v0.350) admits a borrow stored where the body-local checker cannot bound its life — a field, a collection slot, a comparer, a frame, §28.14's two residuals, v0.350's slot-displaced transfer — on *trust*, with checked mode's disposed flag as the backstop and undefined behaviour in an unchecked build. The option on the table: classify these stores **by kind** and give each the cheapest safe treatment, instead of one annotation (`kept`/`scoped`) at every retaining parameter.

**What the corpora hold** (MEASURED, `data/scan_trust.py` over 7,353 units: 3,800 rule-corpus files, 802 doc-extracted blocks, 2,562 lit programs, 189 gtest files holding ~2,000 embedded programs). 203 store sites that rest on the field-held or collection-held clause (169 field stores, 12 property stores, 11 collection stores, 7 field initialisers, 4 primary-constructor captures), plus 2 comparer-held, 3 frame-held, 10 user `scoped` fields and 3 form-3 registrations (§28.14 residuals) and 1 slot-displaced shape. 199 of the 203 stores are a *constructor or method parameter* (183 plain, 11 primary-constructor, 5 paths through a parameter) stored into a plain field or collection; 2 store `this` or a path through it; 2 store a field of `this`. Of the 203, **61** sit in rule/doc/lit programs the spec expects to accept; the gtest units add **49 distinct sites**. The kind can be read only where the storing member's call sites are visible in the same unit; 32 sites resolve:

**Headline measurements.**

1. **Kind 3 dominates.** Two thirds of the sites whose kind is readable are short-lived helpers; kind 1 proper — a child stored into its owner's `owned` storage and never moved out — is almost absent from the corpora (1 site; the spec's own `_owner: Customer` example is a declaration with no construction). Kind 2 is the registry shape, 8 sites. The corpora are small test programs, so this skews toward kind 3; the unresolved fragments' names (7 `owner`-like, 6 registry-like) suggest a real-code mix with more of kinds 1 and 2, but not one that would dislodge kind 3.
2. **The `scoped`-everywhere alternative is not viral in these corpora: 180 of 199 hits need the marker on exactly one signature, 19 need two, none need three.** Forwarding chains (factory → constructor, DI-shaped wiring) are rare in test programs; the one real DI shape found (`Util.Depth` forwarding into `Pair`) needs two. Probe k3d shows the three-signature case by construction (`Bank.Wire(c) → Open(c) → new Account(c)`). The corpus ratio of parameter-sourced back-reference stores to `scoped` class-typed parameters is **199 : 19 ≈ 10 : 1** (the review measured 36 : 12 on r35's report lines; DECLINED 808's bar — "`scoped` has become the norm" — is not met and is moving the other way).
3. **r35 today** (MEASURED, `probes/results.md`, 14 programs × 3 build modes): every kind compiles; checked mode faults deterministically at the stale read in every kind (k1b, k1c, k2a, k3a, k3b, k3d, k4a, k4b: exit 70 `DisposedAccessException`); unchecked mode prints an empty string from freed memory (exit 0) or dies (k2a: exit 2). The report mode names 12 of the 13 stores (the collection store in an expression-bodied `Register(item) => _items.Add(item)` is silent: a report gap beside the review's #7465–#7471). Three findings for the static spellings that exist today: **`new Child(scoped this)` is rejected by r35** ("captures of the function value `this` cannot be verified": the class-typed `scoped` arm is unimplemented — k1e); **`Weak<T>.TryUpgrade()` has the wrong shape on r35** (returns `bool`, not `owned Shared<T>?` — k2b), so the only safe spelling of kind 2 does not compile; **the `scoped` freeze does work for kind 3** (k3c rejects `c.Dispose()` under the live holder at compile time). And one spec/compiler question: **a child's destructor reading its owner during the owner's cascade faults on r35** (k1a: `DisposedAccessException` after "owner body"), although v0.334's text says checked mode faults from logical disposal's *completion*; the kind-1 structural proof cannot be stated without settling this.
4. **The model** (MEASURED, `model/`; bzcore L1 + four holder statements, 42/42 selftest). Derived retention for a constructor storing its parameter is sound at every bound tried (0 newly accepted, 0 newly unsound), rejects 0.4 % / 1.2 % of accepted programs (len 4 / len 5), of which a third fault on every execution and the rest are dead stale holders (a holder whose source was overwritten or disposed and never read again — the same class as K5.1/K5.2's over-rejection, since the holder *is* a stale borrow), and it closes every cross-domain race of the kind-3 shape (`var b := new K(a); Domain.Spawn(W, move a); b.Show()` — 6 and 318 accepted racing programs at the baseline, a K4.3 residual today). The owner-outlives rule is sound **only with the move-out clause**: freezing the move-out is a 96 % over-rejection; re-sourcing the moved-out child to its owner (so kind 1 degrades into kind 3 at the move) changes no verdict at len 4 and rejects 138 programs at len 5 (24 fault on every run, 114 are dead stale back-pointers), 0 unsound, and closes the 6 cross-domain back-pointer races (`new a / link a / fmove b a / send a / puse b`).

**Recommendation and order.**

1. **Do not add a new annotation.** The boundary marker the kind-4 option asks for is the class-typed `scoped` parameter already in the spec (§28.14, v0.331+); its gradual posture ("unmarked stays trust and reported") is exactly today's rule. What is missing is its *implementation* on r35 (k1e) and its reach: it bounds only `using var`/`this`-rooted call sites, so a plain-`var` holder or a holder that is moved on stays trust. Spend the effort there first: implement the class-typed `scoped` arm (the `this` form included) and the report gaps, and measure adoption.
2. **Kind 3 is the one kind worth a mechanism, and derived retention is the mechanism** — with the interface carriage 0132 §6 could not probe and the v0.350 rules now make tractable: a per-parameter `retains` bit computed at the callee's single check (0105's fact-discharged class), carried in §2.8.2 metadata, consumed only to *extend the caller's existing K5/0205 analysis* to the holder (not a new warning). The model's numbers are the evidence 0132 §7 asked for; its bar items (a filed caller-side defect; the 10 : 1 count; a §9.7 carve ruling) are met or measurable. What it newly rejects is small and of the same character as K5.3-b's rejections, which the owner accepted in 0205. It does **not** reach kind 4 (interface and virtual calls, function values, other artifacts without metadata), by construction — there `scoped` stays the spelling and the report stays the audit.
3. **Kind 1 does not need a language rule**: in the corpora it is rare, the structural proof has two holes (move-out; the destructor window) that each need a ruling before the proof is true, and the sharp form of the proof *is* derived retention applied at the move. Record it as a report-silencing refinement to consider after 2, not before.
4. **Kind 2 is a stdlib question, not a kernel one**: a read-checked weak reference over an ordinary owned object is safe in every mode but costs a retained header (or a side table) per *observed* object for as long as any observer exists — the same machinery #4602's bounded retention is building for checked mode (its "escaped" bit and hazardous-alias count are a weak count in all but name). Design it as `Weak<T>` minted from an *owned local or field* (not only from `Shared<T>`), with header retention keyed on a per-object `observed` bit; see §6 for the per-object and per-read costs and the unchecked-build consequence (an observed object keeps its header in unchecked builds too — the only sound way). Decline the generation-word and side-table variants on cost and on the no-GC commitment respectively.
5. **Strict mode** (per-module: every remaining K4.3 admission an error unless `scoped`) is cheap and consistent with the report's zero-report claim; add it when the report is complete (#7465–#7471), since a strict mode over an incomplete report is a false guarantee. Checker Framework's and `#![forbid(unsafe_code)]`'s precedent is exactly this: opt-in, module-granular, over a complete classification.

No proposal draft is attached: derived retention needs the implementation probe 0132 §6 names (one pass to collect, one record to carry) before it is "clearly ready", and the kind-1 and kind-2 options each wait on a ruling (k1a; the retention model). The paste-ready evidence blocks for a future 0132 successor are in §4.

## 1. Method

**Corpora.** (a) `tests/conformance/rules/cases` (3,693 files + 107 multi-unit case directories = 3,800 units; the `//! expect:` header gives the spec's verdict); (b) the docs: every fenced `bezel` block of the twelve documents, extracted with `scripts/extract_doc_examples.py --repo-root` on an exported copy (`work/export`; 802 blocks: 553 fragments, 8 programs, 114 skipped, 67 chained with earlier blocks; the manifest class gives the tier); (c) `tests/lit/**/*.bzl` (2,562 programs; a `%not` in the RUN line marks an expected rejection); (d) every raw-string literal in `tests/**/*.cpp` that contains a Bezel declaration keyword (189 files; the strings of one file are concatenated into one unit because gtest programs are split into prelude/body fragments, so a file's variants of one class are counted once in the "distinct sites" figure and separately in the raw figure).

**Scanner** (`data/bzlex.py`, `data/scan_trust.py`). A coarse lexer and declaration splitter (classes, members, parameter lists with modifiers, bodies), then, per body: parameter/primary/local/field provenance for every expression; the K4.3 store shapes — `_f := p`, `this._f := p`, `obj.P := p` (judged as the receiver's field store, §28.3 *Property stores*), a field initialiser or a body reference capturing a primary-constructor parameter (§22.10), `coll.Add/Insert/Push/Enqueue/AddFirst/AddLast/AddBefore/AddAfter/AddRange/TryAdd/GetOrAdd(…)` and `coll[i] := …` on a borrowing-family receiver or an `OwningDictionary` key, a comparer argument to a hash collection's constructor, `Task.FireAndForget(…)`, a task stored into a field, a user `scoped` field, a form-3 `Subscription` store, and 0210's `var b := x.f; … move x.f …; … b …`. A hit is recorded only when the stored value is parameter-, `this`- or field-sourced (a local or `owned`-parameter source is the compiler's rejection, counted separately: 24) and the target is class- or interface-typed (declared types; records are excluded, their borrows being §9.7's statically rejected regime; a generic `T` holder is kept and its instantiation decides). The v0.350 silence for a parameter or `this` stored into a purely local collection is marked in `notes`.

**Kind classification.** For each hit the scanner finds the storing member's call sites in the unit and classifies the argument bound to the stored parameter at each: `this` held in the caller's `owned` field/owning collection → **1**; a local/`using var`/temporary source with a local or temporary holder → **3**; a source or holder that escapes (returned, stored in a field/collection, a parameter-owned receiver, a path through a parameter) → **2**; a source of unknown provenance (a call result, a forwarded `scoped`) or a member reached only by dispatch with no call site → **4**; a value or `null` argument → **V** (no borrow at that instantiation); a static source → **N** (always-live, no trust). A plain parameter of the caller is followed upward (the virality count); a hit's kind is the most demanding over its sites (1 < 3 < 2 < 4). **Precision:** 24 random accepted-tier hits were read by hand (`work/` transcript): every one is a genuine store of a parameter/`this`/field borrow; two systematic false positives were found and fixed (record declarations; the invalid `p: owned R` spelling); the remaining known imprecision is the **U** bucket (no in-unit call site), which is a limit of the corpora, not of the classifier. Two kind labels were corrected by hand after the first pass (a static source is not kind 1; a field of `this` stored into a *parameter's* property is kind 2).

**Model.** `model/bzcore_trust.py` is `bzcore.py` (spec pin v0.345, unchanged rules) plus four statements over a third class `K` (a holder with one plain field) and a back-pointer cell on `Q`: `newk x y` (`var x := new K(y)`: the callee stores its plain parameter), `kuse x` (a member access through the stored borrow), `link x` (`x.f.Attach(x)`: the owned child points back at its owner), `puse y` (a member access through the back-pointer); three rule knobs: `derived_retention` (the holder carries `y`'s sources: K5's freeze and 0205's holder rule see it), `freeze_linked_fmove` (the naive owner-outlives rule), `linked_fmove_carries` (the sharp one: a moved-out child carries its owner). A `RACE` reached through `kuse`/`puse` is labelled `K4.3-trust-residual`, the recorded clause, not a violation. Feature set `trust` = locals + fields + holders; bounds vars 3 / len 4 (63,702 programs), vars 3 / len 5 (1,407,726) and vars 2 / len 4 with a branch (52,688). Selftest 42/42 unchanged.

**Probes.** `probes/k*.bzl`, `probes/run_all.sh`: each program compiled by r35 under `--checked-disposal --report-trust-admissions`, `--checked-disposal` and `--unchecked-disposal`, run, binaries deleted; `probes/results.md` is the transcript.

## 2. The kinds, with the subtleties the brief asked about

### Kind 1 — back-pointers to the owner

*Claim to prove:* "an owner outlives what it holds in its owned fields", so a child's borrow of its owner needs no trust. Clarke's owners-as-dominators (PRIOR ART: Clarke, Potter & Noble 1998; every path to an object passes through its owner) gives the *reachability* half; Bezel needs the *lifetime* half, and its ownership is affine and movable, which ownership types are not.

- **Destructor order** (§28.4, v0.350: body, then owned fields in reverse declaration order, then base). A child's destructor runs during the owner's step 2, so it reads an owner whose destructor body has already run — a *semantic* hazard (the resource the body released is gone), not a memory one; and whether it is a *checked-mode fault* is what k1a measures: on r35 it is (`DisposedAccessException` after "owner body"), although v0.334's text (rationale §5.28 *Explicit disposal marks; the holder frees*: "checked mode faults from logical disposal's completion: the disposal's own accesses run on a live instance") reads as if the cascade's accesses are the disposal's own. Either the text means only the receiver's own members (then a back-pointer read in a destructor is a defined fault and the proof must exclude destructors) or r35 sets the flag too early (then it is a compiler defect). **This needs a ruling before any structural admission is written.**
- **A child moved out** (`move _child with …`, `move _child!`, `PopLast()`, `PopAt`, `Drain()`): k1b/k1c fault in checked mode and read freed memory unchecked; the proof is false from the move on. The model shows the two ways to close it: freezing the move-out of a linked child (naive) rejects 306 programs at len 4 of which 294 never read the back-pointer — unusable; re-sourcing the taker to the owner (sharp) rejects nothing at len 4 and 138 programs at len 5, every one a moved-out child whose owner is then killed or sent (24 fault on every run, 114 never read the pointer), with 0 newly accepted and 0 unsound. The sharp rule is derived retention applied at the slot kill by move: the moved-out child is a kind-3 holder whose carried source is its former owner.
- **Owning collections** behave like owned fields for slot-held children and like the move-out for `Pop*`/`Drain()`; a borrowing-collection "child" is not owned at all (kind 2).
- **`Shared<T>` owners.** A child holding `s.Get()`'s borrow is bounded by *that handle*, not by the value (§28.13); another handle may be the last one to die, so a child stored into the shared value and holding the handle's borrow is kind 2, not kind 1. A child holding a *clone* is a cycle (leaks; §28.13).
- **Cross-domain sends.** A sendable owner moved to another domain takes its owned children with it (§30.14); a child moved out beforehand and left behind is the kind-3 race the model counts (the domain clause); an owner with a plain back-pointer field is not sendable in the first place (§30.14 rule 2), which closes the send side structurally.
- **Non-immediate ancestors** (k1d): the leaf's store is one admission; every intermediate link is an `owned` field, so the proof composes — but only as long as *every* link stays slot-held, which multiplies the move-out hole by the depth.
- **Siblings** (a field of `this` stored into another field of `this`: 2 sites): sound only by declaration order (the later-declared field is disposed first), a condition the structural rule would have to state.

**Verdict:** the structural proof is real but conditional on (i) the destructor-window ruling, (ii) no move-out or the sharp re-sourcing, (iii) declaration order for siblings. In the corpora it would silence 1 report line. Its honest form is "kind 1 = kind 3 whose source happens to be `this`", which derived retention already covers once a `new Child(this)` result is stored into an owned field of `this` — the caller's K5 then sees `this`'s own disposal order, which is the cascade's. Record, do not pursue first.

### Kind 2 — long-lived non-owning references

The registry/observer/cache/logger shape: 8 resolved sites, 6 more registry-shaped fragments. The holder outlives the method that stored the borrow, and nothing body-local bounds it; derived retention cannot help (0132 §1 excludes collection stores and non-`this` holders for this reason), `scoped` bounds only a `using var`/`this` holder, and the owning family changes who disposes. The safe spelling today is `Shared<T>` + `Weak<T>` (k2b), which converts *every* registered item into a shared object (a count, a control block, `Get()` at every use) and does not compile on r35. A weak reference over an ordinary owned object — read as nullable, liveness checked at the read — is the one treatment that is safe in every build mode without touching the kernel's single-owner rule; its cost is the retention design question of §6.

### Kind 3 — short-lived helpers

21 of the 32 resolved sites. The holder is a `using var`/`var`/temporary in the same body as the source, or a holder returned to the body that owns the source (`Bank.Open(c)`). The hazard is certain and body-local *once the caller can see that the callee kept the parameter*: k3a/k3b/k3d fault on every run; derived retention turns k3a into 0205's dominated-use error, k3b into K5.1's frozen transfer and k3d into the same through the forwarding factories' carried bits. The remaining question of 0132 — interface carriage and drift — is §4.

### Kind 4 — unknown bodies

Interface/virtual dispatch (k4a; `s9_7_0026`), function values (k4b), callees in artifacts compiled without metadata. No fact can be derived; the caller sees a signature. The spec's answer exists: a class-typed `scoped` parameter *is* the `kept`-style marker (gradual, contextual keyword, unmarked stays trust and reported), an interface member may declare it, and §28.14's forwarding rule carries it along a chain of `scoped` parameters. What it lacks is reach (plain-`var` holders, holders moved on, holders stored in fields are "no bounding object" sites and admit nothing) and, on r35, an implementation.

### The remaining clauses

Frame-held (3 sites), comparer-held (2), §28.14 residuals (13) and the 0210 shape (1) are kinds of their own: a frame's bound is settlement (await it; `TaskScope`), a comparer's is the collection's life, the residuals are quiescence and registration lifetime; none is a store a weak reference or a retention bit would retire, and the brief's four kinds do not reach them. They stay reported.

## 3. The single-annotation alternative: virality

Rule: every parameter the callee stores, and every parameter a caller forwards into such a parameter, carries `kept` (here: `scoped`). MEASURED over the 199 hits that store a parameter: 180 need the marker on **one** signature (the storing constructor/method), 19 on **two** (a forwarding factory or wrapper — `Util.Depth(x) → new Pair(p)`, `Client.Run(p) → Keep.Put(p)`), none on three or more; 6 of the 19 chains end at a method with no in-unit caller (a library-shaped unit), where the marker would also have to reach the artifact interface. The DI-shaped programs the brief names (composition roots forwarding dependencies through several constructors) do not occur in the corpora, which are one-screen test programs; probe k3d constructs the three-signature case, and a composition root wiring *n* services through *m* factory layers needs the marker on every one of the *n·m* forwarding parameters, which is the shape Rust lifetime parameters take. The honest comparison: `scoped`-everywhere costs one keyword per retaining signature and freezes the source at every admitted call site (k3c), while derived retention costs nothing in source and gives the same K5 verdict at the same sites — but only within an artifact closure that carries the bit, and never through dispatch.

Reading. (1) Derived retention is a pure narrowing: nothing new compiles, nothing new is unsound, and the newly rejected set splits the way K5.3-b's did (every-run faults plus dead stale holders), which is the shape the owner accepted for 0205. (2) The over-rejections are not spurious in the way the naive owner-outlives rule's are: each is a holder that *does* hold a disposed object, merely never read through — exactly what K5.1/K5.2 reject for a local borrow today. ## 6. The weak-reference runtime: three designs for kind 2

The requirement: a `Weak<T>` minted from an ordinary owned object; `TryUpgrade()`/`Get()` yields null once the object is disposed; safe in *both* build modes. So the liveness of a disposed object must be readable while any observer exists — in an unchecked build too, which today frees the block at the release point. Three designs (PRIOR ART noted where it applies):

| design | per object | per weak read | checked vs unchecked | interaction with #4602 |
|---|---|---|---|---|
| **A. header retention with a weak count** (the #4602 shape; Swift's side-table-less weak refs before 4.x; ObjC weak tables are design C) | one `observed` bit in the header for every object (free when unobserved); for an observed object: a weak count (one word) and the header word kept after disposal until the count reaches zero (the payload is freed at disposal, as #4602 already frees it) | one load (the flag) + one compare; `Downgrade`/weak-dispose touch the count | identical in both modes: an observed object retains its header in an unchecked build too — the only sound way; an unobserved object costs nothing in either | it **is** #4602's bounded-retention mechanism ("effectively a weak count for the borrows the static rules could not bound", issue comment 2026-10-13) with the count made user-visible; the free-at-Dispose amendment stays (unobserved ⇒ free in full); the escape set gets one more populating site |
| **B. generation word** (Vale's generational references; PRIOR ART: Vale, 2021–) | one generation counter in every object header, bumped at reclamation; a weak reference is (address, generation) | one load + one compare of the generation at the remembered address | the address must never be reused for a *different* generation width — i.e. the allocator must keep the generation word at the address across reuse (Vale does this with size-class slabs); Bezel's allocator is the system allocator, so B needs an allocator of its own; in unchecked builds the member-entry flag test stays elided but every weak read still pays the compare | orthogonal to #4602's flag; two liveness mechanisms where one suffices |
| **C. side table** (ObjC/Swift weak tables; a hash from address to a liveness cell) | zero in the object; a table entry per observed object, removed at disposal | a hash lookup | both modes alike; the table is global mutable state, so domain-crossing objects need a synchronised table | heavier per read than A, and a table keyed by address inherits B's reuse problem unless entries are removed at disposal |

Costs in Bezel's terms. A: the header already holds the disposed flag; an `observed` bit fits beside it; the weak count is paid only by observed objects; a weak read is the same cost as the checked-mode member-entry test. The spec change is additive (`Weak<T>` gains a constructor from an owned binding or a `Downgrade()` on an owned local/field; K1.5's producers table gets one row; §28.13's "non-owning observer" sentence already describes it). What it must *not* do is extend the object's life (then it is `Shared`), and what it changes in unchecked builds is one sentence: an observed instance's header is retained until its last observer dies. Against §5.21's declines: this is not "refcounting arbitrary classes via an annotation" (no annotation; the object's lifetime is unchanged; only the observer pays), and not "compiler-inferred sharing" (every weak reference is minted explicitly). B is declined on the allocator requirement and the double mechanism; C on cost and global state. **Recommendation: A, as a stdlib design riding #4602's implementation, after #4602 lands.**

## 7. Prior art (PRIOR ART: from general knowledge; not re-verified here)

- **Go escape analysis / leak tags**: the compiler summarises per parameter whether it "leaks" to the heap or to the result, in the export data, so callers can stack-allocate; summaries are recomputed when bodies change and callers simply recompile. The precedent for derived retention's carriage: a body-derived per-parameter fact in the interface is routine when its only consumer is an *optimisation or an analysis*, not a contract users read. What Go does not do is reject programs on it — the lesson for kind 3 is to consume the bit inside an existing analysis (K5/0205), as recommended.
- **clang `[[clang::lifetimebound]]` and the C++ Lifetime profile** (Herb Sutter / Gábor Horváth): a parameter annotation meaning "the result may refer to this argument", checked at call sites against temporaries and locals; the profile also *infers* it for common signatures (getters, `std::string_view` constructors). Lesson for kind 4: the annotation is declared at the boundary, inferred where the body is visible — the same split as `scoped` + derived retention; and its diagnostics are warnings in a gradual tool, which is what the report mode is.
- **Checker Framework Resource Leak Checker** (`@Owning`/`@NotOwning`/`@MustCall`): ownership of must-close resources via parameter and field annotations, with inference tooling that writes the annotations in; strict by module (a checked compilation fails on unannotated leaks). Lesson for the strict mode: opt-in per compilation unit, over a complete annotation set, with an inference tool that proposes `@Owning` — the analogue of a `--report-trust-admissions` run proposing `scoped`.
- **Ownership types / owners-as-dominators** (Clarke, Potter, Noble; Boyapati; Dietl & Müller's Universes): a child's references to its owner and siblings are the sanctioned ones ("inward" and "sibling" references); the invariant is about reachability and encapsulation, and it is *static and immovable*: objects do not change owner. Lesson for kind 1: the proof is cheap only where ownership is fixed; Bezel's `move` is the hole.
- **Swift `weak`/`unowned`**: `weak` is the read-checked nullable observer (design A/C); `unowned` is the unchecked back-pointer that traps on a stale read — Swift's own answer to kind 1 is *not* a structural proof but a trap, i.e. Bezel's K4.1 posture; `unowned(unsafe)` is the unchecked build.
- **Rust `Weak<T>`/lifetimes**: `Weak` only over `Rc`/`Arc` (Bezel's current position); lifetimes are the viral single-annotation alternative, with elision rules that remove most of the virality for the one-parameter case — which is also what the corpus measurement found: 90 % of sites need the marker in one place, and elision-style defaults ("a constructor that stores its only class-typed parameter") would cover them without inference.
- **Vale generational references**: design B; soundness through an allocator that never recycles a generation slot; the per-read cost is accepted as the price of no GC and no borrow checker.
- **Pony reference capabilities** (`iso`, `trn`, `ref`, `val`, `box`, `tag`): sendability and aliasing as six capabilities on every reference; `tag` is the opaque identity an actor may hold without reading — the kind-2 observer with *no* read at all. Lesson: the cheapest kind-2 reference is one that cannot dereference (a `SlotHandle` key, stdlib §4.21), which Bezel already has for owning slot maps.

## 9. Self-critique

- The kind table rests on 32 resolvable sites out of 203 hits: the corpora are one-screen test programs, so kind 3 is over-represented by construction and kinds 1/2 under-represented; the unresolved fragments' names are a weak proxy. A sweep over a real service codebase does not exist because no external users exist.
- The scanner is syntactic: it resolves declared types within one unit, assumes an unknown type name is a class, and reads property stores through a parameter as field stores; it does not see `AddRange` element types through interfaces, a store inside a lambda's nested statement reaches it only through the flat `;` split, and the gtest units concatenate variants of one program (hence the "distinct sites" figure). Its precision was checked on a 24-hit random sample, not exhaustively.
- The model's holder is one shape (a constructor storing one parameter, read through one member); it has no calls, so interface carriage, drift and separate compilation — the questions 0132 could not settle and that decide kind 4 — are outside it, and "never faults" counts programs that create a stale holder and never read through it.
- The r35 findings (k1a's cascade fault, k1e's rejection, k2b's `TryUpgrade` shape, k2a's silent store) were not de-duplicated against the live tracker beyond the review's issue list (#7465–#7471, #6775, #4604–#4605); the coordinator should run the five-source check before filing any of them.
- The runtime cost table is reasoning, not measurement: no runtime was modified or benchmarked; the per-read cost of design A is asserted equal to the member-entry flag test by construction, not timed.
- The virality figure counts in-unit forwarding only; a chain that leaves the unit (6 of 19) is counted at its visible length.
