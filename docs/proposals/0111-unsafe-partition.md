## 0. Charter

One question: **"which lines in this program can break memory safety?"** Today it is answerable only by a reader already holding the whole unsafety vocabulary in their head, and greppable only if that vocabulary is written down. It is written down nowhere. This proposal writes it down (this proposal's §2, the normative core) and proposes one query answering the question from facts the front end already computes (this proposal's §3). Nothing is adopted; no program changes meaning. The list is the part that must be right — the query is only as good as its vocabulary's completeness.

---

## 1. The lesson and the gap

**1.1 Bezel already has the mechanism, in miniature.** 0106 §2.1's finding: Modula-3's contribution is a *graph discipline* — unsafety declared per unit, visible in the interface, propagated through imports — and Bezel already believes in the marker. Normatively, in the spec's own voice at §2.3:

> `System.Interop` — `Ptr<T>` and the `Interop` intrinsics (§32.12) — is deliberately **not** auto-imported: the `import System.Interop;` line is the audit marker that a file performs foreign-memory access.

Stdlib §10 repeats it in substance (*"which is *not* auto-imported — the `import System.Interop;` line is the audit marker that a file performs foreign-memory access"*) — a decision, not an accident: 0033 §13 q2 put the module home to the owner as "import-line-as-audit-marker", ratified at v0.186. And Bezel gets the quarantine with **no keyword**: rationale §5.15 declines that (*"the user-facing surface never exposes raw pointers, pointer arithmetic, or untyped memory access"*), and this proposal proposes none.

**1.2 What the miniature does not answer.** **(a) One bit, per file** — *some* foreign-memory access happens somewhere in this file; not which lines, members, or obligations. §32.10's obligations are per-declaration while its hazards are per-expression (0106 §4.3's granularity finding), and §32.10 says so itself: a mid-call callback disposing storage whose address the call holds *"is a use-after-free no compile-time rule can see"*. **(b) It covers a minority of the vocabulary** — of the eighteen named members in this proposal's §2, **eight need no FFI-marking import on their homes alone**: `IntPtr`/`UIntPtr`, `CString`, `WString`, `RawBytes` are in `System`, auto-imported (§2.3), and `FromCStringPointer`/`FromWStringPointer` are members of `string`. A **ninth** — `DangerousPointer()` (D1) — is marker-free only under the disputed §2.8.3 rule 2 reading, so the count is nine or eight depending on how the coordinator's issue rules. *That contingency argues for tier 1, not against it:* a query keyed on resolved callees reports D1 either way, while the marker-grep's coverage moves with the ruling. **(c) Nothing reaches the interface** — §2.8.2 clause 1's carriage list has no unsafety row, so a consumer holding an artifact cannot tell whether the module it links declares `extern` blocks. That is tier 2's, named to mark where tier 1 stops.

*Why it matters* (0106 §2.1, re-verified): §28.3's exactly-once guarantee is voided anywhere in a program's closure that `extern` or `Ptr<T>` appears, and whoever assembles a program from many artifacts has no supported way to enumerate where. Every other trust boundary is legible — `owned`, `pure`, contract tiers, `sendable`. Unsafety is the one that is not.

## 2. The unsafety vocabulary ▲ — the normative core

Every row is a site a program can write, whose authority is a spec or stdlib sentence attaching a §32.10 obligation or stating undefined behavior, verified against v0.262 at `8a03dd2`. The last column decides whether the existing marker finds it.

**Band G — reported, not memory-unsafety** (separated so the primary answer stays honest): `Interop.LastErrno()` (stdlib §10.6, §32.9 — a *window* discipline, *"never across an `await`"*: a correctness hazard that cannot corrupt memory), and the `import System.Interop;` line itself (§2.3 — a file fact the query cross-checks against the sites, never relies on to find them).

**Totals: nineteen surfaces** — **eighteen named members** (counting E3's two spellings separately, and excluding band G's `LastErrno`) plus **one implicit handoff** (B5) — carried by **two language forms** (`extern` declarations; extern call sites, with five per-argument tags) and one signature-position fact (A2), across six memory-safety bands and one secondary band.

**2.1 Excluded, with reasons.** `Zero` and `=`/`<>` on `Ptr<T>`/`IntPtr`: no dereference, and `Zero` is the null test §32.12's own example demands. `ToIntPtr()`/`long(ptr)`: the unforging direction — *"no operations dereference"* an `IntPtr` (§32.7) — and its dangerous consumers (C1, E2) are rows already. The C-compatible property (§32.13): computed for every record, a *representation* promise, not an obligation. `string.From(CString/WString)`: the instance's validity was fixed at its producing site, already a row — borderline, recorded. `RawBytes.CopyTo` on a `FromForeign` view: the foreign-ness is E1's fact — **0106 §4.3's granularity finding in miniature**; marking the producer, not every downstream consumer, is the deliberate choice. Spans/`AsSpan`: bounds-checked, no address escapes.

**2.2 The completeness argument.** Three independent enumerations of this surface exist, agreeing modulo three named deltas. **(1) Appendix C.9** — **thirteen** bullets, mostly *rejections* and the rest well-formedness *requirements* (`RawBytes`'s two C slots, `env` pairing, `extern` methods only inside `extern` blocks): either way it is this list's complement — what the compiler refuses or demands — and everything C.9 then admits under trust is a row here. **(2) Appendix D.2's FFI row** — the conformance feature's own inventory, naming `Ptr<T>` and `Interop`, `RawBytes.FromForeign`, `CString`/`WString.Pointer`, `OwningBuffer<T>.DangerousPointer`: bands C, D, E1, F **almost** exactly. *Delta (i):* the §32.7 forging conversion (E3) is declared in a **Core** stdlib section (§10.0, on a §2.3 auto-imported type, unlisted in D.2) but specified only inside D.2's *"§32 entire"* Extended column, and D.3's closing bullet — *"A Core implementation's standard library omits the types of unimplemented Extended features entirely"* — rules on *types*, not on a member whose type is Core. *Delta (ii):* stdlib §10.4's pointer readers (E2) are named nowhere in D.2 at all, so under *"Everything not listed is **Core**"* they are Core. *Delta (iii):* the row names `CString`/`WString.Pointer` but **not `RawBytes.Pointer`**, while its section pointer spans stdlib §10.1–§10.3 — two readings, and they disagree on whether one address accessor is Core. **(3) §32.12 rule 9**, tightest because it enumerates the address space: *"The only addresses in the language are buffer interiors (the stdlib accessors …), foreign values (`Ptr<T>`/`IntPtr` received from native code), and code (`Interop.CodeAddress`)."* The vocabulary is that enumeration's closure under operations producing or consuming one — a closure that must include **implicit** producers, which is exactly what B5 is and what an accessor-only reading of rule 9 misses. *Rule 9's own limit:* it covers addresses the language *exposes*, so E3 is no counterexample (no object address is produced) — but a forged `IntPtr` reaches E2, so rule 9 alone is not a sufficient basis for the list.

**Closed, and how it grows.** Closed because a row must carry a §32.10 obligation or a stdlib-stated UB sentence, and both live in two places — §32 and stdlib §10, plus §4.14's one accessor. It grows **only with FFI revisions**, and §32.14 names the future rows already: `FnPtr<F>` (*"the single most dangerous primitive in this space (it executes, not merely corrupts)"*), export-to-native, `ForeignHandle<T>`, runtime library loading, by-value structs, inline arrays of C-compatible records, call-site varargs, foreign-thread registration — eight, each with its blockers written down, which is what makes this proposal's §5 ratchet a one-line obligation rather than a research problem.

## 3. The design ▲ — one query, no language change

**3.1 Where it lives — recommendation: the primitive in 0052, the aggregator named in 0040.** The query needs a resolved AST for one compilation and nothing more, which is what 0052's `--check` mode produces and where 0052 §2.8 puts its queries; but the *audit* question is program-wide, and only the build tool holds the closure (§2.8.3 rule 1: *"The build supplies the transitive closure"*). Hence **▲ `bezelc --check … --query foreign-obligations`** — 0106 §4.3's own name, kept; whole-unit rather than position-keyed, on 0052 §2.8's precedent for `--query registry` (*"needs no input file"*), riding the same JSON document's `queries` array, with no new binary, mode, or output format — plus **▲ `bezel audit`, 0040 Stage 1**, the rollup over the graph the driver already condenses (0040 §3 Stage 0), reported per artifact: named, not designed. The keyword decline is restated, not reopened: **no `unsafe` keyword in any form** (rationale §5.15; 0106 §4.3 — *"Do not write this up as 'Bezel should reconsider `unsafe`.'"*). No new grammar, modifier, visibility level, or severity.

**3.2 What it reports** (details deliberately implementation-defined, per Appendix D and §2.6): **machine-readable** — per compilation a module rollup (`module`, `declares_extern`, `exports_foreign_signatures`, per-band counts, band G's file facts) and under it one record per site (`member`, `band` tag from this proposal's §2, `site` span, `authority` §, one-line `obligation`, plus band B's per-argument tags) — and a **human summary**, one line per member with a per-module count. The honesty rule is 0052 §2.8's, **extended not quoted**: 0052 writes *"v1 serializes what the ownership pass already computes"* and adds no analysis; this query reads resolved declarations and callees rather than ownership state, so the same rule is applied one pass wider — *v1 serializes what the front end already computes and adds no analysis*. Two points are not latitude: it keys on **resolved callee symbols, never on import lines** (this proposal's §4), and it has **no effect on the build** — it answers, never rejects (an exit-code mode is CI policy, out of scope).

**3.3 The staging argument.** The per-module rollup **is the fact tier 2 would declare.** Tier 2 is a module-header fact ▲, a §2.8.2 clause 1 carriage row ▲, and a safe-may-not-import-unsafe rule ▲; the first two are *carriage of a value*, and this query computes the value. Designing the query first costs tier 2 nothing and buys two things: the fact is defined and field-tested before being frozen into an interface format — cheap now under §2.8.5's recompile-the-world model, expensive after a first external consumer — and "does this module perform foreign access?" gets one definition rather than two. Tier 2 then adds carriage and a rule, not a computation.

## 4. What this deliberately does not do

**No propagation, no partition:** no import rule, no safe/unsafe module split, no transitive unsafety property, no §3.6 row, no §2.8.2 carriage row. That is tier 2, and 0106 §2.1's verdict — *"tier 2 is not obviously worth it before external users"* — stands. **No process obligations:** no CLAUDE.md change, lane rule, gate step, or review checklist; the one process line named in this proposal's §5 is offered, not drafted. **Not a data-flow analysis:** which extern call an address reaches, whether a `Ptr<T>` crosses a domain boundary (§32.10's last bullet and §32.12 r8 make that a hazard, but a flow fact), and downstream reads of a `FromForeign` view are out of v1 as recorded limits. The query is per **site** — finer than §32.10's per-declaration obligations, coarser than taint; 0106 §4.3's granularity finding is why that middle level is the right first one.

**The §2.8.3 rule 2 hole is orthogonal — and is why tier 1 is worth having while the issue is open.** The defect candidate (0106 §2.1(b)) is that rule 2 — *"A file that imports module `A` may freely **use** values of any public type reachable through `A`'s public surface … call their public members"* — appears to make `var p := buf.DangerousPointer(); var v := p.Load();` a complete foreign-memory access in a file with no `import System.Interop;`. **It is being filed as an issue by the coordinator and is not resolved here.** The query is correct either way, because it keys on the resolved callee: `DangerousPointer` and `Load` are rows D1 and C2 whether or not the file spells the import, and closing the reading with a clause would not change the answer by one row. Two verification deltas for whoever rules it, recorded not acted on: **(i) 0106 §2.1's auto-import premise does not hold** — it calls the producer *"declared in `System.Collections.Generic`, which *is* auto-imported"*, but §2.3 auto-imports only `System` and `System.Text` (*"All other library modules require explicit `import`"*) and stdlib §4's intro says *"None are auto-imported except the iteration-interface family"*. This is **not a lane reading**: committed proposal **0025** states the same correction in its own words — *"`System.Collections.Generic` is **not** auto-imported — spec §2.3 auto-imports only `System` and `System.Text`, and stdlib §4 states …"* (its "Why §4, not a new module" note). The hole rests on rule 2's use-without-naming half alone; an issue resting on the premise would be refutable on a bad ground. **(ii) It is a document *conflict*, not a silence** — stdlib §4.14's `DangerousPointer()` declaration carries the comment *"The result type lives in System.Interop (import required at the use site)"* (a two-line comment continuation immediately above the declaration, stdlib §4.14's value-typed-`T` block), an assertion rule 2 appears to override, since `var p := buf.DangerousPointer();` spells no name and rule 2 classes an inferred instantiation as **use**.

## 5. Costs

**Compiler: a read-only pass over resolved ASTs.** The facts exist — `ast::ExternBlock`/`ast::ExternDecl` are their own nodes with a per-declaration `SourceLocation` (`src/ast/Node.hpp`), `ast::SourceFile` carries the module declaration and import list, and member calls carry their resolved callee through sema. The pass adds no analysis and runs after type-checking, so it can affect no diagnostic. **Implementation status, honestly:** at `8a03dd2` `System.Interop` appears nowhere under `src/` — only in `tests/conformance/` (the spec-derived `cases/` plus `test_conformance.py` itself) — so bands C and F land when the `Ptr<T>` surface lands, while A, B, D, E are implementable today. A free self-check comes with it: a row naming a member the front end cannot resolve fails the query loudly instead of silently under-reporting.

**Docs: where the list lives.** Three homes: **(a)** the spec, Appendix C-adjacent — the vocabulary is C.9's complement, but landing it there makes it normative surface amended in lockstep with every FFI revision, buying cross-implementation agreement no second implementation needs; **(b)** a stdlib §10 note pointing at the tool's list — cheap, but a tooling index inside a normative document; **(c)** this proposal plus the tool's registry (0052 §2.2's precedent, under Appendix D's latitude). **Recommended: (c) now, (a) as the graduation target** if a second implementation materializes — under (c) the list costs zero normative surface and matches 0105's landing shape, which 0106 §10 cites as the model for exactly this item.

**Maintenance — the ratchet ▲.** A vocabulary silently falling behind an FFI revision is worse than none, because the answer still looks complete. One line, home `spec-change-process.md` §5's Migration-note requirement: **▲ any revision adding FFI surface names the vocabulary rows it adds.** Named, not drafted — that document is process, not spec, and 0106 §4.2/§4.4 propose two other lines in the same place, so if any land they should land together.

## 7. Questions for the owner

- **Q1 — The query's home.** Recommended: the primitive as `bezelc --check --query foreign-obligations` in 0052, with `bezel audit` as 0040's Stage-1 aggregator. The alternative — wholly in 0040, keeping `bezelc` out of the audit business — costs the build tool a way to ask the front end the question anyway, which is 0052's `--query` under another name.
- **Q2 — The vocabulary list's home.** Recommended: **tooling-defined**, with Appendix C-adjacent material as the graduation target on a second implementation. Asked explicitly because the opposite is defensible: only a *normative* list can hold an implementation to it, and it is the owner's call whether completeness-pressure or amendment-cost dominates before external users exist.
- **Q3 — The ratchet line** (this proposal's §5): draft the one-line `spec-change-process.md` §5 obligation now, landing with 0106 §4.2/§4.4's two lines in one edit?
- **Q4 — Where the conformance-partition question goes (issue-shaped, CLAUDE.md rule 1).** Appendix D.2 partitions the FFI surface by *feature*, but three of this proposal's vocabulary rows sit across the seam rather than inside it, and D.2/D.3 do not resolve them. **(a) A member whose type is Core and whose specification is Extended:** `IntPtr(longValue)` is declared in stdlib §10.0 — a Core section, on a §2.3 auto-imported type, unlisted in D.2 — and specified *only* in §32.7, inside D.2's *"§32 entire"* column (§5.2 supplies the cast syntax and never names `IntPtr`). D.1 obliges a Core implementation to reject a program using an unimplemented Extended feature, and D.3's closing bullet rules on *types* — *"A Core implementation's standard library omits the types of unimplemented Extended features entirely"* — so a member of a Core type has no stated answer. **(b) One accessor of three:** D.2's row names `CString`/`WString.Pointer` but not `RawBytes.Pointer`, while the parenthetical section pointer spans stdlib §10.1–§10.3; the member-list reading makes `RawBytes.Pointer` Core, the section reading makes it Extended. **(c) Why (b) is worth ruling, stated as a reading and not a claim:** under the member-list reading nothing in the composition `string.FromCStringPointer(RawBytes.From(bytes).Pointer)` is Extended — `RawBytes.From` (stdlib §10.3), `.Pointer`, and `FromCStringPointer` (stdlib §10.4) are all unlisted and therefore Core under *"Everything not listed is **Core**"* — and `RawBytes.From` *"allocates a fresh, owned `RawBytes` containing a copy of the source bytes"* with no terminator stated — the contrast is `CString.FromBytes`, which says it *"appends a null terminator"* — so the read is stdlib §10.4's undefined behavior (*"the read may continue past the intended end"*). Under the section reading the route closes at `.Pointer`. **Withdrawn from the earlier draft of this question:** the sharper-sounding `string.FromCStringPointer(IntPtr(n))` composition, which does *not* survive (a) — `IntPtr(n)` is §32.7 surface, so a Core-only implementation rejects it under D.1 and the program never exists. The residual question for the owner is only whether (a)–(c) travel as one conformance issue or are three.
- **Q5 — Two lane findings and an observation.** (i) The two corrections to 0106 §2.1's premise (this proposal's §4), one of them independently corroborated by committed proposal 0025 *[0025's passage was corrected at the 2026-09-17 currency sweep — `System.Collections.Generic` has been auto-imported since v0.289 (0122 L3); the corroboration is historical, see `proposals-currency-2026-09-17.md` §0]* — attach to the coordinator's rule-2 issue (#3278), or file separately? (ii) B5, the nineteenth surface: an ordinary `CString` argument hands out a Bezel-owned address, but §32.10's Bezel-owned-address bullet enumerates only the three accessors — is that enumeration meant to be exhaustive, or does the preceding in-flight-address bullet carry the implicit case? The query reports the call site either way (B1). (iii) Observation only: rationale §5.15's keyword decline is unaffected and restated here, but its premise (*"never exposes raw pointers …"*) narrowed at v0.186, when `Ptr<T>` landed as user-facing typed pointer access behind an import. Whether that paragraph wants a clause is a documents question, outside autonomous scope — recorded so the drift is not found later.
