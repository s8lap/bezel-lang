## 1. Design changes (each a genuine choice for the owner; ranked by cleanliness)

### L1 — Delete the `when` construct in both positions; `when` survives as the guard keyword and the `when true`/`when false` clause

**What.** §19.1 ([`S:4028`](../Bezel_Language_Spec.md#sec-forms)): "**`when` (condition dispatch)** — `when` followed by arms whose patterns are full boolean expressions. The arms are evaluated in textual order; the first whose expression is `true` is selected. This subsumes the `if`/`elif` chain. `when` takes no scrutinee." It exists as the expression atom `WhenExpr ::= "(" "when" WhenArm ("," WhenArm)* ","? ")"` (A.7, `S:11610`) and the statement `WhenStmt ::= "when" WhenArm ("," WhenArm)* ","? "end" "when"? ";"` (A.6, `S:11172`). Meanwhile [§20](../Bezel_Language_Spec.md#sec-the-if-expression) presents "Multi-way selection chains with `elif`, in the statement form's word order" (`S:4274`) and steers many-way selection to `case` (`S:4283`); §20's only mention of `when` is its precedence note ("exactly as the `case` and `when` atoms do", `S:4285`), never the guidance on which ladder to write. `WhenArm ::= (Expression | "_") "=>" ArmBody` admits no guard, so the construct is a pure boolean ladder: `(when c1 => a, c2 => b, _ => z)` ≡ `(if c1 then a elif c2 then b else z)`, and `when … end;` ≡ `if … elif … else … end;`.

**Why it is complexity.** Two grammar productions, their own arm and termination rules (§19.2, §19.7), a dedicated non-exhaustiveness sentence (§19.6, `S:4179`: "having no scrutinee it is never statically exhaustive"), a per-arm discard clause (§21.9, `S:4485`), a precedence-table note (§17.2, `S:3330`), a keyword-disambiguation sentence (§19.4, `S:4165`: "position disambiguates the two"), and a third role for the token `when`. Guide 03 line 50 has to teach a three-sentence rule — "a **two-way** pick on one condition is the conditional atom. A **ladder of conditions** is `(when …)`" — that first-class `elif` (proposal 0057, v0.208) made false. **The verifier added an irregularity the lane missed, in the same direction:** §21.7's *Compound statements carry no special grant* (`S:4471`) lets a callable end with an `if`/`elif`/`else` whose every branch exits, while §21.7 (`S:4469`) and §19.6 (`S:4190`) give a `when` construct **no** grant toward the every-exit-path rule — so a trailing `when … _ => return x, end;` does not discharge totality and its `if`/`elif`/`else` migration does. The construct is not merely a second spelling; it is the weaker of the two.

**Proposed shape.** Delete `WhenExpr`/`WhenStmt`, §19.1's `when` paragraphs, §19.6's `when` sentence, §19.4's disambiguation sentence, and the construct mentions in §17.2, §19.7, §21.9 and the §28.3 producers row (`S:6722`, which keys `case`/`when` identically to `if` — the meet rule is unchanged; the row loses one word). *Correction carried from V2:* Appendix C.7 has **no** construct entry — its only `when` (`S:12017`) is the guard, which stays. `when` remains a contextual keyword for arm guards (§19.4) and the `when true`/`when false` postcondition clause (§22.4; item L7 keeps it). Trace, Guide 03 lines 55–58: `var fee := (when amount > 10_000m => 0m, isPremium => 1m, _ => 2.50m);` → `var fee := (if amount > 10_000m then 0m elif isPremium then 1m else 2.50m);` — same type (§20's common-type left-fold, which §19's preamble already delegates to, `S:4000`), same evaluation order, same ownership meet.

**Record check.** Rationale §11.1 (`R:1287–1298`) argues `when` only against scrutinee-less `case` ("Forcing those into a scrutinee-having `case` would require gymnastics"); the v0.144 changelog (`C:5566`) records `when` being split *out of* `case` for layout reasons — both weigh `when` against `case`, never against `if`/`elif`. Proposal 0057 §2.3 is titled verbatim "**The when atom — same split, same analysis**": it re-spelled `when` in the train that introduced first-class `elif` without asking whether both ladders still earn their place. `D:210`, `D:211` (value-position conditional rivals) and `D:412` (de-`end`ing statement-position `case`/`when`) are adjacent and none covers `when`-vs-`elif`. Not a re-ask.

**Corpus accounting (process §6).** ⚠ The lane's and verifier's usage count — `grep -rl '(when$\|(when ' tests --include=*.cpp --include=*.bzl` → **31** files (24 outside `tests/parser`/`tests/lexer`) — reproduces but is **contaminated by C++ comment prose** (`(when the closure …`, `(when \`using var h\` …`): 16 of the 31 files contain no Bezel `when` at all. The honest recipe — `grep -rlE '\(when(\s*$|\s*//|\s+.*=>)'` — gives **15** files (10 outside parser/lexer), and **every one has a `_` arm**, so the `_`-less migration case below has no corpus instance. Statement form: **2** real sites (`tests/conformance/cases/codegen_0006.bzl:40`, `spec_0115.bzl:1`; three further `^\s*when\b` hits in `spec_0324.bzl` are prose). **`tests/conformance/`: 7 cases** to convert — expression form `codegen_0010`, `guide3_0001`, `spec_0026` (nested), `spec_0035`, `spec_0114`; statement form `codegen_0006`, `spec_0115`. `elif` in tests → **95** lines. Docs: **6** lines outside the spec (Guide 03 and the code-generation reference; the stdlib uses the construct nowhere). `src`: **4** files (`Parser_Exprs.cpp`, `Parser.hpp`, `Parser_Stmts.cpp`, `ownership/Ownership.cpp` — a real semantic arm, not parse-only).

**Migration.** *Newly rejected:* `(when …)` and `when … end;`. *Replacement, in real Bezel per Appendix A:* `(if c1 then a elif c2 then b else z)`; statement `if c1 then … elif c2 then … else … end;` (a `=> stmt;` single-statement arm becomes a one-statement block — the one terseness lost). A `when` expression **without** a `_` arm has runtime content the `if` form lacks — the no-match fault. ⚠ The lane's suggested `else throw new MatchFailureException()` **must not be written into the migration note**: `MatchFailureException` is in §31.4's taxonomy tree (`S:9365`) and the compiler resolves the name (`src/sema/TypeResolution_Names.cpp:137`), but `grep -n MatchFailureException docs/Bezel_Standard_Library.md` → **0** — the stdlib declares no such type, so it is not a user-writable spelling (an impl-ahead-of-doc delta in its own right; it goes to the review record's defects list, not here). An `_`-less form, if one ever appears, migrates to an `else` branch raising a declared exception (`InvalidOperationException`, `S:9360`) or is restructured; the corpus has none. *Doc-only:* Guide 03's three-sentence rule becomes two; `G` loses its `(when …)` rows.

**Change class:** design-change. **Kernel classification:** no contact (§28.3's producers row keys the meet identically; no K changes). **Body-locality:** not applicable (a removal). **Cost stated:** 15 test files, 7 conformance cases, two documents, four compiler files, a grammar edit in A.6 and A.7 — against a construct that is provably `if`/`elif` with a weaker totality story. **Confidence:** medium-high (V2: "the largest elegance win available").

### L2 — Delete `out owned var x`; plain `out var x` adopts the callee's announced classification

**What.** [§22.4](../Bezel_Language_Spec.md#sec-inline-out-declarations) (`S:4628`): "The accepted forms at the call site of an `out owned` parameter are `out using var x` (a scope-bound owned local) and `out owned var x` (an owned local with the standard owned-local discharge rules applying) … Plain `out var x` is **not** accepted at the call site of an `out owned` parameter — the resulting value's ownership would have nowhere to go." Yet §28.3's adoption clause (`S:6658`): "A LHS holding **no classified value** is not state-matched: there is no displaced obligation to drop and none to double-hold, so an RHS of either classification is admissible and the local **adopts** that classification." `var x := Factory();` adopts owned from the callee's declared `owned` return with no use-site marker; `out var x` at an `out owned` parameter is the same situation — a fresh local, a callee-declared owned production — and is the one place the language still demands a use-site `owned`.

**Why it is complexity.** It is the sole surviving use-site `owned` after v0.246 made `owned` "purely declarative"; K3.13 (`S:6549`) says "Fresh producers need no marker anywhere", and an `out owned` result is a fresh producer. The form costs two accepted call-site spellings plus a rejected one (§22.4), the compatibility-check paragraph in §22.6 (`S:4776`), the `out _` clause (`S:4778`), A.4's alternative, and the code-generation reference's rule at `G:474` — "At the call site it accepts **only** `out using var x` or `out owned var x`; plain `out var x` is rejected" — which trips writers precisely because it contradicts the `var x := Factory()` habit the same document teaches. **A gap V2 found that strengthens it:** §22.6 (`S:4776`) sanctions the *pre-declared* form ("disambiguate by pre-declaring a typed local and passing plain `out x`") but neither §22.4 nor §22.6 states what ownership state `x` takes when the parameter is `out owned` — the adoption question is already unanswered in the spec today; the current rule is under-specified, not merely redundant.

**Proposed shape.** §22.4: "`out var x` declares a fresh local that adopts the classification the callee's declaration announces — borrowed against a plain `out` parameter, owned against `out owned` (the adoption clause, §28.3); `out using var x` is the scope-bound owned form and is accepted only against `out owned`." The pre-declared `out x` form is given the same answer in the same sentence. Delete `out owned var` from §22.4, §22.6 (`S:4776`), A.4, and `G:474`. Trace, §22.6's own example (`S:4802`): `if pool.TryPopCached("primary", out using var c) then …` unchanged; a caller wanting a movable local writes `out var c` and `c` is an owned local under §28.3's discharge rules exactly as today's `out owned var c`. Resolution is untouched: §22.6 (`S:4778`) says "the pair itself is not declarable", so at any call site exactly one classification is announced by the resolved signature — the adoption clause's shape.

**Record check.** The rejection's ground dates from v0.93 (`C:2772`: "the resulting value's ownership would have nowhere to go"); the adoption clause landed at v0.270 (`C:8126`: "K1.7 + K3.11 for the adoption clause") and gives the value exactly somewhere to go. 0090 Q5 (`C:7436`) ruled that the form keeps the token `owned` rather than `move` — a spelling ruling, not an existence ruling. Rationale §5.27 (`R:939`) says the `out using var` form "survives", which this item keeps. `D` rows 55, 91, 129, 137 are the nearest (137 declines lifting `out owned` into overload resolution, untouched here); none reaches this form. **New evidence against the v0.93 reason:** the v0.270 adoption clause.

**Corpus accounting.** `grep -rn 'out owned var' tests --include=*.cpp --include=*.bzl` → **259** lines in **68** files; `out using var` → 146 / 42; plain `out var ` → 229. **`tests/conformance/`: 1 case** (`spec_0321.bzl`). `docs/*.md` → **18** lines. `src` → **152** lines across **18** files spanning parser, sema, ownership and codegen (V2 spot-read `sema/ExprTypecheck_Calls.cpp:1257,1400,1576,1703`). ⚠ *V2's correction, kept:* those 152 lines are **not** a net deletion — many are diagnostic strings, and the check does not disappear, it moves from "reject `out var` here" to "classify `out var` from the resolved parameter". Removal is a spelling deletion plus a classification re-key.

**Migration.** *Newly rejected:* `out owned var x`. *Newly defined:* `out var x` against `out owned` (adopts owned; must-use warning fires on an undischarged recipient as today); the pre-declared `out x` against `out owned`. *Replacement:* `out owned var x` → `out var x`, mechanical over 259 lines. *Doc-only:* `G:474`.

**Change class:** design-change. **Kernel classification:** derivation (K1.7 + K3.11 — one more instance of the adoption clause; the register is untouched). **Body-locality:** local. **Cost:** 68 test files of mechanical churn, one conformance case, a grammar alternative in A.4, an 18-file compiler re-key; the reader loses the visual "this recipient is owned" cue that `var x := Factory()` already lacks. **Confidence:** medium-high.

### L3 — Auto-import `System.Collections.Generic`; collapse §2.3's hand-enumerated rows into the module row

**What.** §2.3's always-available table hoists `Array<T>`, `OwningArray<T>` (`S:150`) and fourteen collection *interfaces* (`S:152`) out of `System.Collections.Generic` and then gates the rest: "All other library modules require explicit `import`." (`S:160`). `Dictionary<K,V>`, `Set<T>`, `LinkedList<T>`, `Queue<T>`, `Stack<T>` and their `Owning*` twins therefore require `import System.Collections.Generic;` on paper, and `G:611` instructs writers so: "`System.Collections.Generic` | **explicit** | the collections — *except* the iteration interfaces … which are auto".

**Why it is complexity — three measured facts, the v0.278 shape.** (1) *Unenforced:* `src/sema/TypeResolution_Names.cpp:130–135` — "the compiler does not yet enforce import-gating for that namespace (its sibling collection types Array/Dictionary/… all resolve without import here too)"; `KeyNotFoundException` resolves without import at `:136`. (2) *Unfollowed:* `grep -rlE '\b(Dictionary|Set|LinkedList|Queue|Stack|OwningDictionary|OwningSet)<' tests --include=*.bzl` → **84** files, of which `xargs grep -l 'import System.Collections.Generic'` → **4**; `grep -rl 'Dictionary<' tests --include=*.cpp` → **216** embedded programs; Guides 01–06 → **0** import lines each; widened to every stdlib §4 type → **168** `.bzl` files. **In the normative document itself:** `awk '/^```bezel/,/^```$/' docs/Bezel_Language_Spec.md` shows the spec's own fences naming these types **10** times against **2** imports. (3) *Unargued:* no decline exists (`grep -n -i 'auto-import' docs/proposals/DECLINED.md` → rows 102, 220, 370, 424, 439, none on point); proposals 0025 and 0111 restate the rule without arguing for it.

**Proposed shape.** Add `System.Collections.Generic` to §2.3's auto-imported module rows (beside `System`, `System.Text`, `System.Collections.Linq`); delete the hand-enumerated "Core types" (bar `Object`/`Type`) and "Iteration and collection interfaces" rows — they collapse into the module row as `System`'s already does; delete the "except…" clause at `G:611`. Every program that compiles today compiles unchanged (the gate never existed; no compiler code is added or deleted). Trace: §15.4's `using var ages: Dictionary<string, int> := ["alice": 30, …]` (`S:3007`) is well-formed as written — which is what the fence already assumes.

**The cost, at full strength (V1's correction, adopted).** The lane priced this as "one more module"; the relevant unit is *names*, and proposal 0117 priced its own auto-import in exactly those terms ("Cost: **two** new bare names", `0117:26`). Stdlib §4 adds roughly **twenty-two** — `LinkedList`, `OwningLinkedList`, `Dictionary`, `OwningDictionary`, `Set`, `OwningSet`, `Stack`, `OwningStack`, `Queue`, `OwningQueue`, `OwningBuffer`, `Span`, `ReadOnlySpan`, `ArraySpan`, `ReadOnlyArraySpan`, `IReadOnlySpan`, `SortedDictionary`, `SortedSet`, `FrozenArray`, `Counter`, `KeyNotFoundException`, and kin — into every file with, per rationale §2.3, no opt-out (`D:220` records the no-opt-out cost as deferred). The in-tree corpus already declares user types named `Counter`, `Span` and `SortedSet` (~15 test files); §2.2's rule absorbs every one ("A declaration in the *current module* shadows any same-named import"), so no existing program breaks — but §2.2's *two-imported-modules-export-the-same-name* ambiguity is a live new failure mode for any future user module exporting one of those names. An amendment states this the way 0117 §5 did, and it is the ground on which the owner may decline.

**The precedent, at its true width.** `0117:146`'s invariant is scoped to *extension* modules, and rationale §2.3 closes "**The gate is kept where it earns its keep.**" What transfers from v0.278 is the *method* — a rule unargued, unenforced and unfollowed is decided by what the project does — not the invariant. ⚠ **A contradiction the lane's argument 3 rests on, and the amendment must fix regardless:** §14.2's register bullet (`S:2479`) and `D:424` both say `Array<T>`/`OwningArray<T>` are "always-available names whose home module is not auto-imported, so an extension over them would require an `import` that naming the type does not" — but §2.3's own invariant (`S:164`: "Where the standard library declares an extension over a type this section makes always available, that extension's module is auto-imported") already auto-imports that module for any stdlib extension over `Array<T>`. One of the two texts is stale at v0.286. L3 disposes of both by making the module row explicit; if L3 is declined, the sentence at `S:2479` still needs a carve (it is filed as a defect in the review record).

**Corpus accounting.** Deletion-shaped only for the *doc* rows: no program is rejected. `tests/conformance/`: 19 cases use a §4 collection type, 4 carry the import — all unaffected either way.

**Migration.** *Newly defined:* the §4 names are bare-visible (already true in the compiler). *Newly rejected:* nothing. *Doc-only:* §2.3's two rows, `G:611`'s "except…" clause, the `S:2479` sentence.

**Change class:** design-change on the letter of process §2 (it changes a settled visibility rule) — landed, if accepted, as v0.278 was: "Kernel classification: no contact. Body-locality: not applicable" (`C` v0.278 entry). **Confidence:** high on the facts; the *decision* is the owner's weighing of twenty-two bare names against an unenforced rule.

### L4 — Drop `++`/`--` from the overloadable operator set — the re-measure `D:157` invites

**What.** §25.1 (`S:5755`): "- Unary: `+`, `-`, `~`, `++`, `--`"; §25.2 (`S:5781`): "`++` and `--` are postfix-only and statement-only. There is no separate prefix overload"; §17.6 (`S:3434`): "Overloading `++`/`--` on a class is permitted but uncommon"; `S:3436` the owned-field drop-on-overwrite paragraph; `S:3462` "For a value-type element T that overloads `operator ++`, the assigned value is `T.operator++(__coll[__idx])`"; `S:3468` the `Array<MyClass>`-vs-`OwningArray<MyClass>` slot-admission paragraph; §25.3's `Counter` example (`S:5800`).

**Why it is complexity.** `x++` "is equivalent to `x := x + 1`" for built-ins (`S:3432`); the overload makes it a second desugaring with its own ownership interactions — 314 words in §17.6 exist only for the overloaded case, including a leak-prevention corner (a fresh owned result of a class-typed `++` into a borrowing slot) that arises nowhere else. Rationale §14.1 (`R:1966`) is titled "`++` and `--` are statements" and defends statement-hood only.

**Proposed shape.** `++`/`--` are built-in-numeric statements only: remove both from §25.1's overloadable set and A.4's `OpToken`; delete §17.6 ¶3–4 and the two overload sentences in the indexer-slot subsection, §25.2's bullet, and §25.3's `Counter`. A user type spells increment as `c := c + 1` under its own `operator +` (§25.2's declaring-type rule admits `operator +(c: Counter, n: int)` — V2 traced the replacement as grammatical) or a named method — the posture §25.1 already takes for `not` ("types wanting a domain-specific inversion provide a named method").

**Record check — filed against the indexed row, as V2 required.** `D:157` — "Removing binary bitwise operator overloadability (`&`, `|`, `^`, `<<`, `>>`)", `rejected`, ground "Grammar-touching (Appendix A's shared `OpToken`/`IfaceStaticOperator` productions), strands the compound-assignment desugar, and leaves §14.4's `~` set-complement ground incoherent", reopening bar "**Re-measured each subtraction pass**". This item *is* that re-measure, and it concedes the shared cost: the `OpToken` edit is real. **The new evidence is that the other two grounds do not transfer:** (a) `++` is not compound assignment — no `&=`-style desugar strands; (b) no rationale ground becomes incoherent — §14.1 defends only statement-hood; (c) the stdlib's own ordinal-advance abstraction is already a named method: `ISteppable<T>` declares `Step(value: T, by: long)` (`L:1124–1127`), and `grep -n 'static operator' docs/Bezel_Standard_Library.md` shows the static interfaces declare `+ - * / <` only — **no stdlib conformance is foreclosed.** No `D` row and no rationale passage covers `++` overloadability itself.

**Corpus accounting.** `grep -rn 'operator *++\|operator *--'` — stdlib + guides + code-generation reference → **0**; `tests` → **73** lines in **16** files (`tests/codegen/operator_increment_498_test.cpp`, `owned_field_increment_disposal_1702_test.cpp`, `enum_operators_1582_test.cpp`, `tests/sema/increment_reference_type_2585_test.cpp`, … — most exercise exactly the special-case paragraphs above); **`tests/conformance/`: 1 case** (`spec_0170.bzl`); `src` → **20** lines.

**Migration.** *Newly rejected:* `operator ++`/`operator --` declarations; `c++` on a user type. *Replacement:* `public static method operator +(c: Counter, n: int): Counter => new Counter(c.Value + n);` and `c := c + 1;`. *Doc-only:* none beyond the sections named.

**Change class:** design-change (self-priced honestly: the `OpToken` cost is the one `D:157` names). **Kernel classification:** no contact (§17.6's drop-on-overwrite paragraph is an *instance* of §28.7, deleted with its trigger). **Cost:** 16 test files, one conformance case, a grammar token, 20 compiler lines. **Confidence:** medium-low — the weakest of the four; presented because the reopening bar asks for it, not because the benefit is large.

## 2. Rulings and clarifications (no program the corpus contains is rejected by any item here)

### L5 — Fold §4.2's typed-context widening into §5.1's constant narrowing

**What.** [§4.2](../Bezel_Language_Spec.md#sec-integer-types) (`S:572`): "An integer literal without a suffix has type `int` if it fits in `int`'s range; otherwise the literal requires a suffix or a typed context"; then the **Typed-context widening** paragraph (`S:576`) with its own five-position list. Separately [§5.1](../Bezel_Language_Spec.md#sec-implicit-conversions) (`S:690`): "Constant narrowing applies at **every** position where this section's implicit conversions apply — there is no position carve-out: initializers, assignments, call arguments (`Set(3)`), returns, record positional arguments, collection-literal elements (§15.4), and default arguments — and it participates in overload-resolution applicability (§22.6)".

**The hole.** §4.2 gates at literal *formation*, so an oversized literal in a collection-literal element never becomes "an expression of integer type" and §5.1's premise is never reached: `var xs: Array<long> := [3_000_000_000];` is admitted by **neither** sentence, while `var x: long := 3_000_000_000;` is. ### L6 — K5.4 restated as a consequence of the freeze criterion, not an override of it

**What.** [K5](../Bezel_Language_Spec.md#sec-kernel-k5) (`S:6569–6574`) states the criterion — a kill is unfrozen iff (i) it is keyword-visible at the kill site and (ii) the disposed flag it guarantees is an admissible backstop for every borrow that survives the kill — and appends (`S:6574`) "**or** by K5.4's one recorded structural override (vacuity; the Pattern A chaining case)".
