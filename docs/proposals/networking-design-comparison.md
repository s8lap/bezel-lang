# Networking design (0001/0002) — recorded pros and cons vs the field

Companion to proposals 0001 (client) and 0002 (server). This records *why this shape and not the others'*, with the costs stated as plainly as the benefits — the cons below are real, deliberate trades, not omissions. Written 2026-07-03 at owner request.

## The two structural bets

1. **Fetch symmetry.** One `Request → Response` vocabulary for both directions (client receives what the server returns; `HttpHeaders`, body accessors, and the single-consumption rule are shared). No other mainstream stack has this: .NET has `HttpClient`+`HttpRequestMessage` on one side and `HttpContext` on the other; Node has `fetch` on one side and `req`/`res` event-emitters on the other; Go's two sides are close but not unified. **Cost:** where the two directions genuinely differ (a server body arrives before the handler runs; a client body streams after), the unified type has to carry both stories.
2. **Guarantees over batteries.** The v1 surfaces are deliberately small, and the language does work frameworks elsewhere do at runtime (or not at all): ownership makes body/response lifecycle compile-visible; sendability makes handler data-races a compile error. **Cost:** everything a middleware ecosystem provides — auth, compression, static files, OpenAPI, validation — is absent in v1 and must be designed (not npm-installed) later. This is the single biggest con and it is structural: a checked platform cannot absorb an unchecked ecosystem.

## Client (0001) vs the field

| vs | We win | They win |
|---|---|---|
| **.NET `HttpClient`** | No lifecycle lore (the socket-exhaustion/`IHttpClientFactory` saga does not exist here — derivable defaults replace it); one call instead of the message-class zoo (`HttpRequestMessage`/`HttpContent` hierarchies); a timeout **default** (.NET's infinite-by-default has burned a generation); a real error taxonomy vs `HttpRequestException`-plus-status-spelunking; one-line JSON in both directions; `owned` response bodies make "who disposes this" a compiler question (.NET: `using` by convention, leaks by default). | Maturity and knobs: handler pipelines (`DelegatingHandler`) for cross-cutting concerns, proxy/enterprise-auth coverage, per-request version policy, HTTP/2/3 today, connection-pool tuning that has seen a decade of production. Our equivalents are deferred (0001 §7) and will be designed under ownership constraints rather than ported. |
| **WHATWG fetch** | We keep the shape and fix the recorded traps: no timeout (we default one), `bodyUsed` as a runtime surprise (we make single-consumption a principled §29.11 rule with a typed error), `!res.ok` silence (typed error taxonomy), no derivable defaults (`HttpClient` with-defaults). | Universality: fetch is the same API in every JS runtime and a spec someone else maintains. Ours is ours to maintain. Browser-specific semantics (CORS modes, credentials) don't apply to us — neither win nor loss. |
| **Go `net/http`** | `defer resp.Body.Close()` — forget it and leak — becomes `using var`/owned, compile-visible; error taxonomy vs `if err != nil` with string matching; JSON without hand-rolled decoder plumbing. | Context cancellation is *everywhere* in Go and threaded by convention through every call; our **intra-domain** request cancellation now exists — RFC #810's linked/derived `CancellationTokenSource` landed in v0.173 (stdlib §6.1), and 0001 threads a token through every call — leaving only the **cross-domain sendable cancellation handle** (gap #7) open. Go is still ahead on the ergonomics of pervasive by-convention threading, but the capability gap has largely closed. Go's client is also boringly proven. |
| **Rust `reqwest`** | Comparable async ergonomics without trait-bound error walls; ownership without lifetime annotations at the API surface (the language's affine model does the work). | Ecosystem depth (TLS stacks, HTTP/3, tower middleware); connection-pool maturity. |

## Server (0002) vs the field

| vs | We win | They win |
|---|---|---|
| **ASP.NET (Minimal APIs / MVC)** | **Compile-time data-race freedom** — §30.14 sendability checked at the registration line; ASP.NET's equivalent ("singleton services must be thread-safe", captive-dependency validation) is docs + runtime checks. No DI container required (DECLINED.md D-0001) — composition is constructor parameters with ownership contracts. No reflection/attribute discovery: what you register is what runs; startup is readable top-to-bottom. Closed-by-default faults (opaque 500; no `DeveloperExceptionPage` foot-gun to ship). Concept count: five new types (`IHttpService`, `RouteTable`, `HttpServer`, `HttpRequest`, `HttpResponseException`) over 0001's shared `HttpResponse`/`HttpHeaders`/`HttpMethod`/`Http`, one hook, seven response constructors — vs dozens. | **Everything else**: model binding/validation, auth(N/Z) middleware, OpenAPI generation, response caching, SignalR, output formatters, hosting integration — a decade of batteries. Kestrel's performance engineering. Scoped-DI conveniences for per-request services (we answer with handler locals — simpler, but less automatic). Tooling (analyzers, scaffolding). For a team shipping a big product **today**, ASP.NET wins on completeness; our bet is that a paper-stage language should buy guarantees first and batteries as designed pieces later. |
| **Express / Node** | Typed handlers vs untyped `req`/`res` bags; compile-checked shared state vs "single-threaded so mostly fine" (which stops being fine at `worker_threads`/cluster); a real error taxonomy vs error-first callbacks and unhandled-rejection roulette; route ambiguity detected at registration, not by first-match-wins surprise. | The largest middleware ecosystem in existence; the fastest hack-to-running loop; hot reload; a hiring pool that already knows it. Express's *simplicity of mental model* (one thread, share freely) is genuinely easier until the day it isn't. |
| **Go `net/http`** | The closest philosophical cousin (stdlib server, plain handler funcs, no magic) — our differences are: sendability checked at compile time where Go offers a runtime race detector; route params/verbs first-class (Go grew patterns only in 1.22); typed ownership of request/response lifecycles vs conventions. | Production-proven implementation (keep-alive, h2, timeouts hardened by a decade of internet abuse); goroutine-per-connection is a simpler concurrency story to teach than domains; graceful-shutdown/deadline idioms are mature. |
| **Axum / Actix (Rust)** | Explicit `req.Param`/`req.Json<T>()` accessors instead of extractor magic — no trait-solver error novels when a handler signature is slightly wrong; predictable, greppable data flow. | Extractors, when they work, are compile-checked *binding* sugar in the handler signature; ours is access-time `req.Param<T>`/`req.Query<T>` over `IParsable<T>` with the 400 short-circuit built in — one explicit line per parameter rather than zero, by design (0002 §7 Q4); tower middleware composition (our v1 is one `Around` hook per table); performance ceilings. |

## What would change these judgments

- **A middleware/hooks design that respects ownership** (deferred jointly with 0001 §7) closes the largest structural gap; until then every cross-cutting concern is hand-rolled per app.
- **Cancellation** — RFC #810's linked/derived CTS **landed in v0.173** (stdlib §6.1), so the Go comparison has already moved toward parity on intra-domain request cancellation; the remaining open piece is only the cross-domain sendable handle (gap #7).
- **Streams (#1394/#645)** unlock bodies-as-streams, uploads, and static files; several "they win" cells above are really "we haven't landed streams yet" — **proposal 0006 (the Stream family) now covers this bullet.**
- **Evidence from real Bezel services** — every judgment above is a paper-stage projection; the first thousand lines of real server code will re-rank the deferred list.
