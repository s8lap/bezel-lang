## 0. Summary

**Decision (option (c)).** A `TaskScope` is minted only as the initializer of an `await using var` binding whose static type is `TaskScope`, and that binding is its sole owner. Every other **owning** position is a compile error at the declaration that spells it or at the expression that would place a `TaskScope` in it: a plain `var`, `using var` or `const` binding and an undisposed drop (as today); every position §28.1 admits `owned` at (a parameter — `out` and lambda parameters included — a return slot, a field, a choice payload, a function-type slot, an owning inline-array slot); an owning-collection element or a `Shared<T>` payload — `TaskScope` is admissible as no type argument at all, explicit or inferred, at any §14.1 instantiation site, which also keeps `new T()` under `where T: new()` from minting one; and an owning position of a wider type reached by a §5.1 reference conversion (`owned Object`, `owned IAsyncDisposable`, an `await using var` declared at `Object` or an interface). `TaskScope?` reads as `TaskScope` throughout. **Borrows are otherwise unrestricted**: a plain parameter at `TaskScope`, `Object` or any interface, a pattern binding, a child's self-capture — no implicit discharge runs on a borrow and §28.6 rejects `Dispose()` through one, so no borrow reaches a synchronous disposal path (a borrow at a generic parameter is the type-argument case). One declaration-site rule; zero sites rejected in the tests, the documents and the rule corpus; the compiler checks locals only, so every other holder is spec-ahead-of-impl.

## 1. The problem

Stdlib §6.10 states, verbatim: "**Consumption is `await using` only** — a plain `using var`, or dropping the scope undisposed, is a compile error naming this rule: a synchronous destructor cannot await the drain, and live children hold scope-bounded borrows (§28.14), so no synchronous escape is sound." And §28.12 *Implicit discharge is synchronous*: "The implicit disposal paths — auto-drop of a plain-`var` owned local or undischarged `owned` parameter at scope end, the exception-path cleanup, drop-on-overwrite, container cascades, and frame teardown … — always take the synchronous `Dispose()` path, on every edge and in every context including `async` bodies: an implicit disposal point never awaits."

The rule names two binding forms and the drop. The hazard is every other owning position, each of which §28.12 discharges synchronously, skipping the drain while children still hold the frame's borrows (§28.14 *Quiescence*: "For compiler-known types the guarantee is stated normatively in the standard library (`TaskScope`, …)"):

```bezel
public class Holder
  private owned _scope: TaskScope;                       // (i) an owned field: the cascade disposes it synchronously
  public constructor() _scope := new TaskScope(); end constructor;
end Holder;

public static method Make(): owned Object
  return new TaskScope();                                // (ii) an upcast into an owned return slot
end Make;

public static async method Use(): Task
  using var o := Make();                                 // §6.10 cannot see a TaskScope here: the static type is Object
  var pool := new OwningArray<TaskScope>(1);             // (iii) an owning element, cascaded synchronously
  Take(new TaskScope());                                 // (iv) `Take(owned s: IAsyncDisposable)`: auto-dropped at Take's scope end
  new TaskScope();                                       // (v) an unbound owned temporary, disposed at the statement's end
end Use;
```

Faces (ii) and (iv) are the conversion question 0144 filed; (i), (iii) and (v) are at the type's own name and no conversion rule reaches them. Every one of the five is a holder other than an `await using var` binding of static type `TaskScope`. The compiler's `checkTaskScopeConsumption` (`src/ownership/Ownership_Checks.cpp:23680–23810`, source-read at `478a6de`) rejects a plain `var`, a `using var`, a `const`, a discard and a synchronous `scope.Dispose()` call, and checks the provable missing-`Join` subset; it checks nothing else. No `owned`-position check, conversion check or type-argument check on `TaskScope` exists anywhere in `src/` (`grep -rn TaskScope src/`: sema's member surface, the builtin registry, the runtime, and the consumption check above).

**Measured reach.** `grep` over `tests/` (gtest sources, lit, the conformance corpus) and `docs/` (the twelve documents, the proposals) for a `TaskScope` in any position other than an `await using var` binding or a borrowed plain parameter: **zero** — no `owned TaskScope`, no `<TaskScope>` type argument, no `Shared<TaskScope>`, no `TaskScope` at an `Object`- or interface-typed position, no `is`/`as TaskScope`. The three plain-parameter sites (`taskscope_consumption_610_test.cpp:36`, `localdecl_bare_const_arms_3591_test.cpp:352,368`: `Helper(s: TaskScope)`) are borrows and stay admitted. The rule corpus's `l6_10_0001`–`0007` state the binding-form rule and the `Join`/`Spawn`/fault rules; none states a holder verdict, and none flips.

## 2. Options

- **(a) Status quo.** Keep the binding-form rule. The five faces stay open; it is a soundness loss (the type's quiescence guarantee is normative), not a quality loss.
- **(b) A bare conversion ban.** `TaskScope` admits no §5.1 reference conversion to `Object` or to an interface, borrow or owned. This is the rule 0144's reopening bar named.
- **(c) A holder rule.** A `TaskScope` is minted only as the initializer of an `await using var` binding at its own static type and is owned by that binding alone; every other owning position is rejected at the site; `TaskScope` is not a type argument; borrows are unrestricted.
- **(d) The degraded synchronous destructor.** Give `TaskScope` a destructor that cancels and detaches the drain (the #1422 shape), so every holder is admissible and the synchronous path degrades instead of voiding. Recorded in `DECLINED.md` as `deferred`: "the fallback **only if this static rule proves too restrictive**".
- **(e) (c) with per-instantiation type arguments.** As (c), but admit `TaskScope` as a type argument and reject only the owning substitutions (`OwningArray<TaskScope>`, an `owned T` field at `T := TaskScope`) at the instantiation, admitting `List<TaskScope>`.

## 3. Evaluation

- **Soundness.** (a) is the hole. (b) closes faces (ii) and (iv) only: (i), (iii) and (v) are at the type's own name, and (iii) and `Shared<TaskScope>` are type-argument positions no conversion rule sees. (d) is not sound: a detached drain leaves children running past the frame whose borrows they hold, which is the §28.14 quiescence loss in a different costume; the deferred row's own condition ("only if this static rule proves too restrictive") is not met (§1: zero sites). (c) and (e) close every face: an owning position is either spelled at a declaration (a §28.1 `owned` position; a type argument) or entered by an expression whose static type is `TaskScope` (a conversion into an owning position, an unbound temporary, a plain or `using` binding), and both are visible at the site. Borrows need no rule for the hazard this proposal closes, which is a *synchronous* discharge: no implicit discharge runs on a borrow (§28.12's list is of owned bindings, owned parameters, owned slots and owning containers), §28.6 *Who may call `Dispose()`* makes `Dispose()` through a borrow a compile error, a borrowing collection disposes no element (§28.11), and §28.14's self-capture is a borrow. A borrowed `TaskScope` upcast to `IAsyncDisposable` can be asked for `DisposeAsync()` directly — the §28.12 direct call — exactly as it can at its own type; that call *awaits* the drain, so the quiescence this proposal protects holds, and whether a borrow may trigger reclamation that way is the general "who may call `DisposeAsync`" question, unchanged here and not `TaskScope`'s. A `move` of the binding is already closed: a `using var` is never moved out of (§28.10, axiom A5).
- **Simplicity.** (c) is one sentence with one key, the static type `TaskScope` at an owning position, and a type-argument ban that closes every container (`Shared<T>`, the owning collections, `Task<T>`, a user `Box<T>`) at the type reference. (e) trades that for a per-instantiation rule that re-runs the holder rule through every generic body after substitution — a new reject-at-substitution clause for `owned T` parameters and returns, which §28.1 clauses 3–4 *erase* rather than reject at substitutions they do not admit, and a check on `new T()`, which `where T: new()` admits at `TaskScope` (it has a public parameterless constructor) — to admit a borrowing `List<TaskScope>` nobody has written. (c)'s ban is not a new mechanism: it is decided at §14.1's instantiation sites, explicit or inferred, in §14.2's existing whole-argument shape (a dispatched generic method admits no move-only value type as a type argument). The cost is that a borrow passed to a generic parameter (`Log<T>(x: T)` called with a scope) is rejected; zero such sites exist, and the remedy is a parameter at `TaskScope`, `Object` or an interface. (b) is as simple as (c) but closes less and rejects more (below).
- **Over-rejection (measured, §1).** (c) rejects zero sites. (b) rejects the borrow conversions — `Helper(d: IAsyncDisposable)`, `Log(o: Object)` with a scope argument — which are harmless and today admitted; zero such sites exist either, so (b)'s cost is a future one, but it is a cost bought for a rule that closes less. (e) rejects zero sites and admits nothing (c) rejects in any program found.
- **Consistency.** (c) is §28.14's storage-bounded posture applied to the scope itself: the type's quiescence is a lexical-scope guarantee, and the holder rule states that the lexical scope is the only owner. It composes with proposal 0144: an `await using var o: Object := new TaskScope();` is now rejected at the initializer, before §30.7's `yield return` rule could see it, and 0144's general rule stays for every other class. It composes with the v0.328 §28.12 ruling: the run-time path is unchanged, and the only `await using` binding that can hold a `TaskScope` is one at its own type. The compiler's own §6.10 wording already says "a TaskScope may only be consumed by `await using`" at every arm (`Ownership_Checks.cpp:23696–23730`); (c) is that sentence made true of every holder.
- **Migration reach.** At spec level, (c) newly rejects: a §28.1 `owned` position (parameter, `out` or lambda parameter, return slot, field, choice payload, function-type slot) of type `TaskScope`; a `TaskScope` type argument, explicit or inferred (a borrow passed to a generic parameter included); an owning-collection or inline-array slot of `TaskScope` (a type-argument or slot-type position); an owned conversion of a `TaskScope` into an owning position of `Object` or an interface; and an unbound `new TaskScope()` temporary. Zero sites in tests, docs and the rule corpus. The compiler rejects none of these today (spec-ahead-of-impl, §6). Nothing is newly admitted.

## 4. Decision

**(c).** Declined, recorded in `DECLINED.md` as `declined-at-proposal`:

- **(a)**, because every owning position other than the binding discharges synchronously and voids a normative guarantee. Reopening bar: an async unwind driver that awaits `DisposeAsync` on every implicit discharge path (the driver §30.7 defers), which would make a holder restriction unnecessary.
- **(b)**, because it closes only the upcast faces and rejects harmless borrows. Reopening bar: an owning holder of a `TaskScope` that the holder rule cannot name statically.
- **(e)**, because a per-instantiation rule — new reject-at-substitution clauses where §28.1 erases, and a `new T()` check — buys an admission no program uses. Reopening bar: a program that needs a borrowing collection of `TaskScope`s.

**(d)** keeps its existing `deferred` row unchanged (its condition is unmet; §3), and this proposal adds no second row for it.

## 7. Self-critique (adversarial pass)

- **Is "borrows are unrestricted" sound?** The disposal paths are: explicit `Dispose()` (owner-only, §28.6), the implicit paths (§28.12: auto-drop of an *owned* local or `owned` parameter, drop-on-overwrite of an owned slot, container cascades of *owning* containers, frame teardown of owned bindings), `await using` (an owned right-hand side, or a borrow that "assumes no obligation", §28.10/§28.12), and the direct `DisposeAsync()` call. A borrow reaches none but the last, which is the drain itself and is the same call at the type's own name. Checked against §28.3's producer/borrow taxonomy: a plain parameter, a pattern binding, a field read, a `scoped` capture are all borrows.
- **Does the type-argument ban reach too far?** It rejects `IAsyncEnumerable<TaskScope>`, `List<TaskScope>`, `Dictionary<string, TaskScope>`. Each is either an owning holder or a borrowing one of a value whose only owner is a lexical binding; a borrowing container of scopes would hold borrows that the binding's scope exit invalidates, which §28.11's borrowing-collection rules police as for any class — admissible in principle, used by no program, and the per-instantiation alternative (e) is declined with its bar. Reopenable.
- **Does the §5.1 sentence create a new conversion category?** No: it states that a conversion into an owning position is an owning position of the source's type, which §5.1 already implies ("upcasting an owned value yields an owned value of the wider type"), and names the one class whose owning positions are restricted. No other library type is restricted this way; the sentence is written so that a second one would cite its own section.
- **Is "minted only as the initializer of an `await using var`" too strong for factories?** A factory `Make(): owned TaskScope` would hold the scope in an owned return slot and hand it to a caller who could bind it with a plain `var` or pass it on; the local rules would then re-check at the caller, but the unbound temporary `Make();` would discharge synchronously. Forbidding the slot removes the shape with zero measured cost; a program that wants a configured scope writes a helper taking the scope as a plain parameter (`Configure(s: TaskScope)`), which is a borrow.
- **The `TaskScope?` form.** Stated: "`TaskScope?` reading as `TaskScope` throughout" — an `owned _s: TaskScope?` field is an owning position of the type, and `await using var s: TaskScope? := new TaskScope();` is the admitted binding (critic F5).
- **Record components.** A record admits no `owned` field (§28.1, §28.5), so a record component of type `TaskScope` is a borrow and is admitted; the owning positions are §28.1's list, which the bullet cites rather than paraphrases (critic F2).
- **Composition with 0144 and the §28.12 ruling:** checked above (§3 *Consistency*). With L1 and L3: no shared paragraph; the only shared anchors are the DECLINED table headers and the README `## Graduated` heading, which each insertion leaves in place.
