## 0. Thesis

A function value that captures borrows is a **borrow-carrying value**, and the language already has the rule for such values: a borrow is bounded by its source set ([K2.1](../Bezel_Language_Spec.md#sec-kernel-k2)), sets combine by union ([K2.2](../Bezel_Language_Spec.md#sec-kernel-k2)), an escape must be bounded ([K2.3](../Bezel_Language_Spec.md#sec-kernel-k2)), and a holder no announcement reaches cannot re-establish a set ([K2.4](../Bezel_Language_Spec.md#sec-kernel-k2)). §28.3's closure bullet nonetheless carried, through v0.297, a second and *syntactic* admission for one holder kind — "Capture is permitted for closures that are immediately invoked, closures bound to a `using var` local of function type, and closures passed as an argument to a function-typed parameter" — restated by §28.14 ("admit three escape forms") and §28.9 (the `using var` "serves only the §28.3 capture-scoping and non-reassignability roles"), and taught by the code-generation reference. This proposal deletes the list and states the general rule in its place. The headline sentence — "A borrowed local may not be captured by a closure that may outlive the borrow's source" — stays, as the definition site of *may outlive* that §31.1, §9.7 and Appendix C use; the source-set rule states when it may.

## 1. The rule (as landed, spec §28.3 v0.298)

**Source set, by provenance.** A lambda literal or method reference contributes the sources of the borrows it captures: a captured borrowed local or parameter that binding's source; a captured owned local its enclosing scope (the producers row *Captured owned local inside a closure*); a captured function value its own set, transitively; a method reference's bound receiver as a capture — where a lambda's captures include the free bindings of every lambda nested in its body that resolve outside that body. A local or parameter contributes the union of the sets of the forms the flow analysis traces it to; a plain function-typed **parameter** carries a set its signature does not announce (K2.4) and is bounded by the call — §28.14's call-bounded tier, unchanged. **Invoking** a function value yields a value carrying the invoked value's set (a lambda's body can return a closure only over what the lambda itself captures, its own locals being scope-bound; a method's function-typed return is borrow-free by construction under the sink rule, so a method call's result carries the empty set). A function value read from a field or a collection carries the empty set — those holders admit only capture-free function values, by the sink rule, which is what §28.3's capture-set contribution ("borrow-free by construction") rests on; a `scoped` field's value is never read out as a value at all (§28.14). Any function value the body cannot otherwise trace carries an **unannounced** source, which satisfies no sink rule and is bounded by the call.

**Every §28.3 borrow rule then applies to the function value by that set**, with no closure-specific list:

- it may be bound to a local — plain `var` or `using var` — whose scope does not strictly enclose any source's scope (the local-scope bullet, loop back edges included). A declaration's own block never strictly encloses a source in scope at it, so an initializer is admitted by construction; only assignment to an already-declared local can cross scopes, each assignment checked on its own, and a later read of the local carries the union of the sets the analysis traces it to — reassigning a plain function-typed local is admitted;
- it may be immediately invoked;
- it may be captured by another closure, whose set then includes its own;
- it may **not** be stored in a field, in any collection, or through an `out`/`ref` parameter, and may not be returned from the enclosing method, **while its source set is non-empty**: a function type announces no source set (K2.4), so no holder outside the body can re-establish it and no caller could bound it — the ground §28.14 states for a received callback ("a plain signature carries no capture set"), read at every position that erases the set. A capture-free function value is admitted at each of those sinks; a capture-bearing one is stored only through a `scoped` parameter under §28.14's storage-bounded admission. These sinks were never open — §28.3's *Deferred-activation callees* says the closure-escape rules "admit a borrow-capturing closure into none of those locations", §28.14 that "a call-bounded *function* value may not be stored at all" — and they stay closed; a closure over `this` returned or field-stored is a rejection, as before;
- it may be passed to a function-typed parameter under §28.14's call-bounded/storage-bounded tiers;
- a `return` inside a lambda body leaves only that lambda: a closure returned there over a binding declared outside the body carries only sources the enclosing lambda's value already carries (its captures include the nested lambda's outward-resolving free bindings), so the return escapes nothing that value's binding was not checked for; one over a binding declared inside the body is the scope-bound rejection at that return.

Immediate invocation, `using var` binding, and argument passing — the former "three admitted forms" — are consequences. `using var` on a function-typed local remains permitted and serves only the non-reassignability role (§28.9) — which §28.10 had said all along ("the only effect is the reassignability restriction").

**Grounds.** (1) *Uniformity*: §28.3's local-scope bullet already governs every other borrow-holding local by structural scope comparison, and §28.9 already frames the closure as a borrow-carrier; a second, closed, syntactic list for closures was a redundant special case. (2) *Soundness is unchanged*: the binding, invocation, transitive-capture and argument positions are decided by the scope comparison and §28.14's tiers; the storage and return sinks stay closed on K2.4's ground, so §28.3's capture-set contribution, rationale §5.25, §28.14's asymmetry and the v0.177 record stay true verbatim. (3) *Ergonomics*: a local helper lambda over a borrow needs no `using var` ceremony. (4) *The compiler has implemented the general rule all along*: `checkBorrowStoreEscape`'s block-depth test (`src/ownership/Ownership_Checks.cpp:7226-7263`) is the only plain-local check; the pinned diagnostics "closure capturing `rr` is assigned to `f`, which outlives it" (`tests/lit/ownership/closure_escape_outer_local_861__*.bzl`, `lambda_body_escape_3727__*`, `lambda_body_escape_3743__*`), the sink rows (`lambda_body_escape_3744__*`, `lambda_body_escape_3564__owned_local_returned_closure_rejected.bzl`) and the catch-arm controls (`tests/ownership/catch_escape_test.cpp:333-345`, `:581-597`) pin scope comparisons, never a form check — and the invocation-provenance clause is what fix #3702 (`Ownership_Checks.cpp:4310-4318`) implemented for the method-return leg after a measured SIGSEGV. The closed list was the outlier, not the compiler.

**History of the list (why no reason is on record).** The bullet as first written (`53cf6c8e`, 2026-05-28) admitted closures "immediately invoked or whose lifetime is statically bounded by the borrow's source (a `using var` local of function type, an extension method's parameter)" — the criterion, with two instances. v0.177 (`24fd0f3a`, the call-bounded default, #1419) rewrote it as the enumeration and dropped the criterion; §28.14's "three escape forms" arrived at v0.175 (`dd2a600a`), §28.9's "capture-scoping" sentence at v0.178 (`decb0c79`, a currency revision with no changelog line for it). The v0.177 changelog entry explains only why a *received* callback is call-bounded and why plain function values may not be field-stored. No changelog or rationale entry states a reason for excluding the plain local; §28.10 contradicted the §28.9 sentence throughout.

## 2. Alternatives, declined

- **Keep the closed list** (#4154's option (a): enforce it in the compiler). Declined: it rejects `var f := lambda() => Use(b); f();` — a program every §28.3 sink rule admits and the compiler has always admitted — for a reason no record states, and it keeps `using var` as a capture-scoping marker that §28.10's own semantics (disposal; non-reassignability; the borrow-pin) never gave it. Recorded in `DECLINED.md` (*Closure-capture admission as a closed syntactic list*).
- **Widen by a fourth form only** (a scope-bounded plain local added to the list, in §28.3, §28.14 and the code-generation reference together — the route the v0.297 `DECLINED.md` row named). Declined: it would have kept a list whose reason nobody recorded, and left the next shape (a closure captured by an arm-local closure; a closure reassigned; the result of invoking a closure bound to a local) to be enumerated in turn. The same `DECLINED.md` row.
- **Open the storage and return sinks to a function value whose sources satisfy the object-borrow rules** (a closure over `this` or over a plain object parameter field-stored under the borrowed-field rule's residual, or returned as receiver-sourced) — the first draft's reading of "every rule applies by the set", refuted at the gate round: it would falsify §28.3's capture-set contribution ("borrow-free by construction"), rationale §5.25, §28.14's asymmetry and the v0.177 record, and would need every function-value read from a field or call result to contribute an unannounced or containing-object source. Declined on K2.4's ground; stated in §1's sink rule. Not a `DECLINED.md` row of its own — it is the reading the landed text rules out, recorded here and in the changelog.
- **A runtime backstop instead of a static rule.** Not a live alternative: K4's posture admits a recorded-trust residual only where the guarantee can neither be statically compared nor flag-backstopped, and a local's scope is compared.
