## 0. Thesis

§9.4 (v0.255) says what `this` *is* in a value-kind member body — "a **borrow of the receiver value**" — and what may not be done through it: no store may land in the receiver's own storage. It does not say what the borrow is a borrow *of* when the storage the receiver expression named is overwritten while the member runs. Two readings fit the text. Under a **by-address** reading `this` aliases the source storage, so a closure that runs `p := other` mid-call makes `this` denote `other`'s bytes, and a closure that runs `n := null` leaves `this` over an absent payload; under a **by-copy** reading nothing is observable. The compiler implements the first reading on some paths and the second on others (§7).

This proposal makes the by-copy reading normative, as an **observable semantic** rather than a representation: **the receiver value of a value-kind member call is fixed when the receiver expression is evaluated; `this` denotes that value for the whole activation, and no store during the call — to the receiver's source or to anything else — changes what it denotes.** Because §9.4 already rejects every store through `this` into the receiver, the fixed value is observably a copy only in the hazard case, so the representation is free (§11.8's recorded latitude, applied here): an implementation **copies** the receiver whenever its source *may be written during the call*, and **passes it in place** when the source is provably not writable, under one body-local predicate (§3.2) that the compiler already computes for §7.4. The one place the representation *is* observable is the move-only value kinds, which cannot be copied: there the receiver's storage is **borrowed in place at every source**, and the one read an in-place receiver makes unsafe — a move-only payload binding held across a point at which the source may be written — is rejected at the binding, in §19.3, for member bodies and `case`-over-a-field alike (§13, the owner-delegated decision; §3.4 is the declined alternative). A member whose activation outlives the call (`async`, iterator) holds the fixed value in its frame (§3.1). Kernel cost: a derivation (K8.4's call-bounded temporary, K5.6's non-local storage, K1.6's no-obligation values); body-locality: local (§6). No test in `tests/` flips by the sweep in §4. The compiler's tracked deltas (§7) are the **setter and compound-assignment** accessor paths, which pass the receiver in place today (the getter paths already copy), and one boxed-receiver liveness question.

## 1. The problem

### 1.1 The textual root

Three passages each say something true and together leave the receiver's source unprotected.

- §9.4 *Value receivers are borrows* (line 1479): "`this` binds a **borrow of the receiver value**" and "a store that would land in the **receiver's own storage** is a **compile error at the member body**". It constrains the member; it says nothing about the caller's storage during the call.
- §28.3 *Producers* (line 6990): the `this` row reads "Borrowed (source: caller)". For a class receiver "the caller" names an object whose disposal is flag-backstopped (K4.1). For a value receiver it names *storage* — a local, a field, a slot, a nullable payload — and K5's freeze protects only "an owned **binding** … while a live local borrow of its current value exists" (line 6839): a value binding carries no obligation and is never *consumed* (K1.6), so reassigning it is not a K3 position and the freeze never fires. §28.3 *Scope* then says "Fields and collection slots are **not** frozen ([K5.6])" at all.
- §28.3 *Captured owned bindings* (line 7130) forbids a closure to reassign a captured *owned* binding, and adds: "Mutation of captured **plain** (borrowed- or value-state) locals is unaffected ([§27.5])." A record local is value-state; a closure may overwrite it at will, including while a member of it runs.

§7.4 (line 1072) already knows the hazard in the *store* direction: it rejects `ref n.X` and `n.X += F()` over a mutably captured narrowed `n` because "during [the call] a closure that captured `n`, or another argument naming `n` in the same call, can set `n := null` before that store." The *read* direction — the member body reading `this` — is the gap #5496 names.

### 1.2 Program A — a mutably captured local (the issue's first repro, traced)

```bezel
module Repro;

public record Pt(X: int, Y: int)
  public method Sum(k: () -> ()): int
    var a := X;          // (3)
    k();                 // (4)
    return a + X;        // (5)
  end Sum;
end Pt;

public class C
  public static method Main(): int
    var p := new Pt(1, 2);                      // (1)
    var other := new Pt(100, 200);
    var r := p.Sum(lambda() => do p := other; end);   // (2)
    Console.WriteLine(r);
    return 0;
  end Main;
end C;
```

Trace, against v0.319:

1. `p` is a value-state local of record type (§3.2: "A **value type** is copied on assignment"). No obligation, no classification (K1.6).
2. `p.Sum(…)` binds `this` as "a borrow of the receiver value" (§9.4). The lambda assigns `p`: §27.5 admits it ("Modifications to a captured variable inside the lambda are visible outside"), and §28.3's captured-bindings paragraph exempts value-state locals from the closure consume ban. `p` is **mutably captured** in §7.4's sense (line 1072: "assigned, or passed as `ref`/`out`, anywhere inside any lambda of the enclosing function body"). **Admitted.**
3. `a := X` reads the receiver: 1.
4. `k()` runs the lambda: `p := other`. Under a by-address `this` — the compiler's capture cells make `p`'s storage a heap cell shared by the body and the lambda (`src/codegen/LlvmBackend_Exprs2.cpp:1403–1412`) — `this` now names the cell holding `(100, 200)`.
5. `a + X` is `1 + 1 = 2` under by-copy, `1 + 100 = 101` under by-address. **The text does not say which.** Nothing in §9.4 or §28.3 admits or rejects the overwrite, and nothing fixes the read.

With `Pt` **borrow-bearing** — `record Pt(X: int, Owner: Item)` for a class `Item` — the by-address reading is worse than ambiguous: the overwrite at (4) replaces the `Owner` borrow; with `using var item := new Item(); var p := new Pt(1, item); … p := new Pt(2, other);` under a `do … end` that disposes `item`'s replacement, the member reads a reference §9.7's lifetime rules never checked against *this* member's activation (they bound `p`'s value against its sources, not `this` against the value `p` held at entry). The by-copy reading keeps `this` over the entry value, whose sources §9.7 did check.

### 1.3 Program B — a narrowed nullable local nulled during the call (the issue's second repro)

```bezel
public record Pt(X: int)
  public method Poke(k: () -> ()): int
    k();
    return X;                                 // (3)
  end Poke;
end Pt;

public class C
  public static method Main(): int
    var n: Pt? := new Pt(7);
    if n <> null then                         // (1) narrowed
      return n.Poke(lambda() => do n := null; end);   // (2)
    end;
    return 0;
  end Main;
end C;
```

(1) narrows `n` (§7.4). (2) is a member call on the narrowed value — admitted; §7.4's invalidation clause says the narrowing is "gone" *after* "the first such operation", not during it. The lambda sets `n := null`; §7.3 admits it. (3) reads `X` of a receiver whose storage is a nullable value whose *has-value* state is now false. Under by-address, the member reads the payload bytes of a `null` — defined by nothing (the spec gives no representation to a nulled value payload); under by-copy it returns 7. Nothing in §7.4's narrowed-storage paragraph reaches this: that paragraph governs stores *into* `n`, not the member's reads.

### 1.4 Program C — a record field reassigned through an alias of its holder (the issue's third repro)

```bezel
public record Pt(X: int)
  public method Twice(k: () -> ()): int
    var a := X;
    k();
    return a + X;
  end Twice;
end Pt;

public class H
  public P: Pt := new Pt(1);
end H;

public class C
  public static method Main(): int
    using var h := new H();
    var alias := h;                                    // (1) a borrow of the same object (§3.2)
    return h.P.Twice(lambda() => do alias.P := new Pt(100); end);   // (2)
  end Main;
end C;
```

(1) `alias` is "a borrow of `h`" (§28.3's unmarked binding rule). (2) binds `this` into `h`'s storage; the lambda stores through `alias`. The store is an ordinary field store of a copyable value (§3.2), admitted everywhere. By-address: `2 → 101`. The source is not a local at all, so no capture test can see it: K5.6's words apply — "slot aliases are not body-local" — and so no freeze can be body-local either. **Only a by-copy receiver, or a provably unwritten source, is sound here**; a freeze (the issue's option (ii)) cannot reach this program at all, which is why the owner declined it.

### 1.5 Why it matters beyond the three programs

- **Soundness of borrow-bearing values.** §9.7's lifetime rules check the *value* a binding holds against the sources of the borrows *that value* carries. A by-address `this` lets the member observe a value those rules never checked for this activation — the replacement — and, for a `[N]C` inline-array field or an interface-typed field, a replacement whose own sources may have ended before the member finishes.
- **Choices.** A choice receiver (§35.2: "`this` in a choice instance method is a **borrow** of the receiver value") whose source is overwritten mid-`case this of …` changes case under a selected arm. A fresh read of `this` sees the new value whole, tag and payload together. An arm binding held **in place** across the overwrite, however, keeps addressing payload bytes under the old case. That binding is a borrow of a move-only payload (§35.5: "a binding of a payload of **move-only value type** … is likewise a **borrow**"), and through it the overwrite is type confusion, not merely a stale read. For a copyable choice, §19.3 binds payloads by copy, so the hazard there is the replaced value of §1.2. The same holds for narrowed `Choice?` locals and for choice fields reached through an alias. *(Critique round 1, N8: narrowed. B6 notes that the same in-place binding is reachable through a non-destructive `case` over a field with no member call, Q8.)*
- **Decidability of everything downstream.** §7.4 made its narrowed-storage rule sound by *rejecting* the store positions a mid-call writer can reach; it could do so because a store is syntactically visible. A member body's *reads* of `this` are not visible at the call site; the only call-site-decidable protection is to fix what `this` denotes.

## 2. Constraints and recorded decisions any fix must respect

1. **§9.4 (v0.255): `this` is a borrow; stores into the receiver's own storage are rejected at the member body; the mediating store through a class- or interface-typed hop is legal; constructor bodies are not receiver positions; the synthesized auto-property setter's store "is the external assignment's own store".** The fix must not re-open interpretation 1 (the aliasing receiver) and must leave `Span<T>`'s indexer setter (`Buffer[Start + i] := value`) exactly as legal as it is. A by-copy receiver preserves the mediating store bit for bit: the copy holds the same `Buffer` borrow, and the store lands in the same `OwningBuffer<T>`.
2. **§28.3's `this` producers row — "Borrowed (source: caller)" — and K2's source taxonomy.** Rationale §9.13 records that the v0.255 ruling reads this row as "stating both the ownership and the binding classification". A value receiver's *source* must still be nameable in K2's terms: this proposal names it as a **full-expression temporary** (K2's third source kind, line 6785: "an unbound owned temporary …, live exactly to its K8 boundary" — here the value-typed analogue, which carries no obligation) bounded by the call (K8.4: a temporary "is an admissible borrow source only within its boundary").
3. **K5 and K5.6.** Value bindings are never consumed, so the freeze cannot be the mechanism; fields and slots are not frozen by design. The fix must not add a freeze (option (ii)) and must not treat value storage as frozen.
4. **§3.2's copy rule and §15.3's move-only exception.** "A **value type** is copied on assignment"; owning inline arrays and owning-classified choices "transfer rather than copy" and "cannot be duplicated". A rule that says *copy* must say what happens where copying is forbidden (§3.4 decides: admit in place only where sound, else reject).
5. **Borrow-bearing records and the no-temporary-source rule (§9.7).** A copied receiver carries the same borrows as the source value; its lifetime is the call, which every carried source outlives by the caller's own §9.7 checks on the source binding at the call point. The copy introduces no new source and no new escape (it is a K8 temporary and may not outlive its boundary — nothing in a member body can store `this` itself: §9.4 bans stores into it, and `this` as a *value* — `return this;` — is a copy at a value-typed return, the announcement table's row 7, carrying the receiver's own sources, which the record-return bullet of §9.7 already checks).
6. **`ref`/`out` receivers and the §22.3 location rules.** "A `ref` or `out` argument must be an **assignable storage location** … a **parameter** (the receiver `this` excepted …)". A `ref p: Pt` parameter's storage is the caller's; nothing in the callee's body bounds who else writes it. This proposal classifies it as *not provably unwritten* and stops there (0134 owns anything finer).
7. **`readonly` fields (§7.4 *`readonly` fields narrow*).** "outside its construction window … a `readonly` field has no writer on any path, through any alias". This is the one non-local storage class the text already certifies unwritten; §3.2 admits it as an *optional* in-place source and §9 asks whether to make the admission normative.
8. **Representation latitude (§11.8, rationale §10).** §11.8 states dispatch binding as "a statement about *semantics*, not implementation strategy", and rationale §10 records "Bezel's intended implementation specializes for value-type substitutions". This proposal states the receiver rule the same way: an observable semantic (the value is fixed) plus a representation note (copy where the source may be written, in place where it provably is not) whose two outcomes are indistinguishable by any program the spec admits.
9. **Performance and ABI (rationale §10; `CG29` in `src/`).** The compiler already passes `this` for records and choices as a pointer to a **spilled copy** on the user-method path (§7, item 1) — so by-copy is the *current* cost on that path, not a new one. The ABI (pointer to the value) does not change; what changes is only which storage the pointer names.
10. **Body-locality (proposal 0105 §1).** Any rule that decides *where* the receiver may be passed in place must read only the calling body. The predicate in §3.2 reads the receiver expression, the call's own argument list and §7.4's mutable-capture scan of the body — exactly what `ExprTC::computeMutablyCaptured` (`src/sema/ExprTypecheck.cpp:16232–16240`) already computes.
11. **§7.4's narrowed-storage paragraph (v0.317) and its vocabulary.** "A mutably-captured local has exactly the unseen writer the field paragraph below names" — the fix reuses this vocabulary rather than minting a second writer classification.
12. **The three options the issue listed.** (i) by copy whenever the source may be written — **accepted by the owner**; (ii) freeze the source — cannot reach fields (Program C) and would need a new freeze subject for value bindings; (iii) by-address with the overwrite visible — makes every member body's correctness depend on every caller's closures, and is unsound for choices and borrow-bearing values (§1.5). (ii) and (iii) become `DECLINED.md` rows at graduation (§8).

## 3. The rule

### 3.1 The observable semantic ▲ (spec §9.4, a new paragraph after "Two boundaries.")

> ▲ **The receiver value is fixed at the call.** A member call on a value-kind receiver — a record, choice, enum, inline-array or primitive receiver, directly held, narrowed non-null ([§7.4](#sec-member-access-on-nullable-values)), or boxed ([§8.6](#sec-boxing)); a declared member or an extension member ([§26.7](#sec-ownership-in-extensions)) alike — runs over **the value its receiver expression denoted when that expression was evaluated** — for a boxed receiver, the payload of the box it denoted. For the whole activation `this` denotes that value — its own bytes, the references it holds included, though not the objects those references name: no store that runs during the call — to the storage the receiver expression named, through any alias of it, or to anything else — changes what `this` denotes, and the activation's completion stores nothing back. The receiver value is a **full-expression temporary** of the call ([K8](#sec-kernel-k8)), and the borrow `this` is bounded by it ([K8.4](#sec-kernel-k8)); a borrow-bearing receiver value carries into the call exactly the borrows the receiver expression's value carried, checked at the call site by [§9.7](#sec-records-and-disposal)'s rules as every other read of that value is. A member whose activation outlives the call — an `async` member ([§30.1](#sec-async-methods)) or an iterator member ([§29.3](#sec-iterator-methods)) — holds the fixed receiver value in its frame, as the frame holds a plain value argument ([§29.4](#sec-lazy-evaluation)), the value's borrows becoming carried sources of the frame ([K6](#sec-kernel-k6)). The rule governs what the member **reads**, and an author-written accessor that an assignment or compound assignment invokes ([§6.6](#sec-compound-assignments)) is a member call like any other. The **synthesized** auto-property setter alone runs no author-written body: it stores where the assignment itself stores — the named location — and that store is the assignment's (the boundary above).
>
> Whether the implementation realizes the fixed value as a **copy** or passes the source storage **in place** is unobservable for a copyable value kind and is the implementation's choice, under one obligation. Storage is passed in place only to a member whose activation ends before the call returns, and only where **no code reachable during the call can write it**: a local binding of the calling body that is not mutably captured ([§7.4](#sec-member-access-on-nullable-values)'s sense), is not named by a `ref` or `out` argument of the same call, and is not a parameter that binds the caller's storage (a `ref` parameter, written or inferred, [§27.1](#sec-lambda-parameter-modifiers); a move-only operator operand or `Equals(T)` parameter, [§25.2](#sec-operator-overloading-restrictions)); a `const` local; storage inside such a local; storage inside the enclosing activation's own fixed receiver; or a `readonly` field outside its construction window ([§7.4](#sec-narrowing-applies-to-locals-only)). Everywhere else it is copied. For a **move-only** receiver ([§15.3](#sec-move-only-value-types)) the choice is not free: see *Move-only receivers* below.

**What the paragraph decides, item by item.**

- *Reads through `this` are over the entry value.* Program A prints `2`, Program B returns `7`, Program C returns `2`. The caller's storage still holds whatever the closure stored — `p = other`, `n = null`, `h.P = Pt(100)` — after the call, as §27.5 and §3.2 already say.
- *Writes through `this` are unaffected* — there are none to decide: §9.4 rejects every store landing in the receiver's own storage, in each spelling (direct, bare, compound, `++`/`--`, `ref`/`out` chain, `extern` by-address). The mediating store through a class- or interface-typed hop lands in a heap object the copy and the source both borrow; identical effect.
- *Is the copy observable anywhere else?* Values have no identity (§3.2; rationale §9.13: "values have no reference identity"); `=`/`Equals`/`GetHashCode` are structural; `return this;` is a value return (row 7). `old(E)` in an `ensures` over `this.X` (§22.16: "Copyable operands are captured by copy") reads the fixed value — consistent with by-copy and unobservable under by-address except in the hazard. `GetType()` on a value "is always the static type" (§8.3). The remaining observable surface is exactly the hazard case, which this paragraph defines.
- *Boxed receivers.* §8.6: "a member call on the box reads nothing out — it **borrows** the payload for the call's duration". The payload is immutable (§8.6: "fixed at boxing"), so the fixed-value semantic holds by construction; what the paragraph adds, through the K8 bound, is that the payload **stays alive for the call** — a box is a runtime-managed object that the last reference's reassignment (`o := other` in a closure, `i := null`) releases, so the implementation retains the box across the call or copies the payload at entry. §8 carries the one-sentence §8.6 edit; §9 Q3 lists the probe.
- *Enums and primitives.* Passed by value already (the compiler: enum methods "take `this` by value, not by pointer", `src/codegen/LlvmBackend_Calls2.cpp:12325`); the paragraph is vacuously true and is stated for them so the rule has one scope — all value kinds — rather than a per-kind list.
- *The nested `this`.* Inside a value-kind member body, `this.N()` or a bare `N()` is a member call whose receiver expression is `this` — already a fixed value — so the nested call runs over the same fixed value (in place, with no further copy: "storage inside the enclosing activation's own fixed receiver"). A chain `this.P.M()` over a record field `P` of the receiver is the same.

### 3.2 "May be written during the call": the body-local predicate

The in-place admission is phrased as a closed list, so it is decidable from the calling body alone. Let the **source** of a receiver expression `E` be the storage `E` names when `E` is an lvalue (grammar A.6 `LValue`: a local or parameter, a field path, an index path, a narrowed nullable local's payload, or a chain from one of these through record fields and inline-array slots); a receiver expression that is not an lvalue — a call result, a `with` result, a literal, a boxing conversion — has **no source** and its value is already a temporary. The source is **provably unwritten during the call** exactly when one of the following holds:

1. **An unaliased local.** The root of `E` is a local binding or parameter **declared in the calling body itself** (a lambda body is its own body: a reference from inside a lambda to an enclosing body's local is a *capture*, not a local of the lambda's body), the binding is **not mutably captured** — not "assigned, or passed as `ref`/`out`, anywhere inside any lambda of the enclosing function body" (§7.4, line 1072) — and the binding is **not named by a `ref` or `out` argument** anywhere within the same call's argument expressions (the evaluation-order window between the receiver's evaluation and the call: §7.4's "another argument naming `n` in the same call"). A parameter that binds the caller's storage is **not** such a root: a `ref` parameter, whether its `ref` is written or inferred from the target function type (§27.1 *Lambda parameter modifiers*), and a **move-only operator operand or `Equals(T)` parameter**, which §25.2 says binds "**borrows** of the operand values". *(Critique round 1, B5.)* An `out` parameter is such a root (§22.3: "within the callee the parameter denotes a callee-local slot"), on the reading that proposal 0134's §22.3 clarification pins: the hidden reference designates storage that is the callee's for the call. If that clarification does not land, an `out` parameter is classed writable, which is unobservable for a copyable kind. *(N4.)* A `using var` local and a `const` local qualify trivially (`const` can be neither assigned nor captured mutably, §7.4).
2. **Storage inside the fixed receiver.** The root of `E` is `this` in a value-kind member body, and every hop from `this` stays inside the value (record fields, inline-array slots — §9.4's own key: "what an lvalue chain rooted at `this` reaches without leaving the value").
3. **A `readonly` field outside its construction window**, in §7.4's tracked shape — "exactly **one field off an admitted root** — `this._f`, `TypeName._s`, or `local._f` where `local` is itself narrowing-tracked" — and not inside the declaring type's constructors or initializers. *(Optional for a copyable kind, where it is a pure representation refinement; §9 Q2 asks whether to make it normative for move-only receivers, where it is observable.)*

Everything else **may be written**: a field path through a mutable field or any class- or interface-typed hop; a collection element or heap-array element; a static field (process-global storage, writable by anyone); a `ref` parameter, written or inferred; a move-only operand or `Equals(T)` parameter; a mutably captured local; a local named by a `ref`/`out` argument of the same call; a narrowed nullable *field* (not narrowable anyway); an enclosing body's local referenced from inside a lambda.

**Completeness for locals** (for a member whose activation ends before the call returns; an `async` or iterator member's frame holds the value, §3.1, because the calling body runs on while that activation is live — *critique round 1, B3*). Between the receiver's evaluation and the call's end, a local of the calling body can be written only by (a) a statement of the calling body — none runs, the body is suspended in the call; (b) a `ref`/`out` argument of the same full expression — the language has no assignment *expression* (`:=`, `??=`, `++`/`--` are statements, §21/§17.6; the binding atom declares fresh locals), so no argument expression writes a local directly; (c) a lambda of this body that assigns it or passes it `ref`/`out` — §7.4's mutable capture, which "is deliberately syntactic and conservative: any lambda in the body counts, whether or not it escapes"; (d) another continuation of the domain interleaving at an `await` inside the callee (§30.13) — which can write this body's locals only through (c). The predicate's item 1 excludes (b) and (c); (a) and (d) need no exclusion. For non-local storage no body-local predicate exists (K5.6's ground), so it is classified writable without further analysis.

**What the compiler already has.** `mutablyCapturedNames_` (`src/sema/ExprTypecheck_impl.hpp:445`, computed by `computeMutablyCaptured`, `src/sema/ExprTypecheck.cpp:16232–16240`) is item 1's capture test. It is consumed today by `invalidateCapturedNarrowings` and by the mutable-capture narrowing rejection at `src/sema/ExprTypecheck_Calls.cpp:21661` ("cannot narrow `T?` accessed through …"). The same-call `ref`/`out` test is a syntactic scan of the call's `args`.

### 3.3 Where the semantic is stated (the text's four homes)

- **§28.3 *Producers*, the `this` row** gains the value-kind clause ▲ "— for a value-kind receiver, the call's fixed receiver value, a full-expression temporary bounded by the call ([§9.4](#sec-value-receivers-are-borrows); [K8.4](#sec-kernel-k8))" — so K2's taxonomy names the source and the row stops reading as if a value receiver's "caller" were storage.

### 3.4 Move-only receivers ▲ (spec §9.4, the paragraph's closing sentences; echoed in §15.3 and §35.2)

> **Superseded by §13 (owner-delegated decision, 2026-10-08).** The ▲ paragraph below is the draft's *R* (reject); the decision is *F*, and §13.3 item 1 carries the paragraph that graduates in its place. The section is kept as the record of the alternative weighed.

> ▲ **Move-only receivers.** A move-only value ([§15.3](#sec-move-only-value-types): an owning inline array, an owning-classified choice) cannot be copied, so its receiver can be fixed only by passing its storage in place. A call to a **bodied** member — a declared method or accessor of an owning choice ([§35.2](#sec-choice-members)), or an extension member over either kind — on a move-only receiver is therefore admitted **only where the receiver's source is provably unwritten during the call** (the list above), and only at a member whose activation ends before the call returns. Otherwise it is a **compile error at the call**, naming the source and the remedy: move the value into a local of the calling body, call the member on that local, and restore it on every path — `var c := move h.C; var ok := false; try ok := c.IsOk(); finally h.C := c; end;`. The compiler-provided operations of an inline array ([§15.1.2](#sec-members-and-operations): `Length`, indexing, `GetType`, `ToString`, equality) run no author-written body over `this` and are slot reads under [§28.11](#sec-element-slot-policy)'s posture, not member calls for this rule.

**Why reject rather than admit.** The alternatives were weighed against the one shape that matters: an owning choice field `h.C` overwritten through an alias of `h` while `h.C.M()` runs. (a) *Admit under K5.6's runtime-checked posture* — the posture K5.6 relies on is a **disposed flag on the object a borrow references**; an in-place overwrite of a choice rewrites the **tag and payload bytes under `this`**, flags nothing, and leaves a selected `case this of` arm reading another case's payload — type confusion, which no flag backstops. Rejected. (b) *Freeze the field for the call* — K5.6: "slot aliases are not body-local"; a freeze over `h.C` cannot see `alias.C := …`. Rejected. (c) *Copy the discriminant and borrow the payload* — a partial copy is a new representation with its own rules for every payload kind, for a hazard the move-to-a-local remedy already closes; declined as weight. (d) *Reject* — the §7.4 narrowed-storage ruling's own posture ("Such a chain at those positions is therefore a compile error … the diagnostic names the copy-out spelling"), transcribed from stores to reads. Adopted **in this draft, pending the owner (revised Q1)**. Its cost is measured in §4.3: no in-tree program calls a bodied member on an owning choice held in a field or element, or reached through a borrowing parameter or a captured local.

**What the reject does not close (critique round 1, B6).** The in-place binding that turns an overwrite into type confusion is equally reachable with **no member call**. `case h.C of Ok(arr) => do k(); return arr[0].Name; end, …` over the same field is a non-destructive match, "the default everywhere" (§35.5), and its move-only payload binding is a borrow. §28.3 *Scope* already puts borrows of a field's current value under "the runtime-checked posture". So rejecting `h.C.IsOk()` leaves its body, inlined as `case h.C of …`, admitted with the same hazard. The reject is coherent only together with a decision on that twin (Q8). Alternative (a) above, in the form *F* of revised Q1 (admit in place under §28.3 *Scope*'s posture with a recorded residual, and close the confusion at the binding in Q8), is the other coherent pair.

**The remedy is sound.** `var c := move h.C;` is K9.2's whole-value move out of a field (§28.8.1's `move obj.f`; the spelling for an owning-choice field is re-verified against the compiler at graduation), with the restoration obligation on every exit edge. `c.IsOk()` runs on an unaliased local (item 1). §28.8.1's inventory lists "Method calls" as throwable, so restoration must cover the exception edge: hence `try … finally h.C := c; end`. The store back is unmarked, because a store of a move-only value into an owning location is K3.12's marker-free position, where `move` is rejected (§15.3 *Parameter passing*, §28.8.1). *(Critique round 1, B4: the earlier `…; h.C := move c;` spelling was a compile error twice over.)* A **`readonly`** field admits no move-out outside its construction window, so for it the only spellings are Q2's admission or the `case` twin. For an owning inline array the only bodied members are extension members (§26.2 admits none over inline arrays: "inline arrays have no member bodies … and admits no extension", §9.4), so the sentence reaches owning arrays only through the compiler-provided carve, which admits them.

### 3.5 Operands that bind borrows (§25.2) — a separate question (revised by critique round 1, N1)

§15.3 notes that "Operator operands and the comparison surface's `Equals(T)` parameter are not plain parameters in this sense: they bind borrows — [§25.2]". §25.2 scopes this by kind: "Operands are received as plain borrows (or value copies) under their type kinds". A **copyable** operand is already a copy, so `operator =(a: Pt, b: Pt)` has no Program-A hazard and needs no new sentence. Only **move-only** operands (an owning choice, "the one move-only kind with an operator surface") bind borrows of the caller's storage. Fixing them cannot mean copying. It would be a **use-site** rejection of `h.C = x` or `a.Equals(h.C)` at a writable operand source: a new rejection outside #5496's letter, coupled to Q1's R/F choice. This proposal therefore **does not** extend §25.2. It keeps the predicate sound without that extension by classing a move-only operand or `Equals(T)` parameter as storage the body cannot prove unwritten (§3.2 item 1), so a member call on such an operand inside the operator body follows §3.4. The operand question is filed separately at graduation (§9 Q6).

## 5. Soundness

**Claim.** Under §3.1, every read of `this` in a value-kind member activation reads a value whose carried borrows are live, and no activation observes a value its caller's checks did not admit.

1. **The receiver value exists at entry and is admitted.** The receiver expression's value, at its evaluation, is an ordinary read of the source — a local, a field, a slot, a narrowed payload — admitted by the caller's own rules at that point: §9.7's lifetime rules for a borrow-bearing value, §7.4's narrowing for a nullable payload, §28.11's element posture for a slot. (K2.1: a borrow is valid where every source in its set is live; the value's carried borrows were checked live at the read.)
2. **The fixed value is a K8 temporary bounded by the call.** It is produced by the receiver expression and consumed by the activation; it escapes nowhere: §9.4 bans every store into the receiver; `this` as a value (`return this;`, an argument `F(this)`) is a **copy** at a value-typed position (§3.2), whose carried borrows the record-return bullet of §9.7 and the argument rules then check as for any value — the K8 temporary itself is never a holder's source past the boundary (K8.4: "a borrow or frame that would escape it is **rejected, never lifetime-extended**").
3. **No write reaches it.** By-copy: the copy is storage no program names (K8's temporaries are unnamed), so no store can land in it. In-place: §3.2's items 1–3 each cite the text's own guarantee that the storage has no writer during the call — item 1 by the completeness argument in §3.2 over the four writer classes; item 2 by this very rule applied to the enclosing activation; item 3 by §7.4's `readonly` ground ("no writer on any path, through any alias"). Item 3's **holder** may still be killed during the call, for example by `alias.Dispose()`, a site-announced kill (K4.2), whose destructor disposes the field's payload objects. The member then reads disposed objects through `this`. No tag or payload bytes are rewritten, so K4.1's flag backstops the read, the posture every borrow of that object already has *(critique round 1, N9)*.
4. **Carried borrows stay live for the call.** A carried borrow's source was live at (1). Could it end *during* the call? Only by a consume of that source, which is (a) frozen if the source is a local binding with this value live — and the fixed receiver *is* a live local borrow of every carried source for the call's duration, exactly as "A live local of **borrow-bearing record** type … counts as a live local borrow of every held borrow's source" (§28.3 *The consume-site freeze*) — so a closure cannot consume it (the captured-bindings ban), and the body is suspended; or (b) a site-announced or slot kill under K4's flag backstop, where a stale use faults in checked mode — the posture every other borrow of that source already has. Nothing new is admitted.
5. **Move-only receivers.** Copying is forbidden, so only (3)'s in-place branch is available. *(Superseded by §13.2's soundness trace: under the decision the storage is passed in place at every source, a whole-value store during the call is visible through `this` as a coherent value whose displaced payload objects are flag-backstopped, and the one read no flag reaches — an in-place move-only payload binding held across a write point — is rejected by §13.3 item 2's binding rule, inside the member body and at every other scrutinee alike.)*
6. **Boxed receivers.** The payload is immutable (§8.6), so (3) holds for its contents; (2)'s boundary requires the payload to outlive the call, which the box retention or payload copy provides (§3.1's boxed item; the probe in §9 Q3 confirms the implementation's side).

**Kernel classification.** Derivation: K8 (the fixed receiver is a full-expression temporary; K8.4 bounds the borrow), K1.6 (a value carries no obligation; no consume position is added), K5.6 (non-local storage is "not body-local", so it is classed writable and copied rather than frozen). The in-place predicate is a representation obligation, not a freeze; its body-locality is §6's. *(Critique round 1, N3: K5.5, the freeze's liveness bound, was cited here in error.)* No new K row, no axiom.

## 6. Body-locality (proposal 0105 §1)

**Local.** The rule consumes, at a call site, only: the receiver expression's shape (lvalue or not; its root and hops); the call's own argument list (`ref`/`out` occurrences); the calling body's lambda bodies (the mutable-capture scan — a scan of *this* body, including its nested lambdas, which are part of it); and declared facts of the receiver's type (value kind, move-only by structure, §15.3's "determined by structure, not by declaration" — a signature-level fact). It reads **no member body of the callee**: a callee that never invokes user code is treated exactly as one that does (the same posture as §28.3's `ref`/`out` rule: "a callee that stores nothing is checked as one that stores everything"). Generic instantiation adds nothing: whether a `T`-typed receiver at a value substitution is move-only is a per-instantiation fact of the substitution (§3.6 rule 2), and the predicate over the calling body is substitution-independent.

  - ***R — reject*** (the draft, §3.4). A bodied member call at a source not provably unwritten is a compile error. The in-tree cost is **zero programs** (§4.3 re-sweep). The idiom it rejects is a class's mutable owning-`Result` field tested with `_conn.IsOk()`. The remedy is `var c := move h.C; var ok := false; try ok := c.IsOk(); finally h.C := c; end;`. R does not by itself close the type-confusion hazard: `case h.C of …` over the same field stays admitted (§35.5), so R needs Q8 decided the same way, to be coherent.
  - ***F — admit in place with a recorded residual.*** A member call on a move-only receiver at a writable source runs in place under §28.3 *Scope*'s existing posture for borrows of a field's current value ("the runtime-checked posture"). The confusion is closed where it actually arises, at the in-place **move-only payload binding** held across user code (Q8), for both the member body and the inlined `case`. F rejects nothing new at member calls. Its cost is a K4.3-recorded residual: whole-value reads of `this` after an overwrite see the replacement. That is the by-address reading (iii) the owner declined for copyable kinds, here confined to the one kind that cannot be copied.
  - An optional refinement under either choice (N10): admit, as provably unwritten, a move-only local of an enclosing body referenced inside a lambda. No closure can reassign it (§28.3 *Captured owned bindings*), and the enclosing body is suspended for a synchronous call. This removes one rejected source under R. It is not applied, since it widens the in-place list beyond the owner's "unaliased local".
  - *Author's recommendation: R. Critic: R is coherent only together with Q8, and F is the smaller change to the existing field-borrow posture. Either needs the owner's word.*

That would be a new rejection outside #5496's letter. This proposal makes no §25.2 edit. ## 10. Self-critique (adversarial pass; resolved in the text above)

Counterexamples hunted against the rule, each traced; fixes applied in place.

1. **"The copy is unobservable" — the mediating store.** `Span<T>`'s setter stores `Buffer[Start + i] := value` through `this.Buffer`, a class borrow; the copy holds the same pointer, the store lands in the same `OwningBuffer<T>`. *Holds.* The synthesized auto-property setter: it is invoked only by an external assignment, whose target is the named location, not `this` of a member call — §3.1's accessor boundary states it. *Holds.*

## 13. Owner-delegated decision (2026-10-08)

*The owner accepted the direction on #5496 and delegated the move-only half (revised Q1 with Q2, Q6, Q7, Q8) to this run. This section records the decision, its grounds, the exact text that results, and what it leaves open. It is written against v0.319 at `7882177`; line numbers are of that tree, re-verified on 2026-10-08. The v0.320 commit composing in parallel (`5311c44`, in progress) shifts the spec's lines by +17 from §9.4 onward and is not depended on here; the graduating lane re-verifies every `old` against the tree it lands on, as process §4 requires.*

### 13.1 The decision

**F, with the confusion closed at the binding.** A bodied member call on a move-only receiver is **admitted at every source** and passes the receiver's storage **in place**; for the activation `this` is a borrow of that storage, as a class receiver's `this` is a borrow of its object. The type-confusion hazard — the one consequence of an in-place receiver that no disposed flag backstops — is closed where it arises: **a borrowing-match binding of a payload of move-only value type may not be live at a write point of the construct unless the scrutinee's source is provably unwritten** (§3.2's list, with a binding's source read through to its scrutinee's; a use as a receiver or operand is live across the call — critique round 2). Stated once, in §19.3, that rule covers the member body (`case this of …`, whose source the body never sees) and the `case h.C of …` twin over a field, element, `ref` parameter or operand alike. Three corollaries settle the remaining questions: an **`async` or iterator member cannot be called on a move-only receiver** (Q7, reject at the call site); the **`readonly`-field source is normative** (Q2) — one list, two consumers; the **operand question dissolves** (Q6) and the **scrutinee twin is folded** (Q8), since neither needs a rule the binding rule does not already state.

*R* — rejecting the member call at a source not provably unwritten — is **declined** and recorded (§13.3 item 12). Its rejection is coherent only with the binding rule beside it (§3.4, *What the reject does not close*), and once the binding rule is in place *R*'s extra rejection buys exactly one thing: a snapshot reading of `this` for a kind that, by definition, has no snapshot.

### 13.2 The reasons

**1. Soundness, traced under F.** Take an owning choice with a nested move-only payload and a member that binds it across user code:

```bezel
public class Conn
  public Id: int := 0;
end Conn;

public choice Pool
  Ready(conns: [4 owned]Conn?),     // move-only value payload ⇒ Pool is owning (§35.4)
  Empty;
  public method First(k: () -> ()): int
    case this of
      Ready(arr) => do k(); return arr[0]!.Id; end,   // (3) `arr` used after `k()`
      Empty      => return -1
    end;
  end First;
end Pool;

public class H
  public P: Pool := Pool.Empty;
end H;
```

With `h.P.First(lambda() => do alias.P := Pool.Empty; end)`, `alias` a borrow of `h`: (1) `this` addresses `h.P` in place; the tag is `Ready`; `arr` is bound — and because the payload is move-only, §35.5 makes the binding a **borrow**, which in place is the address of the payload bytes inside `h.P`. (2) `k()` runs `alias.P := Pool.Empty`: §28.7's drop-on-overwrite disposes the four connections (each flagged, K4.1) and stores the new tag. (3) `arr[0]!` reads the slot bytes. If the store left them intact, the read is a flagged object and faults deterministically in checked mode — the posture every borrow of a field's current value has (§28.3 *Scope*). If the store wrote **another payload-carrying case's bytes** there — `Pool.Other(n: int, s: string)` — the read reinterprets an `int` and a `string` reference as a `Conn?` slot: **type confusion, undefined in checked mode too**. Nothing in K4 reaches it, because no object was disposed under the binding; its *address* was retyped.

Under F the member body at (3) is a **compile error**: `arr` is a borrowing-match binding of a move-only value payload over `this`, whose source a member body cannot prove unwritten, used after a write point (`k()`). The fix is `var id := arr[0]!.Id; k(); return id;` — the read moves before the call and the binding is dead when the source can change. The same arm written as `case h.P of Ready(arr) => do k(); return arr[0]!.Id; end, …` in the caller is the same error for the same reason (a mutable field is not provably unwritten), and over a local `p` it is admitted (item 1: no closure can reassign a captured move-only local, §28.3 *Captured owned bindings*; a reassignment or `move` in the arm itself is K5.2's frozen consume while `arr` lives; a `ref p` argument in the construct is excluded by the list).

What F **leaves**: after `k()`, a read of `this` whole — `this.IsOk()`, a fresh `case this of` — sees the replacement, tag and payload together, a coherent value of the receiver's own type; a class-typed payload bound before `k()` (`Ok(c)`, `c: owned Connection`) is a *reference*, not an address into the union, and the overwrite disposes and flags its object, so a use faults exactly as `var c := h.obj; alias.obj := other; c.Ping();` does today. That is **class-receiver semantics**: a Bezel method on a class reads fields that any callee may have changed, and has always done so under the flag. *(Critique round 2, §14.)* Three conditions make "whole" true, and §13.3 states each one. (i) `this` must address a **whole location**, never payload bytes inside another value: a binding used as a receiver or operand is live across the call (B2). (ii) A location emptied with **no replacement** must be backstopped. After a null store or a holder kill, the bytes left in place hold runtime-managed references the disposal released, so §13.3 item 1 leaves such a value in a **disposed state** that checked mode tests on every read through `this` or a borrowing binding (B4). This is the value's K4.1 flag. (iii) An implementation must copy copyable payload bindings, and give `string`/function payload bindings their own reference, at binding (§13.6). F adds **no new K4.3 clause**. It does add *sites* to an existing one (B5). A class-payload binding over an in-place `this`, or over `case h.P of`, that is live across a write point which **moves** the field out to another domain is §28.3 *Scope*'s "slot kill *by move* … governed by the … domain clause ([K4.3]), a recorded obligation". The trust-admission report enumerates those sites as it does every field-held borrow's. Every other displaced object is flagged by the store or the disposal that displaces it.

**Is the binding rule sound and body-local?** A write point is defined syntactically, in evaluation order, over the pattern after the binding's case test, the guard and the arm. It is one of: a call whose resolved declaration is not `pure` (§22.15), an implicit one included; a store of a move-only value to, or a `move` out of, storage other than a local; a disposing store; an `await`; a `yield return`. *(Critique round 2, B3 and N4.)* The binding's liveness is K5.5's backward dataflow over one body, which the freeze already runs: live closures count, and exception edges count. A use as a receiver or operand is live across the call (B2). The source predicate is §3.2's, which reads the calling body only. A pattern binding's source is its scrutinee's (B1). For `this` the predicate is constant (not provably unwritten), so the member body is checked once, as §35.11 requires. For a payload typed by a type parameter, the binding's kind — copy, reference or in-place borrow — is read at the substitution, and the rule is enforced at the instantiation site under §3.6 rule 2, exactly as §7.10's copy demand and §9.2's equality use are: a `case this of Ok(v) => do k(); return f(v); end` in a generic choice body is admitted at every copyable and class substitution and rejected at a move-only one, with the diagnostic naming the instantiation, the binding and the write point. Under rule 2 the rejection is a requirement of the **constructed type**, "checked at every site that names it whether or not the program reaches that member" (round 2, N5), and §35.11's list of instantiation-time rules names it (round 2, B6). **Body-locality: local** for a concrete payload type; **carve-out** (generic instantiation, §3.6 rule 2's two clauses) for a type-parameter payload — the classification proposal 0105 §1 already gives the existing per-instantiation demands.

**2. Consistency with the recorded decisions.** Five were weighed.

- *Rationale §5.22's preference — unrepresentable over detected over silent.* The unsafe outcome (confusion) becomes **unrepresentable** under F: the in-place binding cannot exist across a point at which the bytes can change. *R* does not achieve that: it rejects the member call while §35.5's borrowing match over the same field stays admitted, so the confusion merely moves to the inlined `case` (B6). R is unrepresentable-for-one-spelling; F is unrepresentable-for-the-hazard. The *safe* outcome F leaves (a coherent fresh read) is "silent" only in the sense every class field read is.
- *K4.3's "recorded trust, or nothing".* F adds no K4.3 clause. Displaced objects are flagged by the store that displaces them. A value emptied with no replacement is held in a disposed state that checked mode tests, so its backstop is recorded. The retyped address is rejected statically. *(Corrected by critique round 2, B4/B5.)* The one trust F touches is the existing field-held clause: a class-payload borrow over an in-place receiver at a field, element or `ref` source, live across a write point that moves the field out to another domain, is a new **site** of §28.3 *Scope*'s recorded slot-kill-by-move obligation, and the trust-admission report lists it. *R* would add the same sites through `case h.C of …`, which it leaves admitted.
- *§28.3 Scope and K5.6 — fields and slots are not frozen; borrows of a field's current value live under the runtime-checked posture.* F is this posture applied to a move-only field's current value, with one static closure for the one read the flag cannot catch. *R* would have made the owning choice the only field kind whose current value **cannot be borrowed by a member call at all** — a departure from K5.6's posture for a reason (confusion) K5.6's posture does not have, since class borrows are references.
- *§7.4's field-narrowing refusal and its `readonly` exception.* This is *R*'s strongest precedent: §7.4 refuses to narrow a mutable field because of unseen writers, and names copy-to-a-local as the remedy. The analogy breaks at the remedy. Narrowing's remedy copies; a move-only value's remedy **moves the field out and restores it**, and a restore around a *call* (`var c := move h.C; try … c.IsOk() … finally h.C := c; end;`) is a K9.2 window with a throwable, user-code-running expression inside it — exactly the shape K9's build-before-take discipline exists to keep programs out of, since every callee in the window can observe the hole through an alias of `h`. *R*'s remedy would have taught, as the idiom for reading a `Result` field, the one K9 pattern the spec steers away from. F's remedy for the binding rule, by contrast, is a reordering (read before the call) in the common case, and the owning match over the take (`case move h.C of …`) where the arm really must consume.
- *§35.5's case semantics and §35.2's receiver rule.* §35.2 says `this` in a choice method is a borrow and a method invocation never consumes its receiver; §35.5 says a borrowing match over a field is "the default everywhere" and binds move-only payloads by borrow. F keeps both verbatim and adds one liveness condition to the second. *R* would have left the two in tension (a borrow allowed by `case`, forbidden by `.IsOk()`).
- *0105 body-locality.* Both designs are local. F's generic arm is a §3.6 rule 2 carve-out that already exists for the same shape of demand.
- *The declined options (ii) and (iii).* The owner declined by-address receivers for copyable kinds; F adopts storage semantics **only for the kind that cannot be copied**, and records (iii)'s decline as scoped to copyable kinds (§13.3 item 12). This is not a reopening: the owner's ruling was on the three copyable programs of §1, and both the critic and the owner flagged the move-only case as undecided.

**3. Cost.** In tree, zero flips either way (§12). To the idiom, the designs are not symmetric. *R* rejects the central `Result` idiom at fields — `_conn.IsOk()`, `_conn.IsError()` on a class's mutable owning-`Result` field — and offers a remedy that is a K9 window, or none at all for a `readonly` field without Q2. F rejects a shape the tree has never produced: a borrowing `case` that binds a **nested** move-only payload (an owning inline array or owning choice *inside* an owning choice) from a non-local scrutinee and uses it after a call. The ordinary owning `Result<owned Item, E>` has class payloads and is untouched by the binding rule at every scrutinee. Generic bodies pay at move-only instantiations only. *(Critique round 2, N4: stated honestly.)* Where the rule does bite, it bites hard. Over `this`, a field or a `ref` parameter, a nested move-only payload binding can be used only up to the first non-`pure` call. `Console.WriteLine(arr[0]!.Id); Console.WriteLine(arr[1]!.Id);`, a loop that calls anything, and a block-bodied property read through a slot are all rejected, and calling a nested owning choice's non-pure member on the binding is rejected too (B2). Reads of fields and auto-properties through slots, and calls to `pure` members, are free. The remedies are to read first, to take the field (`case move h.C of …`, K9.2), or to keep the value in a local.

**4. Implementability.** F reuses three things the compiler has: the move-only predicate (`isMoveOnlyValueType`, `src/sema/ExprTypecheck.cpp:4449`), the mutable-capture scan (`computeMutablyCaptured`, `src/sema/ExprTypecheck_Exprs.cpp:16233`; `mutablyCapturedNames_`), and the body-local liveness that the consume-site freeze runs. The write-point classification is a subset of §28.8.1's throwable-expression classifier (`ExprTypecheck.cpp:11981` region, "assume throwable" posture): calls, accessor and operator invocations, disposing stores, `await`, `yield return`; the pure arithmetic faults the inventory also lists are *not* write points. The codegen side is a no-op for the method path (CG29 already passes a pointer; for a move-only receiver `lvalueAddr` is the right pointer and the spill is skipped) and the accessor paths keep `lvalueAddr` for move-only receivers. *R* would have needed the same predicate plus a new call-site rejection and its diagnostic; the two designs are of the same size, and F removes a diagnostic *R* would have had to word around a `try … finally` remedy.

**5. Why not the hybrids.** (a) *F without the binding rule* leaves the confusion open — rejected on soundness. (b) *R plus the binding rule* is strictly more rejection than F for no additional safety — the binding rule already closes the hazard inside the member body regardless of the receiver's source — so its only yield is snapshot semantics for a kind that cannot have them. (c) *Copy the discriminant, borrow the payload* (§3.4 (c)) is a new representation with per-payload-kind rules for a hazard the binding rule closes with one sentence. (d) *A runtime tag re-check at each use through the binding* is "detected" where F is "unrepresentable", would need a new fault, and does not help when the replacement has the *same* case (then the binding silently reads the fresh payload). (e) *N10*, admitting a captured move-only outer local as unwritten: sound (no closure can reassign it; a `move` of it is frozen by its live capture) and cheap, but it widens the list beyond the owner's "unaliased local" wording for a shape the tree lacks — **not applied**, recorded as available to a future lane with a program that needs it.

### 13.3 The rule text that results (old → new; each `old` unique at `7882177`)

1. **spec §9.4** (replaces §8 item 1 and §3.4). *old* (line 1486, the paragraph's last clause): `… and \`i.X := 42\` through an interface view of a boxed record has no settable member to name.` *new*: the same, followed by §3.1's two ▲ paragraphs with these amendments, then the ▲ *Move-only receivers* paragraph below.
   - §3.1 ▲ first sentence: "A member call on a value-kind receiver — a record, choice, enum, inline-array or primitive receiver" → ▲ "A member call on a **copyable** value-kind receiver — a record, enum or primitive receiver, a copyable choice or inline-array receiver ([§15.3](#sec-move-only-value-types))". The deferred-activation sentence stays (copyable kinds).
   - §3.1 ▲ second paragraph's last sentence stays: "For a **move-only** receiver ([§15.3](#sec-move-only-value-types)) the choice is not free: see *Move-only receivers* below."
   - ▲ **Move-only receivers.** A move-only value ([§15.3](#sec-move-only-value-types): an owning inline array, an owning-classified choice) cannot be copied, so the fixed-value semantic above does not reach it. A call to a **bodied** member — a declared method or accessor of an owning choice ([§35.2](#sec-choice-members)), or an extension member over either kind — on a move-only receiver passes the receiver's **storage in place, at every source**, and for the activation `this` is a borrow of that storage, **bounded by the call** as a copyable receiver's fixed value is ([K8.4](#sec-kernel-k8)), and is a borrow as a class receiver's `this` is a borrow of its object. A whole-value overwrite of the storage that runs during the call, through an alias of its holder ([§28.7](#sec-reassigning-owned-fields)), is visible through `this` afterwards, whole, tag and payload together, and every payload object the store displaces is disposed by it and flag-backstopped ([K4.1](#sec-kernel-k4)). That is the posture every borrow of a field's or slot's current value already has ([§28.3](#sec-consume-site-freeze) *Scope*). A move-only value disposed in place **with no replacement** — the nullable location holding it set to null ([§35.9](#sec-choice-nullable)), or its holder destroyed ([§28.4](#sec-the-destructor)) — is left in a **disposed state**. In checked disposal mode a read of the value in that state, through an in-place `this` or through a borrowing-match binding of it, faults as `DisposedAccessException` ([§28.2](#sec-checked-disposal)): the state stands as the value's disposed flag, readable under the deferred reclamation the flag test already relies on, and unchecked mode elides the test. What such a store must never do is leave a borrow addressing bytes it has rewritten. Two borrows could. One is a payload binding of a borrowing match over `this`. The other is a `this` that addresses payload bytes inside another value, because the receiver expression was such a binding. [§19.3](#sec-patterns)'s rule *Move-only payload bindings across a write point* rejects both: `this`'s source is the caller's, which no member body sees, so it is never provably unwritten, and a binding used as a receiver is live across the call. A member whose activation outlives the call — an `async` ([§30.1](#sec-async-methods)) or iterator ([§29.3](#sec-iterator-methods)) member — **cannot be called on a move-only receiver**: the frame could hold the value only by consuming it, which a method invocation never does ([§35.2](#sec-choice-members)), and in place its storage would outlive nothing the frame can see ([K6.4](#sec-kernel-k6)); the call is a **compile error at the call site**, at every source — for a generic choice, at the instantiation whose classification is owning ([§3.6](#sec-derived-type-properties) rule 2) — the diagnostic naming a static member that takes the payloads it needs after a match. The compiler-provided operations of an inline array ([§15.1.2](#sec-members-and-operations): `Length`, indexing, `GetType`, `ToString`, equality) run no author-written body and are slot reads under [§28.11](#sec-element-slot-policy)'s posture, not member calls for this rule.

2. **spec §19.3** (new; the binding rule's home). *old* (line 4255, the paragraph *Pattern binding and ownership*, ending): `… The narrowing produced by the case arm is purely informational about the type tag; it does not change the ownership state of the scrutinee.` *new*: the same, then a new paragraph:
   > ▲ **Move-only payload bindings across a write point.** A borrowing-match binding of a payload of **move-only value type**, at any depth of the pattern ([§35.5](#sec-choice-borrowing-match); an owning inline array, or a nested owning choice), borrows the payload **in place**. It addresses storage inside the scrutinee's source, and a store to that source while the binding is live would leave it addressing another case's bytes, a confusion no disposed flag backstops ([K4.1](#sec-kernel-k4)). Such a binding may therefore not be **live at a write point** of the construct, **unless the scrutinee's source is provably unwritten during the construct**. *Live* has [K5.5](#sec-kernel-k5)'s meaning: some later use on a normal or exceptional path, a live closure that captured the binding included. A use of the binding as the **receiver** of a call, as an operand or `Equals(T)` argument of an operator ([§25.2](#sec-operator-overloading-restrictions)), or as the operand of a compiler-provided operation that invokes the element type's members (an inline array's equality, `ToString` or `GetHashCode`) is live **across** that call, because the callee holds the borrow for its activation. A **write point** is a point of the construct, in evaluation order ([§22.5](#sec-optional-parameters-and-named-arguments), [K9.5](#sec-kernel-k9)), in the pattern after the case test that selected the binding's payload, in the guard, or in the arm, at which one of the following happens:
   > - a call in any spelling whose statically resolved declaration is not `pure` ([§22.15](#sec-pure-members)) — a method, function value, constructor, operator, accessor or extension member, including one a construct invokes implicitly: a named slot's getter or a constant slot's `=` during matching ([§19.3](#sec-patterns)), disposal at scope end, an interpolation's `ToString`, or such a compiler-provided operation;
   > - a store of a move-only value to, or a `move` out of, storage other than a local of the body ([K9.2](#sec-kernel-k9));
   > - a store that disposes a displaced value ([§28.7](#sec-reassigning-owned-fields));
   > - an `await` or a `yield return`.
   >
   > Each arm's case test reads the source as it stands when that arm is tried ([§19.4](#sec-guards)), so a write point in a declined arm's guard is not a write point for a later arm's bindings. The scrutinee's source is **provably unwritten** in exactly these cases:
   > - a local declared by `var`, `using var` or `const`, or a parameter of the body, that is not mutably captured ([§7.4](#sec-member-access-on-nullable-values)) and is not named by a `ref` or `out` argument anywhere in the construct.    > - storage inside such a local.
   > - a `readonly` field outside its construction window, in [§7.4](#sec-narrowing-applies-to-locals-only)'s tracked shape.
   > - a borrowing-match binding whose own scrutinee's source is provably unwritten. A pattern binding's source is its scrutinee's source, so a binding is never a source in its own right.
   >
   > `this` in a value-kind member body is never such a source ([§9.4](#sec-value-receivers-are-borrows) *Move-only receivers*); neither is any other field, an element, a static, or a property or indexer read. The violation is a compile error at the use, naming the binding, the write point and the remedies: read what the arm needs **before** the point; or match the value where the construct owns it — the owning match over the take, `case move h.C of …` ([§35.5](#sec-owning-match); [K9.2](#sec-kernel-k9)'s restoration applies). For a payload typed by a **type parameter** the binding's kind is read at the substitution ([§3.6](#sec-derived-type-properties) rule 2): the use is admitted at a copyable or class substitution. At a move-only substitution it is a requirement of the constructed type, rejected at every site that names that type, as [§7.10](#sec-generics-and-nullability)'s copy demand is.

### 13.4 The questions answered

- **Q1 — F.** A bodied member call on a move-only receiver is admitted at every source, in place; the type confusion is closed at the binding (§13.3 items 1–2). *R* is declined and recorded (item 12).
- **Q2 — normative.** §3.2's item 3 (`readonly` field outside construction, §7.4's tracked shape) is normative for every consumer of the list: it is unobservable for the copyable representation choice and observable for the binding rule, where it admits `case this._pool of Ready(arr) => do k(); … arr …` over a `readonly` owning-choice field. Soundness is §5 item 3's (N9): the holder may be killed during the arm by a site-announced `Dispose()`, which disposes and flags the payload objects and rewrites no bytes. One list, one definition.
- **Q6 — dissolved; no separate question filed.** §25.2 already receives copyable operands as value copies and move-only operands as borrows of the caller's storage. Under F a member call on a move-only operand inside the operator body is in place like every other, and the only hazard — a payload binding of `case a of …` held across a call in the operator body — is the binding rule's, which classes an operand or `Equals(T)` parameter as a parameter binding the caller's storage (not provably unwritten). No use-site rejection of `h.C = x` is needed or added.
- **Q7 — reject.** An `async` or iterator member cannot be called on a move-only receiver, at every source: the frame cannot hold the value without consuming the receiver, and in place the storage outlives nothing the frame can see (K6.4). For a generic choice the rejection lands at the instantiation whose classification is owning (§3.6 rule 2; §35.11's check-once body discipline is untouched). Zero in tree. Copyable kinds keep §3.1's frame-held reading.
- **Q8 — folded, not filed.** The scrutinee twin is the binding rule's primary case, not a separate question: §19.3's paragraph is written over every scrutinee — `this`, a field, an element, a `ref` parameter, an operand — and §35.5 and §15.3 cross-reference it. Filing it separately would have put one hazard under two rules.
- **Q3, Q4, Q5** — unchanged from §9's recommendations (land the §8.6 sentence and probe; keep the predicate in §9.4 as one list; land in either order relative to 0134, whose `out`-root clarification §3.2 item 1 already defers to).

### 13.6 What this decision does not settle

1. **`!` over a nullable move-only location as a receiver** (`h.C!.M()` for `C?` an owning choice): confirm against §7.8 and the compiler whether the expression names the payload storage (then item 1's disposed-state clause covers the null store) or is rejected as a move out of a field (then the null-store half of that clause is vacuous, and the holder-kill half still stands).
2. **Inline arrays whose element type is an owning choice** (`[N]C`): confirm whether such an array is admitted and, if so, that it is move-only by §15.3's structural rule (its slots carry owned payloads), so that an element `arr[i]` is "storage inside" its root for §3.2 and never a free-standing writable source; §28.11 already rejects move-only element types for both collection families.
3. **The write-point classifier**: the normative set (non-`pure` calls in every spelling, implicit ones and those made during matching included; stores of a move-only value to, and `move`s out of, non-local storage; disposing stores; `await`; `yield return` — as revised by critique round 2) is, apart from the store/move points, a subset of §28.8.1's throwable inventory; the lane confirms the compiler's classifier can be narrowed to it, or records the over-approximation (pure arithmetic faults treated as write points) as a spec-ahead-of-impl delta rather than a rule.
4. **Binding-time copies and references** (critique round 2, N3). Confirm three things:
   - a copyable payload binding over an in-place scrutinee (`this`, a field) is copied at binding;
   - a `string`/function payload binding takes its own reference. #2450's no-retain relaxation (`src/codegen/LlvmBackend_Setup.cpp:27524ff.`) is keyed on a bare-identifier local scrutinee and must not reach `this` or a field;
   - the CG29 spill (`Calls2.cpp:12485–12494`) is skipped for a move-only receiver. Today that spill is a bitwise copy of a move-only value, which already exposes released runtime-managed payloads after any overwrite.
5. **The disposed state's encoding** (critique round 2, B4). For an owning choice, a tag value no case uses. 6. **Adjacent, pre-existing, out of scope** (critique round 2, N7). Take a whole-scrutinee `var a` binding of an owning **inline-array** field whose holder is killed in the arm. An interface-typed slot of that array holding a box is runtime-managed (§15.1.1), and the box is released with no flag. File this separately at graduation. It is not introduced by this proposal.

## 14. Critique (round 2)

> **F stands; R is not the sound alternative.** Round 2 found four soundness holes in §13 as drafted (B1–B4 below). Three of them sit in the §19.3 binding rule, and *R* would need that rule too, for the `case h.C of …` twin it leaves admitted. *R*'s own in-place list ("a local binding … of the calling body") also admits a member call on a pattern binding (B2). The fourth hole (B4) is one *R* avoids only at a mutable field: it keeps it at the `readonly` field Q2 makes necessary. Every hole is closed by rule text inside *F*, and §13.3 now carries that text. The decision is not reopened, and §13 is not rewritten to *R*.

An independent adversarial pass on §12–§13, against v0.319 (`7882177`), with the v0.320 working tree (`5311c44`) checked for collisions. The full record is in `scratch/v0321/p0135-13.critic.md`, and the sweep is `scratch/v0321/sweep/mo_sweep.py`.

**The base program is rejected.** §13.2's `Ready(arr) => do k(); return arr[0]!.Id; end` over `this`, and the same arm over `case h.P of`, are both rejected. Over a local they are admitted. The trace in §13.2 is correct.

**BLOCKING (6; all resolved in §13).**
- **B1, nested matches.** "An unaliased local binding … of the body" admitted a pattern binding as a provably unwritten scrutinee. `case this of Wrap(inner) => case inner of Ready(arr) => do k(); … arr …` escaped the rule, and so did `case h.P of var y => case y of …`. *Fixed:* the list names `var`/`using var`/`const` locals and parameters. A binding is provably unwritten exactly when its scrutinee's source is, and the rule covers move-only payloads at any depth (§13.3 item 2).
- **B2, a binding as a receiver or operand.** `inner.Count(k)` uses `inner` before the call. Inside `Count`, `this` addresses payload bytes inside the outer value, and an overwrite by `k()` retypes them under a fresh `case this of`. So §13.3 item 1's "visible … whole" was false for such a `this`. User operators and `Equals(T)` (§25.2 borrows) have the same shape, and so do an inline array's compiler-provided `=`/`ToString`/`GetHashCode`, which call element members between slot reads. *Fixed:* such a use is live across the call (items 1, 2 and 3).
- **B3, write points and liveness.** Four misses. Implicit calls during matching (a named slot's getter, a constant slot's user `=`) after the case test were not counted. `move h.P` followed by a store-back of another case into the moved-from field involves no call and no disposing store (§28.7). A lambda that captured the binding before `k()` and is invoked after it has no textual "use after". Exception edges were not named. *Fixed:* liveness in K5.5's sense, with live closures and exceptional edges counted, and write points in evaluation order over the pattern, guard and arm. Stores of a move-only value to non-local storage, and `move`s out of it, are write points (item 2).
- **B4, `this` after its location is emptied with no replacement.** A null store to the nullable location, or a holder kill (`alias.Dispose()`, or an owner-field overwrite), leaves `this` reading bytes whose `string`/function/box references the disposal released. Nothing tests a flag on a read of `this`: K4.1's check is "a flag test on member entry" of a class instance. *Fixed:* such a value is left in a **disposed state**, and checked mode tests it on every read through an in-place `this` or a borrowing binding. That state is the value's K4.1 flag. The move-only `this` is bounded by the call (item 1; producers row, item 6; C.5, item 8).
- **B5, the K4.3 claim.** "Not a K4.3 entry" was wrong. Take a class-payload binding over an in-place `this` (or over `case h.P of`) that is live across a write point which moves the field out to another domain. That is §28.3 *Scope*'s recorded slot-kill-by-move obligation. *Fixed:* F adds no K4.3 clause. It adds sites to that clause, which the trust-admission report lists (§13.2 items 1–2; rationale item 10).
- **B6, §35.11.** Its closed list of instantiation-time, classification-dependent rules contradicted the type-parameter arm of the binding rule and Q7's generic case. *Fixed:* new item 15.

**NON-BLOCKING (9).**
- **N1:** "after" means evaluation order (§22.5; K9.5's RHS-first).
- **N2:** each arm's case test reads the source when that arm is tried (§19.4). A declined guard's write point does not count against a later arm's bindings, and the compiler may not hoist one tag switch across it.
- **N3:** at graduation, verify that bindings take copies and references at bind (#2450's no-retain relaxation) and that the CG29 spill is skipped for move-only receivers (§13.6 item 4).
- **N4, cost, stated honestly.** A non-`pure` call is the write point, and `pure` calls are exempt (§22.15: a pure call "writes no storage outside the call's own frames"; auto-property getters are implicitly pure). Even so, a nested move-only payload over `this` or a field can be used only up to the first non-pure call (§13.2 item 3; code-generation reference text).
- **N5:** at a move-only substitution the type-parameter arm is a requirement of the constructed type, checked wherever that type is named (§3.6 rule 2).
- **N6:** the move-only `this` is bounded by the call.
- **N7:** a pre-existing owning-inline-array box hazard under a holder kill is recorded for filing (§13.6 item 6).
- **N8:** no collision with v0.320. Every §13.3 `old` is unique in both trees. The code-generation reference §7.3 block shifts by +26 lines.
- **N9:** *R* inherits B1–B3 and keeps B4 at `readonly` fields.

**Sweep (re-run against the strengthened rule).** 13 files declare a choice with a move-only value payload. Every borrowing match over one has a local or parameter scrutinee (or is an owning match), so every nested scrutinee roots in a local. The one field scrutinee among them (`case h.o of`, 4568 T2) is value-like. The 25 other non-local scrutinees in `tests/` bind only copyable, class or `string` payloads. **Flips: zero.**

## 15. Graduation (v0.321)

Every `old` of §13.3 was re-verified against v0.320 (`9e426eb`; `src/` byte-identical to `7882177`) and occurs exactly once; every anchor the new text links resolves to the heading it names. §8 items 4, 5 and 7 (§8.6, §7.4, §26.7) landed as written there, the §7.4 sentence extended by one clause for a move-only `n` (borrowed in place instead, §9.4 *Move-only receivers*). The edit set also carries [#5535](https://github.com/s8lap/bezel-lang/issues/5535): §7.4's `readonly` root reads "`v._f` where `v` is a local variable or non-`ref` parameter that is itself narrowing-tracked", the tracked shape §19.3's `readonly` source cites.

**One deviation from §13.3, and three precision edits.**
- *The copyable in-place list drops the `readonly` field* (§3.1's second paragraph). A `readonly` field has no writer, but its holder can be destroyed during the call (`alias.Dispose()`), and in-place bytes would then hold `string`/function/box references the destructor released, with no flag a read of `this` tests; a copy holds its own references (§3.1: "the references it holds included"). Q2's normative `readonly` source stands for §19.3's list, where §9.4's disposed state backstops a holder kill. For a copyable kind the change only narrows implementation latitude, so no program's meaning moves. The list's obligation now reads "no code reachable during the call can write or release it".
- *The first source of §19.3's list* reads "a local variable or parameter of the body, other than a binding a borrowing match introduces" where §13.3 named locals "declared by `var`, `using var` or `const`". B1's exclusion is kept (a borrowing-match binding is a source only through its scrutinee), and an owning match's transferred binding, a `for` variable or an `out var` local is no longer rejected for its declaration form. Without this, `case move h.C of Wrap(x) => case x of Ready(arr) => do k(); … arr … end` — the remedy the rule itself names — would be rejected over the owned local `x`.
- *"Storage inside such a local"* (in §9.4 and §19.3) now says "reached without leaving the value (§9.4's key)", so `h.P` over a local `h` of class type is not read as storage inside `h`.
- *Critique of the graduation* (`scratch/v0321/g0135.critic.md`). §19.3 also covers a whole-scrutinee binding over a move-only payload binding (`case inner of var z`), and a closure that captured the binding is live across a call that invokes it or takes it as an argument; §35.5's summary names the `readonly` source; every implicit disposal is a write point; the move-only member list says neither move-only kind can be extended (§26.2).
- §19.3's binding rule is indexed in Appendix C.7 (*Patterns and `case`*), not C.5; C.5 carries the receiver row. The code-generation reference's §7.3 example terminates its single-statement arm (`Empty => return -1;`, §19.2).

**§13.6 verifications, by reading (no build).**
1. `h.C!.M()` over a nullable owning-choice field: §17.8's `!` "does not move, copy, or borrow beyond what reading `x` already does", so the receiver names the payload storage inside the `C?` location and §9.4's disposed-state clause covers a null store during the call. The compiler lowers the receiver by value and spills it (`LlvmBackend_Calls2.cpp:12272`, `12485–12494`).
2. `[N]C` over an owning choice `C`: §15.1's element-type list names primitives, records, classes and runtime-managed types only, and §15.3 makes an inline array move-only exactly when its slots carry `owned`; `common::isMoveOnlyValueType` (`src/common/OwnershipFacts.cpp:2327`) matches §15.3 and classes `[N]C` copyable. Admitted and copyable, `[N]C` would duplicate owning values, so the landing rules it: §15.1 rejects a move-only element type, at the instantiation site for a type parameter (zero programs in `tests/` and `docs/`; the compiler admits it today and is tracked). This also keeps the first source of §19.3's list sound: no local other than a borrowing-match binding borrows move-only storage in place, which a `for` variable over a move-only element would.
3. The write-point classifier is new: no compiler code computes it. §28.8.1's throwable classifier over-approximates it (it counts pure arithmetic faults); an implementation that reuses it rejects more than the rule and is a spec-ahead-of-impl delta.

Both are tracked compiler items.
5. The disposed state's encoding: no compiler support; tracked.
6. The owning-inline-array box hazard under a holder kill (round 2, N7): filed separately as a pre-existing question.
