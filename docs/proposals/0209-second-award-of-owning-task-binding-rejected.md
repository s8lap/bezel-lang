## 0. Summary

§30.4 makes a Pattern B task single-consumer: "the first await spends the task regardless of outcome (success, fault, or cancellation), and a second await raises `InvalidOperationException`". The static half of that rule reaches a **plain owned local** only, and for a mechanical reason: the award consumes an owned operand (the consume table's K3.5 row), so a second `await t` is a moved-from read; a `using var` cannot be moved out of (§28.3), so its read is a borrow and its award was left to the run-time exception — the #1785 reading at v0.190, chosen as the one consistent with §28.3, not for any reason about the fault. The fault is as certain through a `using var`, a plain parameter (q09) or any other local as through an owned local, and the language already states the layered reading for the structurally identical case one section earlier: a lazy query's enumeration right is "an affine discipline … it is the *right* that is spent, not the binding's ownership … a compile error where the flow analysis can see it statically; where a re-enumeration is reachable only at runtime, it raises `InvalidOperationException`" (§29.11).

This proposal applies that reading to the award: **a second `await` of a Pattern B task through the same local or non-`ref` parameter binding, whatever the binding's ownership, that the first award dominates on every path is a compile error at the second await, naming the first.** The spent award is a flow fact of the binding and is read exactly as §7.4 reads its narrowing facts — it holds at a point only where it holds on every path reaching it, §7.4's `try` model applies, and a reassignment, a `ref`/`out` pass or a mutable capture across the award clears it. Everything the fact does not reach keeps the run-time `InvalidOperationException`: a field or a slot (not a carrier — another continuation can overwrite it across the very suspension the first await is), a second iteration of a loop over a task bound outside it (q10; a back edge is not dominance), the point after a `try` whose protected block awarded (the retry-after-fault shape of `async_sync_wait_941`). Nothing is newly admitted; the award's semantics (owned operand consumed, borrowed operand spent and left to its holder, v0.335) are untouched.

Measured reach: one guide example that demonstrates the exception, two rule-corpus cases, three gtest rows — every one written to observe `InvalidOperationException` on a straight line — and nothing in the spec's or stdlib's examples.

## 1. The text today

> `OwningTask<T>` is single-consumer by type […]: **the first await spends the task regardless of outcome** (success, fault, or cancellation), and a second await raises `InvalidOperationException`, even after a successful first await — the result has already been moved out.
>
> — §30.4, v0.345

> An **owned** operand task is disposed implicitly by the award, without disposing its result; a **borrowed** one is spent and stays its holder's (both below); either way the task cannot be awaited again, and a second await raises `InvalidOperationException`.
>
> — §30.5, v0.345

> `await` on a `OwningTask<T>` […] a second await a compile-time moved-from read on an owned operand and `InvalidOperationException` on a borrowed one ([§30.5]).
>
> — Appendix C.6, v0.345

> A second enumeration, or any other use after the first, is a compile error where the flow analysis can see it statically […]; where a re-enumeration is reachable only at runtime, it raises `InvalidOperationException`
>
> — §29.11, v0.345

The verdict is split by the operand's **ownership** — moved-from read on an owned operand, exception on a borrowed one — although the fault is a property of the task's result buffer, not of the binding (v0.335's own finding: "Pattern B's single award is the **spent** state §30.4 already names, a property of the result buffer, not of the task's life"). Guide 04 §3 teaches the split as "enforced twice over" and shows the borrowed shape with a run-time comment.

Two facts. **The fault is certain** wherever the first award dominates the second: §30.4 spends the task at the first award whatever its outcome. **The compiler already tracks it**: `recordAwaitOperandConsume` (`src/ownership/Ownership_Checks.cpp:21804–21850`) resolves the operand to the binding, tests the binding's state and reports the second await — and returns early, by design, for the immovable bindings (`if (st->implicitDischarge) return;` with the v0.190 comment: "the single-consumer guarantee is enforced at RUNTIME"). The change is to track a spent-award flag on those bindings beside the consume state the owned ones carry.

## 3. Options

- **O0 — the status quo.** The split by ownership; the certain fault through a borrowed binding is an exception at run time.
- **(a) — a mandated warning** for the dominated second award through a borrowed binding, severity unchanged. Declined (§7): the owned twin is an error, §29.11's twin is an error, and a warning as the end state of a certain fault is the inversion rationale §5.28 reserves warnings against.
- **(b) — the compile error through any local or non-`ref` parameter the first award dominates, §7.4's reading of the fact (adopted).**
- **(c) — (b) plus field and slot carriers** (`await _t; await _t;`). Declined (§7): the first award is a suspension point across which another continuation of the domain can overwrite the field or the slot with a fresh task — §7.4's unseen-writer ground for never narrowing a mutable field — so the second award is not certain to raise.
- **(d) — (b) plus a K7.4-style no-flow-around-a-back-edge rule** for a loop awarding a task bound outside it (q10). Declined (§7): the first iteration's award is sound and the loop may run once; the shape is the run-time exception §30.4 defines, as the lazy query's re-enumeration through a back edge is §29.11's.

## 5. Decision

**Option (b).** Stated in §30.5 *Consumer-side rules* (the home of the award's operand rules), restated in one sentence in §30.4 and in Appendix C.6:

- **The rule.** A second `await` of a Pattern B task through the same **local** binding — plain, `using var`, `await using var`, `const` — or the same **non-`ref` parameter**, whatever the binding's ownership, that the first award dominates on every path is a compile error at the second await, naming the first. A second award reachable only at run time — through a field, a slot or another binding, or on a path the first award does not dominate — raises `InvalidOperationException`.
- **The fact.** The spent award is a flow fact of the binding, read exactly as §7.4 reads its narrowing facts: established at the award; holding at a point only when it holds on every path that reaches it (so a loop's back edge establishes nothing at the loop head, and a `try`'s arms and the point after it see only what every exit carries — §7.4's `try` model); invalidated by a reassignment of the binding (a fresh task, unspent), by passing it as a `ref` or `out` argument, and by a mutable capture across the award itself (the award is a suspension, and a closure that writes the binding may run across it). Fields and slots are not carriers, on §7.4's ground.
- **For an owned operand** the award is also the binding's consume (K3.5, unchanged), so the second await is a moved-from read as well; the verdict is the same and the diagnostic may name either.
- **The diagnostic** names the first award and the remedy: bind a fresh task (`using var t2 := sem.AcquireAsync();`). A retry after a fault is the same shape — §30.4 spends the task "regardless of outcome" — and the remedy is the same.
- **What does not move.** The award's semantics: an owned operand is consumed and disposed by the award, a borrowed one is spent and left to its holder (v0.335). K3.5's row, K5's clauses, the K7.4 join rule for the owned operand, §30.9's fault retention, the `static readonly` exclusion (note (j)).

**Kernel classification** (process §9): a **derivation** — K3.5 (the award is the site-announced consume of an owned operand) + K7.4's dominance (the "every path" reading §28.2 and §7.4 already use), applied to the award right the way §29.11 applies it to the enumeration right; no axiom moves, no kernel text moves. **Body-locality** (proposal 0105 §1): local — the fact lives in one body's flow graph over that body's bindings; a parameter's award in a callee says nothing to its caller.

## 9. Self-critique (adversarial pass)

1. **Is the owner's bar met?** Safer: a certain `InvalidOperationException` becomes a compile error wherever the compiler can see it, with the exact analysis it runs for the owned twin and for §29.11. Simpler: one verdict for one fault instead of two keyed on an accident of §28.3's no-move rule; Guide 04 loses its "enforced twice over" caveat. Migration: every measured site is a demonstration of the exception, and each keeps its subject with a one-line change. Not a taste change: the language already made this choice twice (the owned twin; §29.11). The harm it removes is lower than a silent wrong read (a deterministic exception in both modes), which is why the research lane ranked it fourth; the bar is "clearly an improvement", not "the largest one".
2. **Does the rule reject anything sound?** The §7.4 reading is deliberately conservative: a `try` with arms hides the protected block's award from the point after (the #941 retry shapes stay admitted and raise at run time), a loop's back edge establishes nothing, a mutable capture clears the fact at the award itself, and a reassignment clears it. One over-rejection exists on paper: a second await that is itself in dead code the first dominates (`if false then await t`) — §7.4's facts do not read constant conditions either, and the shape has no site.
3. **The `const` binding.** `const t := Make();` is a runtime `const` holding an owned production — rejected by §21.1 (*Ownership*: "must not be an owned production"); a `const t := other;` over a task is a borrow pin and is a local carrier like any other. Named in the rule for completeness; it changes no verdict.
4. **Cross-body.** A parameter's award in a callee says nothing to the caller: `await Twice(t)` in q09's `Main` sees no fact about `t`, and a `using var t := …; await Twice(t); using var b := await t;` in the caller is the run-time fault — the parameter boundary §29.11 also stops at ("a plain `IEnumerable<T>` parameter is statically untracked — the affine tracking is by provenance"). Stated in §5 (body-locality).
5. **Fields, slots, statics.** Not carriers; §30.5's edit says so and names the run-time fault for them. A `static readonly OwningTask<T>` cannot exist (note (j)); an `owned readonly` instance field could in principle be tracked in §7.4's `readonly` shape, which is the reopening bar on row (c).
6. **Interaction with 0205 and lane F.** 0205 rejects a use the explicit disposal dominates, through the variable and through a borrow; this proposal rejects an award the first award dominates, through the binding. Both read dominance over one body; neither touches the other's text (0205 edits §28.2, §28.3.9, §28.3.12, §28.10; this proposal edits §30.4, §30.5 and C.6). A `t.Dispose(); await t;` on a `using var` is 0205's business (a use after a dominating explicit disposal), not this proposal's.
7. **Other passages stating the old rule.** Swept by grep over the twelve documents for `second await`, `single-consumer`, `spent`, `InvalidOperationException` near `OwningTask`: §30.4, §30.5 (two sentences), C.6, rationale §12.1 (the bullet), Guide 04 §3, the code-generation reference §4.3 (the Pattern B row) are edited; §30.5's `using var task := SomeFactory(); var x := await task;` sentence gains the one clause; §30.9's fault retention, §30.11, §22.12 note (j), rationale §12.15's v0.335 paragraph and the stdlib's `OwningTask<T>` sentences (§6.3's `AcquireAsync` paragraph, §6.7's `WhenAll` note) describe the award's semantics or the single-award *type* and stand; the changelog's v0.190 and v0.335 entries are pinned history.
8. **Implementation risk.** The flag must be per path and joined conservatively (a maybe-spent binding establishes nothing), or a loop head would carry a false fact; the deferred-poison discipline the file already uses for the moved-from arm (#3931) applies. The diagnostic must not fire on the owned twin twice (the moved-from read already reports); one report per site.
9. **Composition (v0.346).** The lane's re-cut of `s30_5_0019` (`var go := true; if go then using var r := await t; end;`) makes the first award non-dominating but moves `r`'s scope end, so the case would print `closed` before `spent` (measured on r35). The landing re-cuts the unbanked case instead with the second award through a plain parameter of a helper, `Retry(t)` awaiting `t` once — another binding, so the run-time `InvalidOperationException` — which keeps the case's `output` and its `rule:` line. The tracker re-cuts `s30_4_0002` and the gtest rows, and must check each re-cut's output the same way.
