## 3. Flags — tier 2: design-level interactions with v0.242–v0.246, for the owner (flag, don't fix)

1. **0008 × v0.242 (proposal 0079) — `BitOperations` vs §6.5's now-native shift faults** *(the charter's named candidate, confirmed)*. Three of 0008's arguments quote or lean on §6.5's **repealed** silent masking: **(a)** §2's "strictly expressible" ripple-carry argument quotes "*a shift never raises `OverflowException`*" — now false as stated (in-domain shifts still don't fault, so the adder construction itself survives, but the quotation no longer matches the spec); **(b)** §3's `Shl` exclusion — "§6.5 *already* provides wrapping shift semantics … reduces the count modulo the width … A `WrappingShl` would duplicate the built-in operator. There is nothing to add" — the exclusion's entire ground is repealed: the built-in `<<` is now the *checked* shift, and the old masked-count behaviour has **no named home** (its sanctioned spelling is the manual `v << (k & 31)`); **(c)** §5.2's rotation contract justifies its offset handling *by analogy to the repealed rule* ("`offset` is reduced modulo the width **(as shift counts are, §6.5)**; never faults") — the cited precedent now points the other way. **Reconciliation options:** (i) keep rotation modular on its own grounds (rotation is inherently periodic — rotate-by-width is the identity; re-word the parenthetical, drop the §6.5 analogy), and record that masked shifting is deliberately spelled `k & 31` with no `WrappingShl` row — the smallest change, likely the right one; (ii) align rotation offsets with the new `0..width−1` fault domain for posture consistency (a real behaviour change to the proposed contract); (iii) *add* a `Wrapping` shift row now that the built-in no longer masks (re-opening the §3 exclusion on its changed ground). Needs an 0008 design-pass decision before implementation; the header now carries the ⚠ pointer.

   **RESOLVED 2026-08-12 —** option (i) executed as ruled (the owner's direction on the recorded flags): rotation re-grounded on its own periodicity, `v << (k & 31)` recorded as the deliberate-mask spelling, the §3 `WrappingShl` exclusion standing re-reasoned, the §2 claim re-derived — [0008's "Delegated ruling 2026-08-12"](../0008-integer-toolkit.md).

2. **0022 (and 0053 by citation) × `where T: hashable` — ruling 2's premise has expired.** 0022 §5.1/§10 Q2 poses the `Assert.Equal<T>` eligibility fork as *(i) compiler-known constraint* vs *(ii) `where T: IEquatable<T>`*, on the stated premise that "the equality-bearing constraint is **not a user-writable `where` clause** today (§14.2 …)". That premise — true at the v0.177 pin — expired at **v0.214**, when `where T: hashable` joined §14.2's derived-property constraints (v0.242 then renamed the *property* to match the keyword). A third option now exists that is strictly better than both horns: declare `Assert.Equal<T>(…) where T: hashable` as **ordinary generic code** — full §8.3 coverage, the instantiation-site diagnostic, no compiler-known machinery (the stdlib's own `Counter<K>` already ships this exact spelling, stdlib §4.20). The expired sentence was deliberately **left in its original spelling** (respelling it would have minted a false claim); the recorded acceptance ruling ("compiler-known, carrying the hashable derived-type-property constraint") likely collapses to the constraint spelling with no compiler work. **0053** inherits the citation (§4.1/§4.2 route `AddProperty`'s enforcement "exactly as `Assert.Equal<T>`'s … constraint"); its own *generatable* classification is genuinely not `where`-writable and is unaffected — only the cited mechanism's description needs to follow whatever 0022's re-cut says. *Provenance note: this expiry predates the graduation program (v0.214); the v0.242 vocabulary respell is what surfaced it.*

   **RESOLVED 2026-08-12 —** the third option executed: `Assert.Equal<T>(…) where T: hashable` as ordinary generic code, acceptance ruling 2 superseded with the premise expiry recorded honestly — [0022's "Delegated ruling 2026-08-12"](../0022-test-framework.md); 0053's citations conformed (§3.4/§4.1/§9/Q2).

3. **0047 × v0.243 — the calculus `throw` vs the Exception-derived requirement.** The calculus (§3.1) has no inheritance: `throw Rhs` throws any owned class `C`, and §5.3's validation bridge pretty-prints calculus programs as *real* Bezel run through `bezelc`. A printed `throw x` at `x: R` (a plain generated class) is a **compile error since v0.243**, so every model-accepted throw-program would spuriously differ as a bezelc reject — a systematic false mismatch in the verdict differential. **Reconciliation options:** (i) the printer derives every *thrown* class from `Exception` (`public class R: Exception … end R;`) — free, and sound: v0.243's own clause-by-clause verification records that the exception-ownership rules are base-class-blind, so the ownership verdicts the differential compares are unchanged; (ii) the calculus adds a thrown-class kind premise (heavier, models a typing fact irrelevant to T1–T3); (iii) exclude throw-programs from the differential (loses coverage of the K3.8/K4.2 announced-kill path — the worst option). (i) looks clearly right but is 0047's S0-stage design call, not a respell.

   **RESOLVED 2026-08-12 —** option (i) executed: the bridge printer derives every thrown class from `Exception` — [0047's "S0 design notes — delegated rulings 2026-08-12"](../0047-mechanized-core-semantics.md), note 1.

4. **0047 × v0.209/v0.246 — the §3.1 A7-by-omission note misstates A7's scope.** "The absence of a transfer marker in **any arm/operand position** is axiom A7 modeled by omission" was written against v0.197, when A7 still covered arm positions. Arm positions have carried the K3.4 marker since **v0.209** (proposal 0056), and v0.246 rewrote A7's register row again: its rejected positions are exactly the `??`-operand and operator-operand halves, now on purely semantic grounds (the unified `move` *parses* there). The calculus's actual omission — it has no arm/operand expression positions at all — is a consequence of A-normalization, not of A7. The note should be re-aimed at the two real A7 positions (or re-grounded on the A-normal form) at 0047's S0 hardening; wording-level, but it names an axiom, so it is not a mechanical respell. *Provenance: pre-program staleness (v0.209), sharpened by the v0.246 row rewrite.*

   **RESOLVED 2026-08-12 —** the §3.1 note re-aimed at A7's two real positions (`??`-operand, operator-operand), the calculus's general omission re-grounded on A-normalization, §4.3's disposition row conformed — [0047's "S0 design notes — delegated rulings 2026-08-12"](../0047-mechanized-core-semantics.md), note 2.
