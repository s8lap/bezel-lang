## 0. The surface, in one block

Every enum `E` with underlying type `U` carries, compiler-provided and unoverridable — by a member or by a declared constant — beside the existing member:

```bezel
public static method FromUnderlyingOrNull(value: U): E?;   // shipped v0.242 (#3044)
public static method FromNameOrNull(name: string): E?;     // ▲ v0.293 — band 2, total
public static method NameOf(value: E): string;             // ▲ v0.293 — total
```

`FromNameOrNull` and `NameOf` are the two directions of **one table — the enum's declared-identifier table**: each constant's own bare identifier, the table §17.9's `nameof(E.A)` reads at compile time and stdlib §2.13's `Type.EnumNames` lists. `E.NameOf(E.A) = nameof(E.A)` for every written constant; `NameOf` extends that to a runtime value. Matching is exact: ordinal, case-sensitive, nothing trimmed; a digit string names no constant because no identifier begins with a digit. Under duplicate values, `NameOf` gives the first-declared constant's identifier and `FromNameOrNull` accepts every declared identifier, so the pair round-trips **up to aliasing**. A `serialized "<name>"` rename (§9.8) changes the encoded form only and is invisible to both. No throwing tier, no `Try` shape, no generic `Enum.Parse<E>`, no change to `ToString` (§4 records each decline, and the serialized-name alternative with it).

## 1. The gap

**As filed.** #2244: "There is no `Enum` static class and no generic string→enum parse anywhere in the stdlib. §2.13's `Type.EnumNames`/`EnumValues` are described as 'the building blocks for … string-to-enum parsing' but no parse member exists … The common workload is config/CLI strings → enum (log levels, modes, formats). Today the only spelling is a hand-written per-enum `case` — idiomatic for one enum, boilerplate at N enums." The sketch — `Enum.Parse<E>`/`TryParse<E>`/`ParseOrNull<E>` "where `E: enum`", "matching declared constant names (ordinal, case-sensitive; no numeric strings — those are the §5.4 cast's job)" — was explicitly "needs design, not proposed here". Both facts still hold at v0.291: `grep -rn 'Enum\.Parse\|FromName' docs/ src/ tests/` finds nothing, and stdlib §2.13 still says it (`docs/Bezel_Standard_Library.md:634`).

**The spec's own example is the boilerplate.** §10.4's `Priority` (`:1718-1736`) hand-writes both directions: a `Name` property over a `case` (value → name) and a `public static method Parse(text: string): Priority?` over a `case` (name → value). Rationale §9.12 already found the first was costing the documents (`docs/Bezel_Design_Rationale.md:1228`).

**One premise of the issue is wrong and the gap is wider than filed.** The issue says "the constant-name table already exists for `ToString` and serialization synthesis". It exists for serialization only: §8.5 (`:1238`) renders an enum by "the type's qualified name" — `$"{Priority.High}"` is `"App.Priority"`, not `"High"`. So there is **no value→name surface for a runtime value either**, outside a serializer. §17.9's `nameof` (`:3479-3500`) is the closest existing surface and falls short on the one axis that matters: it takes a **written** constant, not a value — `nameof(Priority.High)` is `"High"`, but for `v: Priority`, `nameof(v)` is `"v"`, the local's name ("the source-level name of an identifier as a compile-time `string` constant"; "for a dotted expression, the result is the rightmost identifier"). It is, however, the table the value→name direction must agree with (§3.2). A parse without an inverse over a runtime value is half a round trip; §3.4 takes the inverse.

## 3. Design

### 3.1 The two members

```bezel
public static method FromNameOrNull(name: string): E?;   // ▲
public static method NameOf(value: E): string;           // ▲
```

Compiler-provided on every enum `E`, at every nesting depth (#3601's walker already reaches nested enums for `FromUnderlyingOrNull`); no declaration is written; a user **member or declared constant** named `FromNameOrNull` or `NameOf` on an enum is a compile error, exactly as for `FromUnderlyingOrNull` (`src/sema/TypeResolution_Checks.cpp:676-684` already rejects a constant of that name, since constants sit in `t->members` — §3.9 records the spec text catching up). Both are total. Both are statics with the enum type as receiver — the shape sema's recognition device (`enumTypeNamedBy`) already handles.

### 3.2 The matching rule: the declared-identifier table, exactly

**Which name.** `FromNameOrNull` matches against — and `NameOf` returns — the constant's **declared identifier**: the bare name as written, never a qualified `E.A` spelling. Not the serialized name, and not both. This is the table §17.9's `nameof` reads and stdlib §2.13's `EnumNames` lists, so after 0124 three surfaces agree on every enum, renamed or not: `Mode.NameOf(Mode.Fast) = nameof(Mode.Fast) = typeof(Mode).EnumNames[i] = "Fast"`. Reasons, in order of weight:

1. **Coherence.** `nameof` and `NameOf` are one letter apart and both mean "the name of this constant"; if they read different tables they disagree on every renamed enum — a defect generator with no diagnostic. `EnumNames` is documented as the building block for validation lists and help text; a list that validates against a different table than the parser reads accepts what cannot be parsed and rejects what can. One table closes both.
2. **The serialized name is a statement about the encoded form.** §9.8's rename clause is scoped by its own words — "the constant is encoded as `<name>` rather than its identifier" — and the encoded form already has its own complete round trip (§9.8's synthesized `Serialize`/`Deserialize`). A program that receives a wire spelling parses it as what it is: serialized text, through the §2.15 deserializers.
3. **Well-definedness by construction.** Identifiers are unique within a declaration (a duplicate constant name is a redeclaration), so `FromNameOrNull`'s answer is unique without leaning on §9.8's uniqueness clause — whose reach over enum constants (it speaks of "the type's components") is a reading question this proposal no longer needs to settle (§3.9).
4. **The cost, and why it is accepted.** A configuration or CLI boundary that wants to accept the *wire* spelling of a renamed constant cannot use `FromNameOrNull` for it; the remedy is serialization — the string is deserialized as the serialized form it is. The declined alternative (serialized-name matching) would instead couple the two boundaries: adding `serialized "lvl_high"` for a JSON reason would silently re-key every `FromNameOrNull("High")` call to `null`, with no diagnostic. Recorded in `DECLINED.md` with the bar the coordinator set (§4 row 3).

**Comparison.** Exact: ordinal code-point equality (stdlib §9.6's `=`), case-sensitive, no trimming, no normalization. `"high"` does not match `High`; `" High"` does not match `High`. A caller that wants case-insensitive acceptance normalizes first — a policy the boundary owns; an enum cannot know which policy a boundary wants. The issue's own sketch asked for exactly this.

**Digit strings.** `"2"` names no constant — an identifier never begins with a digit (§1) — so the issue's "no numeric strings" holds by construction. The underlying-value direction is `FromUnderlyingOrNull`; a boundary that accepts both spellings composes the two in real syntax — `var v := E.FromNameOrNull(s); if v = null then var n := int.ParseOrNull(s); if n <> null then v := E.FromUnderlyingOrNull(n!); end; end;` for an `int`-backed `E` (`int.ParseOrNull`: stdlib §9.1, `:4963`). Keeping the axes separate is the reasoning §10.4 gives for `FromUnderlyingOrNull`'s parameter being `U` exactly.

**Empty string, `string?`.** `""` is `null` (no identifier is empty). The parameter is non-nullable `string`; a `string?` in hand is narrowed first (`s!` or a null test) — ordinary §5.1 assignability, stated in stdlib §9.9 for boundary code's benefit.

**Duplicate values (§10.2).** `NameOf` returns the first-declared constant's identifier for a shared value; `FromNameOrNull` accepts every declared identifier. §3.5 states what round-trips and what does not.

### 3.3 Tiering under stdlib §1

- **Band 2, and only band 2.** An unrecognized name at a config/CLI boundary is "the absence of a queried value — a lookup … whose target may legitimately not be there — expected, and carrying no information beyond its occurrence" (stdlib `:59`); the value shape is the nullable return, and an enum payload is a non-nullable value type, so `E?` carries the whole signal (stdlib §9.9 already makes this argument, `:5318`).
- **No throwing tier (`FromName`) — and no assert *tier* on the name axis at all.** The no-dual rule *permits* an assert-shaped twin (stdlib `:68`) and does not require one. `FromUnderlyingOrNull`'s assert tier is the checked cast, which pre-existed; the name axis has no cast, and 0124 adds none: `E.FromNameOrNull(s) ?? throw new …` is the recorded **idiom** for the assert stance (§10.4's own example block teaches it), not a tier. The `OrNull` suffix is kept without a non-`OrNull` sibling for uniformity with `FromUnderlyingOrNull` and because band 2's naming convention is the suffix, not the pair. Why no compiler-provided thrower: it would have to choose one exception type for every program where the call site knows which is right (`ProtocolException`, `ConfigException`, `ArgumentException("…", "text")`), and a user who wants a named throwing tier on one enum declares it in three lines — the rewritten §10.4 example shows exactly that (`Parse` delegating to `FromNameOrNull`). Recorded with a reopening bar (§4 row 2).
- **No `Try` shape.** Shape (c)'s false path assigns `default(T)`, but an enum has **no `default(E)` unless a zero-valued constant is declared** (§17.11; §3.6's defaultable row at `:534`: "an enum **declaring a zero-valued constant**"), so shape (c) has no honest false-path value for the general enum; shape (b) is "reserved for acquisition-shaped members" (stdlib `:46`).

### 3.4 The mirror: `NameOf`

**Why it is needed.** Without it the value→name direction for a *runtime* value exists only inside a serializer: §8.5 renders the type name, `nameof` needs a written constant, `EnumNames` is spec-ahead-of-impl reflection indexed by position, and the §10.4 example hand-writes a `case`. Log lines, CLI output, error messages ("unknown mode; valid modes: …"), and any program that emits the strings it later parses need it.

**Coherence with `nameof`.** For every written constant `E.NameOf(E.A) = nameof(E.A)`; `NameOf` is the runtime extension of a compile-time operator over the same table, and §10.4 and §17.9 each say so in one sentence. The name `NameOf` is kept *because* of that identity — the two spellings differ in case exactly as a compile-time operator (lower-case keyword) and a member (PascalCase) differ everywhere else in the language, and they never disagree on a value.

**Why a static `NameOf(value: E)` and not an instance `Name` property.** (i) `Name` is the name §10.4's own example — and by extension real code — gives to a *user-declared* property on enums; a compiler-provided member of that name would break the spec's example and every enum that declares its own `Name`. (ii) The compiler-provided tier is static by construction — sema recognizes it by a type-naming receiver (`enumTypeNamedBy`), and codegen dispatches before ordinary member lookup because no `MethodSymbol` exists; an instance member would be the first compiler-provided *instance* member on an enum, with a new recognition path through value receivers and boxed dispatch to settle. (iii) `E.NameOf(v)` reads as the inverse of `E.FromNameOrNull(s)`. A user who wants the instance spelling writes `public property Name: string => Priority.NameOf(this);`.

**Totality, derived once.** `NameOf` never lacks an answer because no producer of an undeclared enum value exists: §5.4 `:795` states it outright; §17.11's rider makes `default(E)` on a zero-less enum an error (`:534`); §9.8's `Deserialize` rejects an unmatched name; the unchecked entry point is `deferred`, not shipped (`DECLINED.md:234`); §32.13's C-compatible field set admits scalars, inline arrays and records, not enums; and rationale §9.12 establishes no flags idiom exists, so a combined value is not an `E` value at all.

**Why not change `ToString`'s default.** §8.5's qualified-name default for enums is a separate rule with a blast radius the size of every interpolated enum in every program, has its own record, and is adjacent to a recorded deferral (`DECLINED.md:264`). Leaving it, and stating the one-line opt-in — `public override method ToString(): string => Priority.NameOf(this);` — keeps 0124 to its question (§4 row 3).

**The price of the alternative (parse only).** Every emitting program keeps its hand-written table; the spec's example keeps its `Name` boilerplate beside a compiler-provided parse; the round-trip laws cannot be stated; and a later `NameOf` is a second revision touching the same sites. The cost of taking it now: one more reserved name on every enum (`NameOf` — no enum in `src/`, `tests/`, `docs/` or the corpus declares a member or constant of that name; the `docs/` hits are Appendix A.7's `NameOfExpr` production, the `src/` hits C++ identifiers), one more arm at each compiler site (§6).

### 3.5 Round-trip laws (normative, stated in §10.4 — up to aliasing)

For every enum `E`: **(1)** `E.FromNameOrNull(E.NameOf(v)) = v` for every `v: E` — always. **(2)** `E.NameOf(E.FromNameOrNull(s)!) = s` for every `s` that is the **first-declared** identifier of its value; where constants alias (`Legacy := 1, Current := 1`, §10.2's example), every declared identifier reads back to the one value and `NameOf` writes the first-declared one, so `E.NameOf(E.FromNameOrNull("Current")!) = "Legacy"`. Law (1) needs only that identifiers are unique within a declaration, which they are by construction.

### 3.6 The three tables are one

`nameof(E.A)` (§17.9, compile time), `typeof(E).EnumNames` (stdlib §2.13, listing), and `E.NameOf`/`E.FromNameOrNull` (§10.4, runtime) read the declared-identifier table; a help text or validation list built from `EnumNames` matches the parse surface exactly, always. The serialized-name table (§9.8) is the encoded form and nothing else. There is no one-call spelling that lists the serialized names outside a serializer; none is needed, since that table is consumed only by §9.8's own synthesized code. 0124 does **not** change `EnumNames` (unimplemented, #3819); it retires §2.13's claim that the pair is the building block for *parsing* and *formatting* (those are now the enum's own members) while keeping its listing role (Part B, L1).

### 3.7 The §18 boundary (the owner's ruling requires it stated)

`FromNameOrNull` and `NameOf` are **not reflection** in the sense rationale §18 declines. The table consulted is a compile-time constant of *one* declaration — the same identifier list `nameof` folds at compile time; the string names a constant of a *statically known* type, never a member of an arbitrary type; nothing enumerates members, reaches a member by name, reads an attribute, or constructs. Rationale §5.18 draws its line "at lattice metadata because that costs nothing" and classifies enum introspection as "closed, stateless, ownership-free — the safest introspection that exists"; the two members are strictly inside that line — they expose less than `EnumNames` does. Rationale §18's reflection item is unchanged; no shipped marker is owed there.

### 3.8 Why per-enum static, not `Enum.Parse<E>` — and what that gives up

The gap-map row's shape needs `where E: enum`. §14.2 has no such constraint; `where E: value` admits "records, enums, choices, primitives, inline arrays … the unit type", so `Enum.Parse<E>` is either unspellable or under-constrained, and a new constraint kind is a §14.2 design change with Appendix A, §3.6 and constraint-satisfaction knock-on — bought for one member family. A `System.Enum` static class would be a new stdlib type made only of compiler intrinsics. The per-enum static needs neither: the device exists, is enforced, and is implemented.

**What the per-enum device gives up: reach from generic code.** A compiler-provided static is recognized by an enum *type name* (`enumTypeNamedBy`), so from a type parameter there is no route to it — a generic config binder `public method Bind<T>(text: string): T? where T: value => T.FromNameOrNull(text);` has no spelling under 0124 at any constraint. That is the one thing the generic shape uniquely buys, and it is accepted because no filed workload asks for it; it is also the precise reopening trigger (§4 row 1).

### 3.9 Adjacencies kept, not amended — and one spec catch-up carried

- **Reserved names reach constants (spec catches up to the compiler).** `checkEnumRestrictions` tests `m->name == "FromUnderlyingOrNull"` over `t->members` before any `dynamic_cast` (`src/sema/TypeResolution_Checks.cpp:676`), and constants are in `members` (`sema::enumConstantWireNames` iterates and casts to `EnumConstantSymbol`, `src/sema/EnumValues.hpp:127-132`) — so a *constant* named `FromUnderlyingOrNull` is already rejected while §10.4 speaks only of "no user declaration". §10.4's new text says "a member or a declared constant" for all three names; the delta closes in this revision and needs no separate issue.
- **§9.8's uniqueness clause and enum constants.** `:1613` scopes the collision error to "the serialized names of the type's components", while `:1611` distinguishes components from enum members; whether the clause reaches enum constants is a reading question, and this read located no sema diagnostic for it (154 `serialized` mentions in `src/sema/*.cpp`, none a collision diagnostic; the two `tests/` files pairing `serialized` with `duplicate` are record-constructor tests). 0124 no longer depends on it (identifiers are unique by construction). It is filed as its own spec question, [#3863](https://github.com/s8lap/bezel-lang/issues/3863) — not asserted either way (process §5 item 3b).
- **Method-reference form (§27.6).** The compiler treats `E.FromUnderlyingOrNull` as callable only (`src/sema/ExprTypecheck_Calls.cpp:19745-19749`: "a §27.6 method-reference form for it is unspecified"). The two new members inherit that posture; one question for all three, left where it is.
- **Unqualified use inside the enum's own body.** The normative text and every example spell the receiver (`Priority.FromNameOrNull(text)`), matching the implemented recognition device; the bare form is the same open question as for `FromUnderlyingOrNull`.
- **Flags.** No flags idiom exists (rationale §9.12 *The flags question, investigated*, `:1232`); a combined value is not an `E` value, so `NameOf` has nothing undefined to answer. `DECLINED.md:264`'s deferred niceties are untouched.
- **`ToString` (§8.5), `EnumNames` (§2.13), the unchecked entry point (`DECLINED.md:234`)** — untouched.
