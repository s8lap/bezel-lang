## 0. Thesis

§22.6 bans overloading on ordinary-parameter `owned`: `M(t: T)` beside `M(owned t: T)` is a compile error, and the prescribed remedy is dual naming — "`Append` versus `AppendOwned`, or the `FromResult` / `FromOwnedResult` pattern." The ban's recorded reason is a **visibility** claim (§22.6, v0.249): "the call-site syntax (`M(value)`) does not visibly distinguish the two forms, so permitting them as overloads would force the caller to know the resolution outcome to write a correct ownership transfer."

That premise is gone. Since v0.169 a named owned binding passed to an `owned` parameter carries a call-site marker, and since v0.246 the marker is the unified verb: `M(move x)` transfers, `M(x)` borrows — visibly distinct at every call site, with no declaration-token ambiguity left. §22.6's own text concedes it ("the call-site marker `M(move x)` … satisf[ies] this paragraph's own carve-out criterion"), rationale §3.10 concedes it twice (the v0.169 record and the v0.246 reversal record), and the v0.246 changelog records E-f1 as the open question. What kept the ban standing was never a reason — it was scope: "lifting it drags stdlib renames and resolution rules with it." This proposal is those renames and those resolution rules.

**Proposed:** two same-name members may differ by `owned` on ordinary parameters. Resolution needs **no ranking change**: the argument's ownership classification is part of **applicability**, so at most one member of such a pair survives at any argument, and the caller's spelling — not the resolution outcome — decides which:

```bezel
public class Registry
  public method Append(item: Widget);         // borrows; caller keeps ownership
  public method Append(owned item: Widget);   // takes; caller's binding is consumed
end Registry;

r.Append(w);            // borrow — the plain overload; w untouched
r.Append(move w);       // transfer — the owned overload; w moved-from (§22.3, K3.3)
r.Append(new Widget()); // fresh producer: an owned production — the owned overload
```

The stdlib merge program is smaller than the ban's record suggests, and honestly so: the convention-bred `WhenAllOwned`/`WhenEachOwned` merge into `WhenAll`/`WhenEach` (§4 category ii — pairs that were declarable even under the ban, so the merge is separable from the lift itself), while the one genuinely ban-*forced* pair, `FromResult`/`FromOwnedResult`, does **not** merge — §4 category (i) is investigated and withdrawn under this proposal's own declaration guard, with the reasoning stated. The `out owned` and `scoped` halves of the ban deliberately **stand** (§3). The `TryX` acquisition names all stay: they are operation names, not ownership suffixes (§4, category iv–v).

## 1. The exact rule

**Amendment sketch (§22.6, replacing the ordinary-parameter ban paragraph):**

> Ordinary-parameter `owned` joins the distinguishability list: overloads may differ in number, types, the `ref`/`out` modifiers, **or the presence of `owned` on an ordinary parameter**. At an argument position where two applicable candidates differ only by ordinary `owned` — measured on the **substituted** signatures, after per-candidate inference (§14.5; §22.6 already ranks substituted signatures, and the mixed set `M(x: Widget)` / `M<T>(owned x: T)` decides on exactly this predicate — §9 Q8) — the argument expression completes applicability, by four exhaustive clauses. **(1)** An **owned production** is applicable only to the **`owned`** candidate: a move-rooted argument (`move x` — §22.3's call-site marker; `move obj._f`; `move coll[i]`) or any other production the **§28.3 producers table** classifies owned — a fresh `new`, a reference-typed collection literal, an `owned`-returning call, a `Task`-family call, an owned arm-meet, a move-only value result, a Pattern B `await` result. The producers table, not any list in this rule, is normative; the enumeration here is illustrative. **(2)** A **borrow** is applicable only to the **plain** candidate — an unmarked read of a named binding, a storage/property/indexer read, a plain-returning call. **(3)** A **`null` literal** (polymorphic-null, K1 — no value to own, compatible with either) is applicable to both, and the call falls to the ordinary ambiguity rule; because the pair's parameter types are identical, §22.6's explicit-cast remedy cannot select between the members, so the ambiguity diagnostic names the real remedies — bind first and pass the binding (a borrow: the plain member) or transfer a named owned binding (`M(move x)`: the owned member). **(4)** An argument with **no ownership classification** (K1.6 — an ordinary value, a `string`, a boxed value, a function value; reachable at a pair position through boxing or an implicit reference conversion) is likewise applicable to both, and the call falls to the same ambiguity rule with the same remedy naming (§9 Q5 records the route-to-plain alternative). The clause split is decidable from the argument alone: for a named binding, K3.13's no-silent-consume rule and §22.3's marker make the marked/unmarked split total — an unmarked read never consumes, a marked read never borrows — so the argument's spelling, never the candidate under trial, decides its clause. The classification is consulted only where candidates differ by the marker; a single declared member keeps today's compatibility rules unchanged. **No ranking change**: the marker participates in applicability, never in the better-than relation — at most one member of a pair survives applicability at any argument carrying a classification, so the exact-match ranking, the defaulted-arity tie-break, and the non-generic preference operate on the surviving set exactly as written.
>
> **Declaration guard (the #1873 stance, narrowed to an erasure test).** A pair differing only by ordinary `owned` is declarable exactly when, at every differing position, the declared type — nullability stripped — is a **class type**, an **interface type**, or a **type parameter whose constraints exclude every substitution at which the pair collapses**: every substitution at which §28.1 **erases** the marker — a value or runtime-managed substitution, where the substituted signatures become identical — and every **move-only value** substitution, where the marker is admitted-but-redundant (§28.1, §15.3/K3.12: the value transfers under either spelling, so the members collapse in behavior though not in spelling). Whether a constraint set qualifies is decided by §14.2's conformance computation, at the declaration: a class bound (`where T: SomeClass`) qualifies — only class types satisfy it; an interface bound qualifies exactly when no value-kind or runtime-managed type conforms to the named interface — `where T: IDisposable` qualifies (its conforming set is every class plus the `IDisposable`-extending interfaces, §14.2's worked example; records, enums, choices, primitives, and the runtime-managed types never implement `IDisposable`, §28.2) where `where T: IComparable<int>` does not (primitives and records conform, §14.2's worked example); and **`where T: class` does not qualify** — it admits `string` and function-type substitutions (§14.2), at which §28.1 erases the marker and the pair collapses to identical signatures. At any failing position the declaration-site clash error of §11.3 stands — reported at the second declaration, uniformly, exactly as #1873 ruled for the whole ban; per-instantiation collapse errors remain declined (§9 Q6), and the erasure-test-versus-whitelist formulation choice is §9 Q7.

Verified against §22.6's actual text: the applicability facts this rule keys on are compatibility rules the spec **already states** — a borrow may not feed an `owned` parameter (K3.3: only owned productions discharge there), and `M(move x)` at a non-`owned` position is an error naming the borrow default (§22.3; v0.246 Q6). What is genuinely new is their *role*: §22.6 today frames the analogous `out`-binding-form checks as "compatibility checks against the *resolved* signature, not resolution signals," and states it has no resolution-by-call-site-form rule at all — the lift makes the ownership mode precisely such a rule for ordinary `owned` (which is why §3 retires that sentence), so the precedent claimed here is the reuse of the compatibility *facts*, not of any existing resolution mechanism. The form-only ground is likewise stated precisely: it is **K3.13 plus §22.3's marker**, *not* the producers table's owned-local-read row — that row is position-classified ("classified by the position the read appears in") and would be circular as a resolution key; at an argument position the marker discipline makes the split total before any candidate is consulted. The one genuinely new semantic decision is fresh-producer routing (§2 consequence 2). The v0.246 named-argument seam ruling simplifies binding exactly as anticipated: a move-rooted argument is **positional-only** (§22.5 — `M(item := move x)` is a compile error), so named-argument reordering never has to reconcile with a marker; classification-keyed applicability reads named plain-value arguments (`M(item := new T())` is legal and owned-classified) with no special case. One consequent asymmetry is stated rather than hidden: **for a named owned binding, a pair's owned member is unreachable through named-argument syntax** — a caller who both transfers a named binding and names arguments (the optional-parameter call shapes) must pass the marked argument positionally; fresh producers, being plain-value expressions, reach the owned member by name.

## 2. Worked consequences

1. **The recorded harm inverts.** The v0.169 reason was that the caller would need the resolution outcome to write a correct transfer. Under this rule the dependency runs the other way, always: the resolution outcome is a function of what the caller wrote. `Append(x)` cannot consume `x` (an unmarked read of a named binding is a borrow, K3.13 — the no-silent-consume rule is untouched and is what makes the rule sound); `Append(move x)` cannot borrow. There is no call whose meaning the caller must look up.
2. **Fresh producers select the transfer overload.** A fresh production is owned (K1.5); within a pair it is applicable to the `owned` candidate only. This is the useful reading — the alternative (borrow of an unbound temporary, K8) hands the callee a reference that dies at the statement boundary, which at a storing callee is exactly the #1813 trap shape proposal 0081 lints. A caller who genuinely wants a temporary *inspected* but not kept binds it first (`using var t := new Widget(); r.Append(t);`) — the standard remedy, unchanged. Purely additive: where only one member is declared, today's rules (including fresh-at-plain call-bounded borrows) are untouched.
3. **`null` at a pair is ambiguous, loudly.** A nullable-typed pair position fed a bare `null` keeps both candidates applicable and the existing ambiguity error fires, citing both — §22.6's decline-to-guess stance, no new machinery. (Realistically no stdlib pair takes a nullable marked position; §9 Q4 offers the prefer-plain alternative if the owner wants one.)
4. **Interface conformance is per-signature, already marker-aware.** Signature matching reads `owned` today (§28.1's erasure paragraph names §11.2/§12.1; §2.8.6 classifies an `owned` flip as breaking). An interface may declare both members of a pair; a class implements each separately (bodies may delegate); an override repeats the modifier as always (§12). The diamond rule's "same signature" reads marker-aware and is unchanged. A *generic* interface pair falls under the declaration guard like any pair.
5. **Artifact interface: one matching-key sentence, no new carriage, no new category.** §2.8.2 clause 1 already carries ownership modifiers per member, so the interface *content* is unchanged. What changes is §2.8.6's **Member matching** key: overload identity currently lists "declaring type, name, arity, parameter types, and `ref`/`out` modifiers" and files `owned` among the "facts that never distinguish overloads" — ordinary-parameter `owned` moves from that list into the key, one sentence in that paragraph. Delta classification gains no category: *adding* the `owned` member beside an existing plain one is the existing member-added/widening row (its re-route caveat is moot at a pair — the argument's classification selects with today's single-member semantics); *flipping* a parameter plain↔owned, previously a within-match breaking modification, now reports as removal plus addition under the amended key — the verdict stays breaking, only the report shape changes. Appendix C.1's never-distinguishes row narrows in step.
6. **Constructors participate.** §22.6's constructor sentence applies unchanged: `new StreamReader(inner)` / `new StreamReader(move inner)` pairs become declarable — the shape proposal 0006's stream family already reaches for.
7. **Method references resolve by function type.** `(owned T) -> ()` and `(T) -> ()` are distinct function types (§27.1), so an overloaded reference to a pair resolves by target type under §27.6's existing rules; without a disambiguating target it is the existing cited-candidates error.
8. **Defaults.** A pair whose marked position is defaulted on both sides makes an argument-omitting call fill defaults on both — the existing two-defaults-filled ambiguity stance applies (§22.6). Stdlib pairs should not default the marked position (one sentence in stdlib §1).

## 3. What deliberately stands (the un-lifted halves, argued)

- **`out owned` vs `out` stays banned.** The lifted half keys on what the caller *passes* — an expression with a K1 classification. The `out` half would key on how the caller *binds* a result (`out var` vs `out using var`), making `out` the only position where resolution consults a binding form; §22.6's recorded costs (a dedicated `out _` ambiguity remedy — the discard is compatible with both members of such a pair) are unchanged by v0.246, which touched no `out` spelling (`out owned var x` stays declarative — 0090 Q5). And the corpus adds a semantic reason the original text understates: every shipped `out owned`/"pair" is **operation-distinct**, not ownership-distinct — `TryGetValue` leaves the entry where `TryPopValue` removes it; `TryPeek` leaves where `TryPop`/`TryDequeue` remove. Merging them would key a *mutation of the receiver* to how the caller binds an out-result. Guide 2 teaches the naming as load-bearing ("`Get`/`Peek` borrow; `Pop`/`Drain`/`Take` transfer — the name alone tells you whether you now owe a disposal"); that pedagogy survives intact.
- **`scoped` stays banned.** The carve-out criterion is not satisfiable there: a function-typed `scoped` argument carries **no call-site marker at all** (admission is capture-based, §28.14), and lifting only the class-typed `M(scoped x)` face would make `scoped` resolution-significant for one operand kind and invisible for the other — a split inside one modifier. §22.6's "no resolution-by-call-site-form rule" sentence retires (the lifted half is precisely such a rule, for `owned`, where the form is total); the `scoped` rejection re-grounds on the markerless function-typed case.

## 4. The stdlib program (what merges, what stays, and why)

Enumerated by category, counted at v0.249 (occurrences: stdlib doc / spec / tests; the v0.248 counts re-verified unchanged at v0.249 HEAD):

**(i) The ban-forced pair — investigated for merge, and WITHDRAWN: no expressible constraint fits the API.** `Task.FromResult<T>(value: T): Task<T>` (non-class `T`, compiler-special-cased) beside `Task.FromOwnedResult<T>(owned value: T): OwningTask<T> where T: class` (stdlib §6.7; FromOwnedResult: 2 / 6 / 41). The natural merge — `FromResult<T>(owned value: T): OwningTask<T> where T: class` — **fails the §1 declaration guard**: `where T: class` admits `string` and function-type substitutions (§14.2), at which §28.1 erases the marker and the pair collapses onto the plain `FromResult<T>(value: T)`; the guard rejects the pair at the declaration. The repair space was worked and comes up empty. **(a)** `where T: IDisposable` passes the guard (§1) but mis-fits the API: `OwningTask<T>` admits *every* interface type (§14.4's class-only restriction — `OwningArray<IConnection>` is its own worked example), while `where T: IDisposable` admits only `IDisposable`-extending interfaces (§14.2's worked example), so the merged member would reject `FromResult<IConnection>(move conn)` where today's `FromOwnedResult<IConnection>` is legal — a domain regression bought for a name. **(b)** No constraint in §14.2's vocabulary expresses the owning-generic domain ("class or interface kind, minus the runtime-managed types"); §14.4 says so itself — the owning types' own `where T: class` is "a slight imprecision," patched by **compiler enforcement** at the instantiation, not by a constraint. **(c)** Extending that compiler enforcement to bless the stdlib pair's declarability would deepen the very special-casing this API already carries (the class-`T` rejection in `FromResult` is compiler-known, stdlib §2.14/§6.7) and would privilege a stdlib declaration no user could write. **(d)** Weakening the guard to consult per-instantiation ill-formedness — `OwningTask<string>` is rejected at the instantiation anyway (§14.4, §3.6 rule 2), so the collapsed instantiations could never both be *used* — is exactly the per-instantiation collapse checking #1873's record declined and §9 Q6 declines again. **Disposition: category (i) withdraws.** `FromOwnedResult` keeps its name; its 2 / 6 / 41 occurrences and its 14 compiler-source recognition sites are untouched; §30.10's class-`T` diagnostic ("a compile error pointing to the owned variant") and stdlib §6.7's cross-reference keep their referent unchanged. Should a future recorded ruling grow §14.2's constraint vocabulary with a form that spells the owning-generic domain, (i) becomes mergeable then — a liftable, not this proposal. Recorded honestly for §3.10: the ban's letter was never the only thing keeping this pair apart; the erasure geometry is, and it survives the ban's lifting.

**(ii) Convention-bred dual names, already type-distinguished — merge recommended.** `WhenAllOwned` (12 / 5 / 38, + 2 Guide 4 lines shared with the next) and `WhenEachOwned` (4 / 0 / 23), both stdlib §6.7. Their parameter types already differ from their duals' (`Array<Task<T>>` vs `owned OwningArray<OwningTask<T>>`), so these pairs were declarable as overloads even under the ban — the dual naming is the ban's *culture*, not its letter (as is 0006's `MemoryStream.FromBytes` pair, type-distinguished and already same-named in that accepted proposal). Merged: `Task.WhenAll(tasks)` / `await Task.WhenAll(move tasks)`, `Task.WhenEach(tasks)` / `Task.WhenEach(move tasks)` — the call-site marker announces the consuming form, which is the teaching the current names duplicate. Because these pairs were legal under the ban, **the (ii) merges are separable from Q1**: they can be ruled on — and could even land — independently of the lift (§9 Q9). With (i) withdrawn, they are the entire merge program.

**(iii) Return-side `Owned` names — do NOT merge.** `Json.ParseOwned<T>` / `Binary.ParseOwned<T>` (15 / 0 / 23) are distinguished at the **return**, where no call-site marker exists and no overloading-by-return exists; the name is the §28.3 announcement discipline doing its job at a static producer, and the facade naming was owner-ruled at v0.232. (The §28.1 observation that a single `Parse<T>(): owned T` would erase per instantiation is deliberately *not* pursued — the value/class facade split was ruled for its diagnostic quality; reopening it is not this proposal.)

**(iv) The `out owned` Try pairs — stay, with the un-lifted half.** `TryGetValue`/`TryPopValue` (OwningDictionary §4.9; 10 / 3 test-heavy), `TryPeek`/`TryPop` and `TryPeek`/`TryDequeue` (§4.11), `TryTake` (§4.10), `TryPopFirst`/`TryPopLast` (§4.5/§4.7), `Channel<T>.TryReceive` (§6.9). Operation-distinct per §3; no rename.

**(v) The Try tiers that were never ownership duals — untouched, stated so this proposal does not over-reach.** The Try-parse tier (`TryParse` on the §9 primitives, `Guid`/`DateTime` family, `Convert.TryTo*`), shape (b) acquisitions (`Mutex.TryAcquire`, `Weak<T>.TryUpgrade`), shape (d) attempts (`TryAdd`, `TrySet*`, `TryWrite*`), and the `*OrNull` tier signal *decline or absence* (stdlib §1's Try-convention bullet); no borrowing/owning same-operation dual exists behind any of them. They are out of scope by construction.

**§22.6's own text.** The *Practical pattern* section survives — it teaches the `out owned` Try convention, which stands — and the ordinary-parameter remedy sentence ("`Append` versus `AppendOwned` …") retires. `AppendOwned` was never API: 0 stdlib, 0 tests; its three total occurrences (spec 1, rationale 2) are all inside the ban's own records.

## 5. Corpus evidence

- **The premise shift is total.** Every ordinary-`owned` argument in the corpus is marker-bearing or fresh: the v0.246 flip left ~184 `M(owned x)` / `:= owned x` test lines pending their mechanical respell to `move` under #3056 (plus 5 `case owned` scrutinees) — i.e., the marker discipline the resolution rule reads is already universal; only its verb is mid-migration.
- **The ban's regression tests** (tests/lit/sema/) — the family is **seven** files: five rejects sharing one diagnostic string ("overload of `X` is indistinguishable from another overload — overloads must differ in parameter count, types, or `ref`/`out` modifiers; neither `owned` (ordinary or on an `out` parameter) nor `scoped` distinguishes (§22.6/§11.3, v0.181)") and two accept controls. Dispositions under this proposal: **one genuine flip** — `sema_overload__owned_only_difference_diagnoses.bzl` (a concrete class-typed pair) becomes an admitted-pair test. **Four rejects stand, each with the reworded message**: `sema_overload__owned_generic_typeparam_collapse_1873.bzl` and `sema_overload__owned_iface_typeparam_collapse_1873.bzl` do **not** flip — both pairs sit on an *unconstrained* type parameter, which the §1 erasure guard rejects at the declaration exactly as #1873's recorded interpretation did (their messages re-scope to the guard, naming the erasing substitutions); `sema_overload__scoped_only_difference_diagnoses.bzl` and `sema_overload__out_vs_out_owned_clashes.bzl` keep their verdicts (the un-lifted halves) but share the family string, whose "neither `owned` … nor `scoped` distinguishes" wording becomes false under the lift — it rewords to name the standing halves (ordinary `owned` distinguishes under the declaration guard; `out owned` and `scoped` never do). §8's diagnostics item is exactly this rewording, stated here so §5 and §8 agree. **Two accept controls unchanged**: `sema_overload__owned_generic_typeparam_distinct_1873_ok.bzl` and `sema_overload__distinct_names_out_vs_out_owned_ok.bzl`.
- **The rename surface** (category ii only; (i) withdrawn): 61 test lines (38 + 23) + 16 stdlib lines (12 + 4) + 5 spec lines + 2 Guide 4 lines ≈ **84 doc/test lines**, each a single-token name substitution with no call-site shape change (the argument spellings are already marker-correct). **Compiler source is not mechanical**: 47 `WhenAllOwned`/`WhenEachOwned` occurrences in `src/` (28 + 19) are *name-keyed recognition* — sema and codegen special-case the helpers by member name, so the merge re-keys recognition from name alone to name **plus parameter classification** (the borrowing and owning `WhenAll` overloads must be told apart by signature where today the name decides) — plus 6 snake-case runtime-symbol occurrences including the ABI symbol `bz_task_when_all_owned` (runtime header, runtime implementation, codegen's `declareC` site), which may keep its internal spelling but must be re-pointed by the re-keyed codegen. `FromOwnedResult`'s 14 `src/` occurrences are untouched.
- **No pair exists anywhere** — the ban made pairs undeclarable, so the lift changes the meaning of zero existing declarations and zero existing calls.

## 6. Migration and compatibility (changelog categories)

- **Newly defined:** pair declarability; the four-clause ownership-mode applicability rule; the erasure-test declaration guard.
- **Newly rejected:** nothing that exists — the guard rejects a subset of declarations that are all rejected today by the wider ban.
- **Renames (breaking; zero users; hard, no alias — the 0090 Q3 precedent):** `WhenAllOwned` → `WhenAll`, `WhenEachOwned` → `WhenEach`; the old names leave the stdlib in the same revision. (`FromOwnedResult` is **not** renamed — §4 category (i) withdrawn.)
- **Nothing flips:** no existing program changes meaning; single-member call sites resolve exactly as today.
- **Interface carriage:** none new (§2 consequence 5).

## 7. Alternatives considered

1. **Status quo.** Declined: the ban's recorded reason is deleted from under it; keeping it means §3.10 records "re-examined and kept" with no surviving reason beyond migration cost — a timing argument at its weakest point (pre-users) and weakening every revision the dual-name surface grows.
2. **Admit-but-don't-rename** (the lift without the stdlib merge). Viable as staging; declined as an end state: the tax the ban levied was the shipped vocabulary, and the rule change alone leaves it collected while removing the rule that justified it. Offered as Q9's fallback. (Category (i)'s withdrawal is *not* this alternative: (i) is not declined-for-staging, it is undeclarable as a pair under the guard — §4.)
3. **Marker-as-preference** (both candidates applicable; the marked form *preferred*). Declined: with both applicable, an unmarked call at a pair would silently select — re-creating exactly the resolution-outcome-knowledge harm the v0.169 record named. Applicability keeps every selection derivable from the call site's spelling.
4. **Purely syntactic applicability** (move-rooted → owned; everything else, fresh producers included → plain). Declined: it inverts K1.5 (fresh productions *are* owned) and routes fresh arguments into the borrow-of-temporary reading — useless at best, the #1813 shape at worst (§2 consequence 2).
5. **Mandatory marker on fresh producers at pairs** (making applicability purely syntactic the other way). Declined: breaches K3.13's fresh-producers-need-no-marker principle and the v0.246 Q2 one-spelling-per-site discipline for a symmetry no reader needs.

## 8. Implementation sketch

- **sema** (overload resolution): the applicability filter reads the argument's spelling and classification per §1's four clauses (for named bindings the split is the K3.13/§22.3 marker fact; for other forms the producers-table row, already computed for diagnosis); the §11.3 clash check narrows to the erasure guard + the standing halves — the guard is a client of §14.2's conformance computation, which sema already runs for constraint checking; the compiler-known `FromResult` class-`T` special-casing is **untouched** (category (i) withdrawn); the `WhenAll`/`WhenEach` recognition re-keys from member name to name + parameter classification (§5); diagnostics: the shared indistinguishable-overload family string rewords to name the standing halves (§5), and the ambiguity message gains the null-at-pair / no-classification-at-pair remedy naming of §1 clause (3)/(4).
- **parser:** nothing — no grammar delta.
- **stdlib/tests:** the category (ii) renames as one mechanical commit; spec-cited regression tests per `tests/README.md`: pair resolution at each argument kind (marked, borrow, fresh, null, and a no-classification boxed/`string` argument at an `Object`-typed pair), the declaration guard (concrete class, `where T: class` rejected, `where T: SomeClass` and `where T: IDisposable` admitted, `where T: IComparable<int>` and unconstrained rejected), the substituted-signature predicate (the mixed set `M(x: Widget)` / `M<T>(owned x: T)`), interface-pair conformance, constructor pair, method-reference-by-target-type, and the seven-file lit-test disposition of §5.
- **Sequencing:** after #3056's marker respell lands (resolution reads the very marker the corpus is still adopting); the Guide 4 respell rides graduation (v0.249 has landed; the two lines are verified present at v0.249 — header).
- **Size:** moderate, honestly split — one resolution-phase filter (four clauses), one declaration guard (a conformance-computation client), ~84 mechanical doc/test rename lines, and a **non-mechanical** `src/` re-keying: 47 name-keyed recognition sites plus the runtime-symbol surface incl. `bz_task_when_all_owned` (§5).

## 9. Questions for the owner

- **Q1** — lift the ordinary-parameter half via ownership-mode applicability (§1–§2)? Recommended.
