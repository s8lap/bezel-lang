## 0. Thesis

Rationale §5.28 (v0.238, Q1) states the doctrine and v0.243 (proposal 0081) applied it twice more: where the compiler *knows* a program's shape will fault or dangle, silence "is the one place the ceremony exemption's silence stops being honest", and the answer is "a **targeted lint** … no `using var` is demanded, the program stays accepted", the diagnostic naming the boundary event and the remedies, with "**no per-site suppression spelling**". Two more shapes qualify, and both are taught today as traps rather than diagnosed:

- **Lint A** — `for var x in xs do … xs.Remove(x); … end;`: §29.12 says the enumerator is invalidated and "Standard collections detect this and throw `InvalidOperationException` on the next `MoveNext()`". The receiver *is* the loop's source binding; the compiler sees both. Guide 05 §? teaches collect-then-remove as "the standard shape" and the runtime fault as what you get otherwise.
- **Lint B** — `var w := xs[0]; xs.RemoveAt(0); w.Ping();` on an owning collection: §28.11's owned column says `Remove`/`RemoveAt` "**disposes** the removed element", and §28.3's producers table already names this hazard in the indexer row — "the borrow is additionally valid only until the slot is mutated (an indexer-set, `Remove*`, or `Clear` disposes the referent — a mid-scope value kill not statically tracked per slot; checked-mode backstop". The straight-line, same-index subset *is* trackable, and it is exactly §28.2's dominating-kill shape with the kill on the collection instead of on the binding.

Neither lint changes what compiles; both convert a runtime fault (A: `InvalidOperationException` at the next advance; B: `DisposedAccessException` in the default checked build, undefined behavior unchecked) into a compile-time warning at the line that creates it.

## 1. The current state, precisely

§29.12 (v0.306):

> Modifying a collection while iterating it invalidates the active enumerator. Standard collections detect this and throw `InvalidOperationException` on the next `MoveNext()` (or `MoveNextAsync()`).
>
> **What counts as modification.** *Structural* modification invalidates: any operation that adds, removes, or repositions entries or reallocates storage — `Add`, `AddRange`, `Insert`, `Remove`, `RemoveAt`, `Clear`, `Push`/`Pop`, `Enqueue`/`Dequeue`, a dictionary indexer-set that *inserts* a new key, and the in-place `Sort()`/`Reverse()` (they reposition), together with their owning-collection counterparts. An **element-level write that changes no structure** does not invalidate: assigning through the indexer to an existing position (`arr[i] := v`; `dict[existingKey] := v` updating a present key) leaves the enumerator valid, and a later visit of that position observes the new value — for an owning collection such a set still disposes the displaced element per [§28.11](…), which invalidates *borrows of that element*, not the enumerator. The [§29.2](…) protocol-elision optimization must preserve these faults …

and then "The standard pattern for removing during iteration:" with the two-loop example. §29.2's desugaring pins the loop's source: `using var __source := source; using var __enumerator := __source.GetEnumerator(); while __enumerator.MoveNext() do var x := __enumerator.Current; … end;` — and "When `source` is itself an owned local — including a `using var` of class type … the desugaring is adjusted: `using var __source := source;` is replaced by a borrow that pins `source` for the loop's duration". The source binding and the receiver of an in-body call are the same binding by name.

§28.11, *Owning collections*: "`Remove`/`RemoveAt`/`Clear` dispose what they remove, `Dispose()` disposes every element and then frees the backing storage, and reads — the indexer-get and default iteration — produce borrows whose source is the collection (`move coll[i]` is the explicit-take form, below)." The element slot policy's owned column: `Remove`/`RemoveAt` "**disposes** the removed element"; `Clear()` "**disposes** every element"; indexer-get / default iteration "borrow out (source: the collection)". The borrowing family's column: removal "removes the borrow; the caller's ownership is unaffected" — no kill, so lint B has no subject there.

§28.3, producers table, the indexer row: "Owning-family collection: source is `coll`, and the borrow is additionally valid only until the slot is mutated (an indexer-set, `Remove*`, or `Clear` disposes the referent — a mid-scope value kill not statically tracked per slot; checked-mode backstop, [§28.2](…), stdlib §4.5)." And §28.11's per-slot precision statement: "The compiler tracks moved-from state per slot when the index is a compile-time constant or a local read."

§28.2, the model for lint B's shape: "The compiler additionally **must** emit a compile-time warning when a local variable is used (read, borrowed from, or consumed) after an explicit `Dispose()` call — or a discard of the binding — on the same variable that dominates the use site on every path: the straight-line subset of use-after-dispose (derives: [K4.2](…) + [K7.4](…))."

§29.11's provenance vocabulary, reused by lint B: the class-element terminal accessors "whose result at a class or interface element type is a borrow of the element", keyed on "the receiver's statically-tracked provenance", with "a **concrete collection value** as the root — a `new` collection, or a collection-typed parameter, field, or local bound to one" as the sound-silent root of *that* lint (the element's owner is the collection, which outlives the accessor call) — and therefore, for lint B, exactly the root whose later removal kills the element.

Guide 05: "Structurally modifying a collection while iterating it raises `InvalidOperationException` at the next advance (spec §29.12). The standard shape is collect-then-remove, two passes" — with the example. Stdlib §4.5: "The indexer getter produces a borrow of the slot's owned element; the borrow is valid until the slot is mutated (by indexer set, RemoveAt, Clear, or any operation that disposes the slot's contents)."

**What the compiler does today** (§5 item 3b check). Neither warning exists. Lint A: the runtime bumps a modification epoch on every structural call (`src/runtime/bezel_runtime_collections.cpp:148,186,206,213,231` for arrays; `:761-1065` for dictionaries) and the enumerator faults on the next advance; no compile-time diagnostic references §29.12 (`grep -rn "29\.12" src/ownership src/sema` → 0). Lint B: the dominating-`Dispose()` warning is `MethodOwnership::checkRead` (`src/ownership/Ownership_Checks.cpp:2484`; the `OwnershipState::Disposed` branch at `:2671-2690`, message "use of `x` after a dominating explicit Dispose() call"); it is keyed on the binding's own state and never on a borrow's source. The borrow-source machinery exists: `borrowSourceForExpr` (`:5786`) resolves an indexer read's source to the collection binding; `seedOwnedIterVar` (`src/ownership/Ownership.cpp:2862`) and the `ForStmt` visits (`:1933`, `:2096`) bind the iteration variable. The §29.11 terminal-accessor warning itself is **not implemented** (`grep -rn "does not survive\|enumerator-owned" src/` → 0; the corpus's first classification records the warning surface as "a single unimplemented area"), so lint B's accessor-provenance leg rides a trace the compiler will build for §29.11 anyway.

## 2. The rules (exact normative wording)

### 2.1 Lint A — at §29.12, after the *What counts as modification* paragraph

> **The mutation-during-iteration warning.** Because the fault is certain wherever the enumerator advances after the modification, the compiler **must warn** at a call to a structural operation of the list above — the compiler-known members of the standard collections, both families — whose receiver is the **same binding** the enclosing `for` or `await for` iterates: the loop's source expression and the call's receiver are the same local or parameter, or the same member chain rooted at `this` in which every hop is an `owned` field. The call must sit in that loop's body — in the loop's own callable body, not inside a lambda literal or a local type declaration's member body ([§21.10](#sec-local-type-declarations)) that the loop body merely contains, whose invocation the loop does not sequence — and the loop's next advance must be reachable from it: a structural call followed on every path by an exit from the loop — `break`, `return`, a `throw` no `catch` within the loop body handles, or a labeled jump out of it — is exempt, no advance following it; an exit on only some paths exempts nothing, and the call is warned whether or not it is conditional. A dictionary indexer-set is not in the warned set — whether it inserts is a runtime fact. The warning names the next advance as the fault site and the remedies: collect the matches and modify after the loop (the pattern below); or consume the collection through its egress members — `Pop`/`PopAt`/`PopValue` and their kin — in a loop that does not iterate it. A modification through a **different** binding — a borrow copy of the source (`var ys := xs;`), a parameter or field holding the same collection, or a call the body makes — is not traced (a chosen silence, liftable), and the runtime fault remains the guard there. The program stays accepted; no per-site suppression exists (rationale §5.28).

### 2.2 Lint B — at §28.11, *Owning collections*, after the reads sentence

> **The element-borrow use-after-removal warning.** A read that produces such a borrow — the indexer-get `coll[i]`, the iteration variable of default iteration over the collection, and a stdlib §5 class-element terminal accessor whose receiver's statically-traced provenance ([§29.11](#sec-multiple-enumeration)) roots at the collection — names the collection binding as the borrow's source. The compiler **must warn** when a local holding such a borrow is used (read, borrowed from, or passed) after a call on the **same collection binding** that **disposes the borrowed element** and **dominates the use on every path** — the dominating-kill shape of [§28.2](#sec-checked-disposal)'s use-after-dispose warning, with the kill on the collection rather than on the binding: `Clear()`, which disposes every element; `Remove(b)` — the element-removal member of the sequence and set families — where the argument is the borrow itself; and `RemoveAt(i)` where the borrow was taken as `coll[i]` with the same index expression — a constant, or a local read not reassigned between — the per-slot precision the moved-from tracking below uses, and no structural operation of [§29.12](#sec-mutation-during-iteration)'s list on the same collection binding between the borrow and the kill: a reposition or removal ahead of the slot would change which element the index names. An element-level write — an indexer-set — does not draw this warning: it is not a [§29.12](#sec-mutation-during-iteration) structural operation, and the two warnings share one operation vocabulary (a chosen silence, liftable; the checked-mode backstop stands behind it). A keyed removal — `OwningDictionary<K, V>`'s `Remove(k)` after a borrow taken as `od[k]` — is likewise outside the kill set in this revision: the set is keyed on the ordered collections' slot index, and a keyed leg would restate it over key equality ([§8.3](#sec-equals-and-gethashcode)) (a chosen silence, liftable; the backstop stands behind it). A borrow re-taken after the mutation is clean, and a use before the mutation, or on a path the kill does not dominate, draws nothing. The warning names the disposing call and the remedies: re-take the borrow after the mutation; take the element out first through `PopAt`/`Pop`/`PopValue`, which leave no borrow behind; or mutate after the last use. Where the element type overrides `Equals`, `Remove(b)` may dispose an equal element other than the borrowed one; the warning is stated as certain there regardless — an over-warn, recorded, with re-taking the borrow as its remedy. The program stays accepted; no per-site suppression exists (rationale §5.28).

### 2.3 The §28.3 row, Appendix C, stdlib §4.5, rationale §5.28

§28.3's indexer row parenthetical becomes "*(an indexer-set, `Remove*`, or `Clear` disposes the referent — a mid-scope value kill whose dominating straight-line subset draws [§28.11](#sec-owning-collections)'s element-borrow use-after-removal warning and which is otherwise not statically tracked per slot; checked-mode backstop, …)*". Appendix C.3 gains two rows after the terminal-accessor row — Appendix C **does** list warnings (its §15.4 store-warning row and its §29.11 terminal-accessor row are the models; its preamble's "which classes of error are caught at compile time" covers a mandated warning, and C's *Diagnostic identity* note states "a mandated warning [is satisfied] by any warning"). Stdlib §4.5's indexer-borrow sentence gains one cross-reference sentence. Rationale §5.28 gains a "fourth and fifth instances" paragraph. The exact `old → new` pairs are in `scratch/train-A/edits.md` (group C).

### 2.4 Proposed diagnostic texts (§28.3's recommended-message style; not gated)

- *Lint A:* **"`xs.Remove(x)` modifies the collection this `for` is iterating; the enumerator is invalidated and the loop's next advance raises `InvalidOperationException` (§29.12). Collect the matches and remove them after the loop, or consume the collection with `PopAt`/`Pop` in a loop that does not iterate it."**
- *Lint B:* **"`w` borrows an element of `xs` that `xs.RemoveAt(0)` disposed (§28.11); this use raises `DisposedAccessException` in checked disposal mode and is undefined unchecked. Re-take the borrow after the mutation, take the element out first with `PopAt(0)`, or mutate after the last use."**

## 3. False-positive / rejected-shape analysis — what must NOT warn

### 3.1 Lint A

| Shape | Silent? | Why (traced) |
|---|---|---|
| collect-then-remove (§29.12's own example; Guide 05; corpus `s29_12_0003`, `s29_12_0006`) | silent | first loop iterates `transactions`, calls `toRemove.Add(t)` — different binding; second loop iterates `toRemove`, calls `transactions.Remove(t)` — different binding |
| `for var x in xs do if p(x) then xs.Remove(x); break; end; end;` (corpus `s29_12_0007`) | silent | the call is followed on every path by `break`; no advance follows; the runtime never faults — this is the classic legal shape and the reason the predicate is "advance reachable", not "call present" |
| `for var x in xs do if p(x) then _ := xs.Remove(x); return; end; end;` | silent | `return` on every path after the call |
| `for var x in xs do try xs.Add(9); throw new InvalidOperationException(); catch InvalidOperationException => Skip(), end try; end;` | **warns** | the `throw` is handled by a `catch` inside the loop body, so the loop resumes and advances — critique N-5: only a `throw` no in-body `catch` handles is a loop exit |
| `for var x in xs do var grow: () -> () := lambda() => xs.Add(x); end;` (corpus `s29_12_0009`) | silent | the structural call sits in the lambda's callable body, not the loop's; the loop defines the closure and never invokes it (captured `xs` is borrow-state inside the closure — §28.3 *Captured owned bindings* — so the call is admitted), and no advance follows a call the loop never runs. A local type declaration's member body (§21.10) is the same shape. Critique F-4: without this clause the text mandated a warning on a program that never faults. A closure the body *does* invoke (`grow();`) is "a call the body makes" — untraced, the chosen silence below |
| `for var x in xs do if x = 1 then xs[2] := 9; end; end;` (corpus `s29_12_0002`, `s29_12_0008`) | silent | an indexer-set is an element-level write, not in the structural list |
| `for var e in dict do dict[e.Key] := v; end;` | silent | dictionary indexer-set excluded — whether it inserts is a runtime fact |
| `for var x in xs do ys.Add(x); end;` | silent | different binding |
| `for var x in xs do var ys := xs; ys.Add(9); end;` | silent (chosen) | a borrow copy is a different binding; v1 does not follow it — the runtime fault remains |
| `for var x in _items do Helper.Prune(_items); end;` | silent (chosen) | the modification happens inside a call; not traced |
| `for var x in Items() do Items().Add(9); end;` | silent | the source is a call result, not a binding; two calls are two frames |
| `while xs.Count > 0 do using var x := xs.PopLast(); … end;` | silent | not a `for`; this is the remedy |
| `for var x in xs.Drain() do … xs.Add(…) end;` | silent | the source expression is `xs.Drain()`, a call result (a frame), not the binding `xs` — and `Drain` is the sanctioned draining iteration; the runtime behaviour of adding to a draining source is stdlib §4.5's, not this lint's |
| `for var x in xs do if p(x) then xs.Remove(x); end; end;` — conditional, fall-through | **warns** (corpus `s29_12_0005`) | the advance is reachable from the call; every execution that takes the branch faults at the next `MoveNext` |

**"Any path" versus dominance, decided.** The hazard is not "the loop contains a structural call" (a `break` after it is legal and common); it is "the loop *advances* after a structural call". On every execution path from the call to the loop's back edge the fault is certain — the runtime check is unconditional at the next advance, independent of the collection's contents afterwards. So the predicate is *reachability of the advance from the call*, and a conditional call is warned because the branch that runs it always faults when it continues. This is not the §28.2 dominance shape: there, the *use* is the fault site and dominance by the *kill* is what makes the use certain; here, the call is the kill and the advance is the use, and what must be certain is that an advance follows — which is a forward-reachability question, exactly answered by "not post-dominated within the body by a loop exit". No false positive arises from conditionality.

**Residual imprecision, stated.** (1) A `Remove(y)` whose argument is not present removes nothing; §29.12's list names `Remove` without qualifying it, and the runtime bumps the epoch on the call regardless (`bezel_runtime_collections.cpp:186`), so the lint follows the list — but the spec's silence on the not-found case is an open question (§9 Q1). (2) A structural call inside a *nested* `for` over a different binding, whose enclosing `for` iterates the receiver (`for var x in xs do for var y in ys do xs.Add(y); end; end;`): warned — the enclosing loop's advance is reachable; correct.

### 3.2 Lint B

| Shape | Silent? | Why (traced) |
|---|---|---|
| `var w := xs[0]; w.Ping(); xs.RemoveAt(0);` | silent | use before the kill |
| `var w := xs[0]; xs.RemoveAt(0); var again := xs[0]; again.Ping();` (corpus `s28_11_0010`) | silent | the borrow is re-taken after the mutation; `w` is not used after |
| `var w := xs[0]; xs[1] := new Widget(); w.Ping();` (corpus `s28_11_0011`) | silent | indexer-set not in the kill set; here also genuinely sound (a different slot) |
| `var w := xs[0]; xs.RemoveAt(1); w.Ping();` | silent | a different constant index; the borrowed element survives |
| `var w := xs[i]; i := i + 1; xs.RemoveAt(i); w.Ping();` | silent | the local was reassigned between; the per-slot rule declines to compare |
| `var w := xs[0]; if c then xs.Clear(); end; w.Ping();` | silent | the kill does not dominate the use — a conditional kill; the runtime backstop stands (no maybe-consumed rule for borrows is proposed) |
| `var w := xs[0]; xs.Insert(0, new Widget()); w.Ping();` | silent | `Insert`/`Add`/`Sort`/`Reverse` reposition or grow; the element object is alive |
| `var w := xs[0]; xs.Insert(0, new Widget()); xs.RemoveAt(0); w.Ping();` (corpus `s28_11_0012`) | silent | critique F-5: `RemoveAt(0)` dominates the use and matches the borrow's constant index, but the intervening `Insert(0, …)` repositioned `w`'s referent to index 1 — `RemoveAt(0)` disposes the *inserted* element and `w` is alive. The `RemoveAt(i)` leg therefore requires **no §29.12 structural operation on the binding between the borrow and the kill** (`PopAt(j)`, `PopFirst()`, `RemoveAt(j < i)`, `Insert(j ≤ i, …)`, `Sort()`, `Reverse()` all move what `coll[i]` names). The `Clear()` and `Remove(b)` legs are unaffected — they name the element, not a slot |
| `var v := od[k]; _ := od.Remove(k); v.Ping();` on an `OwningDictionary<K, V>` | silent (chosen) | critique N-6: the exact keyed analogue of `RemoveAt` at the borrow's index, and a certain dangle when `k` is a constant or an unreassigned local — but v1's kill set is keyed on the ordered collections' slot index, and a keyed leg would restate the same-index precision over key equality (§8.3); recorded liftable in the normative text, the design being "same key expression, same no-intervening-operation condition". `Clear()` on the dictionary *is* in the kill set (it names every element) |
| `var w := m.Get(h); _ := m.Remove(h); w.Ping();` — a method-call read, e.g. 0130's `OwningSlotMap<T>` | silent (chosen) | a read that is a method call is outside the producer set unless it is a §29.11 class-element terminal accessor; the map's *default-iteration* variable is inside it, so `Clear()` after it warns. The asymmetry is stated at stdlib §4.21 by proposal 0130 (critique N-11); widening the producer set to handle-keyed reads is a liftable of the same shape as the keyed-dictionary leg |
| `var w := xs[0]; var taken := xs.PopAt(0); w.Ping();` | silent | `PopAt` transfers the element out alive (`taken` owns it); `w`'s referent is not disposed by the call — the borrow now has an untracked source, which is §28.3's recorded residual, not a certain dangle |
| `var w := ys[0]; xs.Clear(); w.Ping();` | silent | different collection binding |
| `var w := arr[0]; arr.RemoveAt(0); w.Ping();` on a **borrowing** `Array<T>` | silent | borrowing-family removal disposes nothing (§28.11's borrow column: "removes the borrow; the caller's ownership is unaffected"); the element's holder still owns it |
| `for var w in xs do xs.Remove(w); w.Ping(); end;` | warns twice — lint A (the structural call on the iterated binding) and lint B (the iteration variable used after the dominating `Remove(w)`) | two hazards, two diagnostics; both correct |
| `var w := xs.First(); xs.Clear(); w.Ping();` | warns | the accessor's provenance roots at `xs` (§29.11's concrete-collection root, silent *there*, is exactly the root that names `xs` as the source *here*) |
| `var w := xs[0]; xs.RemoveAt(0); w.Ping();` (corpus `s28_11_0008`); `… xs.Clear(); w.Ping();` (`s28_11_0009`) | **warns** | the dominating kill of the borrowed element |

**The provenance rule, exactly.** Lint B's borrow sources are the three §28.3/§29.11 producers whose source is a *concrete owning-collection binding* in the same body: the indexer-get row (source `coll`), default iteration over the binding (§29.2: over a concrete collection "the chain is slot → collection → binding"), and a §29.11 class-element terminal accessor whose trace "roots at a concrete collection value … a local bound to one" — the trace §29.11 already defines, reused with its own vocabulary and stops (an interface-typed source, a call result, a materializer are *not* such roots for lint B: a materializer's result is a fresh borrowing container whose slots re-borrow the original elements — §29.11's pass-through — and lint B, in v1, keys only on the binding the kill is called on, so `var ys := xs.ToArray(); xs.Clear(); ys[0].Ping();` is silent, a chosen under-approximation recorded here). The producer set is closed: a read that is a method call — `Get`, `GetOrNull`, `TryGetValue`'s out, `Peek` — is not a producer for lint B unless it is a §29.11 terminal accessor, while the default-iteration variable of every owning-family collection is.

## 4. Alternatives considered and declined

1. **Status quo.** Declined per the doctrine: both hazards are recognized by the compiler's existing analyses (the loop's source binding; the borrow's source and the dominating kill), both are taught as traps, and the discard spelling of a comparable act — `_ := task;` — is a hard error. §5.28's argument applies unchanged.
2. **Rejection instead of a warning.** Declined for both. Lint A: the `break`-after-mutation shape is legal and common, and the "advance reachable" predicate is a flow fact a rejection would have to state as a rule of the language; §29.12's runtime fault is the defined semantics and stays. Lint B: §28.3's indexer row records the per-slot kill as *not statically tracked* with the checked-mode backstop as the regime — the same admitted-then-backstopped posture as §28.2's dominating-`Dispose()` warning (rationale §5.1's v0.184 record: "the posture continues to govern straight-line use after a site-announced kill, which stays a (now mandatory) warning plus the checked-mode backstop"). A rejection here would be the borrow-liveness checking rationale §5.1 declines.
3. **Lint A on dominance only** (warn only where every path from the loop head reaches the call). Declined: it would silence the conditional `if p(x) then xs.Remove(x); end;` — the *common* shape of the trap — while the hazard on the taken branch is certain. §3.1's argument.
4. **Lint A without the loop-exit exemption** (warn on every structural call in the body, accept the false positive on `break`). Declined: `if found then xs.Remove(x); break; end;` is a sanctioned, fault-free program; a lint that warns on it teaches a rule the language does not have, and the §5.28 doctrine's bar is *certainty*.
5. **Lint A following borrow copies and parameters** (`var ys := xs;` inside the loop). Declined for v1: aliasing through a copy is the general borrow-liveness question rationale §5.1 declines; the same-binding predicate is local and exact. Recorded liftable.
6. **Lint B on the indexer-set at the same constant index** (`var w := xs[0]; xs[0] := v; w.Ping();` — a certain dangle). Declined for v1 to keep one operation vocabulary across the two lints and §29.12; recorded liftable in the normative text itself.
7. **A general "borrow used after a dominating kill of its source" lint** (any `Dispose()` of any source, e.g. `using var view := h.Borrowed(); h.Dispose(); view.Label` — corpus `s28_10_0012`'s shape). Not taken: it is a wider proposal over every §28.3 producer, with its own provenance table; lint B is its collection-element instance, and its text is written so that the wider lint could subsume it. Recorded follow-on.
8. **Lint B on `PopAt`/`Pop` as kills.** Declined: they transfer the element out alive; the surviving borrow dangles only if the *new* owner disposes it, which is not certain at the call.
9. **Per-site suppression.** Declined, the recorded `DECLINED.md` row (*Per-site suppression spellings for the fresh-store and terminal-accessor lints*), extended to name these two: the remedies are one line each and convert the program from hazardous to sound.
10. **A keyed-removal leg for lint B** (`od.Remove(k)` after `od[k]`, same key expression). ## 5. Kernel and body-locality classification

- **Lint A — kernel.** §29.12 is outside §28/§30.5; stated for completeness: a **derivation** from §29.12's runtime rule (the fault is the language's defined semantics; the lint names it early) over §29.2's desugaring (the pinned `__source` is the binding the receiver is compared against). - **Lint B — kernel.** A **derivation**: [K4.2](../Bezel_Language_Spec.md#sec-kernel-k4) (the disposing removal is a flag-setting kill of the element — the owning column's `Remove`/`RemoveAt`/`Clear` "disposes"; not keyword-visible on the *element*, which is why the backstop, not a freeze, governs it — [K5.6](../Bezel_Language_Spec.md#sec-kernel-k5): "fields and collection slots are not frozen … a slot kill disposes — the K4 backstop is real there") + [K7.4](../Bezel_Language_Spec.md#sec-kernel-k7) (dominance; the straight-line subset) + [K2.1](../Bezel_Language_Spec.md#sec-kernel-k2) (the borrow's source is the collection binding — the producers row) with §29.11's provenance trace supplying the accessor leg. - **Body-locality** (proposal 0105 §1): both **local**. Lint A reads the loop's source expression, the call's receiver, and the body's own control flow; lint B reads the borrow's producer, the kill site, and dominance within one body; neither consumes a per-body fact of another body (lint B's accessor leg reuses §29.11's trace, which is itself local by the same-compilation-unit bound and is here needed only to its concrete-collection root).
