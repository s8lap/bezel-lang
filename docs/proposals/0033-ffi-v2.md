Bezel today can call C functions whose arguments and results are scalars, NUL-terminated strings, or Bezel-allocated buffers — and within that shape §32 is good: the trusted-but-unverified posture is honest, the `CString`-vs-`IntPtr` ownership-contract-at-declaration idea is genuinely elegant, and the v0.163 callback admission rule is the right one. But the review ran the three canonical real bindings against it and all three fail: **sqlite3** (out-pointer handles, unreadable column blobs), **libcurl** (variadic `curl_easy_setopt`, callbacks receiving `(ptr,len)` data Bezel cannot read), **BLAS** (no pointer-bearing numeric buffer — two byte-swizzled copies per matrix per direction). The strongest evidence is first-party: proposals [0007](0007-system-net-substrate.md), [0011](0011-process.md), and [0014](0014-signal-hooks.md) each route their native interaction through runtime-internal C++ rather than through §32 (§9 cites where). This proposal is the completion design: it promotes [§32.11](Bezel_Language_Spec.md#sec-reserved-for-future-revisions)'s unordered reserved list — "typed pointer wrappers, and structured-data marshalling" — into a scoped, staged plan, and adds the two items the reserved list omitted entirely (boundary `out`/`ref`, C-variadic imports).

Nothing here weakens §32's boundary contract. Every operation this proposal adds is **trusted but unverified** in exactly [§32](Bezel_Language_Spec.md#sec-foreign-function-interface)'s existing sense — "if the declaration is wrong, the call is undefined behavior" — and every one of them is *explicit at the call site*: there is no implicit dereference, no hidden copy, no silent promotion anywhere below.

## 0. Not in this proposal: the small §32 defects, routed to this run's spec-amendment trains

The review split its findings by disposition. The internal defects of the *current* chapter are **direct spec amendments** riding this run's revision trains, not design work, and are therefore deliberately absent below — listed here so the reader knows where they went:

- **Owned-return contradiction** — §32.6's unmarked `CString` ownership-transfer return vs [§28.1](Bezel_Language_Spec.md#sec-where-the-owned-modifier-can-appear)'s "owned returns are declared" vs the Appendix A.3 comment citing §32.5/§32.7, which say nothing; the amendment picks the explicit `: owned CString?` spelling (the v0.169 explicitness direction) and aligns all three sites.
- **Nullable-at-boundary silence** — §32.1's example returns `CString?` but §32.5 never admits any nullable form (and the compiler accepts `int?`, which has no C representation — review probe `p5_nullable.bz`); the amendment admits `CString?`/`WString?`/`RawBytes?`/nullable function types as possibly-NULL pointers and outlaws nullable value types.
- **Callback-exception policy** — §32.8's "swallows them, or aborts the program, depending on platform" is platform-nondeterministic semantics with an undefined value returned to the native caller; the amendment defines one behavior (abort with diagnostic, the Rust precedent).
- **Param-modifier silence** — the grammar admits `ref`/`out`/`owned` on extern params, §32.5 restricts only *types*, and the compiler today accepts `out` and **miscompiles it** (review probe `p7_time.bz` segfaults on a real libc call); the amendment *forbids* the modifiers on extern declarations, closing the miscompile. **§5 of this proposal is the design that re-admits `out`/`ref` with defined semantics.**
- **The §32.9 errno example** — `GetErrno()` annotated as "a user-declared extern wrapper" requires a user-compiled C shim §32 has no story for, and the pure-Bezel alternative needs a dereference primitive that doesn't exist; the amendment rewords the example honestly. **§3.6 of this proposal is the real primitive** (`Interop.LastErrno`).
- **Symbol/linking story** — the identifier-is-the-symbol rule is unstated, there is no rename/alias clause (contradicting [rationale §16.1](Bezel_Design_Rationale.md#sec-hand-written-declarations-not-bindgen)'s "with the names they want"), the bare-name resolution algorithm is one worked example, and failure timing (build-time `ld` today; §32.3 implies load-time) is unspecified; the amendment states the rule, adds a **`:= symbol "…"` alias clause**, and pins resolution/failure semantics. This proposal's §6 (variadic aliases) and §7 (per-arity aliases) *build on that clause* and are written assuming it.

Also routed to the same trains and not re-argued here: the inline-array parameter write-back rule and the impossible `[N]T` return-slot claim (§32.5), the synchronous-callback execution context and foreign-thread runtime obligations (§32.10), and the blocking-extern-stalls-its-domain paragraph (§32.10/§30.13). The purely editorial batch the review found already landed at v0.178 (visible at HEAD): `strlen`'s `UIntPtr` return, the x86-64 calling-convention wording, enums/`decimal` in the not-allowed list, and the un-stranding of the v0.175 `scoped` note.

## 1. The gap, measured against three real bindings

All claims verified against v0.178 text and probed against `build/bezelc`.

**What exists.** [§32.7](Bezel_Language_Spec.md#sec-pointers-and-intptr): "`IntPtr` is opaque. Bezel provides no language-level operation to dereference it; that is the native side's job." The only foreign-memory *reads* in the entire system are `string.FromCStringPointer`/`FromWStringPointer` (stdlib [§10.4](Bezel_Standard_Library.md#sec-conversions-to-bezel-types)) — reads until a NUL. Data flows *out* through `RawBytes.Pointer` (stdlib [§10.3](Bezel_Standard_Library.md#sec-rawbytes)), and native code can fill a Bezel-allocated `RawBytes` (read back via `CopyTo`); but data at a native-owned address can never flow in unless it is a NUL-terminated string. Records are rejected wholesale at the boundary (probe `p8_record.bz`: *"extern method parameter `tv` has type `TimeVal`, which is not permitted at the FFI boundary (§32.5)"* — correct per the §32.5 not-allowed list). There is no variadic declaration form, no boundary `out`/`ref` semantics, and only `RawBytes` exposes an address (no `.Pointer` on `CString`/`WString`, nothing on `OwningBuffer<T>`, stdlib [§4.14](Bezel_Standard_Library.md#sec-owned-buffers-and-spans)).

**What that costs, per exemplar:**

| Binding | Blocked on | Fixed in |
|---|---|---|
| sqlite3: `sqlite3_open(&db)` | no boundary out-params | §5 |
| sqlite3: `sqlite3_column_blob` result, `sqlite3_exec` `char** argv` | no foreign-memory reads | §3 |
| sqlite3: `sqlite3*` vs `sqlite3_stmt*` both `IntPtr` | no typed handles | §7 |
| libcurl: `curl_easy_setopt` | no C-variadic imports | §6 |
| libcurl: write callback receives `(ptr, len)` it cannot copy | no foreign-memory reads | §3 |
| BLAS: no address of any `double` buffer; two byte-swizzled copies each way | no typed buffer pointer | §3 |
| POSIX: `struct timespec`, `sigaction`, `sockaddr`, `stat` | no struct marshalling | §4 |
| glibc: `__errno_location()` returns an `int*` nothing can read; §32.9's own example unimplementable | no foreign-memory reads / no errno intrinsic | §3 |

**The first-party evidence.** 0007 wraps OpenSSL "runtime-internally behind a narrow sans-IO seam" of "~8 `bz_tls_*`" C++ entry points (0007 §6); 0011's destructor "SIGKILLs + reaps" through runtime intrinsics because `waitpid`'s out-status and `execve`'s `char*[]` argv are undeclarable (0011 §3 Q2/§4); 0014 delivers signals via "a runtime drain thread" because `struct sigaction` and a callback's code address are inexpressible (0014 §2 D4). Each of those runtime-internal choices has *additional* reasons that survive this proposal (§9 is honest about which) — but the pattern that even first-party designs cannot bind `waitpid` is the clearest possible signal that §32 v1 is a calling convention, not an FFI.

## 2. Design principles

1. **The trust posture is preserved, not diluted.** §32's boundary is trusted-but-unverified; every primitive below is exactly as trusted as the extern call it serves. This proposal adds no bounds checking, no lifetime verification of foreign addresses, and no partially-verified tier (the declined Panama-style alternative is §11). What it adds is *expressiveness* under the same honest contract, with the dangerous operations **named as dangerous** (`Load`/`Store`/`DangerousPointer`) and confined to one explicitly-imported module.
2. **Distinct types over `void*`, extended.** [Rationale §16.2](Bezel_Design_Rationale.md#sec-distinct-types-for-cstring-wstring-rawbytes) already records the argument: "Conflating them — as `void*` does — pushes the burden of remembering which is which onto the programmer at every call site. Distinct types let the compiler refuse calls that mix them up." That recorded reasoning, applied to the review's findings, *decides* two of this proposal's choices: typed pointers over an untyped `Marshal` class (§3.1), and record-typed handles over uniform `IntPtr` (§7.1).
3. **Hand-written declarations, not bindgen — unchanged.** [Rationale §16.1](Bezel_Design_Rationale.md#sec-hand-written-declarations-not-bindgen) stands; everything below is declarable by hand, and a future bindgen tool could emit it (nothing here precludes that, per §16.1's own note).
4. **No hidden costs.** Every copy below is a named method (`CopyToArray`, `FromForeign`); every pointer adjustment is a named, element-scaled method (`Add`, `LoadAt`); C's default argument promotions are a compile error naming the promoted type to write, never an implicit widening (§6.2).
5. **Engage, don't re-propose around, the variadic decline.** [Rationale §17.9](Bezel_Design_Rationale.md#sec-variadic-parameters-params) declines Bezel-side `params` because it hides allocation. C-variadic *imports* are a different question with different constraints (no allocation is at stake; an ABI is), and §6 answers it without touching §17.9: no Bezel method becomes variadic; call sites keep fixed arity.

## 3. Foreign memory access: `Ptr<T>`

The single highest-leverage gap. Two shapes were on the table, per the review: a **Marshal-style static class** (`Marshal.ReadInt32(p)` / `WriteInt32(p, v)` over bare `IntPtr` + byte offsets) or **typed pointer wrappers** (`Ptr<T>` with load/store/element access). This proposal recommends **`Ptr<T>`**.

### 3.1 The decision, argued

- **Rationale §16.2 has already made the argument.** An untyped read surface is `void*` with method-name suffixes: `Marshal.ReadDouble(p)` compiles whether `p` came from `sqlite3_column_blob` or `__errno_location`. `Ptr<double>` vs `Ptr<int>` puts that mistake at compile time — the exact benefit §16.2 records for `CString`/`WString`/`RawBytes`.
- **Element-scaled arithmetic kills the classic FFI bug class.** With byte offsets, every array walk hand-computes `i * sizeof(T)` with a platform-dependent `sizeof`; `LoadAt(i)`/`Add(count)` scale by the target ABI stride, computed by the compiler that knows it. The multiplication is not a hidden cost — it *is* the operation's meaning, and it appears in the method's one-line contract.
- **Extern declarations become self-documenting.** `sqlite3_column_blob(...): Ptr<byte>` says what §32.6 currently spends a paragraph of prose on per function: this is a borrowed, byte-typed pointer.
- **The costs, stated plainly.** `Ptr<T>` is a generic compiler-intrinsic record family where a static class would be ~14 methods; its instantiation gate needs the [§3.6](Bezel_Language_Spec.md#sec-derived-type-properties)-style per-instantiation check (machinery the compiler already runs for `OwningArray<T>`'s element restriction); and generic static access (`Ptr<byte>.Zero`) leans on [§22.12](Bezel_Language_Spec.md#sec-static-members) per-instantiation statics. All existing mechanisms, but more of them than a static class would touch. The lean is that §16.2's recorded value judgment outweighs the surface count. (The full decline record for the Marshal shape is §11.)

`IntPtr` itself **stays opaque** — no arithmetic, no dereference, unchanged. §32.7's sentence is amended to "…no language-level operation to dereference it; typed access goes through `Ptr<T>` ([§32.12], explicit and trusted)". The two types partition the roles: `IntPtr` is *placement* (an opaque address flowing through signatures and pointer arrays), `Ptr<T>` is *access*.

### 3.2 The surface

```bezel
// PROPOSED — module System.Interop (new; NOT auto-imported — the import line is
// the audit marker that a file touches foreign memory; owner question §13 q2).
// Compiler-intrinsic value record; representation identical to IntPtr.
// T is gated (per-instantiation, §3.6-style diagnostic) to the FFI-POINTEE SET:
//   integer types, float, double, bool, IntPtr, UIntPtr — and, per §4 below,
//   C-compatible records. Nested Ptr<Ptr<T>> is NOT admitted in v1 (§11).
public record Ptr<T>
  public static const Zero: Ptr<T>;                    // compiler-provided, like IntPtr.Zero

  public static method FromIntPtr(p: IntPtr): Ptr<T>;  // the only untyped->typed entry: EXPLICIT
  public method ToIntPtr(): IntPtr;

  // Every member below is TRUSTED BUT UNVERIFIED (§32's preamble posture, verbatim):
  // the address's validity, alignment, and pointee type are the programmer's
  // declaration; a wrong one is undefined behavior.
  public method Load(): T;                             // read  *p
  public method Store(value: T);                       // write *p
  public method LoadAt(index: int): T;                 // read  p[index]  (index scaled by T's ABI stride)
  public method StoreAt(index: int, value: T);         // write p[index]
  public method Add(count: int): Ptr<T>;               // p + count elements; negative counts allowed

  public method CopyToArray(count: int): owned Array<T>;   // count elements, copied Bezel-side
  public method CopyFromArray(source: Array<T>);           // source.Count elements written at p

  // Equality is declared explicitly, NOT left to §9.2's record synthesis — the
  // stdlib §10.0 IntPtr precedent, for the same reason: Ptr<T> has no
  // auto-properties, so the synthesized `=` would be the zero-property
  // "every-pair-equal" form. The intrinsic compares the address representation.
  public static method operator =(a: Ptr<T>, b: Ptr<T>): bool;
  public static method operator <>(a: Ptr<T>, b: Ptr<T>): bool;
end Ptr;
```

Rules, normative once this lands:

- **`Ptr<T>` joins §32.5's FFI-compatible list** — parameters, returns, and positions inside FFI function types. It marshals as the pointer it is. (`Ptr<T>?` is *not* needed at the boundary and **not admitted in extern signatures** — the null pointer is `Ptr<T>.Zero`, same as `IntPtr`'s convention. Away from the boundary, `Ptr<T>?` exists like every value type's nullable form ([§7.2](Bezel_Language_Spec.md#sec-nullable-value-types)); no language-wide special rule is proposed — it simply has no FFI meaning.)
- **`bool` pointee**: 1-byte load/store with §32.5's non-zero-is-true read rule, restated at `Ptr<bool>`.
- **`Ptr<T>` is sendable — stated, not silently defaulted.** By [§30.14](Bezel_Language_Spec.md#sec-sendable-types)'s value-type rule (sendable iff not borrow-bearing, not move-only) `Ptr<T>` *computes* sendable, and this proposal ratifies that outcome rather than inheriting it unexamined — because it is the first time the outcome has teeth: today an `IntPtr` crosses domains harmlessly (nothing can dereference it), but a `Ptr<int>` in a spawn argument gives two domains typed `Load`/`Store` over one address — a typed, dereferenceable breach of §30.14's "no mutable state is ever reachable from two domains," which the sendable property otherwise enforces by construction. The alternative — a non-sendable carve-out — is honest-*looking* but laundered in one line (`ToIntPtr`/`FromIntPtr`; `IntPtr` is a sendable record), buying a special §30.14 rule that protects nothing. So: sendable, plus a new §32.10-style programmer-responsibility bullet, normative when this lands: *foreign memory reached through a pointer that has crossed a domain boundary is outside domain isolation; unsynchronized cross-domain `Load`/`Store` on the same address is a data race and undefined behavior — synchronization ([§30.12](Bezel_Language_Spec.md#sec-thread-synchronization)) is the programmer's obligation.* Owner question §13 q11.
- **Pointer-arithmetic stance**: arithmetic exists, is **element-scaled only**, and is **named, never operatored** — there is no `p + 1`, no `-`, no ordering comparisons in v1 (a `<` over unrelated allocations is UB in C; nothing in the exemplar corpus needs it). Byte-granular work is spelled `Ptr<byte>`, where element-scaled *is* byte-scaled. Manual struct-field offsets (the §4-decline workarounds) compose `Add` on `Ptr<byte>` with `FromIntPtr` re-typing — ugly by design; §4 is the non-ugly path.
- **Reading pointers from memory** — the `char**` shape — is `Ptr<IntPtr>`: `LoadAt(i)` yields an `IntPtr` to re-type or hand to `string.FromCStringPointer`. This covers argv/envp/column-name walking without nested `Ptr<Ptr<T>>` (declined v1, §11).
- **No pinning concept exists or is needed.** Bezel has no moving collector ([§28](Bezel_Language_Spec.md#sec-resource-management): no GC; heap objects never relocate), so every address obtained below is stable until its owner's disposal. This is a real simplification over .NET's `fixed`/`GCHandle` machinery and is stated once, normatively, in the new spec section.

### 3.3 Bulk transfer: `RawBytes.FromForeign`

```bezel
// PROPOSED — addition to stdlib §10.3 RawBytes:
public static method FromForeign(p: IntPtr, length: int,
    freeOnDispose: bool := false): owned RawBytes;
```

Wraps `[p, p + length)` **without copying**. With `freeOnDispose := false` (the default) the result is a *view*: `Length`, `Pointer`, and `CopyTo` work over foreign memory, and disposal releases nothing — the standing `RawBytes` destructor contract ("releases the underlying buffer **if owned by this instance**", stdlib §10.3) already has the vocabulary. With `freeOnDispose := true`, disposal passes `p` to the C runtime's `free(3)` — the ubiquitous "returns a malloc'd buffer the caller must free" C contract, e.g. POSIX `getline`'s buffer or `realpath(path, NULL)`. Two honest costs, stated in the stdlib text: (a) if the buffer was not allocated by the same C runtime's `malloc` family, disposal is undefined behavior — the flag is a trust obligation like every §32.10 bullet; (b) a custom deallocator (a library's `libfoo_free`) is **not** expressible through this flag — that contract is the hand-written wrapper class's job (§7.2), and folding a function argument into `FromForeign` was declined (§11). *(Naming note: the review sketched this as an `owned:` flag; `owned` is a reserved modifier ([Appendix B](Bezel_Language_Spec.md#sec-appendix-b)), so the parameter is `freeOnDispose`.)*

Cross-domain note, since §3.2's sendability rule makes the question live: a `FromForeign` view adds no new cross-domain surface. `RawBytes` is a class whose stdlib section states no sendability, and under [§30.14](Bezel_Language_Spec.md#sec-sendable-types)'s class rule (not `sealed` → not sendable) it does not cross domains — so a view over foreign memory cannot be spawned or channeled away. Worth one confirming sentence in stdlib §10.3 when this lands, so the invariant is stated rather than implied (folded into owner question §13 q11).

### 3.4 Addresses of the sibling types

The review found the address asymmetry: only `RawBytes` has `.Pointer`, so a `char*[]` (execve/posix_spawn argv — 0011's exact shape) cannot be built, and no numeric buffer can reach native code without the byte-swizzle detour.

```bezel
// PROPOSED — stdlib §10.1 / §10.2 additions (same contract as RawBytes.Pointer,
// stdlib §10.3: "valid until the RawBytes is disposed"):
public readonly property Pointer: IntPtr;          // on CString and on WString

// PROPOSED — stdlib §4.14 addition, admitted only where T is in §3.2's
// FFI-POINTEE SET (integer types, float, double, bool, IntPtr, UIntPtr) — a set
// that itself CONTAINS the intrinsic records IntPtr/UIntPtr, so the gate's
// rejection wording is "outside the set" (classes, strings, ordinary records),
// NOT "record-typed T". §9's argv row depends on OwningBuffer<IntPtr>; stdlib
// §4.14 already admits record-typed T without owned fields as elements, so only
// the gate is new. Ptr<T> ELEMENTS are excluded here — their DangerousPointer
// would be the declined Ptr<Ptr<T>> (§11); pointer arrays are OwningBuffer<IntPtr>,
// exactly the argv shape. C-compatible record elements (§4) join at Stage B,
// when Ptr<R> exists to give the result a type.
public method DangerousPointer(): Ptr<T>;          // on OwningBuffer<T>; valid until
                                                   //   the buffer is disposed
```

`CString.Pointer` is `IntPtr` (its dominant use is *placement* — storing into pointer arrays); `OwningBuffer<T>.DangerousPointer()` is `Ptr<T>` (its dominant use is typed access and typed extern params). The `Dangerous` prefix marks the one accessor whose result aliases mutable Bezel-owned slots — the name is the warning, following the review's recommendation; the spelling is owner question §13 q8.

**The lifetime hazard, disclosed as semantics — not filed under naming.** "Valid until the buffer is disposed" is the whole contract, and the borrow checker has no sight of it: these accessors hand out addresses aliasing mutable Bezel-owned storage, and once the address crosses the boundary, native code that *retains* it past the synchronous call frame — curl storing a write-target buffer, a userdata slot, an event-loop registration — holds a pointer whose validity ends at a disposal the native side is never told about. That retained-pointer use-after-free is undiagnosable by any rule in this proposal or in §32; it is [§32.10](Bezel_Language_Spec.md#sec-boundary-contract)'s existing "pointer values being valid for their intended use" responsibility, now with a mutable Bezel-owned target. No enforceable restriction exists (any prose ban is laundered through `IntPtr` in one line), so the design position is **disclosure plus pattern**: the new stdlib text states native retention past the call explicitly as a trusted-lifetime obligation, and the recorded idiom is §7.2's wrapper class *owning both the buffer and the registration* — its destructor deregisters (or tears down the native object) before the buffer's disposal runs, so the ordering is structural, not remembered. This is its own owner question (§13 q12), separate from q8's cosmetics.

### 3.5 Worked bindings

**sqlite3 column blob** (the unreadable-result exemplar):

```bezel
import System.Interop;

extern "sqlite3"
  public method sqlite3_column_blob(stmt: IntPtr, col: int): Ptr<byte>;   // borrowed; valid
  public method sqlite3_column_bytes(stmt: IntPtr, col: int): int;        //   until next step
end;

public static class Blobs
  public static method ReadBlob(stmt: IntPtr, col: int): owned Array<byte>
    var n := sqlite3_column_bytes(stmt, col);
    var p := sqlite3_column_blob(stmt, col);
    if n = 0 or p = Ptr<byte>.Zero then          // SQLite returns NULL for the empty blob
      return new Array<byte>(0, 0);              // sized ctor (count, fill), stdlib §4.4
    end;
    return p.CopyToArray(n);                     // ONE explicit copy; result is Bezel-owned
  end ReadBlob;
end Blobs;
```

**curl write callback** (the `(ptr, len)`-data exemplar; the extern declaration for `curl_easy_setopt` is §6's):

```bezel
// C: size_t cb(char* ptr, size_t size, size_t nmemb, void* userdata)
public static class Sink
  public static method OnData(data: Ptr<byte>, size: UIntPtr, nmemb: UIntPtr,
      user: IntPtr): UIntPtr
    var count := int(ulong(size) * ulong(nmemb));        // §32.7 explicit conversions
    using var chunk := data.CopyToArray(count);          // the read §32 v1 could not express
    // hand off: append to §30.12-synchronized state, or route through `user`
    // (the §32.8 user-data discipline) — elided; the READ is the point.
    return UIntPtr(ulong(count));                        // "count consumed" per curl's contract
  end OnData;
end Sink;
```

The callback runs synchronously on the thread inside `curl_easy_perform` — the same-thread context the §32.10 amendment (§0) pins down. One obligation is load-bearing for the *general* shape and is stated here rather than silently assumed: `CopyToArray` **allocates from the Bezel runtime inside a callback**. On the same-thread path that is ordinary Bezel code and fine. But [§32.10](Bezel_Language_Spec.md#sec-boundary-contract) confines a callback reached from a *foreign* thread to §30.12-synchronized state and TCS completion — and says nothing about whether allocation (a runtime service) is available on a domain-less, unregistered thread at all. Whether `CopyToArray`/`FromForeign` may run there is a **runtime obligation this proposal flags, not discharges**; it is routed to the §32.10 amendment train's foreign-thread bullet (§0), alongside the stricter async-signal-safety case §9's 0014 row already flags. Until it is pinned, a binding whose data callback genuinely arrives on a library-owned worker thread must treat in-callback allocation as unspecified; curl's same-thread callback — the example above — does not depend on the answer.

**errno** — the §32.9 example, made real. The portable primitive is a runtime intrinsic (the platform spelling of the thread-local differs: `__errno_location` on glibc/musl, `__error` on macOS, `_errno` on Windows):

```bezel
// PROPOSED — module System.Interop:
public static class Interop
  // The calling thread's C errno, read directly. Valid only when read BEFORE the
  // next extern call or runtime operation on this thread (the .NET GetLastPInvokeError
  // lesson: intervening code may clobber the thread-local) — and NEVER across an
  // await: a continuation may resume on a DIFFERENT OS thread (§30.13), so a
  // post-await read is not clobber-risk, it is ANOTHER thread's errno. Read it
  // FIRST, synchronously, in the same continuation as the failing call.
  public static method LastErrno(): int;

  // See §4.4 for CodeAddress (the one other member proposed on this class).
end Interop;

// What it desugars to on glibc — declarable in v2 as a platform-specific binding:
extern "libc"
  public method __errno_location(): Ptr<int>;
end;
// ... open(path, flags) < 0 → var e := __errno_location().Load();
```

The discipline the doc-comment states is real, not decorative: read errno into a local *before* constructing the exception message (interpolation allocates; allocation is a runtime operation). `Interop.LastErrno()` carries the same caveat. The §32.9 example is rewritten against `LastErrno` when this lands; until then the amendment train's honest rewording (§0) holds the fort.

**argv walking** — sqlite3_exec's `char**` row callback, the pointer-array-read exemplar:

```bezel
// C: int cb(void* user, int argc, char** argv, char** colNames)
public static method OnRow(user: IntPtr, argc: int,
    argv: Ptr<IntPtr>, cols: Ptr<IntPtr>): int
  var i := 0;
  while i < argc do
    var cell := argv.LoadAt(i);                          // char* — NULL for SQL NULL
    if cell <> IntPtr.Zero then
      var text := string.FromCStringPointer(cell);       // stdlib §10.4: copies, no ownership
      // ...
    end;
    i := i + 1;
  end;

end OnRow;
```

**BLAS dgemm** — the double-copy exemplar dissolved by `DangerousPointer`:

```bezel
extern "openblas"
  public method cblas_dgemm(order: int, transA: int, transB: int,

public static method Multiply(a: OwningBuffer<double>, b: OwningBuffer<double>,
```

Addresses are valid across the call: the borrowed buffers outlive the synchronous call frame by the ordinary [§28.3](Bezel_Language_Spec.md#sec-local-variables-ownership-and-borrows) rules, and nothing relocates (§3.2's no-moving-collector note). Compare v1's only route: per-element `BitConverter` swizzling into `Array<byte>`, `RawBytes.From` (a copy), the call, `CopyTo` (a copy), per-element reassembly — per matrix, per direction.

## 4. C-compatible records: struct marshalling

### 4.1 The derived property

Struct marshalling enters through the mechanism [§3.6](Bezel_Language_Spec.md#sec-derived-type-properties) mandates for structural classification ("New rules added to this specification that need a structural classification of types must define it as a derived type property"). One new table row:

| Property | Defined in | Classifies |
|---|---|---|
| **C-compatible** | §32.13 (new; §32.12 is §3's foreign-memory section) | records passable across the FFI boundary: fixed field order, FFI-pointee field types, target-C-ABI layout |

A record is **C-compatible** iff every field's type is:

- an FFI-pointee scalar (integer types, `float`, `double`, `bool`, `IntPtr`, `UIntPtr`, `Ptr<T>`), or
- an inline array `[N]T` of such a scalar — for *primitive* elements this is [§32.5](Bezel_Language_Spec.md#sec-ffi-compatible-types)'s existing packed-layout promise ([§15.1](Bezel_Language_Spec.md#sec-inline-arrays)); for `[N]IntPtr`/`[N]UIntPtr`/`[N]Ptr<T>` elements it is a **delta this proposal owns**, not something §32.5 already gives (its text expressly excludes pointer-typed and record-typed elements): the same packed C-equivalent layout, with the element set extended to the full FFI-pointee scalar set — or
- another C-compatible record (nesting; recursion is impossible because records are value types).

Everything else disqualifies: `string`, `char`, `decimal`, nullable types, enums (same §32.5 idiom — declare the underlying integer, cast at the boundary), class/interface/function-typed fields, and borrow-bearing content generally (excluded already by the scalar gate — a C-compatible record is by construction not [borrow-bearing](Bezel_Language_Spec.md#sec-records-and-disposal) and has no disposal obligations, [§9.7](Bezel_Language_Spec.md#sec-records-and-disposal)). Per §3.6's rules the property is computed never declared, evaluated per-instantiation for generic records, part of the public contract, and named in diagnostics.

**The layout promise — the genuinely new spec surface, stated plainly.** Bezel today makes *no* normative claim about any record's memory layout. This proposal adds one, scoped exactly to C-compatible records: *a C-compatible record's in-memory representation is the target C ABI's layout for the corresponding C struct — fields in declaration order (positional-record parameters in positional order; body-record fields in declaration order), each at its C-equivalent type's ABI alignment, with the ABI's padding and trailing padding.* Field reordering and packing optimizations are forbidden for classified types; all other records keep unspecified layout. This is the first representation promise in the language and deserves its own ratification (owner question §13 q4). What it does **not** promise is platform-independence — sizes and layouts vary exactly as C's do (a record with an `IntPtr` field already varies), and *which* C struct definition matches which platform remains the programmer's trusted declaration, per §32's posture. `glibc`'s and macOS's `struct addrinfo` famously order `ai_addr`/`ai_canonname` differently; the Bezel record for each is a platform-specific declaration, exactly as a hand-written C binding's would be.

**The §3.6 reservation clause, engaged head-on.** §3.6 closes with a clause that cuts *against* this section and must not be walked past: *"Dispatch of behavior (not merely admissibility) on a derived type property — as the element category does for buffer and collection slot semantics — is reserved to compiler-known standard-library types; it is not a user-available mechanism in this revision."* The layout promise attaches a consequence to a derived property of **user** records — a `TimeSpec` gains a pinned representation purely from its structure — and that is more than admissibility, even though it is not runtime dispatch (nothing *executes* differently by classification; a static representation guarantee attaches, compile-time-visible and constant). Sendability, the nearest precedent, governs only whether a value may cross a boundary and never pins a byte. Two readings exist: (a) representation is not "behavior," so the clause is untouched — defensible on the letter, but it reads as lawyering around a clause whose evident purpose is to keep derived properties from silently acquiring semantic weight on user types; (b) the clause needs a scoped amendment. This proposal takes **(b)** and puts the amendment in Stage B's spec surface: §3.6's closing clause gains an explicit, single exception — *"…; the one exception is the C-compatible classification ([§32.13]), whose consequence is a static representation guarantee, not behavior dispatch — a deliberate extension ratified with the FFI's structured-data design."* The ratification rides owner question §13 q4 together with the promise itself; neither lands without the other.

### 4.2 Admission, staged

**v1 (this proposal): by pointer.** A C-compatible record crosses the boundary only *by address*:

- as a `ref`/`out` extern parameter (§5's rules; C sees `T*`) — covering `clock_gettime(&ts)`, `gettimeofday(&tv)`, `sigaction(sig, &act, &old)`, `getsockname(fd, &addr, &len)`;
- as the pointee of `Ptr<R>` — `Load()`/`Store(v)` copy whole structs between foreign memory and Bezel record values, `LoadAt`/`Add` stride by the struct's ABI size — covering result-walking shapes (`getaddrinfo`'s chain: pointer fields are `IntPtr` scalars, so `AddrInfo` classifies; `readdir`'s `dirent*`). A record load is **not** bitwise: `bool` fields are per-field normalized on load (any non-zero byte reads as `true` — §32.5's receive rule, applied field-wise), so a C struct whose flag byte holds 7 yields a Bezel `bool` that equals `true` and hashes as `true`; stores write 0/1 per §32.5's send rule.

**The by-pointer cost, stated honestly too.** Even without by-value passing, Stage B requires a **per-target C-struct layout engine** — field offsets, per-field alignment, intra-struct and trailing padding, for each supported ABI (SysV x86-64, Win64, AArch64) — and that is *new compiler capability*, not "machinery the compiler already runs": what §3.1 cites as already-running is the per-instantiation *gate*, and the only C-layout support in the compiler today is §32.5's packed inline arrays of primitives. Mixed-type fields with alignment and padding are strictly more. `Ptr<R>`'s `Load`/`LoadAt` stride and every marshalled field access depend on this engine; it is the bulk of Stage B's size (§10's table now says so) and is shared with — amortized by — Stage D.

**Explicitly staged later (design now, ship later — Stage D, §10):** **by-value parameters and returns**, and **callbacks receiving structs by value**. The honest reason for the split: passing a struct by value on x86-64 SysV requires the *frontend* to run the ABI **classification** algorithm on top of the layout engine (eightbyte splitting, INTEGER/SSE classing, hidden `sret` for large aggregates — LLVM deliberately does not do this for you), per target, on both the call and callback-receive sides. It is well-trodden but genuinely large work with real miscompile risk, and the by-pointer subset unblocks every exemplar in §1 without it (`div_t`-style small-struct returns are the only corpus casualty). One carve-out ships in v1 because its ABI case stays scalar-simple on every supported target: single-*integer/pointer*-field records (§7.1).

**Declined: unions and bitfields** — with reasons, in §11.

### 4.3 Worked binding: `clock_gettime`

```bezel
import System.Interop;

// C (POSIX, Linux x86-64): struct timespec { time_t tv_sec; long tv_nsec; };
public record TimeSpec(Sec: long, Nsec: long);          // C-compatible: two longs

extern "libc"
  public method clock_gettime(clockId: int, out ts: TimeSpec): int;   // int clock_gettime(clockid_t, struct timespec*)
end;

public static method MonotonicNanos(): long
  var rc := clock_gettime(1, out var ts);               // CLOCK_MONOTONIC
  if rc <> 0 then
    var e := Interop.LastErrno();                       // read FIRST — before the interpolation
    throw new IOException($"clock_gettime failed: errno={e}");   //   allocates (§3.5's window rule)
  end;
  return ts.Sec * 1000000000L + ts.Nsec;
end MonotonicNanos;
```

### 4.4 Worked shape: `sigaction`, and the one intrinsic it still needs

0014's substrate struct, declared per platform (the honest platform-specificity of §4.1 on display — this is the **glibc x86-64** layout; the raw kernel struct orders fields differently):

```bezel
public record SigAction(
  Handler: IntPtr,          // sa_handler / sa_sigaction (union head — see §11, unions)
  Mask: [16]ulong,          // glibc sigset_t: 1024 bits
  Flags: int,
  Restorer: IntPtr);        // glibc-internal; set to IntPtr.Zero

extern "libc"
  public method sigaction(signum: int, ref act: SigAction, out old: SigAction): int;
end;
```

`Handler` is an `IntPtr`, not a function-typed field — function-typed fields are deliberately **not** C-compatible (§4.1), because loading such a field back from foreign memory would materialize a callable Bezel function value from an arbitrary address, which is the call-through-pointer capability §8 keeps deferred. Installing a *Bezel* callback therefore needs one small, deliberately **one-way** intrinsic:

```bezel
// PROPOSED — on System.Interop.Interop:
// The process-lifetime code address of a callback admissible under §32.8.
// Generic, with a §3.6-style per-instantiation gate: F must be an FFI-compatible
// function type (§32.5's function-type rule); any other F is rejected at the
// instantiation site — the same pattern as Ptr<T>'s pointee gate, so the
// "overload set" is the type system's, not an undeclarable open-ended list.
// One-way by design: there is no address→function inverse (see §8).
public static method CodeAddress<F>(callback: F): IntPtr;
```

Three rules make that signature honest, and they are normative text in the new spec section, not reader inference:

1. **The argument position carries [§32.8](Bezel_Language_Spec.md#sec-callbacks)'s admission rule** — static method reference or non-capturing lambda, checked here exactly as at an extern callback parameter; a capturing lambda or bound instance-method reference is rejected with §32.8's diagnostic.
2. **The [§28.14](Bezel_Language_Spec.md#sec-scoped-callback-parameters) call-bounded default is explicitly exempted at this position, not silently violated.** A plain function-typed parameter promises the caller the callee retains nothing past the call — and `CodeAddress`'s entire purpose is a retention (the returned address gets stored into foreign memory as a signal handler or vtable slot). Neither plain nor `scoped` describes that; the honest statement is: values admitted by rule 1 are *environment-free*, so there is no capture set for §28.14's bounds to protect — what escapes is a bare code address, process-lifetime per [§32.10](Bezel_Language_Spec.md#sec-boundary-contract)'s v0.163 registration bullet ("such a pointer may be retained by native code … and remains valid until process exit; there is nothing to pin and nothing to unregister"). The new text states that §28.14 has nothing to check at this position and does not apply — the same reasoning the v0.163 bullet already records for extern callback arguments, extended to the one stdlib method that mints the address.
3. **One-way by design**: no address→function inverse exists (§8 keeps call-through-pointer deferred).

`new SigAction(Interop.CodeAddress(Handlers.OnSignal), mask, flags, IntPtr.Zero)` (with `F` inferred as `(int) -> ()`) then expresses 0014's installation. Whether *running* a Bezel callback in a raw signal-handler context is async-signal-safe is a runtime obligation this proposal flags but does not discharge (§9's 0014 row); the self-pipe pattern's `write`-only handler is the shape that keeps the obligation small.

## 5. `out` and `ref` at the boundary

The amendment train forbids `ref`/`out`/`owned` on extern declarations *today* (closing probe `p7_time.bz`'s live segfault, §0). This section is the design that re-admits two of them with defined semantics — the review's option (b), which "would neatly solve waitpid(&status)/sqlite3_open shapes."

**Admitted forms.** On extern parameters whose type is an FFI-pointee scalar or a C-compatible record:

- `ref p: T` — C sees `T*`, receiving the **address of the caller's storage**, no shadow copy. Direct passing is the *normative* semantics, not a justified-by-unobservability shortcut: a [§32.8](Bezel_Language_Spec.md#sec-callbacks) callback invoked from inside the extern call (the qsort shape) runs Bezel code on the same thread mid-call and *can* observe the storage — through static state, or through a `Ptr` previously derived from it — so direct and copy-in/copy-out are distinguishable in the re-entrant case. Direct is chosen precisely so that what such a callback observes is the native callee's writes as they land, with no shadow-copy surprises. The [§22.3](Bezel_Language_Spec.md#sec-parameter-modifiers) rules apply unchanged: initialized before the call, `ref` written at the call site, native reads *and writes* visible after the call.
- `out p: T` — C sees `T*`, same address passing. §22.3's callee obligation ("must assign on every exit path") **cannot be checked across the boundary**; instead, normatively: *after the call returns, the argument variable is definitely-assigned; whether the native function actually wrote it is part of the trusted declaration.* If it did not, the variable holds indeterminate bits — for integers a garbage value, for `IntPtr`/`Ptr<T>` a garbage pointer whose *use* is where undefined behavior begins. This is stated as a §32.10 programmer-responsibility bullet, not hidden. The practical discipline (check the return code before consuming out-values) is documented but, honestly, unenforced — many C functions write out-params only on success.
- Call-site syntax is unchanged §22.3/[§22.4](Bezel_Language_Spec.md#sec-inline-out-declarations): `ref x`, `out x`, `out var x` (inline declaration included).

**Not admitted, with reasons:** `out owned` (ownership transfer through an out-slot has no defined native contract — who allocated, who frees? the `CString`-return contract of §32.6 covers the owning case, and typed handles + `out h: IntPtr` cover the rest); `ref`/`out` on `CString`/`WString`/`RawBytes`/function types (a `char**` out-param bundles allocation *and* ownership *and* encoding in one slot — declare `out p: IntPtr` and read/wrap explicitly, contract visible at the read site); `scoped` (already illegal on extern, v0.175, unchanged).

**The exemplar, expressible:**

```bezel
extern "sqlite3"
  public method sqlite3_open(filename: CString, out db: IntPtr): int;
  public method sqlite3_close(db: IntPtr): int;
end;

public static method Open(path: string): owned Database    // Database: a wrapper in the §7.2 pattern —
                                                            //   its Stage-A form takes the raw IntPtr; the
                                                            //   §7.2 listing shows the Stage-B typed-handle form
  using var cpath := CString.From(path);
  var rc := sqlite3_open(cpath, out var raw);
  if rc <> 0 then
    // per SQLite's contract a handle may exist even on failure and must be closed:
    if raw <> IntPtr.Zero then
      var ignored := sqlite3_close(raw);
    end;
    throw new IOException($"sqlite3_open failed: rc={rc}");
  end;
  return new Database(raw);
end Open;
```

`waitpid(pid, out status: int, options)` — 0011's shape — falls out identically. Appendix C gains the rule alongside the §32.5 type rule. The compiler work re-implements what `p7_time.bz` proved is currently miscompiled; the amendment's forbid-first sequencing means no user ever sits on the broken path in between.

## 6. C-variadic imports: per-arity aliases on the `symbol` clause

**The trap this section exists to close.** The obvious workaround — declaring a fixed-arity extern for a variadic symbol — is **undefined behavior on x86-64 SysV**: a variadic callee's prologue consults `%al` (the count of vector registers used), which a non-variadic call site never sets. It often works, until it doesn't. The amendment train adds the loud warning to §32.11 (§0); this proposal adds the sound mechanism. [Rationale §17.9](Bezel_Design_Rationale.md#sec-variadic-parameters-params)'s `params` decline is engaged, not contradicted: no Bezel-side method becomes variadic, no allocation is hidden, and every call site below has fixed, declared arity.

### 6.1 The mechanism

The linking amendment (§0) gives `ExternDecl` an alias clause: `:= symbol "name"`. This proposal extends it with a variadic marker:

```
// PROPOSED Appendix A.3 delta (the ":=" symbol clause itself is the amendment's):
ExternDecl     ::= Visibility? "method" Identifier "(" ParamList? ")"
                   (":" "owned"? Type)? (":=" "symbol" StringLiteral VariadicClause?)? ";"
VariadicClause ::= "variadic" "(" IntLiteral ")"
```

`symbol` (the amendment's) and `variadic` are new **contextual keywords** and each takes an [Appendix B.2](Bezel_Language_Spec.md#sec-contextual-keywords) table row on the `convention` precedent — keyword meaning only inside the extern alias clause, ordinary identifiers everywhere else.

`variadic(N)` declares: *the named symbol is a C-variadic function whose fixed parameters are the first N declared parameters; the remaining declared parameters are passed in the symbol's variadic slots.* The Bezel method itself is an ordinary fixed-arity method — ordinary overloading, ordinary call syntax — but the compiler emits the call **with the variadic ABI** (on SysV: `%al` set correctly; on every target: the variadic calling sequence). Several aliases may name one symbol at different trailing shapes.

### 6.2 No silent promotions

C applies default argument promotions to variadic arguments (`float`→`double`, small integers→`int`). Bezel refuses to do this implicitly: **a variadic-position parameter must already have a promoted type** — `int`, `uint`, `long`, `ulong`, `double`, `IntPtr`, `UIntPtr`, `CString`, `WString`, `Ptr<T>`, or an FFI function type. Declaring `float`, `bool`, `byte`, `sbyte`, `short`, or `ushort` in a variadic position is a compile error naming the type to write instead ("C promotes `float` variadic arguments to `double`; declare the parameter as `double`"). The promotion happens in the programmer's declaration, where it is visible — principle §2.4.

`RawBytes` is **excluded from variadic positions**, deliberately: [§32.5](Bezel_Language_Spec.md#sec-ffi-compatible-types) defines it only as "a pointer-and-length pair," and no spec text pins its C-level marshalling shape as one argument or two. In a fixed-arity position that omission is a one-line clarification that can ride the §0 amendment trains; in a variadic slot the argument *count* is the caller-side ABI contract (`%al` and the stack layout depend on it), so admitting `RawBytes` before its shape is normative would rebuild exactly the trap this section exists to close. Pass `Ptr<byte>` or `IntPtr` plus an explicit length argument.

### 6.3 Worked: the two load-bearing cases

```bezel
// curl_easy_setopt(CURL*, CURLoption, ...) — one trailing arg, type keyed by option:
extern "libcurl"
  public method SetOptLong(h: IntPtr, opt: int, value: long): int
      := symbol "curl_easy_setopt" variadic(2);
  public method SetOptStr(h: IntPtr, opt: int, value: CString): int
      := symbol "curl_easy_setopt" variadic(2);
  public method SetOptPtr(h: IntPtr, opt: int, value: IntPtr): int
      := symbol "curl_easy_setopt" variadic(2);
  public method SetOptWriteFn(h: IntPtr, opt: int,
      cb: (Ptr<byte>, UIntPtr, UIntPtr, IntPtr) -> UIntPtr): int
      := symbol "curl_easy_setopt" variadic(2);        // §3.5's Sink.OnData plugs in here
end;

// open(2) with O_CREAT — note open is ITSELF variadic (int open(const char*, int, ...)),
// so BOTH arities go through the clause; a bare 2-ary `method open(...)` declaration
// would be exactly the %al trap this section opened with:
extern "libc"
  public method Open2(path: CString, flags: int): int
      := symbol "open" variadic(2);          // N = declared arity: a variadic call with
                                             //   ZERO variadic args — the SOUND spelling
                                             //   of the fixed-arity workaround
  public method OpenCreate(path: CString, flags: int, mode: uint): int
      := symbol "open" variadic(2);
end;
```

`variadic(N)` with `N` equal to the declared arity is legal and load-bearing: it means "call this variadic symbol with no variadic arguments," which is the only sound way to bind a variadic symbol at its minimum arity. This is also the general recipe for `fcntl`/`ioctl` (aliases per request shape) and — should anyone insist — `printf` (though Bezel string interpolation is the answer to that particular urge).

**True call-site varargs** (`printf(fmt, args...)`, Rust's `...` extern form with per-call-site trailing types) are **declined for v1**: they need a new call-arity rule and per-call-site promotion checking, and the measured corpus (curl_easy_setopt, open, fcntl, ioctl — all fixed small arities behind one symbol) is fully served by aliases. Recorded as the v2 candidate if real bindings show alias proliferation (§11).

## 7. Typed opaque handles

Two distinct problems hide under "handles": *type confusion* (every foreign handle is `IntPtr`, so `sqlite3*` and `sqlite3_stmt*` are interchangeable — directly against [rationale §16.2](Bezel_Design_Rationale.md#sec-distinct-types-for-cstring-wstring-rawbytes)'s own argument) and *lifetime* (who calls the foreign destructor, when). This proposal solves the first with a small admission and answers the second by **recording why hand-written wrapper classes remain the answer**.

### 7.1 Type distinction: single-integer/pointer-field records at the boundary

One admission, riding §4's machinery: **a C-compatible record with exactly one field, of *integer or pointer* scalar type** (the integer types, `IntPtr`, `UIntPtr`, `Ptr<T>` — *not* `float`/`double`, *not* `bool`) **is FFI-compatible in extern signatures directly** (parameter, return, `out`/`ref`, callback positions), marshalling exactly as its field. The field restriction is ABI-driven, not aesthetic. For an integer-class single-eightbyte aggregate, "as the scalar itself" holds on both target families: SysV x86-64 classes it INTEGER (GP register, same as the bare scalar), and Win64 passes 8-byte aggregates *as if they were integers* (RCX/RDX/R8/R9, returned in RAX) — which for an integer/pointer field **is** the bare scalar's convention. For `struct { double }` the two diverge: SysV classes it SSE (XMM, same as bare `double`), but Win64 puts the aggregate in the *integer* slot while a bare `double` rides XMM — so "marshals exactly as its field" would mandate a wrong-register miscompile on a target the rule must vouch for, precisely the `p7_time` defect class this proposal exists to close. Float/double-field records have no exemplar in the corpus (every typed handle in this section wraps a pointer) and join Stage D with the general by-value machinery; `bool` is excluded to avoid pinning an aggregate-normalization rule nothing needs. Other targets must implement the equivalent integer-slot check before enabling the admission.

```bezel
public record Sqlite3Db(Raw: IntPtr);
public record Sqlite3Stmt(Raw: IntPtr);

extern "sqlite3"
  public method sqlite3_open(filename: CString, out db: Sqlite3Db): int;
  public method sqlite3_prepare_v2(db: Sqlite3Db, sql: CString, nByte: int,
      out stmt: Sqlite3Stmt, out tail: IntPtr): int;
  public method sqlite3_step(stmt: Sqlite3Stmt): int;
  public method sqlite3_finalize(stmt: Sqlite3Stmt): int;
  public method sqlite3_close(db: Sqlite3Db): int;
end;
```

Passing a statement where a database belongs is now a compile error — §16.2's promise, delivered at the declaration layer, at zero runtime cost and zero new declaration forms (these are ordinary positional records; `db.Raw = IntPtr.Zero` is the null test).

### 7.2 Lifetime: hand-written wrapper classes remain the answer — recorded, with the probe

The considered alternative was a declaration-bound destructor — some `extern owned handle Sqlite3Db closes sqlite3_close;` form binding a foreign release function at declaration, giving dlopen/dlclose RAII for free. **Declined**, for three reasons:

1. **The pattern it automates already works, today, in ten lines.** Probe `p9_wrapper.bz` (compiled and run, exit 0, against current `build/bezelc`): an ordinary class with an `IntPtr` field whose destructor calls the extern release function — `using var lib := Library.Open("libm.so.6");` disposes through `dlclose` at scope exit. All of [§28](Bezel_Language_Spec.md#sec-resource-management)'s machinery (owned locals, cascade, leak prevention) applies unbought.
2. **Real bindings grow a wrapper class anyway.** A `Database` exposes `Query`/`Execute`/`Prepare`, holds prepared-statement children, translates error codes — the class exists regardless, and the destructor is three of its lines. A language mechanism would optimize away the one part that was never the cost.
3. **Foreign destructors have *policies* a bound function name cannot express.** `sqlite3_close` can return `SQLITE_BUSY` (unfinalized statements); `fclose` can fail and lose data; some libraries want a flush-then-free pair. A destructor *body* expresses the chosen policy; a `closes fn` clause silently discards every return code, and a second class-like declaration kind (declared inside extern blocks, no body, special disposal) is real grammar, sema, and teaching surface spent making that discard convenient.

```bezel
// The recorded pattern (probe p9_wrapper.bz, running today), composing §7.1's record:
public class Database(handle: Sqlite3Db)
  private _handle: Sqlite3Db := handle;

  public readonly property Raw: Sqlite3Db => _handle;

  destructor
    var rc := sqlite3_close(_handle);      // policy lives HERE: this binding chooses to
                                           //   ignore SQLITE_BUSY (leak-on-misuse beats
                                           //   crash); another may Verify or log
  end;
end Database;
```

One implementation footnote from the probing: the *spec-prescribed* null-handle guard (`if h = IntPtr.Zero then`) is currently uncompilable — `IntPtr` does not resolve as an expression head, so neither `IntPtr.Zero` nor the `IntPtr(0L)` conversion exists in practice (**filed: [#1512](https://github.com/s8lap/bezel-lang/issues/1512)**, with §32.6/§32.7/stdlib §10.0 anchors). A compiler bug, not a design input — but it blocks every real binding's error path today and is cheap pre-work (§10).

## 8. Export-to-native and runtime dynamic loading: re-deferred, with reasons

Both remain on [§32.11](Bezel_Language_Spec.md#sec-reserved-for-future-revisions)'s reserved list, now with named blockers instead of bare names:

**Exporting Bezel methods to native callers** — re-deferred. Blockers: (a) a symbol-export and C-ABI entry-generation story (mangling, export tables, per-platform visibility) that belongs with the module/build layer — [#1365](https://github.com/s8lap/bezel-lang/issues/1365)'s module-system spec gap and proposal [0034](0034-module-identity.md)'s artifact-interface design (whose evidence bugs #1487–#1489 are exactly symbol-identity and mangling defects) — not with §32; (b) the runtime-initialization question — a foreign process calling into a Bezel `.so` arrives on an unregistered thread with no domain and possibly no initialized runtime; the §32.10 amendment (§0) pins the *existing* foreign-thread obligations, but "runtime not yet started" is a genuinely open design; (c) no consumer: none of 0007/0011/0014, and no exemplar in the review, needs reverse export — callbacks (§32.8) cover the callback-shaped cases. Re-defer until an embedding use case exists.

**Dynamic library loading at runtime** — re-deferred, with the boundary drawn precisely. Declaring `dlopen`/`dlclose`/`dlsym` is *already expressible* (§32.7's own example; probe `p9_wrapper` exercises it), and this proposal's §7.2 pattern gives the handle RAII. What is **not** expressible is *calling* a `dlsym` result: an `IntPtr`-to-invocable conversion is the call-through-arbitrary-pointer capability, and it is the single most dangerous primitive in this design space (every other §3 operation corrupts data; this one executes it). The shape, recorded not designed: a `FnPtr<F>` intrinsic record (`F` an FFI function type) with `FromIntPtr` and `Invoke`, trusted like everything here. §4.4's `CodeAddress` was made one-way precisely to keep this deferred independently. Defer to its own small proposal once a real plugin/loader use case sets the evidence bar.

## 9. What this unblocks: 0007, 0011, 0014

The review's sharpest observation was that the project's own proposals route around §32. Per proposal — where each routes around it today, what becomes declarable, and (honestly) what stays runtime-internal regardless:

| Proposal | Routes around §32 today | Declarable under FFI v2 | Stays runtime-internal (and why) |
|---|---|---|---|
| **0007 System.Net** | TLS "wrapped runtime-internally" behind "~8 `bz_tls_*`" C++ entry points (0007 §6.2); sockets/DNS as runtime intrinsics (0007 §5.1) | `getaddrinfo`/`sockaddr`/`addrinfo` walking (§4 records + §3 `Ptr` chain-walk + §5 out-params); OpenSSL error-string reads (`ERR_error_string`: §3); BIO byte shuttling (`Ptr<byte>` + `RawBytes.FromForeign`) | The event loop and completion routing: 0007 §1.2's ruling — all real I/O must complete `OwningTaskCompletionSource` tasks onto domains — is a *scheduler-integration* reason, not an expressiveness one; FFI v2 does not dissolve it and does not claim to |
| **0011 Process** | spawn/reap as runtime intrinsics; destructor's kill+reap calls `waitpid` internally (0011 §4); argv marshalling unstated-native | `waitpid(pid, out status, opts)` (§5); `execve`/`posix_spawn` `char*[]` argv (`CString.Pointer` + `OwningBuffer<IntPtr>.DangerousPointer()`, §3.4); `pipe(2)` (the inline-array write-back amendment, §0); `kill`, `fcntl` aliases (§6) | Pipe-fd async completion routing (same scheduler reason as 0007); but the *process* substrate — spawn, reap, kill — becomes an ordinary binding, meaning a future revision of 0011's runtime work can be Bezel source rather than C++ |
| **0014 Signal hooks** | "a runtime drain thread" + native handler installation (0014 §2 D4); `sigaction` inexpressible | `SigAction` record + `sigaction` call (§4.4); handler address via `Interop.CodeAddress` (§4.4); the self-pipe's `write`/`read` externs and `Ptr<byte>` drain reads (§3) | The async-signal-safety obligation: a Bezel static callback running as a raw handler must not touch allocation or runtime services — a *runtime guarantee* this proposal flags (ties to the §32.10 amendment's runtime-obligations bullet) but cannot legislate from the FFI side |

None of the three is re-planned here; their runtime-internal choices stand on their own scheduler-integration grounds. The claim is forward-looking and precise: **the next 0007-class proposal should not need C++ for shapes C programs write daily** — and under §§3–7, it doesn't.

## 10. Staging and sizing

**Terminology, pinned:** *v1* means Stages A+B+C — everything this proposal ships. Stage D is design-now-ship-later and is **not** v1; §12's "not in v1" claims are against this meaning.

| Stage | Contents | Unblocks | New spec surface | Size |
|---|---|---|---|---|
| **A** (v1 core) | `Ptr<T>` over scalars (§3.2); `RawBytes.FromForeign` (§3.3); `CString`/`WString.Pointer`, `OwningBuffer.DangerousPointer` (§3.4); boundary `out`/`ref` on scalars (§5); `Interop.LastErrno` (§3.5) | sqlite3 (open/step/blob/exec), curl callbacks, errno, argv building+walking, BLAS | one new §32 subsection + the §22.3-interaction rules + Appendix C rows | **medium** — the `Ptr` intrinsic family and the out/ref marshalling (re-doing `p7_time`'s path correctly) are the work |
| **B** | C-compatible records: the §3.6 row, the layout promise, by-pointer admission (`ref`/`out` + `Ptr<R>`) (§4); single-integer/pointer-field handle records (§7.1); `Interop.CodeAddress` (§4.4); **the per-target C-struct layout engine** (offsets/alignment/padding for SysV x86-64 / Win64 / AArch64 — *new* compiler capability, §4.2, shared with Stage D) | timespec/timeval, sigaction, sockaddr/addrinfo, typed sqlite3 handles | the §32.13 section + §3.6 table row **+ the §3.6 reservation-clause amendment** + the layout-promise prose (q4) | **medium–high** — the layout engine is the work; the §3.6-gate machinery is reused, layout computation is not |
| **C** | `variadic(N)` on the symbol clause (§6) | curl_easy_setopt, open(O_CREAT), fcntl/ioctl | Appendix A.3 clause + the promoted-type rule | **small–medium** (grammar+sema small; per-target variadic call emission is the care point) |
| **D** (design now, ship later) | by-value struct params/returns, including float/double-field single-scalar records (§7.1's exclusion); struct-receiving callbacks (§4.2); `FnPtr<F>` (§8) | `div_t`-style returns; plugin loaders | per-target ABI classification in the frontend (atop Stage B's layout engine) | **high** — its own review cycle, gated on q10 |

A → B → C are sequential lanes (B leans on A's pointee set; C leans on the linking amendment). Pre-work, cheap and independent: **#1512** (`IntPtr` expression-head resolution — blocks every binding's null test) and the review's `p7_time` miscompile (closed by the forbid-amendment; §5 re-opens the path deliberately).

## 11. Declined, with reasons

- **A Marshal-style untyped read/write static class** (the road not taken in §3.1). Declined: it is `void*` with better manners — rationale §16.2's recorded argument cuts against it directly; byte-offset arithmetic reintroduces the hand-computed-`sizeof` bug class; and an audit surface split across 14 static methods is weaker than one typed family behind one import. Cost of the decline, stated: `Ptr<T>` needs the generic-intrinsic machinery and the per-instantiation gate — more compiler surface than a static class.
- **Bounds- and lifetime-checked foreign memory** (Java Panama's `MemorySegment` with length + temporal checking). Declined for v1: the C side supplies no reliable extents to check against, so the checking is only as good as the same trusted declarations — a *partially*-verified boundary would blur §32's honest "trusted but unverified" line while charging per-access costs. Where a length genuinely exists, `RawBytes.FromForeign(p, length)` *is* the length-carrying form. Revisit only with evidence that real bindings mis-size buffers in ways a declared bound would have caught.
- **Operator pointer arithmetic** (`p + 1`, `p < q`). Declined: named methods keep every adjustment searchable and element-scaled; ordering comparisons over unrelated allocations are UB in C and nothing in the corpus needs them.
- **Nested `Ptr<Ptr<T>>`.** Declined v1: `Ptr<IntPtr>` + explicit `FromIntPtr` re-typing expresses every `T**` shape in the corpus with one extra visible step; keeping the pointee gate non-recursive keeps the intrinsic simple. Additive later if bindings drown in re-typing. Acknowledged: the decline constrains the *intrinsic's gate*, not the shape — a one-field C-compatible record (`public record P(Inner: Ptr<int>)`) is an admitted pointee (§4.2), so `Ptr<P>` reconstructs `Ptr<Ptr<int>>` with one wrapper. That reconstruction is sanctioned, not a loophole: it costs a named type per indirection level, which is exactly the visible-step explicitness this decline buys, and it stays inside the trust posture (nothing here was ever a safety gate).
- **Unions and bitfields.** Declined: a union has no structural spelling that survives §3.6's "computed, never declared" (which member is active is semantic, not structural), and bitfield layout is famously ABI-quirky. Workarounds, recorded: declare the union slot as its widest member (or `[N]byte`) and reinterpret via `Ptr<byte>`/the [§4.14](Bezel_Standard_Library.md#sec-owned-buffers-and-spans) span accessors; declare bitfield-bearing words as their containing integer and mask.
- **A custom-deallocator parameter on `FromForeign`** (`FromForeign(p, len, freeFn)`). Declined: it duplicates what a ten-line wrapper class states more completely (§7.2 — including error policy), for one type only.
- **A declaration-bound foreign destructor** (`closes fn` handle declarations). Declined with the three reasons of §7.2; probe `p9_wrapper` records that the pattern it would automate runs today.
- **True call-site varargs** (`...`). Declined v1 per §6.3: new call-arity machinery for a corpus that per-arity aliases already cover. The v2 candidate if alias proliferation materializes in real bindings.
- **Automatic enum marshalling.** Stays declined per the amended §32.5 (underlying-integer + explicit cast); direct admission is recorded there as a candidate future convenience. Nothing here changes it.
- **Auto-generated bindings.** Not re-opened; rationale §16.1 stands, and every construct here is hand-writable and mechanically emittable.

## 12. What this does NOT give you

- **No safety at the boundary.** Every §3–§7 operation is trusted; a wrong address, length, layout, or arity is undefined behavior exactly as a wrong extern signature is today. The FFI's safety story remains: keep the boundary layer thin, wrap it in owned types, and let §28 govern everything above it.
- **No compiler sight of escaped addresses.** A `DangerousPointer`/`.Pointer`/`ToIntPtr` result retained by native code past the call outlives every check this language has; validity ends at a disposal the native side is never told about (§3.4's disclosure, q12). The wrapper-class idiom (§7.2) is the mitigation, not a mechanism.
- **No by-value structs beyond §7.1's single-integer/pointer-field handle carve-out, and no struct-returning C calls, in v1** (§4.2 staging; Stage D — which also picks up the float/double-field single-scalar records §7.1 excludes for Win64-ABI reasons).
- **No calling function pointers received from native code** (§8; `CodeAddress` is one-way).
- **No C++ interop.** `extern "C"`-shaped symbols only, as ever — name mangling, exceptions, and object layout across a C++ boundary are a different (and mostly declined-by-industry) problem.
- **No relief from platform-specific struct definitions.** A `SigAction` for glibc is not a `SigAction` for macOS; conditional platform declarations are the binding author's job (and a `when`-style conditional-compilation story is [#1365](https://github.com/s8lap/bezel-lang/issues/1365)-adjacent build work, not FFI work).
- **No change to callback admission.** Static-method-or-non-capturing-lambda (v0.163) stands everywhere a function crosses, including §4.4's `CodeAddress` and §6's callback-typed variadic slots.

## 13. Open questions for the owner

1. **Ratify `Ptr<T>` over the Marshal-static shape** (§3.1) — the load-bearing vocabulary decision; everything in §§4–8 is spelled in it.
2. **Module home**: new, *not* auto-imported `System.Interop` for `Ptr<T>`/`Interop` (import-line-as-audit-marker, §3.2), with new members on existing types (`RawBytes.FromForeign`, `.Pointer` accessors) riding those types' existing homes. Also flagged: stdlib §10's existing types have no stated module today — worth one clarifying line in the §10 intro while we are here.
3. **`FromForeign`'s `freeOnDispose` contract** (§3.3): fixed `free(3)` semantics, wrong-allocator-is-UB stated as a trust bullet; custom deallocators stay §7.2's job. Confirm.
4. **The layout promise, together with the §3.6 clause it requires amending** (§4.1) — the language's first normative representation guarantee, scoped to C-compatible records, plus the scoped exception to §3.6's closing reservation clause (the promise attaches a representation consequence to a derived property of *user* records; neither lands without the other). This is the most consequential piece of spec prose in the proposal. The alternative, stated so the ratification is a real choice rather than a rubber stamp: **no layout promise** — §3.6 stays untouched, C structs remain reachable only through `Ptr<byte>` arithmetic plus manual per-platform offsets and `FromIntPtr` re-typing (§3.2's "ugly by design" path), and §4, §7.1, and the timespec/sigaction/sockaddr/addrinfo rows of §1 drop out. Recommended: the promise, with the clause amendment.
5. **Boundary `out`'s definite-assignment trust rule** (§5): granted after the call, honesty delegated to the declaration. The alternative (no `out` at the FFI, `ref`-with-dummy-init only) is safer-looking but just moves the same trust one line up. Confirm `out` as specified.
6. **The `variadic(N)` clause** (§6) riding the linking amendment's `symbol` clause, plus the promoted-type compile error (§6.2). Confirm the decline of true call-site varargs.
7. **Single-integer/pointer-field record admission** (§7.1) as the typed-handle mechanism — the field restriction (no `float`/`double`/`bool`) is what keeps "marshals as its field" true on Win64, where `struct { double }` takes the integer slot while bare `double` rides XMM — and the §7.2 decline of declaration-bound destructors. Confirm both.
8. **Naming** (cosmetic but permanent — the *semantics* of the escaping alias is q12): `DangerousPointer` (the one mutable-Bezel-memory alias) vs `Pointer` uniformly; `Interop.LastErrno()` method vs read-only property; `CodeAddress`.
9. **`Interop.LastErrno` as intrinsic** (§3.5) vs capture-on-return semantics attached to extern declarations (heavier, .NET's `SetLastError` shape). Recommended: the intrinsic, with the documented read-it-first window.
10. **Stage D's bar** (§10): by-value structs and `FnPtr<F>` ship only behind a dedicated review cycle with per-target ABI-classification tests. Ratify the staging.
11. **`Ptr<T>` is sendable — ratify the trust rule** (§3.2). [§30.14](Bezel_Language_Spec.md#sec-sendable-types)'s value-type rule already computes `Ptr<T>` sendable; the proposal keeps that outcome and adds the §32.10-style bullet (foreign memory reached through a crossed pointer is outside domain isolation; unsynchronized cross-domain `Load`/`Store` is UB). The alternative — a non-sendable carve-out — is a special §30.14 rule laundered in one line through `ToIntPtr`/`FromIntPtr` (`IntPtr` is sendable), i.e. it protects nothing. Includes one confirming stdlib sentence that `RawBytes` (hence every `FromForeign` view) is not sendable, stating what §30.14's class rule already implies (§3.3). Recommended: sendable, with the trust bullet.
12. **Escaping mutable-alias pointers — ratify disclosure as the posture** (§3.4). Addresses from `DangerousPointer`/`.Pointer` that native code retains past the synchronous call are a use-after-free hazard no compiler rule can track, and no enforceable restriction exists (`IntPtr` laundering). The proposal's position: an explicit trusted-lifetime sentence in the stdlib text plus the §7.2 wrapper idiom (one class owns buffer *and* registration, so teardown order is structural). The alternative — prose forbidding native retention — would be a rule the compiler cannot check and native code cannot see. Recommended: disclosure plus pattern.
