## 0. Summary

`ws.Add(new Widget("a"))` on a borrowing `Array<Widget>` compiles. §15.4 mandates a warning at the store, because the argument is an unbound owned temporary that the language disposes at the end of the statement while the collection keeps a reference to it: the slot dangles from the statement's end, with certainty, on every execution. A checked build faults the first read of the slot; an unchecked build reads freed memory — MEASURED: `s.Add(new Widget("a")); s.Contains(other)` prints `True` for an object the set never held, `bs.Add(new Box(7)); bs[0].V` prints `7` out of a freed block, and one row of the compiler's own suite passes today only because a disposed object's field still holds its bytes.

The same dangle is already a compile error in the two sibling positions: a fresh non-trivial element inside a borrowing-family collection **literal** (§15.4, "a dangling borrow from birth") and a fresh value stored into a non-`owned` **field** (§28.6's fresh-store error). And §28.11's store rule already **rejects** `coll.Add(local)` when `local` is a scope-bound binding the collection outlives — while admitting the same store of a temporary, whose scope is the narrowest a value can have, with a warning. The warning's severity was decided at v0.238 (rationale §5.28, the ruled Q1) and confirmed at v0.243 (proposal 0081 §4 item 2) on one reason: rejection "cannot be scoped by signature — `coll.Add(new X())` and `sink.Consume(new X())` are indistinguishable plain-parameter calls". §6 brings the evidence against that reason.

**The rule.** A fresh unbound owned temporary of class type — a `new` expression, a collection literal, an `owned`-returning call result, a `move` result, a `Task`-family call result — in a single-element store position of a borrowing-family collection (`Add`/`Insert`/indexer-set and the other stores §28.11's value-copy shape (ii) names, key and value positions alike), or in the key position of `OwningDictionary<K, V>`, is a **compile error at the store site**: the lint's exact predicate, at error severity. The diagnostic keeps the lint's content (the boundary event, split by family; the two remedies). Nothing else moves: a fresh temporary passed to a plain parameter of a user-declared member — `sink.Consume(new X())`, a user class's own `Add` — stays admitted under the v0.314 record, the literal-site rule is unchanged, and the terminal-accessor and mutation-during-iteration warnings are untouched.

**Measured migration** (§5, corrected by the critic): 62 gtest rows in 21 files and one lit row flip from accept (with or without the warning) to reject, every one a test of the shape itself or a fixture that stores a fresh element for convenience — 19 of them fixtures that seed a borrowing `Array<Task>` with `Task.FromResult(…)`, a channel `Receive()` or an `async` call before a `WhenAll`/`WhenAny`; four banked rule-corpus rows change expectation (three `expect: warn`, one `expect: run` fixture); two doc-corpus fragments change text, not verdict; no guide or stdlib example is written in the rejected shape, and the one spec sentence that described it as legal (§28.14's fan-out, written before calls-mint) is restated. The remedy at every site is the one the warning already names: bind first, or use the owning family — one line.

Four things are decided: the temporary dies at the statement's end (K8.1); a borrow of it may not be **stored** (K8.4 names the store among the escapes rejected); the literal and the non-`owned` field reject exactly that store; and a scope-bound local's borrow is rejected at a store into an outliving collection (§28.11 clause 2). One thing is decided the other way: the store of the temporary itself into a standard collection's slot, which clause 4 carves out of K8.4's rejection and sends to a warning, on the ground quoted from §5.28.

## 2. Is the fault certain?

**At the store, yes.** Under K8.1 the temporary is disposed (a trivial-dispose instance: freed, with the §28.2 flag set) at the end of the full expression that produced it, after every use within that expression. The store is that expression's last use. The collection existed before the expression (it is the receiver — a binding, a field, a parameter, a call result) and is not touched by the disposal; after the statement its slot refers to a disposed instance. There is no execution on which this does not happen: no path, no input, no data dependency. §15.4 says so itself ("the retention is statically certain to outlive the value") and 0081 §1.3 proved the only conceivable exception inexpressible ("a fresh task stored into a purely-local borrowing collection that the program finishes reading before statement end is not expressible").

**At the use, yes, and the use is the only reason to store.** Every operation that reaches the slot's value after the statement reads a disposed instance: the indexer-get and default iteration (a member access through the borrow, §28.2's fault), `Contains`/`Remove(item)`/`IndexOf` (an equality scan over the dead element — under the default identity equality a pointer comparison that answers against whatever object now occupies the block, MEASURED below), the stdlib §5 terminals, `ToArray` (copies the dead borrow), the `Keys` view. The operations that do not touch the value — `Count`, `Clear()`, `RemoveAt(i)`, `Dispose()` — are exactly the ones for which the store need not have happened. So the program's sound continuations are the ones in which the stored value is dead: the store is, at best, a construction and a disposal with no effect. That is the class the two sibling rules already refuse without a flow condition: §28.6's fresh-store error does not ask whether the field is read later, and §15.4's literal-site rejection does not ask whether the literal's element is ever reached. §4.4 declines adding a read condition here.

## 3. What exactly is the rule

**Position.** A **single-element store position of a borrowing-family collection**: the members §28.11's value-copy shape (ii) names as single-element stores — `Add`, `Insert`, `Push`, `Enqueue`, `Counter<K>.Increment`'s key — with their siblings on the same family (`TryAdd`, `LinkedList<T>`'s `AddFirst`/`AddLast`/`AddBefore`/`AddAfter`, `GetOrAdd`'s key) and the indexer-set, **key and value positions alike**; on every collection of the borrowing family — the standard borrowing collections (`Array<T>`, `LinkedList<T>`, `Set<T>`, `SortedSet<T>`, `Stack<T>`, `Queue<T>`, `Dictionary<K, V>`, `SortedDictionary<K, V>`, `Counter<K>`) and the four borrowing interfaces stdlib §4.1 says "form the borrowing collection family" (`ICollection<T>.Add`, `IList<T>.Insert`, `IList<T>`'s indexer-set); and the **key** position of `OwningDictionary<K, V>` (`Add`/`TryAdd`/`GetOrAdd`'s key, the indexer-set's key), which owns its values and not its keys (stdlib §4.9). This is the lint's position set as §15.4 states it ("a store-position argument in a **borrowing position** — `Add`/`Insert` and the indexer-set on a borrowing-family collection, key and value positions alike, and the **key** position of `OwningDictionary<K, V>`"); the proposal spells the member list out by reference to §28.11 (ii) so that the two passages name one set. The many-element forms (`AddRange`, `UnionWith`, `CopyFrom`) are not single-element stores and are outside the rule (§9 records the one open question about them).

**Value.** A **fresh unbound owned temporary of class type** (§28.3.11): a `new` expression, a collection literal (built-in or any §15.4.1 target — the factory result is `owned TSelf`), an `owned`-returning call result, a `move` result, or a `Task`-family call result (calls mint, §28.3 *Producers*). Trivial-dispose classes included (the lint's full type set since v0.243; the ruled Q1's `groups.Add("odds", [1, 3, 5])` is the archetype). Value types, `string`, boxes and the other runtime-managed kinds carry no classification and are outside the rule (K1.6), as today.

**Verdict.** A compile error at the store site, whatever the receiver's own lifetime and whether or not the slot is read later (§4.4). The diagnostic names the K8 boundary at which the value dies, the boundary event by family (the compiler's free; the task's disposal — abandonment, §30.5; the value's disposal) and the two remedies — bind the value to a named holder first (`using var t := …; conns.Add(t);`, `var odds: Array<int> := [1, 3, 5]; groups.Add("odds", odds);`), whose lifetime §28.11's store rule then checks, or use the owning family, whose store positions take ownership (`OwningArray<T>`, `OwningDictionary<string, Array<int>>`; for an owning map's *key* only the first remedy applies; for dynamic task fan-in `OwningArray<OwningTask<T>>` with the owning `Task.WhenAll`, stdlib §6.7). The text is the lint's, re-headed.

**Not in the rule.** A fresh temporary (or a scope-bound local) passed to a **plain parameter of a user-declared member** — `sink.Consume(new X())`; a user class's own `Add`, a §15.4.1 user sequence-literal class's `Add` included — keeps §28.3.11's admission under the residual trust K4.3 records and the v0.314 record (rationale §5.24; `DECLINED.md` rows 68 and 69 stand). The literal-site rule is unchanged. A **borrow** stored into a borrowing collection is §28.11's store rule, unchanged. The §28.11 **rejection** half of #3873 (a scope-bound *named* key into an outliving `OwningDictionary`) is a compiler gap, not touched here.

**Derivation.** K8.4 + K2.3: the store is an escape of a borrow of a temporary past its boundary, which K8.4 already lists among the rejected escapes; clause 4 of §28.11 is deleted as the carve-out that sent that one escape to a warning. K8.4's own sentence "A plain parameter announces none" is kept and gains its exception in one appended sentence: the standard borrowing-family store positions are declarations whose retention §28.11's *Value-copy members* reads off the signature, so they fall under K8.4's "every retention a declaration announces" — without that sentence the kernel would still state the residual admission this rule removes. Body-locality (proposal 0105): local — the verdict is read at the call from the receiver's static type and the argument's producer classification, both of which the checker computes today (`producerState`, the `borrowingFamily` head test).

## 4. Options and evaluation

### 4.1 (a) The status quo — the warning, with the `IList<T>` gate widened (#7141)

Keeps the dead-slot program and the silent unchecked read. The warning has no suppression spelling, deliberately (rationale §5.28; `DECLINED.md` row *Per-site suppression spellings*): a mandated warning that no program may legitimately carry, whose remedy is one line, and whose only sound carriers are dead stores, is an error with a softer label — and in an unchecked build a label is all it is. Declined (§7).

### 4.2 (b) The error, at the lint's exact predicate — adopted

Soundness: closes the one shape in which the language stores a reference it knows to be dead, with no new analysis. Simplicity: §28.11's store-site check loses a clause rather than gaining one, and §15.4 loses a recorded asymmetry; the compiler changes one severity and one receiver gate. Consistency: the three positions a fresh value can escape into without an owner — literal element, non-`owned` field, borrowing slot — now take one verdict, and §28.11 no longer rejects a store from a scope-bound local while admitting one from a temporary. Migration: §5, one line per site.

### 4.3 What (b) rejects that is fine

Honestly listed, with the measured count:

1. **The dead store** — `ws.Add(new Widget("a")); … ws.Count` (`g01`): no fault on any path, but no effect either beyond a construction and a disposal. Rejected as §28.6 and the literal rule reject their dead stores; the remedy deletes the line. In-tree: the fixture rows of §5 that seed a collection and read only its `Count` (`async_owned_builtin_collection_param_6368`, `sorted_set_class_element_3428`, `sorted_set_no_compareto_3865`, `array_igrouping_add_segv_4308`'s control, `method_group_fresh_owned_arg_7025`'s control) — every one a test fixture, none a program that wants the element.
2. **A temporary receiver** — `new Array<Widget>().Add(new Widget("t"));` (`g20`): both temporaries die at the same boundary; nothing can read the slot. Rejected uniformly (the lint fires on it today, naming the receiver `it`); zero sites.
3. **A conformer of `IList<T>` or `ICollection<T>` whose `Add` reads the item and keeps nothing** — a user "name collector" implementing the interface as a sink: `names.Add(new Widget("a"))` through the interface type would be sound and is rejected. The interface's `Add` is the family's documented store (stdlib §4.1), a plain parameter cannot take ownership in any conformer, and the fresh value is unreachable after the statement either way; a conformer whose body does not retain is reached at its concrete type, where its own `Add` is an opaque member and stays admitted. Zero sites (the one `IList<Item>` store in the corpus is an `Array<Item>` behind the interface, `method_group_fresh_owned_arg_7025`).

Nothing else: a named holder, a parameter, a field read, an iteration variable, a value-typed or `string` element, an owning-family store, a user-declared callee, a many-element form — each is outside the predicate, as the lint's negative controls pin today (`fresh_store_warning_3364`'s six "does not warn" rows), and each stays accepted.

### 4.4 (c) and (d), declined

**(c) Concrete standard collections only** — the error on `Array<T>` and its siblings, the warning kept on an `IList<T>`/`ICollection<T>`-typed receiver. Splits one shape's verdict by the receiver's static type, the "inverted asymmetry" 0081 §4 item 3 declined for the type set; the interface is where the spec's own words already put the lint (#7141's reading, confirmed here), and the interface's store members are the family's contract. Declined.

**(d) Rejection conditioned on a later read of the slot** — admit the dead store, reject the store whose slot the body reads. Admits only dead code, at the price of a per-slot liveness analysis §28.11 says the language does not run ("not statically tracked per slot"), with aliases, loops and calls on the collection all to be decided; the two sibling rejections carry no such condition. Declined.

**(e) Rejecting the user-declared sink too** (`sink.Consume(new X())`) is not an option this proposal opens: it is `DECLINED.md` row 68 (v0.314, #5360), whose reason — a caller's verdict keyed on another body — is untouched by a rule that reads a standard member's declared signature (§6).

## 6. The case against the recorded decline

The record is rationale §5.28's ruled Q1 (v0.238, owner-ruled 2026-08-04, proposal 0077) and proposal 0081 §4 item 2 (v0.243, owner-ruled 2026-08-11), indexed as `DECLINED.md`'s *Abandonment-lint alternatives* row (`declined-at-proposal`, bar "—(none stated)"), so the governing bar is the process's own: reopened only with new evidence against the stated reasons (spec-change-process §2, §6). The stated reason is one, in two sentences: rejection "cannot be scoped by signature — `coll.Add(new X())` and `sink.Consume(new X())` are indistinguishable plain-parameter calls", and the literal-only asymmetry's ground, "an opaque callee's signature type-announces no retention", "is type-agnostic". Three pieces of evidence, each against the reason rather than a re-asking:

**The lint adopted instead is scoped — by compiler-known member, not by signature — and has run at that scope without a false positive.** The ruled Q1's own remedy keys the warning on the standard collections' store members; the compiler implements exactly that (`warnSec154FreshStore`, reached only through the `borrowingFamily` head test and the `OwningDictionary` key arm, `src/ownership/Ownership_Checks.cpp`), and its negative controls pin `sink.Consume(new X())` silent (`fresh_store_warning_3364.plain_callee_taking_a_fresh_temp_does_not_warn`). The error takes that predicate unchanged. "Cannot be scoped" described a rejection keyed on a parameter's type; it does not describe a rejection keyed on the member the lint is already keyed on.

**§28.11 has distinguished the two "indistinguishable" calls since v0.180.** Its store-site check rejects `coll.Add(local)` for a scope-bound `local` the collection outlives (MEASURED, `g08`, `g09`: "borrow of `w` passed to `.Add(...)` on `ws` would outlive its source"), while `sink.Consume(local)` is admitted under the residual. The language already reads the standard store member as a store and the user member as opaque; the decline's premise that the two calls cannot be told apart was contradicted by a rule that predates it. What the carve-out left was an inversion: the source with the *narrowest* scope of all — the temporary, whose scope is the statement — was the one source the store rule warned about instead of rejecting.

**The retention is type-announced for these members — the spec now says so.** §28.11's *Value-copy members* paragraph (landed with #5693's ruling, after v0.243) states that a standard-library member's "body contributes no requirement (§3.6 rule 2), so what it stores is read off its **declared signature**", and names shape (ii), "the single-element stores `Add`, `Insert`, `Push`, `Enqueue`", as stores "the element slot policy already reads as a store". The literal-only reason was that a signature announces no retention; for the standard store members the specification reads the retention off the signature. The reason no longer holds for exactly the set the rule covers — and keeps holding, as this proposal keeps it, for every user-declared callee.

**And the severity question has a measured answer the record did not have.** The ruled Q1 weighed a warning against rejection with the checked-mode backstop as the safety net. §2's table is the unchecked conformance mode's answer: a `Contains` that says `True` for an object never stored, a read that returns a freed block's bytes, a suite row that passes on them. Proposal 0205 (this train) argued the same point for the dominated use after an explicit disposal, and this proposal keeps its rule consistent with 0205's: where the fault is certain and the analysis exists, the language says so at compile time; where it is conditional, the backstop stays the answer.

**What stays declined.** Rejecting a fresh temporary at a user-declared plain parameter on the strength of the callee's body (`DECLINED.md` row 68, v0.314): untouched — this rule reads no body. Lifetime extension (row 69): untouched. The task-only type set (row 467): untouched, the error keeps the full set. The §15.4.1 user sequence-literal classes: reached by the literal rule, not by this one.

**Process class.** A design change (§2's third rule: it contradicts a recorded decision and narrows a stated admission), so a proposal first, then a ruling-class landing with the adversarial critique, the corpus sweep (§5), the code-generation reference update, and one `spec-tracking` issue (§8).
