## 0. Summary

The spec says, in §8.7, that `Dispose()` is class-only and that the compiler generates `IDisposable` on every non-static class; in §4.6, that "`Dispose()` on a string is a no-op"; in §28.9, that the runtime-managed types' "`Dispose()` is a no-op (or, for types that are not classes and therefore have no `Dispose()` at all, …)"; in the §28 summary table, that `string`, boxed values **and function values** have a no-op `Dispose()`; and in §28.1 clause 6, that `where T: IDisposable` "excludes the runtime-managed reference types". Whether `string` is a class is answered both ways (§3.5 and stdlib §9.6: yes; §3.1 and §14.2: no). And nothing says whether a value typed at an interface that does not extend `IDisposable` — `IList<T>`, `IEnumerable<T>`, a user interface — exposes the member: the compiler admits the call `il.Dispose()` under §28.6's owned-receiver rule and rejects the reference `il.Dispose` as "no member".

This proposal states one surface rule. **`Dispose()` is a member of a class type, of an interface type that is or extends `IDisposable` (the interfaces `where T: IDisposable` admits), and of an interface that declares `method Dispose();` itself (§28.2); `DisposeAsync()` is a member only of a type that declares or inherits it; neither is a member of anything else.** `Object` (already, §8.7), the runtime-managed types (`string`, `Type`, boxed values, function values) and every other interface type have no such member; a call in any spelling or a method reference naming it there is a compile error at the type level; an owned value held at such a type is disposed by the language's discharge points alone — scope end, `using var`, the discard — which dispatch to the runtime type and dispose nothing for a runtime-managed value. A generic body calls `Dispose()` on a `T` value only where its constraints put the member on `T`'s surface (`where T: IDisposable`, an interface bound extending it, a class bound) — never under `where T: class` alone, which admits `string`, function types and member-less interfaces — and no extension block declares either name. Reach: 23 gtest rows flip accept → reject (19 over a non-`IDisposable` interface receiver, 4 over a `where T: class` type parameter) and one lit accept-control row is re-cut; two rejection rows change their diagnostic; the stdlib's `OwningArray<T>` reference implementation (a `where T: class` body) changes one statement to the discard; no corpus, doc or guide program changes verdict.

## 1. The problem

> `string` is **runtime-managed**: its memory is reclaimed automatically. `Dispose()` on a string is a no-op. String fields cannot be marked `owned`.
>
> — §4.6, v0.344

> `Dispose()` is class-only. The compiler generates `IDisposable` on every non-static class. Static classes, records, enums, choices, primitives, and inline arrays do not implement `IDisposable`.
>
> — §8.7, v0.344

> The following types are exempt from manual disposal ([K1.6]'s runtime-managed exemption). Their `Dispose()` is a no-op (or, for types that are not classes and therefore have no `Dispose()` at all, the type's lifetime is managed by the runtime without user involvement).
>
> — §28.9, v0.344

> | `string` | No — runtime-managed | `Dispose()` is a no-op ([§28.9]) |
> | Boxed value types | No — runtime-managed | `Dispose()` is a no-op ([§28.9]) |
> | Function values | No — runtime-managed | `Dispose()` is a no-op ([§28.9]) |
>
> — §28, *Summary of disposal obligations by type kind*, v0.344

> Authors who intend the marker to be meaningful at every instantiation still constrain the domain (`where T: IDisposable` excludes the runtime-managed reference types at the declaration, [§14.2]).
>
> — §28.1 *Type requirement* clause 6, v0.344

> At `U := Object` the bound admits `Object` and every class type, the set a class bound names (`string`, interfaces and function types are not classes, [§8.1]);
>
> — §14.2 *Type-parameter bounds*, v0.344

> classes — which `string` is — cannot overload `=` and `<>` per [§25.2]
>
> — §3.5, v0.344

Three contradictions, one silence:

1. **Does a string's `Dispose()` exist?** §4.6, §28.9's first branch and the summary table say it exists and does nothing. §8.7 (class-only), §28.1 clause 6 (not `IDisposable`) and stdlib §9.6's declaration (no `IDisposable`, no `Dispose` member) say it does not. §28.9's two branches split on "is a class", which §3.5 answers yes and §14.2 answers no.
2. **Does a function value's `Dispose()` exist?** The summary table says it is a no-op; §28.9's second branch, §14.2 ("function types are not classes") and the #7260 ruling say there is none. The compiler gave a closure a *real* disposal that freed its cell under a later call (#7260, measured: a SIGSEGV unchecked, `DisposedAccessException` checked).
3. **Does `Type`'s?** §17.10 and stdlib §2.13: "`Dispose()` on one is a no-op". §28.9's own `Type` bullet: the trivial-dispose free "would set the disposed flag on a token every other holder still reads" — the one thing a disposal would do is the thing that must not happen.
4. **Does an interface type that does not extend `IDisposable` expose `Dispose()`?** No sentence says. The §28 table makes "interface-typed locations" disposable ("treated as class"); §17.13 disposes them by runtime dispatch; §14.2's conformance rule 3 says "an interface conforms exactly when it extends `IDisposable`". The compiler's two spellings disagree (#7068's table): the call compiles, the reference is "no member".

One more conflict the issues do not raise. Suppose the member existed on a runtime-managed type. §28.6 says explicit disposal "requires a receiver the disposer **owns**", and K1.6 says runtime-managed values "carry no classification and no obligation". A string is never owned, so `s.Dispose()` would be rejected by §28.6 even with the member. The only places a string meets disposal are the language's own discharge points — a `using var` over a string, the `for` desugaring's `using var __source` (§29.2: "a no-op"), the discard (§17.13: "purely cosmetic"). Those are facts about discharge points, not about a member.

## 2. Why this is a proposal

§4.6's sentence is a stated admission: "`Dispose()` on a string is a no-op" admits the call. Deciding that the call is a compile error narrows it, and the same decision retires the stated no-op member of `Type` (§17.10, stdlib §2.13) and of function values and boxes (the table). On the interface side, 19 shipped gtest rows and a lit accept-control pin the call; the text is silent rather than admitting, but process §2's stricter-gate rule applies where the class is in doubt, and the two halves are one rule, so one proposal carries both. The alternative readings are recorded as declines so the question stays settled.

## 3. Options

- **1 — mark the string disposed.** `Dispose()` on a `string` sets a disposed state and later operations fault, the owner's test applied to the string itself.
- **2 — the v0.344 words: a no-op member.** `s.Dispose()`, `t.Dispose()` on a `Type`, `c.Dispose()` on a function value compile and do nothing. The compiler's string rejection goes; its closure disposal becomes a no-op.
- **3 — no member (decided).** `Dispose()` is a member of class types, of the interfaces that are or extend `IDisposable` and of an interface declaring it itself; `DisposeAsync()` of the types that declare or inherit it; neither of anything else. `s.Dispose()`, `typeof(T).Dispose()`, `c.Dispose()` on a function value, `o.Dispose()` on an `Object` and `il.Dispose()` on an `IList<int>` are type-level compile errors naming the discharge points.
- **4 — the interface half alone, the other way: an implicit `Dispose()` on every interface type** (#7068 option 2), the member admitted on `IList<T>` and every other interface and §28.6's owned-receiver rule deciding the call. Pairs with option 3 for the runtime-managed types.

## 4. Evaluation

| | Soundness | Simplicity | Consistency | Migration reach |
|---|---|---|---|---|
| 1 | **unsound**: a string has no owner (K1.6), is shared by assignment, may be interned (§4.6), crosses domains as a shared reference because it is immutable (§30.14); the mark changes a value every other holder reads | a disposed state on a value kind that has none | — | — |
| 2 | sound at runtime, but a kill that performs nothing: §28.2's **mandatory** use-after-dispose warning would fire on the next read of a string never disposed, or be carved out for it; §28.6 rejects the call anyway (a runtime-managed receiver is never owned); a `Dispose()` that is not an `IDisposable` implementation (§28.1 cl. 6) is a member shape no other type has | a member with no semantics, plus the carve-outs it needs | the owner's test inverted ("calling Dispose should mark the object as disposed and stop any operations on it") | 0 newly rejected; the compiler's string rejection (1 arm) and closure disposal (3 rows, #7260) change |
| 3 | sound: only values that can be disposed name the member; everything else is disposed where the language already disposes it | one rule — a value exposes the members its type declares — and `Object`'s existing posture extended | `where T: IDisposable` (§14.2 rule 3: an interface conforms exactly when it extends it) and the member surface now agree; `Object` (#6990) and function values (#7260) already answer this way | 23 gtest rows and 1 lit row flip accept → reject (§6); 2 rejection needles change; one stdlib reference-implementation statement re-spelled |
| 4 | sound (every value behind an interface is a class or a box) | a member keyed on nothing the interface declares, on interfaces but not on `Object` | an interface value would expose a member its type does not conform to (`IList<T>` fails `where T: IDisposable`, §14.2 rule 3) | 1 row flips (#6997's ROW 4) |

Option 3 is the smallest rule and the only one that agrees with every neighbouring rule already in force. Option 4 flips fewer rows, but the rows it keeps pin an implementation behaviour the text never stated, and it would make the member surface disagree with the conformance rule the language already uses for exactly this question.

## 5. Decision

**Option 3.** Stated in §8.7 (the home of "`Dispose()` is class-only"), restated in §28.2 and §28.9, and applied in §4.6, §17.10, §15.1.1, §26.3, the §28 summary table, stdlib §2.13, §4.1, §4.5, §4.12 and §9.6.

- **Runtime-managed types.** `string`, `Type`, boxed values and function values are not classes and have no `Dispose()`. `s.Dispose()`, `s?.Dispose()`, `typeof(T).Dispose()`, `x.GetType().Dispose()`, `c.Dispose()` on a function value: compile errors at the type level, the diagnostic the one `Object` already gets ("no member `Dispose` on type `string`: `Dispose()` is class-only (§8.7) …; a string is runtime-managed and has nothing to dispose (§28.9)"). The discharge points keep admitting these values and dispose nothing: `using var s := "x";` (§28.10), `_ := s;` (§17.13), the `for` source binding (§29.2), `using var c := lambda() => 42;` (§28.9's function bullet, unchanged).
- **Interface types.** `Dispose()` is a member of an interface type exactly when the interface is or extends `IDisposable` — the set `where T: IDisposable` admits (§14.2 rule 3 and its worked example: `IOwningCollection<T>`, `IOwningList<T>`, `IOwningEnumerable<T>`, `IEnumerator<T>`, `IAsyncDisposable` and its extenders as that example lists them, a user `interface IRes: IDisposable`) — or declares `method Dispose();` itself, which §28.2 admits ("an interface may itself declare `method Dispose();`"; banked `s28_2_0010`): a value exposes the members its type declares or inherits, and a class implementing such an interface supplies the compiler-generated `Dispose()` (§14.2 rule 1). `DisposeAsync()` is a member of the types that declare or inherit it (`IAsyncDisposable`, `IAsyncEnumerator<T>`, the classes implementing it, §28.12); it is not a member of every class. On `IList<T>`, `ICollection<T>`, `IReadOnlyList<T>`, `IReadOnlyCollection<T>`, `IEnumerable<T>`, `IAsyncEnumerable<T>` and a user interface with neither the extension nor its own declaration, the name resolves to no member: the call in every spelling and the method reference are compile errors, the diagnostic naming the discharge points. An owned value held at such a type is disposed at scope end, by `using var`, or by `_ := il;`, each dispatching to the runtime type (§17.13, the table's interface row).
- **`Object`.** Unchanged (§8.7, #6990).
- **Generic code.** A body calls `Dispose()` on a `T`-typed value only under a constraint that puts the member on `T`'s surface — `where T: IDisposable`, an interface bound extending it, or a class bound (every class has it) — and under no other. `where T: class` admits `string`, function types and member-less interfaces (§14.2's `class` row), so a `where T: class` body has no `Dispose()` on `T`; §14.2's worked example already says `where T: IDisposable` "is what a body that calls `Dispose()` wants" and admits the same class substitutions. **This is newly rejected:** the v0.344 text never said what a `where T: class` body may call, and the compiler admits `t.Dispose()` under `where T: class` and under any interface bound (fix #1293, `src/sema/ExprTypecheck_Calls.cpp:9925–9969`). Remedies, each verdict-preserving: the discard `_ := t;` (a named owned binding, §17.13), `using var`, scope end, drop-on-overwrite for an owned field (`_v := b;` disposes the displaced value, §28.7), or `where T: IDisposable`. `owned T` is erased at a runtime-managed substitution (§28.1 clause 3); `using var` and the discard are admitted uniformly (§28.10, §17.13). The stdlib's own `OwningArray<T>` reference implementation (stdlib §4.5, `where T: class`) disposes each element in `Clear` by `item!.Dispose();`; it is re-spelled `_ := item;` — the discard of a named owned `T?` binding, which disposes the non-null value by dispatch, the same effect.
- **Extensions.** An extension block declaring a member named `Dispose` or `DisposeAsync` is a compile error at the declaration (§26.3's restriction list gains the bullet). With the member gone from `string` and from member-less interfaces, an extension `Dispose()` on them would otherwise resolve (§26.5 rule 1 blocks only by declared name) and look like a disposal it cannot perform — the extension's receiver is a borrow it may not dispose (§26.7). Reach: 0 (no extension declares either name in `tests/`, the corpora or `docs/`).
- **Is `string` a class?** No (§3.1, §14.2, and now §8.7). §3.5's "classes — which `string` is —" is reworded so the §25.2 argument no longer rests on it; stdlib §9.6 says the `class` spelling is the index's declaration form. (The question also reaches §14.2's `U := Object` sentence, which calls the set the class bound names "every class type" while the bound's own row lists `string`, interfaces and function types; that is an editorial for the lane owning §14.2 and is reported, not edited here.)

What a reader sees: `Dispose()` exists exactly where something can be disposed, which is the owner's principle applied directly.

## 9. Declined alternatives (one `declined-at-proposal` row each)

- **Option 2, a no-op `Dispose()` member on the runtime-managed types** (the v0.344 words; #7276 readings (A)/(C)). A call that claims a kill it does not perform: it would draw §28.2's mandatory use-after-dispose warning on a value never disposed, could not be an `IDisposable` implementation (§28.1 clause 6 — a member shape no other type has), and could not be written legally in any case, §28.6 requiring an owned receiver where a runtime-managed value is never owned (K1.6). Reopening bar: none stated.
- **Option 1, marking a string disposed.** Unsound: a string has no owner, is shared by assignment, may be interned, and crosses domains as a shared reference because it is immutable; the mark would change a value every other holder still reads. Reopening bar: none stated.
- **Option 4, an implicit `Dispose()` on every interface type** (#7068 option 2; the compiler's call-form behaviour). Implementable, but an implicit member on interfaces that `Object` lacks, keyed on nothing the interface declares, and disagreeing with §14.2's conformance rule 3, for a spelling the discard, `using var` and scope end already cover. Reopening bar: a measured early-release need that `_ := il;` cannot express.

## 11. Self-critique (adversarial pass)

- **Is "no member" the simplest sound option?** Yes. Option 2 needs a member with no semantics and two carve-outs (the §28.2 warning, §28.1 clause 6's bound); option 1 is unsound; option 4 keys a member on nothing. Option 3 deletes text and adds one sentence.
- **Over-rejection hunted.** `using var`, the discard and the `for` source binding over runtime-managed values: all stated admitted (§28.10, §17.13, §29.2; the §28.9 function bullet keeps "a `using var` local of function type is nonetheless permitted"). Generic bodies: `where T: IDisposable` excludes the runtime-managed types already (§28.1 cl. 6) and admits every class and `IDisposable`-extending interface, so a body under it keeps `t.Dispose()`; a body under `where T: class` alone, or under a member-less interface bound, loses it — 4 gtest rows and the stdlib §4.5 reference implementation, each with a verdict-preserving re-spelling (§5, §6). `await using` over an interface- or `Object`-typed binding: §28.12 selects the run-time object's `DisposeAsync`, a discharge point, unchanged. `IEnumerator<T>`'s explicit `e.Dispose()` in §29.1's manual protocol: `IEnumerator<T>: IDisposable`, admitted. `IAsyncEnumerator<T>.DisposeAsync()`: extends `IAsyncDisposable`, admitted. `OwningDictionary<K, V>: IDisposable` and the owning collections: classes, admitted.
- **Soundness escapes hunted.** A runtime-managed value reached as an `IDisposable` — impossible: no runtime-managed type conforms (§28.1 cl. 6, §14.2 rule 3), and a boxed record cannot implement `IDisposable` (§9.7, §14.2 worked example). An interface-typed owned value with no explicit spelling for early release: `_ := il;` and `using var` exist, both dispatching to the runtime type. A user interface meant to be disposed through: declares `IDisposable`, as `where T: IDisposable` already requires of it.
- **A user interface declaring `Dispose` itself.** §28.2 admits `interface ICloseable method Dispose(); end` (banked `s28_2_0010`); the rule keeps the member on it, so "a value exposes the members its type declares" holds without exception; a class implementing it supplies the generated `Dispose()`, and `c.Dispose()` over an owned `ICloseable` is an ordinary explicit disposal under §28.6.
- **`IAsyncDisposable`.** §14.2's worked example and stdlib §2.10 list `IAsyncDisposable` and `IAsyncEnumerator<T>` among the interfaces conforming to `IDisposable`, while the declarations (spec §28.12, stdlib §2.10) list no extension; the rule is worded on the set `where T: IDisposable` admits, so the member surface and the bound agree whichever way that seam is settled (filed separately).
- **Every other passage stating the rule.** §4.6, §17.10, §28.9's lead, the summary table (four rows), §28.2's restatement, §15.1.1's box clause, stdlib §2.13 and §9.6 are edited; §28.3's exclusion list already says runtime-managed locals "have no `Dispose` to call"; §28.1 clause 6, §14.2 rules 1 and 3 and its worked example, §29.2, §28.10 and §17.13 agree as written. The §28.9 function bullet's "disposal at scope end is a no-op" is about a discharge point and stands. Rationale §4.1 motivates runtime management without a member claim.
- **The `is string a class` seam.** §3.5 and stdlib §9.6 are reworded; §14.2's `U := Object` sentence is reported for its owning lane (§5). Stdlib declares `public class String` and `public sealed class Type` as its index form; §9.6 now says so.
