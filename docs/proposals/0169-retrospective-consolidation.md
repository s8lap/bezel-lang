## 0. Summary

Three passages of v0.316–v0.333's fixes say the same thing twice or three times, and in each the restatement was the part a later fix had to amend. This proposal states each once.

1. **The value-copy register becomes a signature-shape rule (R7).** v0.332 ([#5693](https://github.com/s8lap/bezel-lang/issues/5693)) made the standard library's copying members stores at the call; v0.333 ([#5717](https://github.com/s8lap/bezel-lang/issues/5717)) added a census — stdlib §4's *Value-copy members are stores* (447 words: a definition, a 27-member enumeration by type and a 12-member "not value-copy" list) and 27 `value-copy (§4)` listing markers — beside §9.7's ≈540-word passage and §28.11's ≈200-word sentence. A census is a second statement of a rule the signatures already state, and it had a gap: `Counter<K>.Increment(key)` stores its key and is neither listed nor excluded. ▲ §28.11 states **three shapes** over the declared signature — (i) an `owned` collection result copies in the element values it takes; (ii) a borrowing-family collection's or a span view's method with no return copies in what it takes from an `IEnumerable<T>`, a read-only span or a `T` parameter; (iii) a written span argument receives a copy — and names the **four** members a shape reads that copy nothing (`Set<T>.IntersectWith`/`ExceptWith` remove; `Span<T>`'s class-typed `MoveFrom`/`MoveTo` move). ## 1. The problem

### 1.1 Three statements of which members copy (R7)

At v0.333 a reader finds the value-copy rule in four places: §9.7's collection bullet ("**The standard library's value-copy members** are stores under this bullet … Such a member places `T` values taken from its receiver or from an argument into a fresh collection it returns — among them `Array<T>.ToArray`, `Sorted`, …"), §28.11 *Storing a borrow* ("The standard library's **value-copy members** (§9.7's collection bullet defines them, and stdlib §4 registers them and marks each at its declaration: among them `ToArray`, …)"), stdlib §4's register ("Each value-copy member carries the comment `value-copy (§4)` at its declaration: `Array<T>`'s `FromCollectionLiteral`, `constructor(size, fill)`, …") with its "**Not value-copy members:**" list, and the 27 markers. The first three list the members; the lists have already diverged once (#5717's critic found three members the §9.7 list missed), and the census misses one:

```bezel
record Pair(Item: Item);
class Tally
  private owned _seen: Counter<Pair> := new();     // a field-held tally; Pair is hashable by its component
  public method Note()
    using var it := new Item();
    var p := new Pair(it);
    _seen.Increment(p);     // creates p's entry: a copy of a Pair borrowing `it` into a field-held collection
  end Note;                 // `it` disposed; the entry's key dangles
end Tally;
```

`Counter<K>.Increment(key: K, delta: int := 1)` "absent key is created at `delta`" (stdlib §4.20): a store of `key`. §28.11's slot policy reads the single-element stores by name (`Add`, `Insert`, `Push`, `Enqueue`, `TryAdd`, `GetOrAdd`, an indexer-set); stdlib §4's register lists those as "not value-copy members … each a store in its own right" and says nothing of `Increment`. The program above is rejected by no stated rule. (`Counter<K>` is unimplemented, #3848, so no compiler verdict exists either way.)

A rule stated over signatures needs no census: whether a member copies is visible in its declaration. The retrospective tested that claim (`scratch/matrix2/retro_work/reach_r7.py`), and this lane re-ran it with a parser that reads the markers on comment-continuation lines too (`scratch/v0334/w8work/census.py`, `census.out`): over 513 declarations in stdlib §4–§6, 23 of the 27 marked members are matched by a shape (the parser cannot read the four whose parameters contain `->` or a `where` clause — `Sorted(comparer)`, `OwningBuffer<T>(length, init)` and the two `ToDictionary` forms — which shape (i) reads by hand), **0 marked members miss a shape**, and the 20 unmarked matches are: 9 single-element stores the slot policy already names (`Add`, `Insert`, `Push`, `Enqueue`, `SortedSet<T>.Add`, `Dictionary<K, V>.Add`, `SortedDictionary<K, V>.Add`), 2 `FrozenArray<T>` copies that are vacuous at a sendable `T`, 5 constructors of non-collection types the parser does not scope out (`Atomic<T>`, `Locked<T>`, `RwLocked<T>`, `DrainedEntry<K, V>`; the rule is scoped to collections, spans, buffers and §5), the **four genuine over-reads** the rule names, and **`Counter<K>.Increment`**.

### 1.2 The report's per-family site enumeration (R6)

§28.3's *The trust-admission report* lists, for each recorded clause, the sites at which the compiler admits under it — "a parameter-, receiver- or field-path-sourced borrow stored into a non-`owned` class- or interface-typed field (the borrowed-field store rule above, and its restatements at §28.6, §31.1 and §22.16); such a borrow stored into a borrowing-family collection or the key slot of an `OwningDictionary<K, V>` …; a **transfer** of an owned binding … ; a comparer passed to a hash collection's constructor …; a borrow held by a pending frame past the call that minted it — a task passed to `Task.FireAndForget`, stored, or bound and not awaited on every path …" — and then claims that a silent unit carries no clause. The claim is about the clauses; the enumeration restates each clause's own text at its home, and when 0157 found the collection entry narrower than §28.11's clause ("such a borrow" versus every admitted element) it was the enumeration, not a clause, that was wrong. Under proposal 0159 option (a′) the same enumeration would need a third amendment (a value that holds borrows at a field: `W1a2-s283-report`).

### 1.3 Three statements of why a capture-bearing function value is rejected (R2)

The closure bullet's sink rule (550 words), *Function-typed holders* (762, three sub-bullets each ending "the remedy for a capture-bearing callback is …"), *Set-erasing positions* (1,033), §28.14's formation bar and not-at-`Object` bullet each give the ground: "a function type announces no source set (K2.4), so no holder outside this body could re-establish it and no caller could bound it". The holder sub-bullets add, per holder kind, that the generated constructor parameter or the setter's `value` carries the empty set and is not call-bounded, that a read carries the empty set, and the remedy — the same three sentences three times. The review's reading (RETRO §0) is that the whole family is one sentence: *a value that carries borrows its static type does not announce must not reach a position that announces none*; for function values that sentence is unavoidable in substance (capture-free values are admitted everywhere, so each position must be read for the value's set) but can be stated once.

## 3. The rule

### 3.1 §28.11 *Storing a borrow* — ▲ *Value-copy members* (replaces the value-copy sentence)

> **Value-copy members.** A standard-library member's body contributes no requirement (§3.6 rule 2), so what it stores is read off its **declared signature**, by three shapes over the members of the standard library's collections, spans and buffers and of its query operators (stdlib §4, §5): **(i)** a method, constructor or `static` factory whose result is an `owned` collection — the constructed collection itself, for a constructor — copies into that result every element value it takes: from its receiver, from each argument that is a collection, span or `IEnumerable` over one of the result's element types, from each argument declared at one of them (`fill`), and from each invocation of a function argument whose return type is one of them (`ToDictionary`'s selectors, and `OwningBuffer<T>`'s `init` at a value-typed `T`); **(ii)** a method of a borrowing-family collection or of a span view that declares no return copies into its receiver the values it takes from a parameter declared `IEnumerable<T>`, a read-only span over `T`, or a bare `T` — the many-element forms `AddRange`, `UnionWith`, `CopyFrom` and `Fill`, and the single-element stores `Add`, `Insert`, `Push`, `Enqueue` and `Counter<K>.Increment`, which creates its key's entry, each of which the element slot policy already reads as a store; **(iii)** a method that declares no return and takes a writable span over `T` copies into that span's viewed buffer or array (`CopyTo`). A copy is judged as a store of each placed value into the destination, at the call: at a class or interface element type under this rule, at a value type that holds borrows under §9.7's collection bullet. [the sourcing and destination sentences, unchanged in substance; the destination sentence also carries the old register's "an indexer-set, a span view's included, which writes the buffer or array the span views"] … Four members match a shape and copy nothing: `Set<T>.IntersectWith` and `ExceptWith` only remove, and `Span<T>`'s class-typed `MoveFrom` and `MoveTo` move (K3); the owning family's element stores are transfers through `owned` parameters and `owned`-returning initializers, not copies (the value-typed `OwningBuffer<T>`, whose `init` returns a plain `T`, aside); a lazy query operator returns no `owned` collection and is a frame; and a copy whose elements carry no borrow — a value type that holds none, a null-source value, a `string`, a sendable element (`FrozenArray<T>`) — is a copy and nothing more. An inline array's `ToArray` (§15.1) and range slicing (§15.6) are shape (i)'s copies; a `FromCollectionLiteral` is one at a direct call, a collection literal being judged element by element (§15.4).

The exact text is `W8.json` id `W8-R7-s2811`. §9.7's passage becomes ▲ "**The standard library's value-copy members** are stores under this bullet, read at the call over the declared signature (§3.6 rule 2 …). Which members copy, whence each copied value's sources are read and where the destination lies are §28.11's *Value-copy members*, read here at an instantiation at which `T` holds borrows." followed by the bullet's existing examples (`W8-R7-s97`). Stdlib §4's register becomes a pointer that restates the three shapes in one line and the four named members, and keeps the register's list of single-element stores (`LinkedList<T>`'s `AddFirst`…`AddAfter`, `TryAdd`, `GetOrAdd`, a span view's indexer-set among them), whose only statement it was (`W8-R7-std-register`); the 27 markers go (`W8-R7-marker-*`); §5's list becomes the same pointer (`W8-R7-std-s5`); §4.20 says ▲ "`Increment` … on an absent key stores the key — a store into the tally under language spec §28.11's store rule, as `Dictionary<K, V>.Add`'s is" (`W8-R7-std-counter`); the code-generation reference's note lists the members by shape (`W8-R7-cg`).

**Why these three shapes and no others.** Shape (i) is the register's fresh-result list (`ToArray`, `Sorted`, `Reversed`, `Slice`, the five borrowing `FromCollectionLiteral` factories, `Array<T>(size, fill)`, `LinkedList<T>(source)`, `OwningBuffer<T>(length, init)`, §5's `ToArray`/`ToSet`/`ToDictionary`); its "element values it takes" clause is what makes `Dictionary<K, V>(comparer)` copy nothing (a comparer is of no element type and its invocation returns `bool`/`int`) and `ToDictionary(key, value)` copy its selectors' results (each returns an element type of the result). Shape (ii) is the register's receiver-destination list plus the slot policy's single-element stores, which it reads identically; its no-return condition is what keeps `Remove(item): bool`, `Contains`, `IndexOf` and `SequenceEqual` out, and `Set<T>.Add(item): bool`, `TryAdd` and `GetOrAdd` stay the slot policy's stores by name. Shape (iii) is the span-write list; a writable span parameter is a *destination*, which is why `CopyTo(destination)` is (iii) and not (ii) — the retrospective's draft read it under both, in the wrong direction. The owning family is excluded by its `owned` parameters (K3 transfers, §28.11's owning rows); the `Owning*.FromCollectionLiteral(owned elements: OwningArray<T>)` factories are transfers for the same reason.

### 3.3 §28.3's closure bullet — ▲ *Announcement-erasing positions (the sink rule)* (`W8-R2-sink`)

> **Announcement-erasing positions (the sink rule).** The rule above compares a function value's set where it places one — at a function-typed local, an invocation, a capture and a function-typed parameter, consequences of the set and not a closed list. A position that holds a function value beyond that comparison, or converts it, is **announcement-erasing** when its declared type — a function type, `Object`, or a type parameter an instantiation substitutes with either — announces no source set (K2.4): no holder outside this body could re-establish the set and no caller could bound it, the ground §28.14 states for a received callback (a plain signature carries no capture set). While its source set is non-empty, a function value may **not** be stored in a field, in any collection, in a property or indexer, or through an `out` or `ref` parameter, may not be returned from the enclosing method (by `return`, or by `yield return` in an iterator, whose element type announces no source set either), and may not reach a set-erasing position. A capture-free function value is admitted at each of those positions, and a capture-bearing one is stored only through a `scoped` parameter under §28.14's storage-bounded admission. The announcement-erasing positions are the two lists below, by the declared type that makes each one erasing — *Function-typed holders* (declared at a function type, or a collection slot) and *Set-erasing positions* (declared at a type that is not a function type) — each this sentence's site list, adding no rule; a position on neither list is not announcement-erasing.

The sentence rule case `s28_3_0111` and the matrix's R7 cells quote ("While its source set is non-empty, a function value may **not** be stored in a field, in any collection, in a property or indexer") is kept verbatim. *Function-typed holders* and its three sub-bullets become one bullet (`W8-R2-holders`) that keeps every store, both exclusions, the empty-set reads and the remedies, stated once each; the sentence `s28_3_0111` quotes from it ("At every function-typed holder the closure bullet's sink rule holds: a store of a function value admits a capture-free value and rejects one whose source set is non-empty") is kept verbatim. Provenance clause 1's "in the declaring body and in every lambda body that captures it" becomes "in any body" (`W8-R2-prov1`); the fixpoint sentence is untouched.
