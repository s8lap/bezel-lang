## 0. Summary

**Decision (option (b)).** A direct `DisposeAsync()` call — `x.DisposeAsync()` and the `x?.DisposeAsync()` / `x!.DisposeAsync()` spellings, awaited or not — requires a receiver the caller **owns**, by the same classification §28.6 *Who may call `Dispose()`* already states for `Dispose()`: an owned local or `owned` parameter, a `using var` or `await using var`, an unbound owned temporary, a `move` result, or an `owned` field / owning-collection slot / `static owned` field read by code of the owning object's declaring type. Through a **borrow** it is a compile error, `this` included, with **one exemption**: inside the body of a `DisposeAsync` override, `base.DisposeAsync()` is §28.12 step 2's chain, not a disposal of `this`, and is admitted. The call joins the consume table's row **K3.9** beside `Dispose()` and the discard: the same marker-free, site-announced kill, the same **explicitly-disposed** post-state (scope-end machinery skips the binding; a straight-line use afterward, a second explicit call included, draws §28.2's use-after-dispose warning), the same unfrozen verdict; its disposal moment is the call, with logical disposal completing at the returned task's terminal state and reclamation following there, as §28.12 states. Kernel: a derivation — K3.9's row widened by a spelling, no new axiom, the eleven positions unchanged. Zero sites in tests, docs and the rule corpus are rejected; the compiler checks the `Dispose` spelling only, so the rule is spec-ahead-of-impl.

## 1. The problem

§28.12 step 2, verbatim: physical reclamation runs "exactly once, immediately after whichever logical-disposal path completes — a synchronous `Dispose()`, `await using`'s implicit sequence, or a **direct `DisposeAsync()` call** awaited outside `await using` (legal; the awaited task's completion is logical-disposal completion, and reclamation follows exactly as if `await using` had issued it)". No receiver condition is stated.

§28.6 *Who may call `Dispose()`*, verbatim: "Explicit disposal — `x.Dispose()`, the `x?.Dispose()` / `x!.Dispose()` spellings, and the discard of a named owned binding (§17.13) — requires a receiver the disposer **owns** (derives: K3.9)", and "`Dispose()` through a **borrow** is a compile error." K3.9's row enumerates the same three spellings and the discard. `DisposeAsync()` appears in neither.

So at v0.328 a borrow may await `DisposeAsync()` and trigger the physical reclamation of an object its owner still holds:

```bezel
public class Resource: IAsyncDisposable
  public async method DisposeAsync(): Task
    await Task.Delay(0);
  end DisposeAsync;
  destructor
  end destructor;
end Resource;

public class Program
  public static async method CloseAsync(r: Resource): Task     // `r` is a borrow
    await r.DisposeAsync();                                     // (i) legal at v0.328: reclaims the caller's object
  end CloseAsync;

  public static async method Main(): Task
    using var r := new Resource();
    await CloseAsync(r);
    // `r` is reclaimed; the scope-end disposal and any later use rely on the K4.1 backstop
  end Main;
end Program;
```

The same hole is reachable through every borrow receiver §28.6 lists — a pattern binding, a `catch`-arm binding, a non-`owned` field read, a getter result, an `IAsyncDisposable`-typed view of a borrowed object, and `this` (`await this.DisposeAsync()` in a `CloseAsync()`-style method, the asynchronous form of the self-disposal §28.6 names and rejects).

Three things keep this from being a clarification (L4's write-up, its critique's N4):

1. Adding the call to the consume table is a kernel change: K3.9's row names the spellings, the post-state and the freeze verdict.
2. An override's `await base.DisposeAsync()` — which §28.12 step 2 calls "the override's obligation" — has receiver `this`, which §28.6 lists as a borrow. An owner-only rule needs a stated exemption for that chain, or it rejects the shape §28.12 requires.
3. The rule corpus pins `await r.DisposeAsync(); await r.DisposeAsync();` on a `using var r` as run-and-no-op (`s28_12_0006`, `expect: run`). An owner-only rule with K3.9's post-state makes the second call a use after a dominating kill, and that has to be read against the pin.

**Measured reach.** Every direct `DisposeAsync()` call in `tests/` and `docs/` is on an owned `using var` receiver: `tests/conformance/rules/cases/s28_12_0005.bzl:46` and `s28_12_0006.bzl:33–34` (`using var r := new Resource(); await r.DisposeAsync();`). The gtest mentions (`async_test.cpp:1602, 1637`; `idisposable_iasyncdisposable_iformattable_heap_ptr_4326_test.cpp:109`; `idisposable_iasyncdisposable_member_dispatch_4328_test.cpp:238`) and the doc-example corpus's `spec_0235.bzl:6`, `spec_0255.bzl:4` are comments. No `base.DisposeAsync()` chain exists anywhere in `tests/` or `docs/` (`grep -rn 'base\.DisposeAsync'`: the changelog's #3838 filing text only). The three `virtual`/`override` hierarchies in `tests/codegen/await_using_disposeasync_dispatch_3493_test.cpp:52–57, 194–198` chain nothing. Zero sites are rejected.

## 2. Options

- **(a) Status quo.** A direct `DisposeAsync()` call has no receiver condition; §28.6 governs `Dispose()` only.
- **(b) The owned-receiver rule, with the chaining exemption.** §28.6's rule and K3.9's row cover the direct call in the same spellings; through a borrow it is a compile error, `this` included; `base.DisposeAsync()` inside a `DisposeAsync` override is admitted as §28.12 step 2's chain.
- **(c) Logical disposal only through a borrow.** A borrow may call `DisposeAsync()`, but the call then performs logical disposal only; physical reclamation waits for the owner's disposal point.
- **(d) A warning.** The direct call through a borrow draws a compile-time warning rather than an error.

A fifth shape — (b) with no chaining exemption — is not an option but a contradiction: §28.12 step 2 makes `base.DisposeAsync()` the override's obligation, and every override's receiver is `this`. It is mentioned so that the exemption's necessity is on record; it takes no decline row.

## 3. Evaluation

- **Soundness.** (a) is the hole: a borrower's call reclaims the heap block of an object its owner and every other borrower still treat as live — exactly the ground §28.6 *Borrowed owning collections* states for `Dispose()` ("the owner and every other borrower still treat the container and its elements as live, and a borrower's `Dispose()` would destroy value the owner relies on"). After reclamation the owner's scope-end disposal is a no-op only by K4.1's backstop, and in unchecked builds every later use through the owner is undefined. (b) closes it by receiver, which §28.3 already classifies at every call site. (c) closes the reclamation half but not the logical half — the owner's object has run its cleanup out from under it, and a later member access faults in checked mode exactly as after a borrower's `Dispose()` would; it also splits §28.12's object-central rule ("physical reclamation runs exactly once, immediately after whichever logical-disposal path completes") by receiver classification, which the run-time path cannot see. (d) leaves a sound program's invariant to a lint; §28.6 is exception-free for the synchronous call ("only owners dispose"), and nothing about awaiting makes a borrower's disposal safer.
- **Simplicity.** (b) is one widening of a rule and a row the language already has: the receiver classification is §28.3's, the post-state and scope-end behaviour are K3.9's, and the use-after-dispose warning is §28.2's. The exemption is one syntactic shape — `base.DisposeAsync()` in the body of a `DisposeAsync` override itself — and it admits nothing else `this`-rooted: `this.DisposeAsync()` or a bare `DisposeAsync()` inside the override is recursion into the object's own disposal and stays rejected, and `base.DisposeAsync()` in any other member is the self-disposal §28.6 rejects, through the base's cleanup. (c) needs a second kind of direct call, distinguished by receiver classification, with its own reclamation timing. (d) needs a new warning with no remedy the error does not already name.
- **Consistency.** K3.9's **explicitly-disposed** post-state is what §28.12's "reclamation follows exactly as if `await using` had issued it" already needs: once the direct call has reclaimed the object, the owning binding's scope-end disposal must not run as a disposal of a live object, and K3.9 says the scope-end machinery skips an explicitly-disposed binding (§28.3's auxiliary states). At v0.328 that skip was stated for `Dispose()` and the discard only, so the direct call on a `using var` relied on the runtime no-op; under (b) it is the same compile-time state as `r.Dispose()`. §28.2's second-call clause carries over unchanged: "A second `Dispose()` on the same binding is such a use and draws this warning … the no-op carve-out above states the **runtime** contract of a repeated call and suppresses no diagnostic." §28.12's "A second call to `Dispose()` or `DisposeAsync()` after either has run is a no-op" is that runtime contract, and it now says so. `await using var`'s scope-end await is not a repeat call (the binding reached its discharge point), so the ordinary binding stays warning-free. Proposal 0145's "no borrow reaches a *synchronous* disposal path" stays true and becomes stronger: no borrow reaches any disposal path. The `TaskScope` binding is an owned receiver, so `await scope.DisposeAsync()` on it is admitted as an early release of the same asynchronous path (its `Join` obligation under stdlib §6.10 is unchanged; the compiler's "no member" at that receiver is tracked, #5657 item 6).
- **Over-rejection (measured, §1).** (b) rejects zero sites. The exemption admits the one `this`-rooted shape §28.12 requires and no site uses it yet.
- **The corpus pin (`s28_12_0006`).** The pin is the runtime contract: two direct calls on a `using var`, output `async cleanup` once, then `done`. Under (b) the second call is a straight-line use after a dominating K3.9 kill of the same binding and draws §28.2's mandatory warning — the same two-halves shape as §28.2's second `Dispose()`, for which `AUTHORING.md` provides `warns: yes` on a `run` case. The case keeps `expect: run` and gains `warns: yes`; its banked baseline row (`fail divergence`) is unchanged. `s28_12_0005` (one direct call on a `using var`, then scope end) is unaffected: the binding is explicitly-disposed, the scope-end disposal is skipped, the output is the same.
- **Migration reach.** At spec level, (b) newly rejects a direct `DisposeAsync()` call whose receiver is any borrow §28.6 lists — a plain parameter, a pattern or `catch` binding, a non-`owned` field read, an owned-field read outside the declaring class, a getter result, a captured owned binding, an element borrow, `this`, and `base.DisposeAsync()` outside a `DisposeAsync` override. Zero sites. Newly stated (warning) is a second explicit `DisposeAsync()` on the same owned binding. Nothing is newly admitted beyond what §28.12 already requires (`base.DisposeAsync()` in an override, which no text rejected and which is now exempted expressly).

## 4. Decision

**(b).** Declined, recorded in `DECLINED.md` as `declined-at-proposal`:

- **(a)**, because a borrower's direct call reclaims an object its owner still holds, the hazard §28.6 closes for `Dispose()` with no exception. Reopening bar: a disposal model in which a borrower's disposal is observable to the owner at compile time.
- **(c)**, because logical disposal through a borrow still runs the object's cleanup out from under its owner, and a receiver-classified reclamation timing splits §28.12's object-central rule. Reopening bar: a two-phase contract in which logical disposal is itself a borrower-safe operation.
- **(d)**, because §28.6's rule is exception-free for the synchronous call and the asynchronous one is the same disposal. Reopening bar: evidence that the error rejects a measured idiom the owner cannot spell.

## 7. Self-critique (adversarial pass)

- **Does the exemption leak?** `base.DisposeAsync()` is admitted only in the body of a `DisposeAsync` override itself. §12.3 does not by itself keep `base` out of a lambda nested in an instance member ("`base` is legal only inside instance members of a derived class"), so the exemption says so expressly: a lambda nested in the override is not the override's body, and `base.DisposeAsync()` there stays rejected. `base.DisposeAsync()` in a destructor is rejected (not a `DisposeAsync` body), as is any `base.DisposeAsync()` in a `CloseAsync()` helper. `this.DisposeAsync()` inside the override is recursion into the object's own in-progress disposal and stays rejected with every other `this`-rooted call.
- **Is the chained `base.DisposeAsync()` itself a direct call that reclaims?** It must not be: were it §28.12's "direct `DisposeAsync()` call", reclamation would follow the base level's task while the override is still running. The step-2 clause states it is a step of the logical disposal already under way and triggers no reclamation of its own, and K3.9 says it is not a position of the row (it kills no binding; `this` has no ownership state). (Added at critique, B1.)
- **Is the `await using var` binding's scope-end await a "second call"?** No: §28.2 says the auto-drop and a `using var`'s scope-end disposal are not repeat calls, the binding having reached a discharge point. Only a second *explicit* call on the same binding warns. And a binding whose `DisposeAsync()` was called directly is explicitly-disposed, so no scope-end disposal is issued for it at all — the shape `s28_12_0005` pins keeps its output.
- **Does the unawaited direct call (`using var t := obj.DisposeAsync();`) fit the row?** Yes: the kill is announced at the call; §28.12 already says logical disposal completes at the task's terminal state and reclamation follows there. The binding `obj` is explicitly-disposed from the call statement, so a read of it between the call and the task's completion draws the warning — the right answer, since the object's cleanup is under way.
- **An `owned` field of type `IAsyncDisposable` disposed asynchronously inside the containing class's `DisposeAsync` (`await _inner.DisposeAsync()`)**: the declaring-type field admission, admitted, as `_inner.Dispose()` in a destructor is. The early-release paragraph of §28.6 then applies: the slot keeps its reference, and the containing object's later cascade reaches §28.12's object-granularity no-op.
- **A conditional direct call** (`if c then await r.DisposeAsync(); end;`): K3.9's clause for every row — a conditional kill joins to **maybe-consumed** (K7.4), a later use is §28.3's error, and scope-end disposal is per path. Unchanged from `Dispose()`.
- **Composition with 0145:** the `TaskScope` binding is the owned receiver; nothing in 0145's borrow exemption admitted a borrower's `DisposeAsync()` — 0145's text said whether a borrow may trigger reclamation that way "is the general question, unchanged here", and this proposal answers it. Composition with the v0.328 run-time-object ruling: unchanged, the direct call dispatches as any interface member does.
