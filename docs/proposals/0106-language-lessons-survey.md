## 0. Method

**The question.** Not "what could Bezel add?" — that has no floor. The owner's question is answerable because Bezel records its declines: *is there a class of idea, well established elsewhere, that the register has never considered at all?* The unit of work is a **lesson** — one transferable idea, tested against the register, given one verdict.

**The five-register decline topology.** The digest lane's method note governs every verdict here, and is reproduced because it is what makes an *already-declined* verdict trustworthy:

> Bezel's declines are recorded in **five** places, not one. A verdict of *already-declined* is only safe after checking all five: (1) **rationale §17** — the explicit-rejection register (11 entries, thin); (2) **rationale §18** — the deferred register (~22 entries, thick, many now shipped); (3) **DECLINED.md** — D-0001…D-0004 + a pointer to the gap review's eight; (4) **per-section decision records scattered through the rationale and spec** — this is where most of the substantive declines actually live …; (5) **graduated-proposal decline records**. §17 being short is **not** evidence that a topic is undeclined.

Two corollaries the lanes applied. Many §18 entries are annotated *shipped* — verdicting one of those as open is the likeliest error. And the reversal precedent exists (§17.6 moved inline arrays from rejected to shipped; four axiom tombstones; §19.6's determination rule deleted at v0.245 by proposal 0089), so "Bezel never reverses" is not available as a premise either.

**The verdict vocabulary.** **already-have** — present; these entries *validate*, and are kept short deliberately, because a survey reporting only gaps misrepresents the register. **already-declined** — a register entry covers it, quoted below so the reader can check the decline reaches the lesson rather than a neighbour of it (deferrals count here, marked, since §18 is a register with a weaker bar). **genuinely-open** — no register entry covers it; these carry *why-it-matters* and *cost*. **negative-lesson-already-avoided** — the other language's experience is a warning and Bezel already sits on the right side of it, usually with the reason recorded.

Three scoreboard rows carry a fifth marker, **declined-with-reasons (recommended)**: the register does not cover them and this survey recommends they be *recorded as declined* rather than left open (a fourth such recommendation, contract-carrying aliases, is folded into this study's §6.2(a) rather than given its own row). They are tallied separately so no reader mistakes a recommendation for a ruling.

**Honest absence.** Every genuinely-open verdict states the nearest Bezel features first and where each stops, before claiming absence. Where a lane's *reading* of a rule is its own rather than the document's, it is flagged (this study's §2.1 carries the sharpest instance). Where an absence is a grep result, the grep is stated.

**What the survey found, in one paragraph.** Nothing probed turned out to be a blind spot in Bezel's *worldview*. The genuinely-open items cluster into two shapes. The first is **unfinished edges of features that landed**: a mechanism exists for the neighbouring case and was never extended to this one — record invariants beside class invariants, a file-scoped audit marker that never reaches the artifact interface, a domain that isolates state but not failure. The second is **evolution mechanisms** — editions, a compatibility promise, a warn→deny ratchet, a formatter, a migration tool — exactly the class a pre-user project cannot notice it lacks, and for which the register's own recurring justification ("zero external users") has a named expiry date. The first-rank finding is in the first shape; the largest cluster is in the second.

## 1. Ada and SPARK

**1.1 Constrained subtypes — genuinely-open.** Ada attaches the predicate to the type once. Bezel has the *distinctness* half only: §27.8 prescribes the carrier — *"For genuinely distinct types (`UserId` and `OrderId` should not be interchangeable despite both being `int`), use a single-field record"* — and Appendix A.3's `RecordDecl` admits no `ContractClause`. The mechanism that closes it is a **recorded deferral, not an oversight** — §22.16: *"**Out of scope in this revision**, each recorded: record invariants (constructor-exit plus a `with`-update instrumentation point — a later design)"*. Worked at this study's §6, which is where this verdict's *why-it-matters* and *cost* are priced (its §6.2(d) prices doing nothing; its §6.4 prices each option); the narrow form (d′) is the survey's **first-rank finding**. One half of Ada's lesson Bezel already beats: §32.5 refuses enums at the FFI boundary and §5.4 makes the cast total — *"There is no value of an enum type that is not equal to a declared constant"* — Ada's opt-in `'Valid`, made mandatory.

**1.2 Derived numeric types / units of measure — genuinely-open (notational) / declined-with-reasons (recommended).** Two halves, two verdicts; do not file them together. *Operator inheritance* is open but notational: §25.4 closes the escape (*"There is no syntactic form for declaring 'convert from S to T' on a user type"*), so each newtype costs ~25–30 mechanical lines — and the register already prices this shape, for tuples, in rationale §18: *"an **ergonomic convenience, not a capability gap** … What tuples would add is purely notational."* Constructive form at this study's §6.2(b). *Units of measure* is **declined-with-reasons (recommended)**: the zero-cost half is already delivered by a one-field value record plus §11.8 conformance at a record conformer (*"the markers are erased and every step is a plain copy"*); the algebra half needs a type-level abelian group — neither §14 type parameters nor rationale §18's bare *"Const generics. Generic parameters that are values, not types"* — and §14.6 rejects the *recursive* form the encoding needs, not the encoding itself. §14.6 constrains only edges **within a strongly-connected component** of the instantiation-request graph, requiring each such edge to substitute *"a **bare type parameter in scope at the source declaration** … or a **closed type**"*. Any type-level normalization (reducing `Mul<Meter, Div<One, Second>>`, or proving `Mul<A, B> = Mul<B, A>`) is the expanding in-SCC shape §14.6 names in its own example — *"a field of type `Node<Pair<T, T>>?` inside `Node<T>`"* — and so is the *non-generic* operator spelling `Qty<U> * Qty<U> : Qty<Mul<U, U>>`, since *"a **non-generic** member's edges attach to its **declaring type's node**"*, giving a self-loop with a growing argument. A non-recursive phantom encoding whose product operator is a **generic** member escapes the rule entirely — a type's node carries an edge to its own generic member *"only at a requested instantiation site"*, so nothing puts them in one SCC and the per-edge rule is vacuous — and is merely useless: with no normalization, `Meter * Second` and `Second * Meter` are distinct types and every dimensional identity must be hand-declared. Record it §18-style (an open design, not a rejected one), per rationale §18's allocator-entry placement rule. **The decline prices the *type-level erased* pole only**; this study's §6.2(c) records all three poles of the space, including the one Bezel already ships.

**1.3 Representation clauses — already-have, one narrow residual.** stdlib §4.14's endianness-named accessors (rationale §5.15 grounds the naming in Ada's own bug class: alternatives *"invite the class of bugs where someone forgets that a particular format uses a specific byte order"*), §32.13's normative layout guarantee, §9.8's serialization synthesis. The bit-positional quarter is declined with its reason — §32.13 item 6: *"**Unions and bitfields — declined**"* (with its reason outside the bold: *"no structural spelling survives §3.6's computed-never-declared discipline; bitfield layout is ABI-quirky"*). The residual, sub-byte *extraction*, which that ABI-shaped decline does not reach, is carried at this study's §3.5.

**1.4 Modular types — already-declined (by adjacency; close the hole).** §6.1's checked arithmetic plus proposal 0008's `Wrapping*` methods cover the capability, and 0008 declines both alternative spellings: a wrapping-operator token, which *"makes the safety-relevant switch from 'checked' to 'wrapping' as visually quiet as a one-character typo"*, and a C#-style `unchecked` block, which *"silently reclassifies"* everything inside it. Honest caveat: the *typed* form is not among 0008's declined alternatives and arguably answers the token objection better; the disqualifier is cost. **Recommendation:** convert it to an explicit decline in 0008's register.

**1.5 Elaboration order — already-have.** §22.13 is Ada's design with the static half defaulted (a cycle is a compile error, *"a deliberate approximation"*) and the dynamic half non-observing, explicitly *"stricter than C#'s, which silently observes the field's default value during such forward references."* Ada's residual advantage is §2.8.4 rule 6's recorded deferral of *"cross-unit dependency edges the artifact interface does not yet carry"*.

**1.6 Protected objects and Ravenscar — already-have.** §30.12's locks *"**own their interior**: construction consumes an owned `T`; the interior is reachable only through a scoped guard"* — which Ada's protected object does not do. Ravenscar must be opt-in because full Ada tasking is unanalysable; Bezel's baseline *is* the restricted profile unconditionally (§30.13, §30.14's *"no mutable state is ever reachable from two domains"*, §22.12). The one residual — a wait-on-predicate barrier — is routed by §30.12 itself to the actor idiom, whose recorded hole is rationale §18's multi-consumer-channel deferral; press there.

**1.7 SPARK's contract gradation — already-have (the cited lineage).** §22.16's three tiers, with `static` demanding the proven tier and an out-of-fragment `static` clause *"an error, never a silent downgrade to a runtime check"* — named as the lineage in rationale §11 and proposal 0043's influences row (SPARK, *"at best a discharged proof"*, explicitly not Dafny). **A draft listing SPARK-style gradation as a finding is re-asking a settled question.**

**1.8 A declarable per-unit verification posture — genuinely-open.** SPARK's `SPARK_Mode` makes the verified subset a per-unit posture with an enumerable boundary. Bezel has the slot and nothing in it — §22.16's **assumed** tier is *"unpopulated in this revision; reserved for contract clauses on `extern` declarations, to be designed jointly with the extern-purity question"*; Appendix D's levels grade *implementations*, not user modules; nothing in the five registers declines a posture. *Why it matters:* the realistic verification story for a service is a proven parser inside an unproven program, and without a declared boundary nothing says which modules carry the guarantee or stops erosion when a `static` qualifier is dropped — while §2.8.6 already classifies tier demotion per level, i.e. the *reporting* half exists, unused. The opportunity finding cuts against the owner's worry: SPARK spent years retrofitting alias control onto Ada because frame conditions are undecidable without it, and Bezel has that natively (§28.3's *"disposed **exactly once** at runtime"*, borrow liveness statically enforced). **Bezel is under-claiming an advantage it already paid for.** *Cost:* small-to-moderate and mostly composition — ▲ a module-level posture declaration; one rule that its `static` clauses discharge only against proven-tier facts (metadata §2.8.2 already carries); population of the `assumed` tier at the FFI boundary, already the reserved design. Risk to name: a *new artifact-level concept* in a module system whose §2.8.5 non-goals list is deliberately short.

**1.9 Exception occurrences — already-have.** §31.1 makes a caught exception a borrow; §31.4 chains by snapshot because a live `InnerException` *"would require exception instances to own exceptions, reopening the arm-lifetime rules"*; §30.14 copies message and trace text across the domain boundary rather than the object. *Also already-have without their own entries:* Ada's named-instantiation bound (paid for at v0.262 by §14.6, *"not yet enforced — tracked #3271"*); discriminated records (better served by §35 choices, rationale §9.6; the array-bound discriminant is const generics again); and the constraint's visibility in the interface (§22.16 clauses carried by §2.8.2; §3.6 rule 3; §2.8.6's verdicts).

## 2. The Wirth line — Pascal, Modula-2, Modula-3, Oberon

**2.1 Modula-3's SAFE/UNSAFE partition — genuinely-open** (a completion, not an import). Modula-3's contribution is a *graph discipline*: unsafety declared per unit, visible in the interface, propagated through imports, with a SAFE interface exported from an UNSAFE module as the sanctioned wrapper. Bezel already believes in the marker — stdlib §10: *"`System.Interop`, which is *not* auto-imported — the `import System.Interop;` line is the audit marker that a file performs foreign-memory access."* So this is an incompleteness, three ways. **(a) File-scoped, never in the interface:** §2.8.2 clause 1's carriage list (ownership modifiers, constraints, base types, `const` values, the purity modifier, contract clauses, derived properties) has no unsafety row, so a consumer holding an artifact cannot tell whether the module it links declares `extern` blocks. **(b) Apparently defeatable**, by §2.8.3 rule 2: *"A file that imports module `A` may freely **use** values of any public type reachable through `A`'s public surface — receive them (including into `var`/`using var` bindings with inferred types), call their public members …"* — so `var p := buf.DangerousPointer(); var v := p.Load();` is a complete foreign-memory access with no `import System.Interop;` in the file. The producer is stdlib §4.14's `OwningBuffer<T>.DangerousPointer(): Ptr<T>`, declared in `System.Collections.Generic`, which *is* auto-imported; and the hole is exactly **one producer wide** — `Ptr<T>.FromIntPtr` (stdlib §10.5's *"only untyped->typed entry"*) names the type and still demands the import, and the other foreign-memory producers return `IntPtr`, which is not dereferenceable. One clause closes it. **This reading is the lane's, not the document's, and is flagged as a defect candidate rather than a settled claim** — under CLAUDE.md rule 1 it is the shape that gets an issue, not a silent interpretation. **(c) No propagation rule** naming the trusted-wrapper shape §32.13's wrapper posture already recommends informally.

*Why it matters.* §28.3's exactly-once guarantee is voided anywhere in a program's closure that `extern` or `Ptr<T>` appears (§32.10: *"is a use-after-free no compile-time rule can see"*), and whoever assembles a program from many artifacts has no supported way to enumerate where. Every other trust boundary is legible — `owned`, `pure`, contract tiers, `sendable`. Unsafety is the one that is not. *Cost — two tiers.* **Tier 1, zero language change:** both facts are already syntactically present; surfacing them as a compiler query rides proposal 0052 with no normative surface (proposal 0105's landing shape), plus one clause closing hole (b). **Tier 2, the real partition** (▲ a module-header fact, ▲ an interface row, ▲ a safe-may-not-import-unsafe rule) is a genuine §2.8 addition whose proposal must say plainly that §3.6's closing rule does *not* govern it — a module is not a type. Tier 1 now; tier 2 is not obviously worth it before external users.

**2.2 Opaque types, the ABI half — already-declined.** §2.8.5: *"**ABI stability across recompilation.** The model is recompile-the-world … a stable binary ABI is a separate commitment nothing yet motivates"*, under that section's bar (*"each absence is decided, not forgotten. Revisiting one requires new evidence — real programs hitting real walls — against the stated reason"*). Bezel does not merely fail to hide representation; it publishes it deliberately and prices it, and its substitute is different in kind: §2.8.6 *classifies* the change normatively instead of hiding it.

**2.3 Opacity's other half — under-promising a structural fact — genuinely-open (low rank).** This survives this study's §2.2 decline because it is about the *source* contract. §3.6 rule 3 makes every derived fact promised irrevocably (*"A declaration change that flips a derived type property of a public type … is a breaking change for clients relying on it"*), and the only relief is prose advice — *"Library documentation should state the properties a type's clients are expected to rely on"* — a *should*, in English, with nothing in the interface to carry it. The nearest bar is one interpretation away: §3.6 rule 1 forbids a property being *"asserted, opted into, or **waived** by annotation"*. The lane reads that as governing the property's *value*, not the promise's *scope*; a proposal must confront rule 1 head-on. The notation is cheap (a clause carried like `serialized`, consumed by one §2.8.6 reclassification); the doctrine is not — §3.6 properties dispatch at the *consumer*, so the proposal must say what a consumer may do with an unpromised verdict, and the answer may be "nothing useful", which would kill it.

**2.4 Pascal nested procedures — genuinely-open (low rank).** Bezel shipped the *type* half of this locality argument at v0.225 — §21.10's form lets a shape used once *"live next to its single use instead of at module or class level"* — and the code half has no register entry (rationale §2.2 declines *module-level* free functions, a different level). The endorsed substitute, a local lambda, falls short three checkable ways: it allocates (§27.5: *"Captured variables are heap-allocated in a closure object"*), it cannot recurse, and it is a reference value with runtime-managed lifetime (§28.9). Cost is low — ▲ a capture-free local method declaration ports §21.10's restriction set nearly verbatim, with one deliberate divergence (self-recursion needs the name in scope inside its own body); capture must be out of scope in any v1, since admitting it reopens §27.5 and §28.14 for no gain a lambda does not already give. The bar is rationale §5.13's *"helper-method extraction is good design independently"*, and the honest answer is that this adds two capabilities (recursion without hoisting; no heap closure), not a spelling.

**2.5 Oberon's design by subtraction — already-have (one cultural residual).** Five registers plus a deletion record: the `event` member kind, object-initializer blocks, extension-specificity rules 2–3 deleted after landing, §19.6's determination rule retired at v0.245, `ReadOnlyAsciiByteSpan` deleted with no migration, four axiom tombstones. The honest counterweight: Bezel is *not* a small language — six type-shaped kinds where Oberon reached one, plus properties, overloading, operator overloading, extension blocks, collection literals, the null-conditional family, generics, and six span names for one idea. What Bezel has is a *record* per feature, not a small feature count. The one Oberon-shaped recommendation is cultural: every deletion so far was triggered by a defect or a proposal, never by a scheduled sweep, so a **periodic subtraction review of shipped language surface** is the transferable half.

**2.6 Pascal subranges — genuinely-open**, and this lane's contribution is the counter-evidence. Routed to this study's §6. Wirth shipped subranges in Pascal, kept them in Modula-2, and **removed them from Oberon** — approximately, because they complicated assignment compatibility and parameter passing across the type system for a benefit runtime checks already delivered (lane knowledge, approximate). Ada took the other branch and SPARK depends on it. Consequence: any proposal's hard section is the conversion lattice and overload resolution, not the prover. Priced at its destination, not here — this study's §6.2 and §6.4 carry the cluster's costs. *Also checked and closed:* Pascal sets of small ordinals (already-have — `Set<T>`'s algebra plus §17.9's one structural-dispatch rule; the missing piece is a packed *representation*, served by bitwise ops on an enum's underlying integer and by proposal 0025); Modula-2 coroutines (already-have; residual = rationale §18's synchronization-contexts deferral); Oberon's ban on import cycles (Bezel admits them and prices the consequence at §2.5/§13.4 — the transferable lesson is a *removal*, which §2.8.5's evidence bar governs).

## 3. Erlang and OTP

The sentence that keeps every Erlang-derived recommendation honest: **Erlang's kill primitive cannot be transferred at any price.** A dead BEAM process needs no unwinding; §28.3's guarantee makes an instant kill impossible by construction, and §33.3 admits skipping disposal only at process exit where the OS reclaims. Bezel can adopt let-it-crash's *architecture* — small fallible units, a supervisor rebuilding from a specification, irreplaceable state in the kernel — but must implement it as cancel → quiesce → join → respawn.

**3.1 A domain isolates state but does not bound failure — genuinely-open.** The spec states the gap in its own voice, §30.14 (*Domain completion*): *"Tasks started within the spawned domain that are still pending continue to run in that domain; their eventual exceptions are handled as `Task.FireAndForget` handles them (logged, not propagated — stdlib §6.7)."* An entry fault unwinds one frame; siblings survive it, keep mutating the domain's state, and their own faults are swallowed into a log. Rationale §12.12 confirms the intended role and its limit: *"`Domain.Spawn` is not a concurrency combinator at all — it is an isolation boundary (§12.5), chosen for state separation, with sendability doing the checking."* State separation, not failure separation. No decline is recorded anywhere. Worked at this study's §7.

**3.2 Supervisors and restart — genuinely-open.** Nothing restarts anything — and the greps say so precisely. Over the ten documents in `docs/` (`grep -oih supervis docs/Bezel_Language_Spec.md docs/Bezel_Standard_Library.md docs/Bezel_Design_Rationale.md docs/Bezel_Changelog.md docs/Bezel_Guide_0*.md | wc -l`) the substring `supervis*` occurs **36** times, on 27 lines across 7 documents; the exact token (`grep -oihw supervision …`) occurs **9** times, in 5 of them. Every occurrence is task-level (`Task.FireAndForget`, `TaskScope`, `WhenEach`), a catch-boundary use in Guides 02 and 06, or stdlib §1's consumption-locus band — *"a boundary, supervision, or retry site"*. None is child supervision, and no restart mechanism stands behind any of them. Two findings shape the answer. **The hard precondition is already met** — §30.14's *"The entry must be capture-free"* means the compiler already proves a restarted child inherits nothing, the expensive part of an OTP child spec. **The generic form is expensive for a stated reason** — the entry is a call-site syntactic category, so a supervisor parameterised over a *stored* entry value is not writable in user Bezel; stdlib §6.12 states the precedent verbatim for `Parallel` (*"not writable in user Bezel"*). Hand-written one-for-one supervision composes today from documented members. **Doctrine now, compiler-known helper on evidence** (this study's §7.5).

**3.3 The error kernel — genuinely-open (doc-only).** Push fallible work outward; keep irreplaceable state in a unit that must not fail. Bezel's sendable rules already push programs this way without saying so, so the doctrine is free to state and makes existing rules legible rather than arbitrary. It also corrects a live mis-teach: Guide 04 §6's actor idiom recommends the domain owning entangled state as the home for serialized work — exactly the unit whose crash is unrecoverable. Cost: one rationale §12 entry plus a Guide 04 paragraph.

**3.4 Unbounded mailboxes — negative-lesson-already-avoided.** §30.15 ships bounded channels with the contract in the language: *"Back-pressure therefore composes with the ordinary task machinery and adds no new suspension concept."* Residual, stated honestly: `new Channel<T>()` is still the unbounded one, guarded only by Guide 04's *"Bound your inboxes"*.

**3.5 Bit syntax — genuinely-open (reader half); pattern half declined-with-reasons (recommended).** The nearest feature is byte-granular only (stdlib §4.14 reads nothing narrower than 16 bits; §19.3's pattern kinds contain no binary form); `BitArray` is a bit *set*, not this. Nothing declines a bit-level reader — §32.13 item 6 declines C bitfields for an *ABI-layout* reason, which says nothing about a reader that has no ABI at all. **The GC objection does not transfer, and that is the argument:** Erlang needs refcounted sub-binaries because a matched tail must outlive the match, while Bezel's span already *is* a lifetime-checked sub-binary — stdlib §4.15: *"The `Source` field carries a borrow of the array; per the borrow-bearing-record rule, the span's lifetime is bounded by the source's lifetime."* *Why it matters:* the live queue is thick with consumers (0001/0007, 0002, 0020, 0029, 0069), each of which will hand-roll the same mask-and-shift ladder — the bug class the endianness family exists to eliminate one granularity up. *Cost:* small and stdlib-only — ▲`BitReader` (a borrow-bearing record over `ReadOnlySpan<byte>`, `Try`-shaped per stdlib §1, the byte-aligned tail an ordinary sub-span; a record member cannot write a cursor into its own receiver — §9.4 — so the advance idiom is the span family's slice-and-walk shape, not a self-advancing reader) plus a ▲`BitWriter` mirror; no language change, no compiler-known status, no new derived property. The **pattern-position half** drags binding-surface, exhaustiveness, and borrow-producing-binder questions into pattern position; decline it *in the same record* rather than leave it dangling.

**3.6 Hot code loading — already-declined.** Foreclosed by prerequisites, each recorded with its kind marked: §2.8.5's ABI non-goal (decline); rationale §18's member-access reflection, *"declined, not deferred: it contradicts the ownership model … recorded as declined so the question is settled rather than perennially reopened"*; §2.8.3 rule 4's one-type-in-the-process rule (structural); §32.14 item 8's runtime library loading (deferral). The transferable residual is what hot reload buys in production — change without dropping work, which for AOT is drain-then-exit — and Bezel's shutdown does the opposite (§33.3: *"the runtime signals no cancellation, runs no further continuations of theirs"*). It lands in this study's §7 as the cross-domain stop signal, with proposal 0014 supplying the trigger.

**3.7 Registered names — already-have.** The process-global endpoint is §22.12 rule 2 form (i)'s sanctioned static, with the explicit ruling to *"keep the `Channel<T>` domain-confined and publish a `ChannelSender<T>` static instead"*; the dynamic keyed registry is stdlib §6.11's `static owned readonly` idiom. Liveness is better than `whereis`: *"Sending on a closed channel raises `ChannelClosedException`"* — a defined fault, not a stale handle. The residual (re-registration after a restart) folds into this study's §3.2.

## 4. The evolution playbook — Rust, Go, Swift, Java, C#

**This lane's headline is the most uncomfortable finding in the survey.** Six decision records justify a decision by citing the absence of external users — rationale §3.13 (*"with no external users a deprecation window serves nobody"*), rationale §9.5 (*"the rename only gets more expensive, and the first external user makes the pair permanent"*), the v0.246 and v0.259 changelog ledgers, proposal 0083's "possible only pre-users", proposal 0100's reopening bar. That is a policy with a named expiry condition **and no successor policy anywhere in ten normative documents, 105 proposals, or five registers**. Nothing here is a missing language feature; every gap is an evolution mechanism, which is exactly the class a pre-user project cannot notice it lacks.

**4.1 Editions — genuinely-open (load-bearing).** A per-compilation-unit pin on the source language, one compiler, free interop across pins. Absence is total: *"edition"* appears **zero** times across all ten documents in `docs/` and all 105 numbered proposals preceding this one (107 files — 0046 is doubled); re-verified at HEAD. **Keep editions and ABI apart**: §2.8.5's ABI non-goal is a recorded decision with a stated reason, attacking it is re-asking a decline, and editions do not require a stable ABI — Rust has none either — so a proposal bundling them will be correctly rejected on the ABI half and lose the good half with it. **And build on §2.8.6**, which is *most of an edition's normative vocabulary already written*: verdicts *"identical, preserving, widening, or breaking"*, normative so no two conforming tools classify one delta differently, with per-level layering; §2.8.3's program-wide type identity supplies the interop invariant an edition must never cross. The cheap move is the **reservation** — decide where the pin lives (a module-header clause ▲ vs. a manifest key in proposal 0040's Stage 1) and reserve the §2.8.2 field: a one-revision ruling with essentially no compiler work, impossible once the interface format has an outside consumer. Honest costing: a new §2.8 subsection; none of the three cheap growth clauses (§3.6, stdlib §1, §28.3's axioms) hosts it.

**4.2 Compiler-guided migration — genuinely-open (small).** Bezel already practises this and has never recorded it as doctrine: six in-tree `scripts/migrate_*.py`, one per breaking flip, including a rustfix-shaped one that drives `bezelc`, reads a diagnostic's (line, column), inserts the marker, and re-runs to fixpoint. Proposal 0052 builds the substrate (code taxonomy, JSON diagnostics, confidence-tagged fixits) but is scoped to the agent loop; proposal 0040 has no fix or format stage. The sharpening for an ownership language: the migrations that will be needed are *ownership-marker* migrations, which a human cannot do by eye at scale — and the compiler is already *normatively obliged* to compute the fix (0052 §1.2 tabulates six spec sites mandating that a diagnostic name the remedy) while being architecturally unable to emit it as data. Swift 3→4 is the sequencing warning: a migrator without a pin still hurts. Cost: small, zero normative surface, plus one paragraph in `spec-change-process.md` §5.

**4.3 `unsafe` as an audit index — genuinely-open (tooling).** The *keyword* is correctly declined — rationale §5.15: *"the user-facing surface never exposes raw pointers, pointer arithmetic, or untyped memory access"*. What survives is the *audit* question: §32.10's obligations are per-declaration while the hazards it describes are per-expression, and it says twice that they are things no compile-time rule can see. Bezel's module-level quarantine is already stronger than Modula-3's; the gap is one level down. Cost: a `--query foreign-obligations` in proposal 0052's existing shape, over facts the FFI checker already has; Appendix D's diagnostic-identity latitude means no spec change. **Do not write this up as "Bezel should reconsider `unsafe`."**

**4.4 The warn→deny ratchet — genuinely-open (narrow: promotion policy only).** **Bezel does not need lints.** Its warnings are *normative* (§15.4's *"must warn"*, with content and non-effect both normative), conformance-classified (Appendix D: a mandated warning is satisfied by any warning), and doctrine-governed (rationale §5.28); framing this as "Bezel needs lints" would be false and would get the real gap dismissed with it. The residual is that there is **no ratchet policy**: promotions happen by revision fiat, and `spec-change-process.md` §5 requires the Migration note to record *"what becomes newly-rejected, newly-defined, newly-warned"* — the outcome, never the ramp. It matters because the kernel is still gaining rejections: §14.6 sits in the spec at v0.262 as *"not yet enforced — tracked #3271"*, a rule that will become a rejection for programs that compile today. Cost: one row in the change-class table plus one line in the Migration-note requirement. (The per-site allow rationale §5.28 declines stays declined; its reasons concern the three *current* lints, whose remedies are one line and always sound.)

**4.5 A Go-1-shaped compatibility promise — genuinely-open (free to write, large to keep).** Bezel has the machinery and states no promise: §2.8.6 governs a module auditing itself, not a commitment to users; `spec-change-process.md` disciplines authors; DECLINED.md stabilises *declines*, not accepted surface. The raw material is unusually good — §2.8.6's verdicts are normative and tool-computable, so a Bezel promise could be *mechanically checkable* where Go's is prose. The counterweight any proposal must state: a premature promise is worse than none, because freezing while the kernel is still gaining rules would freeze the wrong language. The lesson is about **naming the moment and the shape** — scope (source compatibility; explicitly not ABI), start condition, escape hatch (an edition boundary, which is why this needs this study's §4.1 for its teeth), and checkability.

**4.6 A canonical formatter — genuinely-open (smallest item, hardest expiry).** No formatter and no formatter design exists; proposal 0040 names `fmt` once, in an aside inside an open question. Two facts make it unobstructed: layout is definitively not parse-significant and was *just* re-decided — proposal 0100 (graduated v0.260) keeps layout non-normative and says of itself *"The blank line is style permanently … A future body-token proposal is a *token* proposal; the layout route is closed"*, with the v0.260 changelog putting the reopening bar at field evidence *"admitting the token space again but never the layout route"*, and the grammar is fully delimited, so a printer has no ambiguity to resolve. The cost curve is not merely steep but vertical — no language has imposed a canonical format after acquiring a corpus — and for a language whose pitch is the legibility of ownership markers, a canonical rendering of where those markers sit is load-bearing, not cosmetic. The load-bearing decision is policy (mandatory-in-CI vs advisory), cheap now and permanent later.

**4.7 Java's checked exceptions — negative-lesson-already-avoided.** §31.3 rejects the mechanism by name: *"Methods do not declare which exceptions they may raise. The compiler does not enforce that callers handle particular exception types."* Three rules independently foreclose the failure modes it was invented to prevent, which makes this avoidance rather than a shrug: stdlib §1's failure-signal rule assigns each condition one mechanism by *where consumption happens*, resolving upstream the pressure that produces `throws Exception`; §31.1 makes a caught binding a borrow, so no ownership obligation rides the propagation path; and §31.4 refuses the exception route for allocation failure because *"making every allocation a potential throw site would put an exception edge on every `new`"* — the checked-exception failure in Bezel's own vocabulary.

**4.8 C#'s unchangeable defaults — negative-lesson-already-avoided (cite as positive evidence).** Rationale §4.3 (*"non-nullability is the default, nullable types are opt-in via `?`"*), with no per-file enable possible since §2.8.5 declines conditional compilation (*"One source text, one meaning"*); rationale §12.3 (*"Bezel's runtime has no synchronization contexts in this version, so no opt-out is needed"*, with an honest caveat matching §18's deferral); §30.3's two-layer rule against sync-over-async (*"a blocking wait on an incomplete task is an error"* — lexical rejection plus a runtime guard, extended verbatim to blocking lock acquisition at §30.12); and `async void`, not merely discouraged but unspellable, since §30.1's return types are a closed list and axiom A6 closes the adjacent discard hole. C#'s most expensive async pitfall, closed structurally, in two places, by one rule.

## 5. Contracts and values — Eiffel, D/Zig, F#, OCaml/Haskell, Pony, Clean, Cyclone

**5.1 Eiffel's behavioural subtyping — already-have, and strongly.** The lane brief guessed the spec might be silent on override contract variance. **It is not.** §22.16 carries a seven-rule subsection: contracts are *"slot-bound"*, inherited verbatim and never restated; an override may add `ensures`; and *"**An override or implementation may not declare `requires` clauses.** Strengthening a precondition breaks every caller dispatching through the base contract, and no weakening syntax exists in this revision: the override's effective precondition is the inherited one, verbatim."* Multiple roots combine by disjunction on `requires` and conjunction on `ensures` — the Eiffel rule, for the same reason (rationale §9.8). Bezel's answer is *stronger* than Eiffel's: it forbids declaring `requires` at all and recovers the forced case through the multi-root rule. The one deliberate Eiffel residual is the refinement syntax, and it is recorded rather than merely absent: §22.16 rule 3 states the absence in the spec's own words — *"no weakening syntax exists in this revision"* — and the decline sits in rationale §9.8 (*"`require else`/`ensure then` refinement syntax is declined until demand materializes"*) with its reasons and revisit bar in proposal 0043 §17 (*"Declined for v1: inherit-verbatim plus add-`ensures` covers the dominant cases with zero new syntax … Revisit on demonstrated demand"*). **Cite this as evidence against the owner's worry, not for it.**

**5.2 Command-Query Separation — negative-lesson-already-avoided (actively wrong here).** Ownership egress makes command-and-query the *correct* shape: stdlib §4's `OwningSet<T>.Pop(query: T): owned T` mutates and returns because **the return is the ownership transfer**; a `Pop` that only mutated would leak or dispose the value. Stdlib §1's Try convention codifies the shape document-wide, so a CQS note would contradict `Pop`, `TryAdd`, and every `Try*` in the library. CQS's checkable half is already mechanized, and stronger than a convention, as §22.15's compiler-verified `pure`.

**5.3 Record invariants — genuinely-open (first rank).** Ada's constrained subtype, Eiffel's invariant, and F#'s smart-constructor DU say one thing: the type, not each construction site, is where a small value's validity lives. §22.16 scopes `invariant` to classes and records record invariants as out of scope; §27.8 simultaneously directs every author to model distinct scalars as single-field records; §9.5's `with` bypasses any constructor `requires`. **Bezel's own recommended newtype shape cannot state its own validity**, and the escape (promote to a class) costs allocation and disposal on a value that wants neither. New sharpening this survey contributes: §22.16's note names two instrumentation points; §9.4's admission of mutable body-form records (*"Mutable records are permitted but are inadvisable"*) makes a public setter exit a third, and §9.8's synthesized `Deserialize` arguably a fourth. Worked at this study's §6.

**5.4 F# units of measure — declined-with-reasons (recommended), at one pole only.** See this study's §1.2 and, for the three-pole treatment, its §6.2(c). The lane's own correction: the two properties services code buys — nominal distinctness and zero runtime cost — are *both available today*; what remains at the F# pole is derived-unit inference, whose habitat is scientific and embedded code. Maple's pole — units carried by the value, checked at evaluation — needs no language change at all and is already shipped in its single-dimension form as stdlib §2.5's `TimeSpan`. If the owner wants one item from this cluster, it should be record invariants.

**5.5 Newtype deriving (Haskell, Nim, OCaml) — already-declined (by adjacency).** `DECLINED.md`, D-0004's 2026-07-21 sweep: *"**Delegation-by-forwarding sugar** (Go embedding / Kotlin `by`): implicit method promotion hides the forwarding call and blurs receiver identity — squarely against announced-flow/no-hidden-magic … Revisiting requires evidence that forwarding boilerplate is a measured, recurring burden the one-line members do not adequately express."* The decline is written about delegation-by-forwarding, and the bridge to `deriving newtype` / Nim `distinct` is **the lane's reading, not the register's**: both are implicit method promotion at the one-field case, but GND derives a *conformance* by representational coercion where Kotlin `by` forwards to a stored delegate. As with typed modular arithmetic at this study's §1.4, the recommendation is to record the newtype-deriving form explicitly in D-0004 so the adjacency stops carrying the weight. Bezel already auto-derives what it decided is safe to derive (§9.2 equality with the v0.244 opt-out; §9.8 serialization by conformance) — the boundary is drawn, not absent.

**5.6 Pony's `val`/`trn` — deeply-immutable shareable graphs — genuinely-open.** §30.14's crossing rule is closed (moved or immutable) and the simultaneous-reach set is the compiler-known synchronized types plus the deeply-immutable `FrozenArray<T>` — so Bezel has `iso`, has `val` for exactly one compiler-known type, and has no user-declarable `val` and no freeze operation. The docs already call this the coming pressure — rationale §12.9: *"The likely first user pressure on that boundary is the **frozen class tree** (a build-once object graph shared read-only across domains: configurations, parsed documents, routing tables, compiled schemas)"* — and stdlib §6.11 states it as *"a recorded gap, not an idiom this section can supply"*. The cheap shortcut is foreclosed: rationale §12.13 declines a user-declarable trait because the facts are compiler-known trust grants, *"not self-certifiable structural properties"*. *Cost:* medium-to-high with a good pre-built shape — deep immutability wants to be ▲ a **derived type property** computed structurally like *sendable*, which is what §3.6's closing rule mandates and §12.13's decline forces. The hard parts are real: *construction* (a graph with back-references cannot be built by ordinary construction — what Pony's `recover` exists for, and Bezel has no ▲ freeze operator and no obvious place to put one under announced-flow) and *disposal ownership* of a graph reachable from several domains (§28.13 is domain-local and records that cycles leak). One derived property, one fact ruling, one construction story — not a new kind and not a new axiom.

**5.7 Failure-path cleanup — sync already-declined, async genuinely-open.** Rationale §17.11 declines `defer`/`errdefer` on three grounds, the third being that the failure half needs a predicate the language lacks (*"are we unwinding?"*), and stdlib §2.21 ships `ScopeGuard`, which *"requires no compiler support"*. The residual is the async half, recorded as an out-of-scope note rather than a decline: *"`AsyncScopeGuard` is deliberately not provided: an `await`-ing cleanup would need `IAsyncDisposable`/`await using` and a `() -> Task` action whose invocation from a synchronous disposal path spec §28.14 rejects — recorded as out of scope, not overlooked."* One sharpening, flagged as the lane's reading and not the document's: the blocker names a *synchronous* disposal path, but §28.12 already provides `await using`, so the real question is narrower — whether §28.14's storage-bounded-capture forms admit a `Task`-returning callback, which the note does not answer. *Why it matters:* failure-path undo in a service is overwhelmingly asynchronous (release a lease, delete a half-uploaded blob, cancel a reservation), and today it is a hand-written commit-flag `try`/`catch` — the shape `ScopeGuard` exists to remove, and the shape that goes wrong under §31.2's later-wins supersession, where a throwing async undo buries the original failure. *Cost:* low-to-medium and stdlib-shaped *if* the §28.14 ruling is yes; a §28.14 amendment if no.

**5.8 Uniqueness polymorphism (Clean) and regions (Cyclone) — genuinely-open (XL); base already-have.** The base first: Clean's uniqueness *is* Bezel's affine ownership plus §15.3 move-only value types plus §28.8's single `move` marker; Cyclone's regions are covered by static borrow lifetimes plus §28.14's `scoped` bounding (A11) plus §28.10's `using var` pin (A5) — no region variables are needed, because there is one region kind and a bounding-object rule for the rest. Cyclone's arena half is separately deferred with a reopening condition. What is absent is the *polymorphism*, named four times as the blocker for four features: owning `Result` combinators (0075 stage 3(a)); rationale §11.4's four-things-at-once list; axiom A14's bar on `owned` generic arguments; axiom A9's two collection families with LINQ-over-owned as the matching stdlib duplication. **This survey's contribution is the aggregate** — nowhere is that total cost stated in one place. It is known to be high: rationale §10 records the retired `<owned T>` attempt as a mechanism that *"made ownership a property of type arguments and drowned in substitution rules"*. The narrower recovery path is rationale §10's erasure insight (*"erasure touches only signature slots"*) — ownership polymorphism at parameter and return positions only, which is all a combinator needs; any proposal must name A14 as its extension point.

**5.9 Zig's explicit failure flow — already-declined, with the residual stated.** Rationale §11.4 confronts the maximal Zig/Rust position and declines it on two grounds: the classification test is *where consumption happens*, not information content (routing environmental faults through `choice` returns *"would evacuate the environmental band into `choice` returns whose exhaustive matches every interior caller would then have to write"*), and constructibility (a `Result`-first Bezel needs ownership-polymorphic combinators — this study's §5.8 — a propagation operator, sendable payloads, and a governed vocabulary, *"each … missing or expensive under landed rules"*). The residual this survey states out loud: **Bezel has bought Zig's legibility of resource flow completely and declined Zig's legibility of failure flow entirely**, with stdlib §1's five bands as a documentation-level substitute for what Zig gets from the type system. A coherent position with a recorded reopening bar — and the largest single place where the announced-flow doctrine does not reach.

### 5bis. The outer ring — briefly

Eight entries, probed after the owner's mid-draft question. Seven of the names return **zero hits** anywhere in the ten documents or the proposals folder (grepped at HEAD: occam, Euclid, Hermes, Lustre, Esterel, PL/I, Monte), so those verdicts rest on the mechanism and never on a citation of the language. The eighth is named once — MATLAB, in proposal 0064's sigil-prefix alternatives table — which moves no verdict here, since the Matlab rows rest on rationale §4.1 and §25.4, not on absence.

**occam / CSP — `ALT`, multi-source channel select — already in a register.** stdlib §6.9 defers *"cancellable and multi-source receive … a first-class primitive needs the same hand-the-owned-item-back protocol"*, and proposal 0060 consolidates the family as one design. A cross-reference, not a finding — and this study's §7.5(1) is its unblocking dependency.

**Euclid (1977) — ban aliasing for verification tractability — a footnote strengthening this study's §1.8.** Euclid restricted aliasing precisely so a verifier could reason about frames, decades before SPARK retrofitted the discipline onto Ada. Bezel has alias control natively, which is why this study's §1.8 states the opportunity as under-claiming rather than as a gap.

**E / Monte, with Pony's authority side — no ambient authority — genuinely-open at the *question* level only.** Bezel's I/O entry points are ambient: stdlib §7.3's `File` is a static class whose `public static method ReadAllText(path: string): string` needs no capability object, and nothing in the five registers addresses ambient authority ("object-capability", "capability-secure", "ambient authority" return zero hits). The near-misses concern ambient *dependencies*, not authority (D-0001's container decline; 0021's Fork A; 0002's rejection of an ambient per-request context), so the absence is honest. **The recommendation is not a feature**: full ocap is a different language, and the survey expects a recorded decline-with-reasons. *Cost:* near zero as asked here (one rationale entry); unbounded if ever answered affirmatively, since a capability discipline reaches every I/O entry point in the stdlib. The narrow salvage is a supply-chain-era rationale note — what Bezel does and does not promise about what a linked artifact can reach — composing with this study's §2.1 unsafety attestation. Convergent validation the other way: E's *vat* (a single-threaded event loop owning its objects, only immutable or copied data crossing) is §30.13's execution domain, arrived at independently.

**Hermes / NIL — typestate — already expressible as a pattern.** A compile-time protocol state machine is writable today from affine ownership: §15.3's move-only value types, where *"Assignment transfers the value from source to destination, leaving the source in moved-from state. Reading from a moved-from location is a compile error"*, and, for class-typed states, an `owned` parameter consuming the old state with an `owned` return minting the next (§28.1, §28.8). Honest limit: there is no consuming *receiver* (`owned this`), so a transition is spelled as a method taking the value as an `owned` parameter, not as `state.Next()`. Actionable item: a **guide section candidate**, not a feature.

**Lustre / Esterel — the determinism lineage — cross-reference.** §30.13's *Determinism* paragraph (proposal 0045, graduated v0.204) makes a domain's execution a deterministic function of its enumerated edges — the property record/replay needs, and the one synchronous languages were built around.

**Maple — the third pole on units, surfaced by the owner's 2026-08-19 question.** Maple is Pascal-descended in surface (`proc`/`end`, `:=`) and tackled units at a pole neither survey lane had priced: the dimension is carried *by the value*, checked at evaluation, with conversion as an explicit boundary operation. That pole needs no language change, and stdlib §2.5's `TimeSpan` is its degenerate single-dimension instance, already shipped. The three-pole record is at this study's §6.2(c); the recorded decline reaches only F#'s type-level pole.

**Matlab / Mathematica — out of domain, two honest notes.** (1) *Copy-on-write value semantics* is a road already taken and declined where it was live — rationale §4.1 weighs *"value-type strings with copy-on-write"* and rejects it because it *"silently allocates on every concatenation"*; the general question is settled by §3.2's total value/reference split plus §28's single-owner model. (2) *Silent broadcasting* is the negative lesson §5.1's posture already avoids: a value converts implicitly only *"when no programmer-visible information is lost"*, and §25.4 admits no user-defined conversions at all.

**PL/I — everything for everyone — the negative lesson the registers stand as a refutation of.** Bezel's answer is not restraint in the feature count (this study's §2.5 is candid that the language is large); it is that every feature carries a record, and five registers exist to say no with reasons.

## 6. Deep dive I — the constrained-types cluster

**Bottom line.** The seed impression that this is "possibly the biggest genuinely-open item, unifiable with Bezel's contract tiers" is **half right, and the wrong half is the expensive one.** Bezel already has the distinctness mechanism, the prover fragment that would discharge range obligations, and the tier machinery to carry the check. What it lacks is narrower than "constrained types": a **constraint slot on a value kind**, and a way to make a value kind **non-fabricable**. Split the cluster; do not promote it as one.

### 6.1 The baseline — where each nearest feature stops

| Nearest feature | Where it stops |
|---|---|
| **Type aliases** (§27.8) | *"A type alias is a pure synonym — it does not create a new type."* No distinctness, no constraint; module-internal, so it cannot appear in a public signature (`public type` is a §18 deferral). |
| **Single-field records** (§27.8's own prescription) | Distinctness ✓. Constraint ✗ — Appendix A.3's `RecordDecl` admits no `ContractClause`. |
| **`requires` on an explicit constructor** (§22.16; A.4 admits `ContractClause*` on `ConstructorDecl`) | Works, and is the real answer today — but guards **one** producer. |
| **Class invariants** (§22.16) | The one construct that says "every value satisfies P" is class-only; A.4's `InvariantDecl` is *"class bodies only; rejected semantically in records and static classes"*. A scalar wrapper must not be a class. |
| **The prover fragment** (§22.16 / D.2) | *"linear integer arithmetic over parameters, fields, `result`, and `old` captures"* — already fixed, already exactly a range wrapper's obligations. The floor is the constraint: *"exactly two things inhabit the proven tier"*. |
| **`Range<T>` + `in`** (§16.3; stdlib §9.8) | `public method Contains(value: T): bool;` — **no `pure` marker** (contrast stdlib §2.2's `public static pure method Abs`). §22.16's clause-typing rule admits a clause expression only under the pure-body rules of §22.15, whose rule 6 (*"Calls to pure members"*) permits a call only where the member is `pure`-declared or pure-classified — and pure-classification reaches only compiler-**synthesized** bodies (§22.15, *Members classified by rule*), so an intrinsic with an authored signature is not rescued by it. **`requires(port in 0..65535)` therefore does not compile today.** |

**The fabrication back doors — the heart of the matter.** §9.5: *"`with` copies field values directly; it does not invoke the record's constructor. A constructor that validates cross-field invariants … is not re-run during `with`."* §17.11 defines `default(T)` for *"Records all of whose declared fields are defaultable"* — fabricated at storage level. §14.2: *"Inside the generic body, `new T()` for a value substitution is equivalent to `default(T)`."* §9.8: a record declaring no explicit constructor is *"constructed directly from the read components at the storage level"*. Two are closable by hand (private auto-property storage closes `with` externally; an explicit constructor closes §9.8's path). **`default(T)` and `where T: new()` are not closable at all** for a pure-value wrapper — and stdlib §1's Try shape (c) *mandates* the fabricating producer: *"`TryX(..., out result: T): bool` with `default(T)` assigned on the false path"*.

**Two register facts bound the space.** §25.4 forbids user conversion operators, so any distinct wrapper costs an explicit factory call at every literal, permanently. And §3.6's closing rule — *"New rules added to this specification that need a structural classification of types must define it as a derived type property under the rules of this section, rather than introducing a parallel mechanism"* — governs any option that classifies types. **The Ada distinction the seed collapsed:** Ada ships *two* mechanisms, a constraint subtype (implicitly interconvertible, zero call-site cost) and a distinct derived type; Bezel's alias is neither and its single-field record is the second only. So the gap is **the constraint half** — and the `subtype`-shaped option is foreclosed independently by §25.4, since free interconvertibility is that option's whole value.

### 6.2 The options, priced

**(a) Contract-carrying type aliases ▲ — decline as spelled.** Three blockers, any one fatal: aliases *see through* (§27.8 — identity, equality, dispatch, overload resolution), so a constrained alias buys range safety and *not* nominal safety, the half a services language needs least; aliases are not exportable, so the feature could not appear in a public signature without lifting a deferral in another subsystem; and there is no conversion boundary to check at, so the check would land at assignment/argument/return positions by a new rule invented for the feature — precisely the parallel mechanism §3.6's closing rule forbids. Its useful content is subsumed by (d′).

**(b) Derived numeric types / operator synthesis — promote, sequenced after (d′).** As a new kind this costs a §3.1 row plus a full storage/generics/serialization/FFI treatment; as sugar over a single-field record it collapses into the one missing thing, **operator generation**. Bezel already generates equality, `ToString`, serialization by conformance, and whole conformances for the primitive tower — it has never pointed that machinery at arithmetic. **Ada's lesson here is negative and Bezel is already on the right side of it:** Ada's derived type inherits the *full* operator set, so `Meters * Meters : Meters` is dimensionally wrong, while Bezel inherits nothing (§25.2: *"Parameters match operands **in order** — there is no automatic commutation"*) and the stdlib's own dimensional type is written on the correct split — `TimeSpan + TimeSpan : TimeSpan`, `TimeSpan * double : TimeSpan`, the crossing operation on the *other* type as `DateTime - DateTime : TimeSpan`, and no `TimeSpan / TimeSpan : double` declared at all. Bezel already does hand-rolled dimensional analysis for the one dimension it ships. The obstruction: stdlib §2.19's `INumber<T>` is closed under `T` (`static operator /(a: T, b: T): owned T`), which a dimensional wrapper cannot honestly witness, so synthesis needs a prior ruling on a closed-subset numeric interface ▲.

**(c) Units of measure — three poles, and the decline reaches only one.** The design space is not units-or-nothing (a framing the owner's 2026-08-19 question corrected, via Maple — a Pascal-descended surface, `proc`/`end`, `:=` — which tackled units at a different pole entirely):

- **(i) Type-level erased units** (F#): unit exponents in the type, checked statically, erased at runtime. **Decline with reasons**, recorded §18-style. Two prerequisites are §18 deferrals (associated types; const generics); the stdlib records the same wall from the other side (`Average` blocked because *"no constraint expresses that mapping"*); and §14.6 removes the *normalizing* route — the argument worked at this study's §1.2, where the inert encoding escapes the rule and degenerates, so the decline stands on the two deferrals and the consequences below, never on §14.6 alone. Easy under monomorphization-without-reflection (erasure is free; no reflection to leak a phantom); hard everywhere else — §9.8 would see only the `double`, §32.13's typed-handle admission excludes `double` single-field records, and §2.8.2 identity would carry a unit-expression argument whose textual identity is fragile.
- **(ii) Value-carried runtime units** (Maple's Units package): the dimension travels *in the value*, arithmetic checks at evaluation, and conversion is an explicit boundary operation. **Expressible today with zero language change** — a value record carrying a dimension vector, §25 operator overloads doing the check, and explicit conversion members, which is exactly §25.4's posture rather than a fight with it. The degenerate single-dimension case is **already shipped**: stdlib §2.5's `TimeSpan` is a record whose producers name the unit (`FromDays`/`FromHours`/`FromMinutes`/`FromSeconds`/`FromMilliseconds`), whose readouts name it again (`TotalSeconds` and kin), and whose operators are declared on the dimensionally correct split (`+`/`-` closed under `TimeSpan`; `*` by a `double` scalar).
- **(iii) Nothing** — the status quo for every other dimension.

*Services relevance.* The unit bugs that bite services are parse-boundary duration and size confusions, which pole (ii) addresses adequately; dimensional algebra (m/s²) is out of domain. The one actionable residue is a possible small stdlib addition — ▲ a parse-and-carry byte-size type for config work — recorded as a low-priority candidate in this study's §9; a repo-wide grep at HEAD found no such type in the stdlib and none in the proposal queue (0008's integer toolkit, 0012, 0015 and 0016 checked explicitly), so the absence is honest.

**(d) Do nothing, priced honestly.** Against `Connect(host, port, budget, timeout)`: `timeout` is free (stdlib §2.5's `TimeSpan`); the other two must be written. **This is today's fully-hardened pattern — current sanctioned Bezel, reproduced as this study's one illustrative block, not proposed surface:**

```bezel
public record Port
  private readonly property V: int;                 // private storage ⇒ `with` inaccessible externally (§9.5)
  public pure property Value: int => V;
  public pure constructor(v: int)                   // band-1 assert tier: `new Port(8080)` — no factory dual (stdlib §1's no-dual rule)
    requires(v >= 0 and v <= 65535)                 // §22.16; the `in` spelling does not compile (this study's §6.1)
    V := v;
  end constructor;
  public static pure method FromOrNull(v: int): Port?;   // band-2 branch tier — stdlib §1's *OrNull tier (§9.9 precedent); body elided
end Port;
```

~8 lines for `Port`; ~20 for a `Money` (validation, `+`, `-`, unary `-`, `*` by `decimal` in *both* operand orders under §25.2's no-commutation rule, the comparison group, the co-declaration obligation). Call sites pay `new Port(8080)` forever. **The residuals are the honest measure, and they are not ergonomic:** (1) `default(Port)` is a valid `Port` that never met the clause — benign here, not for a percentage, a non-empty string, or a currency-tagged amount; (2) `where T: new()` admits it and §14.2 makes `new T()` *mean* it; (3) Try shape (c) actively produces it; (4) §9.8's `Deserialize` *does* run the explicit constructor, so decode validates — but faults with `ContractViolationException`, a band-1 bug report, at a band-2/3 decode boundary. So (d) is not free: its residual is a soundness hole in the one guarantee the wrapper exists to provide.

**(d′) Record invariant members, with non-defaultability falling out — what the analysis actually points at.** ▲ No new type kind, no new conversion rule, no prover work:

1. **Lift §22.16's recorded out-of-scope item**: admit an `invariant` member in record bodies, instrumented at the points §22.16 *already names* — *"constructor-exit plus a `with`-update instrumentation point"* — closing producers (1) and (4) by construction, positional records included.
2. **Let non-defaultability fall out of existing machinery.** *defaultable* is already a §3.6 derived property, computed never declared. One clause — a record carrying an invariant member is not defaultable — closes `default(T)`, closes `where T: new()`, closes `serialized skip` (§9.8 already errors on a non-defaultable skipped component), and forces Try shape (a) instead of (c). It is exactly the shape §3.6's closing rule mandates, and the precedent is already inside §3.6's own *defaultable* row, at member granularity: a non-nullable value type is defaultable only if its components are, *"the primitives, the unit type, an enum **declaring a zero-valued constant**"*, with *"an enum with no zero-valued constant"* listed as not defaultable. That is a **member-level declaration, inside one kind**, that the author flips either way by adding or deleting a member — structurally identical to (d′), and already normative. (§17.11's *"no choice type is defaultable"* is the secondary precedent: it keys on the type *kind*, so it shows a whole kind being non-defaultable, not a member flipping the property within one.)

   *The counter-reading, stated because this is the survey's first-rank finding.* §3.6 rule 1 forbids a property being *"asserted, opted into, or **waived** by annotation"* — and under (d′) an author obtains non-defaultability by *writing* an `invariant` member and waives it by *deleting* one; in the degenerate `invariant(true)` the member has no other effect at all. *The answer:* rule 1's target is **annotation** — a marker whose entire content is the assertion — whereas an `invariant` member carries a predicate the §22.16 instrumentation points actually evaluate, so it has independent checked effect; nothing in §3.6 keys on whether a member is semantically load-bearing, and §22.16 already tolerates a trivially-true clause (its proven tier is defined over *"a **constant expression** … folding to `true`"*). The enum precedent above is the same shape and settles it: a zero-valued constant is likewise a member an author may add solely to obtain defaultability.
3. Optionally, a clause slot on the record declaration so a positional record can constrain its generated primary constructor without being rewritten into body form.

Everything else the cluster wanted then follows from the tier system in place: the clause is **checked** by default, `static` demands the proven tier, and the D.2 fragment already discharges linear integer range reasoning — so a record invariant is a plausible candidate for the language's first genuinely *proven* authored clause.

## 7. Deep dive II — the partial-failure story

**In one line.** Bezel has world-class fault **containment** and no fault **recovery** — and the recovery gap is not one hole but four, of which the smallest and cheapest (a cross-domain stop signal, by a single *fact ruling* on machinery that already exists) unblocks the other three. The seed impression is confirmed and understated: **the supervision question has never been asked in any of the five registers**, which is a different and more interesting fact than a decline. It is not fighting a reopening bar; it is filing an unasked question.

**7.1 The baseline.** *A spawned task throws and nobody awaits it:* the bare discard is a compile error whose message *"names `Task.FireAndForget` specifically"* (§17.13), and the sanctioned idioms then split (§30.10) — `FireAndForget`, where *"exceptions thrown by the task are logged"*, versus `using var t := call();`, where *"any exceptions it raises are silently swallowed"* — with one stated exception the baseline should carry: in checked disposal mode a `DisposedAccessException` in an abandoned continuation is *"first **reported** through the same implementation-defined diagnostic channel as `FireAndForget`'s logging, then swallowed"*, which is the very channel this study's §7.5(2) wants exposed. *A domain's executor sees an unhandled exception:* out of the **entry**, the join raises `DomainFaultedException` carrying *"copies of the original exception's message and stack-trace text"* — detected, but only if someone awaits; out of **any other task**, §30.14's *Domain completion* clause (quoted at this study's §3.1) says *"logged, not propagated"*. Nothing kills, restarts, or quarantines the domain either way. At `Main`'s return, live domains are **abandoned**: *"the runtime signals no cancellation, runs no further continuations of theirs … their owned state is reclaimed by the process exit, not by disposal, and their pending effects are lost"* (§33.3). *Any recorded restart idiom:* none, on two separate greps kept separate. The supervision counts are this study's §3.2's (36 substring / 9 exact-token hits over the ten documents, every one task-level, catch-boundary, or a consumption locus). The *restart* grep is its own: `grep -oih restart <the same ten documents> | wc -l` returned **1** at this study's v0.262 pin — stdlib §8.1's `Stopwatch.Restart()`, a member retired at v0.290 (`Reset(); Start();`), so no `Restart` member remains. The one place the ceremony was measured is proposal 0032's worker-pool probe: *"supervision is lost"*, at *"~60 lines of ceremony for map-square-over-ints"*.

**7.2 The Erlang mapping, worked against ownership.** **DETECTION** — present but pull-based and un-multiplexable: one awaiter per child, and the dynamic as-completed set a supervisor needs does not exist (`WhenAny` needs a borrowing array stdlib §6.7's ruling forbids building from fresh calls; `WhenEach` consumes a fixed snapshot, so a restarted child cannot join an enumeration in flight). **CONTAINMENT** — the strongest suit, better than Erlang's on one axis: owned state dies with its task or domain *deterministically* by unwind disposal (§30.1 disposes an entry's `owned` parameters *"on every completion path (success, fault, and cancellation)"*), where the BEAM relies on per-process heaps and its `terminate/2` is famously unreliable on abnormal exit. Two sub-findings: **`Locked<T>` needs no poisoning** — a guard holder that throws releases by unwind, leaving the interior *logically* torn but structurally unaliasable (§30.12's interior is, in its words, *"reachable only through a scoped guard"*, and must be a sendable class so no borrow escapes), and Bezel has a better-shaped detector than Rust's flag in the class invariant, re-checked at the *next* public entry (§22.16 evaluates it at *"construction exit and the public entry and exit points"*), with two spec-stated limits (invariants are never evaluated on throw paths; checked-contracts mode is not the release default) — **not a soundness-adjacent gap**, memory safety is untouched, and the only defect is that the absence of poisoning is nowhere *recorded*. And **the restart-loses-the-mailbox worry dissolves**: a restarted worker cannot inherit its predecessor's `Channel<T>` (the inbox is owned by the dead domain and disposed with it), which is exactly Erlang's semantics too; ownership costs nothing here, it costs *shape*. **RECOVERY** — absent in both halves. Restart needs a capture-free factory (**already compiler-enforced**, free), a policy, backoff, an intensity limit, escalation (none exist), and critically a way to *stop* the old child, which Bezel cannot do across a domain boundary at all: stdlib §6.8 — *"There is no built-in cross-domain cancellation: `CancellationToken` is a borrow-bearing record and not sendable."*

**7.3 The correction that constrains every option.** **Ownership does *not* make forcible domain teardown good.** It makes the normal and exception paths good — already delivered — and leaves the asynchronous-interrupt path exactly as bad as `Thread.Abort`, which rationale §12.4 already declined: *"Forcible cancellation (Thread.Abort) is unsafe — it can interrupt code holding a lock, corrupt invariants, or skip cleanup."* §30.13's run-to-completion makes it worse, not better. **No proposal here may claim otherwise**; `brutal_kill` should be recorded as declined with §12.4's ground extended to domains, and the need routed to process-level supervision.

**7.4 Two surprising findings.** (i) **The hardest precondition of OTP supervision is already compiler-enforced** — §30.14's capture-free entry rule means a restart provably inherits nothing from the dead child, so Bezel is closer to a supervisor than it looks. (ii) **`Locked<T>` needs no poisoning *and* has a better detector than Rust's — but that detector is off in the default build mode**, an asymmetry worth exactly one recorded sentence.

**7.5 The ranked slate.**

1. **`Shared<CancellationTokenSource>` by fact ruling — own proposal, small.** Grant `CancellationTokenSource` the **synchronized** fact; `Shared<CancellationTokenSource>` then becomes sendable under §28.13's derived-set formula, whose growth clause was built to receive exactly this: *"Growth is governed by stdlib §1's fact discipline: a derived set grows only by a **fact ruling**, which states the facts it grants and confronts each derived-set consequence in its record."* Much machinery is already promised (§30.8 guarantees the token read is atomic and cross-thread-visible). The ruling must confront three nameable things: `Register(scoped callback)` firing across domains (queue to the registering domain, or bar it on shared-source tokens); the source-outlives obligation now spanning domains; and the other two derived sets (likely a **displacement-unbounded** grant alongside, as `Locked<T>` carries). Unblocks graceful shutdown, deadline propagation (the Go `context` lesson — one currency reaching everywhere), supervisor stop, and one of the two preconditions on proposal 0060's cancellable `Receive` (the cross-domain half; 0060's own recorded blocker — the hand-the-owned-item-back protocol on the cancel edge — is untouched). **High** on the move; **medium-high** that `Register` is as tractable as it looks.
2. **A reachable fault sink — very small, rides proposal 0021.** Every swallowed fault in this lane terminates in the implementation-defined diagnostic channel, and nothing exposes it, so a service's own log sink cannot see the faults the runtime swallows on its behalf. ▲ One stdlib hook; it is a §28.14 retention position, so it must join the capture-free register or be a §22.12 rule-4 `static readonly` sink on the `SharedEventSource<T>` precedent. **High.**
3. **Record the process-supervision posture — near zero.** The fail-fast band is already strong and deliberate (§31.4's allocation failure, uncatchable `StackOverflowException`, `Debug.Assert`, §33.3's exit code 70); what is missing is the *posture* — nowhere does any document say process-level supervision is the intended recovery unit for a Bezel service. Stating it settles what the language is *not* promising and would shrink item 5 from "build OTP" to "build the part OTP would not have delegated". A rationale §12.14 entry beside §12.12's shape map. **High** that it should exist; **medium** on where the line falls.
4. **A dynamic as-completed task set — small-to-medium, own proposal.** ▲ An owning set admitting additions while an enumeration is live; must confront §29.11's single-consumption rule and §30.15's at-most-one-consumption precedent. The missing detection primitive, useful well beyond supervision. **Medium-high.**
5. **▲`Supervisor` + ▲`RestartPolicy` — medium, own proposal, gated on 1 and 4.** Akka's history supplies the design constraint free: policy belongs to the parent *as a value*, never as child lifecycle hooks — and Bezel's grain already favours that, since a capture-free entry cannot carry supervision state. **Medium**: worth building, but only after 3 fixes how much of it is really wanted.
6. **Three riders, folded into whichever proposal opens first:** a sendable discriminant on `DomainFaultedException` (▲ a small sendable exit-kind enum as the dispatch surface, the fault's type name carried as diagnostic text only — restart policy is a function of the exit reason, a supervisor dispatching on any string must string-match, and string-matching is exactly the stringly-typed dispatch Bezel rejects elsewhere); the recorded no-poisoning note (this study's §7.2/§7.4); and a must-use-style warning on a `Domain.Spawn` join handle provably never awaited — §17.13's reasoning applied to the path it has not yet reached.
