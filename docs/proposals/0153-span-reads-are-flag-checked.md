## 0. Thesis

The documents disagree on one fact, and five open soundness routes hang on it. Stdlib §4.14 and §4.15 declare the span records as "purely user-level Bezel — no compiler intrinsic", with indexers whose bodies read `Buffer[Start + i]` / `Source[Start + i]`; rationale §5.15 says "`Span<T>` indexes through the buffer's indexer"; and §28.2's checked mode faults on "a property or indexer accessor invocation" on a logically-disposed instance. Read together, every span read is a member access on the span's backing `OwningBuffer<T>` or `Array<T>` and faults when that object is disposed. Spec §9.7 ("a span's buffer window is the canonical case" of an access path with "no per-access disposed-flag check"), §30.1 ("a raw span window has no disposal-tracked object"), the v0.180 instance-field record, K5.9 (v0.331) and the compiler (`bz_array_get` reads a disposed span's source and dies in ASan, `Ownership_Checks.cpp:10821–10830`) say the opposite.

This proposal decides for the first reading, as a design decision: **a read or write through a buffer- or array-backed span, or through an `IReadOnlySpan<TElement>` value over one, is a member access on the span's backing object, and in checked disposal mode it raises `DisposedAccessException` when that object is logically disposed.** Nothing new is added to the language: the stdlib's declared bodies already say it, and §28.2 already faults an indexer invocation on a disposed instance. What changes is that the spec stops asserting the opposite, K5.9 (whose sole ground was the missing backstop) is withdrawn as proposal 0149 pre-committed to do, and the four span routes the matrix left open close the way the same routes close for a class borrow: under the recorded clause each already sits in, with K4.1's flag as the backstop. The cost is one flag test per span access in checked builds and nothing in unchecked builds, which is the cost every member access through a borrow already pays.

## 1. Ground truth

### 1.1 The two readings in the text

- **No check (the controlling reading at v0.331).** §9.7, instance-field bullet (line 1454): a record-carried borrow "may be consumed through access paths with **no per-access disposed-flag check** (a span's buffer window is the canonical case). The checked-mode trust regime is therefore unavailable and the store is **rejected statically**." §30.1 (line 8112): "a raw span window has no disposal-tracked object through which checked mode could catch the dangle." K5's conjunct (ii) (line 6420): "(ii) fails in exactly three recorded shapes … or a surviving borrow is **span-carried** — read through a buffer window that consults no flag". K5.9 (line 6432), §28.3 *Span-carried borrows and the site-announced kills* (line 6771), K6.4 (line 6439), §29.4 (line 7920), the consume table's reading note (line 6376), Appendix C.3 (lines 11893–11894), §30.5's holds-borrows row ("for a span, no backstop", line 8221), §8.6 (line 1203: "a backstop a span's buffer window does not have"), the borrow-erasing bullet (line 1455: "a trust whose backstop a record-carried borrow lacks"), rationale §5.1's v0.331 exception, §5.15's v0.180 clause, §4.2's v0.329 paragraph, the code-generation reference §5 and §7.2, and `DECLINED.md` rows 31, 623 and 624 all state or rest on it — as do three declines whose reopening bars ask for exactly the check this proposal makes: row 34 (v0.329, proposal 0146: a trust clause for a span stored through an `Object` parameter, bar "a box realization under which every read of the payload's borrows is a flag-checked member access"), and rows 617–618 (v0.331, proposal 0150: a span `Task<T>` result, bars "reopened only with a backstop for a span window"). §4 item 3 answers all three.
- **Checked (the stdlib's declared mechanism).** Stdlib §4.14 (line 2779): "`Span<T>` is purely user-level Bezel — no compiler intrinsic. The record machinery, borrow lifetime tracking, and indexer dispatch are all standard language features." Its indexer (lines 2660–2680): `return Buffer[Start + i];` / `Buffer[Start + i] := value;`. §4.15 (line 3230) says the same of `ArraySpan<T>`, whose indexer reads `Source[Start + i]`. Rationale §5.15 (line 604): "`OwningBuffer<T>` … indexes through a bounds-checked indexer … `Span<T>` indexes through the buffer's indexer." Rationale §5.15's v0.105 record and stdlib §4.15's caveat both *rely* on the delegation (the span's reads route "through the array's own Count-checked indexer", `LlvmBackend_Assign.cpp:446`). §28.2 (line 6286): checked mode — "any instance member access on a logically-disposed instance — an instance method call …, a property or indexer accessor invocation, or a field access through the reference — raises `DisposedAccessException`". `OwningBuffer<T>` and `Array<T>` are classes.

The two readings cannot both be normative. The stdlib's bodies are the specification of what a span read *is*; §9.7's sentence is a claim about them that is false under the mechanism §28.2 already defines.

### 1.2 What the backstop requires, and that §28.2 already provides it

A span holds its backing *object*, not a raw pointer: `Span<T>(Buffer: OwningBuffer<T>, Start, Length)`, `ArraySpan<T>(Source: Array<T>, …)`. A read is `Buffer[Start + i]`: the backing object's indexer, bounds-checked against the object's live length (stdlib §4.15's caveat is exactly that an `Array<T>` may shrink under a span, and the read then throws rather than reading stale storage). The flag test §28.2 describes — "a flag test on member entry" — sits in front of the storage read, and §28.2 already gives the implementation the latitude the test needs: "the split between logical disposal and physical reclamation gives the implementation latitude to defer reclaiming a disposed instance's memory in checked mode (quarantine, delayed free) so that the flag remains readable after disposal." The compiler already does this for `Array<T>`: `bz_array_mark_disposed` quarantines the header and `bz_array_is_disposed` reads its flag (`src/runtime/bezel_runtime.h:121–128`, #621, v0.135), and a direct `arr[i]` is guarded in checked builds (`LlvmBackend_Assign.cpp:525–540`, `:1183–1191`). What is missing is the same guard on the span paths (§6).

So the check is not a new mechanism and not a new runtime object. It is §28.2's existing flag test, reached through the stdlib's existing indexer delegation.

### 1.3 The compiler today (`2679585`)

- `LlvmBackend_Assign.cpp:412–463`: `ArraySpan<T>[i]` / `ReadOnlyArraySpan<T>[i]` get — bounds-checked against the span's `Length` and the array's live `Count`, then `bz_array_get` with **no** `bz_array_is_disposed` guard. `:470–515`: the `__Buffer` (`OwningBuffer<T>`) get — bounds-checked, `bz_buffer_get_ptr`, no guard. `:1053–1200`: the setters mirror this (the direct array setter is guarded at `:1183–1191`; the span setters are not). `:744–760`: `move sp[i]`, no guard.
- `src/main.cpp:130–134`: checked disposal mode is opt-in (`--checked-disposal`), where §28.2 makes it the default. That is a pre-existing delta outside this proposal, noted for the tracker.
- `Ownership_Checks.cpp:10821–10830`: the comment that records the ASan SEGV in `bz_array_get` on a disposed span source — the observed behaviour of the unguarded path, not a design statement.
- `Ownership_Checks.cpp:13079–13160` (`checkConsumeFreeze`) and `:12145–12149` (`markDisposedByName`): K5.9 was never implemented (tracked as #5698's second half). No test pins a rejection of `xs.Dispose()` under a live span: `consume_site_freeze_span_1726_test.cpp` and `consume_site_freeze_span_reassign_1741_test.cpp` dispose after the span's last use; `localdecl_bare_const_arms_3591_test.cpp:561` pins a *return* of a span over a local, a static rejection this proposal does not touch.

### 1.4 The routes that hang on the answer

All four are span-only: the same shape with a class-typed borrow is admitted at v0.331 under a recorded clause with the flag as its backstop, and the matrix records each span cell as `missing` precisely because "the span read consults no flag".

1. **#5706 — a span over a field slot's current value, then a slot overwrite.** `var s := _buf.AsSpan(); _buf := new OwningBuffer<int>(4); return s[0];` (same body); `var line := frame.ScanLine(10); frame.Reset(); line[0]` (through a call, stdlib §4.14's own `FrameBuffer`); and the same span captured by a `ScopeGuard` callback (#5680's `this` arm). The class twin — `var r := _reader; _reader := new Reader(); r.Next()` — is K5.6's posture: "slots are not frozen, the displaced object is disposed and flagged, and a member access through the stored borrow afterwards is K4.1's deterministic `DisposedAccessException`" (§28.14, #5680).
2. **#5691 — a method-local collection of spans or frames.** `coll.Add(xs.AsSpan()); sink.Take(move xs); coll[0][0]`. The class twin is §28.11's store rule: "The residual is a K4.3-recorded trust clause … with K4.1's backstop as the named safety net".
3. **#5710 — an iterator frame over a parameter-sourced span stored in an owned field.** The class twin is the field-store residual plus K4.3's frame-held clause.
4. **#5709 — a synchronous lambda over a span passed to an `async` callee and invoked after its `await`, the source disposed before the task settles.** The class twin is §30.1's settlement clause, "with K4.1's backstop as the named safety net".

Under the no-check reading, route 1's through-a-call form has no static rule short of a receiver-exclusivity rule (every non-`pure` call on `frame` frozen while `line` lives), which is the borrow checker rationale §5.1 declined at v0.180 and which no body-local fact can discharge (the callee's body is not visible; a property getter is a call). Routes 2–4 each need a new K5.5 holder kind or a new K4.3 clause with no backstop to name, which K4.3 forbids.

## 2. Measurement

**Verdict changes.** The proposal rejects nothing new. It admits, at compile time, exactly what K5.9 rejected at v0.331: a site-announced kill (`xs.Dispose()`, `_ := xs;`, a direct `DisposeAsync()`) of a binding while a span over its value survives in a traced holder. K5.9's own measurement was "zero sites (gtest, lit, both corpora, the documents and the guides)", it was never implemented (#5698), and no rule-corpus case was written for it ("coverage gaps recorded, not written", v0.331). So the admission flips **no** test, **no** corpus row and **no** document example; the compiler already accepts the shape.

**Runtime changes.** In a checked build, a read or write through a span whose backing object has been disposed — a shape no test, doc example or corpus case exercises (`grep` over `tests/` for a span read after its source's `Dispose()` finds none; the `#2308` comment records the one probe, an ASan SEGV) — becomes a `DisposedAccessException`. In an unchecked build it stays undefined behaviour, as it is today and as a stale class-borrow read is.

**Cost.** One flag load and compare per span read or write in checked builds, in front of two bounds checks the read already performs (the span's `Length`, the backing object's live length). Unchecked builds elide it (§28.2: "implementations are expected to omit it entirely in unchecked builds"). Rationale §5.15 prices `ReadOnlyStringSpan`'s per-access overhead as "one range check, one width-dispatched read — negligible" where "the per-element cost is dominated by compare/branch logic"; the flag test is one more predictable-branch load in that class. The design intent for spans — zero-allocation views, no `ref struct` type kind, borrow tracking through existing machinery (rationale §5.15) — is untouched: the records, their shape and their static rules are the same.

**Sweeps.** `tests/conformance/rules/manifest.tsv`: no case's `rule:` header quotes any edited sentence (the `span` cases under §9.7, §4.14 and §4.15 state the field, static, temporary, `async`, `Object` and lifetime rejections, none of which moves; the two §28.10 cases that quote "site-announced kills stay unfrozen under their flag backstop" quote unedited text). Guides: Guide 05 §7 says a span "cannot sit in a class's instance fields or in any static field, or escape into async frames" — still true — and makes no flag claim; Guides 01 and 04 make none. The code-generation reference's one K5.9 pair (§7.2) and freeze clause (§5) are edited.

## 3. Options

- **A — keep the no-check reading (the status quo as controlling).** Amend stdlib §4.14/§4.15 and rationale §5.15 to say the indexer bodies are models over a window whose buffer access is unchecked. K5.9 stands. Then the four routes of §1.4 each need a static rule: route 1's same-body form a slot-overwrite freeze under a live slot-sourced span local; its through-a-call form a receiver-mutation freeze (every non-`pure` call on the receiver frozen while a receiver-sourced span lives) — a borrow checker in miniature, declined at v0.180 and not body-local; routes 2–4 a new K5.5 holder for local collections, a field-store rejection for frames carrying a span, and a task-local trace (0149's declined option D). Four rules, one of them unimplementable without exclusivity, to preserve a fact the stdlib's own bodies contradict.
- **B — span reads are flag-checked (recommended).** State once, at §28.2, that a read or write through a span is a member access on its backing object; delete the contrary statements; withdraw K5.9 (its ground is false); re-ground the rules that cited the missing backstop on the posture they also stated — a value type that holds borrows is stored past its bound at no position, each such position rejected statically (§9.7's instance-field, static-field and collection bullets, §30.1, §30.5) — keeping every one of them. Close the four routes as runtime-checked under the clauses their class twins sit in. One sentence of mechanism, no new rule, no new verdict.
- **C — B plus a receiver-mutation freeze** for route 1's through-a-call form, as belt and braces. Declined: it is option A's borrow checker, and under B the fault is deterministic in checked mode exactly as for a class borrow of the same slot (#5680's recorded posture).
- **D — B plus a same-body slot-overwrite freeze** under a live slot-sourced span local. Declined: K5.6 says "fields and collection slots are **not** frozen" for every borrow, with the flag as the reason; a span-only exception would re-key K5.6 on the holder's type with zero measured sites, the same non-uniformity 0149 declined for option B there, and it would catch the same-body form only, leaving the through-a-call form to the flag anyway.
- **E — B and retire §9.7's instance-field ban for spans now.** With the flag reaching span reads, a span in a class field could take the field-store residual. Deferred, not done: the ban is kept on the stated posture (no residual-trust storage of a value that holds borrows), the remedy (store the source, re-derive the view) expresses every measured program, the change reaches §9.7, stdlib §4.16, Guide 05, the code-generation reference and the compiler's #1251/#2308 legs, and the owner's direction prefers the narrow change. Reopening bar: a measured program that needs a span field and that the source-field remedy does not express; it is then a proposal, and the subtraction review is its natural venue.
- **F — B, and also trace a method-local collection as a K5.5 holder** (#5691's candidate rule, which this proposal declines against the issue's recommendation). Declined: a collection is a class object reachable through class borrows — an alias local, or a callee's stored plain parameter under the field-store residual (clause 3 admits a borrow of a scope-bound local passed to a storing parameter) — so a body-local trace of the binding cannot see every holder of its elements; that is K5.6's ground for leaving slots unfrozen, and it is what separates a collection from an inline-array local of spans, a value with no such alias, which K5.5 already traces. The trace would reject `coll.Add(xs.AsSpan()); sink.Take(move xs);` in the body that owns `coll` and still miss the same kill through any alias, while `coll.Add(item); sink.Take(move item);` stays under the clause. The collection-held clause with its domain obligation is the recorded home for both — which needs §9.7's collection bullet to say so (§4 item 4).
- **G — B, and keep K5.9 as a compile-time convenience.** Declined: rationale §5.1's v0.180 decline of freezing an explicit `Dispose()` under a live borrow ("a de-facto borrow checker for no soundness gain (the backstop is real)") applies to a span once its backstop is real; keeping the freeze for spans alone keys K5's conjunct (ii) on the holder's type with no backstop difference, and zero measured sites separate it. The cost of declining is real and recorded: in an unchecked build `var s := xs.AsSpan(); xs.Dispose(); s[0]` moves from a compile error to undefined behaviour, exactly as `var r := xs; xs.Dispose(); r.Count` already is.

**Decision: B.** Four consequences, each recorded with its reason:

1. **The mechanism, stated once (§28.2).** A read or write through a buffer- or array-backed span, or through an `IReadOnlySpan<TElement>` value over one, is an instance member access on the span's backing object — the span's accessors read and write `Buffer[Start + i]` / `Source[Start + i]` through the backing class's own indexer — so on a logically-disposed `OwningBuffer<T>` or `Array<T>` it raises `DisposedAccessException` in checked mode and is undefined behaviour in unchecked mode, like every other stale member access. The span's own components (`Start`, `Length`, `IsEmpty`, `Slice`) touch no storage and fault on nothing; holding a span past its source's disposal is not itself an error, reading through it is — the posture of holding a borrow.
2. **K5.9 is withdrawn.** Its ground ("the kill's flag never reaches a span read") is false under 1. Rationale §5.1's v0.180 decline of freezing explicit `Dispose()` — "converts this section's recorded trade-off into a de-facto borrow checker for no soundness gain (the backstop is real)" — applies to spans as to every other borrow; keeping K5.9 would keep a rule whose recorded reason is false, which the project's own discipline (`DECLINED.md`: "where a row's summary and its authoritative record disagree, the record wins") treats as a defect. Proposal 0149 §3 said so in advance: "if it is decided for the check, K5.9 and its rationale exception are withdrawn with the decision". K5's conjunct (ii) returns to "exactly two recorded shapes" (K5.7, K5.8). **K5.5's frame-local trace stays**: a `move`, transfer or reassignment of a carried source sets no flag, and that half of 0149 never rested on the span.
3. **The rules that cited the missing backstop stand, re-grounded.** §9.7's instance-field ban, its borrow-erasing bullet, §8.6's two-position rule, §30.1's across-suspension rule and §30.5's `Task<T>` row each also state a posture the kernel can carry: *a value type that holds borrows is stored past its bound at no position* — every position whose lifetime its carried sources do not provably bound (a class instance field, a static, an escaping or wider-scoped collection, an `async` frame's parameter or result slot, a `Task<T>` result) is rejected statically for it, with the stdlib-certified `CancellationToken` the one recorded exception (§30.1, A10). Where a recorded trust clause carries one of its borrows indirectly — a frame (K6), a local collection's slot (§28.11), a slot read's current value (K5.6) — the clause's backstop now reaches a span read as it reaches any member access. That posture is what the texts now say; "no backstop" is deleted wherever it was the stated reason. No rule's verdict moves. Three recorded declines asked for exactly this backstop as their reopening bar — `DECLINED.md` row 34 (proposal 0146's trust clause for a span stored through an `Object` parameter) and rows 617–618 (proposal 0150's span `Task<T>` result, status quo and trust clause). Their bars are met, and each is **re-decided, not reopened**: the rejection stands on the same posture, and the rows are annotated so. That posture is, after this proposal, a stipulation of regime uniformity rather than a soundness ground — a span in a class field would take the field-store residual exactly as a frame carrying a span parameter already does when stored in a field (#5710) — and retiring the whole family together (the field ban, the `Object`-parameter store, the `Task<T>` result, the `async` parameter) is option E, deferred with a bar.
4. **The four routes close as runtime-checked, like class borrows.** #5706 (all three forms): K5.6's slot posture, the fault at the next read, no K4.3 clause (#5680's text widened from "class- or interface-typed" to every borrow of a slot's current value, a span over it included). #5691: the store is admitted by §9.7's scope comparison and the kill under it is §28.11's collection-held clause with its domain obligation — for the frame twin, the frame-held clause. §9.7's collection bullet said "there is **no trust residual for record-carried borrows**", which as written denies that clause to a span; it is narrowed to the store (the store still admits no residual) and states that a kill of a carried source after the store is the collection-held clause, and §28.11's store rule says the same from its side. Without that edit the route would be an admission with no comparison, no clause and no backstop, which K4.3 forbids. #5710: the field-store residual plus the frame-held clause, exactly as a frame over a parameter-sourced class borrow stored in a field. #5709: §30.1's settlement clause, whose named backstop now reaches the read; 0149's option-D reopening bar ("a span-carried source entering a task frame with no static rule") is therefore not met, and the row is annotated rather than reopened. **None needs a static rule.** The static rules that remain for spans are the ones that decide a bound (scope comparison at a local or collection store, the return bullet, the field and static bans, §30.1's parameter and result bans, the borrow-erasing rule, K5's freeze of the silent kills); they are untouched.

**Unchecked mode.** The question asked whether undefined behaviour there is acceptable for spans as it is for class borrows. Yes, and for the same reason: §28.2 defines unchecked mode as "the release-build relaxation of the default checked semantics — selected per build, never implied — not a different language", and every residual-trust admission in the kernel (K4.3's field-, collection-, comparer- and frame-held clauses, the settlement clause, K5.6's slot posture) already has exactly this shape. Under B a span's undefined-behaviour surface in unchecked mode is **the same set of residual-trust shapes a class borrow has**, no larger: every statically decidable span escape is still rejected at compile time. Under A the surface is larger and undetectable in *either* mode.

**Kernel classification (process §9).** No new axiom, no new clause. K4.1's backstop ("any later use through any alias faults deterministically") is read to cover a span read, which the stdlib's declared bodies make a member access; K5(ii)'s recorded-shape count returns from three to two; K5.6, K4.3's frame-, collection- and field-held clauses and §30.1's settlement clause are applied to a span-carried borrow as to any other. **Body-locality (proposal 0105 §1): no compile-time rule is added or altered** — the one rule removed (K5.9) was local.
