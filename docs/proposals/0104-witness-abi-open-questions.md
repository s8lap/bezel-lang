## 0. Charter and method

0103 left four technical questions open by name. This study resolves each on paper: problem stated with exact quotes, candidates enumerated, each priced against the spec's commitments, a recommendation with the doubt visible. The conformance bar throughout is 0103 §0's: §2.8.2 clause 2 — *"An external instantiation behaves identically to a same-module instantiation of the same generic at the same arguments"* — with §2.8.3 rule 4 pinning static state, recorded initialization, and runtime identity. Nothing normative is drafted; candidate rules are described and marked ▲.

## 1. Function-type identity under owned-erasure (0103 §3.3, "the genuinely hard part")

### 1.1 The problem, exactly

Three commitments jointly close every conversion site. §28.1's bare-type-parameter arm: at a value substitution *"the marker does not survive into a substituted function type's identity (`(owned T) -> ()` at `T = int` *is* `(int) -> ()`, [§27.1])"*. §27.1: *"The modifier is part of the type — `(T) -> ()` and `(owned T) -> ()` are distinct function types, and the same applies to the other modifier forms. Function-type compatibility requires modifiers to match exactly; there is no implicit conversion between modified and unmodified parameter slots."* And §27.1.1's variance rule converts nothing: *"Assignability under this rule preserves **identity**: the value is the same function object viewed at a compatible function type (like interface variance, [§12.9]), so function-value equality ([§27.7.1]) is unaffected by the retyping."* Hence 0103 §3.3's finding, this study's premise: *"A function value flowing between a shared generic frame and concrete code undergoes **no conversion at any site the type system can see**; there is nowhere to hang a reabstraction adapter."*

The observables any resolution must preserve are §27.7.1's **normative** equality: *"A **lambda** (closure) value equals only itself — reference equality on the closure instance. Two separately-constructed lambdas with identical source text are *not* equal, even if they capture the same variables"*; for method references, *"equality is defined on the (method, receiver) pair, so whether the implementation caches or re-allocates the underlying function object is unobservable."* The asymmetry matters: the method-reference rule grants representation latitude explicitly; the lambda rule is violated by any scheme under which a round-tripped lambda compares unequal to itself.

The FFI seam is narrower than feared. §32.5 admits *"Function types `(...) -> T` whose parameters and return type are themselves FFI-compatible"* at extern signatures and excludes *"generic type parameters"* — no bare-T-involving function type ever crosses. §32.8's plain-callback rule is an **argument-form** admission, not a value-representation pin: *"the callback must be a **static method reference or a non-capturing lambda**: both lower to a bare C function pointer with no environment"* — the compiler mints the bare pointer from the statically-known callee, and capture-bearing forms ride the compiler-synthesized `env` trampoline. No option below disturbs either path. §22.3's modifier slots are convention-friendly (`out` is already indirection-licensed: *"An implementation may pass a hidden reference, but a partial write must never be observable on the exception edge"*).

### 1.2 Candidate (a) — one uniform indirect convention for all function-typed values, language-wide

Every invocation of a function *value* (§27.7 — never a direct named-method call) adopts one canonical physical convention — arguments by address, return via caller slot — so `(int) -> ()`, `(T) -> ()` at any substitution, and `(owned T) -> ()` after erasure are one wire shape; nothing remains to adapt. This is Go's position from birth — closures are uniformly a code+environment `funcval`, which is why 1.18 generics faced no reabstraction problem (secondary-sourced). Sound here: equality untouched (values never wrapped), FFI untouched (this study's §1.1). **The price is the leak 0103 §5 item 4 named**: every concrete `Select(lambda(x) => x * 2)` in code that never touches a generic pays the by-address spill per invocation, and register-passing to function values is foreclosed forever. Taxing the whole language for a deferred alternative inverts 0103's disposition; (a) is a fallback, not a recommendation.

### 1.3 Candidate (b) — value-wrapping reabstraction thunks, and why the naive form degenerates

The Swift shape: wrap the concrete-convention value at generic entry/exit in a thunk exposing the erased convention. What must be engineered transparent, stated exactly: (i) §27.7.1 lambda equality — a thunk is a fresh heap object, so `=` must resolve through an **underlying-identity slot** every function value carries and every thunk propagates, or a lambda stored through a shared body into a field declared `(T) -> ()` (any generic container — illustrative; no stdlib type implied) and read back at `T = int` compares unequal to itself — a §2.8.2 clause 2 violation against specialization; (ii) the (method, receiver) pair carried through the wrap — the easy half, covered by the rule's own latitude; (iii) §27.1.1's retyping, which performs no conversion and so offers no wrap site — harmless only if wrapping never depends on retyping sites. All satisfiable without spec change (the spec states equality over values, not representations). What kills the naive form is **storage**: a `(T) -> ()` field in a shared layout has one slot, loaded by shared code and, through substituted member signatures, by concrete callers — so the stored representation must be canonical; entry-wrapped values cannot be stored wrapped, exit thunks appear at every read surface, each mint is a heap allocation (rationale §4.4 makes allocation failure fatal — new fatal sites through shared paths, 0103 §3.4's boxing objection re-arising), and double-wrap avoidance needs the identity slot anyway. Followed to consistency, (b) converges on "every value carries identity and a canonical entry" — (a) with extra allocations. Rejected in this form.

### 1.4 The worked resolution (b′) ▲ — reabstraction on the descriptor, never on the value

Relocate the adapter to the two places the compiler already controls, so no value is ever wrapped:

- **Consume direction.** A shared body *invokes* a function value whose type involves bare T through a per-instantiation **invoke adapter** in the witness descriptor ▲ — one entry per T-involving function type in the body's use set, minted with the instantiation's other descriptor material. The adapter takes (value, T-slots by address) and performs the substituted type's canonical concrete-convention call. Zero allocation; the value passes through the shared frame, is stored, and compares, unmodified.
- **Produce direction.** A closure the shared body *mints* at a T-involving type takes a per-instantiation **entry adapter** as its code pointer — no extra allocation (the closure allocates anyway; only its code pointer differs per instantiation). Method-reference formation inside shared bodies rides the same mechanism, under the spec's own precedent that formation sites synthesize adapters — §27.6: *"Formation may bridge representation-changing conversions by synthesizing an adapter at the reference site"* (the precedent is for the *mechanism* — formation synthesizes code; (b′) extends it to a same-type, representation-only occasion, an extension acknowledged rather than elided).

Each substituted function type's concrete convention stays canonical language-wide — non-generic code untouched. For **lambdas**, §27.7.1 then holds trivially: one closure object, reference equality, unwrapped on every flow path. For **method references**, the produce direction carries a real obligation (adversarially found, recorded here): §27.7.1 makes a static reference equal every other reference to the same method — *"A static (or extension-method) reference to `M` equals every other reference to `M`."* — so a reference to `T.Parse` formed inside a shared body (per-instantiation entry-adapter code pointer) and a reference to `int.Parse` formed in concrete code (direct code pointer) must compare **equal** at `T = int`, per §11.8's as-if-separately-compiled bar. With distinct code pointers, equality must resolve through a **method-identity token** carried in the function-object representation — a slice of the identity machinery this study's §1.3 charges against candidate (b), re-imported for method references only. It is licensed by the rule's own latitude (*"whether the implementation caches or re-allocates the underlying function object is unobservable"*) and costs one word per function object, but it is an obligation, not a triviality. Honest costs: the descriptor grows by the body's T-involving function-type use set per instantiation; the adapters are **residual per-instantiation codegen**, qualifying payoff (a) exactly as 0103 §3.3 conceded — and for minted closures the *capture layout* is per-instantiation too where T-typed locals are captured (witness-sized slots, sized from the descriptor; no new cost, but per-instantiation surface beyond the code pointer); the method-identity token above; and the site enumeration — every creation and invocation of a T-involving function value in shared bodies — is argued complete from §27's closed surface (calls §27.7, lambdas §27.3, references §27.6, retyping §27.1.1 which converts nothing) but not proven.

### 1.5 Candidate (c) — scope restriction, and the recommendation

(c): shared codegen is not offered for bodies with function-typed positions involving bare T; those instantiations stay monomorphized. For D this is the natural first stage: the seal **rejects** such a body with a diagnostic naming the member and the shape — the compile-time-never-runtime discipline of 0103 §7 item 2's generalized fallback sentence, avoiding Mono's gsharedvt runtime-failure mode (0103 §6 row D). The scope cost, plainly: function-typed T positions are the signature shape of the entire stdlib §5 query surface, so under (c) the most generic-heavy code in the corpus stays monomorphized — acceptable for D's evidence-gathering charter, corrosive for C's.

**Recommendation (a staged pair): (c) as D's first stage; (b′) as the recorded full resolution for C/E and D's lift. (a) declined (language-wide tax); value-wrapping (b) declined (equality-transparency engineering plus allocation-bearing fatal sites, degenerating into (a)).** Confidence: **medium-high**. The doubt: (b′)'s site enumeration is argued, not mechanically verified; the method-reference identity-token obligation (this study's §1.4) is stated, not designed; and no adapter-invocation multiplier has been measured on bezelc (0103 §5 item 1's flags apply). If (b′) fails adversarial review, (a) is the sound fallback and its tax must then be re-priced, not assumed away.

## 2. The `Weak<T>` bitwise-move question (0103 §7 item 4's named pre-measurement)

### 2.1 The finding that dissolves the question

0103 §7 item 4 required *"the `Weak<T>` bitwise-move question (§28.9's lifecycle latitude) that decides whether the transfer entry is memcpy"* — the worry being a runtime free to hold interior pointers into `Weak<T>`-typed *slots* (a registry of weak locations), making a witness move a fix-up operation rather than memcpy.

**The question dissolves at the spec layer: `Weak<T>` is not within §28.9's latitude at all.** The lifecycle sentence — *"The implementation of runtime-managed types' lifecycle (reference counting, region allocation, or other) is not part of this specification"* — governs the runtime-managed set (`string`, boxed values, function values). `Weak<T>` is not in it; §28.13 places both handle types in the ordinary class regime: *"**Handles are ordinary owned class instances.** Every rule of this chapter applies to a handle unchanged"*, and *"Weak handles are themselves ordinary owned class instances and are disposed like any other."* A `Weak<T>`-typed slot holds an ordinary class reference; what is compiler-known is *behavior*, not representation — stdlib §2.16: *"Both types are compiler-known; the shared count and last-one-disposes behavior are not expressible in user Bezel."* The weak mechanism (liveness, upgrade, zeroing) is **target-side**, in the stable-address heap structure the handle references; no rule anywhere hands the runtime a *storage location's* address, and every existing relocation of references — assignment, `move`, §15.2 collection growth, §22.3's hidden-reference latitude — already presumes location-independence.

### 2.2 The implementation, checked

bezelc agrees, verbatim (comments at the v0.261 snapshot). `src/runtime/bezel_runtime_shared_weak.cpp`: *"Control block layout: { void\* value; atomic\<long\> strong; atomic\<long\> weak; void (\*dispose_value)(void\*); bool disposed }"*; *"Handles (strong and weak) are both pointers to this struct; the compiler passes them as `ptr` and calls the functions below."* `src/runtime/bezel_runtime.h`: *"Shared handles (bz_shared_t\*) and Weak handles (bz_weak_t\*, which is the same struct) are opaque to Bezel code; codegen stores them as plain ptr."* Liveness is a count in the heap control block; `bz_weak_try_upgrade` CASes the strong count there; no registry of slot addresses exists anywhere in `src/runtime` or `src/codegen` (searched). Moving a `Weak<T>` value is moving one pointer. (Hygiene note, not this study's to fix: the `.h` comment still says *"unsynchronised — domain-local per spec §28.13"* while the `.cpp` records the v0.140/#689 atomics upgrade; and the `.cpp` layout comment itself has drifted — the shipped struct carries two flags (`int value_disposed; int8_t handle_disposed`, the #627 checked-mode quarantine split), not the single `bool disposed` the comment says. Neither drift touches the pointer-handle finding.)

### 2.3 The commitment to record ▲

**Resolution: record bitwise-movability as an invariant, not a move witness with fix-up.** Candidate invariant ▲, Appendix-C-adjacent in 0103 §8's manner: *a stored value's bit pattern is location-independent — no runtime mechanism may key on the address of the storage location holding a value, so relocating any Bezel value by copying its representation and abandoning the source preserves semantics.* This already holds for move-only values (0103 §3.1's transfer row: relocation is bitwise because moved-from is static — no drop flags), and a fix-up registry would be exactly the *"hidden per-type runtime"* shape whose retraction rationale §5.28 records (0103 §1.4) — declined on recorded temperament, not just cost. Scope stays as 0103 §3.1 drew it: this governs the **move** entry only; the **copy** entry remains lifecycle-aware and is not assumable memcpy. And the invariant carries its presupposition on its face (adversarial sharpening): location-independence is claimed **at admitted move points only** — interior borrows into value storage (a span over an inline array, a `ref` slot) are address-dependent while live, and it is §28.3's consume-site freeze, not this invariant, that guarantees no such borrow is live across a move; dropped, the presupposition yields an immediate span counterexample. What the invariant purchases against the future, said plainly: it fences §28.9's latitude away from *moving/compacting* allocators for the runtime-managed types (which would need to locate references in slots). Nothing in the corpus contemplates one; if one is ever wanted, this invariant is the recorded decision to reopen. Confidence: **high** — spec, stdlib, and shipped runtime agree, and the fenced-off alternative's shape carries a recorded decline.

## 3. The uniform virtual-slot ABI (0103 §3.4's generic-virtual bullet)

### 3.1 The surface and the product, re-located

The surface is normative and cannot be declined away. §12.1: *"A method, property, or indexer is non-virtual unless marked `virtual`"*, with override matching exact up to one recorded allowance — *"with one allowance: an override may declare a parameter as `T?` where the overridden member declares `T`"* (contravariant nullability widening, monotone down the chain) — and otherwise strict: *"Parameter modifiers that must match: `ref`, `out`, `owned`, `scoped`"*; *"Return types must still match exactly (no covariance in this version)."* Generic methods participate: §14.2's *Constraints on overrides and interface implementations* opens *"An `override` of a generic method, and a method implementing a generic interface member, **inherits the overridden or implemented declaration's constraints**"* and closes with the commissioned sentence, re-located here (§14.2, v0.261): *"dispatch flows through the base or interface signature, so its constraints are the only ones call sites are ever checked against — an *added* constraint on the override would go unenforced at every virtual call (unsound), and a *weakened* one would advertise admissions the dispatch surface never grants."* Two structural gifts fall out: every override carries the **same constraint set** (admission is decided statically at the call site; the slot never re-checks), and the call site always **knows the type argument statically** (§14.5's inference is expression-local, 0103 §2; §17.10 accepts only closed instantiations, rationale §5.18 via 0103 §3.4 — no construct produces a type argument at runtime).

The product problem is 0103 §3.4's: under monomorphization, a virtual slot for `M<U>` at `U = int` must exist on every conformer — including ones in artifacts that never saw `int` — a (conformer × instantiation) product no compilation sees. It is live in-tree: bezelc's #580 machinery (comment, `src/codegen/LlvmBackend_impl.hpp`) records that *"a VIRTUAL generic method call cannot dispatch through the fixed vtable slot (the slot holds the i32-erased template, so a non-int type argument is passed at the wrong width/representation — a miscompile)"*, and its shipped answer — *"The dynamic type is one of a statically-known finite set (the static class and its subclasses). Emit a dispatch-by-descriptor: load the receiver's td (vtable[0]), and for each candidate class call the monomorphized override it most-derives"* — enumerates candidates from **one compilation's view**, the exact shape that cannot see a conformer another artifact adds. (Read from the machinery; no cross-artifact miscompile is asserted — that path is gated off anyway, 0103 §4.1 item 2.)

### 3.2 The sound layout, worked per design

**Under C: one slot per generic virtual member, uniform convention, instantiation as argument.** The slot's convention ▲: (receiver, one static descriptor per method type parameter, then the member's slots under this study's §1's canonical convention, §28.1's erasure read per category). The **caller passes the descriptors** — it always has them statically (this study's §3.1) — so the CLR's per-call runtime lookup, which 0103 §5 item 1 records as AOT-unavailable, is simply unnecessary: the CLR needed it because its shared code lost the instantiation's identity; a Bezel call site never does. **Who mints slots:** the declaring base/interface's compilation assigns the index with the rest of its vtable/itable; each conformer supplies exactly **one** uniform-convention body per override (its shared body, which C emits for every export anyway) — and §12.1's nullability-widening allowance is absorbed **override-side**: a body that widens a bare-`U` parameter to `U?` wraps the incoming value through the passed descriptor's `T?` companion entries (0103 §3.1's row) at its own entry — cheap, override-local, and priced here rather than elided. (A function value formed *over* a generic virtual method — `obj.M` with `M<U>`'s argument fixed at the formation site per §14.5 — binds the descriptor at formation exactly as it binds the receiver; later invocations dispatch with the stored pair, adding no lookup.) **Where the closed-instantiation-set invariant bounds:** not in the table — the table is (conformer × member), finite per hierarchy; the instantiation axis arrives as an argument, and the invariant's remaining job is 0103 §3.4's original one: every descriptor a static linker-uniqued symbol. The product dissolves instead of being enumerated.

**Under D: the same slot rule, plus two recorded consequences.** (i) The seal must **reject** a generic virtual member whose signature falls in the witness-inexpressible class — under this study's §1's staged pair, bare-U-involving function-typed positions while D sits at stage (c) — naming the member and the shape (the generalized fallback discipline; never a runtime failure). (ii) The uniform slot is **hierarchy-infectious**: an override in an *unsealed* module of a sealed base's generic virtual must still compile (or thunk) to the base's slot convention — one uniform body per override even in modules that never opted in. That is 0103 §3.4's *"reabstraction obligation at every override"*, confirmed and sharpened as D's cross-module cost line; rejecting the override instead is unavailable — the override surface is §12.1's, and a seal on the base's module may not break a derived module's spec-conferred rights.

**Under E: E degenerates to C at every virtual generic boundary.** A slot holds one entry, but E's bodies are per-shape and a conformer's compilation cannot know which shapes external instantiations need — completing a per-shape slot table cross-artifact needs bodies at link time, piercing the sealing payoff for exactly these members. The sound hybrid ▲: the slot takes C's uniform witness-convention entry; stenciled bodies serve only direct and devirtualized calls. Go, facing the same product, declined methods with type parameters outright (the restriction is in the Go spec; the dictionary-product motivation is secondary-sourced); Bezel's surface is already normative, so the uniform slot is forced.

**Recommendation: record the uniform witness-convention virtual slot — one slot per generic virtual member, static descriptors as arguments, one uniform body per override — as the only sound shape under all of C/D/E**, with D's two consequences recorded beside it. Confidence: **high on soundness** (forced by elimination: per-instantiation slots recreate the product, runtime lookup is AOT-unavailable, per-shape slots need link-time bodies), **medium on cost**: every non-devirtualized generic-virtual call pays full witness indirection even at value substitutions; §12.4 sealing and static-type devirtualization recover the hot cases, but the multiplier is unmeasured on bezelc — 0103 §5 item 1's honesty flag applies.

## 4. Polymorphic recursion (0103 §3.4: "must stay a compile-time rejection")

### 4.1 What the current spec says: nothing — the absence claim, with near-misses

0103 §3.4 asserts polymorphic recursion *"must stay a compile-time rejection"*; this study checked whether the current spec actually rejects `F<T>` calling `F<Box<T>>`. **It does not — no rule of v0.261 addresses recursive generic instantiation or bounds the instantiation closure.** The four nearest passages, and why each falls short:

1. **§14.2 (constraint cycles):** *"A self-referential bound (`where T: T`) or a cycle among type-parameter bounds (`where T: U` together with `where U: T`) is a compile error at the declaration."* — a cycle in one declaration's constraint graph; nothing about the call graph between declarations or growing type arguments.
2. **§27.8 (aliases):** *"A generic alias may not reference itself (no recursive aliases) and must resolve to a concrete type after substitution."* — aliases only; the rule guards alias resolution, and an alias creates no type.
3. **§12.10 (inheritance cycles):** *"An inheritance cycle is a compile error. A type may not, directly or transitively, list itself among its base types"* — the base-type relation; `F<T>` calling `F<Box<T>>` lists nothing as a base.
4. **§35.1 (value self-containment):** *"a value type cannot contain itself. Recursive sums are expressed with a class node in the cycle (an `owned` class payload whose class holds the nested choice), exactly as recursive records are."* — data-layout recursion at the *same* type, explicitly *licensing* recursion through a class node; it never contemplates a chain of distinct, growing instantiations, and `Box<T>` contains nothing of `Box<Box<T>>`. The **growing-field case turns this licence against the rule** (adversarially found): a *class* field of a growing instantiation of the declaring type — `class Node<T>` with `private owned _next: Node<Pair<T, T>>?` — is declarable, the field being a reference the value-containment rule never sees; yet it routes the same divergence through the **data structure**, with no call involved: `Node<int>`'s synthesized disposal cascade and §3.6's derived-property computations — trivial-dispose is *"evaluated coinductively (assume the types under test trivial-dispose, then check the rules)"* (§28.9), over a "types under test" set that here grows without bound — meet an unbounded instantiation closure (the nested-datatype shape of the functional-programming literature). So even §3.6's own machinery meets the divergence, which strengthens the gap finding and obliges the rule below to cover field and payload edges, not calls alone.

The gap's consequence is untenable under the semantics-not-strategy posture. §2.8.2 clause 2 obliges an implementation to *"**Instantiate** every public generic type and generic method at arbitrary module-external type arguments satisfying the declared constraints"* — but a monomorphizing implementation *cannot terminate* on any instantiation of an expanding-recursive generic (the body's call requests the next instantiation regardless of dynamic reachability), while a witness implementation with runtime descriptor construction could compile and run it. Program admissibility would depend on codegen strategy — precisely what §11.8 forbids observables to do (0103 §1.2). The spec must reject the shape or mandate its support; silence is the one untenable position. Per CLAUDE.md's discipline this is recorded as a **finding and flagged for an issue** (this study's Q1), not silently assumed.

### 4.2 What bezelc does: diverges — established from the machinery

A live probe could not be executed in this session (no `build/bezelc` exists in the container; building one is out of this study's scope), so the behavior is established from the instantiation machinery and flagged as such. `buildSpecializedMethodFn` (`src/codegen/LlvmBackend_Calls2.cpp`) memoizes specializations on the #1947 **recursive structural identity key**, whose comment is explicit that nested self-instantiations are deliberately distinct: *"`Foo<int>` and `Foo<Foo<int>>` both keyed on `Foo` AND both erase to `ptr`, so the second reused the first's specialized body"* (the bug the recursive key exists to prevent). The function has **no depth bound and no cycle detection across distinct keys** (searched: no instantiation-depth or pending-instantiation machinery anywhere in `src/`); the cache entry *is* registered before body emission (`specializedMethods_[cacheKey] = specFn;` precedes the emit) — a de-facto in-progress marker, which is exactly why *same-key* recursion (`F<T>` calling `F<T>`) terminates today — but an expanding chain never re-hits a key. Specialization re-enters the emitter mid-body (#2281's frame save/restore, 0103 §4.1 item 4); for `F<T>` calling `F<Box<T>>`, each re-entry mints a fresh key (`F<int>`, `F<Box<int>>`, `F<Box<Box<int>>>`, …), the cache never hits, and the compiler recurses unboundedly: **bezelc neither rejects nor terminates — it diverges** (stack or memory exhaustion, whichever lands first). The unexecuted probe, reproduced inline so the hand-off cannot be lost to scratch GC (a convenience copy sits at `/var/tmp/bezel-scratch/poly_rec_0104.bzl`), exercises **both routes** — the call route and this study's §4.1's field route:

```bezel
// 0104 probe — polymorphic recursion, two routes. Does bezelc reject, diverge, or accept?
record Box<T>(Value: T);
record Pair<TFirst, TSecond>(First: TFirst, Second: TSecond);

public static class P
  public static method F<T>(depth: int, seed: T): int          // route 1: the call route
    if depth <= 0 then return 0; end;
    return 1 + F<Box<T>>(depth - 1, new Box<T>(seed));
  end F;
end P;

public class Node<T>                                           // route 2: the field route
  private owned _next: Node<Pair<T, T>>?;
end Node;

public static class Program
  public static method Main(): int
    using var n := new Node<int>();
    return P.F<int>(3, 42);
  end Main;
end Program;
```

### 4.3 The proposed rule ▲, and the alternatives declined

**Candidate rule ▲ (described, not drafted): rejection at the declaration.** Over the static instantiation-request graph among generic declarations — an edge per instantiation a declaration's compilation must request: generic calls, generic-type instantiations, base-clause references, and **field, choice-payload, and signature types** (field and payload edges explicitly included — this study's §4.1's growing-field case is the second route the enumeration must cover, or the rule leaks), labeled with the requested substitution, override edges included (an override's body contributes its requests to the base member's node, since dispatch reaches it) — every edge inside a strongly-connected component must substitute each target parameter with a **bare type parameter of the source** or a **closed type**; an in-SCC edge nesting a source parameter inside a constructed argument (`F<Box<T>>`) is a compile error **at the declaration**, in the house's existing declaration-site shape (§14.2's bound cycles, §27.8's alias rule), with a diagnostic naming the cycle and the growing argument: *"generic method `F`'s instantiation closure is unbounded: `F<T>` requires `F<Box<T>>` (this call), which requires `F<Box<Box<T>>>`, and so on; a recursive generic call may not nest a type parameter inside a constructed type argument."*

Declined alternatives: **(i) an instantiation-site depth limit** (C++'s / Rust's `recursion_limit` shape) — acceptance keyed to an implementation-defined knob, unusable under the artifact model: clause 2 makes every public generic externally instantiable, a promise a depth-limited exporter cannot keep, and the diagnostic lands at an importer's instantiation deep in a chain rather than at the defect. **(ii) Accept-and-support** (the CLR's lazy-JIT road) — AOT-unavailable (0103 §5 item 1), and for the witness designs it would mandate exactly the runtime metadata cache whose absence 0103 §3.4 records as the design's biggest advantage over Swift; the closed-instantiation-set invariant would fall. **(iii) Rejection only at instantiation** — leaves an exported generic that can never be instantiated at any argument compiling silently, a lie of a public surface under clause 2. The known over-rejection is stated, not hidden: a growing self-call that is dynamically unreachable still rejects — correctly under monomorphization, where the compile-time closure diverges regardless of reachability, and conservatively-honestly under any strategy, since clause 2's obligation is instantiation, not execution.

**Installed base** (the migration row's question): a grep-scale sweep of the entire `tests/` and `docs/` corpus at this snapshot — all 657 generic declaration names, each checked for in-declaration self-references instantiated at a constructed argument containing a type parameter — found **zero** expanding self-edges outside this study's own text. The sweep decides direct self-edges only; mutual cross-declaration cycles are beyond grep, and a precise sweep is owed at issue-filing time. As proposed, the rule newly rejects nothing in the repository. Two seams recorded beside it: **cross-module cycles** (`F` in module A, `G` in B, `G` requesting `F<Box<T>>`) are visible to a declaration-site check today only because §2.8.2 carries bodies — under the sealed designs this study serves, the interface must carry instantiation-request edges, which is exactly 0103 §2 Class C's transitive-instantiation-request summary row; and the rule's shape has house precedent in §22.13's static-initialization dependency graph (a declaration-level graph with body-derived edges) and §2.5's import-SCC machinery, which already own the vocabulary.

**Confidence: high** on the absence finding and the strategy-dependence argument; **medium-high** on bezelc's divergence (machinery-derived, probe unexecuted); **medium-high** on the rule's exact shape — the SCC formulation needs adversarial review (higher-order flows through function values add no instantiation edges, since invoking a function value requests no instantiation, but a reviewer should re-derive that; and the bare-or-closed condition deliberately admits bounded permutation cycles like `F<T, U>` calling `F<U, T>`).
