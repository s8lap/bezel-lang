## 0. Summary

Today the spec says that reassigning an owned field, or disposing it explicitly, while a local borrow of its current value exists is admitted and "caught as `DisposedAccessException` in checked disposal mode and undefined unchecked" (§28.7 *Overwrite while borrowed*, K5.6). For the straight-line shape —

```bezel
var b := _w;                      // a borrow of the field's current value
_w := new Widget("second");       // drop-on-overwrite disposes exactly that value
Console.WriteLine(b.Name);        // faults on every run
```

— the compiler says nothing, the checked build exits 70, and the unchecked build prints an empty line and exits 0: the silent wrong read proposal 0205 measured for a local's explicit `Dispose()`, one clause over. The fault is **certain** whenever nothing between the borrow and the write can have taken the value out of the field — and the only operation that can is the replacing `move` (§28.8.1), a write of the same path, or a call that performs one. Proposal 0205 does not reach the shape: its holder check reads K5.5's source sets, which name the holder (`this`), not the field's value, and its kernel model confirms the gap — after 0205, the twelve certain-fault programs its all-features population still admits are all `new a / fbrw b a / fst a / use b`, this proposal's shape (0205 §4.5).

This proposal makes the use a **compile error** where the fault is certain: a local initialized from a direct read of an owned field (`var b := r.f;`, `r` being `this` or a local or non-`ref` parameter) is used after a **disposing write** of the same field — a reassignment (the store of `null` at a nullable field included), an explicit `Dispose()` or a direct `DisposeAsync()` — that follows the borrow with **no invalidating operation** between them on any path (§7.4's forms: no call — a constructor's included — accessor, user-defined operator, function-value invocation or `await`; no `yield return`; no disposal of another value, whose destructor the body does not show; no other write to the path or to its root; no `move` of any field path, the replacing `move` being the one operation that takes a value out of a field) and **dominates** the use on every path, the local not reassigned between the borrow and the use; a read of the field itself after an explicit disposal in the same window is the same error, a repeated explicit disposal of the field (§28.2's no-op) excepted. The write's own right-hand side is outside the window (§9 item 11). The write stays permitted — K5.6 is not touched, and the compiler's K5.6 posture for everything outside the window (a write on some paths, a window with a call in it, a borrow held through an alias, closure, span or record, a two-segment path, a collection or inline-array slot) is unchanged. The remedy is one line: use the borrow first, or take the value out with `move r.f with …`, whose result the taker owns.

**Why a separate proposal, and why not the collection leg.** 0205's rule is over a *local's* explicit disposal, traced through K5.5's provenance; this rule is over a *field path*, its kills are a reassignment as well as a disposal, its certainty predicate is a window rather than a source set, and the record it reopens is K5.6's posture as `DECLINED.md` cites it (proposal 0153's option D, the v0.331 #5680 rows), not rationale §5.1's v0.180 narrowing. Folding the two would mix two reopening arguments in one document and widen 0205's trackers. The owning-collection slot leg (§8 of the hunt: `var w := pool[0]; pool.RemoveAt(0); w.Name`) is declined (§7): it reopens proposal 0181's v0.338 retirement of the element-borrow warning on a stated bar that is unmet, re-adds the per-slot predicate the subtraction review removed, and would have the compiler re-grow code [#6573](https://github.com/s8lap/bezel-lang/issues/6573) decided to delete.

**Measured reach**: one banked rule-corpus row (`s28_7_0005`, `accept` → `reject`) and one gtest row (`codegen_checked_disposal_bounded_retention_4602.spec_28_2_k5_6_field_overwrite_displaced_borrow_still_faults`), both of which exist to observe the backstop and keep doing so under a conditional write; no guide, specification, stdlib or doc-corpus program writes the shape; the tree has zero sites of the explicit-disposal variant (§5).

## 1. The text today

> **Overwrite while borrowed.** Reassigning a plain-`var` owned **local** while a live local borrow of its current value exists is rejected by the consume-site freeze (K5.2; §28.3) — the implicit disposal would silently invalidate the borrow. Reassigning an owned **field or collection slot** is not statically frozen (K5.6; the consume table's frozen column, §28.3); a borrow of the displaced value is invalidated at the overwrite, caught as `DisposedAccessException` in checked disposal mode and undefined unchecked — the same runtime-checked posture as explicit `Dispose()` (rationale §5.1).
>
> — §28.7, v0.345

> 6. **fields and collection slots are not frozen** — the clause bounds what the freeze's *subject* is: slot aliases are not body-local, and a slot kill disposes — the K4 backstop is real there; the slot kill *by move* is instead governed by K4.3's domain clause
>
> — §28.3.1 K5 clause 6, v0.345

> A later **read** of the slot is not statically diagnosed — §28.2's use-after-dispose warning is a straight-line rule over a **local**, while a field's value is readable and reassignable from every method of its declaring type and this section's admission is by declaring type, not by receiver instance — so the reader is K4.1's backstop
>
> — §28.6, v0.345 (after an explicit `Dispose()` of an owned field)

> **Scope.** Fields and collection slots are **not** frozen (K5.6): a borrow of `obj.f`'s or `coll[i]`'s current value is invalidated by an overwrite or mutation of the slot under the runtime-checked posture (§28.7, §28.11).
>
> — §28.3.9, v0.345

> What a field read through `acct` or `this` points at can still be overwritten under the holder, and that is checked mode's business — the same posture every field borrow has.
>
> — Guide 01 §5

Three things are decided: the write is not frozen (K5.6, with its reason — a slot alias is not body-local); a stale read through the borrow is the flag's business; and a later read of a disposed field is not statically diagnosed, because §28.2's rule is over a local. What no sentence decides is whether the compiler may *reject* a use it can see is certain to fault: K5.6's reason is about the **kill** — a callee may write the field unseen, so no freeze at the visible write guarantees anything — and says nothing against rejecting a **use** that a visible write certainly precedes with nothing unseen in between. §28.6's "not statically diagnosed" sentence gives a reason ("a field's value is readable and reassignable from every method") that is exactly the window condition's complement: *between* two statements of one body with no call, nothing from another method runs.

## 3. Options

### 3.1 O0 — the status quo

K5.6's posture for every field write, a certain fault included. Cost: the silent faults of §2 and an asymmetry with proposal 0205 (a local's dominating explicit disposal rejects the use; a field's does not, although the compiler can see both).

### 3.2 (a) — a mandated warning in the window

Changes no verdict; mandates a warning the spec's doctrine (rationale §5.28: warnings only where load-bearing) would have to defend as the final state of a certain fault; the project's one warn-first placement here (§28.2, v0.184) was never a ramp. Declined (§7) on 0205's ground.

### 3.3 (b) — the dominated use in the window is an error (adopted)

As §0 states it; the normative text is §8. The write stays legal and unfrozen; what is rejected is the use.

### 3.4 (c) — freeze the field write under a live local borrow

K5.6 flipped for the same-body form: the shape of proposal 0153's option D ("Freezing a same-body field-slot overwrite under a live span local", `declined-at-proposal`) generalized from spans to every borrow. Declined (§7): K5.6's reason stands — a callee writes the field unseen, so the freeze guarantees nothing the flag does not — it rejects the *write* and so reaches none of the field-read-after-`Dispose()` shape, it would be K5.6's first exception (proposal 0143's option (d) and 0153's option D were declined for being that), and the rule the owner's bar asks for is the narrow one.

### 3.5 Widenings of (b), declined (§7)

**(d)** reaching holders of the borrow — an alias chain (`var c := b;`, f02), a closure capturing `b`, a span over an owned buffer field, a borrow-bearing record or choice carrying it, a two-segment path (`_a._b`), a field read through a root written in the window: each needs a provenance the field-source fact does not carry (0205's holder check reads K5.5's sets, which name `this`), the span forms are 0153's declined options B–F, and the tree has zero such sites. **(e)** the owning-collection slot leg (§8 of the hunt): §7.

## 4. Evaluation

### 4.1 Soundness

(b) admits nothing the current rules reject and rejects only a use that faults whenever it executes, plus the null-test over-rejection 0205 already records (f06's `b <> null` after a store of `null`: when `_w` was `null` nothing faults, and the test is still a use) and the right-hand-side over-rejection of §9 item 11 (ii). The certainty argument is the window: a displaced field value survives its store only through the replacing `move` (§28.8.1: "yields the location's previous value, owned"), which is a write of the path, or through a call that performs one; §7.4's invalidating forms, with a `yield return` and another value's disposal beside them, are exactly the operations that can run code the body does not see (a call, a constructor's included, an accessor, a user operator, a function-value invocation, an `await`, the consumer at a `yield return`, a destructor; §9 item 11), and a write to the root `r` (an assignment, a `ref`/`out` argument, a mutable capture) is what makes `r.f` name another field afterwards. With none of them between the borrow and the write, the value `b` borrows is the value the write disposes, on every path through the window; dominance of the write over the use then makes the fault certain at the use. Everything outside the window keeps K5.6's posture, in the direction the backstop covers.

Kernel classification (§9 checklist): a **derivation**, no axiom — K3.11 at a slot (the overwrite is a consume of the displaced value, disposed) or K3.9 at a slot (the explicit disposal), K2.1 (the local's borrow is of the field's current value, receiver-sourced), the K7.4 dominance §28.2 already uses, and §7.4's invalidation walk for the window. K5 is untouched: clause 6 still says fields and slots are not frozen, and nothing in (b) freezes one. Body-locality: **local** — one body's flow graph, one path spelling, one window.

### 4.2 Simplicity

One sentence a writer can hold: *if you copy a field into a local and then overwrite or dispose the field with nothing in between that could have moved the value out, you may not use the copy afterwards — use it first, or take the value out with `move`.* The analysis is the compiler's: the field-root fact `disposeAliasSource` already records which field a local borrows (`Ownership.cpp:8070`, fix #4283); the dominance is `checkRead`'s (`Ownership_Checks.cpp:3340`); the window is §7.4's invalidation walk, which the nullability pass runs over the same statements. What is added is a per-local "borrows the current value of `r.f`, taken at site S" fact, cleared by any invalidating operation or any write to `r.f` or `r`, and consulted at a disposing write of `r.f` to mark the local's value killed; the use check is then 0205's.

### 4.3 Consistency

- **With proposal 0205.** The two rules have one shape — a use that a visible kill certainly precedes is rejected; the kill is not frozen — and together they leave no certain fault admitted within the kernel model's straight-line bounds; with a branch, the joins whose paths kill the borrow by different kills (the holder's disposal on one, the field's overwrite on the other) stay the checked-mode fault under both (0205 §4.5) — a combined "every path kills it by one of the two rules" test is the unproposed widening. The field rule is narrower on purpose: a window instead of a source set, because the field's value has no body-local generation the K5.5 machinery tracks.
- **With K5.6 and its reason.** "Slot aliases are not body-local" is why the write cannot be frozen; it is also why the rule needs a window and stops at the first call. The clause's text is untouched; §28.3 *Scope* gains one clause saying where the use is rejected.
- **With §28.6.** "A later read of the slot is not statically diagnosed" becomes "diagnosed only within §28.7's window": the sentence's own reason (other methods can write the field) is the window's complement. The sentence also named "§28.2's use-after-dispose *warning*", stale under 0205; one edit fixes both.
- **With §7.4.** The window's forms are §7.4's invalidating forms, verbatim in kind, and the admitted roots are §7.4's `readonly`-narrowing roots (`this`, a local, a non-`ref` parameter; one field off the root) — a reader who knows when a narrowing survives knows when this rule applies.
- **With §28.11.** The owning-collection sentence "not statically tracked per slot" stays true; the code-generation reference's §7.5 pair (`var w := xs[0]; xs.RemoveAt(0); w.Ping(); // compiles SILENTLY`) stays true. The asymmetry — a field path is tracked within a window, a slot is not — is stated in the new paragraph and in the §7 decline with its reason.

### 4.4 Migration (measured, §5)

Newly rejected: the shapes of §2's first five rows. Remedy: use the borrow before the write, or `using var old := move r.f with fresh;` and use `old`. Nothing newly admitted, nothing newly warned. Ramp: none — a design change, not a ratchet; the Migration note states the end state.

## 6. The case against the recorded posture

K5.6 is a kernel clause with a stated reason, and `DECLINED.md` cites it in five rows (45, 46, 132, 759/760/766/785/802 — the #5680 rulings and proposal 0153's options). Every one of them declines a **freeze** or a **trust clause** at the write; none declines a rejection at the use, because none was asked. The nearest, proposal 0153's option D ("Freezing a same-body field-slot overwrite under a live span local sourced at that slot's current value", `declined-at-proposal`, bar *—(none stated)*), is declined because "K5.6 states that fields and collection slots are not frozen for every borrow, with the flag as its reason; a span-only key would re-key the clause on the holder's type, reach the same-body form only, and separate zero measured sites". (b) keys on nothing about the holder's type, freezes nothing, and the sites it separates are measured (§2, §5): the certain fault in an unchecked build is a silent read of a freed block. The row is annotated, not reversed: the freeze stays declined, and a span over the field's buffer stays outside the rule.

The bar this proposal is held to is the owner's: **clearly an improvement**. Safer — a certain fault that is silent at compile time and silently wrong in one of the two conformance modes is rejected. Simpler — the rule is the one 0205 states, one clause over, and it adds no new kind of analysis (a field-root fact the compiler already records, a window the nullability pass already walks). Negligible migration — one corpus row and one gtest row, both written to observe the backstop, both kept observing it with a conditional write. Not a taste change — the rejected programs are wrong on every run.

**Process class.** A design change (§2's third rule: it changes a stated verdict and contradicts a recorded posture), so a proposal first, then a ruling-class landing with the adversarial critique, the composition check (§9 item 8), the corpus sweep (one row), the code-generation reference update, and one `spec-tracking` issue.

## 9. Self-critique (adversarial pass)

1. **Is the window really certain?** The question is whether anything but §7.4's forms, a write to the path, or a write to the root can move a field's value out between two statements of one body. A `ref`/`out` argument naming `r.f` is an argument of a call (excluded). A closure formed earlier and invoked in the window is a function-value invocation (excluded). A `for` desugaring's hidden iteration or a lazy query enumerated in the window runs its body through calls (excluded). A `try` whose `catch` arm lies between: the arm runs only on a throw, which comes from an operation; a `finally` is a block of statements under the same rule. An `await` is excluded. A `lambda` *formed* in the window (not invoked) runs nothing. A field write through a different root naming the same object (`h2._w := …` with `h2` an alias of `this`): a write to another path; it does not move `_w`'s value out, it disposes it — the fault is still certain, and the rule, keyed on the visible write of `r.f`, rejects correctly; if instead it were a replacing `move` through `h2` (`var t := move h2._w with fresh;`), the value survives in `t` and a rule keyed on `r.f` alone would be wrong. **Found in this pass, and closed in the text:** the window excludes a `move` of **any** field path, through whatever root it names the field by — the replacing `move` is the one operation that takes a value out of a field, so excluding it everywhere costs nothing and needs no alias reasoning.
2. **Over-rejection.** The null test through the borrow after a store of `null` (f06 when the field was `null`), as in 0205's p16: a use, recorded. A dead borrow (`var b := _w; _w := new …;` with `b` unread): not rejected — the rule rejects a *use*. A read of `r.f` after `r.f := e`: not rejected — it reads the new value. A read of `r.f` after `r.f.Dispose()` followed by `r.f := e` with the read between: rejected, correctly (dispose-then-assign reads nothing in between; the idiom §28.7 names is `_w.Dispose(); _w := new …`).
3. **The `this`-escape during construction** (§22.7): a constructor body's `var b := _w; _w := new …; b.Name` is the same certain fault; the rule applies in constructors and the destructor alike, and the construction window changes nothing about it.
4. **The root as a parameter**: `h: Holder` plain, `var b := h.W; h.W := new …; b.Name` — a store into an owned field through a borrowed receiver is admitted today (f11 compiled with a local root); the rule applies. A `ref` parameter root is excluded, as in §7.4 (its aliases are the caller's).
5. **Does the same-variable half (a read of `r.f` after its explicit disposal) over-reach?** It is the field twin of 0205's promoted warning, measured at zero sites, and §28.6's own sentence is amended to say where it is diagnosed. Without it the rule would reject `b.Name` and admit `_w.Name` on the same disposed object — the inversion 0205 §4.3 refuses for locals.
6. **Interaction with proposal 0153 (span reads are flag-checked).** A span over an owned buffer field (`var s := _buf.AsSpan(); _buf := new …; s[0]`) is a holder over the borrow — outside the rule, declined under (d), and the annotated option-D row keeps its posture. No new route for a span is opened or closed.
7. **The §8 decline against the owner's bar.** p27a/p27b are as certain and as silent as f01, and declining them is a decision on the *record* (0181's bar, #6573's deletion), not on the hazard; if the owner reads the bar as met by the hunt's measurement, the leg is the lint-B predicate at error severity with the indexer-set leg added, and its text is the paragraph 0181 deleted. Stated in §7 so the critic and the owner can reverse it without reopening the rest.
8. **Composition with the v0.346 train.** Lane Q's #7364 ruling appends one sentence after the first sentence of §28.7 *Overwrite while borrowed*; this proposal anchors on the second sentence and appends a paragraph after the whole — disjoint; both apply in either order. Proposal 0205 edits §28.2, §28.3.1, §28.3.9, §28.3.12, §28.10 and C.3; this proposal's C.3 bullet, rationale paragraph, §4.6 row and §7.2 pair ride 0205's edits. Lane G's 0207 edits §28.11 *Borrowing collections* and the `OwningDictionary` key sentence; this proposal edits nothing in §28.11. Lane S's edits are elsewhere. The K5 clause-6 text is untouched by every lane.
9. **Implementation risk.** The fact must be cleared conservatively: any statement kind the implementation does not classify clears it (the rule errs toward admitting, which the backstop covers). The dominance is the existing one. The explicit-disposal path marks the field path killed in the window only — not the field's state across methods, which §28.6 keeps untracked.
10. **What the model could not say.** The kernel model's borrow of `a.f` is sourced at `a` (0205 §4.5), so this rule has no mutation there; its twelve-program residual under 0205 is this shape, which the rule rejects by inspection. A per-field value generation in Γ would let the model measure (d)'s widenings too; recorded as a question for the model lane in `F.md`.
11. **Critic's pass (v0.346): the window, tightened.** Four holes in the draft's window, each an over-rejection of a program that does not fault (none admits a fault), closed in the normative text: (i) *a constructor call, a `yield return`, a disposal of another value.* §7.4's forms include a constructor call; a `yield return` hands control to the consumer, which can call `h.Rotate()` (a replacing `move` of the field) before the iterator resumes; a discard, a scope-end drop or a drop-on-overwrite of another value runs a destructor that can do the same through a non-owned field holding the root. All three now break the window, "on any path from the borrow to the write". (ii) *The write's right-hand side.* The store displaces the value its operand finds after evaluation (§7.4 *Storage inside a narrowed nullable value*: "an assignment stores after its right operand is evaluated"), so `r.f := Take();`, `Take()` taking the value out, would be rejected though the borrow's referent survives. Counting the operand in the window would be the sound-precise choice, but it would drop the shape this proposal exists for — `_w := new Widget("second")` evaluates a constructor — and every measured site (f01, p10, `s28_7_0005`, the 4602 row). The text keeps the operand outside, states the over-rejection, and gives the one-line rewrite that puts the call in the window (`var n := Take(); r.f := move n;`). The owner may prefer the other side of this trade; if so the rule reaches only `null`, `move` of a local, a parameter or a literal on the right, and the explicit disposal. (iii) *The local rebound.* `var b := _w; _w := new …; b := _w; b.Name` (probe `Fcrit/probes/c04`, prints `second`) was rejected by the draft's letter; the local must be a stable local (§7.4) unassigned from the borrow to the use. (iv) *A repeated explicit disposal of the field.* `_w.Dispose(); _w.Dispose();` (probe c05, accepted today, prints `ok`) is a "read of `r.f` after its explicit disposal in the window" by the draft's letter, an error for the one use proposal 0205 keeps at a warning because §28.2 defines it as a no-op; now excepted. The probes that would show (i) and (ii) running need the replacing `move`, which r35 does not parse (#5923; `Fcrit/probes/unprobeable/`); the argument is from §28.8.1's text, as f03/f05's is.
