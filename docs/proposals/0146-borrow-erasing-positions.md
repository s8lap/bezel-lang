## 0. Thesis

A box announces no borrow. §9.7's instance-field bullet rejects storing a borrow-bearing record statically, on a stated ground: "a record-carried borrow … may be consumed through access paths with **no per-access disposed-flag check** (a span's buffer window is the canonical case). The checked-mode trust regime is therefore unavailable and the store is **rejected statically**." That ground is keyed on the value's *declared* type. §8.6 then admits boxing such a value "for a short-lived interface call (e.g. passing to a method accepting `Object`)", and the callee receives a parameter whose declared type is `Object`: it cannot tell a box that carries borrows from a class reference, whose store into a field §28.3's field-store bullet admits under K4.1's backstop. So `method K(x: Object) F := x;` compiles, `k.K(buf.AsSpan())` compiles, and after `buf` is disposed `(k.F as Span<int>)[0]` reads freed storage — no rejection, no backstop, no recorded trust clause. §28.14 already rejects the box at a `scoped` interface parameter on exactly this ground ("the callee may keep the box in a field of the bounding object, which §9.7 and §8.6 reject"); a plain parameter is not reached.

The language has already decided this shape once, for function values: a closure carries borrows its type does not announce, and §28.3's *Set-erasing positions* rejects a capture-bearing function value at every position declared `Object` or at a bare type parameter substituted with a function type, on the caller's side, over the callee's declared signature — "the declared type announces no source set, so no holder reached through it could re-establish one (K2.4), and no rule reading the position … sees a borrow to bound (K2.3)". A box that carries borrows is the same value in a different carrier. This proposal states the twin rule, **borrow-erasing positions**: a value that holds borrows (§3.6) converts to `Object` or to an interface type at exactly two positions — as the receiver of a member call, where §8.6 and §9.4 already bound the box by the call and the member reads the payload at its own type (and of an extension call on `IReadOnlySpan<TElement>`), and at a position declared `IReadOnlySpan<TElement>`, the one interface the standard library declares for the purpose, whose values are read as holding the span's borrows by every rule that reads a value that holds borrows (the compiler already enforces this callee-side for the field store, #4751). Every other conversion is a compile error at the conversion site.

Measured reach: **two test files flip** (five tests), one of which already pins a return §8.6 rejects at HEAD; zero doc examples, zero guide examples, zero rule-corpus cases state the old admission at an `Object` or non-view interface position.

## 1. Ground truth

### 1.1 The rule today

- **§8.6 *Boxing of borrow-bearing records*** (line 1203): "The compiler enforces: a boxed borrow-bearing record value may not be stored in a location that could outlive the source of any borrow the record contains. In practice, this means a borrow-bearing record may be boxed for a short-lived interface call (e.g. passing to a method accepting `Object`) provided the boxed value does not escape the borrow's source scope. Storing a boxed borrow-bearing record in a field, returning it from a method, or capturing it in a closure that escapes the source scope is rejected by the same rules as the unboxed form (§9.7, §28.3). The canonical sanctioned use is passing a span to a parameter of type `IReadOnlySpan<TElement>` (stdlib §4.16) …". The admission is stated of the *caller's* box; the rejection of the store is stated of the *value*, which the callee no longer sees as one.
- **§9.7's instance-field bullet** (line 1454) rejects "a borrow-bearing record value" stored in an instance field, with the no-backstop ground quoted above, and its generic reading: "a bare `T` stored into an `Object`- or interface-typed field is the same store through §8.6's box at such a substitution" (v0.328, #5629). The bullet reads the stored value's declared type. A parameter declared `Object` is not one.
- **§28.3's field-store bullet**, clause 3 (line 6734): "An unbound owned temporary or a borrow of a scope-bound local, passed to a plain parameter that the callee stores … is admitted at the call, for a local, virtual, interface or imported callee alike", under K4.1's backstop — "a member access through the stored borrow after the source's disposal raises `DisposedAccessException`". For a boxed span the stored reference is the box, which stays alive; the dangling pointer is inside its payload, and a read through `(o.F as Span<int>)[0]` is not a member access on a disposed instance.
- **§28.14** (line 7684): "A **value-typed argument** at an interface-typed `scoped` parameter … A borrow-bearing value is rejected there: the callee may keep the box in a field of the bounding object, which §9.7 and §8.6 reject for a record-carried borrow whatever the field's lifetime; the remedy is a class implementing the interface." The plain parameter, which may store under clause 3, is the one not reached — and `scoped` on `Object` is itself a compile error, so no marker exists for an `Object` parameter at all.
- **§28.3 *Set-erasing positions*** (line 6753): the function-value twin, quoted in §0. Rationale §4.2's v0.320 paragraph records its cost: "`Console.Write`/`WriteLine(Object)`, `StringBuilder.Append(Object)` and `Equals(Object?)` reject it; `f = g` compares function values, and a description prints."
- **Stdlib §4.16** (line 3375): "the boxed copy holds the same borrows as the original, the boxed value's lifetime is bounded by the source of every borrow it carries, and the compiler enforces that the boxed value does not escape the source scope. … A method declaring `IReadOnlySpan<TElement>` cannot store the parameter in a field that outlives the call, return it from a method whose return-lifetime rules do not establish source lifetime, or capture it in a closure that escapes. These are the standard borrow-bearing-record constraints; nothing new is added by the interface." A callee-side rule, stated for one interface, which no spec text states.

### 1.2 The compiler today (`src/` at `d708e13`; read from source and recorded test names, no build was available to this lane)

- The `IReadOnlySpan<TElement>` callee-side rule **is implemented for the field store**: `src/ownership/Ownership_Checks.cpp:9697–9838` (#4751, v0.307) adds the interface as a "fourth carrier" of §9.7's instance-field rule beside records, spans and choices, keyed by `common::isIReadOnlySpanType` (`src/common/OwnershipFacts.cpp:1788`); `tests/sema/ireadonlyspan_field_storage_4751_test.cpp` and rule-corpus case `l4_16_0004` pin it.
- A boxed borrow-bearing record stored into an `Object`/interface **field** is rejected (`s8_6_0004`), and the collection-literal-into-inline-array-field face too (`Ownership_Checks.cpp:9846–9900`, #4478).
- **No check exists at a conversion to `Object` or an interface at a call argument, a local or a return**: `grep -n "boxed\|boxing" src/ownership/Ownership_Checks.cpp` finds only the two legs above. The conversion itself is identified by `isBoxingTargetType` (`src/sema/ExprTypecheck.cpp:4434`, applied at `:5009`). §28.14's rejection of a borrow-bearing value at a `scoped` interface parameter is likewise unimplemented (no `scoped`-keyed borrow-bearing leg in `src/sema` or `src/ownership`).
- Tests that exercise the admitted conversion: `tests/codegen/span_range_tostring_2661_test.cpp:178` (`Console.WriteLine(sp)` on a buffer-backed `Span<int>`) and `tests/codegen/xmod_imported_span_box_vtable_3358_test.cpp:150–231` (`var o: Object := irs;` and `WrapSpan(): Object` returning the box of a `using var` buffer — a return §8.6 and §9.7's return bullet already reject at HEAD, which the compiler does not enforce).

## 3. Options

### 3.1 Option A — status quo (silent)

Keep §8.6's "passing to a method accepting `Object`" and §28.3's residual. The store is admitted with a backstop the value does not have, against §9.7's own ground and K4's third clause ("Recorded trust, or nothing"). **Unsound.**

### 3.2 Option B — a recorded K4.3 trust clause (the issue's answer 3)

Admit the callee's store of a plain `Object`/interface parameter as a recorded trust clause, reported by `--report-trust-admissions`. K4.3 admits a trust clause only "where an admission's temporal guarantee can neither be statically compared (K2.3) nor flag-backstopped"; here the obligation *can* be stated statically (the box's sources are the caller's), and §9.7's instance-field bullet has already declined the trust posture for record-carried borrows on the no-backstop ground, with `CancellationToken` rejected "for regime uniformity". Reversing that is a larger design change than the question asks, and it would leave the first memory-unsafe admission without a backstop in the language. Declined (§5.6, row 1).

### 3.3 Option C — borrow-erasing positions, caller-side, with `IReadOnlySpan<TElement>` as the admitted interface (**recommended**)

A value that holds borrows (§3.6: a borrow-bearing record or inline array, a choice that holds borrows) is converted to `Object` or to an interface type at two positions only: the **receiver** of a member call (already call-bounded, §8.6/§9.4, the member's body reading the payload at its own type) or of an extension call headed `IReadOnlySpan<TElement>`, and a position declared **`IReadOnlySpan<TElement>`**. The receiver of an extension call headed `Object` or another interface is *not* admitted: the extension body reads `this` at the head type, which announces no borrow, and §28.3's field-store bullet (clause 3) admits passing it on to a parameter that stores it. Every other conversion — a parameter (plain or `scoped`), a bare type parameter substituted with `Object` or such an interface, a local, a field, a collection slot or literal element, a record component, a choice payload, an inline-array slot, a `ref`/`out` location, a return — is a compile error at the conversion, checked by the caller over the callee's declared signature, per instantiation (§3.6 rule 2), the generic body never re-checked. The admitted interface is sound because a value declared `IReadOnlySpan<TElement>` is **classified as holding borrows** — the span's — so every §9.7 bullet and §28.3 rule reads it as it reads the span: a callee's `IReadOnlySpan` parameter cannot be stored in a field (the compiler's #4751 leg, now a spec rule), returned past its source, captured by an escaping closure, or passed on at an `Object` position; it can be indexed, bound to a local, passed to another `IReadOnlySpan` parameter, unboxed by `as` or a pattern. The classification is by declared type (§3.6 rule 1), so a boxed `ReadOnlyStringSpan` at that type is read conservatively. Sound, callee-blind, one rule in the shape §28.3 already has. Cost: five tests, and the same short list of non-storing standard-library calls the set-erasing rule already rejects for closures (`Console.WriteLine(span)`, whose spelling is `span.ToString()`).

### 3.4 Option D — a callee-side rule: a plain `Object` or interface parameter is never stored (the issue's answer 2)

Sound and callee-local, but it retires the back-reference idiom for every interface-typed parameter (`constructor(logger: ILogger) _logger := logger;`), which §28.3's field-store bullet names as "the idiomatic form", under K4.1's live backstop. The reach is every class-typed-or-interface borrow stored from a parameter across the repository, for a hazard that only a boxed value carries. A narrower callee-side rule keyed on "an interface a borrow-bearing value type implements" is not modular: the implementing record may live in a module the callee cannot see (§2.8.3), so the callee's verdict would depend on a declaration outside its compilation closure. Declined (§5.6, row 2).

### 3.5 Option E — option C with a standard-library register of non-storing `Object` positions

Admit the box at `Console.Write`/`WriteLine(Object)`, `TextWriter.Write`/`WriteLine(Object)` and `StringBuilder.Append(Object)`, which render and do not store, by a register in the shape of §28.14's retention register. The admission would be **sound**: stdlib §2.1 states that the `Object` overloads "invoke `ToString()`", §7.4 fixes `TextWriter.Write(Object)` as a non-`virtual` base implementation `Write(value.ToString())` (so no subclass, and no `Console.Out`, can retain the argument), and §3.1 states that `Append(value: Object)` "keeps `value.ToString()`'s text, not `value`" — a stated no-retain contract at each. It is declined on its form, not its soundness: it is a per-member allowlist, the first outside §28.14's retention register, which a user rendering API (a `TextWriter`-like class, a logger) could not share — the ground on which v0.320 declined exempting `EventSource<T>.Raise` by name (`DECLINED.md`, whose bar is "a signature-level announcement that a parameter is not retained, usable by user members alike"); the set-erasing twin declined the same rendering admission for closures (rationale §4.2, v0.320), so the twins would disagree at the same position; the spelling `span.ToString()` or `$"{span}"` exists at every such site; and the measured reach is one test. A variant without a register — `IReadOnlySpan<TElement>`-typed overloads of `Console.Write`/`WriteLine`, `TextWriter.Write`/`WriteLine` and `StringBuilder.Append`, which rule 2 would admit — is declined with it: six new members for one test, a generic overload beside a non-generic `Object` one at every span argument (an overload-ranking question §22.6 would have to settle), and it covers spans only, not a borrow-bearing record. Declined (§5.6, row 3), reopenable by a non-rendering standard-library `Object` position whose call-bounded use has no spelling, or by the `Raise` row's signature-level non-retention announcement, which would admit these calls without a register.

### 3.6 Option F — option C with source-tracked `Object` locals

Admit `var o: Object := span;` with the box's sources tracked through the local by flow analysis, rejecting only the escapes. The set-erasing rule rejects a capture-bearing closure at an `Object` initializer; a local can be declared at the span's own type or at `IReadOnlySpan<TElement>`, where every rule reads it; and an `Object` local that holds a borrow would be the one reference-typed local whose later uses — `Keep(o)`, `xs.Add(o)` — need a provenance the type does not carry. Declined (§5.6, row 4).

### 3.7 Option G — user-declared borrow-view interfaces

Let a user interface opt in to `IReadOnlySpan<TElement>`'s role, so a borrow-bearing record could be passed at it. It needs a declaration-site marker (a keyword or a stdlib marker interface) and a rule that every parameter of that type is read as holding borrows; no program in the repository needs it (every borrow-bearing record implementing an interface is passed at its own type). Deferred (§5.6, row 5), reopenable by a program that needs a user view interface over a borrow-bearing value and cannot write the concrete type or a class.

## 5. Decision (delegated ruling, 2026-10-08)

### 5.1 The rule

**Option C.** The text is §6's.

1. **Borrow-erasing positions.** A value that holds borrows (§3.6's holds-borrows property) may not reach a position declared `Object`, or an interface type other than `IReadOnlySpan<TElement>`, nor a position declared at a bare type parameter that the instantiation substitutes with such a type — a parameter, plain or `scoped`, a local, a field, a record component, a choice payload, an inline-array slot, a collection slot or collection-literal element, a `ref` or `out` location, a return slot, and the receiver of an extension call headed `Object` or such an interface. The conversion (§8.6's box, or the reference conversion of an `IReadOnlySpan<TElement>` value to `Object` or another interface, implicit or by an `as` or a typed-pattern binding at such a type) is a compile error at the conversion site, the caller's check over the callee's declared signature, per instantiation.
2. **The two admitted positions.** The receiver of a member call (§8.6, §9.4: the box lives for the call and the member reads the payload at its own type) or of an extension call headed `IReadOnlySpan<TElement>`, and a position declared `IReadOnlySpan<TElement>`.
3. **`IReadOnlySpan<TElement>` values are read as holding borrows.** A value declared at that interface type is read as holding the borrows of the span it boxes, by declared type: the interface is not a value type and has no holds-borrows property (§3.6's row gains a pointer), but every rule that reads a value, parameter, local or substitution that holds borrows, or whose type is a value type that holds borrows, reads it as the span; a parameter so declared is parameter-sourced. It is the one reference type so read.
4. §8.6's sentence "The compiler enforces: a boxed borrow-bearing record value may not be stored in a location that could outlive the source of any borrow the record contains" stands verbatim (rule-corpus `s8_6_0004` quotes it); the admitted positions keep the unboxed value's rules.

### 5.2 Kernel classification (spec-change-process §9)

**Derivation: K2.3 + K2.4**, the same pair the set-erasing rule derives from — the declared type announces no source, so no rule reading the position can bound one, and the caller is the only party that sees the source. No consume position, borrow source or flag schedule changes; no axiom is extended. K4's third clause is satisfied by rejecting statically instead of recording a clause.

### 5.3 Body-locality (proposal 0105 §1)

**Local** at the conversion site, over the callee's declared signature; **carve-out, confinement (i)** for the type-parameter-substituted twin, which is checked at the instantiation that substitutes `Object` or the interface (the set-erasing rule's shape). Rule 3's classification is a declared-type fact every body reads locally.

### 5.4 Implementation sketch (`d708e13`)

- At every implicit conversion `isBoxingTargetType` admits (`src/sema/ExprTypecheck.cpp:4434`, applied at `:5009`), and at the reference conversion of an `IReadOnlySpan`-typed value to `Object`, test the source type with `isBorrowBearingRecordOrSpan` / `isBorrowBearingChoice` / the borrow-bearing-inline-array predicate (`src/common/OwnershipFacts.cpp:1757` and siblings) and the target with `isIReadOnlySpanType` (`:1788`); reject unless the conversion is a member-call receiver or the target is `IReadOnlySpan<TElement>`. For a target that is a type parameter, run the test at the instantiation, as `checkOwningElementInstantiations`'s worklist does.
- Extend the three carrier predicates' consumers (§9.7's bullets in `Ownership_Checks.cpp`: return, closure capture, collection copy, async parameter/result, `ref`/`out`) with the `IReadOnlySpan<TElement>` carrier the field-store leg already has (`:9697`), so a parameter-sourced interface value is rejected at a return and at an `Object` argument.
- Diagnostic: name the value's type, the position's declared type, and the remedies (`.ToString()` / an interpolation hole for rendering; a parameter at the value's type or at `IReadOnlySpan<TElement>`; a class implementing the interface).

- `xmod_imported_span_box_vtable_3358.local_single_module_control` (`tests/codegen/xmod_imported_span_box_vtable_3358_test.cpp:217`): `var o: Object := irs;`. New expectation: rejected at the initializer.

## 7. Self-critique (adversarial pass)

- *Is `IReadOnlySpan<TElement>`'s admission actually sound, or does it just move the hole?* The callee sees the declared type, and rule 3 makes that type hold borrows, so every bullet reads the parameter as the span: the field store is rejected (bullet 15; #4751 implements it), a return is rejected unless receiver-sourced (the return bullet; a parameter-sourced return is the `param_rooted_return_rejected_9_7_v301` shape), an escaping capture is rejected (the closure bullet), a copy into a field-held collection is rejected (the collection bullet), an `async` parameter is rejected (§30.1), and a conversion to `Object` is rule 1. The interface's members return `TElement` (a `T?` borrow at class `T`, parameter-sourced through the box), `int`, `bool` — no borrow-retaining handle. The remaining residual is the one §9.7 carries for every span: the source outliving the call, which the ordinary scope and freeze rules decide.
- *Can a receiver-position box escape through `this`?* (Critic, B1.) In a member of the value's own type, no: the body reads `this` at the record type, so §9.7's bullets and rule 1 apply to it (`Keep(this)` over `Keep(x: Object)` is rule 1). In an extension on `IReadOnlySpan<TElement>`, no: rule 3 reads `this` as the span. In an extension on `Object` or a user interface, yes — the body sees a plain reference and §28.3's clause 3 admits `k.Keep(this)` — so that receiver is a borrow-erasing position (rule 1). Measured reach: zero (no borrow-bearing record is the receiver of a user-interface- or `Object`-headed extension call in `tests/` or `docs/`; spans implement no interface but `IReadOnlySpan<TElement>`).
- *Does an `as` launder the box?* (Critic, B2.) `s as Object` over `s: IReadOnlySpan<int>` is legal (a reference operand, §12.7) and its result is a borrow of `s`'s source typed `Object?` (§17.4), which `Keep(…)` would then receive with no conversion at the call; rule 1 names the `as` and the typed-pattern binding as conversions. A value-typed operand at a reference `as` target is already a compile error (§12.7).
- *Does rule 1 reject the receiver of `span.ToString()` or `$"{span}"`?* No: a member-call receiver is not a borrow-erasing position (rule 2), as a function value as the receiver of an `Object` member is not a set-erasing one. Interpolation invokes `ToString` (§8.5, §18.5).
- *Does rule 1 reject `span is IReadOnlySpan<int>` or `o as Span<int>`?* No: §8.6 says a type-test operand and a pattern scrutinee are not boxing positions, and `as` on an `Object` reads a box out; `o` itself can hold no borrow-carrying box after this rule, so the span read out carries no borrow either.
- *Does rule 3 contradict §3.6?* (Critic, B3.) §3.6's row says "only a record, an inline array or a choice can hold borrows", and §35.4 defines the property for value types; rule 3 therefore does not give the interface the property — it states how every rule keyed on it reads a value declared at the interface — and §3.6's row points there.
- *Does rule 3 over-reject a `ReadOnlyStringSpan` at `IReadOnlySpan<char>`?* A field declared `IReadOnlySpan<char>` holding a boxed string span is rejected at the store, though the box carries no borrow. The classification is by declared type (§3.6 rule 1: a type is never classified by its contents), as `Object`-typed fields are borrow-carrying whatever they hold; the spelling is a `ReadOnlyStringSpan` field. No test or document stores one at the interface type.
- *Is the generic twin enforceable?* `b.Keep<Object>(span)` substitutes `Object` for `x: T` at the call; the caller sees the substituted signature, exactly as it sees `Holder<() -> int>`'s. `b.Keep<IReadOnlySpan<int>>(span)` is admitted at the call, and `Keep`'s `F := x` is §9.7's instance-field bullet read at that instantiation under #5629's per-instantiation reading, which requires the substituted type to hold borrows — rule 3 supplies that. A dispatched `Put<T>(x: T) F := x;` is rejected at its body already (#5629's dispatched clause).
- *Composition with #5629 and 0141:* unchanged verdicts; the laundering the L1 critique named is closed at the call. The #5629 decline of excluding borrow-bearing values at every dispatched call stands: a span at `i.Show<Span<int>>(span)` is a span-typed position after substitution, not a borrow-erasing one.
- *Composition with §28.14's scoped interface rule:* the sentence already rejects the box at a `scoped` interface parameter; the plain one is now rejected too, and `IReadOnlySpan<TElement>` is the exception at both (a `scoped IReadOnlySpan<int>` parameter admits the box, and the callee's store of it into the bounding object's field is bullet 15's rejection, so the admission is harmless).
- *Does the rule break `Equals(Object?)`?* A record's `=` and `Equals(T)` take the record type (§9.2); a direct `pair.Equals(otherPair)` at the `Object?` overload is rejected — the set-erasing rule's `x.Equals(f)` cost, with `Equals(T)` as the spelling.
- *Separate compilation:* the check reads the callee's declared signature and the argument's declared type, both in the caller's closure; no body is read. The witness of a borrow-bearing record's interface conformance is unaffected: the record still implements the interface, and its members are called on the record directly.
- *History narration:* the normative edits state the current rule only; the "canonical sanctioned use" wording is recast as the rule, not narrated.
