The static class carve-out (§11.7) is unchanged. **Declined:** the class-only reservation (a `rejected` row).
  - **§2.7 rule 1, §11.6 — a qualified chain resolves against the head type's members, declared or inherited ([#7077](https://github.com/s8lap/bezel-lang/issues/7077)).** `K.N` for `N` declared in a non-generic `B` and `class K: B` names the one type `B.N`, as a type and at a chain head. A nested type of a generic base gets no type-position spelling through a deriving type (`K.Node<int>` for `class K: Tree<int>` is not a type), while a chain head reaches its statics through that name (`K.Node<int>.Create()`). **Declined:** the declaring type's name as the only route; the deriving-type route in a type position for a generic base (two `rejected` rows).
  - **§11.6, §2.7 *Through nesting* — a name spelled like the enclosing type's type parameter is the §11.6 error whatever else holds the name ([#7116](https://github.com/s8lap/bezel-lang/issues/7116)).** The parameter, found at its type's link, ends the lookup for its name although it cannot be used there, as a local type's body does not reach past an enclosing method's local (§21.10); a same-named module type is named by qualification. The compiler already does this. **Declined:** the bare name passing over the parameter (a `rejected` row).
  - **§22.8 — `TypeName.F` in a generic type's static constructor is the current instantiation's ([#6903](https://github.com/s8lap/bezel-lang/issues/6903)).** Each instantiation's initialization is its own window, so `G<string>.F := e` inside `G<T>`'s static constructor is a compile error; otherwise `G<int>`'s initialization would write `G<string>`'s cell after it was read. The issue's second question is decided by §22.7 as written: a read of `G<string>.S` runs `G<string>`'s static constructor first, so the measured `0` is an implementation defect. **Declined:** any instantiation's cell (a `rejected` row).
  - **§22.8, the code-generation reference §7.8 — a member store into a `readonly` field is a write of the field for the placement rule, not for the single-assignment rule ([#6982](https://github.com/s8lap/bezel-lang/issues/6982)).** A member store (§9.7's term: an inline-array element, a record-typed field's settable member, a compound store or `++`/`--` on either, a `ref`/`out` binding of one) is admitted only where the whole-field store is: inside the window, through the spelling the whole-field store takes there, outside every lambda. It does not count toward the single-assignment rule, so element-wise filling in the constructor, in a loop included, stays admitted. **Declined:** an element store as an assignment for every rule; `readonly` as whole-field only (two `rejected` rows).
- **Patterns, flow and artifacts (lane `C3`; rulings).**
  - **§19.3 (*Type parameters as pattern types*), §12.7 — the per-instantiation identity test strips nullability from both sides ([#7034](https://github.com/s8lap/bezel-lang/issues/7034); [#5191](https://github.com/s8lap/bezel-lang/issues/5191) gains the row).** `var x: int` over `v: T` at `T = int?` binds `42` and declines `null`, as the non-generic `case n of var x: int` over `n: int?` does. **Declined:** the pattern never matching (a `rejected` row).
  - **§12.7 (*A nullable target*), §19.5, the code-generation reference §7.8 — a nullable target tests as its underlying type ([#7032](https://github.com/s8lap/bezel-lang/issues/7032)).** `x is T?` answers as `x is T`, `false` at `null`; `is not` is its negation and `as T?` is `as T`; the generic and non-generic forms agree; a pattern type written `T?` is the test `T` makes. The null test is `is null`. **Declined:** `null is T?` as `true`; a written nullable target as a compile error (two `rejected` rows).
  - **§21.3 (*A `while true` loop has no condition-false exit*), §7.4; rationale §18 — the point after `while true` is reached only through the `break`s that target it ([#6772](https://github.com/s8lap/bezel-lang/issues/6772)).** Definite assignment and §21.7's every-exit-path rule already read it so; flow narrowing now does too, each `break` a path carrying its own facts, in whatever iteration it runs. The rule is syntactic: the literal `true`, parenthesized or not. **Declined:** the opaque condition (a `rejected` row).
  - **§2.8.2 (*No restrictions beyond visibility*), Appendix C.13 — an artifact whose interface lacks a fact the consumer's rules need is rejected at import, whatever implementation or revision produced it ([#7281](https://github.com/s8lap/bezel-lang/issues/7281)).** The consumer names the artifact and never resolves or instantiates as if the fact were absent; a fact whose absence the rules themselves read (a contract-opaque artifact's) is not one. How a consumer recognises such an artifact is implementation-defined, and refusing every older artifact conforms under §2.8.5's recompile-the-world model. **Declined:** the stale interface as the user's problem (a `rejected` row).
- **Standard-library contracts (lane `E`; rulings).**

- **The fold-ins (lane `F`).**

The compiler already does both.
  - **§6.2 — a constant operand across signedness (clarification; surfaced by `C3` under #6887).** Where §5.1's table relates the operand types by no conversion and an operand is an integer constant, the constant converts to the other operand's type when its value fits; between two constants the unsuffixed literal is tried first, then a suffixed literal, then a named `const`, the left first between two of one kind (`5U + 10` is `uint`, `3U + -1` is `2`, `5UL + -1L` and `-1L + 5UL` are `long`); a pair neither of which fits (`4000000000U + -7`) is the error. The rule corpus already banked this reading.
  - **§19.3 — the binding a nullable pattern type introduces has the written type and enters its arm narrowed non-null (ruling; surfaced by `C3` under #7032).** It is not retyped: a binding at a pattern type parameter substituted to a nullable type keeps the written `T`.
