## 0. Summary

§27.6 forms `obj.Method` as an ordinary bound reference for any instance method, capturing a class- or interface-typed receiver by reference. §28.6 admits explicit disposal only as a call on a receiver the disposer owns, a site-announced kill whose explicitly-disposed post-state the analysis records (K3.9), and rejects a disposal through a borrow. §28.3 rejects a closure disposing a captured owned binding because "a closure-side consume would be a kill no body-local liveness can see". Nothing says what `d.Dispose` means. Read as §27.6's ordinary reference, its invocation is a disposal at a site no liveness sees, through the borrow the reference captured — the thing both other rules exist to prevent — and one character separates the rejected `lambda() => d.Dispose()` from the admitted `lambda() => d.Dispose`.

This proposal makes the formation a **compile error**: a method reference to `Dispose` or `DisposeAsync`, bound or type-qualified, over any receiver. Disposal is announced at its site, never handed out as a function value; the remedies are the call, the discard, or a lambda that disposes a value it receives as an `owned` parameter. Reach: zero accepted programs anywhere in the tree (two rejection rows keep their verdict); the staged #7025 lowering is reversed.

## 1. The problem

> Method references work for static methods, instance methods (the instance is captured at formation — by reference for class- or interface-typed receivers, **by copy** for value-shaped receivers […]), properties, and extension methods.
>
> — §27.6, v0.344

> Explicit disposal — `x.Dispose()`, the `x?.Dispose()` / `x!.Dispose()` spellings, a **direct `DisposeAsync()` call** in the same three spellings, awaited or not ([§28.12]), and the discard of a named owned binding ([§17.13]) — requires a receiver the disposer **owns** (derives: [K3.9]) […]. The calls and the discard are one consume-table row ([K3.9]): the same site-announced kill, the same explicitly-disposed post-state […]
>
> — §28.6 *Who may call `Dispose()`*, v0.344

> `Dispose()` or a direct `DisposeAsync()` call through a **borrow** is a compile error.
>
> — §28.6, v0.344

> a closure cannot consume, reassign, or dispose a captured owned binding (a closure-side consume would be a kill no body-local liveness can see — K5.5's decidability bound […])
>
> — §28.3 *Captured owned bindings*, v0.344

> The compiler additionally **must** emit a compile-time warning when a local variable is used (read, borrowed from, or consumed) after an explicit `Dispose()` or direct `DisposeAsync()` call […] on the same variable that dominates the use site on every path
>
> — §28.2, v0.344

§28.6's list of explicit-disposal forms is closed and does not include a method reference. §27.6 forms one anyway. The formed value is `() -> ()`; at `f()` the compiler sees a function-value call and can read neither §28.6 (whose receiver is it?) nor K3.9 (which binding is killed?) nor §28.2 (which variable is now disposed?). Measured (QUOTED, #7067): over an owning collection the thunk double-frees; over a class (#7025's lowering) the invocation performs logical disposal and the holder's release point frees — memory-safe, but the binding stays owned-live to the analysis, so a later `Take(move d)` hands out a disposed object with no diagnostic and a later `d.Dispose()` draws no repeat-dispose warning. Inside a closure the one-character pair is rejected / accepted (#7110).

## 2. Why this is a proposal

§27.6's sentence admits a bound reference over any instance method; `Dispose` is one. Rejecting its formation narrows that admission, and it reverses a shipped fix (#7025, staged) that chose the opposite. Process §2's design-change class applies.

## 3. Options

- **A — reject the formation, on every receiver (decided; #7067 interpretation 1, #7110 reading B).** `d.Dispose`, `oc.Dispose`, `D.Dispose`, `IDisposable.Dispose`, `x.DisposeAsync`, inside a closure or outside one: a compile error at the formation naming the call, the discard, and the `owned`-parameter lambda.
- **B — the ordinary value-capturing thunk** (#7067 interpretation 2). The reference holds a copy of the receiver reference; invoking it calls `Dispose()`.
- **C — a slot-capturing disposer** (#7067 interpretation 3). The reference's environment holds the holder's slot; invoking it disposes and empties the slot, so the scope-end pass sees nothing to dispose.
- **D — a reference bound to the scope-end obligation** (#7067 interpretation 4). Forming `oc.Dispose` makes the reference a "dispose at scope end" marker: the collection is disposed when the reference goes out of scope whether or not it is called.
- **E — class receivers only** (the staged #7025 lowering). Admit the reference over a class receiver, whose invocation performs logical disposal while the holder's release point reclaims; reject it over interface receivers (whose implementation path reclaims).

## 4. Evaluation

| | Soundness | Simplicity | Consistency | Migration reach |
|---|---|---|---|---|
| A | sound: every disposal is a call or a discard at a site the analysis reads | one sentence; removes a spelling | agrees with §28.6 (a disposal through a borrow is rejected), §28.3 (a closure may not dispose a captured owned binding) and K5.5; closes #7110's one-character gap | 0 accepted rows; 2 rejection rows keep their verdict; #7025's staged rows reverse |
| B | **unsound** on the owning-collection path (the measured double free); on the spec's own model (logical disposal only, the holder frees) memory-safe but a hidden kill: §28.2's mandatory warning cannot fire, a later transfer hands out a disposed object | the ordinary §27.6 thunk | contradicts §28.3's ground for closures | — |
| C | memory-safe; the kill is still invisible to liveness (a read of the binding after `f()` is undiagnosed) | a new closure kind that writes a holder's slot; a disposal obligation carried by a function value, which K1.6 says carries none | an exception to §28.3's closure rule for one member | — |
| D | memory-safe | a function value that disposes something when *it* dies — a disposal obligation on a runtime-managed value (K1.6), and `var f := oc.Dispose;` never called would dispose `oc` at `f`'s scope end, whichever is shorter | the reference would be a `using var` in disguise | — |
| E | memory-safe (idempotence + the holder's free), the hidden kill remains | the rule splits by receiver kind | §28.6 states its rule once for every receiver; an interface- and a class-typed binding would differ on a §27.6 formation | #7025's 2 staged rows |

A is the only option under which every disposal stays a site-announced kill. B is unsound in the implementation and a hidden kill in the model; C and D are new mechanisms for a spelling with no measured use; E keeps the hidden kill and splits the rule.

## 5. Decision

**Option A.** Stated in §27.6, cross-referenced from §28.6 and §28.3 *Captured owned bindings*, with an Appendix C.3 bullet.

- The rejected formations: a bound reference over a class- or interface-typed receiver (`d.Dispose`, `oc.Dispose`, `x.DisposeAsync`), formed anywhere — in a body over an owned local or `owned` parameter, over a borrow, over a field, inside a closure over a captured binding; a type-qualified (unbound) reference (`D.Dispose`, `IDisposable.Dispose`, `IAsyncDisposable.DisposeAsync`), whose invocation would dispose its plain-parameter argument, a borrow.
- Where the receiver's type has no `Dispose` member at all (proposal 0200: `Object`, a runtime-managed value, a non-`IDisposable` interface), the no-member diagnostic applies instead; both are type-level errors at the formation, so no formed value ever exists.
- The remedies the diagnostic names: `d.Dispose();` at the site; `_ := d;`; `using var`; or, for a callback that must dispose, `lambda(owned x: D) => x.Dispose()` invoked with `move d` (§28.9's "a callback that must genuinely consume a value takes an `owned` parameter"; §28.6 admits disposal of an `owned` parameter; §28.1 admits `owned` lambda parameters).
- Kernel: a derivation — K3.9 (explicit disposal is a site-announced kill with a recorded post-state) and K5.5 (a kill no body-local liveness can see is outside the decidability bound). Body-locality: local (the formation site).

## 9. Declined alternatives (one `declined-at-proposal` row each)

- **Option B, the ordinary value-capturing thunk** (#7067 interpretation 2). Unsound in the implementation's owning-collection path, which reclaims at the call (the measured double free); under the spec's logical-disposal model still a kill no liveness records, the hidden consume §28.3 rejects for a closure. Reopening bar: none stated.
- **Options C and D, a slot-capturing disposer or a reference bound to the scope-end obligation** (#7067 interpretations 3 and 4). Each is a new closure kind — writing a holder's slot, or carrying a disposal obligation a function value never carries (K1.6) — for a spelling with zero measured uses; the kill stays invisible to liveness. Reopening bar: a measured program whose deferred disposal no `owned`-parameter lambda or `using var` expresses.
- **Option E, class receivers only** (the staged #7025 lowering). Memory-safe under idempotence and the holder's free, but the binding stays owned-live to the analysis after the invocation — §28.2's mandatory straight-line warning cannot fire and a later transfer hands out a disposed object — and the rule would split by receiver kind what §28.6 states once for every receiver. Reopening bar: none stated.

## 11. Self-critique (adversarial pass)

- **Is a rejection the simplest sound option?** Yes. Every admitting option either hides a kill from the analysis or adds a closure kind; the rejection removes a spelling that has one sound replacement (`lambda(owned x: D) => x.Dispose()`) and two direct ones.
- **Does it reject anything the stdlib relies on?** No stdlib member is documented to take a `Dispose` reference; no stdlib example forms one. `Subscription`, `CancellationToken.Register` and the task continuations take lambdas or unrelated references.
- **Neighbouring cells.** A method reference to a *user* method that disposes its `owned` parameter (`Pool.Return` with `owned` slot) is an ordinary reference whose function type carries the `owned` slot: admitted, unchanged — the kill is announced at the `move` argument of the invocation. A method reference to `Close()` or any non-`Dispose` member on an owned receiver: an ordinary bound reference borrowing the receiver, admitted, subject to §28.3's source set. A `DisposeAsync` override's chained `base.DisposeAsync()`: a call, not a reference, unchanged (§28.6's exemption). `await using`'s discharge: not a reference.
- **Type-qualified references.** `D.Dispose` yields `(D) -> ()`; its invocation `g(d)` passes `d` to a plain slot, a borrow, so the disposal would be through a borrow (§28.6). Rejected at the formation for the same reason; stated in the paragraph.
- **Inside closures (#7110).** The formation inside a lambda body is the same formation; rejected by the same sentence, with §28.3's cross-reference so a reader of the closure rule finds it.
- **History narration.** The normative text states the rule; the story (the #7025 lowering, the measured double free) is in rationale §4.2's dated paragraph and the changelog.
