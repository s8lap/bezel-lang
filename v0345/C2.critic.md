## Findings and fixes

1. **#6982: "through `this`" wrongly rejected a static field (fixed).** The new member-store sentence admitted a member store "only inside the window, through `this`, outside every lambda body". A `static readonly` field has no `this`. Its whole-field store is spelled with the bare name or `TypeName.F` in the static constructor (§22.8). As written, the sentence would reject filling a `static readonly` *non-owning* inline array element by element in its own static constructor. That contradicts the code-generation-reference blockquote's own "admitted only where the whole-field store is". 0 in-tree sites (MEASURED: the static-readonly inline-array fields in `inline_array_unit_element_3712_test.cpp` and `inline_array_interface_record_static_init_4467_test.cpp` have no element stores), but the text was unsound in wording. New text: "through the spelling the whole-field store takes there (an lvalue chain rooted at `this` for an instance field; the bare name or `TypeName.F` in the static constructor for a `static readonly` one)". The code-generation reference §7.8 blockquote got the matching change. The `C2.md` decision, changelog bullet and ruling comment are updated too.

2. **#7121 / 0202: "in an expression" left qualified patterns in neither row (fixed).** The lane narrowed the *Chain head* row to "in an expression, a name followed by `.`". A qualified pattern without an argument list (`case Color.Red`, `case System.IO.Stream`) is not an expression. It is also not a type position: A.7's comment says the pattern "is a constant pattern … [or] a type-test pattern" decided "by name resolution". So after the edit that head had no row. The row now keeps every name followed by `.` *except* the head of a qualified name in a type position, and says explicitly that such a pattern stays a chain head. The "not reordered" replacement now reads "last at a chain head", not "at an expression chain head". Proposal §5 point 2, §10 and the `C2.md` ruling comment are updated to match.
   - What remains is a visible mismatch, not a silent one. Take one match over a nested choice `C` that an imported `C` shadows. `case C.Circle(var r)` is a destructuring head, which is a type position, so it finds the nested `C`. `case C.Empty` is a chain head, so it finds the import's `C`. The second fails to type-check against the scrutinee, so the user sees an error; the remedies are §19.8's prefix omission or `Outer<int>.C.Empty`. This is recorded in the proposal's self-critique.

3. **0202: the Warning row still told the user to qualify with `this.` (fixed).** After the lane's edit the row fires for a nested type, but its effect cell still said "qualify `this.` to reach the member", which does not reach a nested type. A new edit, `C2-7121-spec-2.7-warning-row-remedy`, changes the cell to "qualify `this.` to reach an instance member, the enclosing type's name a static or a nested type (the paragraph below)". Proposal §10 lists it.

4. **0202: the proposal misplaced aliases in its self-critique (fixed in the proposal).** It said "An alias-qualified head is rule 2's." In fact import aliases are the last step of rule 1. So under 0202, a nested type also outranks a same-named *alias* at a qualified head in a type position: the same change of meaning as the import case, with 0 sites. It is moot wherever §2.2's alias-collision rule ("a type declared in the file's module") already forbids such an alias. The bullet is corrected. One more point on the "not reordered" sentence: it says the warning row fires where an import or module declaration wins. That is true for those two. An alias at a chain head resolves to a module, not a type, so no warning fires for it. That gap already existed for every member (see question Q2 below) and the lane's text does not claim otherwise.

5. **#6764: §35.1 still listed three reserved case names (fixed).** §35.1 says "`Equals`, `GetHashCode` and `ToString` are reserved against case names on every classification", and it is where a reader looks up case names. The lane's §9.2 sentence now also reserves `GetType` and `ReferenceEquals` against choice cases, so §35.1's list was incomplete. A new edit, `C2-6764-spec-35.1`, adds one sentence after "a consequence its recorded flip list does not carry." The anchor is unique and no other lane touches it. The `C2.md` table row, changelog bullet and ruling comment name §35.1.

6. **#6982: the lane's "to file" question on rule 4(h) is folded (decided by the current text).** §22.12 rule 4(h) is unqualified: "a slot store or a `move arr[j]` through it is a compile error naming K9.4 — … no per-method window can cover it". So the static constructor cannot fill those slots either, and the lane's "additionally fixed at initialization" already says so. Which diagnostic is reported is the implementation's choice under Appendix D, and the #6982 tracker already keeps K9.4 (`s22_12_0048`'s needle). The `C2.md` *New questions* section now lists it as folded item 5. The other "to file" item, #6903's Q2 (does a generic instantiation's static constructor run before first use), is a compiler tracker, not a spec question, and stays as written.

## Residual questions to file

- **Q1. Title:** "§2.7 rule 1 / *Through nesting*: where does a type's own type parameter rank at a chain head?"
  **Body:** Rule 1 places a type's type parameter "at that type's own position in the *Through nesting* chain", and *Through nesting* visits each type "at the rank the table gives its members", which at a chain head is "last, after aliases". Read literally, in `class Box<T> where T: INumber<T>` with a module-level type `T`, the chain head `T.Zero()` resolves to the module's `T`, not the parameter. Inside a nested type, v0.345's #7116 sentence ("a compile error naming this rule, whatever else holds the name … a same-named module declaration or import is not reached by the bare name") then overstates the case at a chain head, where module declarations rank before the link. The compiler walks scopes, which puts type parameters before module types at every head (`ExprTC::lookupName`, `src/sema/ExprTypecheck.cpp:14245`). Recommendation: a type parameter is not demoted at a chain head (it is not a member), so the #7116 sentence holds as written. One clause in rule 1. 0 in-tree sites. Label `spec-question`.
- **Q2 (optional, low priority). Title:** "§2.7: an import alias at a chain head silently shadows a same-named enclosing member".
  **Body:** Aliases rank before the chain-head member fallback. A head that resolves to an alias resolves to a module, so the Warning row ("chain head resolves to a type") does not fire. A member `Tx` and an alias `Tx` give `Tx.M()` the module's `M` with no warning. Check first whether §2.2's alias-collision list ("a type declared in the file's module") already covers nested types; if it does, only the member case remains. This is not 0202's issue. Label `spec-question`.
