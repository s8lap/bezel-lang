## 1. #7276 — does `string` have a `Dispose()` member? (with #7273, and the §28 table's function-value row)

**Decision.** No. `Dispose()` is a member of class types, of the interfaces that are or extend `IDisposable` (the set `where T: IDisposable` admits) and of an interface declaring `method Dispose();` itself (§28.2); `DisposeAsync()` of the types that declare or inherit it; neither of anything else: `string`, `Type`, boxed values and function values are not classes (§14.2, now §8.7 too) and have no member; `s.Dispose()`, `typeof(T).Dispose()`, `x.GetType().Dispose()` and `c.Dispose()` on a function value are compile errors at the type level, with the reason `Object` already gets (#6990), and the discharge points — `using var`, the discard, the `for` source binding, scope end — stay admitted over such values and dispose nothing. The owner's test (calling `Dispose` should mark the object disposed and stop operations on it) rules out a member that does nothing; marking a string disposed is unsound (shared by assignment, interned, crosses domains as a shared reference). Even with a member the call could not be written: §28.6 requires an owned receiver and a runtime-managed value is never owned (K1.6). The triage's recommendation (option 3) is taken unchanged; `string` is stated not to be a class, §3.5's "classes — which `string` is —" reworded and stdlib §9.6's "treated as both a primitive and a class" replaced with "the index's declaration form".

## 3. #7067 and #7110 — a method reference to `Dispose`; the reference form inside a closure

**Decision.** A method reference naming `Dispose` or `DisposeAsync` — bound (`d.Dispose`, `oc.Dispose`, over a class- or interface-typed receiver, inside a closure or outside one) or type-qualified (`D.Dispose`, `IDisposable.Dispose`) — is a compile error at its formation, on every receiver (#7067 interpretation 1; #7110 reading B). Explicit disposal is a site-announced kill of an owned binding whose post-state the analysis records (K3.9); invoked through a function value it would happen at a site no liveness can see, through the borrow the reference captured — the ground on which §28.3 already rejects `lambda() => d.Dispose()` over a captured owned `d` and §28.6 rejects a disposal through a borrow. The remedies: the call, the discard, or `lambda(owned x: D) => x.Dispose()` invoked with `move d`. Where the receiver's type has no `Dispose` member (0200), the no-member diagnostic precedes. The triage's recommendation is taken unchanged; the staged #7025 fix (a thunk over a class receiver) is reversed.

**Class: design change → proposal 0201.** §27.6 admits a bound reference over any instance method; rejecting `Dispose`'s narrows it and reverses a staged fix.

**Proposal.** `C1-0201.proposal.md`. Options **A (reject on every receiver, decided)**, B (the value-capturing thunk), C (a slot-capturing disposer), D (a reference bound to the scope-end obligation), E (class receivers only — the staged #7025 lowering). Three `declined-at-proposal` rows (B; C+D; E).
