# Lane C1 critic: the disposal surface (v0.345)

**Verdict: ACCEPT-WITH-FIXES.** Both decisions hold up: 0200 (no `Dispose()` member outside the disposable types) and 0201 (no method reference to `Dispose`/`DisposeAsync`). Each is the simplest sound option, and each is correctly classed as a design change. The #7068 deviation from the issue's recommendation is well grounded. It matches the triage's recommendation (`scratch/rule1024/R1.json` #7068: "the declared-surface rule … rejects both spellings and flips the ten shipped call-form rows"), and 0201 rejects the issue's other half, the bare reference, on separate grounds.

The 0200 rule text as drafted had three defects. It stripped `Dispose` from interfaces that declare it themselves. It paired `DisposeAsync` with every class. Its generic-code half was wrong: it claimed no generic body changes, but 4 gtest rows and the stdlib's own `OwningArray<T>` reference implementation stop compiling. It also opened one neighbouring cell (extension members). All of these are fixed in the lane's files.

Originals are kept in `scratch/v0345/C1crit/*.orig`. `C1work/build.py` was patched by `C1crit/patch_build.py` and rebuilt, and now produces 24 edits.

## Findings

### F1 (major): the rule removed `Dispose` from interfaces that declare it (fixed)
The draft §8.7 said `Dispose()` is a member "of a class type, of an interface type that is or extends `IDisposable` …, and of nothing else". That contradicts §28.2 v0.344: "**Interfaces are unaffected** … an interface may itself declare `method Dispose();` … a user interface declaring it directly is admitted on the same ground". It also contradicts Appendix C ("an interface may declare `Dispose()` itself") and the banked case `s28_2_0010` (`interface ICloseable method Dispose(); method Flush(); end`). Under the draft, a value of type `ICloseable` would have no member its own type declares, which breaks the proposal's own principle, "a value exposes the members its type declares".

**Fix:** the member is kept on an interface that declares `method Dispose();` itself. This is updated in §8.7, the §28 table's interface row, §28.2's restatement, Appendix C.3, the code-generation reference's blockquote, rationale §5.2, the proposal (§0, §3, §5, §10, §11) and C1.md, including the #7276 and #7068 ruling comments.

### F2 (major): `DisposeAsync` was attributed to every class (fixed)
"`Dispose()` and `DisposeAsync()` are members of a class type, of an interface type that is or extends `IDisposable` or `IAsyncDisposable`" reads as giving `DisposeAsync()` to every class. It also gives `Dispose()` to every extender of `IAsyncDisposable` purely through the pairing. That contradicts §28.12: "classes **may** implement `IAsyncDisposable`".

**Fix:** `DisposeAsync()` is "a member only of a type that declares or inherits it — `IAsyncDisposable`, the interfaces extending it, a class implementing it (§28.12)". The interface half of `Dispose()` is now worded on "the interfaces `where T: IDisposable` admits (§14.2 rule 3 and its worked example)", so the member surface and the bound agree by construction. F7 explains why that wording was chosen.

### F3 (major): `where T: class` bodies are newly rejected, and the lane missed it (fixed)
The proposal said "a `where T: class` body never had it (§14.2's worked example)" and "No generic idiom changes". No v0.344 sentence says what a `where T: class` body may call. The compiler admits `t.Dispose()` under `where T: class` and under any interface bound: `src/sema/ExprTypecheck_Calls.cpp:9925–9969`, fix #1293's `scanRefConstraint`, whose comment reads "a `class`, interface, or class-type constraint makes the call legal". Under 0200 that body is ill-formed, because `class` admits `string`, function types and interfaces without the member.

I re-measured with `C1crit/scan_generic2.py`, a type-parameter-typed receiver read against the program's own `where` clauses, and checked the hits by hand. **4 gtest rows flip accept → reject:**
- `generic_owned_param_disposal_1483.explicit_dispose_in_generic_no_double_free`
- `codegen_generic_owned_field.reassigned_owned_type_param_field_disposed_once_991`
- `codegen_generic_owned_field.two_swaps_owned_type_param_field_991`
- `xmod_extension_type_param_scope_3643.local_extension_ref_constrained_param_admits_dispose_spec_28_2`

**The stdlib's normative `OwningArray<T>` reference implementation** (stdlib §4.5, `where T: class`) calls `item!.Dispose();` in `Clear`. It would no longer compile. Its doc-corpus extract, `tests/conformance/cases/stdlib_0051.bzl`, is `skip`, which is why no corpus verdict moved.

No member-less-interface-bound body disposes anything, in `tests/` or in the docs.

**Fixes:**
- §8.7's generic sentence now says which constraints put the member on `T`'s surface: `where T: IDisposable`, an interface bound extending it, or a class bound. It names `where T: class` as excluded and gives the remedies.
- Appendix C.3 bullet extended to match.
- A code-generation reference *Looks right, is rejected* line added: `method Drop<T>(owned x: T) where T: class  x.Dispose(); end`.
- **New edit `C1-7276-stdlib-4.5-reference-impl-discard`:** `item!.Dispose();` becomes `_ := item;`. This is the discard of a named owned `T?` binding (§17.13 *Discard of a named owned binding*), which disposes the non-null value by dispatch, so the effect is the same.
- Proposal §5/§6/§7/§8/§11 and C1.md updated with the migration rows and re-spellings. The rows re-cut to drop-on-overwrite (`_v := b;`), `_ := t;`, and `where T: IDisposable` for the #3643 extension-scope row. The tracker gains a step that narrows the #1293 gate.

### F4 (moderate): a neighbouring cell opened by the change, extension members (folded)
Once `string` and member-less interfaces lose the member, an extension `method Dispose()` on them would resolve, because §26.5 rule 1 blocks only by declared name. At v0.344 the string's stated no-op member blocked it. Such an extension looks like a disposal it cannot perform, since an extension's receiver is a borrow it may not dispose (§26.7). Reach is 0: no extension anywhere in `tests/`, the corpora or `docs/` declares either name.

**Folded (small, follows from "of nothing else"):** new edit `C1-7276-spec-26.3-no-extension-dispose`, a §26.3 restriction bullet. §8.7 and Appendix C.3 cross-reference it. Proposal 0200 §5 has an *Extensions* bullet and a §8 corpus case.

### F5 (minor): the README row's numbers (fixed)
The row said "17 gtest rows … zero corpus, lit, doc or guide programs" and "17 rows re-pinned". The proposal and md say 19 rows plus one lit re-cut. It now says 23 gtest rows (19 + 4) and one lit row, and names the stdlib reference-implementation re-spelling.

### F6 (minor): matrix cell not listed (fixed in the proposal)
Disposal matrix R10/C9 (`v0.336.json` cell 99) cites "§28.2 (summary: runtime-managed `Dispose()` is a no-op)" and notes "an explicit `Dispose()` on one is the no-op and no use-after question arises". Its `exempt` verdict stands on a stronger ground, and the next matrix run should re-quote it. Added to proposal 0200 §6. R10/C3 and R10/C12 were already listed and I checked them; neither verdict moves.

### F7 (seam, to file): does `IAsyncDisposable` extend `IDisposable`?
§14.2's worked example and stdlib §2.10 list `IAsyncDisposable` and `IAsyncEnumerator<T>` among the interfaces conforming to `IDisposable`. The declarations (spec §28.12, stdlib §2.10) list no extension, and rule 3 reads the extension chain. This is pre-existing, but 0200 makes it load-bearing.

The rule is now worded on "the interfaces `where T: IDisposable` admits", so the member surface follows whichever way the seam is settled, and no measured program depends on it. I found no `IAsyncDisposable`/`IAsyncEnumerator` receiver making an explicit sync `Dispose()` call in `tests/` or the docs. A ready-to-file issue is in C1.md, *To file* #2. It also notes that §9.7 does not forbid a record from implementing `IAsyncDisposable`.
