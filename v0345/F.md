## Item 1 — `String.From(buffer, start, length)` and `string.AsSpan(start[, length])` have no stated window bound (E.critic.md, residual question)

**Decision.** Both members take the library's one bound. `AsSpan(start)` and `AsSpan(start, length)` are §4.14's eager factories — "The `AsSpan`/`AsReadOnlySpan` factories validate eagerly" (stdlib §4.14, *Construction patterns*), as `Array<T>.AsSpan` and `OwningBuffer<T>.AsSpan` already state in so many words ("`IndexOutOfRangeException` if `start` or `length` is out of range against the array's `Count`", §4.4 :1736; §4.14 :2641) — so the window is checked at the call against `Length` (`start` in `0..Length`, `length` ≥ 0, `start + length` ≤ `Length`) and raises `IndexOutOfRangeException`, as `AsSpan(r)` and the slice `s[r]` do (spec §4.6); `start = Length` is the empty span. `From(buffer, start, length)` reads the same window over the array's `Count` and raises `IndexOutOfRangeException` outside it — stdlib §1's *Window parameters* row names it as the convention's own example, and the §7.1 `Stream` window states the rule "like every other bounds rule in this library". §4.14's no-eager-check rule is for the direct span constructors and the `(start, length)` `Slice`, not for a factory, so it does not reach `string.AsSpan`. The E critic's open question ("checks eagerly, as `AsSpan(r)` does, or follows §4.14's deferred per-access check") is answered: eagerly.

**Class.** Clarification: every sentence states a rule the library already states for the sibling factories and the window convention; no verdict moves.

**Edit.** `F-1-stdlib-9.6-aspan-from-window`: one passage appended to §9.6's `Length and s[i]` paragraph, after its `AsSpan()` sentence.

**Compiler facts.** `src/codegen/LlvmBackend_String.cpp:1448–1518` lowers `AsSpan(start)` and `AsSpan(start, length)` with eager guards (`start < 0 || start > count`, then `len < 0 || len > count − start`) raising `IndexOutOfRangeException`, and `AsSpan(r)` the same way; its comment reads "Bounds-checks mirror `Array<T>.AsSpan` (IndexOutOfRangeException)". `src/codegen/LlvmBackend_Calls2.cpp:1116–1158` lowers the three-argument `From` with the guard "start in [0, n]; count >= 0; start + count <= n" raising `IndexOutOfRangeException`. The text matches the compiler. **No tracker.**

**Reach.** Zero flips. `tests/` uses of `string.AsSpan(start[, length])` are all in range (`"abcdef".AsSpan(1, 3)`, `"hello".AsSpan(1, 3)`, `"hello world".AsSpan(6, 5)`, `"ab 42 cd".AsSpan(3, 2)`, `src.AsSpan(0)`); no test or corpus case pins an out-of-range `AsSpan` or `From` fault; the doc corpus's `stdlib_0147` (the §9.6 fence) is `skip:signature`. Guides: no `From(buffer, …)` and no `AsSpan` with arguments.

**Corpus gap (to write after landing).** `l9_6`: `"abc".AsSpan(1, 3)` → raises `IndexOutOfRangeException`; `"abc".AsSpan(3)` → `""`-equivalent empty span (`IsEmpty`); `String.From(['a','b','c'], 1, 3)` → raises; `String.From(arr, arr.Count, 0)` → `""`.

**Changelog bullet (draft).**
- **Stdlib §9.6 — `string.AsSpan(start)`, `AsSpan(start, length)` and `String.From(buffer, start, length)` state their window bound (clarification; surfaced by lane E's critic under [#7161](https://github.com/s8lap/bezel-lang/issues/7161)).** The `AsSpan` overloads are §4.14's eager factories, as every `AsSpan` in the library is: the window is checked at the call against `Length` and raises `IndexOutOfRangeException` outside `0..Length`, `start = Length` being the empty span; `From` reads the same window over the array's `Count` under §1's *Window parameters* convention and the §7.1 window's rule. ## Item 2 — §6.2 should state the equal-width signed/unsigned constant rule (C3.md "to file" 1, as corrected by C3.critic.md)

**Decision.** §6.2 says "the smaller-range operand is implicitly promoted to the larger type" and "if no implicit conversion exists between the operand types … compile error", which decides nothing for `int` beside `uint` or `long` beside `ulong` (neither range contains the other, and §5.1's table relates them by no conversion). The rule corpus banks the reading the compiler implements (`s6_2_0003`, `s6_2_0004`, `s5_1_0128`–`0131`, all `pass`): a constant operand converts to the other operand's type by §5.1's constant narrowing when its value fits, and the operation runs at that type (`u + 1`, `1 + u` → `uint`); between two constants the unsuffixed literal converts (`1U + 2`, `2 * 3UL`, `5U + 10` → `uint`, `ulong`, `uint`); where it does not fit, the suffixed constant converts to `int` instead when its value fits (`3U + -1` is the `int` `2`); a pair neither of which fits the other's type (`4000000000U + -7`) is the compile error. A named `const` converts on the same terms, by its value. **Critic fix:** between two constants the order of trial is stated whole — the unsuffixed literal, then a suffixed literal, then a named `const`, the left operand first between two of one kind, the first that fits converting — so two suffixed literals (`5UL + -1L`, `-1L + 5UL`: both `long`) and a literal that does not fit beside a named constant that does are decided too (the drafted text left both open). One paragraph states this where a reader looks.

**Why the unsuffixed literal is the one that converts.** It is the one spelling that states no width (§4.2's suffix discipline, "no accidental width"); a suffixed constant was written to state one. This is what the compiler does (`ExprTypecheck_Exprs.cpp:7483–7500`: "it is the unsuffixed `int` literal that is 'untyped' and adopts the other's type … Only when the `int` literal does not fit (`3U + -1`) does the other literal adopt `int` instead") and what `uint_literal_left_operand_6984_test.cpp` `two_literals_unsuffixed_adopts_spec_5_1` pins (`3UL * 2` → `6` as `ulong`; `1 + 18000000000000000000UL`; `3U + -1` → `2`). C3's §16.1 edit relies on exactly this answer for `5U..10` (`Range<uint>`) and `-5..10U` (`Range<int>`), and its DECLINED row for the "tie is an error" sub-recommendation cites §6.2 for it, so the paragraph is now the sentence that row cites.

**Class.** Clarification (the banked reading, confirmed; no verdict moves). The paragraph is scoped to operand pairs §5.1's table relates by no conversion in either direction with a constant operand, so it says nothing new about `short` beside `ushort` or `byte` beside `sbyte` with two non-constants (not opened here).

**Edit.** `F-2-spec-6.2-constant-across-signedness`: one paragraph after §6.2's last sentence.

**Compiler facts.** `src/sema/ExprTypecheck_Exprs.cpp:7455–7527` (the `adopt` lambda, the two-literal order, the named-constant search). Matches on every banked and pinned row. **Three corners diverge (critic, read from the code; unprobed):** (a) two suffixed literals: the left one adopts with no fallback, so `-1L + 5UL` is rejected while `5UL + -1L` is `long`; (b) a literal beside a named constant: the literal adopts with no fallback, so `-1 + U` over `const U: uint := 5` is rejected though `U` fits `int`; (c) a named constant wider than the type it would adopt (`sb + K`, `sb: sbyte`, `const K: ulong := 1`) keeps the §6.2 rejection ("deferred", `:7429–7434`). **Tracker to file (`spec-tracking`).** Title: "§6.2 (v0.345): a constant operand across signedness — three corners of the constant search reject what the rule admits". ## Item 3 — the type of the binding a nullable pattern type introduces (C3.md "to file" 2)

**Decision.** The binding has the pattern's **written** type. Where that type is nullable (`var s: string?` — under C3's §19.5 edit the test the pattern `string` makes, matching non-null values only), the binding enters the arm's guard and body narrowed non-null, as a local §7.4 narrows after a test it has passed, so `s.Length` needs no `!`, and §7.4's invalidating forms (a nullable store, a `ref`/`out` argument, a mutable capture) apply to it as to any local (critic fix: the draft said "throughout", which §7.4's invalidation contradicts). The binding is **not retyped** to `string`. The decisive ground is the generic case: `var x: T` over a scrutinee at `T = int?` must bind an `x` of type `T` — the body is checked once (§3.6 rule 2) and `T` is the only type it can give the binding — so the non-generic form does the same, and the narrowing supplies the usability. C3's recommendation ("the binding takes the written type, narrowed non-null in the arm … no retyping") is taken. A nullable-typed binding is a shape with no in-tree use, so this is also the cheapest answer.

**Class.** Ruling (the text was silent).

**Edit.** `F-3-spec-19.3-nullable-binding-type`: one passage appended to *Type patterns with binding*.

**Compiler facts.** `src/sema/ExprTypecheck.cpp:28449–28452` gives the binding its written type ("Explicit type annotation wins; otherwise inherit scrutinee type"), so `s` is `string?` as ruled; whether the arm narrows it non-null is unmeasured — `PendingArmTypeFact` (`:16375–16400`) narrows the *scrutinee* carrier, and no test reads a member of a nullable-typed pattern binding. **Tracker to file (`spec-tracking`).** Title: "§19.3 (v0.345): a typed pattern binding whose written type is nullable (`var s: string?`) is narrowed non-null in its arm". The generic twin `var x: T` at `T = int?` already keeps type `T`.

## Item 5 — overload ranking of a target-typed range literal (C3.critic.md; C3.md "to file" 4)

**Decision.** §22.6's constant paragraph already grades a compile-time integer constant at its own static type (exact at `Log(int)`, converting where §5.1's narrowing reaches a candidate, graded alike everywhere for a target-typed constant with no type of its own). A range literal argument is graded the same way: it is read at the `Range<T>` its endpoints give it on their own (0204's §16.1 endpoint rule — `Range<int>` for `0..10`), exact at a parameter of that type and converting at every other `Range<T>` parameter its target typing reaches, co-equal with every other conversion, so `M(0..10)` against `M(r: Range<int>)` beside `M(r: Range<long>)` selects the first; a literal its endpoints give no type (`0..3_000_000_000`, one endpoint having no standalone type, §4.2) converts at every `Range<T>` candidate whose `T` holds both endpoints, so `M(Range<long>)` beside `M(Range<ulong>)` is ambiguous, remedied by a suffix — the mirror of `f(3_000_000_000)`. C3's recommendation (one clause mirroring §5.1's) is taken; the clause is placed in §22.6, where the ranking lives and where the mirrored constant sentence is, rather than in §16.1 (C3's new paragraph), which F does not edit.

**Class.** Ruling (silence; the analogy §22.6 already draws for constants).

**Edit.** `F-5-spec-22.6-range-literal-rank`: one passage appended to §22.6's *The argument's static type* paragraph.

**Compiler facts.** The compiler types a range literal from its low endpoint today (0204's tracker, `ExprTypecheck_Exprs.cpp:15850`) and has no target typing to rank; the ranking lands with 0204's implementation. **Tracker:** an item for 0204's tracker — "at an overloaded call a range literal argument is exact at the `Range<T>` its endpoints' §6.2 common type gives, converting at every other `Range<T>` candidate; rows: `M(Range<int>)`/`M(Range<long>)` on `M(0..10)` → the first; `M(Range<long>)`/`M(Range<ulong>)` on `M(0..3_000_000_000)` → ambiguous".

**Reach.** Zero sites: the standard library declares no `Range` parameter at a type other than `Range<int>` (22 `r: Range<int>` parameters; no `Range<long>`/`Range<uint>`/`Range<ulong>`/`Range<byte>`/`Range<char>` parameter), and no test declares an overload pair differing only in a `Range<T>` parameter's `T` (the `Range<long>`/`Range<char>` hits in `tests/` are locals, returns and `default` operands).

The first half is the rule: *Type-parameter bounds* admits a substitution "by these three relations only" — identical, a class derived from a class substitution (§12), a type conforming to an interface substitution — and `string`, interfaces and function types are none of these at `U := Object` (they are not classes, §8.1; §12's derivation is a class relation). ## Item 9 — does `IAsyncDisposable` extend `IDisposable`? (C1.critic.md F7; C1.md "To file" 2)
